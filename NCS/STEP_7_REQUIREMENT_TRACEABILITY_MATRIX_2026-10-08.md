## Purpose and branch discipline

This matrix is the first continuation action required by `NCS/NCS_NEXT_CHAT_HANDOFF_2026-10-08.md`. It maps existing requirements to their current canonical owner and evidence; it does not create a new architecture, contract, root, policy, or runtime claim.

The repository currently has relevant material on both `ncs-clean-architecture` and `main`. References below name their branch deliberately. This document does not imply that the branches are merged, synchronized, or equivalent. Do not silently copy or merge main-only files into the clean branch.

Status meanings:
- **COVERED** — the semantic requirement and canonical owner are explicit; this does not imply runtime enforcement.
- **PARTIAL** — some required semantics/evidence are explicit, but a material part remains unresolved or unproven.
- **GAP** — the recovered repository does not define a required rule or mechanism sufficiently.
- **UNKNOWN** — the requirement depends on deployment/environment facts or evidence not yet established.

## Consolidated result

1. **No missing semantic document justifies creating another generic trust abstraction.** Existing contracts and research cover many requirements at the semantic level.
2. **The decisive gaps are deployment/evidence gaps, not merely missing field names:** independent root recognition, concrete effect boundaries and bypass closure, offline currentness/revocation bounds, predecessor cutoff, and real recovery/succession independence.
3. The authority decision is closed normatively: Kevin is initial authority; daughter is a future intended successor only. The mechanism and succession conditions remain unresolved and must not be invented.
4. The matrix does not establish any runtime guarantee and does not authorize implementation, root selection, commissioning, enrollment, rotation, or recovery execution.
5. Branch difference remains explicit: the trust-root contract and trust-role map cited here are currently verified on `main`; the authority/succession decisions and this matrix are on `ncs-clean-architecture`. This is traceability across refs, not a merge.

## Next exact action

Use this matrix to build the **claim-relative deployment / protected-effect / failure-domain inventory**. Keep the scope bounded to real intended Nexo capabilities (e.g., owner/Constitution changes, device control, credential/root changes, recovery, and irreversible external effects), and mark any capability not yet selected as UNKNOWN rather than assuming a deployment.

For each effect class record:
- exact protected claim/effect and target;
- last component that can cause the effect and possible bypass paths;
- constitutional/policy authority required;
- independent root/recognition dependencies;
- shared software, hardware, provider, admin, update, network, clock, storage, and evidence dependencies;
- online/offline assumptions and how currentness/revocation are known;
- recovery and predecessor-fencing behavior;
- what is directly verified, assumed, or still unknown.

Only after this inventory should the candidate recognition families be compared. Do not select a root family, device, vendor, authenticator, quorum, or protocol on the user's behalf. Do not implement Constitution Authority Context or protected commissioning while independent recognition and final enforcement remain unproven.
