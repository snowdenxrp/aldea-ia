# AB104.133 — shared-journal different-key concurrency hardening — 2026-09-26

Previous: AB104.132.

Audit finding:
- AB104.132 correctly serialized overlapping effects that reused the same idempotency key.
- A remaining race existed when two different idempotency keys shared the same durable execution journal and state revision: both could enter precondition/handler execution concurrently, so a state mutation by one effect could invalidate the assumptions of the other.
- The concrete Lúmina adapter uses a shared execution journal when runtime memory is shared, so this was a real in-process state-concurrency boundary.

Repair:
- Added a journal-scoped promise queue in `src/nexo/effect-adapter.js`.
- Effects sharing the same execution journal now execute their full fresh-effect lifecycle serially, regardless of idempotency key.
- The existing same-key in-flight map remains for duplicate callers, while the journal-wide queue prevents different-key state interleaving.
- Historical execution-journal results remain the durable replay source.
- Added a regression in `tests/nexo/effect-adapter.test.mjs` using two adapter instances, two different idempotency keys, a blocked first handler, and a second effect whose precondition must not run until the first effect has completed.
