## INVESTIGAR

Audited the canonical main tree after AB104.149.

### Caller audit result

No current repository caller was found that invokes executeLuminaNexoStep() or supplies persistPreparedIntent.

The current execution-capable pieces are therefore separated:

- src/nexo/runtime.js exposes the persistence-owner seam.
- src/nexo/simulation-adapter.js forwards the seam into createEffectAdapter().
- src/nexo/effect-adapter.js invokes persistPreparedIntent after creating prepared and before the effect handler.
- scripts/assistants.mjs is the current canonical state-loading/planning/checkpoint path, but it currently builds and persists a mission plan; it does not execute the mission through executeLuminaNexoStep().
- scripts/simulate.mjs owns world-state.json persistence, lock acquisition, stateRevision checking, temp-file write and rename.
- Therefore there is presently **no real end-to-end prepare-before-effect caller** to wire. Inventing one would change execution topology rather than repair an existing caller, so that step remains deliberately pending.

### Persistence research

Node.js documents that promise-based filesystem operations are not synchronized/threadsafe and concurrent modifications require explicit coordination. writeFile(...,{flush:true}) can flush the descriptor after a successful write, but this does not create an atomic transaction spanning a durable checkpoint and an external effect. See current Node.js documentation.

The transactional-outbox literature likewise treats crash-after-delivery-before-record as an ambiguity requiring idempotency/reconciliation rather than assuming atomic exactly-once behavior.
