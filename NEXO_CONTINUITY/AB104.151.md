## INVESTIGAR

Finding: the repository currently has a complete Nexo execution primitive, but no production caller that drives it.

scripts/assistants.mjs:
- loads canonical world state;
- runs debugger/tester/analyst/squad;
- builds a Nexo mission;
- persists the mission plan through recordNexoPlan + persistState;
- does not call executeNexoStep or executeLuminaNexoStep.

scripts/simulate.mjs:
- owns world-state persistence;
- owns stateRevision conflict checking;
- owns the filesystem lock and temp-file/rename persistence;
- does not execute Nexo missions.

src/nexo/runtime.js:
- exposes executeNexoStep and executeLuminaNexoStep;
- already accepts persistPreparedIntent;
- commits mission outcome to in-memory durable-memory structures;
- but has no owner callback capable of durably checkpointing the prepared intent before effect execution.

Therefore the missing link is not a forgotten callback at an existing call site. The missing link is the execution-owner boundary itself.

## ANALIZAR

Do not connect persistPreparedIntent directly to persistState inside the generic adapter/runtime. persistState requires caller-owned simulation state, stateRevision expectations, and filesystem ownership. Node.js also documents that fs/promises operations are not synchronized/threadsafe and concurrent modifications require explicit coordination; writeFile flush only addresses flushing written data, not a multi-resource transaction. citeturn0search2

The correct next design question is therefore: what component is authorized to transition a mission from planned/executing into an effect lifecycle while owning the canonical state revision?
