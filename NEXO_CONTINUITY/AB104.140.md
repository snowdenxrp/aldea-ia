Research performed:
- Official Node.js v22 documentation confirms fs/promises filesystem operations are not synchronized/threadsafe and concurrent modifications require care.
- Node documents exclusive creation via O_EXCL / the x flag (for example wx); it fails when the path already exists. Node also warns that exclusive creation may not work reliably on network filesystems.
- This supports using an atomically-created lock marker as a candidate local-filesystem coordination primitive, but it does NOT by itself solve stale-lock recovery after process death, fencing, or network-filesystem semantics.
- Therefore no production lock was added in this checkpoint.

Deployment invariant audit:
- .github/workflows/lumina-simulation.yml has concurrency group lumina-simulation with cancel-in-progress=true, so GitHub Actions scheduled/manual/push executions are serialized at the workflow level.
- The workflow also rebases before push and has a retry path.
- This is deployment-specific coordination, not a general filesystem CAS guarantee.
- A future local/multi-process Nexo runtime cannot inherit the GitHub Actions guarantee automatically.

Dual durable-memory audit:
1. world-state.json contains simulation state and nexoMemory.
2. scripts/simulate.mjs loads state.nexoMemory into createSimulation and persists simulation.nexoMemory back into world-state.json.
3. scripts/assistants.mjs separately loads .lumina-assistant-memory.json into a learning-memory object and writes learned assistant memory back to that separate file.
4. scripts/assistants.mjs currently does NOT load persisted.nexoMemory into its simulation and does NOT write simulation.nexoMemory to world-state.json.
5. The assistant workflow generates a nexoMission from the separate assistant-memory object, but the current learning step does not persist that mission into either store via recordNexoPlan.
6. Therefore the stores are currently operationally separate. This is not yet classified as a corruption bug because they have different apparent roles (assistant learning corpus vs durable Nexo simulation/runtime mission memory), but there is a semantic boundary that must be made explicit before Nexo depends on both.
7. Important risk: if the assistant process is expected to reason over the authoritative durable Nexo mission state, it currently does not automatically read world-state.nexoMemory. That is a read-model gap, not evidence of data loss.

Crash-window frontier:
- effect-adapter.js persists its execution journal only into the supplied in-memory executionJournal. Durable Nexo memory persistence happens later through the simulation/world-state persistence path.
- Therefore a physical external effect can occur and the process can die before the execution journal reaches durable storage. After restart, the durable record may say nothing happened even though the external effect happened.
- Current adapter pre/postconditions and idempotency reduce some ambiguity but do not eliminate this physical-effect-before-durable-record crash window.
- This remains UNKNOWN/UNRESOLVED and must not be called exactly-once.

No production lock or memory unification was implemented in this checkpoint because the required semantics have not been fully established.
