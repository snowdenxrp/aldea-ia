# AB104.138 — stale-writer revision guard researched, implemented, and CI-validated — 2026-09-26

Previous: AB104.137.

Research result:
- Persistence writer topology confirmed in scripts/simulate.mjs and .github/workflows/lumina-simulation.yml.
- world-state.json is read, advanced, and atomically replaced by scripts/simulate.mjs.
- The scheduled/push simulation workflow serializes its own workflow executions with concurrency group lumina-simulation and cancel-in-progress=true, then rebases before pushing. This reduces one known GitHub Actions writer race, but it is not a general filesystem/process CAS guarantee.
- scripts/assistants.mjs writes .lumina-assistant-memory.json separately. It does not currently write the Nexo memory embedded in world-state.json, so the two durable stores remain separate boundaries and require a later consistency audit.
- Atomic temp-file + rename was confirmed as replacement semantics only; no prior durable revision existed.

Repair:
- Commit a22c3592e5c73299db0d78be6113cecc51a0f146 adds a persisted non-negative integer stateRevision to world-state.json.
- loadState defaults legacy states to stateRevision=0.
- persistState accepts expectedRevision and stateRevision.
- When expectedRevision is supplied, persistState rereads the current file and rejects a mismatch with STATE_REVISION_CONFLICT before writing.
- main now loads revision R and persists R+1 while requiring expectedRevision=R.
- This establishes a durable stale-writer guard for callers using the contract. It does not yet claim a lock-free atomic CAS across the read/check/write window; two writers can still theoretically both observe the same revision before either writes. That limitation remains explicitly open.
- The restart persistence test was extended to verify sequential revisions and rejection of a stale writer.

Important semantic boundary:
- The current expectedRevision check is a check-then-write sequence, not a filesystem-level atomic compare-and-swap. If two independent processes both read revision R and both write R+1, the last rename can still win. The guard rejects writers that are already stale before they attempt the write, but it does not close the simultaneous same-revision race.
- Therefore multi-process linearizability remains UNKNOWN/PENDING.
