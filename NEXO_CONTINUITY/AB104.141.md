# AB104.141 — cross-process persistence lock repaired and validated — 2026-09-26

Previous: AB104.140.

Implementation:
- Added filesystem coordination around persistState in scripts/simulate.mjs.
- Each state path has a sibling lock directory: world-state.json.lock.
- Lock acquisition uses fs.mkdir without recursive mode; an existing lock yields EEXIST and the caller waits.
- Lock owner metadata records pid, unique token, and createdAt.
- The entire expectedRevision read/check, temp write, and rename occurs while the lock is held.
- finally always releases only when the stored owner token still matches.
- Temporary filenames retain the per-process sequence introduced in AB104.139.
- Stale recovery is conservative: only a lock with age > 60s and a non-live owner PID is reclaimed; an incomplete lock with no owner is reclaimed only after the same age threshold.
- No automatic reclamation of a lock held by a live process, even if old. This avoids reclaiming a suspended but still-live writer.
- This is a local-filesystem coordination mechanism. It is NOT claimed safe for arbitrary network filesystems or distributed hosts.

Adversarial validation:
- Added tests/nexo/persistence-lock-worker.mjs and updated simulation-restart-persistence.test.mjs to launch two independent Node processes against the same state file.
- The test requires exactly one writer to commit revision 1 and the other to receive STATE_REVISION_CONFLICT.
- Added a crash test that creates an owned lock, kills the owner process, ages the lock beyond the recovery threshold, and verifies a later writer can recover and persist.

Semantic result:
- Same-revision concurrent writers are now serialized on the local filesystem before revision check and rename.
- Therefore the previous demonstrated last-writer-wins race for world-state.json is prevented for cooperating processes using persistState and the same filesystem lock path.
- expectedRevision is still not an intrinsic filesystem CAS; correctness now depends on all writers honoring the lock protocol.
- External/uncooperative writers that bypass the lock can still violate the protocol.
- Network filesystem/distributed-host guarantees remain outside this mechanism.
- This does NOT solve the external-effect crash window or exactly-once semantics.
