# AB104.145 — blocked reconciliation must not erase prepared ambiguity — 2026-09-26

Previous: AB104.144.

## INVESTIGAR
Inspected the canonical effect adapter and its tests after AB104.144.

Found a semantic defect in `src/nexo/effect-adapter.js`: when a `prepared` entry was reconciled and the reconciliation returned a `blocked` result other than the special no-reconciler code, the adapter persisted that blocked result over the `prepared` journal state. That converted unresolved external-effect uncertainty into a cached terminal-looking state and prevented a later stronger reconciliation attempt from running.

Node.js v22 documentation confirms that asynchronous filesystem operations use the threadpool and concurrent modifications require care; this reinforces keeping the repository's cooperating-process serialization explicit rather than assuming fs/promises itself supplies synchronization. citeturn0search0

Research also reconfirmed the Transactional Outbox failure window: a process can crash after an external publication/effect but before recording completion, so replay must tolerate duplicates and use idempotent/reconciliation-aware consumers rather than assume exactly-once delivery. citeturn0search1

## CONSTRUIR
Commit `fe6de9c48bc420d275c09769f36b00555eaa1ea2` repairs the adapter:
- A `blocked` reconciliation result is returned but is NOT persisted.
- The journal remains `prepared`.
- A later reconciliation attempt can therefore resolve the ambiguity.
- Non-blocked terminal reconciliation results are still persisted.

Commit `46ef11b6029d6ad2659836d69aaa11254d992443` adds a regression test:
- provider unavailable/blocked reconciliation leaves journal `prepared`;
- handler is not executed;
- a later verified reconciliation can complete the same operation.
