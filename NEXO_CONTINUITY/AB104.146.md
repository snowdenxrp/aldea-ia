# AB104.146 — exception outcome ambiguity preserved for reconciliation — 2026-09-26

Previous: AB104.145.

## INVESTIGAR
Re-audited the canonical effect adapter after AB104.145, focusing on crash/timeout/error windows.

Found a second ambiguity boundary: a handler exception was being persisted as terminal `failed`. For an external effect, an exception does not prove the effect did not happen. A timeout can occur after the provider accepted the operation but before the caller receives a response. Persisting `failed` would allow later idempotent lookup to return the cached failure without reconciliation.

## CONSTRUIR
Commits:
- `64237bf5f9d87dac650d9ae428e645ae082f2412` initially changed handler exceptions to `blocked/EFFECT_OUTCOME_UNKNOWN`.
- `cbd79f998039874b0e3eb55e8a6fb583bdf0b8666` corrected the persistence boundary: an unknown exception result is returned but NOT persisted as terminal. The journal remains `prepared`, allowing explicit reconciliation.
- `f763eacc47618d0ae2afb5ee64f37fe2fd79f316` added the first exception ambiguity regression test.
- `c7b64967fde2218c31f3243fc5a7fb2435b54df9` extended it: after ambiguous exception, verified reconciliation can complete the operation.

Current intended semantics:
1. intent is recorded as `prepared`;
2. handler exception => return `blocked/EFFECT_OUTCOME_UNKNOWN`, do not finalize the journal;
3. later execution with reconciliation resolves the prepared entry;
4. handler is never blindly retried merely because the first call threw.

## IMPORTANT NEW LIMIT
The current `executeLuminaNexoStep` creates its execution journal from `simulation.nexoMemory.nexo.executions`. The journal is still in-memory until `persistState()` writes the whole simulation. Therefore the crash window between physical Lúmina mutation and durable state persistence remains unresolved.
