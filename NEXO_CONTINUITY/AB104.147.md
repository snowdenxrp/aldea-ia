# AB104.147 — effect journal promoted to durable Nexo state — 2026-09-26

Previous: AB104.146.

## INVESTIGAR
Inspected the canonical runtime, simulation persistence, memory schema, and effect adapter.

Confirmed the crash-durability gap: `executeLuminaNexoStep()` was passing `runtimeMemory.nexo.executions` as the effect adapter journal. That collection is outcome history; it does not necessarily contain a durable `prepared` intent. A crash after intent/effect but before `recordNexoExecution()`/state persistence could therefore erase the recovery fact.

Node.js v22 explicitly states that `fs/promises` operations use the threadpool and are not synchronized/threadsafe, so concurrent modifications require explicit coordination. citeturn0search0 The transactional-outbox literature likewise treats crash/replay windows as requiring durable intent plus idempotent/reconciliation-aware processing. citeturn0search1

## SEMANTIC LIMIT
This does NOT yet make the external effect itself durable or exactly-once. There is still a crash window between the physical external mutation and the durable checkpoint. The journal now survives only if the checkpoint occurs before the crash. A crash before checkpoint can still lose the intent.

The next architecture-level question is therefore not “can we save the journal?” but “what ordering/ownership contract guarantees recovery sees the intent before an external effect is allowed?”
