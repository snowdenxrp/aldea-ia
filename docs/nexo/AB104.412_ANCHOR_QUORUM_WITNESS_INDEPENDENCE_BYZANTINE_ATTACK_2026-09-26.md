# Nexo AB104.412 — Anchor Quorum, Witness Independence and Byzantine Equivocation

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.411 → AB104.412
Implementation: NOT PERFORMED

## Research question

How many independent continuity observations are actually meaningful, how do shared failure domains invalidate an apparent quorum, and how should Nexo handle Byzantine anchor equivocation without creating an unbounded governance TCB?

## Evidence reviewed

RFC 9162 shows that append-only consistency proofs can establish that one tree extends another, but also states that a malicious log can present inconsistent views to different clients. Detecting this requires comparison between observers; simply receiving a validly signed statement from one log is insufficient to establish non-equivocation. citeturn0search1turn0search2

RFC 9334 separates Verifier appraisal from Relying Party application-specific authorization. It also treats trust relationships and freshness as architectural inputs rather than universal guarantees. This supports keeping witness evidence outside the final Z1 authority decision until Nexo's own policy validates it. citeturn0search0turn0search3

## Core finding

A quorum is meaningful only relative to an explicit failure-domain and independence model.

MULTIPLE_OBSERVERS != INDEPENDENT_OBSERVERS
QUORUM_COUNT != QUORUM_SAFETY

Three replicas backed by the same database, deployment, key, operator, cloud control plane, or derivation code can fail together.

Conversely, two genuinely independent observations may be more informative for a particular claim than many correlated replicas.

## Candidate witness identity

A witness record should expose claim-relevant dependency information, such as:

- WITNESS_ID
- WITNESS_DOMAIN
- FAILURE_DOMAIN_SET
- TRUST_ROOT
- SOFTWARE/VERIFIER_GENERATION
- OBSERVATION_GENERATION
- OBSERVED_ANCHOR_ID
- OBSERVED_ROOT
- OBSERVED_PREDECESSOR
- OBSERVATION_TIME / freshness basis
- POLICY_VERSION
- KEY/TRUST_GENERATION
- EVIDENCE_ID
- INDEPENDENCE_METADATA
- LIMITATIONS
- STATUS

This is evidence about independence, not proof of independence.

## Failure-domain matrix

Candidate domains:

- cryptographic key
- root of trust
- anchor implementation
- storage backend
- database
- network/control plane
- cloud/provider
- region
- deployment pipeline
- container/image
- operating system/runtime
- verifier implementation
- policy source
- schema/derivation engine
- operator/governance path
- time source
- recovery/backup system

Two witnesses sharing any security-critical domain may be correlated for the property that depends on that domain.

Therefore:

WITNESS_A != WITNESS_B does not establish independence.

The dependency closure must be compared.

## Byzantine equivocation

Attack:

1. Anchor signs ROOT=A at generation 500 for witness W1.
2. Anchor signs ROOT=B at generation 500 for witness W2.
3. W1 validates A.
4. W2 validates B.
5. Both are individually authentic.

Neither signature proves which branch is current.

Candidate state:

ANCHOR_EQUIVOCATION => DISPUTED / QUARANTINED

The correct response is not an arbitrary majority unless a previously protected protocol defines how that majority is authoritative.

## Why simple majority is insufficient

Suppose:

W1, W2, W3 all share one compromised signing key.

W4 is independent and sees a conflicting root.

A 3-of-4 numerical majority could simply represent three copies of the same false view.

Therefore Nexo needs:

CLAIM -> REQUIRED_INDEPENDENCE_DOMAINS -> WITNESS_SET -> EVALUATION

not:

CLAIM -> NUMBER_OF_WITNESSES -> ACCEPT.

## Common-mode compromise

If all witnesses depend on the same:

- policy;
- anchor key;
- software library;
- derivation algorithm;
- deployment artifact;
- cloud region;
- operator;
- network path;

then the apparent quorum may have no independent evidentiary value for the affected claim.

Candidate invariant:

COMMON_MODE_COMPROMISE_CAN_COLLAPSE_QUORUM

This extends AB104.392's failure-domain model.

## Witnesses versus authorities

Witnesses should normally report observations; they should not decide which history Nexo must adopt.

Candidate flow:

ANCHOR_OBSERVATIONS
→ WITNESS_EVIDENCE
→ DEPENDENCY_CLOSURE
→ CONSISTENCY / EQUIVOCATION ANALYSIS
→ Z1 POLICY
→ AUTHORITY DECISION

This prevents a witness quorum from becoming an accidental second authority layer.

## Evidence disagreement

If witnesses disagree, classify:

- STALE_OBSERVATION
- NETWORK_PARTITION
- REPLICATION_LAG
- DIFFERENT_VALID_GENERATIONS
- EQUIVOCATION
- WITNESS_COMPROMISE
- COMMON_MODE_FAILURE
- UNKNOWN

Do not collapse every disagreement into Byzantine compromise.

But unresolved disagreement about a security-critical continuity property must not be treated as affirmative current continuity.

Candidate:

UNRESOLVED_SECURITY_CRITICAL_DISAGREEMENT => UNKNOWN / HOLD / QUARANTINED

## Generation and predecessor binding

A witness should not only report a root; it should bind the observed root to its predecessor and generation.

Candidate:

GENERATION_N
+ ROOT_N
+ PREVIOUS_ROOT_N-1
+ PREVIOUS_GENERATION
+ ANCHOR_ID
+ TRUST_GENERATION

This allows detection of:

- rollback;
- fork;
- skipped generations where prohibited;
- anchor identity substitution;
- key-generation mismatch.

Still, this proves consistency of the declared chain, not semantic correctness of the state.

## Witness freshness

Freshness should be claim-specific.

A witness that observed G=500 yesterday may be useful historical evidence but insufficient to authorize an E4 effect today.

RFC 9334 explicitly describes freshness as a policy choice and notes that state can change immediately after evidence/result generation. citeturn0search0

Therefore:

WITNESS_FRESHNESS != CURRENT_AUTHORITY

## Witness loss

If enough witnesses become unavailable to satisfy the required independence threshold, the system should not silently lower the threshold to preserve availability.

Candidate:

REQUIRED_WITNESS_SET_UNSATISFIED => HOLD / REVALIDATE

A lower threshold is a policy change requiring its own protected authorization, not an automatic operational fallback.

## Dynamic witness sets

Adding a witness does not automatically increase assurance if it shares all relevant dependencies.

Removing an independent witness can reduce assurance.

Changing the required witness set changes the claim's assurance semantics.

Candidate:

WITNESS_POLICY_CHANGE => NEW_ADMISSION_BOUNDARY

for claims whose safety depends on that policy.

## Quorum and effect class

Candidate policy direction, not a final numeric choice:

- E0 may need little or no continuity quorum if no authority/effect claim depends on it.
- E1/E2 may use bounded provider guarantees where the provider itself supplies the required property.
- E3/E4 need stronger current-state continuity and replay protection.
- E5 requires participant/domain-specific closure; one global witness quorum cannot prove cross-resource atomicity.

These are design categories, not final thresholds.

## Governance TCB boundary

If unresolved anchor conflict is handed to an operator, that operator becomes part of the decision path for the affected recovery property.

Therefore governance must be explicitly modeled:

GOVERNANCE_DECISION
= evidence + authorized role + scope + reason + affected generations + resulting policy/epoch + audit record

It must not be an opaque “admin override.”

However, governance can authorize a recovery action; it cannot retroactively prove that an unknown external effect did not occur.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| many correlated witnesses | count => independence | dependency analysis |
| shared key | signatures differ => independent | trust-root comparison |
| shared deployment | different instances => independent | deployment-domain comparison |
| stale witness | signed old view => current | freshness check |
| equivocation | two valid roots => choose majority | conflict/quarantine |
| witness outage | fewer available => lower threshold | preserve protected policy |
| common-mode verifier | multiple appraisals => independent | verifier dependency closure |
| policy fork | witnesses use different policy | policy-version binding |
| recovery witness | restored witness => current | independent continuity |
| operator quorum | several approvals => independent | governance dependency analysis |
| cross-provider witness | provider success => global continuity | participant-specific evidence |
