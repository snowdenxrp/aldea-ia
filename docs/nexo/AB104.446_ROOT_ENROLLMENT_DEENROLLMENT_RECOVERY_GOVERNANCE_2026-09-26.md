# Nexo AB104.446 — Root Enrollment, De-enrollment and Recovery Governance Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.445 → AB104.446
Implementation: NOT PERFORMED

## Research question

How can Nexo add/remove trust roots and change quorum or recovery policy without creating a self-authorizing path, stale-evaluation race, or fail-open emergency mechanism?

## External evidence

RFC 9334's RATS model separates trust anchors, Verifier appraisal, Attestation Results, and Relying Party authorization. Trust-anchor configuration is therefore itself part of the relying party's security boundary. citeturn0search2turn0search4

NIST SP 800-57 treats key lifecycle, compromise, revocation, replacement and destruction as managed security events rather than ordinary configuration changes. citeturn0search49turn0search48

NIST SP 800-207's zero-trust model emphasizes explicit policy enforcement and continuous evaluation rather than implicit trust based solely on network or organizational location. citeturn0search3

RFC 9162's transparency model supplies a useful precedent for monitoring consistency and exposing divergent histories, while leaving policy/governance decisions outside the log itself. citeturn0search5

## Core finding

Root enrollment is an authority transition.

Therefore:

ROOT_ENROLLMENT != CONFIG_UPDATE

and:

ROOT_DEENROLLMENT != KEY_DELETION.

The protected fact is not merely which keys exist, but which roots are currently eligible to contribute to a particular claim under which policy generation.

## Attack G1 — self-enrollment

A new root claims:
“I am now an authorized witness.”

No.

Candidate:
UNENROLLED_ROOT_CANNOT_AUTHORIZE_ITS_OWN_ENROLLMENT.

Enrollment requires an already-authorized recovery/governance basis.

## Attack G2 — compromised root enrolls a second root

Root A is compromised.
A enrolls B.
B signs that A and B are independent.

This is circular.

Dependency closure must include the enrollment authority.

## Attack G3 — threshold lowering

Current policy requires 3 independent domains.
During recovery, someone changes threshold to 1.

This is itself a protected policy transition.

Candidate:
QUORUM_POLICY_CHANGE => NEW_ADMISSION_BOUNDARY.

It cannot retroactively make an old evaluation valid.

## Attack G4 — threshold increase during evaluation

Evaluation starts under threshold 2.
Policy changes to threshold 3 before commit.

Old evaluation must become stale.

Candidate:
THRESHOLD_GENERATION_CHANGE => STALE_EVALUATION.

## Attack G5 — root removal race

Root R is current during quorum evaluation.
R is revoked.
Old quorum result attempts commit.

Final gate must revalidate:
- root status;
- trust generation;
- witness set;
- dependency closure;
- quorum threshold;
- policy generation.

## Attack G6 — de-enrollment without effect invalidation

Root removed but old admission contexts still reference it.

Those contexts can become stale authorization.

Therefore:
ROOT_DEENROLLMENT => DEPENDENT_ADMISSION_INVALIDATION.

## Attack G7 — root replacement masquerading as same identity

Old root key is replaced but RootID remains unchanged.

This can create generation confusion.

Candidate identity:
ROOT_ID + ROOT_INCARNATION + KEY_GENERATION.

Key rotation and root incarnation must be distinct when semantics differ.

## Attack G8 — Byzantine conflicting roots

R1 says current root set = S1.
R2 says current root set = S2.

If both are validly signed, this is not resolved by signature validity.

Candidate:
CONFLICTING_ROOT_SET => DISPUTED / QUARANTINED.

Need independent recovery authority or explicit governance resolution.

## Attack G9 — unavailable root

A required root is offline.

Do not silently substitute an unapproved root or lower threshold.

Candidate:
REQUIRED_ROOT_UNAVAILABLE => HOLD unless policy explicitly defines a safe degraded mode.

## Attack G10 — emergency recovery

Suppose normal quorum cannot be formed after a catastrophe.

Emergency path must not simply disable quorum.

Instead:
EMERGENCY_RECOVERY
→ distinct authority basis
→ bounded scope
→ explicit recovery generation
→ stronger audit/evidence
→ restricted effects
→ later reconciliation
→ explicit return to normal policy.

Emergency is a different authority mode, not a weaker normal mode.

## Attack G11 — emergency mode becomes permanent

A bounded emergency path can become an indefinite backdoor.

Candidate:
EMERGENCY_AUTHORITY_REQUIRES_EXPIRY_OR_EXPLICIT_RENEWAL.

If renewal requires a current trusted basis, renewal cannot be self-issued by emergency mode.

## Attack G12 — recovery authority compromised

The authority that can enroll roots is itself compromised.

Then ordinary root enrollment cannot establish trust.

Need a higher/independent recovery governance basis or full quarantine.

## Attack G13 — stale witness enrollment

A root is validly enrolled under old dependency state but later its trust root, software, policy or failure-domain relationship changes.

Enrollment is historical evidence, not perpetual current independence.

Candidate:
DEPENDENCY_DRIFT => ROOT_STATUS_DEGRADED/STALE.

## Attack G14 — witness set rollback

Restore old configuration containing revoked roots.

Configuration signature alone does not establish currentness.

Need protected configuration generation/continuity.

## Attack G15 — split-brain governance

Two recovery authorities independently enroll different root sets.

This is governance equivocation.

Candidate:
SAME_GOVERNANCE_GENERATION + DIFFERENT_ROOT_SET
=> GOVERNANCE_EQUIVOCATION.

Freeze affected high-consequence transitions.

## Candidate final admission predicate

A quorum evaluation can contribute to Z1 only if, at the protected boundary:

- governance generation current;
- root-set version current;
- every contributing root current;
- every required root/dependency current;
- threshold current;
- claim scope current;
- trust/policy generations current;
- no conflict/equivocation;
- no quarantine;
- recovery mode valid;
- evaluation freshness valid.

Any protected generation change => stale evaluation.

## Emergency recovery contract

Emergency mode must specify:
- trigger conditions;
- authorized initiator;
- maximum scope;
- allowed effect classes;
- root requirements;
- evidence requirements;
- external effect handling;
- expiration;
- renewal;
- exit criteria;
- reconciliation requirements;
- audit retention;
- failure behavior.

High-consequence irreversible effects should not become automatically admissible merely because emergency mode is active.

## Governance and Z1

Root governance should be outside ordinary model inference.

Planning/model output may propose:
ADD_ROOT / REMOVE_ROOT / CHANGE_THRESHOLD.

Z1 decides whether that protected governance transition is authorized.

This prevents the model layer from rewriting its own trust basis.

## Important distinction

A root is not trusted because it is “in the list.”

The list itself is protected state with:
- identity;
- generation;
- provenance;
- dependency closure;
- policy;
- invalidation semantics.

Therefore:

TRUST_LIST != TRUST_STATE_UNLESS_CURRENT_AND_PROTECTED.

- Need analyze emergency recovery when every normal governance authority is unavailable.
- Need study threshold signatures versus explicit multi-party approval and their independence limits.
- Need analyze governance key rotation/recovery.
- Need determine minimum audit evidence for root enrollment/de-enrollment.
- Formal verification, implementation, fault injection and deployment validation remain unperformed.
