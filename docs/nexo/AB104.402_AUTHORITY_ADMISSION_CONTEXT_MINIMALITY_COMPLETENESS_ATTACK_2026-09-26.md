# Nexo AB104.402 — AUTHORITY_ADMISSION_CONTEXT Minimality vs Completeness Attack
Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Chain: AB104.401 -> AB104.402

## Research question

Can AUTHORITY_ADMISSION_CONTEXT remain claim-specific and minimal without allowing a malicious, buggy, incomplete, or downgraded claim contract to omit a dependency that is actually required for the protected property?

## External evidence reviewed

- RFC 9334 (RATS): Evidence is appraised by a Verifier into an Attestation Result; the Relying Party applies its own appraisal/authorization policy. Freshness narrows accepted recency but does not eliminate races after appraisal.
- NIST SP 800-162 (ABAC): authorization can depend on subject, object, requested operation, and environment attributes; attribute integrity, provenance, completeness, allowable values, and change history require explicit management.
- XACML 3.0: missing attributes can make a decision Indeterminate when required, rather than silently treating absence as a security-relevant value.

These sources support separation of evidence/appraisal from authorization and treating required context as policy/model-governed data, not as an arbitrary caller-supplied snapshot. They do not by themselves prove Nexo's proposed architecture.

## Core attack

If CLAIM_CONTRACT is allowed to define its own complete dependency set, a faulty or malicious contract can omit a field that is actually required by the protected property:

1. Claim contract declares only {identity, target_version}.
2. Actual safety property also depends on resource_incarnation and authority_epoch.
3. AUTHORITY_ADMISSION_CONTEXT is constructed from the declared set.
4. Final gate sees all declared fields current.
5. Z1 grants authority.
6. A stale incarnation or authority generation can therefore cross the gate.

This is a semantic omission attack, not merely a stale-value attack.

## Main result

AUTHORITY_ADMISSION_CONTEXT must NOT be a universal state snapshot, but its required fields cannot be determined solely by the claim contract being evaluated.

The minimum safe model is a claim-specific REQUIRED_AUTHORITY_CONTEXT derived from protected semantic authorities outside the claim instance itself:

CLAIM/EFFECT PROPERTY
  + EFFECT_CLASS
  + PROTECTED POLICY/SCHEMA
  + REQUIRED PROPERTY RULES
  -> REQUIRED_CONTEXT_SCHEMA
  -> REQUIRED_SET_ROOT
  -> INSTANCE CLOSURE
  -> AUTHORITY_ADMISSION_CONTEXT
  -> Z1 FINAL GATE

The claim contract may request or refine context, but it cannot unilaterally subtract a dependency required by the protected property model.

## Minimality rule

"Minimal" must mean MINIMUM SUFFICIENT FOR THE CLAIM CLASS/PROPERTY, not "smallest set declared by the requester."

Candidate rule:

REQUIRED_CONTEXT = closure(
  property-required fields
  ∪ effect-class-required fields
  ∪ policy-required fields
  ∪ dependency-derived fields
  ∪ resource/path requirements
)

A field may be omitted only when its non-applicability is itself established by the authoritative semantic model.

ABSENT != NOT_APPLICABLE.

## Claim-by-claim dependency selection

Candidate protected dependency classes:

- Identity/authority: identity, authority epoch/scope, delegation chain where applicable.
- Target correctness: target version, resource identity, resource incarnation.
- External effect safety: EffectID, provider fence generation, idempotency/capability profile, durable intent.
- Evidence validity: claim version, required-set root, closure root, policy/schema versions, verifier trust generation, dependency generations, invalidation generation.
- Path enforcement: adapter/path identity and its validated capability profile where the claimed property depends on it.
- Time/freshness: freshness basis only when the property explicitly requires temporal validity; time is not automatically a universal dependency.

Each effect/claim class gets a required-field schema. The schema is versioned and itself part of the protected dependency closure.

## Omission attack classes

1. Explicit subtraction: contract says a known dependency is irrelevant.
2. Optional-field downgrade: required field becomes optional during migration.
3. Wildcard substitution: resource/authority/incarnation is replaced by ANY.
4. Null-as-valid: missing value is interpreted as unconstrained.
5. Version rollback: older contract version has a smaller dependency set.
6. Inheritance gap: child contract omits a parent safety dependency.
7. Dynamic dependency suppression: runtime branch requires a new dependency after the initial closure.
8. Capability laundering: a provider capability is treated as present without a current validated capability profile.
9. Adapter substitution: contract omits adapter/path binding even though enforcement depends on it.
10. Semantic conflict: contract says a field is irrelevant while the protected property model says it is required.

Safe response for unresolved applicability, conflict, incomplete derivation, or missing required context: UNKNOWN / HOLD / REVALIDATE, not grant.

## Anti-self-definition boundary

Candidate invariant:

CLAIM_CONTRACT_CANNOT_DEFINE_ITS_OWN_TCB.

More precisely:
- The contract declares the intended claim/property.
- A protected semantic rule set determines the minimum required context.
- Z1 verifies that the supplied context covers that protected requirement.
- The contract cannot lower the requirement by omission.
- A derived context schema is evidence/configuration, not authority by itself.
- Z1 remains the authority boundary.

This prevents a circular proof in which a claim is safe because its own contract says the fields needed to prove it are unnecessary.

## Completeness vs integrity

A signed or hashed context schema can prove integrity of the declared schema, but not semantic completeness. This carries forward AB104.396–AB104.398.

Therefore at least two roots remain distinct:

REQUIRED_SET_ROOT = what the protected semantic model says is required.
INSTANCE_CLOSURE_ROOT = what the concrete dependency graph actually contains.

A matching root proves consistency with the corresponding source; it does not prove that the source's semantics are correct. That remains a separate validation question.

## Monotonicity candidate

A safety-preserving contract refinement should be monotonic with respect to required context:

Adding a dependency may cause HOLD/REVALIDATE/rejection if unavailable, but must not silently remove an already-protected dependency.

Candidate invariant:
REQUIRED_CONTEXT_REFINEMENT_CANNOT_WEAKEN_PROTECTED_PROPERTY.

Contract migration that removes a dependency therefore requires a new semantic validation boundary, not merely a version bump.

## Context-size control without universal snapshot

To avoid universal-state explosion, Z1 should bind only the closure needed by:
- the protected property,
- effect class,
- declared resource/path,
- current policy/schema,
- and dynamically discovered dependencies before final authorization.

Ordinary planning/model state, telemetry, embeddings, UI state, and unrelated memory remain outside unless the protected property explicitly makes them authoritative dependencies.

If a dependency is discovered only after the final gate, the prior authorization cannot be assumed to cover the new dependency. A new admission/evaluation boundary is required.

## Candidate final-gate predicate

GRANT iff, at one protected linearization point/equivalent:

- claim/property contract version is accepted;
- REQUIRED_SET_ROOT matches the authoritative semantic requirement;
- INSTANCE_CLOSURE is complete for that required set;
- every required context field is present and semantically bound;
- no field is satisfied by wildcard/null-as-unconstrained semantics;
- all required dependency generations/incarnations are current;
- authority epoch/scope is current where required;
- effect-class capability requirements are current;
- no unresolved contradiction, derivation incompleteness, or invalidation exists;
- the final protected predicate has not crossed a generation change.

Otherwise: REJECT / HOLD / REVALIDATE / UNKNOWN according to the failure mode.

## Remaining UNKNOWN / not proven

- No formal proof yet that the proposed derivation mechanism is complete.
- No complete machine-checkable required-context schema exists yet.
- No formal proof that all dynamic dependencies can be discovered before the final gate.
- No implementation or runtime validation performed.
- No universal field list should be frozen yet; field requirements remain claim/effect specific.
- The semantic authority that defines required context remains a TCB boundary and needs further attack.
