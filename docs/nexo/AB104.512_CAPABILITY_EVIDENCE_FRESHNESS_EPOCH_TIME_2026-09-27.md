# AB104.512 — capability evidence freshness, epochs, and time

## Evidence
RFC 9334 (RATS) explicitly presents nonce- and epoch-based freshness models that avoid relying solely on synchronized clocks, and warns that a relying party must not continue using an attestation result beyond the validity period it accepts. Timestamp-based freshness instead requires appropriate clock synchronization. citeturn0search1turn0search6 RFC 3339 likewise notes that systems exchanging UTC timestamps need a synchronization mechanism. citeturn0search0

etcd provides a useful concrete contrast: leases have server-selected TTLs, expiration is determined by the etcd cluster, and expiration deletes attached keys; lease status exposes remaining TTL and a revision. citeturn0search4turn0search5 etcd revisions are monotonic logical ordering, distinct from wall-clock time, although historical revisions can eventually be compacted. citeturn0search3turn0search11

## Nexo freshness model
A capability claim should not depend on a single timestamp. Candidate evidence:
`CapabilityEvidence = {TargetIdentity, Incarnation, Capability, Scope, ConfigDigest, AuthorityEpoch, EvidenceEpoch, IssuedAt, ValidUntil, MonotonicGeneration, SourceRevision, Nonce/Challenge, TrustBasis}`.

Freshness is multidimensional:
1. **Temporal freshness** — evidence has not exceeded its accepted lifetime.
2. **Epoch freshness** — evidence belongs to the current authority/trust epoch.
3. **Generation freshness** — evidence generation is not older than the current monotonic generation.
4. **Revision freshness** — provider state is at/after the required authoritative revision.
5. **Challenge freshness** — where applicable, evidence answers a verifier-controlled nonce/challenge.

No one dimension substitutes for another.

## Trusted time versus generations
Wall-clock time is useful for expiry but vulnerable to synchronization errors and rollback assumptions. Monotonic authority generations provide ordering without requiring clocks to agree.

Candidate rule:
`AuthorityEpoch_current == Evidence.AuthorityEpoch`
`Generation_current >= Evidence.MonotonicGeneration`
`Now_within_validity_window`
`ProviderRevision >= RequiredRevision` when a revision boundary exists.

A local clock saying evidence is fresh cannot override a newer authority epoch or revocation generation.

## Delayed attestation
An attestation can be cryptographically valid yet stale when delivered after an epoch transition. RFC 9334's epoch-ID model directly captures this: evidence associated with a previous epoch can be rejected once the relying party has moved beyond the accepted epoch window. citeturn0search1

Therefore:
`VALID_SIGNATURE + OLD_EPOCH => STALE_EVIDENCE`, not current capability.

## Clock rollback
If freshness relies on wall time, a backward clock adjustment can incorrectly extend apparent validity. Nexo should therefore treat wall-clock validity as one input, not the sole freshness authority. A rollback or unexplained time discontinuity affecting a trusted clock source should trigger `TIME_TRUST_DEGRADED` and invalidate time-dependent capability claims until revalidation.

Monotonic local elapsed-time measurement can prevent a process from believing less time has passed after a local rollback, but it does not establish global time or authority epoch. This remains a distinct trust boundary.

## Lease semantics
A lease is not merely a timestamp stored by the client. etcd's lease TTL is granted and evaluated by the authoritative cluster, and expiration causes attached keys to be deleted. citeturn0search4 Nexo should prefer an authority-issued lease/generation over a client-computed expiry when the capability controls protected authority.

## Capability validity predicate
Candidate protected predicate:
`VALID_CAPABILITY := IdentityCurrent ∧ IncarnationCurrent ∧ ScopeMatch ∧ ConfigMatch ∧ TrustBasisValid ∧ AuthorityEpochCurrent ∧ GenerationCurrent ∧ FreshEnough ∧ RevisionSatisfies ∧ ChallengeSatisfied`.

If a required predicate cannot be established:
`UNKNOWN_CAPABILITY => NO_PROTECTED_ALLOW`.

## Invariants
- `WALL_CLOCK_FRESHNESS != AUTHORITY_FRESHNESS`
- `TIMESTAMP_VALID != CURRENT_EPOCH`
- `VALID_SIGNATURE != FRESH_EVIDENCE`
- `OLD_EPOCH_EVIDENCE => NO_CURRENT_AUTHORITY`
- `CLOCK_ROLLBACK != VALIDITY_EXTENSION`
- `LOCAL_MONOTONIC_TIME != GLOBAL_TIME_AUTHORITY`
- `PROVIDER_TTL != NEXO_AUTHORITY_EPOCH`
- `LEASE_RENEWAL != TRUST_BASIS_REVALIDATION`
- `UNKNOWN_TIME_TRUST => NO_TIME_DEPENDENT_PROTECTED_ALLOW`
- `COMPACTED_REVISION != PROOF_OF_CURRENT_STATE`
- `FRESHNESS_DIMENSIONS_MUST_BE_EXPLICIT`

## Status
Research complete. Capability freshness should combine authority epochs/generations with provider revisions and, where appropriate, nonce-based freshness; wall-clock expiry remains a bounded input rather than sole authority. No implementation or formal verification performed.

Next exact step: AB104.513 — research capability evidence revocation and negative evidence: how to prove a capability is no longer valid, how revocation races with in-flight effects, and how deletion/absence/expired leases should propagate into the protected final gate.
