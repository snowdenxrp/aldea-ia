# Nexo AB104.533 — Temporal composition and final revalidation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Fresh capability components do not imply a fresh composed authorization at effect time. Between capability validation and external admission, any dependency can change. The final protected gate therefore needs a coherent revalidation point for all authority-critical dependencies, not independent cached checks.

## Evidence
etcd transactions atomically evaluate multiple comparisons and apply the success branch only if all comparisons hold; etcd linearizable operations provide current ordering, while watch streams are ordered but are not themselves linearizable. Kubernetes resourceVersion is scoped to a resource type and can be used for optimistic concurrency; its documentation also distinguishes current, not-older-than, exact, and potentially stale reads. A 2026 Kubernetes controller-runtime explanation shows the concrete race between a cached read and a later update: a write using an old resourceVersion receives 409 rather than silently overwriting the newer state.

## Candidate temporal model
At capability appraisal:
C_i = (scope_i, target_i, incarnation_i, epoch_i, generation_i, evidence_i)

At final admission:
Revalidate all required C_i against one coherent authoritative snapshot or equivalent fencing protocol.

Then:
CAPABILITIES_VALIDATED
-> FINAL_REVALIDATION
-> EFFECT_ADMITTED
-> PROVIDER_CONDITIONAL_ACCEPT

If any authority-critical dependency changed, expired, was revoked, became UNKNOWN, or no longer matches the target/incarnation, reject/recompute/quarantine.

## Why independent freshness is insufficient
C1 may be fresh at t1.
C2 may be fresh at t1.
C3 may be fresh at t1.
At t2, C2 can be revoked while C1/C3 remain individually fresh.
A composed claim using the cached trio is stale even though each component's local freshness window has not expired.

Therefore:
FRESH(C1) AND FRESH(C2) AND FRESH(C3) != FRESH(COMPOSITION)
unless their dependency snapshot and validity relation are jointly bound.

## Candidate final-admission binding
FinalAdmission = {
 DependencyClosureDigest,
 StateRevision/VersionSet,
 AuthorityEpoch,
 RevocationGeneration,
 FenceRevision,
 TargetIdentity,
 TargetIncarnation,
 PolicyProfile,
 CapabilityEvidenceDigests,
 AdmissionRevision
}

The provider request must bind the exact target/incarnation and, where supported, provider-side conditional version/fence predicates.

## Critical distinctions
- FRESH_COMPONENTS != FRESH_COMPOSITION
- CACHED_VALIDATION != FINAL_AUTHORIZATION
- WATCH_EVENT != FINAL_LINEARIZABLE_READ
- RESOURCE_VERSION != GLOBAL_AUTHORITY_EPOCH
- FINAL_REVALIDATION != PROVIDER_COMMIT
- PROVIDER_CONDITIONAL_ACCEPT != EXTERNAL_WORLD_CONFIRMATION
- TARGET_VERSION != TARGET_INCARNATION
- LOCAL_REVISION != CROSS_DOMAIN_ORDER

## Failure handling
If a dependency changes after final validation but before provider enforcement:
- if provider enforces the bound version/fence atomically: provider rejects stale request;
- if provider cannot enforce it: Nexo cannot claim stale-writer protection and must rely on reconciliation/UNKNOWN;
- if the target was replaced: old operation remains bound to the old incarnation;
- if the authority epoch/revocation changed: no new protected admission under the old state.

## Nexo implication
This closes an important gap between the capability graph and the effect adapter: the dependency closure must be snapshotted/revalidated at the protected transition boundary. Cached evidence may inform planning, but cannot by itself authorize a protected external effect.
