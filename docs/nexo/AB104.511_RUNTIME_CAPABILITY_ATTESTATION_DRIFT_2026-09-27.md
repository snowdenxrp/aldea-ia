# AB104.511 — runtime capability verification and capability drift

## Evidence
NIST describes remote attestation as cryptographic evidence of runtime measurements, including code/configuration measurements, evaluated by a verifier against expected values; the relying party can use the result to decide whether secrets or keys should be provisioned. citeturn0search5turn0search6 Kubernetes provides a concrete capability-gating pattern: nodes declare supported features, the scheduler filters against those declarations, admission validates them, and the kubelet performs a final check before execution. This is explicitly intended to handle mixed-version environments. citeturn0search0turn0search1 Kubernetes also documents that significant node replacement/configuration changes should produce a fresh node registration rather than silently retaining the old identity/state. citeturn0search4

## Nexo capability evidence
A provider capability claim should be represented as:
`CapabilityClaim = {ProviderIdentity, TargetIdentity, Capability, Scope, Version, ConfigDigest, Measurement/Attestation, EvidenceEpoch, ObservedAt, ValidUntil, TrustBasis, PolicyProfile}`.

A documented capability is only the baseline contract. Runtime eligibility additionally requires evidence that the deployed target still matches the expected capability configuration.

## Capability verification layers
1. **Static contract** — provider/documentation defines what should be supported.
2. **Deployment evidence** — version/configuration identifies what was deployed.
3. **Runtime probe** — safe probe tests the behavior actually exposed.
4. **Attestation** — when available, hardware/TEE-backed measurements bind runtime state to a verifier.
5. **Operational evidence** — repeated observations/canaries detect behavioral drift.

No layer should silently substitute for another. NIST's attestation model explicitly separates measured runtime evidence from the relying party's policy decision. citeturn0search5turn0search6

## Capability drift
Drift events include:
- provider version change;
- configuration/profile change;
- target/resource replacement;
- attestation measurement change;
- capability probe failure;
- loss/expiry/revocation of evidence;
- provider contract change;
- failover to a target with different capability scope.

Any drift affecting a capability required by a protected effect invalidates the capability claim for that effect until revalidation.

Candidate transition:
`CAPABILITY_VALID → DRIFT_SUSPECTED → REVALIDATING → VALID | UNKNOWN | REVOKED`

`UNKNOWN` must not be promoted to `VALID` solely because the previous claim was valid.

## Demotion
Capability loss must be monotonic with respect to authority: a target can be demoted immediately when evidence becomes invalid, while restoration requires fresh evidence and an explicit promotion gate.

`VALID → UNKNOWN` may be automatic on evidence expiry/failure.

`UNKNOWN → VALID` requires:
`fresh evidence + current target identity/incarnation + current configuration + required probe/attestation + current trust basis + policy revalidation`.

This mirrors Kubernetes' layered feature checks: declaration influences scheduling, admission validates, and the runtime performs a final compatibility check. citeturn0search0

## Canary safety
A canary must itself have a bounded effect contract. A probe cannot be allowed to mutate an external system merely to prove that mutation works. Prefer read-only or explicitly reversible test operations, and treat successful canary execution as evidence only for the tested scope/version/path.

`CANARY_SUCCESS != UNIVERSAL_CAPABILITY`
`PROBE_SCOPE != EFFECT_SCOPE`

## Attestation limitations
Attestation can establish measured runtime state under its trust model; it does not automatically prove external resource state, authorization legitimacy, or semantic correctness of the provider's implementation. NIST describes the verifier/relying-party boundary explicitly. citeturn0search5

## Candidate runtime gate
`current target identity → capability evidence → evidence freshness → config/version match → optional attestation/probe → dependency closure → final authorization gate`.

If any required capability is `UNKNOWN`, the protected effect is held/recomputed/quarantined according to effect class; no stale capability claim may silently authorize it.

## Invariants
- `DOCUMENTED_CAPABILITY != RUNTIME_VERIFIED_CAPABILITY`
- `ATTESTATION != EXTERNAL_STATE_PROOF`
- `CANARY_SUCCESS != UNIVERSAL_CAPABILITY`
- `CAPABILITY_EXPIRY => NO_NEW_PROTECTED_ALLOW`
- `TARGET_REPLACEMENT => REVALIDATE_CAPABILITIES`
- `CONFIG_CHANGE => REVALIDATE_CAPABILITIES`
- `UNKNOWN_CAPABILITY != VALID_CAPABILITY`
- `UNKNOWN → VALID REQUIRES FRESH EVIDENCE`
- `CAPABILITY_SCOPE_MUST_BIND_TO_EFFECT_SCOPE`
- `RUNTIME_EVIDENCE != AUTHORITY_BY_ITSELF`

## Status
Research complete. Runtime capability verification should be a layered evidence process, with immediate fail-closed demotion and explicit re-promotion. No implementation or formal verification performed.
