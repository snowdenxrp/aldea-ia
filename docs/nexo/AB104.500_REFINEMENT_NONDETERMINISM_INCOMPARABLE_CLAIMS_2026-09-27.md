# AB104.500 — refinement under nondeterminism, underspecification, incomparable claims

## Evidence
TLA+ refinement is semantic and permits implementation steps that are invisible at the abstract level (stuttering), provided observable behavior remains allowed by the abstract specification. citeturn0search0 Trace inclusion is a direct way to compare observable behavior, while simulation is a commonly used, efficiently checkable sufficient condition for trace containment. citeturn0search1turn0search7 Contract refinement adds assumptions/guarantees and can differ from plain trace inclusion; nondeterministic, non-input-enabled systems also show that different refinement/conformance relations need not coincide. citeturn0search4turn0search12

## Nexo finding
No single relation should be silently chosen for every certificate claim. Nexo needs a layered relation because authority certificates combine state, inputs, assumptions, guarantees, and security-critical exclusions.

Candidate stack:
1. **Trace inclusion** for externally observable authorization behavior.
2. **Simulation/refinement mapping** as a practical sufficient proof technique where state correspondence is available.
3. **Contract refinement** for assumption/guarantee changes, especially when a new profile changes what inputs or environments it accepts.
4. **Explicit incomparability** when neither profile safely subsumes the other.

## Nondeterminism
If the old profile intentionally leaves behavior unspecified, the new profile may resolve that nondeterminism only when every chosen behavior remains within the old allowed behavior, or when the new restriction is explicitly classified as stricter. Refinement must not turn an underspecified security obligation into permission.

`OLD_ALLOWED(C) ⊇ NEW_ALLOWED(C)` is a useful candidate direction for protected authority outcomes, but only after defining exactly what counts as an observable authority outcome.

## Incomparable claims
If a field/claim changes meaning such that neither profile's accepted behavior set contains the other's, classify:
`INCOMPARABLE(C) => NO_SILENT_MIGRATION(C)`.

The claim requires an explicit semantic migration boundary, new domain/profile identifier, and fresh authority decision. Historical certificates remain valid only under their historical semantics.

## Security-specific observation
A pure trace relation can miss assumptions about the environment, freshness, authority epochs, or hidden security state. Therefore the trace alphabet for Nexo should include security-relevant observables such as profile/domain, authority epoch, decision digest, fence/generation, and rejection/quarantine outcomes. Contract assumptions must also be checked separately rather than assumed from trace compatibility. citeturn0search4

## Candidate decision
For Nexo certificate migration, the best current design candidate is **contract-aware trace refinement**, with simulation/refinement mappings used as proof techniques where applicable. It is not a final selection: the certificate claim language still needs formalization and adversarial counterexamples.

## Invariants
- `TRACE_COMPATIBILITY != AUTHORITY_COMPATIBILITY`
- `SIMULATION_PROOF != IMPLEMENTATION_CORRECTNESS`
- `UNDERSPECIFICATION != PERMISSION`
- `RESOLVING_NONDETERMINISM_MUST_NOT_ADD_AUTHORITY`
- `INCOMPARABLE_CLAIM => EXPLICIT_MIGRATION`
- `CHANGED_ASSUMPTION => CONTRACT_REFINEMENT_CHECK`
- `HISTORICAL_SEMANTICS != CURRENT_SEMANTICS`
- `PROFILE_ID + DOMAIN + AUTHORITY_EPOCH MUST BE BOUND`

## Status
Research complete. No implementation or formal verification performed. This is a design candidate, not a finalized semantic relation.
