# NEXO AB104.753R — completed-receive retention/replay and disconnect lifecycle re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct source findings

`MockSelector.completedReceives` is a mutable list. `completeReceive()` appends to it, and `completedReceives()` returns the same list. `MockSelector.clear()` clears it, but normal `MockSelector.poll()` does not clear completed receives.

`NetworkClient.handleCompletedReceives()` iterates `selector.completedReceives()`. It does not clear that list itself. Therefore, in the test double, if `poll()` exits by exception during receive processing, the receive list is not removed by `MockSelector.poll()` or by `handleCompletedReceives()`; source inspection of this test harness indicates the receive remains in the list until explicit clearing. This is test-harness behavior and must not be generalized automatically to the production selector implementation.

For connection cleanup, `NetworkClient.disconnect(nodeId)` explicitly closes the selector, clears all in-flight requests for the node through `cancelInFlightRequests`, and marks connection state disconnected. Automatic timeout/disconnection processing similarly clears in-flight requests. But these paths occur after `handleCompletedReceives()` in `poll()`, so an exception escaping receive parsing prevents those later cleanup phases in the same invocation.

## Evidence boundary

No test was found that injects an independently correlated response, catches the resulting `poll()` exception, and then checks whether the receive is replayed on a second `poll()` or whether the connection/request state is repaired. Therefore replay-after-mismatch is NOT_EXECUTED.

The distinction is important:
`MockSelector test-list retention != production-selector receive retention`.
