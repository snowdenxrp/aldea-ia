# Nexo AB104.427 — Trusted Time vs Generations/Fences and TCB Minimization

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.426 → AB104.427
Implementation: NOT PERFORMED

## Research question

Which Nexo properties genuinely require physical time, which can be enforced with monotonic generations/fences, and when would a trusted global clock become an unnecessary TCB component?

## Evidence

RFC 5905 describes NTP synchronization and explicitly discusses clock error, frequency error, synchronization, authentication, and the security consequences of time failure. It also notes the interaction between trusted time and cryptographic lifetime enforcement. citeturn0search1

NIST guidance treats synchronization accuracy as application-dependent and distinguishes time synchronization mechanisms from the security requirements of the applications using them. citeturn0search0turn0search4

Google's Spanner architecture uses bounded clock uncertainty as part of externally consistent transaction ordering, illustrating that physical-time assumptions can be made explicit rather than treated as exact global truth. citeturn0search9turn0search14

The distributed-systems literature on fencing/leases provides a contrasting approach: stale ownership can be rejected using monotonic fencing tokens at the resource boundary, without requiring a globally synchronized clock for every authorization decision. This is consistent with the Nexo findings from AB104.381–AB104.385.

## Core finding

Nexo should not introduce trusted physical time into the TCB merely because timestamps are convenient.

Candidate separation:

PHYSICAL_TIME
→ properties about elapsed time / deadlines / temporal validity

GENERATION + FENCE
→ properties about authority order / stale actor exclusion

STATE_VERSION / INCARNATION
→ properties about current resource state

Therefore:

TIME_REQUIRED_FOR_PROPERTY != TIME_REQUIRED_FOR_AUTHORITY_ORDER

## Property taxonomy

### P0 — pure state relation

Example:
“resource version equals expected version.”

Candidate mechanism:
STATE_VERSION.

Physical time unnecessary.

### P1 — authority freshness by generation

Example:
“request was issued under the current authority epoch.”

Candidate:
AUTHORITY_EPOCH + protected final gate.

Physical time unnecessary.

### P2 — stale actor exclusion

Example:
“old owner cannot mutate the resource after fencing.”

Candidate:
RESOURCE_FENCE_GENERATION enforced by the resource.

Physical time unnecessary if the resource-side fencing mechanism is authoritative.

### P3 — replay exclusion

Example:
“same EffectID cannot be admitted twice.”

Candidate:
DURABLE_REPLAY_STATE + EFFECT_ID + generation.

Physical time optional unless policy intentionally uses expiry windows.

### P4 — dependency currentness

Example:
“evidence was generated under current policy/trust/dependency generations.”

Candidate:
GENERATION BINDING + invalidation generation.

Physical time may be used as supplementary freshness evidence, but does not replace state generation.

### P5 — absolute deadline

Example:
“operation must not be admitted after 12:00:00 UTC.”

This genuinely requires a time basis.

Candidate:
TRUSTED_TIME_CONTEXT + uncertainty + explicit deadline semantics.

### P6 — elapsed-duration safety property

Example:
“if condition X persists for no more than N seconds, transition Y is safe.”

Requires a bounded duration mechanism.

A local monotonic clock may suffice if the entire property is local.

Distributed duration requires an explicit clock/uncertainty model.

### P7 — certificate/credential expiry

If expiry is defined in physical time, trusted time is required somewhere in the validation path.

However, an alternative protocol can replace time-based expiry with generation/revocation state where semantics permit.

## Trusted time is not one thing

Candidate layers:

T0 local wall clock;
T1 local monotonic clock;
T2 synchronized physical clock;
T3 bounded-uncertainty distributed clock;
T4 provider-enforced clock;
T5 independent trusted-time authority.

The required layer is property-specific.

## TCB minimization principle

If property P can be enforced by:

PROTECTED_STATE
+
GENERATION
+
FENCE

without physical-time assumptions,

then adding a global trusted clock increases dependency surface without increasing the proof obligation for P.

Candidate:

UNNECESSARY_TIME_DEPENDENCY => TCB_EXPANSION_WITHOUT_PROPERTY_GAIN.

## Authority epochs versus time

Authority revocation can be modeled:

EPOCH_7 → EPOCH_8

rather than:

valid_until = 12:00:00.

This avoids ambiguity caused by clock skew for authority ordering.

But epoch rollover still requires a protected authoritative mechanism.

Therefore:

GENERATION_ORDER != FREE_CLOCK.

## Fence generations versus lease expiry

Lease expiry answers:

“Has a duration elapsed according to some clock?”

A fence answers:

“Which generation is currently permitted to mutate this resource?”

For stale-actor exclusion, the second question is usually closer to the safety property.

Candidate:

SAFETY = FENCE_ENFORCEMENT
LIVENESS = LEASE/EXPIRY

Do not use lease expiration as a substitute for resource-side fencing when stale requests can cause protected effects.

## Revocation

Physical-time revocation:

credential valid until T.

Generation-based revocation:

credential bound to AUTHORITY_EPOCH E;
current epoch becomes E+1.

The second can provide deterministic ordering without synchronized clocks.

But it may not satisfy a policy requiring automatic expiration after elapsed time.

## Evidence freshness

Time-based freshness:

age <= Δ.

Generation-based currentness:

evidence_generation == current_generation.

The latter is stronger for state invalidation but cannot answer absolute elapsed-age requirements.

Candidate combined policy:

CURRENTNESS = generation/state relation
FRESHNESS = optional time relation

Do not conflate them.

## Recovery

Recovery should prefer generation changes where possible:

NORMAL_AUTHORITY_E
→ RECOVERY_AUTHORITY_E+1
→ NEW_CURRENT_AUTHORITY_E+2.

This makes restored old state unable to become current merely because its timestamp looks recent.

Time may still be needed for recovery windows or operator/governance deadlines.

## External providers

Provider-side expiration may require provider time.

If Nexo relies on that expiration for a protected claim:

PROVIDER_TIME_SOURCE becomes part of dependency closure.

But Nexo should not assume that provider expiry proves cancellation/non-execution unless the provider semantics explicitly establish it.

## Hybrid design candidate

Nexo could use:

1. generations/fences for authority ordering;
2. resource versions/incarnations for state identity;
3. durable replay state for effect identity;
4. logical ordering for causal protocol events;
5. physical time only for claims that actually require elapsed-time semantics.

This minimizes trusted-time scope.

## Trusted-time failure

If physical time is required and time becomes:

DEGRADED / UNKNOWN / UNTRUSTED

then affected claims should transition according to policy:

HOLD
REVALIDATE
DOWNGRADE
QUARANTINE

Do not silently replace trusted time with an untrusted local clock.

## Time as evidence, not authority

A trusted-time result should remain:

TIME_EVIDENCE

and be evaluated by Z1.

It should not itself authorize an operation.

Therefore:

TRUSTED_TIME_RESULT != AUTHORITY.

## Clock compromise

If a trusted time source is compromised:

1. identify affected claims;
2. freeze time-dependent admission where required;
3. preserve historical evidence;
4. determine compromise interval if possible;
5. invalidate dependent freshness decisions;
6. revalidate affected claims;
7. reconcile effects whose timing was security-relevant.

Historical timestamp validity does not automatically remain current assurance.

## Decision rule candidate

Before adding physical time to a protected path:

1. identify the exact property;
2. prove that generation/fence/state mechanisms cannot express it;
3. define required temporal semantics;
4. define clock uncertainty/failure model;
5. bind clock evidence to current trust/policy generations;
6. include time source in dependency closure;
7. define UNKNOWN behavior.

If steps 1–2 cannot justify physical time:

prefer generation/fence/state mechanisms.
