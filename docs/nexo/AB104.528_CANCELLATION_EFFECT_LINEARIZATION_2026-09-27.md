# Nexo AB104.528 — Cancellation/effect linearization boundary

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A provider can only close the cancellation-vs-effect race if it exposes an authoritative ordering or terminal operation state whose semantics establish which side won. A client observing CANCELLED and another observer seeing completion does not create an order by itself.

## Evidence
Google's Long Running Operations contract says cancellation is asynchronous and best-effort; clients must query the operation to determine whether cancellation succeeded or the operation completed despite cancellation. etcd provides atomic transactions guarded by revisions, and its linearizable mode provides current-state reads; serializable reads may be stale. Kubernetes finalizers likewise keep a deletion request in a terminating state until cleanup completes.

## Candidate linearization cases
L0 — cancellation request only: no ordering proof.
L1 — cancellation accepted: request entered provider state; no proof effect did not commit.
L2 — provider terminal cancellation with authoritative operation state: establishes provider-scoped terminal outcome if its semantics exclude later completion.
L3 — provider exposes a single ordered state transition showing cancellation before effect commit: strongest provider-local closure.
L4 — cross-domain bound: provider outcome is cryptographically/transactionally bound to Nexo fence/effect identity and target incarnation.

Only L3/L4 can support a strong claim that cancellation won the provider's effect race; L2 may be enough for a provider-scoped state if the provider's contract explicitly makes it terminal and non-applying.

## Ambiguous observation
If Nexo observes CANCELLED but later receives a completion receipt, the records must not be overwritten. Preserve both observations and classify the operation as CONFLICTING_PROVIDER_EVIDENCE / UNKNOWN until authoritative provider ordering resolves the conflict.

If the provider cannot expose ordering, current target state alone does not establish whether the old effect committed.

## Critical distinctions
- CANCEL_ACK != CANCELLATION_LINEARIZATION
- PROVIDER_TERMINAL_STATE != CROSS_DOMAIN_ORDER
- TWO_OBSERVATIONS != ORDERING_PROOF
- CANCELLED_AFTER_EFFECT != NOT_APPLIED
- EFFECT_RECEIPT_AFTER_CANCEL != AUTOMATIC_CONFLICT_RESOLUTION
- LINEARIZABLE_PROVIDER_READ != NEXO_PROVIDER_CROSS_DOMAIN_ORDER
- FENCE_REVISION != PROVIDER_COMMIT_REVISION unless explicitly bound

## Nexo implication
The external-effect protocol should require an explicit provider ordering/terminality capability before using cancellation as a negative-effect closure mechanism. Otherwise cancellation is a control request plus evidence, while the original operation remains independently reconcilable.
