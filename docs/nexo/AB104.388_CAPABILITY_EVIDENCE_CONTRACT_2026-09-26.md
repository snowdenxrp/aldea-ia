## Research question
What evidence is sufficient to promote a provider capability from UNKNOWN/UNVALIDATED to VALIDATED?

## Promotion rule

A capability may become VALIDATED only when all claim-specific predicates hold:

1. The exact provider/resource/incarnation and adapter path are identified.
2. The provider's documented semantics support the claimed primitive, where documentation exists.
3. The actual adapter path is shown to exercise that primitive.
4. The protected operation is tested at the boundary where the claim is made.
5. Negative/adversarial behavior is tested, not only successful behavior.
6. Restart/failover semantics are tested when durability is part of the claim.
7. The evidence is bound to the relevant provider/API/adapter versions.
8. No known contradictory evidence remains unresolved.
9. The claim's scope and limitations are explicitly recorded.
10. A capability is not promoted merely because another provider or another API has the same feature name.

## Evidence classes

### D — Documentation
Official provider documentation establishes that an API/feature is specified.

Strength: establishes intended semantics.
Does not establish: actual deployed adapter path, failover preservation, or Nexo-specific composition.

### O — Direct observation
Controlled execution demonstrates the provider behavior.

Strength: validates observed runtime behavior for the tested scope.
Does not establish: all future versions, all failover paths, or untested concurrency cases.

### A — Adversarial observation
Tests stale fence, stale target, concurrent mutation, timeout, delayed request, restart, and relevant negative paths.

Strength: exposes falsely permissive assumptions.

### F — Failover/recovery evidence
Exercises restart, replica transition, provider failover, resource replacement, and recovery.

Required for claims involving DFS/XF.

### I — Independent evidence
A second logically independent evidence path confirms the same property.

Important for high-consequence claims because one test harness/provider telemetry path may share common-mode failure.

| Capability | Minimum promotion evidence |

| AF | D + O + A at actual mutation boundary; stale-generation rejection must be demonstrated |
| DFS | AF evidence + F showing fence/high-water mark survives recovery |
| EI | D + O demonstrating exact identity binding |
| ID | D + O + duplicate/retry adversarial test |
| DI | D/O of durable intent ordering + crash-window test |
| AB | D + O showing acknowledgement binds to exact effect identity and defined semantics |
| R | D + O + ambiguous-outcome/reconciliation test |
| CA | D + O + race/acceptance-window tests |
| RV | D + O + exact compensation identity/state test |
| XF | F + A across the specific failover mechanism |
| MC | D + O + A across every participant and coordination boundary |

## Negative evidence rule
A failed adversarial test is not merely a test failure; it is evidence against the claimed capability.

Examples:
- stale RF accepted → AF cannot be VALIDATED for that boundary;
- old RF accepted after restart → DFS/XF cannot be VALIDATED;
- duplicate EffectID creates duplicate effect → ID claim fails;
- ACK cannot identify which EffectID executed → AB is insufficient for confirmation;
- reconciliation cannot distinguish two same-looking effects → R is insufficient for exact confirmation.

## Evidence freshness and invalidation
Capability evidence becomes stale when any relevant semantic input changes:
- provider API/version changes;
- resource replacement/incarnation changes;
- adapter implementation/version changes;
- gateway policy/fence mapping changes;
- failover topology changes;
- provider configuration changes affecting conditional/fence enforcement;
- observed semantic drift;
- unresolved security/control-plane incident.

Status should become UNKNOWN/DEGRADED until revalidation.

## Independence / common-mode requirement
Multiple observations from the same adapter, same provider telemetry, or same control plane are not automatically independent.

For high-consequence claims, Nexo should record an evidence dependency graph:
EVIDENCE_NODE → DEPENDS_ON → PROVIDER / ADAPTER / CONTROL_PLANE / OBSERVER / RESOURCE

A claim should not be called independently corroborated when all evidence nodes share the same failure domain.

## Capability validation is claim-specific
A provider can be:
- VALIDATED for target conditional writes;
- UNKNOWN for authority fencing;
- VALIDATED for idempotency;
- UNKNOWN for failover preservation;
- VALIDATED for reconciliation.

There is no single global "provider is safe" bit.

## Candidate promotion state machine

UNVALIDATED
→ DOCUMENTED
→ OBSERVED
→ ADVERSARIALLY_VALIDATED
→ FAILOVER_VALIDATED (when required)
→ CAPABILITY_VALIDATED

Any contradiction:
→ UNKNOWN/DEGRADED

Safety-critical unresolved contradiction:
→ QUARANTINED

Revalidation must produce a new evidence record; old evidence remains immutable historical evidence.
