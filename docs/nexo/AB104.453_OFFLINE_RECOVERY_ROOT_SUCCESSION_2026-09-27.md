# Nexo AB104.453 — Offline / Pre-established Recovery Root and Succession

Date: 2026-09-27
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.452 → AB104.453
Implementation: NOT PERFORMED

## Research question

Can Nexo use a pre-established recovery root without turning it into an unbounded permanent super-root, and what happens when that root is lost, compromised, rotated, or its custodians disappear?

## Evidence

RFC 6024 states that trust-anchor management requires an initial trust-anchor manager and that bootstrap may use out-of-band transport; it also requires recovery from loss or compromise of a trust-anchor manager without depending on ordinary trust-store reinitialization. It requires source authentication, authorization and replay detection, and emphasizes that trust-anchor constraints define scope. citeturn0search1

NIST SP 800-57 notes that additional key copies increase exposure and that compromise requires revocation, replacement where needed, and damage assessment. citeturn0search2

NIST defines split knowledge so that fewer than the threshold number of key shares provide no useful key knowledge. This supports threshold custody as a possible protection mechanism, but split knowledge alone does not prove independence of custodians or governance. citeturn0search0

NIST SP 800-193 describes protected recovery mechanisms, trusted recovery authorization, notification of recovery events, protection against rollback to vulnerable versions, and the need for backups whose protection is at least as strong as the active critical data. citeturn0search3

## Core finding

A pre-established recovery root is useful only if it is itself governed as a protected trust dependency.

Therefore:

RECOVERY_ROOT != INVULNERABLE_ROOT

and:

RECOVERY_ROOT != UNBOUNDED_SUPER_ROOT.

The recovery root must have explicit authority constraints.

## Attack R1 — recovery root can authorize anything

If the recovery root can directly authorize ordinary external effects, policy changes, arbitrary credentials and arbitrary history correction, it becomes a hidden permanent super-root.

Candidate invariant:

RECOVERY_ROOT_SCOPE ⊂ NORMAL_SYSTEM_EFFECT_SPACE

for recovery-specific operations, unless a separate governance decision explicitly expands scope.

## Attack R2 — root key copied everywhere

More copies improve availability but enlarge compromise exposure. NIST explicitly notes this tradeoff. citeturn0search2

Therefore availability copies must not automatically count as independent authority.

COPY_COUNT != INDEPENDENCE.

## Attack R3 — threshold shares all depend on one custodian domain

A 3-of-5 scheme can still have one organization, administrator, HSM vendor, identity provider or backup system controlling all five shares.

Therefore:

THRESHOLD >= K does not imply K independent authorities.

The dependency/failure-domain closure must be evaluated.

## Attack R4 — threshold share reconstruction becomes a permanent secret

If recovery requires reconstructing a complete private key, the reconstructed secret becomes a new high-value target.

Candidate preference:

THRESHOLD_SIGNING_WITHOUT_LONG_LIVED_RECONSTRUCTED_ROOT

when technically and operationally suitable.

If reconstruction is unavoidable, the ceremony must define memory exposure, zeroization, custody, destruction and post-ceremony invalidation.

## Attack R5 — lost custodians

If one or more custodians disappear, become unavailable, or lose credentials, recovery availability can collapse.

Candidate:

CUSTODIAN_LOSS != AUTHORITY_LOSS

provided the recovery governance has a protected succession/rotation mechanism.

## Attack R6 — succession is self-authorized

A custodian appoints their successor through the ordinary Nexo system after compromise.

That does not establish independent succession.

Succession must be authorized by a currently valid recovery governance basis.

## Attack R7 — root compromise with valid signatures

A compromised recovery root can produce cryptographically valid recovery authorizations.

Therefore signature validity proves origin under the root, not that the root is currently uncompromised or that the requested operation is legitimate.

Candidate:

VALID_SIGNATURE != CURRENT_RECOVERY_AUTHORITY_VALIDITY.

## Attack R8 — root rollback

An older recovery root or older policy is replayed.

RFC 6024 specifically requires replay detection for trust-anchor management and warns that replay can reintroduce compromised trust anchors. citeturn0search1

Candidate controls:
- recovery generation;
- root incarnation;
- monotonic/anti-rollback state;
- nonce/event binding;
- explicit revocation;
- protected evidence of the latest accepted recovery generation.

## Attack R9 — recovery root restores compromised root

The recovery root signs:
“restore Root-A.”

If Root-A belongs to the compromised interval, recovery can reintroduce the compromise.

Candidate:

COMPROMISED_ROOT_INCARNATION ∈ INVALIDATED_SET => NEVER_REACTIVATE.

Replacement requires a new incarnation.

## Attack R10 — backup is mistaken for current root

A backup copy of the recovery root does not prove that it is the current valid incarnation.

Candidate:

BACKUP_PRESENT != CURRENT_RECOVERY_ROOT.

The current recovery generation must be independently established.

## Attack R11 — recovery root and backup share the same failure domain

A geographically separate backup may still share:
- same cloud;
- same administrator;
- same identity provider;
- same vendor;
- same signing service;
- same software;
- same policy repository.

Geographic separation alone is insufficient.

Candidate:

RECOVERY_INDEPENDENCE = DEPENDENCY_CLOSURE_PROPERTY.

## Attack R12 — root cannot be revoked while Nexo is down

If revocation exists only inside Nexo, a compromised recovery root can remain valid during the very period when Nexo cannot defend itself.

Candidate:

RECOVERY_ROOT_REVOCATION_MUST_HAVE_AN_EXTERNAL_OR_PREESTABLISHED_PATH.

## Attack R13 — root rotation creates simultaneous valid roots

During rotation, old and new roots both authorize recovery.

This creates ambiguity and replay windows.

Candidate transition:

OLD_ROOT_VALID → ROTATION_PENDING → NEW_ROOT_VALIDATED → ACTIVATED → OLD_ROOT_REVOKED.

The activation boundary must be durable and unambiguous.

## Attack R14 — partial rotation

Some recovery stores accept Root-B while others still accept Root-A.

Candidate:

ROOT_ROTATION_IS_NOT_COMPLETE_UNTIL_REQUIRED_PARTICIPANTS_HAVE_A_COMMON_ACTIVATION_GENERATION.

Unreachable participants may remain quarantined rather than silently accepting divergent authority.

## Attack R15 — root succession without evidence preservation

The new root replaces the old root and deletes evidence of why.

This destroys auditability.

Candidate:

SUCCESSION_EVENT_IS_IMMUTABLE_EVIDENCE.

It records:
- predecessor;
- successor;
- authorization basis;
- generation;
- participants;
- reason;
- scope;
- time/nonce;
- invalidation status.

## Attack R16 — root becomes historical correction oracle

Recovery root says:
“everything signed before compromise was false.”

That exceeds the evidence available.

Root succession can establish new authority; it cannot retroactively prove every historical claim.

## Candidate recovery-root lifecycle

PROVISIONED
→ ACTIVE
→ ROTATION_PENDING
→ NEW_ROOT_VALIDATED
→ NEW_ROOT_ACTIVE
→ OLD_ROOT_REVOKED
→ RETIRED
→ DESTROYED / ARCHIVED_EVIDENCE

Compromise branch:

ACTIVE
→ COMPROMISED_SUSPECTED
→ RECOVERY_RESTRICTED
→ REVOKED
→ REPLACEMENT_REQUIRED.

Loss branch:

ACTIVE
→ UNAVAILABLE
→ QUORUM_EVALUATION
→ SUCCESSION_OR_EXTERNAL_RECOVERY.

## Candidate succession ceremony

1. Detect root rotation/loss/compromise.
2. Enter recovery-restricted state.
3. Freeze ordinary recovery-root privileges as required.
4. Authenticate the succession authority.
5. Verify dependency/failure-domain independence.
6. Verify predecessor status.
7. Generate a fresh root incarnation.
8. Bind new root to a new activation generation.
9. Publish/record immutable succession evidence.
10. Activate new root.
11. Revoke predecessor.
12. Verify required participants converge.
13. Reconcile outstanding recovery authorizations.
14. Explicitly release restricted state.

## Important distinction: threshold custody vs threshold governance

Threshold cryptography can protect a secret.

It does not by itself establish:
- who should be a custodian;
- whether custodians are independent;
- what they are allowed to authorize;
- whether a requested recovery is legitimate;
- whether historical claims are true.

Therefore:

THRESHOLD_CRYPTOGRAPHY ≠ THRESHOLD_GOVERNANCE.
