## Research question
What is the minimum provider capability vector required for E0–E5, and what happens if capability weakens while an operation is already in flight?

Fresh provider documentation confirms that conditional writes can atomically protect target state at the provider boundary, but that is distinct from an authority fence. For example, S3 evaluates If-Match against the target ETag during the write and rejects mismatches; this is useful target protection but does not itself encode Nexo authority generation. citeturn0search0turn0search3

## Capability notation
Let:
- AF = authority fence at claimed mutation boundary
- DFS = durable fence state across restart/failover
- TC = target conditional/version check
- EI = stable effect identity
- ID = defined idempotency/dedup semantics
- DI = durable intent before crash-sensitive release
- AB = acknowledgement bound to exact effect identity/semantics
- R = exact reconciliation
- CA = cancellation with defined race semantics
- RV = reversal/compensation semantics
- XF = failover preserves required guarantees
- MC = multi-resource coordination semantics

A capability marked REQUIRED means the property cannot be claimed without it under the current research model. "Conditional" means effect/provider-specific; absence forces a narrower claim, HOLD, UNKNOWN, or a new protected path.

## Minimum vectors

| Effect class | Minimum vector | Main property supported | Important missing capability changes |
|---|---|---|---|
| E0 observation/read | TC or equivalent freshness + AB + R when outcome can be ambiguous | bounded/current observation claim | AF usually not needed unless read itself has authority-sensitive side effect; no R means ambiguity remains UNKNOWN |
| E1 reversible/compensatable mutation | AF + DFS + TC + EI + DI + AB + R + RV | protected mutation with recovery path | no AF => stale-authority property unavailable; no R => ambiguous outcome persists; no RV => compensation claim unavailable |
| E2 idempotent mutation | AF + DFS + TC + EI + ID + DI + AB + R | retry-safe-equivalent under provider semantics | ID without AF does not prevent stale-authority effect |
| E3 non-idempotent but reversible | AF + DFS + TC + EI + DI + AB + R + RV; ID strongly preferred where supported | controlled non-idempotent effect with compensation path | no RV => no safe compensation claim; no R => UNKNOWN after ambiguity |
| E4 irreversible/non-compensatable | AF + DFS + TC where applicable + EI + DI + AB + R + XF; CA if a pre-acceptance stop property is claimed | strictest protected external effect | any essential gap => HOLD/REJECT or claim downgrade; no blind retry |
| E5 multi-resource/cross-resource | per-participant E1/E2/E3/E4 vector as applicable + MC + participant-level R + participant identity/fence + XF | candidate coordinated composition | any relevant participant gap => global property narrowed; partial commit/UNKNOWN explicit |

### Important qualification
The vectors are not universal provider requirements. They are the minimum candidate controls for the corresponding **claims** in Nexo's current contract. A provider may support a narrower operation without satisfying the stronger claim.

## Capability downgrade model
Provider capability must be versioned and bound to:
PROVIDER_ID + RESOURCE_ID + RESOURCE_INCARNATION + ADAPTER_VERSION + CAPABILITY_PROFILE_VERSION.

A capability change must be treated as a protected state change, not ordinary telemetry.

### Safe rule
If a required capability disappears while an operation is:
- REQUESTED/ADMITTED: reject or re-admit under current profile.
- INTENT_DURABLE: no external release until current capability is revalidated.
- READY: do not release if required property can no longer be enforced.
- ATTEMPT_RECORD_DURABLE: release only if the provider boundary still enforces the required fence/condition; otherwise HOLD/UNKNOWN according to whether release may have escaped.
- EXTERNAL_ATTEMPTED: do not retroactively classify the effect as safe; resolve via ACK/reconciliation.
- UNKNOWN: reconcile before any retry unless the provider's identity semantics independently establish safe-equivalent retry.
- CONFIRMED: capability downgrade is not retroactive; future operations use the new profile.

## Adversarial downgrade attacks

### A — Fence capability disappears after FINAL_GATE
Local state says authority was valid, but provider no longer enforces the fence.
Result: stale-authority exclusion cannot be claimed for a release occurring after the capability loss. HOLD unless a stronger boundary still enforces it.

### B — Failover silently loses fence high-water mark
A provider restarts and accepts old RF values.
Result: provider failover semantics violated. NO_EFFECT_FROM_STALE_AUTHORITY becomes unavailable. Quarantine/HOLD until fence state is restored and stale work is controlled.

### C — Adapter reports P5 but runtime path falls back to P1
A feature negotiation/configuration says native fence exists, but actual request path only supplies ETag.
Result: capability profile mismatch; the stronger claim is invalid. Treat as safety-relevant configuration fault.

### D — Capability profile changes while multi-resource operation is partially committed
R1 remains P5, R2 downgrades to P1.
Result: do not upgrade global status from PARTIAL/UNKNOWN to success merely because R1 is strong. Reconcile R2 and preserve participant-level evidence.

### E — New provider generation claims fresh capability but resource incarnation changed
New RF is valid for an old/new scope incorrectly.
Result: RESOURCE_INCARNATION mismatch; reject. A new provider-local token cannot silently authorize an old operation against a replacement resource.

### F — Capability disappears after external acceptance
Not retroactive. Preserve exact historical capability profile/version used at acceptance. Future effects must use current profile.

### G — Gateway claims P4 but downstream is actually P0
Gateway authorization is not downstream stale-effect prevention.
Result: gateway may enforce its own boundary, but downstream claim must be downgraded/blocked according to effect class.

### H — Provider returns a successful ACK while capability profile is already UNKNOWN
ACK is not automatically confirmation unless the acknowledgement is bound to exact identity and the contract defines the provider semantics as sufficient. Otherwise reconcile.

## Capability state machine
Candidate states:
CAPABILITY_VALIDATED
CAPABILITY_DEGRADED
CAPABILITY_UNKNOWN
CAPABILITY_QUARANTINED

Transitions:
VALIDATED → DEGRADED when a required primitive is known lost.
VALIDATED → UNKNOWN when health/semantics cannot be established.
DEGRADED/UNKNOWN → QUARANTINED when safety-critical claims cannot be maintained.
DEGRADED/UNKNOWN → VALIDATED only after explicit revalidation of the exact adapter/provider path, version, resource incarnation, and required semantics.

No operation may silently retain an old capability profile merely because its admission happened earlier.

## Candidate invariants
