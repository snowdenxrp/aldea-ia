# Nexo AB104.394 — Adversarial Closure-Engine Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## 1. Objective
Attack the AB104.393 dependency-closure mechanism itself. The closure engine must not turn an incomplete, stale, contradictory or race-affected graph into a current safety claim.

External evidence reinforces two relevant boundaries: RFC 9334 separates Attester, Verifier and Relying Party and warns that freshness cannot eliminate state-change races; in-toto demonstrates explicit provenance chains but its own security audit documents replay/reuse issues when metadata is not sufficiently bound to its governing layout. Therefore Nexo must bind graph identity, policy and dependency state explicitly rather than rely on graph presence alone. citeturn0search1turn0search4

## 2. Attack A — graph cycles
Attack: A depends on B, B depends on C, C depends on A.
Required behavior: traversal must terminate without treating cycle completion as evidence of validity. The closure result becomes UNRESOLVED/UNKNOWN unless the cycle is explicitly permitted and all nodes have independently resolvable state.
Candidate invariant: CLOSURE_CYCLE != VALIDATION.

## 3. Attack B — conflicting dependency paths
Attack: Claim reaches the same provider through two paths with different resource incarnations, policy versions or epochs.
Required behavior: do not choose one path silently. The claim enters UNKNOWN/QUARANTINED until the contradiction is resolved or policy proves one path irrelevant.
Candidate invariant: CONFLICTING_REQUIRED_DEPENDENCIES_MUST_NOT_BE_COLLAPSED.

## 4. Attack C — stale graph version
Attack: graph G7 is evaluated against current dependency state while the claim was issued against G6, or vice versa.
Required behavior: graph identity/version is checked against the evidence-bound dependency root. A newer graph does not automatically reinterpret old evidence; a stale graph cannot establish current usability.
Candidate invariant: GRAPH_VERSION_MUST_BIND_TO_EVIDENCE_CONTEXT.

## 5. Attack D — reverse-index divergence
Attack: optimized index says Dependency X affects claims A and B, but authoritative graph says X affects A, B and C.
Required behavior: reverse index is advisory only. Current claim evaluation recomputes authoritative closure. Divergence itself is an integrity/operational warning and must not cause omission of C.
Candidate invariant: REVERSE_INDEX_IS_NOT_AUTHORITY.

## 6. Attack E — snapshot race
Attack: closure reads graph at G7, then dependency state changes from epoch E4 to E5 before evaluation completes.
Required behavior: graph and required protected dependency versions must be evaluated against a coherent snapshot or equivalent validation boundary. A mixed snapshot is UNKNOWN/HOLD, not CURRENT.
Candidate invariant: CLOSURE_EVALUATION_REQUIRES_COHERENT_STATE_SNAPSHOT.

## 7. Attack F — graph changes during traversal
Attack: node/edge is added, removed or replaced while traversal is running.
Required behavior: traversal must be bound to an immutable graph snapshot/version. If the graph cannot provide snapshot semantics, the engine must detect version change and restart/reject rather than combine generations.
Candidate invariant: NO_CROSS_GENERATION_CLOSURE.

## 8. Attack G — policy changes after appraisal
Attack: evidence was verified under policy P7; current operation requires P8.
Required behavior: P7 remains historical evidence. It cannot satisfy a P8 current-use requirement unless policy explicitly defines compatibility/equivalence and that compatibility itself is current and protected.
RFC 9334 distinguishes the Verifier's appraisal policy from the Relying Party's application-specific policy and notes that appraisal policy can change after evidence generation. citeturn0search1

## 9. Attack H — compromise timing
Timeline:
1. Evidence E is issued under dependency D1.
2. E is verified.
3. D1 is compromised or revoked.
4. Claim C is requested for operational use.
Required behavior: historical verification remains retained; current usability becomes UNKNOWN/QUARANTINED unless an independent, current validation establishes the required property.

If compromise happens after an external effect was already confirmed, the historical confirmation is not erased. If compromise affects evidence needed to establish an unresolved outcome, that outcome may become UNKNOWN and require reconciliation.

## 10. Attack I — dependency appears only after use
Attack: a previously omitted transitive dependency is discovered after a claim was used.
Required behavior: do not backfill it as if it had been validated. Preserve the original evaluation, mark the completeness failure, and re-evaluate the current claim under the expanded closure.
Candidate invariant: LATE_DISCOVERED_DEPENDENCY != RETROACTIVE_VALIDATION.

## 11. Attack J — replayed provenance
Attack: valid old evidence or an old graph is replayed after replacement.
Required behavior: bind current-use evaluation to graph identity, policy version, resource incarnation, dependency epochs and freshness. in-toto's security audit documents real replay/reuse classes, showing why provenance metadata needs explicit binding rather than merely being signed. citeturn0search4turn0search24

## 12. Attack K — nested gateway dependency
Attack: gateway G is validated, but downstream resource R silently changes from a fenced path to an unfenced fallback.
Required behavior: the closure includes the actual enforcement path. A gateway assertion cannot substitute for downstream enforcement if downstream behavior is part of the claimed property.
Candidate invariant: CLAIMED_ENFORCEMENT_PATH_MUST_BE_IN_CLOSURE.

## 13. Attack L — failover path substitution
Attack: active resource uses durable fence state, then failover activates a path that lacks the same high-water mark.
Required behavior: failover state is a dependency. If preservation is not established, the capability becomes UNKNOWN/DEGRADED and dependent safety claims cannot remain unqualified.

## 14. Candidate atomic evaluation boundary
AB104.394 strengthens AB104.393 with a candidate evaluation sequence:
1. Acquire immutable graph snapshot/version.
2. Resolve complete required dependency closure.
3. Acquire or bind the protected state versions/epochs for all currentness-required dependencies.
4. Validate graph integrity, identity, scope and policy binding.
5. Check every dependency against its bound protected state.
6. Detect graph-version or protected-state changes before commit of the evaluation result.
7. If any relevant generation changed, discard the mixed evaluation and retry from a new coherent snapshot.
8. Persist the evaluation result with graph version, dependency-state versions, policy version and invalidation set.

This is a candidate protocol, not yet a formal atomicity proof.

## 15. Machine-checkable result classes
- CURRENT: complete closure, coherent snapshot, all required dependencies valid/current, no contradiction.
- DEGRADED: policy explicitly permits bounded degradation and no safety-critical dependency is unresolved.
- UNKNOWN: closure incomplete, state snapshot incoherent, required freshness unavailable, or outcome cannot be established.
- QUARANTINED: dependency compromise/revocation or graph integrity failure.
- HISTORICAL_ONLY: retained historical result that is not admissible for current use.

UNKNOWN and QUARANTINED must not silently become CURRENT through retry alone.

- QUARANTINED != CURRENT

## 17. What remains open
This attack closes several unsafe shortcuts in the candidate closure engine, but it does not prove completeness of dependency discovery or atomicity of the underlying protected state.

Next unresolved questions:
1. Can the graph snapshot and all dependency-state versions be captured under one authoritative linearization boundary without over-expanding the TCB?
2. What happens when the dependency set itself changes during that boundary?
3. How are graph migrations/version coexistence handled?
4. How are Byzantine graph nodes and contradictory signed statements handled?
5. What minimum closure coverage is required for E0-E5 effect classes?
6. Can revocation propagate safely without a single global invalidation bottleneck?

## 18. Exact next action
AB104.395 — research and attack the coherent-snapshot/linearization boundary: dependency graph mutation concurrent with evidence evaluation, version coexistence, migration, revocation races, and whether a protected dependency snapshot can remain minimal without expanding the authoritative TCB.

No implementation or formal proof is claimed.
