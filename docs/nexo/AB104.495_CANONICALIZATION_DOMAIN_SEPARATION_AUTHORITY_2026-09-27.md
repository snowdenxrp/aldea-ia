# AB104.495 — canonicalization and domain separation for authority certificates

## Evidence
RFC 8949 defines deterministic encoding requirements so equivalent data has a single protocol-defined serialization; it warns that protocols must explicitly choose deterministic representations when multiple encodings could carry the same semantics. citeturn0search0turn0search5 RFC 8446 provides concrete domain-separation evidence: signatures include an explicit context string so signatures made in different contexts cannot be treated as interchangeable. citeturn0search1turn0search2 RFC 9180 similarly uses domain-separated, prefix-free labels to model cryptographic operations as independent even when underlying primitives are shared. citeturn0search4turn0search8

## Nexo requirement
A quorum certificate must sign a uniquely typed, deterministically encoded statement whose semantic domain is explicit. Candidate signed envelope:

`NEXO-QC-v1 || Domain || ProtocolID || DecisionType || MembershipEpoch || MembershipDigest || TrustBasisEpoch || ThresholdProfile || CheckpointDigest || View/Revision || DecisionDigest`

The exact byte serialization must be deterministic and versioned. Fields must not be accepted through multiple encodings that produce the same application meaning unless the canonicalization rule explicitly makes them identical.

## Domain separation
Different authorization purposes must use distinct domains, for example:
- `NEXO/QC/AUTHORITY_ACTIVATION/v1`
- `NEXO/QC/WITNESS_REENROLLMENT/v1`
- `NEXO/QC/CHECKPOINT_ACCEPTANCE/v1`
- `NEXO/QC/RECOVERY_RELEASE/v1`

A signature valid in one domain must never be interpreted as a statement in another domain.

## Replay / cross-protocol boundary
The signed bytes should bind protocol version, message type, membership epoch, configuration digest, trust-basis epoch, and relevant checkpoint/revision. This prevents an old valid signature from becoming a new authority statement merely because a verifier interprets the same payload under a different context.

New distinctions:
`VALID_SIGNATURE != VALID_SEMANTIC_CLAIM`
`VALID_SEMANTIC_CLAIM != VALID_CURRENT_AUTHORITY`
`CANONICAL_ENCODING != AUTHORIZATION`
`DOMAIN_SEPARATION != TRUST_INDEPENDENCE`
`PROTOCOL_VERSION != MEMBERSHIP_EPOCH`

## Canonicalization boundary
Canonical serialization prevents ambiguity between encoders/verifiers; it does not prove the truth of fields. Domain separation prevents cross-context interpretation; it does not establish that the signer is trustworthy. Epoch/configuration binding prevents replay across authority generations; it does not by itself prove independent governance.

## Adversarial cases
- alternate serialization of the same logical fields;
- omitted/default fields interpreted differently by old/new implementations;
- duplicate map keys or non-deterministic ordering;
- protocol-version confusion;
- domain-string collision or prefix ambiguity;
- same key authorized in multiple semantic domains;
- recovery certificate replayed as ordinary activation;
- old epoch certificate accepted by a verifier that checks signature but not current epoch.

## Invariants
- `ONE_SEMANTIC_STATEMENT => ONE_ACCEPTED_CANONICAL_ENCODING`
- `DIFFERENT_AUTHORIZATION_DOMAINS => DIFFERENT_DOMAIN_SEPARATION`
- `OLD_EPOCH_SIGNATURE => NO_CURRENT_AUTHORITY`
- `DOMAIN_VALIDITY != TRUST_VALIDITY`
- `CANONICALIZATION != TRUTH`
- `SIGNATURE_VALIDITY != SEMANTIC_AUTHORIZATION`
- `PROTOCOL_VERSION_MISMATCH => REJECT_OR_EXPLICIT_MIGRATION`
- `UNSPECIFIED_ENCODING_AMBIGUITY => NO_AUTHORITY_PROMOTION`

## Status
Research complete. Canonicalization and domain separation are necessary anti-confusion/replay boundaries but are not sufficient for trust independence, freshness, or external-state truth. No implementation or formal verification performed.

Next exact step: AB104.496 — investigate certificate evolution/version migration: how a new certificate schema or domain can be introduced without allowing old verifiers to accept weakened semantics or new verifiers to reinterpret historical certificates.
