# Nexo AB104.536 — Fence exhaustion, rollover, and namespace reuse

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A fencing token is safe only within an authority scope whose ordering remains monotonic and whose identity is not silently reused. Numeric monotonicity alone is insufficient: wraparound, restore, namespace reuse, or authority-epoch changes can make an old token numerically appear current.

## Evidence
etcd revisions are monotonically increasing over a cluster lifetime, but compaction removes older revisions. etcd also models key generations across create/delete lifetimes, while Kubernetes explicitly requires resourceVersion to be treated as opaque rather than numerically ordered. These sources support separating ordering values from identity, generation, and retention semantics. citeturn0search0turn0search1turn0search9

## Candidate fence identity
Fence = {
  AuthorityEpoch,
  FenceScope,
  FenceRevision,
  TargetIdentity,
  TargetIncarnation,
  IssuerIdentity,
  PredecessorFenceDigest,
  ActivationRevision,
  Status
}

Acceptance requires:
1. same protected FenceScope;
2. current AuthorityEpoch;
3. target identity/incarnation match;
4. FenceRevision valid and not below the last accepted fence for that scope;
5. predecessor/continuity evidence where required;
6. no rollback/restore state that can resurrect an older fence.

## Exhaustion/rollover
Never silently wrap FenceRevision to zero or a lower value.
Instead:
- enter FENCE_EXHAUSTION / ROTATION_PENDING;
- allocate a new AuthorityEpoch or namespace with an explicit trust transition;
- bind the new namespace to the old terminal fence;
- prevent old and new namespaces from both being accepted as current for the same protected scope;
- require provider-side transition if the provider enforces the fence.

A larger integer width reduces practical exhaustion but does not remove the semantic requirement.

## Restore/failover
Restoring a snapshot containing an older fence must not lower the live fence.
If the restored state cannot prove continuity with the current fence, recovery enters UNKNOWN/QUARANTINE and requires explicit recovery authorization.

## Namespace reuse
Reusing FenceScope after decommission is unsafe unless a new authority epoch/incarnation is bound. Otherwise delayed old messages can collide with a numerically valid new token.

## Critical distinctions
- FENCE_REVISION != FENCE_IDENTITY
- NUMERIC_MONOTONICITY != AUTHORITY_CONTINUITY
- WRAPAROUND != SAFE_RESET
- SNAPSHOT_RESTORE != FENCE_ROLLBACK_AUTHORIZATION
- NEW_NAMESPACE != NEW_TRUST_BASIS
- NAME_REUSE != INCARNATION_REUSE
- HIGHER_TOKEN != CURRENT_AUTHORITY without scope/epoch validation
- LARGER_INTEGER != SOLVED_ROLLOVER_SEMANTICS

## Candidate transition
ACTIVE(F,n)
-> EXHAUSTION_DETECTED
-> OLD_SCOPE_FENCED
-> NEW_EPOCH/NEW_SCOPE_PREPARED
-> CONTINUITY_VALIDATED
-> NEW_SCOPE_ACTIVATED
-> OLD_SCOPE_RETIRED

Any ambiguous dual-active condition => UNKNOWN_AUTHORITY / QUARANTINE.

## Nexo implication
Fence tokens need explicit identity, scope, epoch, continuity, and recovery semantics. The final architecture should never depend on a bare integer token. Rollover is an authority transition, not a counter reset.
