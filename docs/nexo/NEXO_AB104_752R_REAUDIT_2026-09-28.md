# NEXO AB104.752R — NetworkClient.poll() exception lifecycle re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct source findings

`NetworkClient.poll()` calls `handleCompletedReceives()` before disconnections, timeout handling, rebootstrap, and `completeResponses()`.

`handleCompletedReceives()` iterates the selector's completed receives. For each receive it first removes the next FIFO in-flight request and then calls `parseResponse()`. There is no local catch around `parseResponse()` inside this method, and `poll()` has no catch around the completed-action processing block. Therefore a non-special `CorrelationIdMismatchException` escapes the `poll()` call and the remaining statements in that invocation are not reached.

Because the request is removed before parsing, the mismatch can leave a consumed in-flight entry while the exception escapes. Any later completed receives in the same iteration are also not processed by that invocation. This is source-derived; no test was executed to establish the exact resulting state after the exception.

`completeResponses()` itself catches exceptions thrown by callbacks, but it is reached only after `handleCompletedReceives()` returns, so that catch does not protect a parse mismatch.

## Test evidence

Repository search found no dedicated `assertThrows(... client.poll() ...)` test for `CorrelationIdMismatchException`. Existing `NetworkClientTest` completeReceive→poll tests use matching correlation IDs or other response conditions.
