# Nexo AB104.525 — Late asynchronous completion across incarnation/fence changes

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A late provider completion or callback must be bound to the exact operation, target incarnation, and fence/generation that were authorized for it. A callback arriving after target replacement or fence advancement cannot silently apply to the new incarnation.

## Evidence
- AWS EC2 documents that mutating requests can return before asynchronous workflows finish and can time out before completion; idempotency prevents repeated completion when the same token and parameters remain within the provider's scope.
- AWS EC2 documents regional versus zonal idempotency scope, demonstrating that operation identity is not necessarily global.
- Kubernetes resourceVersion identifies an ordering point for stored state and watches can track subsequent changes; Kubernetes documentation also distinguishes stale/any-version reads from more current consistency semantics. Kubernetes controller-runtime documentation describes relisting when a watched version is no longer available, showing that a client cannot assume an old observation stream remains valid forever.
- Kubernetes v1.36 staleness mitigation explicitly detects stale controller caches, reinforcing that stale observations must not be treated as current state.

## Race
T0 authorize EffectID E against TargetIncarnation I1 and Fence F1
T1 external provider begins asynchronous work
T2 target is deleted/replaced; new incarnation I2 appears
T3 Nexo advances fence to F2
T4 old provider workflow completes
T5 late callback/receipt arrives referencing E/I1/F1

The callback is historical evidence for E/I1, not authority to mutate I2.

## Candidate acceptance rule
A late callback may be admitted as evidence only if:
1. EffectID/OperationID and request digest match the durable intent;
2. TargetIdentity and TargetIncarnation match the authorized incarnation;
3. provider evidence is bound to the provider scope that executed the operation;
4. callback/receipt status is authenticated and non-ambiguous;
5. the callback does not claim authority over a newer fence/incarnation;
6. any external mutation is reconciled against the current target before further action.

If the provider cannot bind completion to incarnation or operation identity, result remains UNKNOWN or requires conservative reconciliation.

## Critical distinctions
- LATE_CALLBACK != CURRENT_AUTHORITY
- OLD_EFFECT != NEW_INCARNATION
- TARGET_NAME != TARGET_INCARNATION
- PROVIDER_RECEIPT != AUTHORIZATION_TO_MUTATE_CURRENT_TARGET
- FENCE_ADVANCE != RETROACTIVE_CANCELLATION
- CALLBACK_AFTER_REPLACEMENT != PROOF_OF_CURRENT_TARGET_EFFECT
- ASYNC_COMPLETION != CURRENT_STATE
- PROVIDER_SCOPE != GLOBAL_IDENTITY

## Fence interaction
Advancing a Nexo fence prevents future protected admission only where the provider actually enforces the fence/precondition. It cannot retroactively undo an already committed external effect. If the old effect completed after a fence advance but was already admitted under F1, Nexo records the historical outcome and reconciles current state; it must not rewrite the event as if it were authorized under F2.

## Incarnation interaction
Delete/recreate must create a distinct target incarnation. Name reuse cannot inherit an old operation's authority. A late callback for I1 must never be used as evidence that I2 was affected unless an independent provider proof explicitly binds it to I2.

## Nexo implication
External-effect records need durable TargetIncarnation and FenceRevision bindings, not only target names. Provider capability assessment must include whether asynchronous completion receipts preserve these bindings. When they do not, UNKNOWN remains possible after late completion.
