# Nexo AB104.445 — Multi-Root Recovery and Independent Trust Reconstruction

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.444 → AB104.445
Implementation: NOT PERFORMED

## Research question

How can Nexo establish a replacement trust basis after a trust-domain compromise without circularly using the compromised domain to validate its own recovery?

## External evidence

RFC 9334's RATS architecture separates Attester, Verifier, Relying Party, and trust anchors; the Relying Party can require evidence about the Verifier and its environment. This directly supports making trust reconstruction a dependency-checked process rather than a self-attested transition. citeturn0search2turn0search4

NIST SP 800-57 treats key compromise, replacement, revocation, and recovery as explicit lifecycle events. It also distinguishes key compromise from ordinary key retirement. citeturn0search49turn0search48

RFC 9162's transparency model demonstrates a useful pattern for independent observation: signed append-only history plus consistency proofs can expose divergent views, but detection does not itself choose a new authority. citeturn0search5

NIST SP 800-193 separates platform recovery from normal operation and emphasizes authenticated recovery/update paths and protection against rollback. citeturn0search0

## Core finding

Recovery after trust-root compromise cannot be:

COMPROMISED_ROOT → NEW_ROOT

because the compromised root would be implicitly authorizing its own replacement.

Candidate principle:

OLD_TRUST_DOMAIN_CANNOT_SELF_ATTEST_NEW_TRUST_DOMAIN.

## Recovery trust layers

A replacement trust basis should be composed from distinct domains:

1. Historical continuity evidence.
2. Independent witness/anchor evidence.
3. Independent key/trust-root governance.
4. Fresh hardware/platform evidence where available.
5. External resource/effect evidence.
6. Protected recovery policy.
7. Explicit Z1 recovery decision.

No single layer automatically authorizes the others.

## Attack MR1 — self-signed recovery

Compromised root signs:
“vendor compromised, replacement root is trusted.”

Signature authenticity proves only possession of the compromised key.

Result:
SELF_ATTESTED_RECOVERY => INSUFFICIENT.

## Attack MR2 — two compromised roots

Two keys from the same compromised failure domain sign each other.

Different keys do not imply independent trust.

Result:
KEY_COUNT != INDEPENDENCE.

## Attack MR3 — quorum of correlated roots

Five witnesses exist, but all depend on the same vendor cloud/control plane.

A 3-of-5 quorum does not establish independence.

Result:
QUORUM_COUNT != FAILURE_DOMAIN_QUORUM.

## Attack MR4 — independent witness but stale

A genuinely independent witness has last trusted state G41 while compromised domain reports G48.

The witness provides a historical lower bound, not automatic proof that G41 remains current.

Result:
INDEPENDENT_HISTORY != CURRENT_STATE.

## Attack MR5 — external resource confirms state

External resource says state is R48.

This may validate resource state but not Nexo authority history.

Result:
RESOURCE_STATE != AUTHORITY_HISTORY.

## Attack MR6 — new hardware with old identity

New device H2 is provisioned with old identity A7.

Without a protected replacement ceremony, cloned identity can recreate stale authority.

Result:
NEW_HARDWARE + OLD_IDENTITY != CONTINUITY.

## Attack MR7 — recovery verifier is itself compromised

The new root is validated by a verifier descended from the compromised vendor.

The recovery appears independent but is not.

Result:
RECOVERY_VERIFIER ∈ COMPROMISED_CLOSURE => RECOVERY_UNTRUSTED.

## Attack MR8 — recovery policy rollback

Recovery uses an older policy that permits weaker trust requirements.

Result:
RECOVERY_POLICY_GENERATION < REQUIRED_POLICY_GENERATION
=> RECOVERY_EVALUATION_STALE.

## Attack MR9 — conflicting roots

Independent Root A says G49/R49.
Independent Root B says G49/R49b.

Do not average or select by simple majority.

Candidate:
SAME_GENERATION + CONFLICTING_ROOTS
=> DISPUTED
=> FREEZE
=> DIVERGENCE_ANALYSIS.

## Attack MR10 — root unavailable during recovery

A required independent witness disappears.

Do not silently reduce threshold.

The recovery evaluation becomes stale if the missing root was required for the claim.

## Attack MR11 — recovery succeeds but old credentials remain valid

New trust root is established while old compromised credentials remain accepted.

Recovery is incomplete.

Candidate:
NEW_ROOT_VALID
AND
OLD_ROOT_ACCEPTED
=> UNSAFE_RECOVERY.

## Attack MR12 — recovery root is accepted before its dependencies

A new key is created, but its provenance, hardware identity, policy, witness dependencies, or recovery governance are not validated.

The key becomes a shortcut around the trust graph.

Therefore:
NEW_KEY != NEW_TRUST.

## Candidate root admission

A candidate replacement root must satisfy:

1. identity verified;
2. key/hardware provenance verified;
3. trust-generation lineage established;
4. required independent witness evidence available;
5. dependency closure complete;
6. recovery policy current;
7. old-root invalidation semantics established;
8. affected external effects reconciled or explicitly quarantined;
9. Z1 recovery authority approves;
10. new recovery generation committed.

This is an admission process, not a cryptographic equation.

## Old-root invalidation

Replacement is incomplete unless old trust paths are fenced/revoked.

Candidate:

NEW_ROOT_ESTABLISHED
→ OLD_ROOT_REVOKED
→ OLD_KEY/FIRMWARE/VERIFIER_DEPENDENCIES_INVALIDATED
→ OLD_ADMISSION_CONTEXTS_STALE
→ REVALIDATE.

This extends AB104.414's protected-generation invalidation race.

## Multi-root trust model

Roots can have different roles:

R0 — historical continuity witness
R1 — hardware/platform identity
R2 — policy/governance root
R3 — resource/effect witness
R4 — recovery authority

No root should be assumed to prove properties outside its claim scope.

Candidate:
ROOT_SCOPE != GLOBAL_TRUST.

## Candidate independence requirement

For claim C and root R:

INDEPENDENT_FOR(C,R)
iff
R is outside the minimum dependency closure whose compromise can falsify C
AND
the admission path does not reintroduce that compromised domain.

This is stronger than:
different key,
different machine,
different region,
different organization name.

## Recovery states

NORMAL
→ COMPROMISE_SUSPECTED
→ AUTHORITY_FROZEN
→ TRUST_DOMAIN_QUARANTINED
→ EVIDENCE_COLLECTION
→ ROOT_INDEPENDENCE_ANALYSIS
→ REPLACEMENT_ROOT_PENDING
→ DEPENDENCY_VALIDATION
→ OLD_ROOT_INVALIDATION
→ RECOVERY_GENERATION_COMMIT
→ REVALIDATION
→ EXPLICIT_RELEASE.

Failure:
→ QUARANTINED / UNKNOWN.

## External effects during trust recovery

Existing external effects must not be erased.

For each affected operation:
- preserve OperationID;
- preserve EffectID;
- preserve AttemptID;
- classify external state;
- reconcile where possible;
- keep UNKNOWN where not determinable;
- apply compensation only where separately authorized.

Trust-root recovery does not rewrite effect history.

## Important distinction

A replacement root can establish:

“From recovery generation G50 onward, this new trust basis is authorized.”

It cannot automatically establish:

“Everything before G50 was correct.”

Historical claims require separate evidence.

## Residuals

- Need formal threshold/governance model for multi-root recovery.
- Need distinguish Byzantine root sets from simply unavailable roots.
- Need model emergency recovery when no independent root survives.
- Need analyze minimum external evidence needed to preserve each effect class.
- Need investigate root enrollment and de-enrollment without circular trust.
- Formal verification, implementation, fault injection, and deployment validation remain unperformed.
