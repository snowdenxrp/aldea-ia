# NEXO AB104.744R — Re-audit: OFLE serialization/version evidence

## Direct evidence

### RequestResponseTest
RequestResponseTest.testSerialization() iterates every ApiKeys value and every supported version, then calls:
- getRequest(apikey, version)
- checkRequest(request)
- checkErrorResponse(request, unknownServerException)
- checkResponse(getResponse(apikey, version), version)

The same factory switch explicitly maps OFFSET_FOR_LEADER_EPOCH to createLeaderEpochRequestForReplica(1). Therefore OFLE is included in the repository-wide request/response serialization matrix across supported API versions.

This is broad protocol serialization evidence, not OFLE-specific semantic reducer evidence and not correlation-mismatch evidence.

The file also contains a direct ResponseHeader serialization/parsing test. It verifies the serialized header's correlation ID after parsing. That establishes generic response-header round-trip behavior.

### OffsetFetcherTest
Direct inspection found real consumer-layer OFLE response construction and matching:
- OffsetForLeaderEpochResponseData
- OffsetForLeaderTopicResult
- EpochEndOffset
- Errors.NONE
- OffsetsForLeaderEpochResponse
- prepareResponseFrom(...) with an OFLE request matcher.

The matcher verifies requested TopicPartition keys and the test completes validation successfully.

A reusable helper prepareOffsetsForLeaderEpochResponse(...) constructs a one-topic response using Collections.singletonList(new EpochEndOffset(...)).

This confirms real consumer integration coverage for valid OFLE responses and request matching.

### What this does NOT prove
The inspected tests do not deliberately create:
- duplicate OFLE response partitions;
- unrequested OFLE response partitions;
- conflicting duplicate ordering;
- OFLE response/header correlation mismatch;
- exhaustive reducer error matrix.

The repository-wide RequestResponseTest also does not establish a dedicated OFLE response-version test with independent assertions per OFLE version; it establishes generic all-API serialization coverage.

## Correction to AB104.744 claim boundary

The strongest defensible claim is:
OFLE participates in Kafka's generic all-version request/response serialization matrix, and consumer tests exercise valid OFLE responses/request matching.

It is NOT defensible to call that equivalent to dedicated OFLE response-version, correlation-mismatch, or reducer adversarial coverage.
