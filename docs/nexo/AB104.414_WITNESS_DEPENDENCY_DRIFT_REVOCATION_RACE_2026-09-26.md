# Nexo AB104.414 — Witness Dependency-Drift Detection and Revocation-Race Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.413 → AB104.414
Implementation: NOT PERFORMED

## Research question

How can Nexo prevent a witness that becomes stale, revoked, compromised, or correlated during quorum evaluation from continuing to contribute evidence to a protected decision?

## Evidence

RFC 9334 separates evidence appraisal from Relying Party authorization and emphasizes freshness as an architectural concern: an Attestation Result may become stale when the underlying state or appraisal policy changes. citeturn0search2turn0search4

NIST SP 800-57 treats trust anchors as foundational trust inputs and recommends prompt revocation when a private key is compromised; historical possession of a previously valid key therefore cannot by itself establish current trust. citeturn0search49turn0search5

RFC 5280 makes the trust anchor an input to validation and defines certificate-status mechanisms for revocation; validity of a signed object and current authorization are therefore distinct questions. citeturn0search3turn0search6

RFC 9162 shows that monitoring and comparison can detect inconsistent views, but detection can be asynchronous; this is directly relevant to a witness that changes status while a decision is already being evaluated. citeturn0search0

## Core finding

The critical race is:

1. WITNESS is CURRENT.
2. Quorum evaluation begins.
3. A dependency, trust generation, key, policy, software generation, or independence property changes.
4. Revocation/invalidation is recorded.
5. The old evaluation attempts to commit.

A naive design can accidentally accept:

OLD_WITNESS_STATE + NEW_INVALIDATION_STATE

The protected decision therefore needs a generation/fencing boundary, not merely a fresh read performed earlier.

## Candidate protected predicate

Candidate final witness contribution:

CONTRIBUTE iff

- witness status is currently eligible;
- trust generation matches expected generation;
- key generation matches expected generation;
- witness incarnation matches;
- dependency closure root matches;
- claim scope matches;
- required independence constraints remain satisfied;
- invalidation generation matches;
- evidence freshness satisfies policy;
- no unresolved conflict exists;
- all protected quorum conditions hold;

AND these conditions are evaluated against one coherent protected state/linearization point or equivalent fencing mechanism.

## Revocation race matrix

| Event order | Candidate result |
|---|---|
| revoke → evaluation | witness excluded |
| evaluation → revoke → final gate | reject/re-evaluate |
| final gate → revoke → later external effect | depends on protected commit semantics; revocation is not retroactive |
| ambiguous ordering | UNKNOWN/HOLD |
| dependency drift → final gate | reject/revalidate |
| final gate → dependency drift | historically valid decision; later use must observe new generation |
| witness key compromise detected | invalidate current-use evidence according to policy |
| quorum member disappears | do not silently lower threshold |
| witness returns after suspension | re-enrollment/revalidation required |

## Generation fencing

Candidate witness state carries:

WITNESS_GENERATION
TRUST_GENERATION
DEPENDENCY_GENERATION
INVALIDATION_GENERATION
ENROLLMENT_GENERATION

A quorum evaluation captures the expected generations.

If any protected generation changes before finalization:

STALE_EVALUATION => REJECT / REVALIDATE

This is analogous to the authority and resource fencing already established in AB104.369–AB104.387.

## Why timestamps alone are insufficient

A wall-clock timestamp does not establish that the witness's dependency state remained unchanged between appraisal and final gate.

Therefore:

TIME_FRESH != STATE_FRESH

and:

RECENT_EVIDENCE != CURRENT_AUTHORIZATION

RFC 9334 explicitly treats freshness as an architectural/policy issue rather than assuming a single universal freshness mechanism. citeturn0search2

## Revocation propagation race

A distributed invalidation can be observed by different components at different times.

Therefore Nexo needs to distinguish:

REVOCATION_ISSUED
REVOCATION_OBSERVED
REVOCATION_PROTECTED
REVOCATION_EFFECTIVE_FOR_ADMISSION

The last state is the relevant boundary for Z1.

Before that boundary, other components may still possess stale information. After that boundary, protected decisions must not accept the invalidated witness under the affected scope.

## Quorum evaluation cannot snapshot only witnesses

A witness's current eligibility depends on more than witness metadata:

WITNESS
→ KEY/TRUST
→ SOFTWARE/VERIFIER
→ POLICY
→ DEPENDENCIES
→ FAILURE DOMAINS
→ CLAIM SCOPE
→ EVIDENCE FRESHNESS
→ INVALIDATION

A snapshot that omits a dependency that later changes can remain internally consistent while being semantically stale.

Therefore:

COHERENT_SNAPSHOT != COMPLETE_CURRENTNESS

This carries forward AB104.395–AB104.398.

## Dependency-drift detector

Candidate detector outputs:

- dependency root/version;
- observed generation;
- expected generation;
- changed dependency IDs;
- affected claims;
- affected failure domains;
- effective time/sequence;
- evidence source;
- confidence/status;
- invalidation generation;
- limitations.

Status:

NO_CHANGE
CHANGE_DETECTED
REVALIDATION_REQUIRED
INVALIDATED
UNKNOWN

Detector output is evidence, not authority.

## Missed drift

If the detector does not observe a relevant dependency change:

NO_DETECTION != NO_DRIFT

Therefore a high-consequence property cannot depend solely on a best-effort detector unless its failure mode is explicitly accepted by policy.

Candidate response:

UNDETECTABLE_CRITICAL_DRIFT => UNKNOWN/HOLD or stronger independent control.

## Quorum shrink attack

Suppose threshold = 3 of 5.

Two witnesses become invalid.

A naive implementation changes threshold to 2 of 3 to preserve availability.

This silently changes the security property.

Candidate invariant:

REQUIRED_QUORUM_POLICY_CHANGE => NEW_ADMISSION_BOUNDARY

Witness unavailability must not automatically weaken the protected threshold.

## Quorum replacement attack

An invalid witness is removed and replaced during an in-flight evaluation.

If the replacement inherits the old evaluation's quorum slot without independent admission:

OLD_QUORUM_CONTEXT + NEW_WITNESS

may bypass enrollment/revalidation.

Candidate:

WITNESS_SET_CHANGE => QUORUM_REVALIDATION

## Dependency drift during quorum

If W1 and W2 were independent at evaluation start, then W2 migrates onto W1's provider before finalization:

INITIAL_INDEPENDENCE != FINAL_INDEPENDENCE

The final gate must evaluate the protected dependency generations, not reuse the original classification.

## Witness evidence already produced before revocation

A signed result generated before revocation can remain valid historical evidence.

But:

HISTORICAL_VALIDITY != CURRENT_ADMISSION_ELIGIBILITY

Policy must explicitly determine whether pre-revocation evidence remains usable for a given claim.

For high-consequence current authorization, stale/affected evidence should not silently remain current.

## Compromise timing

If compromise occurs at unknown time between evidence generation and detection:

COMPROMISE_TIME = UNKNOWN

Nexo cannot safely assume all evidence before detection is unaffected.

Candidate state:

AFFECTED_INTERVAL_UNKNOWN => affected evidence QUARANTINED or downgraded according to claim policy.

## Independent invalidation observer

For critical witness revocation, the same system that evaluates the witness should not be the sole source proving its continued validity.

However, adding observers does not automatically create independence. The observer's own trust/dependency closure must be evaluated.

This carries forward AB104.391–AB104.412.

## Candidate final-gate algorithm

1. Load coherent protected witness/quorum snapshot.
2. Verify witness enrollment and scope.
3. Verify trust/key generations.
4. Verify dependency closure and independence.
5. Verify evidence freshness.
6. Verify failure-domain constraints.
7. Verify invalidation generation.
8. Verify quorum threshold and membership.
9. Re-check protected generations at linearization/fencing boundary.
10. If any protected generation changed: reject/revalidate.
11. Persist the decision with all generations and witness identities.
12. Treat later revocation as a new state transition, not silent history rewriting.
13. Reconcile any external effect whose authorization depended on a subsequently invalidated witness.

## New invariants

- WITNESS_REVOCATION_BEFORE_FINAL_GATE => NO_CONTRIBUTION
- PROTECTED_GENERATION_CHANGE => STALE_EVALUATION
- STALE_EVALUATION_CANNOT_COMMIT_AS_CURRENT
- DEPENDENCY_DRIFT => REVALIDATION
- WITNESS_SET_CHANGE => QUORUM_REVALIDATION
- QUORUM_THRESHOLD_CHANGE => NEW_ADMISSION_BOUNDARY
- MISSED_DRIFT != NO_DRIFT
- DETECTOR_OUTPUT != AUTHORITY
- REVOCATION_ISSUED != REVOCATION_EFFECTIVE_FOR_ADMISSION
- HISTORICAL_VALIDITY != CURRENT_ADMISSION_ELIGIBILITY
- UNKNOWN_COMPROMISE_INTERVAL_CANNOT_BE_SILENTLY_TREATED_AS_SAFE
- MULTIPLE_OBSERVERS != INDEPENDENT_OBSERVERS
- COHERENT_SNAPSHOT != COMPLETE_CURRENTNESS
- WITNESS_RETURN_AFTER_SUSPENSION => REVALIDATION
- REPLACEMENT_WITNESS_CANNOT_INHERIT_STALE_QUORUM_AUTHORITY
