# Nexo AB104.524 — Retention-boundary races

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
The idempotency retention boundary is itself a concurrency boundary. An operation can complete, its response can be lost, and the idempotency record can expire while a delayed retry or failover is still possible. Therefore TTL expiration must not automatically convert UNKNOWN to NOT_APPLIED.

## Evidence
- AWS EC2 documents that mutating APIs can time out or encounter server issues before completion even though the request may already have progressed, and idempotency exists to prevent duplicate completion.
- AWS ECS documents a 24-hour RunTask client-token TTL and scope/parameter binding. The same token with different parameters can be rejected; the retention window is finite.
- etcd documents that historical revisions can be compacted, making older revisions inaccessible. A time-based retention window therefore creates an explicit historical coverage boundary.

## Race timeline
T0 INTENT_DURABLE
T1 EXTERNAL_ATTEMPTED
T2 RESPONSE_LOST / UNKNOWN
T3 PROVIDER_OPERATION_COMMITS
T4 IDEMPOTENCY_RECORD_APPROACHES_EXPIRY
T5 DELAYED_RETRY_OR_FAILOVER
T6 IDEMPOTENCY_RECORD_EXPIRES
T7 RECONCILIATION_QUERY

If T7 occurs after the provider's deduplication/history boundary, absence of the record cannot establish NOT_APPLIED.

## Candidate safe rule
Let ambiguity interval end at the latest point where a delayed duplicate, late completion, or provider-side asynchronous workflow could still affect the target. The idempotency/history retention guarantee must extend beyond that point by a policy-defined safety margin.

Candidate:
RETENTION_COVERAGE >= MAX(ASYNC_COMPLETION_BOUND, MAX_RETRY_DELAY, FAILOVER_REPLAY_BOUND, RECONCILIATION_DELAY) + SAFETY_MARGIN

This is a design constraint, not a universal numerical formula.

## Clock/TTL rule
Wall-clock TTL is insufficient by itself when clock trust or provider expiry semantics are uncertain. Use provider-defined expiry evidence or a conservative bound. If expiry time is UNKNOWN, the protected decision cannot assume the deduplication record has expired safely.

## Failover rule
Provider failover does not automatically preserve the same idempotency namespace. Reconciliation must establish that the replacement endpoint shares the same operation-history scope, or treat the operation as UNKNOWN.

## Delayed retry rule
After UNKNOWN, a retry is admissible only when:
- same logical OperationID/EffectID and request digest are preserved;
- provider idempotency scope still covers the operation;
- target identity/incarnation remains valid;
- the retry cannot bypass a newer fence/revocation;
- reconciliation has not already established APPLIED.

Otherwise: reconcile first or quarantine.

## Critical distinctions
- IDEMPOTENCY_TTL != EFFECT_LIFETIME
- TTL_EXPIRY != NOT_APPLIED
- CLOCK_EXPIRY != PROVIDER_HISTORY_EXPIRY
- PROVIDER_FAILOVER != SAME_IDEMPOTENCY_NAMESPACE
- DELAYED_RETRY != NEW_LOGICAL_OPERATION
- RECORD_ABSENCE_AFTER_EXPIRY != HISTORICAL_NONOCCURRENCE
- TIMEOUT != NOT_APPLIED
- UNKNOWN_AFTER_TTL != SAFE_TO_RETRY
- RETENTION_WINDOW != REVOCATION_FINALITY

## Nexo implication
The provider capability vector needs explicit fields for retention horizon, expiry semantics, failover namespace continuity, asynchronous completion bound, and late-retry behavior. The final protected-effect gate must treat an expired/uncertain history boundary as UNKNOWN unless an independent authoritative evidence source closes the interval.
