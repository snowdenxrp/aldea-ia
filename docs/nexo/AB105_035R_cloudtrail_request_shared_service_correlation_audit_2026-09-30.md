# AB105.035R — CloudTrail requestID, sharedEventID, serviceEventDetails: operation-correlation boundaries
Date: 2026-09-30
Status: RESEARCH/AUDIT ONLY — no implementation, no semantic freeze.

## Research question

When do CloudTrail requestID, sharedEventID, serviceEventDetails, and related fields provide a bounded operation correlation, and when do they remain only event-level evidence?

## Primary evidence

AWS documents requestID as the value that identifies the request and states that the called service generates it. eventID is a CloudTrail-generated GUID identifying one event. sharedEventID is generated for CloudTrail events from the same AWS action that are delivered to different AWS accounts; each such record still has a unique eventID and recipientAccountID. serviceEventDetails identifies a service event, including what triggered it and the result. citeturn0search0turn0search2

AWS documents AwsServiceEvent as an event type generated by an AWS service rather than directly by a public AWS API request. Its serviceEventDetails can contain service-specific information about the trigger and result. citeturn0search11

AWS also documents that large CloudTrail event payloads can truncate requestID and serviceEventDetails, among other fields. citeturn0search0turn0search4

## Findings

### F1 — requestID is stronger than timestamp correlation, but remains request-level identity

requestID is generated by the called service and identifies the request. This is a useful direct correlation key when another provider artifact exposes the same request ID.

However, requestID alone does not establish:
- the resulting resource incarnation;
- the exact ConfigurationItem state;
- that the request succeeded;
- that no other operation intervened;
- that a later service-generated event was caused by this request.

Therefore:
requestID match -> REQUEST_CORRELATED
not automatically CAUSALLY_BOUND.

### F2 — sharedEventID is an AWS-action correlation edge across recipient accounts

AWS explicitly defines sharedEventID as common to CloudTrail records generated from the same AWS action and delivered to different accounts. The individual eventID values remain distinct. citeturn0search0

Therefore:
sharedEventID match + compatible recipient-account semantics
-> SAME_AWS_ACTION_CORRELATED

This is stronger than eventID equality for cross-account copies because eventID is intentionally unique per event record.

But sharedEventID is optional and only present when CloudTrail delivers the action to multiple accounts. Its absence therefore cannot mean that no cross-account relationship exists.

### F3 — sharedEventID is not a universal operation identifier

The documented contract is specifically “events from the same AWS action” in the multi-account delivery case. It does not establish a universal identifier spanning every downstream state transition caused by that action.

Thus:
sharedEventID != resource incarnation
sharedEventID != complete operation graph
sharedEventID != causal closure

### F4 — serviceEventDetails can expose trigger/result semantics, but is service-specific

For AwsServiceEvent records, serviceEventDetails can describe what triggered the service event and its result. citeturn0search11

This can provide a stronger causal edge than timestamp proximity when the service documents the semantics of those fields.

But serviceEventDetails is optional and service-specific. Therefore its absence is not negative evidence, and its contents cannot be generalized into one AWS-wide causal schema.

### F5 — requestID/serviceEventDetails can be truncated

AWS documents field truncation when CloudTrail event payloads exceed size limits; requestID and serviceEventDetails are among fields that can be truncated. citeturn0search4

Therefore:
missing/truncated correlation field
-> UNKNOWN for claims that require that field.

The architecture must preserve a distinction between:
FIELD_ABSENT_BY_CONTRACT
FIELD_NOT_PRESENT_IN_RECORD
FIELD_TRUNCATED
FIELD_PRESENT_AND_MATCHING.

These are not equivalent.

### F6 — recipientAccountId is essential context for shared events

AWS documents that recipientAccountId can differ from the account in userIdentity during cross-account resource access. citeturn0search0turn0search2

Therefore cross-account reconstruction needs:
eventID + sharedEventID + recipientAccountId + resource identity + event semantics.

Ignoring recipient account can cause two distinct delivery records to be collapsed incorrectly.

### F7 — event type separates direct API activity from service-generated activity

AwsApiCall and AwsServiceEvent represent different event-generation mechanisms. A service-generated event can occur without a directly corresponding public API request. citeturn0search11

Therefore an architecture that requires every state transition to map to a requestID is unsound.

Some valid event chains may begin with:
AWS_INTERNAL/SERVICE_EVENT
rather than a user/API request.

## Bounded correlation ladder

For an event chain:

1. eventID -> unique CloudTrail record.
2. requestID match -> same service request, when both artifacts expose and document the field.
3. sharedEventID match -> same AWS action across documented multi-account delivery.
4. serviceEventDetails trigger/result -> service-specific causal context.
5. resource identity + event semantics -> candidate state-transition relation.
6. target state + incarnation evidence + competing-event coverage -> potentially bounded causal binding.

No single identifier closes the entire chain.

## Refined decision states

REQUEST_CORRELATED
= documented requestID match.

AWS_ACTION_CORRELATED
= documented sharedEventID relationship across recipient accounts.

SERVICE_TRIGGER_EVIDENCED
= serviceEventDetails provides documented trigger/result semantics.

RESOURCE_TRANSITION_COMPATIBLE
= event semantics and resource identity are compatible with observed state.

CAUSALLY_BOUND
= claim-specific evidence closes the remaining causal dependencies.

UNKNOWN
= required correlation field, coverage, semantics, or identity binding is missing.

## New distilled rule

Identifiers reduce ambiguity; they do not automatically close causality.

requestID match
-> request correlation

sharedEventID match + cross-account context
-> same-action correlation

serviceEventDetails + documented service semantics
-> service-trigger evidence

Only after resource identity, state transition, temporal consistency, and alternative-event coverage are also satisfied can the chain become bounded causal evidence.

## Anti-collapse rules

- requestID != eventID.
- requestID != resource incarnation.
- requestID match != state-transition proof.
- sharedEventID != eventID.
- sharedEventID != universal operation ID.
- sharedEventID absent != no cross-account action.
- serviceEventDetails != universal schema.
- serviceEventDetails absent != no trigger.
- truncated field != negative evidence.
- recipientAccountId != caller account.
- AwsServiceEvent != API request.
- multiple event records != multiple underlying actions when sharedEventID proves same action.
