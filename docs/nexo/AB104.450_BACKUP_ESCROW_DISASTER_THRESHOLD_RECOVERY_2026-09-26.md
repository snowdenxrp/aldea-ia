# Nexo AB104.450 — Backup/Escrow Recovery and Disaster Restoration of Threshold Shares

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.449 → AB104.450
Implementation: NOT PERFORMED

## Research question

How can Nexo use backups or escrowed threshold-share material for disaster recovery without resurrecting revoked authority, compromised identities, stale generations, or a compromised trust domain?

## External evidence

NIST SP 800-57 distinguishes ordinary key recovery from compromise recovery. Backup can restore unavailable key material, but when compromise is suspected the affected keying material must be replaced rather than simply returned to normal use. NIST also notes that backup copies increase exposure and should be governed accordingly. citeturn0search36turn0search39

NIST's threshold-cryptography work treats setup, maintenance, system model, adversary assumptions, and implementation validation as part of threshold security. Threshold cryptography distributes trust across components but does not by itself define the recovery/governance semantics. citeturn0search5turn0search6turn0search11

NIST SP 800-193 requires recovery mechanisms to resist corruption of active protection mechanisms and recommends protecting recovery mechanisms independently from the running firmware; authenticated recovery material must be verified before restoration. citeturn0search0turn0search38

## Core finding

A backup is historical key material, not current authority.

Therefore:

BACKUP_PRESENT != AUTHORITY_CURRENT.

And:

SUCCESSFUL_RESTORE != SAFE_REACTIVATION.

## Attack B1 — restore revoked share

Member M was revoked in generation G8.
Backup contains M's share from G6.
Disaster restoration loads the share.

The share may be cryptographically valid but must not regain authority.

Candidate:
RESTORED_SHARE_GENERATION < CURRENT_GENERATION => REJECT/QUARANTINE.

## Attack B2 — restore old member set

A full backup contains root set S5.
Current root set is S8.
Restoring the backup reconstructs S5.

Do not treat successful database restoration as current governance restoration.

Candidate:
RESTORED_GOVERNANCE_VERSION != CURRENT_GOVERNANCE_VERSION => HISTORICAL_INPUT_ONLY.

## Attack B3 — compromised backup

The backup store itself was within the compromised trust domain.

Restoring it can reintroduce compromised material.

Candidate:
BACKUP_DEPENDENCY_IN_COMPROMISED_CLOSURE => BACKUP_UNTRUSTED.

## Attack B4 — backup authenticity but stale currentness

Backup is authentic and untampered, but old.

Integrity does not prove currentness.

Invariant:
BACKUP_INTEGRITY != CURRENT_AUTHORITY.

## Attack B5 — escrow quorum recreates old authority

Escrow holds enough old shares to reconstruct the previous threshold authority.

This can bypass current membership revocation.

Therefore escrow recovery must require current recovery authorization before any old material can be used.

## Attack B6 — backup restoration as hidden root enrollment

Restoring an old root certificate/configuration silently makes the old root eligible.

Configuration restoration must not itself enroll roots.

Candidate:
RESTORE != ENROLLMENT.

## Attack B7 — key recovery after suspected compromise

If compromise cannot be excluded, recovered shares should be treated as exposed historical material, not as replacement authority.

Candidate path:
RECOVER_FOR_ANALYSIS
→ ASSESS_COMPROMISE
→ PRESERVE_REQUIRED_HISTORY
→ GENERATE_NEW_AUTHORITY
→ INVALIDATE_OLD_AUTHORITY
→ REVALIDATE.

## Attack B8 — disaster causes emergency fail-open

All normal roots are unavailable.
Operator restores the latest backup and lowers threshold.

This combines stale state with reduced authority.

Candidate:
DISASTER != AUTHORITY_RELAXATION.

## Attack B9 — backup from future/alternate branch

Two recovery sites have different backups at the same generation.

Both are authentic but disagree.

Do not choose by timestamp alone.

Candidate:
SAME_GENERATION + DIFFERENT_STATE => RECOVERY_CONFLICT.

## Attack B10 — restored hardware with restored identity

New device H2 loads old device identity H1 and old shares.

This can create cloned authority.

Candidate:
NEW_HARDWARE_REQUIRES_NEW_OR_REVALIDATED_INCARNATION.

## Attack B11 — backup metadata omitted

Share bytes are recovered, but generation, member incarnation, policy, root-set digest, or compromise status is missing.

The cryptographic material cannot be safely interpreted.

Therefore:
KEY_MATERIAL_WITHOUT_REQUIRED_METADATA => UNKNOWN_CONTEXT.

## Attack B12 — backup chain rollback

A backup is validly signed but comes from an earlier continuity anchor.

Restoration must preserve monotonic authority generations and reject silent rollback.

## Attack B13 — recovery site dependency collapse

Primary and backup sites are geographically separate but share:
- same cloud control plane;
- same identity provider;
- same administrator;
- same signing root;
- same backup management system.

Physical separation does not prove trust independence.

Candidate:
BACKUP_INDEPENDENCE_REQUIRES_DEPENDENCY_CLOSURE_ANALYSIS.

## Candidate restoration classes

### R0 — historical reconstruction

Restore only to inspect/reconstruct history.

No authority activation.

### R1 — non-authoritative service recovery

Restore data/services whose operation does not require protected authority.

Still subject to dependency validation.

### R2 — authority candidate reconstruction

Recover old material only as input to a new protected recovery ceremony.

Old material cannot self-activate.

### R3 — compromised-material analysis

Isolate recovered material to determine historical impact.

No operational signing.

## Candidate disaster recovery sequence

DISASTER_DETECTED
→ FREEZE_AFFECTED_AUTHORITY
→ IDENTIFY_LAST_INDEPENDENTLY_VALIDATED_STATE
→ CLASSIFY_BACKUP_DEPENDENCIES
→ VERIFY_BACKUP_INTEGRITY
→ CHECK_GENERATION/CURRENTNESS
→ CHECK_COMPROMISE_STATUS
→ RECONSTRUCT_HISTORY
→ ESTABLISH_NEW_TRUST_BASIS
→ NEW_KEYS/INCARNATIONS
→ INVALIDATE_OLD_AUTHORITY
→ REATTEST
→ RECONCILE_EXTERNAL_EFFECTS
→ COMMIT_NEW_RECOVERY_GENERATION
→ EXPLICIT_RELEASE.

## Important distinction

If compromise is suspected:

RECOVERED_OLD_KEY
is not
NEW_RECOVERY_KEY.

NIST explicitly supports replacing compromised keying material rather than simply returning recovered material to normal use. citeturn0search36turn0search37

For Nexo, this becomes:

RECOVERED_SHARE = EVIDENCE / MIGRATION INPUT
until a new protected authority generation is established.

## Backup destruction and retirement

When old material is no longer required, backup copies should be retired/destroyed according to their security lifecycle rather than left indefinitely available. This matters because an apparently revoked authority can remain recoverable from forgotten backups. citeturn0search36

## Independent recovery basis

A backup system should not be the sole authority for proving that the backup itself is trustworthy.

Candidate dependency classes:

BACKUP_STORAGE
BACKUP_CONTROL_PLANE
BACKUP_IDENTITY
BACKUP_SIGNING_ROOT
BACKUP_RECOVERY_OPERATOR
BACKUP_METADATA
BACKUP_TIME/GENERATION SOURCE.

If all derive from the same compromised domain, apparent redundancy collapses.
