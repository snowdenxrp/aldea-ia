# Nexo AB104.454 — Threshold Recovery Custody, Collusion, and Failure-Domain Attacks

Date: 2026-09-27
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.453 → AB104.454
Implementation: NOT PERFORMED

## Research question

What does a threshold recovery scheme actually guarantee, and what additional conditions are required for Nexo to claim independent recovery authority under collusion, correlated compromise, malicious participants, and availability failures?

## Evidence

NIST defines split knowledge such that fewer than the threshold number of shares provide no information about the protected key beyond limited metadata. This is a cryptographic secrecy property, not a governance-independence claim. citeturn0search0

NIST's threshold-cryptography program describes threshold schemes as distributing trust across parties and identifies security against different adversary types, including active/adaptive adversaries, as a distinct research concern. citeturn0search3turn0search4

The FROST RFC explicitly assumes that fewer than the threshold number of participants are corrupted and that signer configuration/distribution is securely established. It also says the coordinator and participants are chosen externally to the signing protocol. Thus the protocol's threshold property does not itself establish who the participants should be or whether their governance/failure domains are independent. citeturn0search5

NIST's general key-management guidance treats key protection, backup, compromise, recovery, authentication, authorization, availability and trust-anchor management as distinct lifecycle concerns. citeturn0search2

## Core distinction

Nexo must not collapse these different thresholds:

1. CRYPTO_THRESHOLD — minimum shares/participants required by the cryptographic scheme.
2. GOVERNANCE_THRESHOLD — minimum authorized decision makers required by policy.
3. INDEPENDENCE_THRESHOLD — minimum number of independently compromised failure domains tolerated.
4. AVAILABILITY_THRESHOLD — number of participants that must remain reachable to recover.
5. EVIDENCE_THRESHOLD — minimum independent evidence sources required for a particular recovery claim.

These values MAY differ.

Therefore:

CRYPTO_THRESHOLD != GOVERNANCE_THRESHOLD != INDEPENDENCE_THRESHOLD != AVAILABILITY_THRESHOLD != EVIDENCE_THRESHOLD.

## Attack T1 — k-of-n mathematically valid, but k custodians collude

If the adversary compromises k or more valid shares, threshold secrecy is defeated.

The threshold scheme's security assumption is therefore explicit:

COMPROMISED_CUSTODIANS >= CRYPTO_THRESHOLD
=> CRYPTOGRAPHIC_AUTHORITY_COMPROMISED.

This does not imply the whole system is irrecoverable if an independent recovery basis exists, but the affected root must be treated as compromised.

## Attack T2 — fewer than k shares, but one upstream service controls them

Example:
5 shares, threshold 3.
All five custodians authenticate through one compromised identity provider.

The attacker may not possess three mathematical shares immediately, but can compromise the common authorization path.

Candidate:

COMMON_DEPENDENCY_COMPROMISE => EFFECTIVE_THRESHOLD_REDUCTION.

The dependency closure must therefore include authentication, provisioning, update, network, administrative, HSM, backup and policy dependencies relevant to the recovery claim.

## Attack T3 — geographic separation mistaken for independence

Shares in five buildings can still share:
- same cloud;
- same vendor;
- same administrator;
- same identity provider;
- same firmware;
- same recovery service.

Therefore:

GEOGRAPHIC_DIVERSITY != FAILURE_DOMAIN_INDEPENDENCE.

## Attack T4 — organizational separation is fake

Five departments controlled by one administrator are not five independent governance domains.

Candidate:

ADMINISTRATIVE_COMMON_MODE => NON_INDEPENDENT.

## Attack T5 — malicious threshold participants

A participant can provide a syntactically valid share while attempting to:
- approve the wrong recovery event;
- approve stale generation;
- authorize a larger scope;
- suppress evidence;
- induce conflicting outputs;
- replay an old ceremony.

Therefore threshold participation requires protocol-level context binding and authorization validation.

## Attack T6 — cryptographically valid but semantically wrong signature

A valid threshold signature proves that the threshold protocol produced a signature under the group key.

It does not prove:
- current policy;
- correct target;
- correct generation;
- independent governance;
- truth of historical state.

Candidate:

VALID_THRESHOLD_SIGNATURE != VALID_RECOVERY_DECISION.

## Attack T7 — coordinator compromise

FROST's model permits a coordinator that is not trusted with private key material, but its security assumptions still constrain participant corruption. citeturn0search5

Nexo therefore must not allow a coordinator to:
- select unauthorized participants;
- alter recovery scope;
- replace the challenge;
- substitute the target;
- suppress required approvals.

Candidate:

COORDINATOR_UNTRUSTED_FOR_SECRET != COORDINATOR_TRUSTED_FOR_POLICY.

## Attack T8 — malicious participant causes denial of service

A participant refuses to respond or intentionally supplies invalid protocol data.

Availability and safety must be separated:

PARTICIPANT_FAILURE may reduce AVAILABILITY without granting permission to lower SAFETY.

If the remaining independent threshold cannot be reached, state becomes recovery-unavailable rather than automatically authorized.

## Attack T9 — participant replacement during active ceremony

A participant is revoked after contributing to a recovery decision.

The system must define whether the authorization remains valid.

Candidate conservative rule:

REVOCATION_BEFORE_FINAL_COMMIT => INVALIDATE_UNCOMMITTED_RECOVERY_AUTHORIZATION.

Already committed recovery generations require separate reconciliation rather than silent retroactive mutation.

## Attack T10 — share rotation without group-key rotation

Refreshing shares may improve operational security but does not automatically establish a new authority generation.

Therefore distinguish:

SHARE_REFRESH != PARTICIPANT_ROTATION != ROOT_ROTATION != GOVERNANCE_ROTATION.

## Attack T11 — new participant inherits compromised lineage

A newly enrolled participant receives a share or authorization through a compromised provisioning path.

The new participant may be cryptographically fresh but not independently established.

Candidate:

NEW_IDENTITY != NEW_TRUST_BASIS.

## Attack T12 — collusion threshold and governance threshold differ

Example:
Crypto threshold = 3/5.
Governance requires 4/5.

A 3-person coalition may be cryptographically capable of signing but policy-ineligible.

Therefore cryptographic authorization must be followed by policy authorization.

## Attack T13 — governance threshold lower than cryptographic threshold

The opposite is also dangerous: 2 authorized humans may approve, but the cryptographic mechanism requires 3 shares. This is a liveness problem, not permission to bypass the cryptographic threshold.

Candidate:

GOVERNANCE_APPROVAL_CANNOT_SUBSTITUTE_FOR_REQUIRED_CRYPTOGRAPHIC_PARTICIPATION.

## Attack T14 — independent evidence threshold silently reduced

If recovery normally requires two independent evidence domains and one becomes unavailable, accepting one without changing the claim class is unsafe.

Candidate:

MISSING_REQUIRED_INDEPENDENT_EVIDENCE => CLAIM_REMAINS_UNKNOWN_OR_SCOPE_REDUCED.

## Attack T15 — threshold changes during recovery

An attacker changes 3-of-5 to 2-of-5 while the ceremony is running.

Candidate:

THRESHOLD_AND_PARTICIPANT_SET_ARE_IMMUTABLE_FOR_A_RECOVERY_EVENT.

Any change requires a new recovery event/generation.

## Attack T16 — recovery root uses the same implementation everywhere

Identical software, HSM firmware or protocol implementation across all custodians creates correlated failure risk.

Implementation diversity is not automatically independence, but common-mode software faults must be represented in dependency closure.

## Attack T17 — all shares backed up together

Separate encrypted backups do not establish independence if one backup administrator or key-management system can retrieve them all.

Candidate:

BACKUP_SEPARATION_REQUIRES_ACCESS_AND_DEPENDENCY_SEPARATION.

## Attack T18 — share compromise discovered after authorization

A later compromise finding may invalidate the assumption under which a recovery decision was made.

Candidate:

POST_AUTHORIZATION_COMPROMISE => REASSESS_RECOVERY_GENERATION_IF_COMPROMISE_INTERVAL_OVERLAPS_AUTHORITY.

Do not rewrite immutable evidence; append a new invalidation/reassessment record.

## Candidate assurance model

For a recovery decision R:

SAFE_AUTHORIZATION(R) requires all applicable predicates:

C_crypto(R)
and C_governance(R)
and C_independence(R)
and C_context(R)
and C_freshness(R)
and C_scope(R)
and C_evidence(R)

If any required predicate is UNKNOWN:

HIGH_CONSEQUENCE_RECOVERY => HOLD / QUARANTINE.

Unknown availability must not be converted into approval.

## Failure-domain graph

For each participant p:

DEPENDENCY_CLOSURE(p) =
identity
+ credential issuance
+ authentication
+ authorization
+ share custody
+ HSM/device
+ firmware/software
+ network/control path
+ backup/recovery
+ administrator
+ policy source
+ external services.

Independence is then evaluated over the closures, not participant labels.

Candidate:

INDEPENDENCE(P) = PROPERTY_OF_DEPENDENCY_CLOSURE(P).

## Candidate threshold vector

For each recovery operation:

RecoveryThresholdVector =
{
  crypto_k,
  governance_k,
  independent_domains_k,
  availability_k,
  evidence_k,
  max_effect_class,
  required_freshness,
  required_context
}

This vector is operation-specific.

There is no single universal recovery threshold.

RECOVERY_READY

RECOVERY_PARTIALLY_AUTHORIZED
RECOVERY_QUORUM_UNAVAILABLE

RECOVERY_AUTHORIZED requires all mandatory threshold dimensions to pass.

## New invariants

- CRYPTO_THRESHOLD != GOVERNANCE_THRESHOLD
- GOVERNANCE_THRESHOLD != INDEPENDENCE_THRESHOLD
- INDEPENDENCE_THRESHOLD != AVAILABILITY_THRESHOLD
- EVIDENCE_THRESHOLD IS CLAIM-SPECIFIC
- COMPROMISED_CUSTODIANS >= CRYPTO_THRESHOLD => ROOT_COMPROMISED
- COMMON_DEPENDENCY_COMPROMISE => EFFECTIVE_THRESHOLD_REDUCTION
- GEOGRAPHIC_DIVERSITY != FAILURE_DOMAIN_INDEPENDENCE
- ADMINISTRATIVE_COMMON_MODE => NON_INDEPENDENT
- VALID_THRESHOLD_SIGNATURE != VALID_RECOVERY_DECISION
- COORDINATOR_UNTRUSTED_FOR_SECRET != COORDINATOR_TRUSTED_FOR_POLICY
- PARTICIPANT_FAILURE != SAFETY_PERMISSION
- SHARE_REFRESH != ROOT_ROTATION
- NEW_IDENTITY != NEW_TRUST_BASIS
- THRESHOLD_AND_PARTICIPANT_SET_IMMUTABLE_PER_RECOVERY_EVENT
- MISSING_REQUIRED_INDEPENDENT_EVIDENCE => UNKNOWN_OR_SCOPE_REDUCTION
- BACKUP_SEPARATION_REQUIRES_DEPENDENCY_SEPARATION
- UNKNOWN_REQUIRED_THRESHOLD => HIGH_CONSEQUENCE_RECOVERY_HOLD
