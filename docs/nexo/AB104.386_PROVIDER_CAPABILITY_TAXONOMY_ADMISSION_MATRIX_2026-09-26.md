## Research question
How should Nexo classify external providers according to the primitives they actually enforce, rather than treating every provider as equivalent?

## Fresh evidence
Google Cloud Storage supports generation/metageneration preconditions that are evaluated on the target resource and can reject a mutation when the expected generation does not match. Multiple preconditions can be combined, but these are target-state conditions, not automatically Nexo authority fences. citeturn0search0turn0search5

Amazon S3 supports conditional writes using If-Match/If-None-Match and can enforce that requests include conditional headers through bucket policy. These mechanisms protect target-state conditions, but an ETag condition is not itself a monotonically ordered authority fence. citeturn0search1turn0search2

Azure Blob supports ETag and other conditional headers, including combinations evaluated together. Again, this provides target preconditions but does not by itself establish a Nexo authority-generation protocol. citeturn0search6turn0search8

## Capability dimensions
Each provider/resource adapter should declare capabilities independently:

- AUTHORITY_FENCE: provider/resource can reject stale authority generations at the protected acceptance boundary.
- DURABLE_FENCE_STATE: required fence/high-water mark survives restart/failover.
- TARGET_CONDITION: provider atomically checks target version/ETag/generation with mutation.
- STABLE_EFFECT_ID: provider recognizes a stable logical effect identity.
- IDEMPOTENCY: repeated same identity is deduplicated with defined semantics.
- DURABLE_INTENT: provider or Nexo boundary durably records intent before release where required.
- ACK_IDENTITY_BINDING: provider acknowledgement is bound to exact effect identity and operation semantics.
- RECONCILIATION: provider can query exact effect/resource state after ambiguous outcomes.
- CANCELLATION: provider can reliably prevent or cancel an effect before acceptance, with defined race semantics.
- REVERSAL: provider supports a defined compensating operation after acceptance.
- FAILOVER_SEMANTICS: provider preserves the above guarantees across replica/failover transitions.
- CROSS_RESOURCE_COORDINATION: provider participates in a defined multi-resource commit/coordination protocol.

No capability should be inferred merely because a provider offers a similarly named feature.

## Provider classes

### P0 — No relevant safety primitive
No durable fence, target conditional, reliable idempotency, or reconciliation sufficient for the required effect.
Admission: HOLD/REJECT for protected effect classes.

### P1 — Target-conditional only
Supports atomic target conditions such as ETag/generation/version.
Admission:
- useful for NO_LOST_UPDATE / stale-target prevention;
- insufficient for NO_EFFECT_FROM_STALE_AUTHORITY unless the condition itself is proven to encode current authority;
- retry remains subject to effect identity and provider semantics.

### P2 — Idempotent-only
Supports stable request identity/deduplication but no authority fence.
Admission:
- may permit safe-equivalent retry for the same effect identity;
- does not solve stale-authority exclusion;
- does not prove external confirmation.

### P3 — Reconciliation-capable
Can query exact effect/resource state after ambiguous attempts.
Admission:
- improves UNKNOWN resolution;
- does not prevent stale effects by itself;
- must be combined with authorization/fencing appropriate to the effect class.

### P4 — Gateway-fence compatible
Provider lacks native Nexo authority fencing but can receive requests only through a controlled gateway boundary whose semantics are explicit.
Admission:
- possible only for properties actually enforced by gateway;
- downstream stale-request safety remains a separate claim;
- gateway becomes part of TCB.

### P5 — Native resource-fence capable
Provider/resource atomically validates a durable, resource-scoped monotonic fence at mutation acceptance.
Admission:
- candidate for strict stale-authority exclusion when the fence is correctly bound to Nexo authority and incarnation;
- still requires target conditions, identity, reconciliation, and other effect-class controls as applicable.

### P6 — Coordinated multi-resource capable
Provides or participates in a defined coordination protocol with durable participant state and explicit partial/unknown semantics.
Admission:
- candidate for stronger multi-resource properties;
- still requires proof of the actual protocol and provider failover semantics;
- never infer global atomicity merely from individual P5 capabilities.

## Important distinction: conditional version vs fence
A generation/ETag/version check answers approximately:
"Is the target still the expected version?"

A fence answers:
"Is this request still authorized to act under the current ownership/authority generation?"

A provider may implement the first without the second. Therefore:
TARGET_CONDITION != AUTHORITY_FENCE

A provider with P1 should not be promoted to P5 merely because its conditional write is atomic.

## Effect-class interaction
Provider capability is necessary but not sufficient.

For E0 observation, confirmation and evidence semantics dominate.
For E1/E2 mutations, target conditions + stable identity/idempotency + reconciliation may be enough for some claims, depending on authority requirements.
For E3/E4, stale-authority prevention, identity, reconciliation, and compensation/reversal semantics become stricter.
For E5 multi-resource effects, participant capabilities and coordination must be evaluated as a graph; the weakest participant can constrain the global property.

## Mixed-provider multi-resource rule
For resources R1..Rn, define a per-participant capability vector:
C_i = {fence, target_condition, identity, idempotency, intent, confirmation, reconciliation, failover, ...}

Global admission cannot simply use the average or majority capability. A claimed property must be supported by every participant whose behavior is relevant to that property.

Candidate rule:
GLOBAL_PROPERTY_CLAIMABLE only if all required participant-specific predicates are satisfied and the coordination/reconciliation contract covers the composition.

If one participant cannot enforce stale-authority exclusion, Nexo must not claim that property for the entire multi-resource effect unless a stronger independent boundary actually prevents that participant from receiving/accepting stale work.

The profile itself is evidence/configuration, not proof that the provider behaves correctly. Claims about safety must remain tied to verified provider semantics and the actual adapter path.

## Candidate invariants
- PROVIDER_CAPABILITY_MUST_BE_EXPLICIT
- TARGET_CONDITION != AUTHORITY_FENCE
- IDEMPOTENCY != AUTHORITY_FRESHNESS
- RECONCILIATION != PREVENTION
- PROVIDER_FEATURE_NAME != PROVEN_GUARANTEE
- GLOBAL_PROPERTY_REQUIRES_ALL_RELEVANT_PARTICIPANT_PREDICATES
- FAILOVER_SEMANTICS_MUST_BE_DECLARED
- CAPABILITY_PROFILE_IS_NOT_ITSELF_PROOF
- GATEWAY_BOUNDARY_MUST_BE_EXPLICIT
- UNKNOWN_PROVIDER_CAPABILITY => HOLD_OR_DOWNGRADE_CLAIM
