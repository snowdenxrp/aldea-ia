# Nexo AB104.432 — Lease/Fence Crash-Restart Semantics

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.431 → AB104.432
Implementation: NOT PERFORMED

## Research question

What happens to leases, fence generations, delayed requests, duplicated requests, and authority after crash, restart, failover, or resource recovery?

## Core finding

A fence is only a durable safety boundary if its generation survives the failure modes that can otherwise resurrect stale authority.

Therefore:

DURABLE_FENCE_STATE > PROCESS_LOCAL_FENCE_STATE

and:

RESTARTED_PROCESS != NEW_AUTHORITY unless authority state explicitly establishes that transition.

## Crash classes

### C1 — client crash

A client may crash after admission but before observing the external result.

The operation must remain identifiable by durable EffectID/OperationID semantics.

Crash does not imply non-execution.

### C2 — authority-service crash

If the authority service loses its generation state, it must not silently restart at an old generation.

Candidate recovery states:

RECOVERED_WITH_CONTINUITY
RECOVERED_WITH_NEW_EPOCH
RECOVERY_REQUIRED
QUARANTINED.

### C3 — resource crash

The resource must recover its fence state without accepting previously fenced generations as current.

If durable fence state is unavailable, high-consequence mutation should remain blocked until continuity is re-established.

### C4 — storage rollback

Restoring an older snapshot can resurrect an old generation.

Therefore:

RESTORED_STATE_WITHOUT_CONTINUITY_PROOF != CURRENT_STATE.

This carries forward AB104.410–AB104.413.

## Fence generation

Candidate monotonic relation:

G_new > G_old

must remain distinguishable across restart and recovery.

Generation reuse without an incarnation/epoch boundary can permit an old delayed request to appear current.

Candidate:

GENERATION_REUSE_WITHOUT_DISTINGUISHABLE_INCARNATION => STALENESS RISK.

## Delayed request after failover

Timeline:

T0 resource accepts G7
T1 resource advances to G8
T2 resource crashes
T3 resource recovers
T4 delayed G7 request arrives.

Safe recovery requires the recovered resource to preserve the fact that G8 superseded G7, or to enter a state where it cannot safely accept the request.

Recovery that forgets G8 is not equivalent to recovery of the same authority state.

## Duplicate request

Duplicate OperationID must not be interpreted as a new authorization merely because the process restarted.

Candidate:

EFFECT_ID + OPERATION_ID + DURABLE_REPLAY_STATE

must survive the relevant crash boundary for exactly-once-like effect claims.

This does not prove exactly-once external execution; it prevents local identity from being silently regenerated.

## Lease crash semantics

A lease stored only in process memory cannot safely establish durable ownership after crash.

After restart, the process must not infer:

LOCAL_LEASE_MEMORY == CURRENT_AUTHORITY.

A lease backed by durable authoritative state can be reconstructed according to its provider-defined semantics.

## Lease expiry during crash

If the holder crashes and its lease expires, a new holder may acquire authority.

The old holder may later resume or delayed requests may arrive.

Lease expiry alone does not guarantee those stale requests are rejected.

Therefore:

LEASE_EXPIRY + NO_FENCE != STALE_REQUEST_EXCLUSION.

## Fence survives lease holder failure

A stronger pattern is:

lease/ownership selects current holder
+
fence generation identifies current authority
+
resource enforces fence generation.

Then an old holder can remain alive or resume after a crash without being able to mutate a resource once its generation is stale.

## Resource restart

Resource recovery should establish one of:

1. preserved current fence generation;
2. a strictly newer recovery generation;
3. quarantine until authoritative state is reconstructed.

Unsafe:

restart → reset fence to initial/default value.

## Recovery generation

A recovery epoch can make restarted authority distinguishable from pre-crash authority.

Example:

NORMAL E7
→ CRASH
→ RECOVERY E8

Old E7 requests are then rejected if the resource requires E8.

But generating E8 must itself be protected and durable.

## Delayed network packets

A delayed packet is not made current by arriving after recovery.

Candidate:

NETWORK_DELAY != AUTHORITY_REVALIDATION.

The receiver must validate generation/incarnation at the protected boundary.

## Packet duplication

Duplicate delivery must not create a new effect identity.

Therefore transport-level duplication and application-level replay are separate properties.

## Failover

Failover can create split authority if both old and new instances believe they are current.

Candidate safety condition:

AT_MOST_ONE_CURRENT_FENCE_GENERATION_CAN_MUTATE_THE_RESOURCE.

This requires an authoritative election/lease/fencing mechanism whose failure semantics are explicit.

## Split brain

If A believes it owns G8 and B believes it owns G8 simultaneously, generation equality alone does not establish uniqueness.

Candidate:

GENERATION_EQUALITY != UNIQUE_AUTHORITY.

Authority identity/incarnation and fencing enforcement remain necessary.

## Recovery and external effects

A crash after sending an external request but before recording the result creates an ambiguous state.

Recovery must not infer:

NO_LOCAL_RECORD => NO_EXTERNAL_EFFECT.

Instead use the existing external-effect reconciliation model:

UNKNOWN → RECONCILE → CONFIRMED / FAILED / AMBIGUOUS according to provider evidence.

## Candidate recovery contract

RECOVERY_CONTEXT:

- AUTHORITY_DOMAIN
- AUTHORITY_INCARNATION
- PRE_CRASH_GENERATION
- RECOVERY_GENERATION
- RESOURCE_ID
- RESOURCE_INCARNATION
- FENCE_GENERATION
- LEASE_GENERATION
- STORAGE_SNAPSHOT_ID
- STORAGE_DURABILITY_STATUS
- LAST_CONFIRMED_OPERATION_ID
- REPLAY_STATE_GENERATION
- TRUST_GENERATION
- POLICY_VERSION
- RECOVERY_EVIDENCE
- CONTINUITY_STATUS
- LIMITATIONS.

## Candidate recovery state machine

RUNNING
→ CRASH_DETECTED
→ RECOVERY
→ CONTINUITY_VALIDATION
→
  CURRENT_RESTORED
  | NEW_RECOVERY_GENERATION
  | QUARANTINED

No automatic transition from CRASH_DETECTED directly to RUNNING for protected effects.

## Candidate stale-request rule

At the resource boundary:

ACCEPT iff

request_fence == current_fence
AND
request_resource_incarnation == current_incarnation
AND
request_authority_generation is current
AND
replay/effect identity is acceptable.

Otherwise reject or route to reconciliation.

## Candidate crash-safe composition

DURABLE AUTHORITY GENERATION
+
DURABLE FENCE GENERATION
+
RESOURCE INCARNATION
+
DURABLE EFFECT/REPLAY IDENTITY
+
RECOVERY CONTINUITY CHECK
+
RESOURCE-SIDE ENFORCEMENT.

This is a candidate safety composition, not an implemented architecture.

## New invariants

- DURABLE_FENCE_STATE > PROCESS_LOCAL_FENCE_STATE
- RESTARTED_PROCESS != NEW_AUTHORITY
- RESTORED_STATE_WITHOUT_CONTINUITY_PROOF != CURRENT_STATE
- GENERATION_REUSE_WITHOUT_DISTINGUISHABLE_INCARNATION => STALENESS_RISK
- LEASE_EXPIRY + NO_FENCE != STALE_REQUEST_EXCLUSION
- NETWORK_DELAY != AUTHORITY_REVALIDATION
- GENERATION_EQUALITY != UNIQUE_AUTHORITY
- CRASH_WITHOUT_EXTERNAL_RESULT != EXTERNAL_NON_EXECUTION
- DUPLICATE_DELIVERY != NEW_EFFECT_IDENTITY
- RECOVERY_MUST_NOT_SILENTLY_ROLL_BACK_AUTHORITY_GENERATION
- RESOURCE_RESTART_MUST_PRESERVE_OR_ADVANCE_FENCE_STATE
- SPLIT_BRAIN_REQUIRES_EXPLICIT_AUTHORITY_EXCLUSION
- UNKNOWN_EXTERNAL_RESULT_REMAINS_UNKNOWN_UNTIL_RECONCILIATION
