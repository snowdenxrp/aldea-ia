## A1 wrapper resolution

The temporary target-broker wrapper can delegate all Authorizer methods to a private StandardAuthorizer instance. Its authorize() method must:
- call the real StandardAuthorizer delegate first;
- inspect the returned result for the target Topic WRITE action;
- record delegated ALLOW as A1 authorization witness;
- then wait on the A1 barrier BEFORE returning from the wrapper authorize call.

Important semantic wording:
"A1 real target Produce authorization reaches the wrapper; the delegated StandardAuthorizer result is ALLOW; the wrapper then holds the authorization call at the barrier."
Do NOT say the authorization call "returned ALLOW to Kafka" while it is held at the wrapper barrier.

The wrapper must not block start() or metadata publication. Its start() delegates directly to StandardAuthorizer.start(serverInfo). configure() delegates directly before any barrier use. No initialization/metadata path may depend on the A1 latch.

## D1 resolution

A stronger D1 witness is a second, independent real Produce request sent to the SAME target broker after D0. The target broker's wrapper receives a fresh authorize() invocation for the second request and should delegate to StandardAuthorizer, which must return DENIED after the deletion is observed locally.

This is preferred over a direct out-of-band authorize() call because it exercises the actual broker request authorization path and produces an externally observable authorization result.

D1 acceptance:
- fresh producer/request;
- direct target-broker connection, not cluster-wide bootstrap ambiguity;
- after D0 completion;
- target wrapper/delegate observes DENIED for topic WRITE;
- no reliance on describeAcls absence as a freshness proof.

If the second real Produce cannot be made to yield an unambiguous fresh target-broker authorization witness, stop and record UNKNOWN rather than substituting direct ACL inspection.

## Admin/DeleteAcls setup issue resolved

A normal Admin DeleteAcls request requires authorization on the broker/controller path. The harness therefore needs a distinct administrative principal or an equivalent controlled setup so the producer principal is not a super-user.

Do NOT make the Produce principal a super-user, because then ACL deletion would not force a DENIED target authorization.

The safest low-complexity setup currently identified is:
- seed the target WRITE ACL and the required administrative cluster-level authorization through the active controller's StandardAuthorizer/AclMutator metadata path;
- use the normal Kafka Admin client for D0;
- use a non-superuser producer principal for A1/D1.

However, the exact principal/authentication configuration for the Admin client versus producer is still a harness-construction item and MUST be compiled/observed before runtime. Do not silently assume PLAINTEXT principal behavior is sufficient.
