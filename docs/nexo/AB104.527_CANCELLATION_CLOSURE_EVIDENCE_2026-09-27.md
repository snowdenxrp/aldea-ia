# Nexo AB104.527 — Evidence required to close UNKNOWN after cancellation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A cancellation acknowledgment is insufficient by itself to close the original UNKNOWN. Strong closure requires provider evidence that is bound to the exact operation and establishes a terminal condition under the provider's semantics, plus enough evidence to exclude an already-applied effect.

## Evidence
- Google Cloud long-running-operation cancellation APIs explicitly state cancellation is best-effort and not guaranteed; clients must inspect the operation afterward to determine whether cancellation succeeded or the operation completed despite cancellation.
- Kubernetes deletion demonstrates a similar two-stage model: a delete request returns 202 and leaves the object terminating while finalizers perform cleanup; only after the terminal condition is reached is deletion complete.
- AWS EC2 states asynchronous workflows may continue after the request returns and uses idempotency to control duplicate completion.

## Candidate closure levels
C0 CANCEL_REQUESTED — no closure.
C1 CANCEL_ACKNOWLEDGED — provider accepted the cancellation request; original UNKNOWN remains.
C2 CANCEL_TERMINAL — provider reports a terminal cancellation state for the exact OperationID and documents that the operation will not complete.
C3 NON_EFFECT_CONFIRMED — in addition to C2, authoritative evidence covers the ambiguity interval and target incarnation strongly enough to establish that the protected external effect did not occur.

Only C3 should normally permit UNKNOWN -> NOT_APPLIED. C2 may permit a provider-scoped state such as CANCELLED, but Nexo must not silently equate that state with historical non-occurrence unless provider semantics prove the equivalence.

## Critical distinctions
- CANCEL_REQUESTED != CANCEL_ACKNOWLEDGED
- CANCEL_ACKNOWLEDGED != CANCEL_TERMINAL
- CANCEL_TERMINAL != NON_EFFECT_CONFIRMED
- PROVIDER_CANCELLED != GLOBAL_NOT_APPLIED
- TERMINAL_OPERATION_STATE != HISTORICAL_NONOCCURRENCE unless semantics bind them
- CANCEL_RECEIPT != EFFECT_ABSENCE_PROOF
- CURRENT_CANCELED_STATE != PROOF_NO_PRIOR_EFFECT
- CANCELLATION != COMPENSATION

## Race closure
If cancellation races with completion:
1. preserve the original operation history;
2. query authoritative operation state;
3. bind the result to exact OperationID/EffectID and target incarnation;
4. determine whether provider semantics make cancellation terminal before effect commit;
5. if not, reconcile the external target/postcondition;
6. if evidence remains insufficient, retain UNKNOWN.

## Nexo implication
Provider capability assessment must separate cancellation request, cancellation acknowledgment, terminal cancellation, and non-effect proof. A provider that exposes only best-effort cancel cannot satisfy a strong negative-effect claim by cancellation acknowledgment alone.
