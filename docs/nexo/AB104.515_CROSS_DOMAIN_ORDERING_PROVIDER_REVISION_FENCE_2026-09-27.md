# AB104.515 — cross-domain ordering: Nexo authority vs provider state

## Evidence
etcd transactions can atomically compare key revisions and apply writes; the resulting store revision provides an authoritative ordering point inside the etcd trust domain. Linearizable reads reflect current consensus, while serializable reads may be stale. citehttps://etcd.io/docs/v3.6/learning/api/ The etcd API also permits explicit minimum revision constraints, allowing a reader to reject observations older than a required revision. citehttps://github.com/etcd-io/etcd/blob/main/api/etcdserverpb/rpc.proto etcd's STM implementation guards a transaction's read set using the observed modification revisions, demonstrating that a local revision can close races within that authoritative store. citehttps://github.com/etcd-io/etcd/blob/main/client/v3/concurrency/stm.go

## Core finding
Nexo authority state and an external provider normally have different ordering domains:
`NexoRevision != ProviderRevision`.

A timestamp, HLC value, or locally observed sequence number can provide correlation/order information, but cannot by itself prove that an event in domain A happened before an event in domain B unless the protocol establishes a shared trust/communication boundary.

Therefore the canonical bridge should be a **binding artifact**, not an assumed common clock:
`Binding = {OperationID, EffectID, NexoAuthorityEpoch, NexoFenceRevision, ProviderTargetIdentity, ProviderTargetIncarnation, ProviderRevision?, RequestDigest, BindingDigest}`.

## Three ordering levels
### L1 — Single-domain authoritative ordering
If Nexo and the relevant provider state are committed by one authoritative transactional system, a single revision/linearization point can order the protected transition.

### L2 — Cross-domain explicit binding
If the provider exposes a conditional operation accepting a Nexo-issued token/fence and returns a provider revision/receipt bound to that token, Nexo can establish a causal binding without pretending the two revisions are the same clock.

### L3 — Observation-only correlation
If the provider exposes only ordinary reads, timestamps, asynchronous callbacks, or opaque receipts, Nexo can correlate observations but cannot prove a cross-domain ordering strong enough for a protected-effect guarantee.

`L3 + REQUIRED_STRONG_ORDER => UNKNOWN_OR_QUARANTINE`.

## HLC limitation
A hybrid logical clock can produce useful causal-ish timestamps when participants exchange timestamps and maintain the protocol correctly, but the resulting ordering is still not a proof of external-state commit unless the provider's state transition is bound to that clock/token. Nexo should therefore treat HLC as metadata/order evidence, not as a universal fencing mechanism.

## Provider revision binding
A provider revision is useful when Nexo can require:
`ObservedProviderRevision >= RequiredProviderRevision`
and the provider guarantees that the revision is authoritative for the queried target state.

But:
`ProviderRevision >= X` only proves the observation is at/after X inside that provider's ordering domain. It does not prove that Nexo's authority decision occurred before or after a separate Nexo revision unless the two are explicitly bound.

## Fence-token bridge
The strongest generic cross-domain candidate is:
1. Nexo commits an authority/fence generation.
2. Nexo issues an immutable `EffectID` + fence token bound to that generation and target incarnation.
3. Provider accepts the token conditionally and rejects stale generations, or records it in an authoritative operation record.
4. Provider returns a receipt containing the token/effect binding and its own revision.
5. Nexo records the provider receipt without conflating provider revision with Nexo revision.

This creates a causal chain:
`Nexo fence commit → provider conditional acceptance → provider revision/receipt`.

If step 3 is unavailable, the chain stops at an authorization statement and cannot prove provider-side stale-writer exclusion.

## Exact UNKNOWN boundary
Nexo must downgrade to `UNKNOWN` when any required cross-domain relation is unprovable, including:
- provider revision unavailable when required by the effect class;
- provider revision exists but is not authoritative for the target;
- receipt cannot be bound to the exact EffectID/request digest;
- provider does not enforce the supplied fence/generation;
- target incarnation changed or cannot be established;
- Nexo/provider clocks are being used as the only ordering proof;
- an asynchronous acknowledgement cannot be distinguished from a durable provider state transition;
- a crash occurs between external dispatch and durable receipt recording.

## HLC / timestamp rule
`HLC_ORDER != EXTERNAL_COMMIT_ORDER` unless the external transition explicitly commits/binds the HLC-derived token under a trusted provider contract.

`TIMESTAMP_ORDER != FENCE_ENFORCEMENT`
`PROVIDER_REVISION != NEXO_REVISION`
`RECEIPT != WORLD_TRUTH`

## Final-gate candidate
`CurrentNexoAuthority`
AND `CurrentNexoFence`
AND `CurrentTargetIncarnation`
AND `ProviderCapabilityForRequiredBinding`
AND `ProviderRevisionFreshEnough`
AND `EffectID/RequestDigestBinding`
AND `ProviderFenceEnforced`

Otherwise:
`NO_STRONG_CROSS_DOMAIN_ORDER => UNKNOWN_OR_QUARANTINE`.

## Invariants
- `NEXO_REVISION != PROVIDER_REVISION`
- `HLC_ORDER != EXTERNAL_COMMIT_ORDER` without explicit binding
- `TIMESTAMP_ORDER != FENCE_ENFORCEMENT`
- `PROVIDER_REVISION >= X != NEXO_EVENT_ORDER`
- `PROVIDER_RECEIPT != WORLD_TRUTH`
- `OPAQUE_ACK != DURABLE_EFFECT_CONFIRMATION`
- `UNBOUND_FENCE_TOKEN != STALE_WRITER_PROTECTION`
- `NO_PROVIDER_FENCE_ENFORCEMENT => NO_PROVIDER_SIDE_STALE_WRITER_CLAIM`
- `UNKNOWN_CROSS_DOMAIN_ORDER => NO_BLIND_PROTECTED_ALLOW`
- `CRASH_BEFORE_RECEIPT_DURABILITY => UNKNOWN_UNLESS_RECONCILED`

## Status
Research complete. Nexo should not manufacture a common timeline between its authority domain and an external provider. Strong cross-domain ordering requires an explicit binding/fence protocol or a single authoritative transaction domain. Otherwise the correct semantic result is bounded observation plus `UNKNOWN`, not inferred ordering.

No implementation or formal verification performed.

Next exact step: AB104.516 — research provider-side fencing contracts in concrete systems: conditional writes, generation-match/ETag/precondition mechanisms, stale-writer rejection, and what evidence is actually returned when a provider accepts or rejects a fence.
