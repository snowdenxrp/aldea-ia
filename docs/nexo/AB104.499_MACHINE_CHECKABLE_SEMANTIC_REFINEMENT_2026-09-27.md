# AB104.499 — machine-checkable certificate semantic refinement and downgrade detection

## Evidence
TLA+ work on security properties explicitly uses refinement mappings and model checking, demonstrating a concrete route for checking that a lower-level protocol preserves a higher-level specification. citeturn0search2 TLS 1.3 provides a concrete protocol example where version negotiation is authenticated and downgrade is explicitly detected; unacceptable negotiated versions cause handshake failure. citeturn0search1 COSE requires critical protected parameters to be understood, with invalid criticality processing treated as a fatal error. citeturn0search0

## Candidate Nexo refinement relation
Represent each certificate profile as a transition system `P=(States,Inputs,Transitions,Claims)` and define an abstraction function `α` from new-profile states to old-profile states.

A migration is safe for claim C only if every new-profile protected transition maps to an old-profile transition that is permitted for C, or is explicitly classified as a stricter transition:

`∀ t_new ∈ ProtectedTransitions(C): α(t_new) ∈ Allowed_old(C) OR t_new ∈ ExplicitlyStricter(C)`

A counterexample is any reachable `t_new` whose abstraction authorizes a transition forbidden by the old profile, or whose required security condition disappears during translation.

## Downgrade detection
Check at least:
1. profile identifier is authenticated;
2. semantic profile is bound to the decision digest/domain;
3. migration epoch is current;
4. critical fields are understood;
5. old profile cannot be selected merely because a node lacks new-profile support;
6. a transition from new authority to old authority requires an explicit authorized migration record.

TLS provides a useful pattern: compatibility can exist while downgrade protection independently prevents an attacker from forcing a weaker negotiated version. citeturn0search1

## Counterexample-driven validation
For each migration pair generate adversarial cases:
- omitted critical field;
- same field name with changed semantics;
- old profile accepted by a new verifier under a new policy;
- new certificate translated into a weaker old claim;
- mixed nodes selecting different profiles;
- stale migration epoch;
- conflicting migration records;
- rollback after new profile activation.

Any counterexample blocks automatic promotion until the mapping/policy is changed and rechecked.

## Important distinction
`SERIALIZATION_EQUIVALENCE != SEMANTIC_EQUIVALENCE`
`PARSE_SUCCESS != REFINEMENT`
`REFINEMENT != AUTHORIZATION`
`MODEL_CHECKED != IMPLEMENTATION_CORRECT`
`COMPATIBILITY != DOWNGRADE_RESISTANCE`

The refinement model can establish a property only for the modeled semantics and assumptions. It does not by itself prove parser correctness, cryptographic implementation correctness, deployment configuration, or external-world authority.

## Candidate promotion levels
`E0_PARSEABLE → E1_STRUCTURALLY_VALID → E2_SEMANTICALLY_MAPPED → E3_REFINEMENT_CHECKED → E4_AUTHORITY_ELIGIBLE → E5_DEPLOYED`

No automatic promotion from E3 to E4: current authority, trust basis, migration policy, and runtime evidence remain separate gates.

## Status
Research complete. No implementation or formal verification performed. This establishes the candidate shape of a machine-checkable refinement relation and adversarial counterexample suite; the relation itself remains a design candidate until the certificate claim language is formally specified.
