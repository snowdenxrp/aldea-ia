## Purpose
Determine what can and cannot be reconstructed after crash/restart at every external-effect state, without silently promoting uncertain external outcomes.

## Reconstruction matrix

| Durable state before crash | What recovery may know | Required recovery action | Retry posture |
|---|---|---|---|
| REQUESTED | Request may exist; no durable admission/intent assumed | Reconstruct as REQUESTED; re-run admission only with current authority, target versions and policy | New admission; no external effect assumed |
| ADMITTED, intent not durable | Admission decision may have existed only transiently | Treat external execution as forbidden unless an independent durable effect record proves otherwise; reconcile if any attempt could have escaped | Do not blindly retry |
| INTENT_DURABLE | Exact OperationID/EffectID and intended effect are durable | Revalidate current authority, recovery ownership, target/incarnation and prerequisites; do not infer external attempt | Same logical effect only under retry contract |
| READY | Durable intent exists, but external attempt status may depend on durable attempt record | Revalidate final gate; if attempt record is absent but the system permits a request to have escaped, reconcile rather than infer non-execution | HOLD/reconcile unless non-execution is established |
| EXTERNAL_ATTEMPTED | Attempt is durable; outcome may be unknown | Promote to UNKNOWN unless exact provider outcome is durably bound; require reconciliation | No blind new EffectID; same EffectID only if safe-equivalent |
| PROVIDER_ACKNOWLEDGED | Ack is durable, but its semantic sufficiency may vary by effect class | Validate exact identity, provider semantics and evidence freshness; confirm only if contract permits | No retry if confirmation is established; otherwise reconcile |
| EXTERNAL_CONFIRMED | Exact confirmation is durable and valid | Restore confirmed state; preserve evidence binding | No retry as recovery |
| UNKNOWN | Ambiguous external outcome is durable | Enter RECONCILIATION_REQUIRED; establish recovery owner/fence | Retry only after new admission and effect-class/provider rule |
| RECONCILIATION_REQUIRED | Evidence collection is pending | Acquire current evidence; do not self-upgrade to success | No blind retry |
| PARTIAL_COMMIT | Participant-level mixed outcomes durable | Preserve each participant state; reconcile unknown participants; compensation only under fresh authority | No global success while participant remains UNKNOWN |
| COMPENSATION_REQUIRED | Original effect remains durable; compensating effect pending | Admit compensation as a new protected operation | New EffectID/OperationID |
| QUARANTINED | Recovery cannot establish required authority/integrity/evidence | Remain quarantined; require authorized recovery path | No effectful retry |

## Critical crash windows

### A. Before INTENT_DURABLE
The absence of durable intent is not, by itself, proof that no external request escaped if the implementation permits an attempt before durable intent. Therefore the proposed state machine must enforce ADMITTED → INTENT_DURABLE before any crash-sensitive external attempt. If that ordering is structurally guaranteed, recovery can safely treat the missing intent as non-executable for that operation.

### B. After INTENT_DURABLE, before READY
No external attempt should be permitted. Recovery re-establishes current authority/fence and prerequisites.

### C. READY → EXTERNAL_ATTEMPTED boundary
This is the most important ambiguity boundary. A crash can leave durable evidence of intent but incomplete evidence of whether the provider received/executed the request. Recovery must not infer non-execution from a missing response.

### D. During/after external attempt
A lost response or timeout yields UNKNOWN unless independent evidence resolves it. RFC 9110 explicitly warns against automatically retrying non-idempotent requests unless idempotent semantics are known or the client can establish the original was not applied. citeturn0search2

### E. Provider acknowledgement before durable confirmation
An acknowledgement is not automatically equivalent to external confirmation. The contract must define whether the acknowledgement itself is authoritative evidence for the claimed property; otherwise reconciliation remains necessary.

## Fence rollover during recovery
1. Read current RecoveryFence/authority epoch.
2. Compare durable operation fence with current fence.
3. If stale: do not execute under the old fence.
4. Re-admit under the current authority only if the operation's effect class permits continuation.
5. If the provider supports stable EffectID/idempotency, reuse may be safe-equivalent only under provider semantics; otherwise treat a new attempt as a new effect.
6. If provider execution may already have happened, reconcile before creating a new effect.

## External provider capability requirement
The recovery contract must declare, per provider/effect class:
- stable identity support;
- deduplication semantics;
- fence/generation enforcement;
- conditional state/version support;
- query/reconciliation capability;
- acknowledgement semantics;
- behavior across provider failover;
- cancellation/reversal semantics.

AWS Durable Execution documentation reinforces the distinction: replay can rerun a side effect, while idempotency keys can make repeated attempts safe only when the external service actually deduplicates the same key. For interrupted side-effecting work, AWS recommends checking the external system before deciding how to proceed. citeturn0search0turn0search6

Transactional outbox research also reinforces that durable local publication does not eliminate duplicate downstream delivery; consumers need idempotency, and cross-service transaction handling may require saga-style coordination. citeturn0search1

## New findings
1. **Durable intent is necessary but not sufficient.** It closes the local crash-intent gap; it does not establish external execution outcome.
2. **The READY boundary is not inherently safe.** Safety depends on whether an external attempt can escape before its durable attempt marker.
3. **Missing attempt evidence cannot automatically mean non-execution.** The state machine must structurally prevent unrecorded attempts or require reconciliation.
4. **Fence rollover converts stale work into non-executable work, not automatically into cancelled work.**
5. **Recovery needs a capability matrix per provider/effect class.** Generic retry logic cannot assume fencing, deduplication, or query semantics.
