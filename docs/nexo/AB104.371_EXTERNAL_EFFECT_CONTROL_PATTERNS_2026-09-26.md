# NEXO — AB104.371 — External-effect control mechanisms by effect class

Date: 2026-09-26
Status: RESEARCH / DESIGN EVIDENCE ONLY
Implementation: NOT PERFORMED. No V21. No formal proof.

## Objective

Continue exactly from AB104.370. Compare mechanisms that control the boundary:

LOCAL_LINEARIZATION -> EXTERNAL_ATTEMPT

The question is not which mechanism is "best", but which property each mechanism actually establishes and where UNKNOWN remains.

## Evidence

RFC 9110 defines conditional requests as preconditions evaluated before applying a method. If-Match is explicitly intended for state-changing operations and lost-update prevention; the recipient must evaluate it before applying the method and must not apply the method when the condition is false. This is strong evidence for recipient-side state preconditions, not proof of Nexo's complete external-effect model.

AWS documentation describes conditional writes as capable of idempotent retry when the condition and mutation are evaluated together, and describes stable idempotency tokens as a mechanism for making repeated requests have the same effect as one request. These are implementation evidence, not formal proof of Nexo properties.

The Transactional Outbox pattern stores the message/intent in the same database transaction as the local state change, then relays it separately. It avoids the local-DB/message-broker dual-commit gap, but the relay can publish more than once after a crash; therefore the consumer must be idempotent or otherwise deduplicate.

## Mechanism analysis

### 1. Provider-side fencing

Request carries an authority generation/fence that the protected resource itself validates.

Establishes, if the provider truly enforces it:
- stale generations can be rejected at the resource boundary;
- delayed requests from an older authority generation need not be accepted;
- client-side revocation is not the sole safety mechanism.

Does NOT by itself establish:
- that the effect never happened before the fence changed;
- knowledge of an already attempted request with no observable outcome;
- cross-provider atomicity;
- recovery correctness.

UNKNOWN remains when the provider cannot establish whether a request executed.

Design status: strongest candidate for preventing stale external actuation where supported, but provider-specific.

### 2. Conditional request / version precondition

The external resource checks an expected current version/state before applying the mutation.

Establishes:
- mutation is conditional on recipient-observed state;
- stale target versions can be rejected.

RFC 9110 explicitly specifies this pattern for HTTP conditional requests and state-changing methods.

Does NOT by itself establish:
- authority freshness unless authority is represented in the recipient's condition;
- cross-resource atomicity;
- knowledge of outcome after a transport failure;
- protection against a provider that accepts the request but has ambiguous execution semantics.

Design implication:
A target-version condition and an authority fence are distinct predicates unless the external resource defines them as one protected authorization state.

### 3. Stable effect identity / idempotency key

A stable EffectID is reused across retries.

Establishes, if the receiving resource honors it:
- duplicate retries can map to the same logical effect;
- retries need not create duplicate side effects.

AWS documents this as a retry-safety mechanism and notes the distinction between at-most-once, at-least-once, and idempotent behavior.

Does NOT establish:
- stale-authority rejection;
- that an effect did not happen;
- cross-resource atomicity;
- cancellation;
- provider-side freshness of authority.

Important:
Idempotency answers primarily "is this repeated attempt the same logical effect?" It does not answer "is this effect currently authorized?"

### 4. Durable intent / transactional outbox

The local protected transaction records the external intent atomically with the local state transition; a relay later attempts delivery.

Establishes:
- local commit and durable recording of intent can share one local transaction;
- recovery can discover work that must be attempted;
- the crash gap "local commit happened but intent was never durably recorded" can be eliminated when both are in the same transaction.

Does NOT establish:
- that the external provider executed the intent;
- exactly-once external effect;
- stale-authority rejection;
- remote cancellation;
- cross-resource atomicity.

The outbox relay can publish more than once if it crashes after publishing but before recording completion. Therefore downstream idempotency/deduplication remains necessary.

### 5. Reconciliation

After an ambiguous attempt, query/observe the external resource and correlate using EffectID, provider state, independent observation, or another effect-specific evidence source.

Establishes:
- a mechanism to reduce UNKNOWN;
- explicit distinction between observed external state and internal assumptions.

Does NOT establish:
- that the original effect was prevented;
- instantaneous knowledge;
- perfect observation;
- atomicity between local state and external world.

Reconciliation is therefore a closure mechanism for uncertainty, not a replacement for fencing.

## Effect-class matrix

| Effect class | Fencing | Conditional state | Effect identity/idempotency | Durable intent | Reconciliation | Residual UNKNOWN |
|---|---|---|---|---|---|---|
| Local protected mutation | internal authority fence | VersionSet/CAS | operation identity | durable commit | recovery | store failure/ambiguity |
| HTTP/API state mutation | provider-dependent | often available | provider-dependent | outbox/intent possible | provider query | transport/remote execution ambiguity |
| Message publication | broker-dependent | sequence/version sometimes | consumer dedup | outbox strongly relevant | consumer/offset/state inspection | delivery/execution ambiguity |
| Physical/device actuation | device-dependent | often limited | device-specific | command intent | sensor/independent observation | high if no trusted feedback |
| Account/financial external effect | provider-dependent | provider-dependent | often available | intent ledger/outbox | authoritative provider state | provider semantics/settlement timing |
| Multi-provider operation | rarely common | separate domains | per-provider | coordinator state | required | substantial |

The table is a research classification, not an architecture selection.

## Combined pattern emerging

For an authority-sensitive external effect, no single mechanism closes all boundaries.

A candidate layered contract is:

1. Protected local authorization/final gate.
2. Durable external intent/effect identity.
3. Provider-side fence or equivalent authorization condition when available.
4. Provider-side idempotency/effect identity when supported.
5. External attempt state.
6. Reconciliation after ambiguous outcomes.
7. Explicit UNKNOWN when evidence cannot close the uncertainty.
8. Compensation/reversal only as a new protected effect.

This is a composition of mechanisms, not proof that their composition is universally safe.

## Important negative finding

Transactional outbox is NOT an external-effect commit protocol.

It closes a local durability/intent gap but deliberately leaves delivery/execution as a separate step.

Likewise:

Idempotency != authorization freshness.

Conditional state check != authority fencing.

Reconciliation != prevention.

Fencing != proof of past non-execution.

These distinctions must remain explicit in Nexo.

## Candidate external-effect contract refinement

An EffectContract should distinguish at least:

- EffectID
- OperationID
- AuthorityEpoch / fence
- RequiredScope or PolicyVersion where applicable
- TargetVersion / conditional state
- IntentDurabilityState
- AttemptNumber
- AttemptTimestamp/ordering metadata where trustworthy
- Provider acknowledgement
- Provider execution state
- Reconciliation evidence
- Cancellation/reversal capability
- Retry semantics
- Idempotency semantics
- Fence enforcement semantics
- UNKNOWN conditions
- Recovery ownership

Potential states:

INTENT_DURABLE
-> READY
-> ATTEMPTED
-> PROVIDER_ACKNOWLEDGED
-> EXTERNAL_CONFIRMED

with side branches:

REJECTED
CANCELLED
UNKNOWN
RECONCILIATION_REQUIRED
COMPENSATION_REQUIRED

These are candidate semantics only; formal state-machine closure remains open.

## New boundary finding

AB104.370 showed:

LOCAL_LINEARIZATION != EXTERNAL_ATTEMPT.

AB104.371 refines this further:

EXTERNAL_ATTEMPT != EXTERNAL_CONFIRMED.

Therefore at least three distinct boundaries must remain visible:

CONTROL_LINEARIZATION
EXTERNAL_ATTEMPT
EXTERNAL_CONFIRMATION

Collapsing them into one "success" state would erase important UNKNOWN cases.

## Open questions

1. Which Nexo effect classes can require provider-side fencing as a hard admission criterion?
2. What is the minimum trusted evidence needed to move ATTEMPTED/UNKNOWN to CONFIRMED?
3. How should providers with idempotency but no fencing be classified?
4. How should providers with fencing but no idempotency be classified?
5. Can durable intent and effect identity survive authority epoch rollover without accidentally preserving stale authorization?
6. What happens when reconciliation itself is partitioned or stale?
7. Which physical effects require independent observation rather than provider acknowledgement?
8. What is the exact compensation state machine when reversal is itself uncertain?
