# Nexo AB104.526 — Cancellation vs fencing of in-flight external operations

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Cancellation is not a universal inverse of an external effect. Nexo must distinguish:
- PREVENT_NEW_ADMISSION: fence/revocation blocks future protected attempts;
- CANCEL_IN_FLIGHT: provider explicitly accepts and enforces cancellation of an already-running operation;
- COMPENSATE_AFTER_EFFECT: a separate operation attempts to restore state;
- UNKNOWN: cancellation outcome cannot establish whether the original effect already occurred.

## Evidence
AWS EC2 documents asynchronous mutating requests and idempotent retries, showing that request return and workflow completion are distinct. Kubernetes deletion similarly has an accepted/terminating phase: DELETE can return 202 while finalizers perform cleanup, and final removal occurs only after finalizers are cleared. Kubernetes therefore demonstrates that requesting cancellation/deletion is not identical to completion of the underlying work.

## Candidate state model
EFFECT_IN_FLIGHT
-> CANCEL_REQUESTED
-> CANCEL_ACCEPTED
-> CANCEL_CONFIRMED
or
-> CANCEL_REJECTED
or
-> CANCEL_UNKNOWN

The original effect independently remains:
EXTERNAL_ATTEMPTED -> APPLIED | NOT_APPLIED | UNKNOWN

Cancellation evidence must not overwrite the original effect history.

## Core rule
A cancellation request is an intent unless the provider contract supplies authoritative evidence that cancellation was accepted and that the original operation can no longer produce the protected effect.

Even CANCEL_CONFIRMED may only establish provider-defined cancellation semantics. If the provider cannot guarantee no prior/late effect, reconciliation remains required.

## Fence rule
Advancing a fence can prevent a stale actor from making a new protected attempt only if the provider enforces that fence/precondition. A Nexo-local fence cannot retroactively cancel an already accepted provider operation.

## Compensation rule
A compensating operation is a new logical effect with its own OperationID/EffectID, authority, target incarnation, fence, idempotency, and reconciliation. It does not erase the original effect.

## Critical distinctions
- CANCEL_REQUESTED != CANCELLED
- CANCEL_ACCEPTED != ORIGINAL_EFFECT_NOT_APPLIED
- CANCEL_CONFIRMED != WORLD_TRUTH
- FENCE_ADVANCE != RETROACTIVE_CANCELLATION
- REVOCATION != UNDO
- COMPENSATION != HISTORICAL_ERASURE
- DELETE_REQUESTED != DELETE_COMPLETED
- PROVIDER_ACK != EXTERNAL_EFFECT_CONFIRMED
- UNKNOWN_CANCELLATION != NOT_APPLIED

## Race
If revocation/fence F2 occurs after operation E was admitted under F1:
1. block any new E/F1 admission where enforcement exists;
2. preserve E's historical state;
3. attempt provider cancellation only if supported;
4. reconcile whether E applied before/after cancellation;
5. if ambiguous, retain UNKNOWN and quarantine further protected action as required.

## Nexo implication
The external-effect contract should expose cancellation capability separately from idempotency and fencing. A provider capability claim of “supports cancellation” is incomplete without scope, timing boundary, guarantee of no future effect, late-completion semantics, and reconciliation behavior.
