# Nexo AB104.399 — Independent and Differential Validation of Semantic Derivation

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective
Determine how a semantic REQUIRED_SET derivator can be independently validated without making the production derivator, its verifier, or the test harness an unbounded authoritative TCB.

Fresh evidence:
- NIST defines IV&V as objective review/analysis/testing intended to verify requirements and validate implementation. citeturn0search3turn0search0
- NIST identifies requirements analysis, test generation, mutation analysis, formal analysis, and independent V&V as distinct techniques rather than a single proof mechanism. citeturn0search25turn0search26
- NASA model-based development guidance uses reference models and distinguishes requirements-based validation from conformance testing against a model. citeturn0search12turn0search13

## 1. Three different validation questions

A derivator needs separate tests for:

1. SPECIFICATION VALIDITY
   Does the semantic specification actually express the intended required dependencies?

2. DERIVATOR CONFORMANCE
   Does implementation D produce the result required by the specification?

3. IMPLEMENTATION/ENVIRONMENT BEHAVIOR
   Does the deployed derivator execute the validated implementation with the expected inputs, versions and configuration?

Passing (2) does not prove (1).

## 2. Candidate independent reference model

Define a small, auditable REFERENCE_SEMANTICS model independent from the production derivator.

Inputs:
- claim/effect contract;
- policy;
- schema;
- semantic rule version;
- branch context.

Output:
- canonical REQUIRED_SET;
- conflicts/cycles;
- completeness status;
- explanation/provenance.

The production derivator output is compared against the reference model.

Important limitation:
If both implementations share the same semantic specification bug, differential agreement does not prove the specification is correct.

Therefore differential validation is evidence of implementation conformance, not semantic truth.

## 3. Independent model diversity

Candidate validation layers:

A. REFERENCE_MODEL — simple, auditable semantics.
B. PRODUCTION_DERIVATOR — optimized implementation.
C. PROPERTY_SUITE — invariants independent of implementation.
D. ADVERSARIAL_GENERATOR — malformed/conflicting/recursive inputs.
E. OPTIONAL SECOND_IMPLEMENTATION — independently developed derivation.
F. HUMAN/DOMAIN REVIEW — specification-level validation for safety-critical semantics.

NIST's IV&V concept supports separating objective validation from the development path. citeturn0search3

## 4. Differential disagreement rule

If Reference R and Production P disagree:

R != P => NO_CURRENT_COMPLETE_RESULT.

Do not choose:
- majority output;
- newer timestamp;
- production output;
- reference output

unless an explicit adjudication rule exists.

Create:
DERIVATION_DISPUTE record containing:
- input root;
- semantic versions;
- R output/root;
- P output/root;
- disagreement class;
- evidence;
- adjudication status.

Status becomes UNKNOWN/QUARANTINED for safety-critical use until resolved.

## 5. Property-based validation

Properties should be independent of expected exact output where possible.

Candidate properties:
- adding a mandatory dependency cannot silently remove unrelated mandatory dependencies;
- changing an irrelevant field cannot change REQUIRED_SET;
- changing resource incarnation changes bindings where incarnation is required;
- identical canonical semantic inputs produce identical root;
- policy version change invalidates incompatible results;
- unresolved conflict never yields COMPLETE;
- unresolved recursion never yields COMPLETE;
- resource limit never yields COMPLETE;
- undeclared runtime dependency cannot be silently accepted;
- historical result remains immutable.

These properties detect classes of bugs that a finite example corpus can miss.

## 6. Mutation testing

Mutate the derivator/specification intentionally:
- remove one dependency;
- invert a precedence rule;
- delete a recursion edge;
- swap branch conditions;
- ignore schema version;
- ignore resource incarnation;
- bypass conflict detection;
- truncate recursion;
- return COMPLETE on LIMIT_REACHED.

The validation suite should detect each mutation.

A surviving mutation is evidence of a test/specification gap, not proof of correctness.

NIST materials explicitly identify mutation analysis and testing as V&V techniques. citeturn0search26

## 7. Model-based testing

A reference state/transition model can generate semantic derivation cases:
- policy transitions;
- schema migrations;
- branch changes;
- dependency additions/removals;
- recursive graphs;
- conflicts;
- resource replacement.

NASA research describes requirements-based validation separately from conformance testing between implementation and model. citeturn0search12

## 8. Oracle problem

The reference model itself is an oracle only if its semantics are independently justified.

Therefore:
REFERENCE_MODEL != AUTOMATIC_TRUTH.

Candidate trust chain:
SPECIFICATION_REVIEW
→ REFERENCE_MODEL
→ PROPERTY_SUITE
→ ADVERSARIAL/MUTATION TESTS
→ DIFFERENTIAL CONFORMANCE
→ INDEPENDENT APPRAISAL
→ OPERATIONAL AUTHORITY.

No single test layer is sufficient.

## 9. Attack — correlated implementations

Production P and reference R share:
- same parser;
- same policy compiler;
- same semantic library;
- same generated artifact;
- same test fixtures.

A common bug can survive both.

Therefore independence must be dependency-graph based, consistent with earlier AB104.392–398 work.

Candidate minimum for high-consequence semantic claims:
- distinct implementation paths;
- distinct semantic parsing where practical;
- independent test generation;
- no single shared artifact that can falsify all outputs;
- explicit common-mode dependency record.

## 10. Attack — verifier compromise

If the verifier is compromised, it may mark disagreement as resolved.

Therefore verifier outputs are evidence, not authority.

Verifier result must bind:
- exact input root;
- semantic versions;
- reference/production versions;
- test suite version;
- dependency closure;
- verifier identity/version;
- appraisal policy;
- validity/invalidation generation.

Compromise of a required verifier invalidates current claims depending on it.

## 11. Attack — incomplete test generator

A generator may never produce the rare case that exposes a semantic omission.

Therefore coverage cannot be only line/branch coverage.

Candidate semantic coverage dimensions:
- every rule;
- every precedence relation;
- every dependency type;
- every conflict class;
- every recursion/cycle class;
- every branch predicate;
- every migration mapping;
- every invalidation path;
- every resource/incarnation binding;
- every LIMIT_REACHED path.

Coverage itself is evidence, not proof of completeness.

## 12. Attack — exact agreement but wrong semantics

R and P both return {D1,D2}; intended semantics require {D1,D2,D3}.

Result:
AGREEMENT != CORRECTNESS.

This is the decisive limitation of differential testing.

Semantic specification review and independently derived properties are therefore mandatory for the strongest claims.

## 13. Candidate adjudication states

DERIVATION_VALIDATED_CURRENT
DERIVATION_VALIDATED_HISTORICAL
DERIVATION_DISPUTED
DERIVATION_UNKNOWN
DERIVATION_QUARANTINED
DERIVATION_INVALIDATED

No automatic promotion from DISPUTED/UNKNOWN/QUARANTINED to CURRENT merely because a later retry repeats the same answer.

## 14. TCB boundary

Candidate Z1 dependency:
- approved semantic specification/version;
- validation policy;
- validity/invalidation state;
- trusted appraisal result;
- exact REQUIRED_SET_ROOT.

Outside Z1:
- expensive reference execution;
- test generation;
- mutation campaigns;
- historical corpora;
- graph traversal;
- analytics.

Z1 does not need to reproduce the entire derivation process if it can validate a protected, claim-specific appraisal result under an independently governed policy.

However, if the appraisal result is itself safety-critical, the verifier and its trust closure become part of the claim TCB. This is a claim-specific expansion, not a universal move of the entire verification stack into Z1.

## 15. Candidate invariants

- DIFFERENTIAL_AGREEMENT != SEMANTIC_TRUTH
- REFERENCE_MODEL != AUTOMATIC_ORACLE
- PRODUCTION_CONFORMANCE != SPECIFICATION_CORRECTNESS
- DISAGREEMENT => NO_CURRENT_COMPLETE_RESULT
- MUTATION_SURVIVAL => VALIDATION_GAP
- LIMIT_REACHED != COMPLETE
- COMMON_MODE_DEPENDENCIES_COLLAPSE_INDEPENDENCE
- VERIFIER_OUTPUT != AUTOMATIC_AUTHORITY
- VERIFIER_COMPROMISE_INVALIDATES_DEPENDENT_CURRENT_CLAIMS
- SEMANTIC_COVERAGE != FORMAL_PROOF
- HISTORICAL_VALIDATION_IS_RETAINED
- CLAIM_TCB_IS_PROPERTY_SPECIFIC

## Status

AB104.399 establishes a layered validation strategy:
reference semantics + independent properties + adversarial/mutation testing + differential conformance + independent appraisal.

The key result is negative but important:
**agreement between two derivators cannot prove semantic correctness if they share the same flawed specification or common-mode dependency.**

Formal proof, complete semantic specification, implementation correctness, and deployment correctness remain unproven.

## Exact next action

AB104.400 — attack the proposed validation stack itself: common-mode failures, specification bugs, test-suite blind spots, verifier compromise, stale appraisal, and whether the resulting evidence chain can be represented without creating an oversized authoritative TCB.
