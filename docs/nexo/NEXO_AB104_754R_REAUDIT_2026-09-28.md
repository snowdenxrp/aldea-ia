# NEXO AB104.754R — production Selector completed-receive lifecycle re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct findings

The production `Selector` is materially different from `MockSelector` for receive retention. Its `poll()` invokes a private `clear()` at the **start** of each poll, and `clear()` empties `completedReceives`, `completedSends`, `connected`, and `disconnected`. Thus, for Kafka client-side use, completed receives are intentionally retained only until the next selector poll, allowing the caller to process them in any order during the current poll interval.

`Selector.completedReceives()` returns the values of the internal completed-receive map. The source documentation explicitly says clients rely on the start-of-next-poll clearing model, while SocketServer uses explicit `clearCompletedReceives()` after processing.

Therefore the earlier AB104.753R warning is confirmed: MockSelector retention cannot be generalized to production. In production client usage, if `NetworkClient.handleCompletedReceives()` throws during processing, the current completed receive is not automatically cleared at that point by `NetworkClient`; however, a subsequent call to `Selector.poll()` begins by clearing the previous completed receives. A replay on the next selector poll is therefore **not expected from the Selector's completed-receive container**. This is source-derived, not an executed mismatch/replay test.

The production Selector's explicit `clearCompletedReceives()` exists for SocketServer, whose processing path clears receives after processing (including its exception-handling structure). This server-side lifecycle is distinct from NetworkClient's client-side start-of-next-poll lifecycle.

## Evidence boundary

No test was executed in this audit. No test was found that deliberately causes a NetworkClient correlation mismatch, then invokes a second production Selector poll and asserts non-replay. Existing Selector tests demonstrate normal receive observation and explicit clearing, but do not establish the mismatch/exception scenario.
