# AB105.084R — evidence dependency and common-mode failure

Date: 2026-09-30
Chain: AB105.083R -> AB105.084R

## Objective
Determine how Nexo should treat observations that appear independent but share an underlying source, sensor, provider, credential, clock, verifier, policy, or collection path.

## Fresh primary evidence
RFC 9334 defines Evidence as claims generated by an Attester and appraised by a Verifier; trust in the result depends on the Attesting Environment, trust anchors, endorsements, appraisal policy, and reference values. It also explicitly warns implementers to evaluate emergent risk when multiple roles or components are combined. Therefore multiple evidence records do not automatically represent independent trust paths. [RFC 9334] citeturn0search0turn0search25
RFC 9334 also describes composite devices in which several sub-entities contribute claims but may share an overall attesting environment or hierarchy. This demonstrates that multiple claims can be distinct observations while sharing a common trust dependency. citeturn0search0
NIST defines statistical independence as information about one variable not changing the assessment of another. For Nexo, the practical security analogue is that separately recorded observations must not be counted as independent corroboration when they share a failure dependency. citeturn0search3

## Finding
Evidence multiplicity is not evidence independence.

Ten observations produced by one compromised source are not ten independent confirmations.
Likewise:
SOURCE_A + SOURCE_B + SOURCE_C
does not imply three independent sources if all depend on:
COMMON_PROVIDER / COMMON_SENSOR / COMMON_CREDENTIAL / COMMON_VERIFIER / COMMON_POLICY / COMMON_CLOCK / COMMON_COLLECTION_PATH.

## Normative dependency contract
Every evidence item that materially contributes to a consequential decision should expose, directly or through a dependency graph:
- EVIDENCE_ID
- SOURCE_ID
- COLLECTION_PATH
- TRUST_ANCHOR
- VERIFIER_ID where applicable
- POLICY_ID / POLICY_VERSION
- CREDENTIAL_OR_ATTESTATION_ROOT where applicable
- CLOCK/FRESHNESS_ROOT where relevant
- UPSTREAM_DEPENDENCIES
- COVERAGE_SCOPE
- APPRAISAL_STATE

These fields permit Nexo to calculate evidence dependency overlap instead of merely counting records.

## Dependency graph
Evidence nodes remain immutable.
Dependency edges describe shared assumptions or common-mode roots:
DERIVED_FROM
TRUSTS
COLLECTED_VIA
VERIFIED_BY
POLICY_DEPENDS_ON
SHARES_ROOT
SHARES_CLOCK
SHARES_CREDENTIAL

An evidence set with a common dependency root must be marked correlated.

## Evidence independence classes
INDEPENDENT — no material shared failure dependency identified within the declared model.
CORRELATED — one or more material common dependencies identified.
UNKNOWN_INDEPENDENCE — dependency graph incomplete.

Independence is therefore an appraisal property, not a property of source count.

## Decision rule
If a decision requires N independent confirmations:
- fewer than N independent paths -> insufficient evidence;
- N or more paths with unknown dependency -> UNKNOWN unless policy explicitly permits them;
- multiple correlated observations -> count according to the common dependency policy, not raw observation count.

Do not invent a numerical independence score unless a validated quantitative model exists.

## Common-mode examples
1. Multiple APIs backed by the same provider control plane -> correlated.
2. Multiple sensors receiving the same upstream measurement -> correlated.
3. Multiple logs generated by the same event and mirrored into different stores -> duplicate/correlated, not independent operations.
4. Multiple verifiers using the same compromised policy/reference-value source -> correlated.
5. Different evidence signed by the same compromised attesting root -> shared trust dependency.
6. Independent clocks observing the same event -> potentially independent timing evidence, but not independent proof of the event itself.
7. Separate credentials issued by the same compromised authority -> shared trust dependency.
8. Two observations with unknown provenance -> UNKNOWN_INDEPENDENCE, not independent.

## Anti-collapse rules
1. OBSERVATION_COUNT != INDEPENDENT_EVIDENCE_COUNT.
2. DIFFERENT_SOURCE_ID != INDEPENDENT_TRUST_ROOT.
3. DIFFERENT_STORAGE != DIFFERENT_EVENT.
4. DIFFERENT_API != DIFFERENT_OPERATION.
5. DIFFERENT_VERIFIER != INDEPENDENT_APPRAISAL if policy/reference roots are shared.
6. DIFFERENT_TIMESTAMP != INDEPENDENT_CLOCK.
7. DIFFERENT_CREDENTIAL != INDEPENDENT_AUTHORITY.
8. SIGNATURE_VALID != SOURCE_INDEPENDENT.
9. CORRELATED != INVALID.
10. UNKNOWN_INDEPENDENCE != INDEPENDENT.

## Integration with reconciliation
Conflict reconciliation must first determine whether apparently conflicting observations share dependencies.
If two observations share a common source and disagree, the result is not automatically stronger because there are two records; the common source may be the common cause of the disagreement.
If two observations are independently rooted and disagree, CONFLICT may carry stronger evidentiary significance, but it still does not by itself establish which observation is correct.

## Integration with authorization
Two independent authorization checks are useful only if their authority roots and policy inputs are independently established.
A second check performed by the same compromised policy/verifier path does not create independent authorization evidence.

## Result
No new identity primitive is required.
New generic requirement identified: evidence provenance must preserve dependency structure so Nexo can distinguish multiplicity from independence.
This is a direct extension of the existing Evidence Dependency Graph concept and does not alter closed physical/configuration/causal/authorization branches.
