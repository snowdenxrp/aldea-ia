# Nexo AB104.431 — Linearizable Reads, Leases, Watches and Fencing

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY

Implementation: NOT PERFORMED

## Research question

What does each currentness mechanism actually guarantee, and why does a current read not automatically authorize a later protected effect?

## Evidence

Google Spanner documents linearizability as a property of individual read/write objects and external consistency as a stronger transaction-level property. Strong reads observe effects committed before the read begins. citeturn0search0turn0search2

AWS DynamoDB distinguishes eventually consistent from strongly consistent reads. Strong reads return the latest committed data for supported local resources, but AWS explicitly notes that a read does not prevent the item from being modified immediately afterward. citeturn0search1turn0search10

AWS also documents that global-table consistency depends on the selected mode and region; some cross-region reads can remain stale under eventual consistency. citeturn0search6turn0search11

## Core finding

A linearizable/current read can establish a fact about state at its linearization point.

It does not automatically establish that the same state remains valid at a later external-effect point.

Therefore:

CURRENT_READ != FUTURE_AUTHORIZATION

and:

LINEARIZABLE_READ != LINEARIZABLE_EFFECT.

The latter requires the effect boundary itself to participate in the protected protocol.

## Mechanism comparison

### M1 — eventually consistent read

Guarantee candidate:
- returns a committed but potentially stale state.

Useful for:
- telemetry;
- low-consequence optimization;
- discovery.

Not sufficient alone for:
- immediate revocation;
- stale-authority exclusion;
- high-consequence currentness.

### M2 — strongly consistent / linearizable read

Guarantee candidate:
- read observes the latest state according to the service's consistency contract at its linearization point.

Useful for:
- current-state observation;
- protected precondition evaluation.

Residual:
state can change after the read.

### M3 — transactional read + conditional write

A transaction can bind observation and mutation within one atomic service boundary when the service supports the required transaction semantics.

This is materially stronger than separate read and write operations.

But it still does not automatically cover an external provider outside that transaction.

### M4 — lease

Lease answers an ownership/liveness question bounded by expiration.

It does not inherently reject every delayed old request.

Therefore:

LEASE_VALID != REQUEST_CURRENT.

### M5 — watch/stream

A watch provides ordered updates or change notifications according to its protocol.

It can maintain a local current-state replica if:
- updates are authenticated;
- ordering/generation is tracked;
- gaps are detected;
- reconnect/recovery obtains missing state.

A watch is not automatically a currentness proof if continuity can be lost.

### M6 — fencing

A fence makes the resource itself reject stale generations.

This directly addresses stale-actor safety.

Candidate:

RESOURCE_ENFORCEMENT_AT_EFFECT_BOUNDARY > CLIENT_OBSERVATION_ONLY

for the specific stale-actor property.

## Read-before-effect race

Timeline:

R1: read current authority = G7
R2: authority changes to G8
R3: external effect uses G7.

Even if R1 was perfectly linearizable, the request is stale at R3.

Therefore the required property must be checked at or bound to R3.

Candidate controls:
- resource-side fencing;
- conditional write against current generation;
- atomic transaction including the protected effect;
- equivalent provider-enforced precondition.

## Read + local decision + external call

Protocol:

READ_CURRENT
→ COMPUTE
→ SEND_EXTERNAL_REQUEST

has an unavoidable TOCTOU window unless the external recipient enforces a matching condition.

The longer the window, the greater the operational exposure, but reducing latency alone does not establish safety.

## Lease analysis

Lease can help establish:

OWNER_UNTIL

but not necessarily:

NO_OLD_OWNER_REQUEST_CAN_EXECUTE.

For Nexo, lease expiration is a liveness/ownership mechanism.

Fence generation is the stronger safety mechanism for stale requests.

Candidate:

LEASE = LIVENESS/OWNERSHIP
FENCE = STALE-ACTOR SAFETY

Some systems may use both.

## Watch analysis

A watch-based local replica can become current only while its continuity assumptions hold.

Candidate state:

WATCH_CURRENT(G)
→ WATCH_GAP
→ WATCH_STALE
→ SNAPSHOT_REVALIDATION
→ WATCH_CURRENT(G+n).

Do not continue using stale state during the gap for protected effects.

## Linearizable read does not mean globally current across services

A linearizable read is scoped to the consistency domain that provides it.

If Nexo reads authoritative state from service A and then effects resource B, A's linearizability does not automatically constrain B.

Therefore:

CONSISTENCY_DOMAIN_A != CONSISTENCY_DOMAIN_B.

Cross-domain safety requires a binding mechanism.

## Conditional write

A conditional write such as:

write iff version == G7

moves the check closer to the mutation.

This is stronger than:

read version G7
then unconditional write.

It can provide atomic stale-target exclusion for the resource that enforces the condition.

It still does not establish:
- external world state beyond the resource;
- cross-resource atomicity;
- upstream authority semantics unless the condition includes them.

## Multi-resource effect

For R1 and R2:

R1 condition passes
R2 condition fails.

Conditional writes prevent stale mutation independently but do not create atomic cross-resource commit.

Result remains:

PARTIAL_COMMIT / RECONCILIATION_REQUIRED

where applicable.

## Current read + fencing

Candidate strong composition:

1. linearizable/current read of authority;
2. final authority gate;
3. issue resource-bound fence generation;
4. resource validates fence at mutation;
5. external outcome separately reconciled.

The read supplies current state evidence.
The fence enforces stale-actor exclusion.
The external reconciliation establishes what actually happened.

These are different proof obligations.

## Strong read + lease without fencing

Potential failure:

lease appears valid;
old request delayed;
new lease holder takes ownership;
old request arrives before the old lease's local clock interpretation catches up.

Without resource-side fencing, stale execution may remain possible.

Therefore:

STRONG_READ + LEASE != STALE_ACTOR_PROOF

unless the service explicitly defines stronger semantics.

## Provider examples

DynamoDB strongly consistent reads are useful evidence that “latest committed state” is a defined service property, while its documentation also warns that modifications can happen immediately after the read. citeturn0search1

Spanner provides stronger transaction semantics when reads and writes occur within its transaction model; its external consistency guarantee is therefore not equivalent to merely performing a strong read followed by an unrelated external call. citeturn0search0turn0search2

## Candidate property mapping

| Property | Candidate primary mechanism |
|---|---|
| observe latest local authoritative state | linearizable/strong read |
| bind read + local mutation | transaction/conditional mutation |
| stale actor exclusion | resource-side fencing |
| ownership/liveness | lease |
| low-latency state propagation | watch/push |
| gap recovery | snapshot + generation validation |
| cross-provider effect | participant fences + reconciliation |
| external-world confirmation | provider/resource evidence + reconciliation |

This is a research matrix, not a final technology selection.

## Important boundary

Nexo should avoid treating “strongest available read” as a universal solution.

The question is not:

“Did we read current state?”

It is:

“Was the property that matters enforced at the boundary where the protected effect becomes possible?”

This reinforces the AB104.369–AB104.385 protected-transition model.

## New invariants

- CURRENT_READ != FUTURE_AUTHORIZATION
- LINEARIZABLE_READ != LINEARIZABLE_EFFECT
- LEASE_VALID != REQUEST_CURRENT
- STRONG_READ + LEASE != STALE_ACTOR_PROOF without stronger provider semantics
- WATCH_CURRENTNESS_REQUIRES_GAP_DETECTION
- CONSISTENCY_DOMAIN_A != CONSISTENCY_DOMAIN_B
- READ_BEFORE_EFFECT != EFFECT_AUTHORIZATION_AT_EFFECT_BOUNDARY
- CONDITIONAL_RESOURCE_WRITE > UNCONDITIONAL_WRITE_AFTER_READ for stale-target exclusion
- CONDITIONAL_WRITE != CROSS_RESOURCE_ATOMICITY
- FENCE_ENFORCEMENT_AT_RESOURCE != UPSTREAM_AUTHORIZATION_PROOF
- WATCH_GAP => REVALIDATION_REQUIRED
- STRONG_READ_IS_SCOPE_BOUND
- CURRENTNESS_IS_PROPERTY_AND_BOUNDARY_SPECIFIC
