## Why this re-audit exists

## Direct source findings

### 1. OFLE reducer
File: clients/src/main/java/org/apache/kafka/clients/consumer/internals/OffsetsForLeaderEpochUtils.java

Confirmed directly:
- partitionsToRetry starts as the complete requestData key set.
- unrequested response partitions are ignored with a warning.
- NONE writes endOffsets and removes the partition from retry.
- retry-class errors leave the partition in retry.
- UNKNOWN_TOPIC_OR_PARTITION also leaves it in retry.
- TOPIC_AUTHORIZATION_FAILED removes the partition from retry and accumulates unauthorized topic.
- duplicate response entries are not rejected by this reducer.
- because endOffsets is a Map and later NONE entries can replace an earlier value, duplicate ordering can affect the resulting map; retry removal is not reversed by a later retry-class entry.

These are source-code semantics, not test execution.

### 2. Correlation validation
File: clients/src/main/java/org/apache/kafka/common/requests/AbstractResponse.java

Confirmed directly:
- ResponseHeader is parsed using apiKey.responseHeaderVersion(apiVersion).
- request and response correlation IDs are compared immediately after header parsing.
- mismatch throws CorrelationIdMismatchException.
- API body parsing occurs only after the correlation check.

This establishes implementation behavior, not deliberate OFLE mismatch execution.

### 3. NetworkClientTest evidence
File: clients/src/test/java/org/apache/kafka/clients/NetworkClientTest.java

Direct inspection confirms:
- imports include RequestTestUtils and NetworkReceive.
- helper code repeatedly uses RequestTestUtils.serializeResponseWithHeader(response, version, request.correlationId()).
- responses are injected with selector.completeReceive(new NetworkReceive(...)).
- awaitReady is explicitly used before creating requests in the existing produce helper because bootstrap/API-version traffic can consume correlation IDs.
- the file's testCorrelationId() checks uniqueness and avoids the SASL reserved range.

Crucially, direct inspection did NOT find a dedicated NetworkClientTest method deliberately injecting a mismatched response correlation and asserting CorrelationIdMismatchException.

Therefore the previous statement that an OFLE-specific mismatch test existed remains false, and a generic direct NetworkClient mismatch execution test is also NOT established by this file.

### 4. Existing generic mismatch evidence elsewhere
File: server/src/test/java/org/apache/kafka/server/ForwardingManagerTest.java

testResponseCorrelationIdMismatch() deliberately serializes an AlterConfigsResponse using requestCorrelationId + 1. However, the test passes the response through Envelope/ForwardingManager and ultimately asserts an UNKNOWN_SERVER_ERROR count rather than directly asserting CorrelationIdMismatchException.

Therefore this is evidence that a mismatched correlation value can be constructed and exercised through that higher-level path, but it is NOT equivalent to direct NetworkClient/OFLE mismatch evidence.
