# Nexo AB104.546 — EffectID + fence revision conflict semantics

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Effect identity and authority generation solve different problems. EffectID answers “is this the same logical operation?”; FenceRevision answers “which authority generation is allowed to act?”. They must not be collapsed into one field.

A request with the same EffectID but a different request fingerprint is a conflict, not a retry. A request with the same EffectID and same fingerprint but an older fence is a stale replay/conflict; it must not be promoted to success merely because the logical operation is recognized. A request with the same EffectID and same fingerprint under a newer valid fence is a reconciliation/resubmission of the same logical effect, not automatically a new effect.

## Evidence
The IETF Idempotency-Key draft requires an idempotency key to be unique and not reused for a different payload; it describes duplicate retries as returning the previous result and concurrent requests as conflicts. Solana's current idempotency documentation similarly binds a key to a normalized request fingerprint and rejects reuse with a different payload. Fencing literature independently shows that monotonic fencing tokens order ownership generations and must be enforced at the protected resource. These sources support treating identity/fingerprint and authority generation as separate predicates. citeturn1search3turn1search0turn1search1

## Candidate admission matrix
Let E = EffectID, D = RequestDigest, F = FenceRevision.

1. E unknown + current valid F + valid request -> NEW_EFFECT_CANDIDATE.
2. E known + D equal + F current/accepted -> IDEMPOTENT_REPLAY / RETURN_STORED_RESULT.
3. E known + D different -> EFFECT_ID_CONFLICT; never silently overwrite.
4. E known + D equal + F stale -> STALE_REPLAY / RECONCILE; do not execute merely because E matches.
5. E known + D equal + F newer -> SAME_EFFECT_RESUBMISSION under a newer authority; provider must define whether this can advance the same effect or only reconcile it.
6. E known + D equal + F unknown/unverifiable -> UNKNOWN_AUTHORITY; HOLD.
7. E unknown + F stale -> REJECT_STALE_AUTHORITY before creating a new effect record.

## Important equality rule
A fence token can identify an ownership generation, but equality of fence token does NOT imply equality of operation. Multiple commands can legitimately share one owner generation. Therefore the resource may need a second per-generation sequence or idempotency invariant.

Candidate protected predicate:
`(FenceEpoch, FenceRevision) >= current authority` AND `EffectID/Digest` matches the durable effect record, with all relevant updates inside the provider's atomic boundary.

The exact comparison (`>` versus `>=`) depends on the operation contract. If one generation may issue multiple operations, equal fence values can be valid and EffectID/sequence must distinguish them. If one generation is allowed only one final mutation, equality can instead represent already-applied state. This is a contract decision, not a universal rule.

## Conflict states
Do not collapse these into generic FAILURE:
- EFFECT_ID_CONFLICT — same identity, different intent.
- STALE_FENCE — same/known intent presented by obsolete authority.
- FENCE_UNKNOWN — authority cannot be established.
- DUPLICATE_IN_PROGRESS — same logical effect is already executing.
- DUPLICATE_COMPLETED — same effect already has durable outcome.
- RESUBMISSION_ALLOWED — same effect may be reconciled/continued under current authority.
- EFFECT_OUTCOME_UNKNOWN — provider boundary may already have been crossed.

## Critical distinctions
- EFFECT_IDENTITY != AUTHORITY_GENERATION
- SAME_EFFECT != SAME_AUTHORITY
- SAME_FENCE != SAME_OPERATION
- IDEMPOTENT_REPLAY != NEW_EFFECT
- SAME_ID_DIFFERENT_DIGEST != RETRY
- NEWER_FENCE != PROOF_OLD_EFFECT_DID_NOT_EXECUTE
- STALE_FENCE != EFFECT_NEVER_APPLIED
- RECONCILIATION != REEXECUTION
- IDEMPOTENCY != FENCING
- FENCING != EXACTLY_ONCE

## Nexo implication
The effect contract should carry at least `EffectID`, `RequestDigest`, `AuthorityEpoch`, `FenceRevision`, `TargetIdentity`, `TargetIncarnation`, and an explicit outcome/status record. The execution plane must preserve the distinction between identity conflict, stale authority, duplicate, resubmission, and unknown external outcome.
