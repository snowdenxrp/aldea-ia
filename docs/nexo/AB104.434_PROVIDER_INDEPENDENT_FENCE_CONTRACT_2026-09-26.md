# Nexo AB104.434 — Provider-Independent Fence Contract

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.433 → AB104.434
Implementation: NOT PERFORMED

## Objective

Define the minimum semantics a provider/resource must expose before Nexo can rely on fencing, without selecting a technology yet.

## Core distinction

LEASE establishes an ownership/liveness condition.
FENCE establishes stale-authority exclusion at the protected resource boundary.

Therefore:

LEASE != FENCE

and:

FENCE_CLAIM != FENCE_ENFORCEMENT.

A system may issue generations without actually enforcing them where the protected effect occurs.

## Candidate Fence Contract

A protected request carries at minimum:

- authority_domain
- authority_incarnation
- authority_generation
- resource_id
- resource_incarnation
- fence_generation
- operation_id
- effect_id
- policy/trust generation where required

The resource accepts only when its protected current state satisfies the contract.

Candidate predicate:

ACCEPT iff

request authority/incarnation is current
AND request fence generation satisfies resource fencing policy
AND resource incarnation matches
AND operation/effect identity passes replay policy
AND all effect-specific preconditions hold.

## Required provider properties

### P1 — monotonic distinguishability

Old authority must remain distinguishable from new authority across restart/failover.

### P2 — durable or externally reconstructable fence state

The resource cannot reset to a state that makes an old request appear current.

### P3 — protected enforcement boundary

The generation check must occur at or inseparably bind to the mutation boundary.

### P4 — stale-request rejection

A request carrying an obsolete generation must be rejected, not merely logged.

### P5 — restart safety

Crash/restart must preserve or advance fencing state, or place the resource into quarantine.

### P6 — split-brain safety

Two authorities must not be able to mutate the same protected resource under indistinguishable current authority.

### P7 — replay semantics

Duplicate operation identity must not silently become a new effect after restart.

### P8 — recovery semantics

Recovery must expose enough evidence to establish which generation/incarnation is current.

## What the contract does NOT prove

Fencing does not prove that upstream authorization was semantically correct.

It does not prove that an external world effect did not occur.

It does not provide cross-resource atomicity.

It does not by itself prove uniqueness of authority unless the underlying election/authority protocol provides that property.

It does not replace external reconciliation.

Therefore:

FENCE_SUCCESS != EXTERNAL_EFFECT_CONFIRMED.

## Provider adapter boundary

Nexo should not encode ZooKeeper/etcd/database/cloud-specific semantics into the core.

Instead define an adapter capability set:

FENCE_ISSUE
FENCE_VALIDATE
FENCE_REVOKE
FENCE_RECOVER
FENCE_CURRENT
FENCE_DURABILITY
FENCE_FAILURE_SEMANTICS.

Each provider must supply evidence for the capabilities it claims.

## Capability levels

F0 — no fencing guarantee.

F1 — generation metadata only.

F2 — resource-side conditional generation check.

F3 — durable restart-safe fencing.

F4 — split-brain-resistant authority + durable resource fencing.

F5 — verified end-to-end effect-boundary fencing with explicit recovery semantics.

These levels are candidate taxonomy only; they are not provider certifications.

## Admission rule

A high-consequence effect must not infer F4/F5 merely because a provider advertises leases, locks, transactions, or strong reads.

The exact stale-actor property must be mapped to the provider's documented semantics and failure behavior.

## Testable obligations

A future implementation must be able to test:

1. old generation rejected after rollover;
2. delayed old request rejected after failover;
3. duplicate operation remains same operation identity;
4. restart does not reset fence to an old value;
5. storage rollback cannot silently resurrect old authority;
6. split-brain attempt cannot obtain simultaneous protected mutation;
7. recovery enters safe state when continuity cannot be established.

These are future verification targets, not completed tests.

## Candidate state machine

UNFENCED
→ FENCE_ISSUED
→ FENCE_CURRENT
→ FENCE_SUPERSEDED
→ FENCE_REVOKED

Failure/recovery:

FENCE_CURRENT
→ RECOVERY_REQUIRED
→ REVALIDATING
→ FENCE_CURRENT
or
→ QUARANTINED.

No automatic transition from uncertain recovery directly to protected mutation.

- LEASE != FENCE
- FENCE_CLAIM != FENCE_ENFORCEMENT
- OLD_GENERATION_MUST_REMAIN_DISTINGUISHABLE
- RESOURCE_FENCE_MUST_SURVIVE_OR_SAFELY_BLOCK_AFTER_RESTART
- STALE_FENCE => NO_PROTECTED_MUTATION
- FENCE_SUCCESS != EXTERNAL_EFFECT_CONFIRMED
- FENCING != CROSS_RESOURCE_ATOMICITY
- STRONG_READ != FENCE_ENFORCEMENT
- PROVIDER_ADVERTISEMENT != VERIFIED_FENCE_PROPERTY
- UNCERTAIN_RECOVERY => NO_AUTOMATIC_PROTECTED_MUTATION
- DUPLICATE_OPERATION_ID != NEW_EFFECT_IDENTITY
