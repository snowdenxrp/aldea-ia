## Research question
Should Nexo require each protected resource to validate global authority plus its local fence, or place that translation in a trusted gateway?

## Fresh evidence
Kleppmann's fencing analysis makes the resource-side check the critical safety boundary: the protected resource must reject an older fencing token after a newer token has been accepted. A coordinator-side lease check alone does not close delayed-request races. citeturn0search0

This creates two architectural choices for heterogeneous providers:
1. direct resource enforcement;
2. a Nexo-controlled gateway that becomes the protected resource boundary before downstream release.

The second option can centralize Nexo semantics, but it does not magically transfer the gateway's guarantees to an uncooperative downstream system.

## Comparison

| Property | Direct resource validation | Trusted gateway translation |
|---|---|---|
| Stale GAE rejection | Resource must understand/validate authority binding | Gateway validates GAE before issuing local RF |
| Stale RF rejection | Resource validates RF | Gateway validates RF; downstream must still enforce any needed stale-request property |
| Heterogeneous provider support | Harder | Easier at gateway boundary |
| Gateway TCB size | Smaller | Larger |
| Provider independence | Lower | Higher at protocol boundary |
| Downstream stale-request safety | Strong only if provider enforces | Not automatically strong; depends on downstream |
| Failover complexity | Distributed across resources | Concentrated in gateway + downstream |
| Fence-state persistence | Required per resource | Required at gateway and/or downstream boundary |
| Multi-resource atomicity | Not provided | Not provided |
| Evidence/reconciliation | Provider-specific | Gateway adds observations but cannot invent downstream truth |
| Operational complexity | Higher at each provider | Higher in gateway and integration layer |

## Model A — Direct resource validation
Request carries:
AUTHORITY_DOMAIN + GAE + RESOURCE_ID + RESOURCE_INCARNATION + RF + EFFECT_ID

Resource-side acceptance requires current GAE binding, valid RF, correct incarnation, target preconditions, and effect contract at the protected linearization point.

Advantages:
- Safety check occurs where mutation is accepted.
- No extra intermediary for the critical predicate.
- Failure domain is closer to the actual resource.

Costs:
- Every resource adapter/provider must implement the semantics.
- Heterogeneous providers may lack a suitable conditional/fencing primitive.
- Multi-resource effects still need coordination/reconciliation.

## Model B — Trusted gateway
Gateway accepts the Nexo request, validates current GAE, maps it to a resource-scoped RF, persists the mapping/high-water mark, and sends downstream.

Advantages:
- Centralizes Nexo authority semantics.
- Can adapt heterogeneous provider APIs.
- Can provide a uniform effect contract to the rest of Nexo.

Costs:
- Gateway becomes part of the TCB.
- Gateway failover must preserve authority-to-fence mappings.
- A stale request already released downstream can still execute unless the downstream resource itself enforces a compatible fence or equivalent condition.
- Gateway success is not downstream confirmation.
- A gateway cannot provide cross-provider atomicity by itself.

## Critical boundary
The gateway is a valid protected boundary only for properties it actually controls.

If:
GATEWAY_ACCEPTED(F2) → DOWNSTREAM_SEND(F2)

but the downstream provider accepts an older delayed F1 without checking RF, then gateway validation does not establish:
NO_EFFECT_FROM_STALE_AUTHORITY

Therefore:
GATEWAY_FENCE_ENFORCEMENT != DOWNSTREAM_FENCE_ENFORCEMENT

## Failure and failover matrix

| Failure | Direct resource model | Gateway model |
|---|---|---|
| Coordinator crash | Resource fence state must survive; new authority must revalidate | Gateway must recover mapping and fence state before release |
| Resource restart | High-water mark must persist | Downstream still requires compatible persistence if it is safety boundary |
| Gateway restart | N/A | Recovery must not issue/accept stale mappings |
| Provider failover | Every acceptance replica must preserve fence semantics | Gateway can preserve its state, but provider failover can still lose downstream fence state |
| Network partition | Resource-side fence still decides if request arrives | Gateway cannot prevent downstream execution unless downstream enforces fence |
| Delayed old request | Rejected if resource high-water mark is newer | Rejected only where the request's fence is actually enforced |
| Lost response | UNKNOWN until evidence/reconciliation | UNKNOWN; gateway logs are not proof of downstream state |
| Multi-provider partial commit | Explicit participant states | Same; gateway does not make commit atomic |

## TCB implications
Direct validation distributes part of the TCB across each resource boundary. Gateway translation concentrates it in the gateway, but also makes the gateway responsible for:
- authority validation;
- fence issuance;
- mapping durability;
- resource incarnation binding;
- rollover;
- failover;
- recovery fencing;
- audit/evidence semantics.

This is not automatically better or worse; it changes where the claim must be proven.

## Candidate architectural conclusion
For Nexo, the cleanest general contract is not "always direct" or "always gateway."

Instead:
- **Direct provider fencing** when the provider can atomically validate a durable resource-scoped fence at the actual mutation boundary.
- **Trusted gateway** when provider heterogeneity prevents direct Nexo-aware fencing, but only if the gateway is itself an explicit protected boundary and downstream semantics are separately classified.
- **HOLD / UNKNOWN / downgraded claim** when neither boundary can enforce the required stale-authority property.

This preserves the distinction:
CONTROL_AUTHORIZATION != RESOURCE_ACCEPTANCE != EXTERNAL_CONFIRMATION.

## New findings
1. The gateway is not a substitute for a protected downstream boundary when stale-request rejection is required at the final resource.
2. Direct validation gives the strongest locality of the safety predicate but increases adapter requirements.
3. Gateway translation can improve interoperability but expands the TCB and failure/recovery surface.
4. Fence mappings must be durable and incarnation-bound.
5. Neither architecture establishes cross-provider atomicity.
6. Evidence generated by the gateway cannot be treated as proof of downstream execution state unless its semantics establish that property.
7. Provider capability must be declared per effect class, not assumed globally.
