# AB104.516 — provider-side fencing contracts

## Evidence
Google Cloud Storage supports generation/metageneration preconditions and returns `412 Precondition Failed` when the target no longer matches the supplied generation. These preconditions are explicitly intended to prevent races during writes/deletes/metadata updates. citeturn0search0 Amazon S3 supports conditional writes using `If-Match`/`If-None-Match`; an `If-Match` write succeeds only when the supplied ETag matches, otherwise it fails, and concurrent operations can also produce conflict responses. citeturn0search1 Kubernetes exposes preconditions binding an operation to both `resourceVersion` and `uid`, showing the distinction between current version and resource identity. citeturn0search7

## Core finding
Provider-side preconditions are a concrete form of **stale-writer exclusion**, but their assurance is exactly the scope the provider guarantees. They are not automatically Nexo authority tokens.

Candidate provider contract:
`PRECONDITION = {TargetIdentity, TargetIncarnation?, TargetVersion/Generation, NexoFenceToken?, OperationDigest}`

Provider executes the effect only if all required predicates hold atomically at its own mutation boundary.

## Capability classes
### P0 — No conditional mutation
Provider accepts ordinary writes only. Nexo cannot prove stale-writer exclusion.

`P0 + protected stale-writer requirement => UNKNOWN_OR_UNSAFE_EFFECT_CLASS`

### P1 — Version/ETag conditional mutation
Provider atomically checks an ETag/version/generation before mutation. This closes a race against modifications represented by that version.

### P2 — Identity + version conditional mutation
Provider checks both resource incarnation identity and version. This is stronger against delete/recreate/name-reuse races than version alone.

### P3 — Nexo-issued fence/generation enforcement
Provider accepts a Nexo fence/generation and rejects stale values at the mutation boundary. This creates a direct bridge from Nexo authority epoch/fence to provider-side stale-writer exclusion.

### P4 — Durable operation identity + fence + queryable reconciliation
Provider additionally preserves an operation identity and exposes authoritative status/reconciliation semantics, allowing UNKNOWN outcomes to be resolved without creating a second logical effect.

These are capability classes, not quality scores.

## Important distinction: version vs fence
A provider version/ETag can prove that the target has not changed relative to the supplied precondition. It does **not** by itself prove that Nexo's authority is current.

Conversely, a Nexo fence token can represent current Nexo authority but is useless for provider-side stale-writer protection if the provider does not enforce it atomically.

Therefore strong protection requires both sides where the effect class demands it:
`CURRENT_NEXO_FENCE + PROVIDER_ENFORCED_PRECONDITION`.

## Resource incarnation
Kubernetes' combination of UID and resourceVersion is a useful concrete model: `uid` identifies the resource incarnation while `resourceVersion` identifies a version in the provider's ordering domain. citeturn0search7

Nexo candidate:
`TargetIdentity + TargetIncarnation + ProviderVersion`

A name-only target is insufficient when deletion/recreation can cause the same logical name to refer to a new resource.

## Failure semantics
Provider responses must be classified, not collapsed into success/failure:
- `PRECONDITION_REJECTED`: provider proves required predicate was false at mutation boundary.
- `NOT_FOUND`: only meaningful if provider semantics establish the relevant incarnation/deletion state.
- `CONFLICT`: concurrent mutation/transition; do not blindly retry.
- `TIMEOUT/UNKNOWN`: no proof of non-application.
- `ACK`: provider acknowledgement at its declared scope; not automatic world truth.
- `APPLIED_WITH_RECEIPT`: strongest provider-local evidence when bound to exact operation identity and target incarnation.

## Fence contract candidate
`FenceToken = {NexoAuthorityEpoch, FenceRevision, TargetIdentity, TargetIncarnation, EffectID, RequestDigest, Expiry/LeaseGeneration?}`

Provider requirements when P3 is claimed:
1. validate token at mutation boundary;
2. reject stale/unknown fence generations;
3. bind accepted token to the exact operation/effect;
4. make acceptance durable according to the effect class;
5. expose enough evidence to reconcile after crash.

If the provider cannot perform these atomically, Nexo must not claim provider-side stale-writer exclusion.

## Key invariants
- `PROVIDER_VERSION_CHECK != NEXO_AUTHORITY_CHECK`
- `NEXO_FENCE != PROVIDER_FENCE_ENFORCEMENT`
- `NAME != RESOURCE_INCARNATION`
- `VERSION != INCARNATION`
- `PRECONDITION_REJECTION != PROOF_OF_GLOBAL_NON_EFFECT`
- `TIMEOUT != NOT_APPLIED`
- `ACK != WORLD_TRUTH`
- `PROVIDER_FENCE_UNENFORCED => NO_STALE_WRITER_EXCLUSION_CLAIM`
- `P3_FENCE_REQUIRES_ATOMIC_PROVIDER_ENFORCEMENT`
- `P4_REQUIRES_QUERYABLE_RECONCILIATION`

## Status
Research complete. Concrete systems confirm that generation/ETag/resourceVersion preconditions can close provider-local races, while identity binding handles delete/recreate hazards. Nexo's strongest provider contract therefore requires explicit target incarnation, provider version/precondition, and—when stale Nexo authority must be rejected—an enforced Nexo fence at the provider mutation boundary.

No implementation or formal verification performed.

Next exact step: AB104.517 — research crash semantics of provider-side preconditions: what can be proven after timeout/connection loss, how conditional mutation interacts with idempotency, and how to distinguish `PRECONDITION_REJECTED`, `APPLIED`, and `UNKNOWN` during reconciliation.
