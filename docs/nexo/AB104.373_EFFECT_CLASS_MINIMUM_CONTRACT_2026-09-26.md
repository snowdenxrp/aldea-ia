## Objective
Classify external effects by reversibility, idempotency, provider fencing, and observability; derive minimum candidate controls without selecting technology.

## Evidence
RFC 9110 defines idempotency by intended server effect and advises against automatic retry of non-idempotent requests unless semantics are known to be idempotent or the client can detect that the original was not applied. Conditional requests can require the target state to match before the method is applied. citeturn0search1turn0search0

## Effect classes

### E0 — Read / observation
Risk: no external mutation.
Minimum candidate: authenticated target + freshness requirements appropriate to the claim.
External confirmation: observation/evidence binding.
Unknown outcome: observation may be stale; do not equate missing observation with absence.

### E1 — Reversible / compensatable mutation
Examples: state changes with a documented inverse operation.
Minimum candidate:
- current authority + required scope
- target VersionSet/conditional state
- stable EffectID/OperationID
- durable intent before attempt when crash recovery matters
- provider fence where stale authority must be rejected remotely
- reconciliation after ambiguous outcome
- compensation represented as a NEW protected effect
Candidate admission can be possible when all required controls for the specific provider are enforceable.

### E2 — Idempotent mutation
Repeated identical requests have one intended effect under provider semantics.
Minimum candidate:
- authority/fence still required
- stable EffectID or provider-native idempotency key
- target precondition when concurrent state matters
- durable intent where recovery requires it
- reconciliation for lost acknowledgement
Idempotency reduces duplicate-effect risk; it does not establish authorization freshness. RFC 9110 explicitly treats retryability as dependent on idempotent semantics. citeturn0search1

### E3 — Non-idempotent but reversible mutation
Retry can create another effect, but an inverse exists.
Minimum candidate:
- provider-side fence if stale authority must be excluded
- unique stable EffectID that provider can recognize, or an equivalent exact effect identity
- target conditional state where relevant
- durable intent
- reconciliation before retry after UNKNOWN
- compensation only through a new authorized operation
If exact identity cannot be established, UNKNOWN must block blind retry.

### E4 — Irreversible / non-compensatable mutation
Highest control requirement.
Candidate minimum:
- current authority and scope
- provider-enforced fence or equivalent trusted atomic authorization frontier
- exact EffectID/OperationID semantics
- target conditional state where applicable
- durable intent and durable decision evidence
- independent or sufficiently strong external confirmation
- reconciliation path
- explicit HOLD/STOP behavior for UNKNOWN
If any control that is essential to the stated safety property cannot be enforced or evidenced, candidate result is HOLD/REJECTED, not SAFE-ADMISSIBLE.
No blind retry after UNKNOWN.

### E5 — Multi-provider / cross-resource mutation
No assumption of global atomicity.
Minimum candidate:
- per-resource effect identity
- per-resource authority/fence semantics
- explicit coordination protocol
- durable participant intents/results
- reconciliation graph
- explicit partial-commit states
- compensation where available
- UNKNOWN participant outcome remains UNKNOWN
CONTROL_ATOMICITY, COORDINATION_ATOMICITY, EFFECT_ATOMICITY, and OBSERVATION_ATOMICITY remain distinct.

## Derived minimum rule
For each effect class define:
1. Authorization freshness requirement.
2. Target freshness/VersionSet requirement.
3. Effect identity requirement.
4. Provider fence requirement.
5. Idempotency requirement.
6. Durable-intent requirement.
7. Confirmation requirement.
8. Reconciliation requirement.
9. Retry rule.
10. Compensation/reversal rule.
11. UNKNOWN policy.
12. Recovery owner/fence.

A missing capability is not automatically unsafe in the abstract; it is a contract mismatch if the claimed property requires that capability.

## Key conclusion
There is no single universal “external effect protocol.” The minimum contract is effect-class- and provider-dependent. The architecture must declare the required property first, then determine whether the available provider controls/evidence can support that property.
