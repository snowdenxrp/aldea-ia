# AB104.509 — reconciliation against distributed/eventually consistent targets

## Evidence
etcd assigns a monotonically increasing revision to modifications and supports point-in-time reads at a specific revision; linearizable reads reflect current consensus, while serializable reads may be stale. Watch events are ordered by revision but are not themselves linearizable and may be delayed. citeturn0search0turn0search5 AWS EC2 documents that asynchronous mutation requests can time out before their workflows finish, creating uncertainty about whether the operation succeeded; idempotency prevents duplicate completion when the same token and parameters are retried. citeturn1search0 Stripe likewise stores the result associated with an idempotency key and rejects reuse with different parameters, while allowing retries after connection failures. citeturn1search3

## Nexo reconciliation model
For an external target that does not provide a single strongly consistent read, reconciliation must distinguish:
`OBSERVED_APPLIED`, `OBSERVED_NOT_APPLIED`, and `UNKNOWN`.

A target observation should be bound to:
`{OperationID, EffectID, TargetIdentity, ResourceIncarnation, ProviderRevision/Receipt, ObservationRevision, ObservedAt}`.

A read that is merely stale cannot prove `NOT_APPLIED`. A watch event can indicate a change, but cannot by itself prove current target state because delivery may lag. etcd explicitly requires correlation with a linearizable revision when current state matters. citeturn0search0turn0search3

## Idempotency ledger
A durable Nexo ledger should bind one `OperationID` to one canonical request digest and target identity. Provider idempotency mechanisms demonstrate the useful invariant that the same key with different parameters must not silently become a second operation. citeturn1search0turn1search3

Candidate:
`OperationRecord = {OperationID, RequestDigest, EffectID, TargetIdentity, TargetIncarnation, IntentRevision, AttemptHistory, ProviderReceiptRefs, ReconciliationState}`.

`OperationID` is not itself proof that the external effect happened; it is the identity used to prevent/recognize duplicate attempts.

## Read-after-write and failover
If a provider exposes a monotonic revision/receipt, Nexo can require reconciliation at or beyond the revision that contains the operation. A read from a stale replica, or an observation without a comparable revision, cannot establish `NOT_APPLIED` merely because the effect is absent there.

During provider failover:
- preserve the same `OperationID` for the same logical operation;
- do not create a new `EffectID` merely because the executor changed;
- revalidate target identity/incarnation;
- reconcile against the provider's authoritative or sufficiently fresh status source;
- if the provider cannot establish a trustworthy result, remain `UNKNOWN`.

## Receipt semantics
A provider receipt proves what the provider claims at its stated scope. It does not automatically prove physical/external-world completion beyond that scope.

Therefore:
`PROVIDER_RECEIPT != WORLD_TRUTH`
`PROVIDER_ACK != EXTERNAL_CONFIRMED`
`STALE_NOT_FOUND != NOT_APPLIED`
`WATCH_EVENT != CURRENT_STATE`

## Revocation interaction
If revocation occurs while an effect is `UNKNOWN`, Nexo must not infer that revocation proves the effect did not happen. The correct state remains `UNKNOWN` until reconciliation establishes an outcome. A later retry requires a fresh authorization gate and the same logical operation identity when retry is semantically permitted.

## Candidate reconciliation gate
`load durable OperationRecord → obtain current/fresh target observation → bind observation revision/receipt → verify target identity/incarnation → compare request/effect identity → classify APPLIED/NOT_APPLIED/UNKNOWN → authorize retry only if policy permits`.

If the target cannot provide sufficient freshness or identity evidence:
`INSUFFICIENT_RECONCILIATION_EVIDENCE => UNKNOWN_OR_QUARANTINE`.

## Invariants
- `OPERATION_ID != PROOF_OF_EFFECT`
- `STALE_READ != NOT_APPLIED`
- `WATCH_EVENT != CURRENT_STATE`
- `PROVIDER_ACK != WORLD_TRUTH`
- `UNKNOWN != SAFE_TO_RETRY_BLINDLY`
- `SAME_OPERATION_RETRY => SAME_CANONICAL_REQUEST_DIGEST`
- `TARGET_INCARNATION_MUST_BE_REVALIDATED`
- `FAILOVER != NEW_LOGICAL_OPERATION`
- `REVOCATION_DURING_UNKNOWN != PROOF_OF_NOT_APPLIED`
- `INSUFFICIENT_RECONCILIATION_EVIDENCE => UNKNOWN_OR_QUARANTINE`

## Status
Research complete. No implementation or formal verification performed. The remaining design problem is defining provider-specific reconciliation capability classes and the minimum evidence required to transition `UNKNOWN` to `APPLIED` or `NOT_APPLIED`.
