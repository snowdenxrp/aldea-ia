# NEXO AB104.730 — OffsetForLeaderEpoch protocol-shape and provenance audit

Date: 2026-09-28

## Findings

The OffsetForLeaderEpoch response schema carries, depending on version, error_code + partition + (from v1 onward) leader_epoch + end_offset, and from later versions also throttle_time_ms. Protocol documentation confirms v0 lacks leader_epoch while v1+ carries it. v4 adds compact/tagged encoding and topic identifiers. These are serialization/protocol-shape concerns, not proof that the reducer preserves provenance.

Kafka has separate server-side request tests covering protocol error production:
- UNKNOWN_TOPIC_OR_PARTITION;
- NOT_LEADER_OR_FOLLOWER on follower/non-replica;
- current-leader-epoch validation producing NONE, FENCED_LEADER_EPOCH and UNKNOWN_LEADER_EPOCH.
These tests establish that several raw error codes can be generated by the broker path.
A Jira history item also documents prior correction of wrong error-code behavior for OffsetsForLeaderEpoch from non-replica.

Kafka also has client-side OffsetFetcher tests containing a list of the seven retriable errors, but those tests concern ListOffsets/retry behavior, not exhaustive direct coverage of the OffsetsForLeaderEpochUtils reducer. They therefore cannot close the reducer gap.

## New provenance conclusion

Raw errorCode is necessary but not sufficient if Nexo's claim depends on the meaning of the returned epoch boundary. For a successful response, the minimum semantic tuple is:
(topic/partition, request identity, response error code, leader epoch when protocol version supplies it, end offset, protocol version/schema identity).

For a failed response, end_offset and leader_epoch may carry sentinel/undefined values; they should remain recorded as received rather than normalized away before provenance capture. Protocol version must also be retained because v0 cannot supply leader_epoch while v1+ can.

Throttle time is operational metadata, not by itself authority provenance, unless a specific Nexo policy claim depends on quota timing.

Topic identity/version matters: modern v4 response/request uses topic identifiers, so a stable Nexo provenance record should not rely only on topic string if the surrounding protocol layer exposes a topic incarnation/ID.

## Important boundary

The reducer currently receives a parsed response and requestData, then returns endOffsets + partitionsToRetry or throws authorization. It does not return raw error identity for retry branches. Therefore the Nexo capture boundary should be immediately at the parsed-response boundary, before reducer classification, with the original request/operation identity and protocol version bound.

This is stronger than the AB104.729 conclusion that only errorCode needs preservation.
