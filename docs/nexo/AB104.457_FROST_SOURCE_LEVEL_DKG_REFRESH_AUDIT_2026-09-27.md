# Nexo AB104.457 — FROST source-level DKG/refresh audit
Date: 2026-09-27
Status: research-only; no Nexo implementation

## Scope
Audited the current Zcash Foundation FROST source at source level, focusing on DKG, refresh, participant identity handling, secret-package lifecycle, and the boundary between cryptographic correctness and Nexo recovery authority.

External evidence: RFC 9591 and the Zcash Foundation repository; NCC Group's public assessment states that its 2023 assessment covered the v0.6.0 release and that identified issues were remediated and retested. The repository states that the audit covered frost-core and several ciphersuites, including trusted-dealer and DKG key generation, but not every crate/feature.

## Source findings

### 1. DKG explicitly depends on authenticated participant binding
part2() and part3() document that map identifiers must come from the participant-to-channel mapping and that the implementation assumes assurance that a package came from the participant named by the identifier.

Nexo consequence:
- cryptographic package validity does NOT establish participant identity;
- authenticated channel/identity binding is an external dependency of DKG;
- participant enrollment and binding therefore remain part of the authority/security TCB when DKG is used for recovery-root material.

### 2. DKG requires a consistent broadcast view
The module documentation states that participants must maintain a consistent view of public commitments and that the commitment values must be honestly broadcast over a secure broadcast channel.

Nexo consequence:
- VALID_DKG_PROOF != CONSISTENT_GLOBAL_DKG_VIEW;
- a valid local proof cannot by itself establish that every participant saw the same commitment set;
- broadcast consistency must be represented as evidence with its own dependency closure.

### 3. Proof-of-knowledge binds identifier/context, but does not create governance authority
The Schnorr-style DKG proof challenge incorporates the participant identifier, verifying key and nonce point. This prevents certain rogue-key/replay classes at the cryptographic layer.

Nexo consequence:
- proof validity can support a protocol implementation claim;
- it cannot establish legitimate enrollment, authorized participant set, or valid Nexo recovery-root authority.

### 4. Threshold parameters are carried through the packages and checked
DKG validates min/max signer counts. part2() checks package count and threshold consistency; part3() checks matching participant sets between round 1 and round 2.

Nexo consequence:
- protocol-level participant-set/threshold consistency is useful evidence;
- it is not equivalent to Nexo GOVERNANCE_THRESHOLD or INDEPENDENCE_THRESHOLD;
- the semantic recovery event must bind threshold, participant set, generation/incarnation and governance scope outside the cryptographic library.

### 5. Secret material has explicit zeroization intent, but persistence/recovery semantics remain external
Secret packages derive Zeroize/ZeroizeOnDrop, while long-lived signing shares are stored in KeyPackage. The library documents which packages must remain secret and which communication channels require confidentiality/authentication.

Nexo consequence:
- memory hygiene evidence is distinct from durable secret custody;
- crash recovery, backup, rollback, hardware custody, revocation and compromise response remain outside this source-level primitive;
- ZEROIZE_SUPPORT != TRUST_RECOVERY.

### 6. Refresh preserves the group verifying key while changing participant verifying shares
The DKG refresh path creates zero-sum refresh material and combines it with the old signing share. The resulting group verifying key remains unchanged while verifying shares change.

Nexo consequence:
- a refresh epoch cannot be treated as a new trust root merely because shares changed;
- unchanged group key means cryptographic continuity, not proof that governance continuity is legitimate;
- participant removal through refresh must be coupled to an explicit Nexo membership/authority transition.

### 7. Refresh participant membership is an explicit input
The trusted-dealer refresh API takes an explicit identifier list; missing participants are effectively removed. The DKG refresh API takes a selected participant count/set.

Nexo consequence:
- participant-set change is a protected transition;
- REFRESH_SUCCESS != AUTHORIZED_PARTICIPANT_ROTATION;
- old participant revocation must be represented and independently evidenced.

### 8. Important source-level asymmetry: refresh DKG skips proof verification in refresh_dkg_part2()
The current refresh code explicitly comments that it does not verify the proof of knowledge for each incoming round-1 refresh package in refresh_dkg_part2(). It later reconstructs commitments and verifies received secret shares in refresh_dkg_shares().

Nexo consequence:
- this is not automatically a vulnerability: the refresh protocol has different algebraic requirements because the refresh polynomial has zero constant term;
- however, it creates an evidence boundary that Nexo must not accidentally interpret as equivalent to full initial-DKG authentication;
- surrounding authenticated participant binding and final share verification are therefore critical;
- this deserves adversarial test coverage before any reuse in a Nexo trust-root protocol.

### 9. Integration tests model transport/storage rather than proving an independent deployment
The refresh tests simulate separate participants using in-memory maps, then serialize/deserialize packages to model communication/storage. The test comments distinguish this simulation from real participant environments.

Nexo consequence:
- passing these tests demonstrates library-level behavior under modeled cases;
- it does not establish secure transport, identity enrollment, durable crash recovery, rollback resistance, hardware custody, independent failure domains, or governance legitimacy;
- TEST_PASS != DEPLOYMENT_ASSURANCE.

## AB104.458 continuation findings — NCC audit traceability

The public NCC report reviewed v0.6.0 at commit 5fa17ed, over 25 person-days, and reported 8 findings: 3 medium, 3 low, 2 informational. It explicitly says the review targeted the implementation against the FROST reference/paper rather than reviewing those source materials themselves, and that retesting confirmed all findings fixed. cite(report lines 23-65)

The most relevant audit finding for Nexo's authority/evidence model is NCC-E008263-AW3, "Insufficient Participant Commitment List Checks." NCC found that a participant did not validate that its own identifier and commitments in the signing package matched what it sent earlier, and did not ensure expected participant-set consistency. NCC described possible DoS and potential forgery avenues, including ROS-style attacks if a participant's own commitments are absent. The fix added participant-count validation and related validation changes; NCC marked it fixed after retest.

The audit therefore reinforces a key Nexo rule: cryptographic protocol state must be checked against the participant's locally authoritative view, not merely against syntactically valid incoming objects. In Nexo terms: EXTERNALLY_VALID_OBJECT != LOCALLY_AUTHORIZED_CONTEXT.

NCC-E008263-9XW found insufficient validation of custom identifier-list length against threshold parameters, with possible DoS and loss of threshold-assumption security. This directly supports binding participant-set cardinality to the protected recovery event rather than accepting it as an untrusted mutable input. Nexo rule: PARTICIPANT_SET_VALIDITY includes threshold consistency, membership authority, generation and event binding.

The report's client response also states that an untrusted dealer means security is lost and DKG should be used so no single entity is trusted. For Nexo this is only one layer: DKG removes a single cryptographic dealer dependency, but does not establish governance legitimacy, independence of participants, current authority, or deployment trust.

The audit scope is also bounded: the reviewed release covered the core crates and key generation/signing, but excluded frost-secp256k1-tr and rerandomized FROST. Therefore audit evidence cannot silently be promoted to claims about excluded components or today's entire repository. The current repository separately records later security fixes, including a 2025 advisory that refreshing shares with a smaller min_signers reduces group security.

## AB104.460 — source-diff audit of NCC fixes

The actual fix diffs show that the audit response was not merely defensive error handling; several fixes moved security-relevant assumptions into persistent protocol state or changed APIs so invalid states become harder to represent.

### 1. Minimum participant constraints (PR 453)
The fix centralizes validation of `min_signers`/ `max_signers` and invokes it at trusted-dealer generation, DKG part 1, and repair-share entry points. Tests explicitly cover min < 2, max < 2, and min > max. This means the same semantic invariant is enforced at multiple protocol-entry boundaries rather than only in one lower-level polynomial routine. cite(turn0search1)

**Nexo extraction:** `VALIDATION_AT_ONE_LAYER != PROTECTED_TRANSITION_COVERAGE`. Any authority-changing operation must validate its security parameters at every entry path capable of creating or transforming authoritative state.

### 2. Missing signing-package validation (PR 452)
The fix makes the signer verify that its own identifier exists in the signing package and that the supplied commitment equals the commitment generated from its own nonces. The added tests exercise both missing and incorrect commitments. NCC's report describes the original condition as potentially enabling stronger attacks when an attacker controls commitment values. cite(turn0search12turn0search1

**Nexo extraction:** a participant must authenticate the binding between **identity → locally generated intent/commitment → received package**. Mere syntactic membership is insufficient.

### 3. Participant-count validation (PR 480)
The fix adds `min_signers` to `KeyPackage` and checks the number of commitments before signing. The test suite deliberately mutates the stored threshold downward to exercise protocol failure separately from the ordinary pre-check. This is a strong example of testing the security boundary rather than only the happy-path API. cite(turn0search12turn0search1

**Nexo extraction:** threshold metadata becomes part of the participant's protected cryptographic state; therefore Nexo must bind threshold/generation/policy version to the authoritative transition and treat threshold changes as protected governance events, not ordinary parameters.

### 4. Unchecked access (PR 477)
The fix replaces several indexing/unwrap paths with explicit error-returning accessors, adds identifier-set checks during aggregation, and changes missing commitment/binding-factor conditions into protocol errors. It also introduces lint-level defenses against indexing/unwrap in the relevant crate. This reduces panic-oriented failure paths, but it does not by itself establish recovery correctness, availability, or authority legitimacy.

**Nexo extraction:** `NO_PANIC != SAFE_RECOVERY`; failure must be explicit, durable where relevant, and mapped into Nexo's STOP/HOLD/UNKNOWN/reconciliation semantics.

### 5. Important version boundary
The official repository states that NCC audited v0.6.0 at commit 5fa17ed and that the named crates plus DKG/key generation/signing were in scope; other components were excluded. Current repository code has continued evolving, so the audit is evidence for that bounded release, not a blanket claim over today's complete repository. cite(turn0search0turn0search2

### New Nexo invariants
- `SECURITY_PARAMETER_VALIDATION = ENTRY_PATH_COMPLETE`, not merely a single helper check.
- `IDENTITY_BINDING = ID + LOCALLY_GENERATED_MATERIAL + RECEIVED_CONTEXT`.
- `THRESHOLD = PROTECTED_STATE`, when threshold controls authority/security.
- `EXPLICIT_ERROR != PANIC`, but both remain below recovery correctness until state/effect consequences are defined.
- `AUDIT_EVIDENCE` is always scoped by release, commit, crate/module, finding, fix and retest.

## AB104.461 — Ed448 timing/zeroization and custody lifecycle

NCC's v0.6.0 finding table records three Ed448-specific issues: incorrect base-field negation (72Y, medium), potential timing attacks (T3P, low), and lack of zeroization in scalar inversion (HGL, informational); all were marked fixed. The project issue tracking identifies the concrete mitigations: field negation/reduction and stricter field types for 72Y, removal of timing-sensitive assertions for T3P, and changing scalar inversion's table handling to avoid leaking values to the heap for HGL. citeturn0search20turn0search2

### Security meaning for Nexo
1. CONSTANT_TIME_INTENT != CONSTANT_TIME_EVIDENCE: removing timing-sensitive assertions addresses a concrete source, but deployment/runtime evidence still needs scope if Nexo makes a side-channel-resistance claim.
2. ZEROIZATION_PRESENT != SECRET_LIFECYCLE_COMPLETE: zeroizing a local object does not establish protection against swap, snapshots, core dumps, allocator copies, logging, serialization, DMA, crash persistence, or compromised runtime/hardware.
3. CRYPTO_CORRECTNESS != CUSTODY_CORRECTNESS: a mathematically correct threshold operation can still leave recovery material exposed or stale.
4. MEMORY_HYGIENE_SCOPE = TYPE + TRANSITION + STORAGE + CRASH + TELEMETRY + RUNTIME: Nexo should treat secret-material handling as a lifecycle property, not a destructor-only property.

Current project evolution reinforces this boundary: a 2025 issue proposed broader ZeroizeOnDrop/secrecy coverage, and 2026 issues requested zeroization for signing nonces and DKG round packages containing secret material. The current changelog also records additional ZeroizeOnDrop work and a DKG round-2 serialization fix. These are later than the audited v0.6.0 release and therefore demonstrate that memory-hygiene assurance evolves after an audit. citeturn0search8turn0search10turn0search12turn0search13

### New Nexo custody evidence chain
SECRET_CREATED → SECRET_BOUND_TO_IDENTITY → SECRET_USED → SECRET_PERSISTENCE/TRANSFER → SECRET_ZEROIZED_OR_EXPLICITLY_RETAINED → CRASH/RECOVERY_RECONCILIATION → DECOMMISSION_VERIFIED

For each sensitive object, Nexo should eventually be able to state which lifecycle stages are proven, which are merely intended, and which are UNKNOWN. A ZeroizeOnDrop implementation is evidence for one stage, not proof of the complete chain.

### New invariant
ZEROIZATION_CLAIM_SCOPE <= OBSERVED_MEMORY_LIFECYCLE_SCOPE

## AB104.462 — zeroization evolution: source, tests, audit and runtime boundaries

The current FROST project history gives a stronger concrete example of why Nexo must model memory hygiene as an evolving evidence claim. The 2025 zeroization work explicitly targeted broader assurance with ZeroizeOnDrop/secrecy, while later issues identified secret-bearing types that had still escaped that coverage: SigningNonces and DKG round packages. Those gaps were subsequently addressed in 2026; the DKG round-2 package ZeroizeOnDrop change passed the project's CI matrix. 

The important distinction is temporal and scope-based: an audit of the 0.6.0 release can establish evidence about that snapshot, but later code changes can introduce new secret-bearing object classes or new lifecycle paths. The project's own audit page says the NCC assessment covered v0.6.0 and specified crates/components, while the current repository is at a later major version.

The official DKG documentation also makes custody assumptions explicit: round-1 and round-2 secret packages remain in memory between protocol stages; round-2 packages must be encrypted in transit because exposure can reconstruct the generated secret; and the application is responsible for the authenticated mapping between communication channels and participant identifiers.

### Nexo evidence separation
- E0 source intent: type derives/explicit zeroization code exists.
- E1 source behavior: source path demonstrates when the sensitive value is dropped/zeroized.
- E2 test/CI: tests and CI establish that the code builds and the intended trait/behavior is exercised; they do not prove every runtime memory path.
- E3 independent audit: NCC can bound claims to the audited release/scope and retest.
- E4 deployment/runtime: requires evidence about actual process, allocator, crash handling, snapshots, transport, host/hardware and operational configuration.
- E5 recovery/custody assurance: requires evidence that secret lifecycle remains controlled across compromise, restart, rotation, decommission and recovery.

### New Nexo rules
1. AUDIT_SNAPSHOT != CURRENT_IMPLEMENTATION.
2. ZEROIZE_TRAIT != MEMORY_ERASURE_PROOF.
3. CI_PASS != DEPLOYMENT_CUSTODY_PROOF.
4. ENCRYPTED_TRANSPORT != END_TO_END_CUSTODY_COMPLETE.
5. SECRET_TYPE_COVERAGE must be recomputed whenever new protocol objects or lifecycle paths are introduced.

### New research result
Memory hygiene is not a one-time cryptographic property. It is a versioned lifecycle invariant whose evidence must be re-evaluated whenever protocol objects, serialization, transport, recovery, or deployment topology changes.

## AB104.463 — 2026 zeroization coverage and residual custody surface

The current source history confirms that zeroization coverage is still an actively maintained property. Issue #986 identified SigningNonces as secret nonce scalars whose leakage or reuse can recover the private key; its follow-up CI run for the ZeroizeOnDrop implementation completed successfully. Issue #1018 then identified DKG round1::Package and round2::Package as additional secret-bearing package types that had escaped the earlier zeroization pass; round2::Package contains a signing share and round1::Package contains a proof-of-knowledge signature containing a secret nonce scalar. The corresponding implementation CI run for #1040 completed its matrix successfully.

This exposes a recurring pattern: a first zeroization pass can cover obvious secret containers while leaving protocol messages or transport-facing objects with embedded secret material. Therefore Nexo must inventory secrets by data-flow and protocol role, not only by type names.

The DKG documentation is especially important: it requires an authenticated mapping from communication channels to participant identifiers, requires a broadcast channel for round 1, and requires encrypted round-2 packages because an observer can reconstruct the generated secret. The library therefore explicitly places parts of identity, transport and custody outside the cryptographic primitive.

A second residual surface is serialization. FROST's changelog records a fix for DKG round-2 SecretPackage serialization and notes that older long-term serialized packages could require manual parsing/discarding during migration. A separate refresh issue demonstrated that a post-part2 refresh SecretPackage could fail serialization because refresh legitimately uses an identity constant term while the borrowed DKG type rejected it. This means serialization format is itself part of secret lifecycle and recovery semantics.

### Nexo-derived rules
- SECRET_IN_TYPE != ALL_SECRET_PATHS_COVERED.
- PROTOCOL_MESSAGE != PUBLIC_DATA merely because it is transported between participants.
- AUTHENTICATED_CHANNEL_BINDING != GOVERNANCE_AUTHORITY.
- ZEROIZE_ON_DROP != ZEROIZE_AFTER_SERIALIZATION/TRANSPORT.
- SERIALIZABLE_SECRET != RECOVERY_SAFE_SECRET.
- Every secret-bearing object needs a lifecycle record covering creation, derivation, transport, serialization, persistence, crash, recovery, rotation and destruction.
- Any change that introduces a new secret-bearing field/type or a new serialization path invalidates a prior blanket zeroization claim until re-audited.

### Evidence result
E2 CI evidence is now concrete for two later zeroization additions, but it remains evidence of the tested build matrix, not proof of host-memory erasure, crash-dump policy, allocator behavior, snapshot handling, DMA exposure, or hardware custody. Those remain E4/E5 UNKNOWN for Nexo.

## AB104.464 — durable secret material: persistence, rollback and recovery boundary

Research shows that making recovery material durable is not equivalent to making it safe. OWASP's current guidance treats secret management as a lifecycle covering creation, rotation, revocation, expiration, backup/restore and decommissioning, and recommends encrypted backups with restricted access plus tested restore procedures. It also distinguishes server-side at-rest encryption from client-side encryption, where plaintext remains unavailable until the intended consumer decrypts it.

For cryptographic keys specifically, OWASP states that keys require protection in both volatile and persistent memory, that exported/offline key material should be encrypted with a key-encryption key, and that formal processes must cover generation, storage, distribution, rotation and decommissioning. It also notes that a fully compromised application may still be able to obtain keys, so storage controls must be tied to the threat model.

Applied to Nexo recovery material, four distinct states must not collapse:
- SECRET_IN_MEMORY: material currently resident in a process.
- SECRET_DURABLE_ENCRYPTED: encrypted persistence exists, but recoverability and authority are separate questions.
- SECRET_RECOVERABLE: an authorized process can reconstruct/use the material under current policy.
- SECRET_REVOKED_OR_DECOMMISSIONED: the material must no longer authorize/use protected operations.

A durable encrypted backup therefore proves neither current authority nor safe recovery. Conversely, deleting a ciphertext copy does not by itself prove that plaintext copies, old backups, snapshots, caches or retired keys are gone.

### Rollback finding
If durable recovery material is restored from an older snapshot, Nexo must bind the recovered artifact to an authority generation, policy baseline, cryptographic version and continuity anchor. A syntactically valid old secret must not silently regain authority after a newer rotation/revocation event.

### Key-wrapping finding
Envelope encryption creates at least two lifecycle objects: the protected secret/data key and the wrapping key. Rotation, compromise, recovery and destruction therefore need dependency-aware ordering; deleting the wrapper while retaining ciphertext creates unrecoverable data, while retaining an old wrapper after revocation may preserve unintended decryptability.

### Recovery finding
Backup existence is evidence of availability, not evidence of authorization. Recovery must separately establish:
ARTIFACT_INTEGRITY → VERSION_COMPATIBILITY → CURRENT_AUTHORITY → REVOCATION_STATUS → CONTINUITY/ANTI_ROLLBACK → EXPLICIT_RECOVERY_RELEASE.

### New Nexo invariants
- DURABLE_ENCRYPTION != AUTHORITY.
- RESTORE_SUCCESS != RECOVERY_AUTHORIZATION.
- CURRENT_GENERATION > SNAPSHOT_GENERATION => NO_SILENT_REPROMOTION.
- CIPHERTEXT_DELETION != PLAINTEXT_ERASURE.
- WRAPPING_KEY_LIFECYCLE >= PROTECTED_SECRET_LIFECYCLE.
- BACKUP_AVAILABILITY != TRUST_RECOVERY.

### Evidence status
The external guidance establishes lifecycle requirements and threat-model boundaries, but does not prove any Nexo implementation. Nexo remains research/design-only; concrete storage technology, HSM/vault selection and implementation are deliberately deferred.

## AB104.465 — rollback-resistant recovery and key-wrapping dependency graph

NIST defines key management as the complete lifecycle of cryptographic keying material, including generation, storage, establishment, use and destruction; its key-management-system definition additionally includes backup, archive, recovery, revocation and destruction. This supports treating recovery metadata and state transitions as first-class security objects rather than incidental storage details.

OWASP likewise requires backup/restore procedures to be tested and audited, backups to be encrypted and access-restricted, and secret lifecycle metadata to record creation, consumption, rotation, archival and deletion. Its key-management guidance distinguishes data-encryption keys from key-encryption/wrapping keys and requires independent lifecycle management and tested rotation/decommissioning.

### Rollback-resistant recovery model

A recovered artifact cannot be trusted solely because its cryptographic integrity verifies. Nexo must validate a recovery artifact against an authoritative continuity state:

ARTIFACT_HASH → ARTIFACT_VERSION → AUTHORITY_GENERATION → REVOCATION_STATE → POLICY_BASELINE → CONTINUITY_ANCHOR → CURRENT_RECOVERY_FENCE

If any authoritative comparison is unavailable, the recovered authority remains UNKNOWN rather than being promoted by successful decryption or signature verification.

### Snapshot fork finding

Two validly signed snapshots can still represent different points in authority history. Therefore VALID_SIGNATURE != CURRENT_STATE. A snapshot restored after a later revocation/rotation must be treated as historical evidence until its generation and dependency closure are reconciled with the current authoritative history.

### Key-wrapping dependency graph

For envelope encryption, the protected secret and its wrapping key form a dependency edge:

WRAPPING_KEY → PROTECTS → SECRET_MATERIAL

A rotation or revocation cannot be modeled as a single-key event when multiple ciphertext generations remain. Each durable artifact needs binding to its encryption-key generation and intended usage. Old wrapping keys may need controlled retention to recover legitimate historical backups, while a compromised or revoked wrapping key must not silently regain authority merely because an old ciphertext remains decryptable.

### Quarantine conditions

A restored recovery artifact enters QUARANTINED when any of these are unresolved:
- authority generation is older than a known revocation/rotation boundary;
- continuity anchor is missing, forked or inconsistent;
- wrapping-key generation cannot be established;
- artifact provenance is incomplete;
- required dependency versions cannot be reconstructed;
- recovery occurred from an untrusted or stale snapshot;
- current authority cannot independently validate the artifact.

QUARANTINED != DESTROYED: quarantine preserves evidence while preventing authorization.

### New Nexo invariants
- VALID_ARTIFACT != CURRENT_AUTHORITY.
- VALID_SIGNATURE != CURRENT_STATE.
- DECRYPTABLE_BACKUP != RECOVERABLE_AUTHORITY.
- SNAPSHOT_RESTORE != AUTHORITY_RESTORATION.
- REVOCATION_AFTER_SNAPSHOT => NO_SILENT_REPROMOTION.
- WRAP_KEY_GENERATION MUST BE BOUND TO PROTECTED_ARTIFACT_GENERATION.
- UNKNOWN_DEPENDENCY => NO_AUTHORITY_PROMOTION.
- QUARANTINE PRESERVES EVIDENCE WITHOUT GRANTING AUTHORITY.

### Research status

## AB104.466 — adversarial recovery matrix: stale state, forks, compromise and UNKNOWN effects

NIST's current key-management guidance treats backup, recovery, revocation, replacement and destruction as explicit key-management functions, while its recovery guidance emphasizes identifying the correct backup version and establishing confidence in recovered data integrity. This supports testing recovery as an adversarial state-selection problem, not merely a restore operation.

### Recovery attack matrix

| Adversarial condition | Unsafe promotion | Required Nexo disposition |
|---|---|---|
| Backup older than revoked authority generation | Old key regains authority | QUARANTINE; require current authority reconciliation |
| Snapshot fork with two valid histories | Both treated as current | UNKNOWN_ORDER / QUARANTINE until authoritative continuity resolves fork |
| Wrapping key compromised after backup creation | Decryptability treated as trust | QUARANTINE; evaluate every artifact generation affected |
| Partial restore | Missing dependency silently defaulted | HOLD; dependency closure incomplete |
| Missing recovery witness/quorum | Available local share treated as sufficient | UNKNOWN authority; no threshold lowering |
| Restore during EXTERNAL_EFFECT UNKNOWN | Recovery assumes effect was never executed | Freeze duplicate effect admission; reconcile external identity first |
| Restored policy/config older than authority state | Historical policy becomes active | Reject promotion; require current PolicyBaseline |
| Valid signature from obsolete generation | Signature treated as current authorization | Historical evidence only |
| Backup modified but re-signed by a newly recovered root | New root self-validates old state | Reject unless new root itself has independently established authority |
| Rollback after successful rotation | Revoked generation becomes live | Fence old generation and preserve anti-rollback evidence |

### Critical cross-domain result

Recovery of Nexo's authority state cannot be isolated from external-effect history. If an effect was UNKNOWN at crash time, restoring an older state that lacks the effect record could cause a duplicate external action. Therefore recovery must reconcile authority history and external-effect identity/state before releasing new effects.

This strengthens the existing rule:

NEW ATTEMPT != NEW EFFECT

and adds:

RESTORED HISTORY != COMPLETE EFFECT HISTORY.

### Recovery ordering candidate

STOP/QUARANTINE → LOAD ARTIFACT → VERIFY INTEGRITY → CHECK VERSION/GENERATION → RECONCILE REVOCATION → RECONCILE CONTINUITY → RECONCILE EXTERNAL EFFECTS → ESTABLISH CURRENT AUTHORITY → RECOVERY FENCE → EXPLICIT RELEASE

The sequence is a research candidate, not an implementation prescription. Any implementation would require formal refinement and fault-injection evidence.

### New invariants
- STALE_BACKUP => NO_AUTHORITY_PROMOTION.
- FORKED_HISTORY => UNKNOWN_UNTIL_AUTHORITATIVE_RECONCILIATION.
- COMPROMISED_WRAP_KEY => AFFECTED_ARTIFACTS_QUARANTINED.

- RESTORED_HISTORY != COMPLETE_EFFECT_HISTORY.

## AB104.467 — crash consistency: durable intent versus external effect

AWS's transactional-outbox guidance confirms the dual-write failure boundary: a local database commit and external notification are separate systems, so a crash can leave the local state committed while the notification is absent, or vice versa. The outbox pattern atomically stores the local change and intent, then relays it later; consumers must tolerate duplicate delivery and therefore need idempotent processing.

The same source warns that ordering matters for event-sourced recovery and that cross-service transactions require a different coordination pattern such as a saga; the outbox itself does not make an external effect atomic.

Stripe's idempotency documentation gives a concrete production API example: the same idempotency key lets a retry recover a response after a connection failure without creating a second charge. The mechanism depends on the server retaining and correlating the key with the operation state; therefore idempotency is an effect-identity mechanism, not proof that the external world is globally atomic.

### Nexo crash matrix

| Crash boundary | Durable local state | External state | Recovery meaning |
|---|---|---|---|
| Before durable intent | absent | absent/unknown | no admitted effect; normal new admission may be possible |
| After durable intent, before attempt | intent exists | not attempted | retry same EffectID only if authority/fence still valid |
| After external attempt, before local result | intent exists | UNKNOWN | MUST NOT create a new EffectID; reconcile first |
| After provider acknowledgement, before local commit | ack may exist externally | acknowledged/possibly applied | reconcile provider/external identity before retry |
| After local commit, before relay acknowledgement | committed intent/effect record | may be applied | relay/reconcile using same identity |
| External compensation started but outcome unknown | compensation intent exists | UNKNOWN | quarantine affected operation until reconciled |

### Critical distinction

OUTBOX_DURABLE != EXTERNAL_EFFECT_DURABLE

The outbox gives durable local intent. It does not prove that the provider executed the effect, nor that the effect can be rolled back. Likewise:

IDEMPOTENCY_KEY != ATOMICITY

It prevents or detects duplicate processing only when the receiving system actually honors and retains the identity semantics.

### Recovery candidate

For an external effect, the minimum crash-safe evidence chain is:

ADMITTED → INTENT_DURABLE → EFFECT_ID_STABLE → EXTERNAL_ATTEMPTED → PROVIDER_RESPONSE/UNKNOWN → RECONCILED → FINAL_STATE

A crash after EXTERNAL_ATTEMPTED with no trustworthy result must preserve UNKNOWN. Recovery may retry only after proving the retry is safe-equivalent under the provider's semantics, or after an authoritative reconciliation says the previous effect did not occur.

### New Nexo invariants
- OUTBOX_DURABLE != EXTERNAL_EFFECT_CONFIRMED.
- IDEMPOTENCY_KEY != ATOMICITY.
- CRASH_AFTER_ATTEMPT => UNKNOWN_UNTIL_RECONCILED.
- RETRY_MUST_REUSE_EFFECT_ID_WHEN_SEMANTICALLY_SAFE.
- NEW_EFFECT_ID_AFTER_UNKNOWN => DUPLICATE_RISK.
- LOCAL_COMMIT != EXTERNAL_COMMIT.
- RECONCILIATION_REQUIRED_BEFORE_AUTHORITY_RELEASE when an unresolved effect can affect safety or future state.

### Evidence status

AB104.467 confirms that durable intent, idempotency and reconciliation are complementary controls with different claims. This aligns with the existing Nexo external-effect state machine and strengthens the separation between control atomicity, effect atomicity and observation atomicity.

## AB104.468 — concrete outbox/idempotency implementations and failure evidence

Concrete implementations reinforce that the outbox pattern provides a durable handoff from local transactional state to asynchronous delivery, but delivery remains at-least-once unless additional semantics are supplied. AWS explicitly recommends idempotent consumers and preserving notification order; Debezium documents the same failure window and uses a unique event ID for consumer duplicate detection.

A real open-source implementation, tomorrow-one/transactional-outbox, uses an outbox sequence/id plus producer idempotence and explicitly states that database/network failures or process crashes can produce duplicates; consumers remain responsible for deduplication. Its multi-instance relay uses a database lock so another instance can take over after a crash.

A separate integration-test repository demonstrates an important evidence boundary: component tests use real PostgreSQL, Kafka, Debezium and WireMock, inject transient third-party failures, run multiple service instances, and verify duplicate-event handling. This is materially stronger than a unit test of an outbox table, but it still does not prove arbitrary provider-side external-effect semantics.

Debezium's exactly-once work documents a concrete database-connection-break test: continuously written database changes are subjected to connector failure/restart and the test checks that recovery resumes from the correct point without duplicate delivery. It also notes that stronger EOS requires dedicated testing across connectors.

### Evidence boundary for Nexo

| Mechanism | What concrete code/tests can establish | What remains external/UNKNOWN |
|---|---|---|
| Transactional outbox | local state + intent committed together | external provider execution |
| Relay/CDC | committed outbox entries forwarded under tested failure model | provider semantics and unreconciled effects |
| Stable event/effect ID | duplicate correlation/detection | uniqueness/retention guarantees at provider |
| Idempotent consumer | repeated delivery does not repeat the protected local transition | external side effects performed by the consumer |
| Database lock/lease | one active relay under tested lease semantics | Byzantine/crash/clock assumptions beyond test model |
| Integration failure tests | behavior under modeled failures | unmodeled provider/network/hardware failures |
| Exactly-once connector mode | stronger delivery semantics within declared connector boundary | end-to-end exactly-once external effect |

### Nexo consequence

The outbox should be modeled as an intent durability mechanism, not an external-effect commit mechanism. A provider-facing adapter still requires its own contract:

EffectID + ProviderScope + ProviderGeneration + IdempotencyRetention + Query/ReconciliationCapability + Cancellation/CompensationSemantics

If any required provider property is unavailable or unproven, Nexo cannot silently promote an UNKNOWN external outcome to CONFIRMED.

New invariants:
- OUTBOX_EVIDENCE_SCOPE != PROVIDER_EFFECT_EVIDENCE_SCOPE
- INTEGRATION_TEST_SCOPE != DEPLOYMENT_FAILURE_SCOPE
- DELIVERY_EXACTLY_ONCE != EXTERNAL_EFFECT_EXACTLY_ONCE
- PROVIDER_IDEMPOTENCY_UNKNOWN => EFFECT_OUTCOME_UNKNOWN_AFTER_CRASH
- RELAY_FAILOVER != EFFECT_RETRY_AUTHORIZATION

## AB104.469 — provider idempotency windows, expiry and late retry hazards

Concrete provider documentation shows that idempotency is bounded by provider-defined scope and retention, not an eternal property of an EffectID. Stripe states that keys may be removed after at least 24 hours and that reusing a pruned key creates a new request; AWS ECS documents a 24-hour client-token TTL for RunTask; PayPal states that PayPal-Request-Id is retained for up to 45 days. Therefore the same logical EffectID can cease to be recognized by the provider after its retention window.

AWS also documents that retries with the same token and different parameters can fail with an idempotent-parameter mismatch, while regional/zonal scope can change whether the same token denotes the same operation. This means Nexo must bind effect identity to provider scope and exact request parameters, not treat a bare token as globally unique semantics.

### Late-retry matrix

| Condition | Naive retry | Nexo disposition |
|---|---|---|
| Provider idempotency window still valid | Reuse same key | Potentially retry, subject to authority/fence and provider semantics |
| Window expired, original outcome UNKNOWN | Reuse key assuming duplicate suppression | UNSAFE: provider may treat it as a new operation |
| Key reused after provider pruning | Same EffectID assumed same effect | Treat provider-side identity as UNKNOWN; reconcile first |
| Same key + changed parameters | Assume update of original operation | Reject/mismatch; never silently mutate effect identity |
| Same key across provider scopes | Assume global deduplication | Scope-bound identity; separate effects may legally occur |
| Provider response lost but resource query available | Blind retry | Query/reconcile by stable external identity first |
| Provider response lost and no reconciliation API | Blind retry | UNKNOWN; do not create a new effect identity for safety-sensitive action |
| Provider retention policy changed | Existing retry assumptions remain | Revalidate capability/evidence contract |

### Key result

EFFECT_ID_STABLE is necessary but not sufficient. Nexo needs a provider-specific predicate:

IDEMPOTENCY_VALID(EFFECT_ID, PROVIDER_SCOPE, REQUEST_FINGERPRINT, CURRENT_TIME/GENERATION)

When this predicate is false or unprovable, the old EffectID is no longer enough to make a retry safe. A provider query/reconciliation mechanism, a durable provider-side resource identity, or another independently authoritative mechanism is required.

This yields a stronger rule:

EXPIRED_IDEMPOTENCY_WINDOW + UNKNOWN_OUTCOME => NO_AUTOMATIC_RETRY

and:

PROVIDER_IDENTITY_SCOPE != NEXO_EFFECT_IDENTITY_SCOPE.

### Time semantics

Provider TTL introduces a new dependency on time. If Nexo relies on an expiration window, it must know which clock and policy define that expiration and must not assume local wall-clock time is authoritative. Where expiration status cannot be established, preserve UNKNOWN rather than guessing that the key is still valid.

### New invariants
- IDEMPOTENCY_IS_PROVIDER_SCOPED.
- IDEMPOTENCY_RETENTION_IS_PART_OF_EFFECT_CONTRACT.
- EXPIRED_WINDOW + UNKNOWN => NO_AUTOMATIC_RETRY.
- REQUEST_FINGERPRINT_CHANGE => NEW_OPERATION_OR_REJECTION.
- PROVIDER_SCOPE_CHANGE => DISTINCT_IDEMPOTENCY_DOMAIN.
- UNPROVEN_IDEMPOTENCY_VALIDITY => UNKNOWN.
- TIME_BASE_FOR_EXPIRY MUST BE EXPLICIT.

Evidence status: provider-specific semantics are now established from current AWS, Stripe and PayPal documentation; Nexo still has no provider selected and no implementation.

## AB104.470 — reconciliation by resource lookup and query/retry races

Provider lookup can reduce uncertainty after a lost response, but it does not automatically make a retry safe. AWS's asynchronous communication guidance describes a claim-check pattern in which a durable identifier is returned and the client later queries status; it also requires the validity period of that identifier to be explicit. AWS's outbox guidance separately warns that duplicate delivery is expected and consumers must be idempotent.

Stripe documents a stronger provider-side case: the idempotency key stores the first result and subsequent identical requests return that result, while a reused key after pruning can create a new request. This means lookup and idempotency are distinct mechanisms and must not be conflated.

### Query-after-timeout race matrix

| Sequence | Lookup result | Retry risk | Nexo disposition |
|---|---|---|---|
| Timeout → lookup finds exact provider resource bound to EffectID | FOUND | Duplicate retry unnecessary | CONFIRM/RECONCILE if evidence is authoritative enough |
| Timeout → lookup says NOT_FOUND while provider processing is still possible | NOT_FOUND | Immediate retry can race with delayed creation | UNKNOWN; wait/reconcile if provider semantics allow |
| Timeout → lookup stale/replica-lagged | NOT_FOUND or old state | Retry can duplicate | UNKNOWN until sufficiently fresh observation |
| Timeout → lookup finds resource but fields differ | CONFLICT | May indicate partial/incorrect execution | QUARANTINE + reconciliation |
| Timeout → lookup API unavailable | NO_OBSERVATION | Retry may duplicate | UNKNOWN; no new EffectID for safety-sensitive effect |
| Lookup succeeds → effect changes concurrently | STALE_FOUND | False confirmation or unsafe compensation | Require generation/version/ETag or equivalent concurrency evidence |
| Lookup finds resource after idempotency TTL expired | FOUND | Provider key may no longer suppress retries | Bind confirmation to resource identity; do not rely on key alone |
| Lookup and retry run concurrently | race | Two effects can be created | Serialize through control fence or provider-supported conditional operation |

### Critical result

A provider resource identifier is useful evidence only if Nexo can establish its binding to the intended EffectID and determine the freshness/concurrency semantics of the lookup. A negative lookup is not necessarily proof of absence when propagation, indexing, or eventual consistency can delay visibility.

Therefore:

QUERY_NOT_FOUND != EFFECT_NOT_EXECUTED

and:

QUERY_FOUND != EFFECT_AUTHORIZED

A positive lookup can establish external state without proving that Nexo was authorized to create it. Conversely, a valid local authorization does not prove the provider created the intended resource.

### Candidate reconciliation contract

EffectID → ProviderOperationID/ResourceID → ProviderScope → RequestFingerprint → ProviderGeneration/Version → ObservationTime/Source → CurrentProviderState

The observation must carry provenance and freshness. If the provider supports conditional reads (for example, an ETag/version/generation) that evidence should be captured so a subsequent action cannot silently act on stale state.

### New invariants
- QUERY_NOT_FOUND != ABSENCE.
- QUERY_FOUND != AUTHORIZATION.
- STALE_OBSERVATION != CURRENT_STATE.
- RESOURCE_ID_BINDING_MISSING => UNKNOWN.
- LOOKUP_DURING_RETRY_RACE => SERIALIZE_OR_PRESERVE_UNKNOWN.
- IDEMPOTENCY_EXPIRED + RESOURCE_ID_CONFIRMED => RECONCILE_BY_RESOURCE_ID.
- NEGATIVE_OBSERVATION_REQUIRES_PROVIDER_FRESHNESS_SEMANTICS.
- OBSERVATION_PROVENANCE + FRESHNESS ARE PART OF RECONCILIATION_EVIDENCE.

Evidence status: provider lookup/reconciliation semantics researched; no assumption that a lookup endpoint is linearizable or authoritative unless the provider contract proves it.
