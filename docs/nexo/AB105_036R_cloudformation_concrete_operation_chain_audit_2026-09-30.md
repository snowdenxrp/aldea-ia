# AB105.036R — Concrete CloudFormation operation chain: API request → StackEvent → resource state
Date: 2026-09-30
Status: RESEARCH/AUDIT ONLY — no implementation, no semantic freeze.

## Research question

Using CloudFormation as a concrete provider case, how far can the chain be reconstructed from an API request through CloudFormation operation events and resource state without converting correlation into universal causality?

## Primary evidence

AWS CloudFormation documents that all StackEvents triggered by a given stack operation receive the same ClientRequestToken, which can be used to track that operation. StackEvent also exposes OperationId when present, EventId, StackId, LogicalResourceId, PhysicalResourceId, ResourceProperties, ResourceStatus and Timestamp. citeturn0search0turn0search2

AWS CloudTrail's CloudFormation documentation shows API events such as CreateStack and UpdateStack containing requestID and eventID, with the response including the stackId. citeturn0search6

AWS's concrete StackEvent examples show one ClientRequestToken shared across the events generated during a stack operation, while individual StackEvents have distinct EventIds and can transition a resource from CREATE_IN_PROGRESS to CREATE_COMPLETE. PhysicalResourceId is populated for the created resource in the later events. citeturn0search5

AWS documents that requestID identifies the service request and eventID uniquely identifies the CloudTrail event record. citeturn0search1

## Findings

### F1 — CloudFormation provides a stronger provider-native operation boundary

For a stack operation, ClientRequestToken is explicitly documented as shared by all StackEvents generated by that operation. This creates a provider-native operation grouping stronger than timestamp proximity. citeturn0search0

Therefore:

ClientRequestToken match across StackEvents
-> SAME_CLOUDFORMATION_STACK_OPERATION

This is a bounded provider claim, not a universal operation-ID theorem.

### F2 — CloudTrail requestID and eventID remain separate from ClientRequestToken

The initiating CloudTrail API record has requestID/eventID, while the resulting StackEvents use ClientRequestToken/EventId/OperationId.

AWS does not establish in the cited contract that CloudTrail requestID is universally equal to CloudFormation ClientRequestToken.

Therefore the bridge must be represented as:

CloudTrail API event
-> operation invocation
-> CloudFormation ClientRequestToken / OperationId
-> StackEvents

not as:

requestID == ClientRequestToken

unless a concrete provider record explicitly proves such equality.

### F3 — StackEvent EventId identifies an event, not the whole operation

Every StackEvent can have its own EventId while sharing one ClientRequestToken. citeturn0search0turn0search5

Therefore:

multiple StackEvent EventIds + one ClientRequestToken
-> multiple provider events within one bounded stack operation

This is positive operation grouping evidence, not evidence of multiple independent operations.

### F4 — OperationId can strengthen the operation boundary when present

StackEvent exposes OperationId as the unique identifier of the operation that generated the event. citeturn0search0

When present and consistently bound across the relevant events, OperationId provides another provider-native operation key.

But it is optional. Missing OperationId cannot become negative evidence that no operation occurred.

### F5 — Resource state is downstream evidence

A StackEvent can bind LogicalResourceId and, when available, PhysicalResourceId to a status transition and resource properties. citeturn0search0turn0search5

Thus:

operation grouping
+
resource identity
+
status transition
-> strong bounded provider evidence that the resource participated in that CloudFormation operation.

However, this still does not prove that CloudFormation was the only actor capable of changing the underlying resource after or outside the operation.

### F6 — PhysicalResourceId strengthens incarnation binding but remains provider-specific

A concrete StackEvent can show a PhysicalResourceId for the resource participating in the operation. citeturn0search5

This is stronger than a reusable logical name for incarnation binding, but the claim remains bounded to CloudFormation's resource semantics. It must not be generalized into an AWS-wide non-reuse theorem.

### F7 — ResourceProperties bind intended/recorded configuration, not independent historical truth

StackEvent can expose ResourceProperties used for the resource. citeturn0search0turn0search5

Therefore they strengthen the state-transition description, but do not independently prove:
- the underlying service accepted every property as intended;
- no external mutation occurred afterward;
- no earlier state existed outside retained events;
- no event was omitted from the retained history.

## Concrete evidence chain

For a covered CloudFormation operation:

1. CloudTrail CreateStack/UpdateStack event exists.
2. CloudTrail event has requestID/eventID and returns stackId.
3. CloudFormation operation has ClientRequestToken and, when present, OperationId.
4. StackEvents sharing the ClientRequestToken identify the operation's event set.
5. StackEvent binds LogicalResourceId and possibly PhysicalResourceId.
6. ResourceStatus/ResourceProperties describe the provider-observed state transition.
7. Separate AWS Config evidence can then be used as another observation layer rather than being treated as the same event ledger.

The strongest justified statement is:

CLOUDFORMATION_OPERATION_RESOURCE_TRANSITION_EVIDENCED

when the chain is intact.

It is not automatically:

REAL_WORLD_CAUSALITY_COMPLETE.

## Three-valued causal result

### BOUNDED_PROVIDER_CAUSALITY

Allowed when:
- initiating API evidence is present;
- CloudFormation operation identity is bound;
- StackEvents are linked by documented ClientRequestToken and/or OperationId;
- target resource identity is bound;
- state transition is documented by StackEvent;
- temporal and retention coverage are sufficient for the claim.

### CORRELATION_ONLY

Used when event/resource identifiers align but the provider operation boundary or state transition cannot be closed.

### UNKNOWN

Required when key events, operation identifiers, retention coverage, or resource identity are missing or ambiguous.

## Important boundary

This concrete case demonstrates that a provider can expose a much stronger causal chain than generic CloudTrail timestamps.

But it also demonstrates why the architecture must preserve provider-specific contracts:

CloudFormation ClientRequestToken semantics cannot be promoted into a universal AWS operation contract.

## Anti-collapse rules

- CloudTrail requestID != CloudFormation ClientRequestToken unless explicitly proven for the instance.
- CloudTrail eventID != StackEvent EventId.
- StackEvent EventId != operation identity.
- ClientRequestToken != universal AWS operation ID.
- OperationId missing != no operation.
- PhysicalResourceId != universal non-reusable incarnation theorem.
- ResourceProperties != independent proof of actual final state.
- StackEvent status transition != complete external-world history.
- CloudFormation operation evidence != all possible resource mutations.
- Provider-native causal binding != universal causality.
