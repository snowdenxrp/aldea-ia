# AB105.059R — CloudFormation correlation matrix

Date: 2026-09-30
Chain: AB105.058R -> AB105.059R

## Research question

Which joins among RequestId, ClientRequestToken, ChangeSet ARN, OperationId, StackId, LogicalResourceId, and PhysicalResourceId are exact, bounded, or UNKNOWN?

## Evidence

CloudFormation `DescribeEvents` makes `OperationId` the explicit unique identifier for an operation and can query by `OperationId`, `ChangeSetName`, or `StackName`. Its OperationEvent includes StackId, OperationId, ClientRequestToken, LogicalResourceId, PhysicalResourceId, and event metadata. citeturn0search0turn0search2

CloudFormation StackEvent likewise exposes StackId, OperationId, ClientRequestToken, LogicalResourceId, and PhysicalResourceId. AWS states that events generated by a given stack operation receive the same ClientRequestToken. citeturn0search1

CloudTrail records the API request, including requestID/eventID, request parameters, response elements, caller identity, source IP, user agent, and time. Its requestID is the CloudTrail/API request identifier, not the CloudFormation resource-operation identifier. citeturn0search6

## Correlation matrix

| Pair / join | Classification | Rule |
|---|---|---|
| StackId + OperationId | EXACT within CloudFormation operation context | OperationId identifies the operation on the specified stack. |
| OperationId + StackEvent.OperationId | EXACT | Same provider operation identifier. |
| ClientRequestToken + StackEvent.ClientRequestToken | BOUNDED operation grouping | AWS assigns the same token to events from the operation that generated them. |
| OperationId + ClientRequestToken | BOUNDED | Strong operation record when both appear consistently; token alone is not the universal operation identity. |
| LogicalResourceId + OperationId | BOUNDED resource-in-operation identity | Prevents collapsing same logical resource across different operations. |
| PhysicalResourceId + OperationId | BOUNDED incarnation-in-operation identity | Stronger than logical ID alone; still does not prove external-world persistence. |
| LogicalResourceId + PhysicalResourceId | BOUNDED incarnation identity | Must remain operation-scoped to avoid historical ambiguity. |
| ChangeSet ARN + ResourceChange | EXACT plan association | ResourceChange belongs to the queried ChangeSet. |
| ChangeSet ARN + OperationId | BOUNDED execution association | DescribeEvents can query by ChangeSetName, but queryability is not by itself proof that every planned ResourceChange executed. |
| CloudTrail requestID + CloudFormation OperationId | UNKNOWN unless independently correlated | AWS documentation does not establish requestID = OperationId. Never equate them. |
| CloudTrail eventID + OperationId | UNKNOWN unless independently correlated | EventID identifies the CloudTrail event, not the CloudFormation operation. |
| CloudTrail requestID + ClientRequestToken | UNKNOWN unless the token is explicitly present in the relevant request and matches | Do not infer equality from temporal proximity. |
| CloudTrail eventTime + CloudFormation Timestamp | BOUNDED temporal relation only | Different ledgers; timestamps do not create causal identity. |
| ChangeSet ARN + CloudTrail ExecuteChangeSet request | BOUNDED request/plan relation | Shows the API request targeted that change set; does not prove resource outcome. |
| PhysicalResourceId + CloudTrail requestID | UNKNOWN by default | Requires an explicit independent bridge. |

## Key conclusions

### 1. OperationId is the primary CloudFormation operation key

When present, OperationId should be the canonical operation identifier in the reconstruction model. StackId scopes it to the stack.

### 2. ClientRequestToken is correlation evidence, not a substitute for OperationId

It is useful for grouping events from an operation, but it must not be promoted into a universal operation identity.

### 3. ChangeSet ARN is a plan/execution bridge

A ChangeSet ARN identifies the change set targeted by the request and can be used to retrieve associated operation events. It does not convert ResourceChange plan semantics into proof that each resource change executed.

### 4. PhysicalResourceId is the incarnation bridge

LogicalResourceId identifies the template-level resource; PhysicalResourceId identifies the physical instance. Both must be scoped by operation when reconstructing replacement history.

### 5. CloudTrail requestID/eventID must remain separate identifiers

CloudTrail proves the API request and its caller/context. It must not be silently mapped to CloudFormation OperationId.

## Distilled join rules

`StackId + OperationId -> EXACT_OPERATION_SCOPE`

`OperationId + event.OperationId -> EXACT_OPERATION_MEMBERSHIP`

`CloudTrail requestID/eventID == OperationId -> FORBIDDEN_UNLESS_EXPLICITLY_PROVEN`

`timestamp proximity -> NO_IDENTITY`

## Anti-collapse rules

- RequestId != OperationId.
- CloudTrail eventID != OperationId.
- ChangeSet ARN != OperationId.
- ClientRequestToken != PhysicalResourceId.
- LogicalResourceId != PhysicalResourceId.
- LogicalResourceId alone != incarnation identity.
- PhysicalResourceId alone != operation identity.
- Same timestamp != same operation.
- ExecuteChangeSet request != successful replacement.
- ChangeSet ResourceChange != executed resource transition.
- CloudTrail API evidence != CloudFormation resource outcome.
- Matching names/ARN fragments != identity proof.
