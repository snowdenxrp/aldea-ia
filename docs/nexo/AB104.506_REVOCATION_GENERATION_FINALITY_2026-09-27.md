# AB104.506 — revocation generation and finality contract

## Evidence
RFC 7009 states that a successful revocation invalidates the token immediately, while acknowledging propagation delay between servers; it therefore requires minimizing that window and warns clients not to continue using the token after successful revocation. citeturn0search0turn0search2 RFC 7662 requires an authorization server performing introspection to check the token's current state, including whether it has been revoked. citeturn0search5 RFC 9700 also treats refresh-token revocation as a security response and supports revoking related credentials after security events. citeturn0search8

## Nexo contract
A protected effect must bind authorization to a monotonic revocation generation:

`Authorization = {ClaimDigest, AuthorityEpoch, RevocationGeneration, DependencyClosureDigest, FenceRevision, DecisionDigest}`

A revocation event advances the relevant generation:

`G_new > G_authorized`

An effect may proceed only if the final effect gate observes a state whose revocation generation is at least the generation bound by the authorization decision and whose claim remains active.

For security-critical claims, a cached authorization result is therefore not sufficient by itself.

## Concurrent authorization/revocation
Adversarial schedule:
`A reads G=7 -> R commits G=8 -> A attempts effect`.

The final gate must detect `G=8 > G_auth=7` and deny/recompute. Otherwise the system has a time-of-check/time-of-use revocation race.

Reverse schedule:
`R prepares -> A commits effect -> R commits G=8`.

Whether the effect is allowed depends on the declared linearization point. The contract must state whether authorization protects only effects committed before revocation finality or whether revocation can invalidate already-committed effects. Nexo must not leave this implicit.

## Finality boundary
Candidate protected-effect rule:
`ALLOW_EFFECT iff current_authority_valid AND current_revocation_generation ==/compatible_with authorized_generation AND fence_current AND dependency_snapshot_valid`.

If current state cannot be established, the safe outcome for protected effects is `UNKNOWN/QUARANTINE`, not an assumption that no revocation occurred.

## Retry and idempotency
A retry after timeout must not create a second semantic authorization. Bind the effect to `operation_id + DecisionDigest + RevocationGeneration`. A repeated operation either observes the already committed result or re-enters the final authorization gate; it must not bypass revocation checking.

## Crash recovery
Persist the authorization generation and effect state before declaring a protected effect committed. On recovery, a previously prepared but uncommitted effect must be revalidated against the current revocation generation. A committed effect must not be resurrected as a new authorization merely because its acknowledgement was lost.

## Network partition
Propagation delay means different nodes can temporarily disagree about revocation state. RFC 7009 explicitly acknowledges this class of delay. citeturn0search0 Therefore Nexo must distinguish:
`REVOCATION_KNOWN_ACTIVE`
`REVOCATION_NOT_OBSERVED`
`REVOCATION_STATE_UNKNOWN`.

`NOT_OBSERVED != NOT_REVOKED` for claims whose safety requires current revocation knowledge.

## Alternate execution paths
Every path capable of producing the protected effect must cross the same finality/revocation gate. A secondary executor, offline queue, recovery worker, or retry handler cannot treat an older authorization as sufficient.

## Invariants
- `REVOCATION_GENERATION_MONOTONIC`
- `STALE_AUTHORIZATION => NO_PROTECTED_EFFECT`
- `NOT_OBSERVED_REVOCATION != PROVEN_NOT_REVOKED`
- `UNKNOWN_REVOCATION_STATE => QUARANTINE_OR_RECOMPUTE`
- `RETRY != NEW_AUTHORITY`
- `CRASH_RECOVERY != AUTHORITY_RESURRECTION`
- `ALL_EFFECT_PATHS => SAME_FINAL_REVOCATION_GATE`
- `LINEARIZATION_POINT_MUST_BE_EXPLICIT`
- `REVOCATION_FINALITY != EVENTUAL_PROPAGATION`
