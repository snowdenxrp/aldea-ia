# Nexo AB104.447 — Threshold Signatures, Multi-Party Approval and Byzantine Root Governance

## Research question

Can threshold cryptography safely implement Nexo's root governance, and what additional controls are required so cryptographic quorum is not mistaken for independent authority?

## External evidence

NIST describes threshold cryptography as distributing trust for cryptographic operations across parties and explicitly identifies integrity and availability benefits. It also distinguishes system models, thresholds, setup/maintenance and implementation validation as security considerations. citeturn0search1turn0search3

NIST's 2026 threshold call requires technical specifications, reference implementations and experimental evaluation, reinforcing that a threshold construction's cryptographic definition is not by itself evidence of implementation correctness. citeturn0search0turn0search2

NIST's threshold research also discusses Byzantine consensus and shows that required thresholds depend on the failure model and timing assumptions; e.g. classical Byzantine settings can require n >= 3f+1 under the cited assumptions. This is evidence against treating a generic “2-of-3” or “3-of-5” number as universally safe. citeturn0search48

## Core finding

A threshold signature can prove:

“a sufficient number of authorized signing shares participated.”

It does NOT automatically prove:

- the participants are independent;
- they are uncompromised;
- their failure domains are independent;
- the policy used by them is current;
- the proposal being signed was semantically correct;
- the signer set was current;
- the recovery process was non-circular.

Therefore:

THRESHOLD_SIGNATURE != INDEPENDENT_AUTHORITY_PROOF.

## Attack T1 — correlated threshold parties

Five signers run in the same compromised cloud account.

3-of-5 signature succeeds.

Security property requiring independent domains is not established.

Invariant:
SIGNER_COUNT != FAILURE_DOMAIN_COUNT.

## Attack T2 — cloned signer identity

An attacker clones one signer environment and obtains multiple signing shares or credentials.

Cryptographic count can remain high while effective independent control is low.

Candidate:
UNIQUE_CREDENTIALS != UNIQUE_TRUST_DOMAINS.

## Attack T3 — threshold policy rollback

Current policy is 4-of-7.
Old policy says 2-of-3.
An attacker restores old policy and obtains a valid old-policy signature.

Candidate:
VALID_SIGNATURE_UNDER_OLD_POLICY => STALE_AUTHORIZATION.

## Attack T4 — signer-set rollback

Current root set S8 is replaced by signed historical S5.

A signature over S5 can be cryptographically valid but not current.

Candidate:
VALID_SIGNATURE != CURRENT_GOVERNANCE_STATE.

## Attack T5 — semantic equivocation

Threshold participants sign different semantic objects that serialize differently but are interpreted as the same governance action by different components.

Therefore signed bytes need canonical semantics and context binding.

Candidate signed governance object must include:
ACTION_ID
TARGET
CURRENT_ROOT_SET_VERSION
POLICY_GENERATION
TRUST_GENERATION
RECOVERY_GENERATION
CLAIM_SCOPE
EFFECT_SCOPE
EXPIRY/VALIDITY
DEPENDENCY_ROOT.

## Attack T6 — signer approval of stale proposal

Proposal P was evaluated against root set R7.
Root set becomes R8.
Signers sign P without revalidating R8.

Protected final gate must reject stale governance context.

## Attack T7 — threshold signers are all downstream of one authority

Seven organizationally distinct signer accounts depend on one identity provider or one recovery administrator.

The apparent quorum collapses to one dependency.

Candidate:
INDEPENDENCE_REQUIRES_DEPENDENCY_CLOSURE_ANALYSIS.

## Attack T8 — Byzantine minority

Some signers intentionally sign conflicting governance proposals.

A valid threshold signature does not tell Z1 whether the semantic proposal is safe; it only satisfies the configured signing predicate.

Conflict detection must be explicit.

## Attack T9 — quorum intersection mistaken for truth

Two quorums may overlap yet authorize conflicting state transitions if the protocol lacks a monotonic state machine and fencing.

Therefore:
QUORUM_INTERSECTION != SEMANTIC_CONSISTENCY.

## Attack T10 — signer replacement race

Signer S2 is revoked and replaced.
An in-flight signature still includes S2.

Need generation-bound signer membership:
ROOT_SET_VERSION + MEMBER_INCARNATION.

## Attack T11 — threshold increase as denial-of-service

If a governance transition raises threshold beyond currently available signers, availability can collapse.

Safety and liveness must be modeled separately.

A safer threshold cannot automatically be assumed operationally acceptable.

## Attack T12 — threshold decrease as fail-open

The opposite change can create a safety violation.

Thus:
THRESHOLD_CHANGE is a protected transition with its own authorization and effective generation.

## Threshold vs multi-party approval

Threshold signature:
- compresses multiple approvals into one cryptographic artifact;
- can reduce coordination overhead;
- protects the underlying secret from a single share holder.

Explicit multi-party approval:
- can preserve individual identities and reasons;
- can support richer evidence and dissent;
- may expose more metadata and require stronger audit handling.

Neither construction automatically establishes independence.

Candidate architecture:
MULTI_PARTY_GOVERNANCE_RECORDS
→ independent appraisal
→ threshold/explicit approval
→ Z1 final gate.

Threshold cryptography is a mechanism, not the governance model.

## Byzantine root governance

For each governance generation G:

ROOT_SET(G) =
{member identity, incarnation, scope, failure domain, dependency closure, status}.

A governance transition is admissible only if:

- G is current;
- proposal context is bound to G;
- threshold policy is current;
- required members are current;
- failure-domain constraints are satisfied;
- dependency closure has no forbidden common-mode dependency;
- no unresolved governance conflict exists;
- recovery state permits the transition.

## Byzantine conflict rule

If independent authorized groups produce conflicting governance states for the same generation:

SAME_GOVERNANCE_GENERATION
+
CONFLICTING_STATE
=>
GOVERNANCE_EQUIVOCATION
=>
FREEZE_HIGH_CONSEQUENCE_TRANSITIONS.

Do not choose a winner from signature count alone.

Resolution requires an authority/evidence path outside the conflicting decision set.

## Threshold safety classes

Candidate Nexo policy should distinguish:

T0 — cryptographic validity only.
T1 — membership/currentness validated.
T2 — dependency/failure-domain independence validated.
T3 — semantic proposal validated.
T4 — protected Z1 transition admitted.
T5 — resulting external effect separately evidenced.

A T0 signature must never be silently promoted to T4.

## Emergency governance

If normal threshold is unavailable:

Do not simply reduce t.

Instead create a separate emergency governance transition with:
- distinct recovery authority;
- explicit scope;
- restricted effect classes;
- bounded lifetime;
- independent evidence;
- full audit;
- post-recovery reconciliation.

If no independent authority exists, high-consequence decisions remain UNKNOWN/HOLD.
