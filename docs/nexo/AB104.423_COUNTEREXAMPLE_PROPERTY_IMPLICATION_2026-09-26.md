# Nexo AB104.423 — Counterexample Generation and Property Implication

Status: RESEARCH / DESIGN ONLY
Continuity: AB104.422 → AB104.423

## Research question

How can Nexo systematically search for models that satisfy the quorum/failure-domain specification while violating the intended protected property, and distinguish a real semantic counterexample from an abstraction artifact?

## Evidence

NIST documents model checking as a method that can generate counterexample traces when a formal property is not satisfied, and describes combining model checking with specification mutation to automatically generate discriminating tests. citeturn0search0turn0search3

NASA's formal-methods material describes model checking as checking a model against a property and producing a counterexample when the property fails; it also notes the need to validate whether an abstract counterexample corresponds to concrete behavior in counterexample-guided refinement. citeturn0search24turn0search29

NASA requirements guidance emphasizes that requirements should be clear, complete, assumption-explicit, and verifiable; its verification matrix ties each requirement to a defined verification approach. citeturn0search1turn0search2

## Core finding

The critical question is not merely:

“Does the quorum specification satisfy itself?”

It is:

“Does every model admitted by the quorum specification also satisfy the intended protected property?”

Candidate implication:

SPECIFICATION => PROPERTY

must be established within an explicitly defined model and assumption scope.

If there exists:

MODEL ∈ SPECIFICATION
AND
MODEL ∉ PROPERTY

then the specification is insufficient for that property.

## Counterexample classes

### CE1 — direct semantic counterexample

The model satisfies all quorum rules but violates the protected property.

Result:

SPECIFICATION_INSUFFICIENT.

### CE2 — hidden dependency counterexample

Two witnesses appear independent in the declared graph but share an omitted dependency.

Result:

DECLARED_INDEPENDENCE != ACTUAL_INDEPENDENCE.

### CE3 — boundary counterexample

All witnesses agree, but the external resource has a different state.

Result:

WITNESS_AGREEMENT != EXTERNAL_STATE_CONFIRMATION.

### CE4 — recovery counterexample

Normal-state model satisfies the property, but restore/failover permits stale authority.

Result:

NORMAL_PROOF != RECOVERY_PROOF.

### CE5 — partition counterexample

The quorum rule accepts a state while the current authoritative state is unreachable or disputed.

Result:

QUORUM_ACCEPTANCE != CURRENT_AUTHORITY.

### CE6 — Byzantine counterexample

Multiple witnesses produce authentic but incompatible observations.

Result:

SIGNATURE_COUNT != STATE_CORRECTNESS.

### CE7 — unknown-state counterexample

An unavailable dependency is interpreted as safe/default.

Result:

UNKNOWN_COLLAPSED_INTO_SAFE.

### CE8 — temporal counterexample

A quorum is valid at t0 but invalidated at t1 before protected admission.

Result:

HISTORICAL_VALIDITY != CURRENT_VALIDITY.

## Three logically different outcomes

### PROVED_WITHIN_SCOPE

No counterexample exists within the modeled state space and assumptions, or a formal proof establishes implication.

This does not prove the real-world property outside that scope.

### COUNTEREXAMPLE_FOUND

A model satisfying the specification violates the protected property.

This directly falsifies the claimed implication.

### INCONCLUSIVE

Search exhausted its resources, abstraction was insufficient, or the model class was not fully covered.

Inconclusive must not be converted into proof.

## Bounded exhaustive model checking

For small models, enumerate:

- witness count;
- dependency topology;
- failure domains;
- quorum threshold;
- witness states;
- trust generations;
- partition states;
- revocation states;
- recovery states;
- unknown states.

Check:

SPECIFICATION(model) => PROPERTY(model)

for every generated model.

A single violating model is sufficient to produce a semantic counterexample.

## Symbolic/model-checking approach

For larger bounded state spaces, encode:

STATE
+ TRANSITIONS
+ ENVIRONMENT ASSUMPTIONS
+ SPECIFICATION
+ NEGATION(PROPERTY)

Then search for a reachable state satisfying:

SPECIFICATION ∧ ¬PROPERTY.

If found, the trace is a candidate counterexample.

NIST's model-checking work explicitly uses counterexample traces to expose specification/property violations. citeturn0search0turn0search25

## Counterexample validation

An abstract counterexample may be spurious.

Candidate process:

ABSTRACT_COUNTEREXAMPLE
→ CONCRETIZATION
→ CONCRETE_TRACE_CHECK
→ REAL_COUNTEREXAMPLE or SPURIOUS

NASA's counterexample-guided abstraction/refinement material uses this distinction explicitly. citeturn0search29

A spurious counterexample should refine the abstraction rather than be treated as proof of safety or failure.

## Counterexample minimization

A useful counterexample should be reduced to a minimal explanatory model where possible.

Candidate reduction dimensions:

- minimum witnesses;
- minimum dependencies;
- minimum failure domains;
- minimum transitions;
- minimum state changes.

But minimization must preserve the violating property.

Candidate result:

MINIMAL_COUNTEREXAMPLE_CERTIFICATE.

## Counterexample taxonomy

Every counterexample should identify whether the failure is caused by:

- specification omission;
- ambiguous semantics;
- wrong failure model;
- wrong boundary;
- missing dependency;
- quorum rule;
- recovery semantics;
- temporal race;
- unknown handling;
- implementation mismatch;
- abstraction artifact;
- external-world assumption.

This prevents “fixing” a semantic failure by merely changing code.

## Mutation-based implication testing

Generate specification mutants:

M1 remove a required dependency;
M2 lower quorum threshold;
M3 accept stale witness;
M4 collapse UNKNOWN into SAFE;
M5 remove recovery fencing;
M6 remove external-state binding;
M7 ignore trust-generation changes;
M8 allow conflicting roots;
M9 remove continuity predecessor;
M10 allow failover without revalidation.

For each mutant:

SEARCH(MUTANT ∧ ¬PROPERTY)

A validation suite should expose safety-relevant mutations.

NIST has demonstrated specification-level mutation plus model checking as an automatic test-generation strategy. citeturn0search0turn0search12

## Vacuity attack

A specification can appear to imply a property because its preconditions are impossible or overly restrictive.

Example:

SPECIFICATION requires a state that can never occur.

Then:

SPECIFICATION => PROPERTY

may be mathematically true but operationally meaningless.

Candidate check:

REALIZABILITY(SPECIFICATION)

must accompany implication checking.

NASA material identifies consistency/realizability analysis as a distinct formal-requirements concern. citeturn0search27

## Overconstraint attack

The opposite problem is a specification that only permits trivially safe states and therefore does not represent the intended operational mission.

Candidate:

REALIZABLE != MISSION_VALID.

Thus implication must be paired with validation of intended operating scope.

## Assumption leakage

A proof may rely on an environmental assumption that is stronger than the actual deployment.

Candidate record must separate:

MODEL_ASSUMPTION
from
DEPLOYMENT_GUARANTEE.

If the deployment cannot guarantee the assumption:

PROOF_SCOPE_MISMATCH.

## Counterexample from omitted participant

Suppose specification models:

R1 + R2

but real operation can trigger:

R1 → R2 → R3.

If R3 is protected and omitted:

SPECIFICATION may prove safety of an incomplete model.

Therefore:

UNMODELED_PROTECTED_PARTICIPANT => PROPERTY_PROOF_INCOMPLETE.

This carries AB104.405–AB104.407 footprint closure forward.

## Temporal implication

Static implication is insufficient for dynamic authority.

Candidate temporal form:

For every reachable state/time t:

SPECIFICATION(t) => PROPERTY(t)

and for every protected transition:

ADMISSION(t) => REQUIRED_CONTEXT_CURRENT(t)

The model must include relevant invalidation transitions.

## Recovery implication

Separate property:

NORMAL_SPECIFICATION => NORMAL_PROPERTY

from:

RECOVERY_SPECIFICATION => RECOVERY_PROPERTY.

A normal-mode proof cannot automatically cover restore/failover.

## Differential counterexample search

Two independently formulated models:

MODEL_A
MODEL_B

should compare:

- reachable states;
- counterexample traces;
- minimal violating structures;
- assumptions.

Agreement is useful evidence.

Disagreement requires semantic reconciliation.

## Z1 boundary

A property implication result is evidence about the specification.

It cannot itself grant authority.

Therefore:

PROPERTY_IMPLICATION_RESULT != AUTHORITY

## New invariants

- SPECIFICATION => PROPERTY MUST BE CLAIM_SCOPED
- SPECIFICATION_SATISFIES_ITSELF != PROPERTY_PROVED
- COUNTEREXAMPLE_FOUND => CLAIMED_IMPLICATION_FALSE_WITHIN_MODEL
- INCONCLUSIVE != PROVED
- SPURIOUS_COUNTEREXAMPLE != REAL_COUNTEREXAMPLE
- ABSTRACT_PROOF_SCOPE != DEPLOYMENT_GUARANTEE
- REALIZABLE != MISSION_VALID
- UNMODELED_PROTECTED_PARTICIPANT => PROPERTY_PROOF_INCOMPLETE
- NORMAL_PROOF != RECOVERY_PROOF
- HISTORICAL_PROPERTY_VALIDITY != CURRENT_ADMISSION_VALIDITY
- UNKNOWN_CANNOT_SILENTLY_BECOME_SAFE
- MUTATION_SURVIVAL => VALIDATION_GAP
- PROPERTY_IMPLICATION_RESULT != AUTHORITY

- Full formal property language is still open.

- Realizability versus mission adequacy needs separate validation.
- Counterexample completeness for arbitrary dynamic systems remains open.
- External-world observability remains an independent boundary.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
