# NEXO AB104.227 — OPERATION REGISTRY ATOMICITY RECEIPT BINDING CRASH RESTORE ATTACKS V1 — 2026-09-26

## Status
Research/study only. No architecture implementation.

## Core result
AB104.227 exposed a further boundary: an operation registry is useful only if its identity check, effect mutation and committed result are ordered atomically enough to prevent two different outcomes from being inferred from one operation identity.

Candidate invariant:
For one target boundary, an accepted operation must create one durable identity binding:
(operation_id, effect_identity, payload_fingerprint, target_incarnation, authority_context, result)
and the target state transition must be atomically related to that binding.

A registry entry written before the effect but without atomic relation to the effect can create:
- false COMMITTED if the registry says done but the effect never happened;
- false NOT_COMMITTED if the registry is absent after the effect happened;
- duplicate execution if the registry is lost/rolled back.

Therefore "operation exists in registry" is not by itself proof of effect completion.

## Attack A — check registry, then effect, then record result
Two workers can both observe absence if the check and insertion are not atomic.
Both may cross the external boundary.
A unique constraint/conditional insert can serialize ownership, but ownership alone still does not prove the effect committed.

## Attack B — registry reservation before effect
Worker creates RESERVED(operation_id), crashes before effect.
A later worker sees RESERVED.
Correct result is not automatically NOT_COMMITTED; it depends on whether the reservation semantics guarantee no external acceptance occurred and whether the reservation itself is authoritative for the effect boundary.
A reservation is an intent/claim, not completion proof.

## Attack C — effect commits, registry write fails
Target mutates resource, then registry persistence fails.
Recovery sees no registry record.
This is UNKNOWN unless target state/receipt independently proves the effect.
Blind retry can duplicate.

## Attack D — registry commits, effect fails
If registry says COMPLETED before the actual effect, recovery can falsely reconstruct success.
Therefore completion record must not outrun the actual effect commit boundary unless it is itself the atomic commit record of that boundary.

## Attack E — effect + registry atomic transaction
If the target owns both resource mutation and operation registry and commits them in one atomic transaction, a strong boundary becomes possible:
- both durable;
- or neither durable.
This resembles transactional conditional writes studied in etcd, where comparisons and writes are applied atomically. This is an external reference, not a Nexo architecture decision. citeturn0search1turn0search3

## Attack F — response lost after atomic commit
Target has both resource mutation and operation record, but response disappears.
Recovery queries operation_id and matching fingerprint.
If target's registry is authoritative and continuity is intact, it can return the prior result without re-executing.
This is reconstruction, not permission to repeat.

## Attack G — same operation_id, different payload
The registry contains operation_id X with fingerprint F1.
Retry presents X/F2.
This is collision/quarantine.
It must not be treated as a new attempt merely because the operation_id matches.

## Attack H — same operation_id after expiry
If the registry expires X and later accepts X as a new operation, identity reuse becomes dangerous.
A stable idempotency identity therefore needs an explicit namespace/incarnation/retention policy.
Expiry itself never proves the old operation did not happen.

AWS durable execution documentation explicitly distinguishes retry semantics and recommends stable idempotency keys for external services; it also describes conditional database writes and deterministic event IDs as ways to tolerate retries. citeturn0search0

## Attack I — restore old registry snapshot
Target once knew X=COMMITTED, then restores a snapshot from before X.
A new request with X may appear unseen.
Without protected continuity/anti-rollback, registry absence is not NOT_COMMITTED.
This directly carries forward AB104.201-202.

## Attack J — restore resource and registry from different snapshots
Resource state says effect happened; registry says it did not.
Neither isolated snapshot is enough.
The combined state must have a common commit/sequence/epoch boundary or be classified inconsistent/UNKNOWN.

## Attack K — cloned target
Two clones have identical registry state and can independently accept requests.
Local uniqueness is insufficient when both can reach the same external resource.
Canonical target identity/incarnation and external authority are required.

## Attack L — receipt generated outside commit boundary
A receipt may be generated by an intermediary before the target commit, or may only prove that a statement was recorded.
Receipt authenticity/inclusion does not automatically prove the underlying effect.
The receipt contract must explicitly state what boundary it attests.

## Attack M — crash between effect commit and receipt emission
Effect is committed; receipt not returned.
This is not NOT_COMMITTED.
If target operation record is authoritative, reconciliation can classify COMMITTED.
If target cannot prove the prior commit, remain UNKNOWN.

## Attack N — crash after receipt but before local checkpoint
Receipt is authoritative evidence.
Recovery should reconstruct the durable local state from it, not execute the effect again.

## Attack O — relay/outbox duplication
A relay can publish externally and crash before recording publication, causing a duplicate publication on restart. Transactional outbox documentation explicitly describes this failure mode and therefore relies on consumers being idempotent. citeturn0search9
This confirms that local "sent" state is not equivalent to external "processed" state.

## Attack P — target rejects duplicate
A duplicate request may be safely mapped to the original operation only if the target's duplicate semantics bind the response to the same operation identity/fingerprint and do not silently create a new operation.
An error message alone is not sufficient evidence without a defined contract.

## New distinction
There are at least four different durable facts:
1. INTENT_RECORDED
2. OPERATION_RESERVED
3. EFFECT_COMMITTED
4. RESULT_RECEIPT_RECORDED

They must not be collapsed into one "operation exists" boolean.

The strongest candidate target boundary is:
CONDITIONAL AUTHORITY/FENCE/VERSION CHECK
→ atomically mutate target + register EFFECT_COMMITTED
→ produce/bind receipt
→ local recovery consumes receipt/evidence.

If receipt delivery is separate from commit, receipt absence cannot mean effect absence.

## Evidence classification
- Atomic target mutation + authoritative operation record committed together -> strongest COMMITTED evidence.
- Reservation only -> INTENDED/RESERVED, not COMMITTED.
- Missing registry after possible target mutation -> UNKNOWN.
- Registry says committed but target state is incompatible -> INCONSISTENT/QUARANTINE until authoritative target evidence resolves it.
- Registry restored older than target -> UNKNOWN/continuity failure.
- Same identity + different fingerprint -> COLLISION.
- Expired identity -> new-use eligibility only if explicit target semantics permit it; expiration never erases historical uncertainty.

## DO-NOT-REPEAT
- registry presence != effect completion
- reservation != effect commit
- receipt existence != target truth without receipt semantics
- registry absence != NOT_COMMITTED
- expiry != historical erasure
- local lock != distributed fencing
- local prepared intent != external acceptance
- same operation_id + different fingerprint != retry
- no V21
- no architecture implementation
- no unsupported formal/CI/fault-injection claims
