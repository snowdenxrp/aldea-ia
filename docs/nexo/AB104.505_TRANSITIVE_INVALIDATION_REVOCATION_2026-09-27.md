# AB104.505 — transitive invalidation, revocation races and bounded liveness

## Evidence
A recent IETF draft on finality-bound revocation identifies the exact security gap relevant to Nexo: a permit can be valid when issued yet become revoked before the protected effect, and cached/stale authorization must not survive the final consequence boundary. It recommends making current authoritative revocation state part of the final authorization predicate immediately before commit and treating crash recovery and alternate effectuation paths as part of the threat model. citeturn0search4turn0search7 Dependency-aware invalidation systems provide a concrete implementation pattern: invalidating a source can traverse reverse dependencies transitively, while bounded traversal is an explicit trade-off rather than proof that all dependents were found. citeturn0search0turn0search3

## Nexo finding
Revocation/invalidation must be modeled as a semantic state transition over the dependency graph, not as deletion of one record.

Candidate states:
`VALID → STALE_PENDING_INVALIDATION → INVALIDATED → QUARANTINED/RECOMPUTABLE`.

For protected authority, `STALE_PENDING_INVALIDATION` is already insufficient for authorization. The system may continue serving historical evidence for audit, but it cannot use that evidence to produce a new protected ALLOW unless the current revocation generation is revalidated.

## Transitive invalidation
If claim B depends on A and C depends on B, revoking A must invalidate C even when C has no direct edge to A.

`REVOCATION(A) => INVALIDATE(transitive_dependents(A))`.

For a hypergraph, invalidation must also propagate through claims whose conjunctive prerequisite contains the revoked dependency.

A bounded traversal is an optimization/availability policy, not a safety proof. If the complete dependent closure cannot be established, the protected decision must be `UNKNOWN/QUARANTINE` or use a separately proven conservative boundary.

## Race at the effect boundary
A dangerous sequence is:
`ALLOW@R17 → revocation@R18 → EFFECT`.

The earlier ALLOW cannot remain authoritative merely because its signature is valid. At the protected commit boundary, the system must establish:
`current_revocation_generation >= required_generation`
and bind that generation to the exact operation/effect.

This matches the finality-bound revocation principle: current revocation state must participate in the final protected authorization decision. citeturn0search4turn0search7

## Fail-closed versus liveness
Complete invalidation can be expensive or temporarily impossible during partitions. Nexo must not silently trade safety for liveness by assuming that unvisited dependents are still valid.

Candidate policy:
- low-consequence/read-only claims may use an explicitly bounded-staleness profile;
- protected consequential effects require complete/authoritatively bounded revocation validation;
- inability to prove closure completeness → `UNKNOWN/QUARANTINE`;
- no automatic lowering of invalidation scope because of outage.

## Crash consistency
If revocation is observed and invalidation is in progress, a crash must not resurrect the pre-revocation authority state. Recovery must restore or advance the invalidation generation before any protected effect can commit. citeturn0search4

## Invariants
- `REVOCATION => TRANSITIVE_INVALIDATION`
- `STALE_PENDING_INVALIDATION => NO_PROTECTED_ALLOW`
- `VALID_SIGNATURE != CURRENT_AUTHORITY`
- `BOUNDED_TRAVERSAL != COMPLETE_CLOSURE`
- `UNKNOWN_CLOSURE => UNKNOWN_OR_QUARANTINE`
- `FINAL_EFFECT_REQUIRES_CURRENT_REVOCATION_STATE`
- `REVOCATION_GENERATION_MUST_BE_MONOTONIC`
- `CRASH_RECOVERY_MUST_NOT_RESURRECT_PRE_REVOCATION_AUTHORITY`
- `OUTAGE != SAFETY_THRESHOLD_DOWNGRADE`
- `ALTERNATE_EFFECT_PATH => SAME_REVOCATION_FINALITY_REQUIREMENT`

## Status
Research complete. The main result is a strict separation between invalidation propagation and final authority: invalidation can be asynchronous for some low-risk data, but protected consequences need an authoritative current-state check at the final effect boundary. No implementation or formal verification performed.
