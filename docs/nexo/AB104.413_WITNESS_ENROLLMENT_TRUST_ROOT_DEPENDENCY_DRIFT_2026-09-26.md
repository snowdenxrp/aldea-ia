# Nexo AB104.413 — Witness Enrollment, Trust-Root Rotation and Dependency Drift

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.412 → AB104.413
Implementation: NOT PERFORMED

## Research question

Can a malicious, stale, compromised, or no-longer-independent witness enter Nexo's evidence set, and how should trust-root/key rotation and dependency drift invalidate an apparently independent witness?

## Evidence reviewed

RFC 9334 separates reference values, verifier appraisal, attestation results, and Relying Party authorization. It also states that freshness is policy-defined and that state or appraisal policy can change immediately after evidence is produced. Therefore witness enrollment and current-use status must be separately governed. citeturn0search0

RFC 9162 shows that Certificate Transparency logs can provide signed tree heads and Merkle consistency proofs, but also identifies conflicting log views and the need for monitors/clients to compare observations. It explicitly notes that the log itself is a trusted third party in the base design and that consistency-view detection requires additional comparison mechanisms. citeturn0search1turn0search36

RFC 5280 treats trust-anchor information as a configured trust input containing issuer/key information, reinforcing that trust roots are inputs to validation rather than facts established by the certificate path itself. citeturn0search3

## Core finding

Witness independence is not a permanent attribute.

A witness that was independent at enrollment can become correlated later through:

- software replacement;
- shared deployment;
- common cloud/provider;
- policy synchronization;
- trust-root convergence;
- operator/control-plane changes;
- shared verifier library;
- common backup/recovery path;
- key rollover;
- common time source;
- adapter replacement.

Therefore:

WITNESS_INDEPENDENCE_AT_ENROLLMENT != CURRENT_WITNESS_INDEPENDENCE

## Enrollment attack

If the witness set is mutable, an attacker may attempt:

1. register a witness they control;
2. make it appear independent;
3. obtain an evidence role;
4. create a quorum with existing correlated witnesses;
5. use the apparent quorum to promote a stale/forked anchor.

Candidate rule:

NEW_WITNESS != TRUSTED_WITNESS

Enrollment must establish identity, trust root, intended role, dependency declaration, supported claim classes, and an authorized activation decision before the witness can contribute to protected quorum calculations.

## Candidate witness lifecycle

UNENROLLED
→ CANDIDATE
→ IDENTITY_VERIFIED
→ DEPENDENCIES_APPRAISED
→ CLAIM_SCOPE_ASSIGNED
→ TRUST_GENERATION_BOUND
→ ACTIVATED
→ CURRENT
→ DEGRADED / STALE / CONFLICTED
→ SUSPENDED
→ REVOKED / RETIRED

A witness can remain historically valid after becoming unusable for current authorization.

- WITNESS_ID

- WITNESS_ROLE
- CLAIM_CLASSES
- FAILURE_DOMAIN_SET

The witness does not self-declare these as authoritative.

## Independence is claim-specific

A witness can be independent for one claim and correlated for another.

Example:

- independent storage provider;
- same policy engine;
- same key management service.

For storage-integrity evidence, the storage failure domain may be independent.

For policy-integrity evidence, it is not.

Therefore:

WITNESS_INDEPENDENCE = f(CLAIM, DEPENDENCY_CLOSURE)

not a global boolean.

## Trust-root rotation

A trust-root change creates at least:

OLD_TRUST_GENERATION
→ TRANSITION
→ NEW_TRUST_GENERATION

A new trust root must not automatically validate all historical witness evidence or current witness authority.

Candidate distinctions:

- historical evidence accepted under old root;
- currently usable evidence under old root;
- currently usable evidence under new root;
- disputed evidence crossing the transition.

Candidate rule:

TRUST_ROOT_CHANGE => REVALIDATION_BOUNDARY

The exact transition may be claim-specific.

## Key rotation

Key rotation must distinguish:

KEY_VALID_FOR_HISTORY
from
KEY_VALID_FOR_CURRENT_ADMISSION

A witness signed under a retired key may remain useful to reconstruct history, while new high-consequence evidence may require the new key generation.

If the old key is compromised, affected current-use evidence may need invalidation. Historical records must not be silently rewritten.

## Dependency drift

A witness initially has:

DEPENDENCY_ROOT = D1

Later its software, policy, provider, trust root, or deployment changes:

DEPENDENCY_ROOT = D2

Even if WITNESS_ID and key remain unchanged, its assurance may have changed.

Candidate:

DEPENDENCY_ROOT_CHANGE => WITNESS_REVALIDATION

No assumption that “same witness” means “same assurance.”

## Hidden dependency attack

A witness declares:

DEPENDENCIES = {software, database}

but its current path also depends on:

shared policy service → shared operator → shared cloud control plane.

If the hidden dependencies are security-relevant, the witness's declared independence is incomplete.

Therefore:

DECLARED_DEPENDENCIES != REQUIRED_DEPENDENCY_CLOSURE

This carries forward AB104.396–AB104.398.

## Witness substitution

An attacker replaces the verifier or adapter while preserving:

WITNESS_ID
and possibly
KEY_ID.

If Z1 only checks the identity, the replacement can inherit historical trust incorrectly.

Candidate binding:

WITNESS_ID + INCARNATION/GENERATION + PATH_ID + DEPENDENCY_ROOT

where claim semantics require it.

## Witness incarnation

A restarted/replaced witness should not automatically inherit current status.

Candidate:

WITNESS_ID_same + WITNESS_INCARCATION_different
=> REVALIDATE

This mirrors RESOURCE_INCARNATION.

## Trust-root convergence attack

Two supposedly independent witnesses begin using the same root of trust after a migration.

Before migration:

TRUST_ROOT_A != TRUST_ROOT_B

After migration:

TRUST_ROOT_A == TRUST_ROOT_B

Their signatures may remain distinct, but the security dependency has converged.

Therefore:

MULTIPLE_KEYS != MULTIPLE_TRUST_DOMAINS

## Policy convergence attack

Likewise:

W1 policy source = P
W2 policy source = P

They may independently execute software but share the same policy compromise.

For policy-dependent claims:

COMMON_POLICY_SOURCE => COMMON_MODE_DEPENDENCY

## Provider convergence attack

Two witnesses hosted by different services may ultimately depend on the same underlying provider, region, identity system, DNS, deployment pipeline, or recovery service.

Thus geographic or vendor diversity alone does not establish independence.

## Dynamic drift monitoring

Independence should be re-evaluated when relevant dependencies change.

Candidate invalidation triggers:

- trust-root rotation;
- key compromise;
- software generation change;
- verifier implementation change;
- policy version change;
- adapter/path change;
- provider/region migration;
- backup/recovery event;
- operator/control-plane change;
- dependency graph change;
- witness incarnation change.

Candidate status:

CURRENT → REVALIDATION_REQUIRED

not silently CURRENT.

## Enrollment authority boundary

Witness enrollment must not be controlled solely by the witness set being enrolled.

Candidate:

ENROLLMENT_REQUEST
→ independent identity/trust verification
→ dependency closure
→ claim-specific independence assessment
→ protected enrollment decision
→ activation generation
→ witness becomes eligible.

This avoids circular trust.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| self-enrollment | signed witness metadata => trusted | independent enrollment |
| fake diversity | different IDs => independent | dependency closure |
| shared key | different signatures => independent | trust-root analysis |
| shared policy | different software => independent | policy dependency analysis |
| provider convergence | different vendors => independent | infrastructure closure |
| key rollover | new key => new trust domain | trust-generation analysis |
| software replacement | same ID => same assurance | incarnation/generation binding |
| hidden dependency | declared set => complete set | semantic dependency closure |
| stale witness | historically valid => current | freshness/invalidation |
| compromised old key | valid historical signature => current | compromise invalidation |
| witness outage | remove from quorum silently | protected witness policy |
| dependency drift | same witness => same independence | revalidation |

## Candidate invariants

- WITNESS_INDEPENDENCE_AT_ENROLLMENT != CURRENT_WITNESS_INDEPENDENCE
- NEW_WITNESS != TRUSTED_WITNESS
- WITNESS_INDEPENDENCE = f(CLAIM, DEPENDENCY_CLOSURE)
- TRUST_ROOT_CHANGE => REVALIDATION_BOUNDARY
- KEY_VALID_FOR_HISTORY != KEY_VALID_FOR_CURRENT_ADMISSION
- DEPENDENCY_ROOT_CHANGE => WITNESS_REVALIDATION

- WITNESS_ID != WITNESS_INCARCATION
- MULTIPLE_KEYS != MULTIPLE_TRUST_DOMAINS

## Residuals / not proven

- Exact enrollment authority location in Z0/Z1.
- Formal dependency-closure algorithm for witnesses.
- Quantitative/claim-specific independence thresholds.
- Secure witness key lifecycle and compromise recovery.
- Trust-root migration protocol.
- Detection latency for dependency drift.
- Formal anti-correlation guarantees.
- Privacy impact of publishing dependency metadata.
- Implementation and fault-injection correctness.
