# Nexo AB104.426 — Distributed Time, Clocks, Deadlines and Freshness Semantics

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.425 → AB104.426
Implementation: NOT PERFORMED

## Research question

What can Nexo safely claim when physical clocks, monotonic clocks, logical ordering, lease expiry, delayed messages, clock uncertainty, and clock failure disagree?

## Evidence

NIST describes distributed time synchronization as requiring explicit mechanisms and known accuracy characteristics; it discusses NTP and IEEE 1588 and emphasizes that synchronization quality depends on application requirements. citeturn0search0turn0search4

RFC 5905 describes NTP clock error, frequency error, synchronization, and the security interaction between time synchronization and authentication. It explicitly notes a circular dependency: reliable enforcement of cryptographic lifetimes requires a reliable clock, while reliable time depends on trusted synchronization sources. citeturn0search1

NIST also documents that time service can be security-critical for mechanisms such as access control and authentication. citeturn0search10

Google's Spanner work provides a concrete distributed-systems example in which the API exposes clock uncertainty rather than pretending synchronized clocks are exact; that uncertainty participates in consistency decisions. citeturn0search9turn0search14

## Core finding

A timestamp is an observation of a clock, not proof of global event order or current authority.

Therefore:

TIMESTAMP != GLOBAL_ORDER

and:

CLOCK_SYNCHRONIZED != CLOCK_TRUSTED_FOR_THIS_PROPERTY.

## Time classes

Nexo should distinguish at least:

### T0 — wall-clock / UTC time

Useful for human/audit chronology and expiry semantics when explicitly defined.

It is not automatically safe for ordering distributed events.

### T1 — monotonic local time

Useful for measuring local elapsed duration without wall-clock rollback.

It cannot by itself establish cross-node order.

### T2 — logical generation/order

Authority epochs, fence generations, sequence numbers, and event ordering can establish protocol order without synchronized physical clocks.

They do not automatically establish elapsed time.

### T3 — bounded physical-time uncertainty

A time service may provide an interval or uncertainty bound rather than an exact instant.

This can support claims whose policy explicitly incorporates the uncertainty.

### T4 — external provider time

A provider may enforce expiration using its own clock.

Nexo must not assume its local clock and provider clock have identical semantics.

## Freshness is claim-specific

Candidate:

FRESHNESS = PROPERTY + CLOCK_BASIS + MAX_AGE + UNCERTAINTY + STATE_BINDING.

Therefore:

FRESH_TIMESTAMP != FRESH_STATE.

An evidence item can have a recent timestamp while the underlying resource or authority state has already changed.

## Deadline semantics

A deadline can mean different things:

- sender-local deadline;
- receiver-local deadline;
- globally bounded deadline;
- provider-enforced expiry;
- authority admission deadline;
- lease expiration.

These are not interchangeable.

Candidate:

DEADLINE_SCOPE must be explicit.

## Sender versus receiver time

Suppose sender says:

expires_at = 12:00:10

Receiver's clock says:

12:00:11

The receiver cannot safely reject solely from the sender timestamp unless the protocol defines clock relationship and uncertainty.

Candidate:

REMOTE_TIMESTAMP_WITHOUT_CLOCK_BINDING != PROOF_OF_EXPIRY.

## Delayed-message attack

A valid message issued at t0 may arrive at t1 after:

- authority revocation;
- fence rollover;
- resource replacement;
- policy change.

Therefore:

MESSAGE_FRESHNESS != AUTHORITY_CURRENTNESS.

This reinforces AB104.407–AB104.414.

## Replay and time

Time-based replay protection alone is insufficient when clock assumptions can fail.

Candidate replay predicate should combine:

EFFECT_ID / NONCE
+
DURABLE_REPLAY_STATE
+
CURRENT_GENERATION
+
OPTIONAL_TIME_WINDOW.

Time is an additional constraint, not the sole identity mechanism for protected effects.

## Lease expiry

A lease or TTL can provide liveness/ownership semantics, but expiration based on one clock does not by itself prove that all delayed holders have stopped acting.

This carries forward the fencing result:

LEASE_EXPIRY != STALE_REQUEST_EXCLUSION.

A resource-side fence or equivalent enforcement boundary is required where stale actors could cause protected effects.

## Monotonic clocks

Monotonic clocks are valuable for local duration measurement.

But:

LOCAL_MONOTONIC_TIME != DISTRIBUTED_AUTHORITY_ORDER.

If a protected property crosses nodes, a protocol-level generation/order relation is generally required.

## Logical clocks

Logical clocks can represent causal/order relationships.

But:

LOGICAL_ORDER != PHYSICAL_TIME.

A logical clock should not be used to claim that a deadline elapsed unless that semantic relationship is explicitly established.

## Hybrid time

A system may combine:

physical time
+
logical/generation state
+
uncertainty.

Candidate principle:

USE_PHYSICAL_TIME_FOR_TIME_PROPERTIES;
USE_GENERATIONS/ORDER_FOR_AUTHORITY PROPERTIES;
USE_BOTH_ONLY_WHEN_THEIR_RELATION_IS_PROVEN.

## Clock failure classes

Candidate:

C1 clock stopped;
C2 clock jumps forward;
C3 clock jumps backward;
C4 frequency drift;
C5 synchronization loss;
C6 malicious time source;
C7 delayed time update;
C8 inconsistent node clocks;
C9 leap/UTC representation issue;
C10 provider/local clock disagreement.

Each failure class can affect different properties.

## Clock source independence

Multiple time sources are not automatically independent.

If all derive from:

- same upstream;
- same network;
- same GNSS source;
- same provider;
- same software;
- same operator;

then source count can overstate assurance.

This follows the same failure-domain algebra from AB104.417–AB104.418.

## Time-source quorum

A time-source quorum can improve confidence in a time estimate, but:

TIME_QUORUM != AUTHORITY_QUORUM.

And:

TIME_AGREEMENT != CORRECT_TIME

unless the trust/failure model supports that conclusion.

## Uncertainty interval

Candidate time evidence:

TIME_INTERVAL = [EARLIEST, LATEST]
+
SOURCE
+
TRUST_GENERATION
+
UNCERTAINTY_BASIS
+
OBSERVATION_GENERATION.

A property requiring “current by deadline” should evaluate the relevant interval, not a single nominal timestamp.

## Safe freshness predicate

Candidate:

FRESH iff

NOW_BASIS is trusted for the claim
AND
OBSERVATION_TIME is within allowed bound
AND
clock uncertainty is within policy
AND
underlying state generation remains current
AND
no invalidation generation has advanced
AND
resource incarnation remains bound.

This deliberately prevents time from substituting for state currentness.

## Unknown clock state

If the time source becomes untrusted or uncertainty exceeds policy:

CLOCK_STATUS = UNKNOWN/DEGRADED.

Do not silently assume:

UNKNOWN_TIME => CURRENT_TIME.

For security-critical deadlines:

UNKNOWN_TIME => HOLD / REVALIDATE / QUARANTINE

according to policy.

## Clock rollback

A backward wall-clock jump can cause:

- unexpired credentials to appear expired or vice versa;
- replay windows to reopen;
- leases to appear valid;
- evidence freshness to be miscomputed.

Therefore security-sensitive replay/authority state should not depend solely on wall-clock monotonicity.

## Clock jump forward

A forward jump can prematurely expire:

- leases;
- evidence;
- credentials;
- recovery windows.

Safety and liveness effects differ; policy must define the response.

## Clock uncertainty and authority

A clock can be synchronized and still have uncertainty too large for a particular property.

Candidate:

CLOCK_VALID_FOR_CLAIM != CLOCK_SYNCHRONIZED_IN_GENERAL.

## Provider deadline semantics

If a provider enforces expiry, the provider's time semantics become part of the effect path.

Candidate dependency closure must include:

PROVIDER_TIME_SOURCE
+
EXPIRY_SEMANTICS
+
CLOCK_TRUST_GENERATION

when deadline enforcement affects the protected property.

## Final-gate race

Suppose evidence is valid at t0.

At t1:
clock uncertainty expands or state generation changes.

At t2:
Z1 attempts commit.

The final gate must validate current time semantics and state generations together where the property requires both.

Candidate:

TIME_VALIDATION
AND
STATE_VALIDATION
AND
AUTHORITY_VALIDATION

at one protected boundary/equivalent fencing protocol.

## Time cannot prove external non-execution

A deadline passing locally does not prove a remote operation stopped.

Therefore:

LOCAL_EXPIRY != REMOTE_CANCELLATION
LOCAL_TIMEOUT != EXTERNAL_NON_EXECUTION.

This preserves the external-effect conclusions from AB104.370–AB104.380.

## Candidate time state machine

TRUSTED
→ DEGRADED
→ UNCERTAIN
→ UNTRUSTED
→ REVALIDATION_REQUIRED
→ TRUSTED

Parallel invalidation may force:

UNTRUSTED → QUARANTINED.

Historical time observations remain historical.

## Time abstraction rule from AB104.425

Safe abstraction is property-specific.

If only event order matters:

WALL_CLOCK → ORDER_RELATION

may be possible.

If elapsed duration matters:

WALL_CLOCK → ORDER_ONLY

is insufficient.

If authority currentness matters:

GENERATION/STATE_BINDING must remain explicit.
