# AB104.496 — certificate schema/version migration without semantic downgrade

## Evidence
RFC 7696 treats cryptographic migration as an explicit protocol concern: algorithm selection must be identified, transition mechanisms should be integrity protected to prevent downgrade, and legacy algorithms may need explicit deprecation/disablement. citeturn0search4turn0search5 Current TLS 1.3 specifies explicit version negotiation and rejects obsolete/weak versions rather than silently interpreting them as equivalent security contexts. citeturn0search8turn0search3 COSE provides authenticated algorithm identification and a `crit` mechanism for parameters that a processor must understand; an unsupported critical parameter is a fatal processing condition. citeturn0search1turn0search10

## Nexo migration model
A certificate schema transition must distinguish three things:
`SCHEMA_VERSION` = how the statement is encoded;
`SEMANTIC_PROFILE` = what security/authority claim it means;
`AUTHORITY_EPOCH` = which trust configuration may authorize it.

These cannot be inferred from one another.

Candidate transition:
`V_old ACTIVE → V_transition PREPARED → V_new VALIDATED → V_new ACTIVE`

The transition record should bind:
`OldSchema + NewSchema + SemanticProfile + Domain + MembershipEpoch + MembershipDigest + TrustBasisEpoch + MigrationPolicy + ActivationRevision`.

## Legacy verifier safety
An old verifier that does not understand a new security-critical field must not treat the field as irrelevant and accept the statement under weaker semantics. Critical fields therefore need an explicit fail-closed mechanism analogous to COSE's `crit` processing. citeturn0search1

If a new schema has stronger semantics, old verifiers should either reject it or remain restricted to an explicitly defined legacy authorization domain. They must never silently promote the new statement into an old semantic profile.

## New verifier safety
A new verifier must not reinterpret historical old-schema certificates as if they were issued under the new semantics. Historical certificates retain their original schema/domain/epoch. Promotion to current authority requires an explicit migration/translation certificate authorized under the new policy.

## Downgrade prevention
Algorithm/schema negotiation or selection must be integrity protected; otherwise an attacker can force a weaker interpretation during migration. RFC 7696 explicitly identifies this as a downgrade risk. citeturn0search4

Candidate rule:
`NEGOTIATED_PROFILE = intersection(supported, policy_allowed, epoch_allowed)`
then bind the selected profile into the authenticated certificate/transition record.

No automatic fallback from `V_new` to `V_old` is allowed for protected authority decisions unless a policy explicitly permits the legacy profile and its security properties remain sufficient for that claim.

## Historical preservation
Migration must not rewrite old certificates. Preserve original bytes/digest, signer/key epoch, schema, domain, membership digest and issuance context. A translated representation is a new statement with a new signature and explicit relation to the historical source.

`TRANSLATION != ORIGINAL_CERTIFICATE`
`NEW_SIGNATURE != HISTORICAL_REWRITE`
`SCHEMA_MIGRATION != TRUST_MIGRATION`

## Invariants
- `UNKNOWN_SCHEMA => REJECT_OR_QUARANTINE`
- `UNKNOWN_CRITICAL_FIELD => REJECT`
- `OLD_SCHEMA_CERTIFICATE != NEW_SCHEMA_AUTHORITY`
- `VALID_OLD_CERTIFICATE != CURRENT_NEW_POLICY_AUTHORITY`
- `DOWNGRADE_SELECTION => REJECT`
- `MIGRATION_REQUIRES_EXPLICIT_AUTHORIZATION`
- `HISTORICAL_CERTIFICATE_BYTES_ARE_IMMUTABLE`
- `TRANSLATION_REQUIRES_NEW_DOMAIN_AND_SIGNATURE`
- `SCHEMA_VERSION != SEMANTIC_PROFILE`
- `SEMANTIC_PROFILE != AUTHORITY_EPOCH`

## Status
Research complete. This establishes a migration boundary but does not choose a concrete serialization or migration protocol. No implementation or formal verification performed.
