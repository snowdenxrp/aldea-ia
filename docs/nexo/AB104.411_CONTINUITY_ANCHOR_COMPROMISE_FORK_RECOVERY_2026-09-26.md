# Nexo AB104.411 — Continuity-Anchor Compromise, Equivocation and Fork Recovery

Date: 2026-09-26

## Research question

What happens when the external continuity anchor itself is compromised, equivocates, becomes unavailable, is restored from backup, or disagrees with Nexo's protected history?

## Evidence reviewed

RFC 9162 shows that append-only Merkle consistency can prove that one tree extends another, but explicitly notes that a misbehaving log can present inconsistent views to different clients; detecting this requires comparison/auditing across observers. Therefore an anchor is not automatically trustworthy merely because its state is signed. citeturn0search0turn0search5

RFC 9334 separates freshness from current validity: evidence or attestation results can become stale immediately after generation, and epoch changes can make previously produced results unacceptable. This supports treating an anchor's generation as a state input rather than permanent authority. citeturn0search1

in-toto demonstrates a separate trust pattern: a signed layout defines authorized steps and signed link metadata provides evidence that the steps were performed as specified. This supports separating an authority/root from the evidence chain it validates. citeturn0search3turn0search6

## Core finding

A continuity anchor is an evidence/control dependency, not automatically the ultimate source of truth.

ANCHOR_SIGNATURE_VALID != ANCHOR_CORRECT
ANCHOR_CURRENT != HISTORY_COMPLETE
ANCHOR_AUTHENTIC != AUTHORITY

If the anchor can equivocate, Nexo must be able to detect disagreement or deliberately enter a fail-closed/quarantined state.

## Anchor threat classes

### 1. Unavailable anchor

The anchor cannot be reached.

Safe behavior depends on effect class:
- ordinary informational operation may continue if the claim does not require current anchor state;
- safety-critical authorization: HOLD / REVALIDATE;
- high-consequence external effect: no new grant unless an independently valid current-state mechanism exists.

Availability must not silently become authority.

### 2. Stale anchor

ANCHOR_GENERATION < REQUIRED_CURRENT_GENERATION => STALE

Stale does not mean malicious, but it cannot establish current authorization.

### 3. Equivocating anchor

Two clients receive:

G=200, ROOT=A
G=200, ROOT=B

Both can be cryptographically valid.

Candidate:

EQUIVOCATION_DETECTED => QUARANTINED

No local majority assumption should silently choose one history.

### 4. Compromised signing key

An attacker can potentially create syntactically valid anchor statements.

Key compromise must invalidate current trust in affected anchor generations according to protected policy. Historical signatures may remain useful for audit but cannot automatically grant future authority.

### 5. Anchor restored from backup

The anchor itself can suffer the same rollback problem as Nexo state.

RESTORED_ANCHOR != CURRENT_ANCHOR

An anchor cannot prove its own freshness solely from a backup restored inside itself.

### 6. Anchor fork

Two recovery paths may create locally consistent continuations:

H0 → H1 → H2A
H0 → H1 → H2B

Both can have valid internal signatures.

If both claim to be current:

FORK_CONFLICT => QUARANTINED / GOVERNANCE_RECONCILIATION

unless an independent authoritative rule establishes which branch is valid.

## Candidate anchor contract

Claim-required fields may include:
- ANCHOR_ID
- ANCHOR_DOMAIN
- GENERATION
- STATE_ROOT
- PREVIOUS_ROOT / PREVIOUS_GENERATION
- POLICY_VERSION
- SCHEMA_VERSION
- AUTHORITY_EPOCH
- KEY/TRUST_GENERATION
- ISSUED_AT / validity information where required
- OBSERVER / witness information where applicable
- INVALIDATION_GENERATION
- STATUS

The anchor does not decide Nexo authority merely by returning these fields.

## Three separate questions

A. Integrity — did this anchor statement come from the expected source and remain unmodified?

B. Consistency — does this state extend previously accepted anchor history without contradiction?

C. Authority — does Z1 currently accept this anchor as sufficient evidence for the protected property?

Therefore:

INTEGRITY != CONSISTENCY != AUTHORITY

## Independent observation

RFC 9162 is directly relevant: an append-only source can still show different views to different clients, so observers must compare views to detect equivocation. citeturn0search0

Candidate Nexo mechanism:

ANCHOR
→ independent observation(s)
→ consistency comparison
→ conflict detection
→ evidence status

Possible observer classes:
- independent verifier;
- separate trust domain;
- separate failure domain;
- external transparency/log witness;
- previously pinned anchor state.

Independence must be measured by dependency graph, not by number of software instances.

## Witness limitation

A witness can detect disagreement only if it has an independent view or protected prior state.

If ANCHOR + WITNESS share the same compromised key, database, deployment, policy, or operator path, they may reproduce the same false state.

MULTIPLE_OBSERVERS != INDEPENDENT_OBSERVERS

## Anchor compromise response

Candidate state machine:

CURRENT
→ SUSPECTED_COMPROMISE
→ AUTHORITY_FROZEN
→ DEPENDENCY_IMPACT_ANALYSIS
→ HISTORY_COMPARISON
→ REPLACEMENT_ANCHOR_ESTABLISHED
→ AFFECTED_CLAIMS_REVALIDATED
→ RECOVERY_RELEASE

If compromise cannot be resolved:

QUARANTINED

The system must not let the compromised anchor certify its own replacement.

## Anchor replacement

A replacement anchor needs an explicit trust transition:

OLD_ANCHOR
→ authenticated revocation/retirement decision
→ new anchor identity
→ cross-reference to accepted history
→ new key/trust generation
→ protected activation
→ dependent-claim revalidation

The new anchor should not simply copy the old anchor's authority state without proving continuity.

## Conflict with protected Nexo history

Suppose Nexo's durable history says:

G=500, ROOT=X

while the anchor says:

G=500, ROOT=Y

Neither should automatically override the other.

Candidate:

CONFLICTING_PROTECTED_HISTORY => DISPUTED / QUARANTINED

Then classify the conflict as possible replication lag, stale anchor, local Nexo corruption, anchor corruption, fork/equivocation, or unknown.

Only after classification and evidence should recovery proceed.

## Total anchor loss

If the external anchor is unavailable or destroyed, ask whether current continuity can be proven from surviving state.

If all independent continuity evidence was lost:

CURRENT_CONTINUITY = UNKNOWN

The system may preserve historical records and recover non-authoritative functionality, but must not silently manufacture current authority.

## Anti-self-recovery rule

A compromised/recovered authority must not be allowed to declare that its restored state proves it is current.

RECOVERED_AUTHORITY_CANNOT_SELF_CERTIFY_CURRENTITY

Recovery needs a trust path external to the state being recovered, or explicit governance/quarantine when that path is unavailable.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| anchor outage | unavailable => safe to continue | claim-specific HOLD/REVALIDATE |
| stale anchor | signed => current | generation validation |
| equivocation | both signed => choose one | conflict/quarantine |
| key compromise | signature valid => trusted | trust-generation invalidation |
| anchor backup rollback | restored => current | external continuity evidence |
| forked recovery | locally consistent => globally valid | independent comparison |
| shared witness | two views agree => independent | dependency-domain analysis |
| anchor replacement | new key => inherited authority | explicit trust transition |
| history conflict | anchor wins automatically | DISPUTED/quarantine |
| total anchor loss | surviving local data => current | UNKNOWN continuity |
| self-recovery | restored authority certifies itself | external recovery authority |
