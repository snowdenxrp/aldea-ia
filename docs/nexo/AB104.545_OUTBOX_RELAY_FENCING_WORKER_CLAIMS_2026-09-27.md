# Nexo AB104.545 — Outbox relay worker fencing

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A relay claim lease prevents concurrent ownership only while every subsequent state transition is fenced by the current claim identity. Lease expiry can safely enable takeover, but it cannot prove that the old worker did not already dispatch the effect. Therefore worker fencing reduces stale-worker state corruption; it does not eliminate duplicate external delivery.

## Evidence
A current transactional-outbox implementation uses `FOR UPDATE SKIP LOCKED` to distribute claims, a visibility lease for crash recovery, and requires every later write to present the lease owner/token. Its documentation explicitly notes that a stale relay may have published after its lease expired, so consumers still require idempotency. citeturn0search3turn1view0 A 2026 machine-checked analysis independently identifies the crash boundary: the relay's durable state cannot by itself determine whether the sink accepted the effect; sink-side evidence or fencing is needed to escape that information limit. citeturn1view2

## Candidate claim protocol
CLAIM(row, owner, lease_token, expiry)
-> publish using stable EffectID
-> SETTLE only WHERE current_lease_token == lease_token AND state permits

If lease expires:
OLD_WORKER may still be executing externally, but it loses authority to mutate the durable row because settlement is fenced by the claim token.

NEW_WORKER may reclaim only after the authoritative lease boundary says the old claim is no longer current.

## Critical race
T0 old worker claims token A
T1 old worker starts provider call
T2 lease A expires
T3 new worker claims token B
T4 old provider call completes

At T4, a fenced `markPublished(A)` must fail. But the external provider may already have accepted the call. Therefore:
`STALE_SETTLEMENT_REJECTED != STALE_EFFECT_PREVENTED`

Preventing the latter requires provider-side fencing/idempotency at the effect acceptance boundary.

## Lease sizing
The lease must exceed the worker's bounded local critical work budget sufficiently to avoid unnecessary duplicate claims, but no finite TTL proves the remote call cannot outlive it. If a worker cannot complete within the remaining lease budget, it should stop starting new dispatches or renew through an authoritative transition. Renewal itself is not proof that an in-flight external call is fenced.

## Claim identity
Do not use worker identity alone as the fence. A restarted worker can reuse the same process/host identity. Use a unique claim token/generation bound to:
- Outbox/EventID
- OperationID/EffectID
- Worker incarnation
- Claim generation
- Authority epoch where required
- Lease validity boundary

## Recovery
- crash before external call: reclaim and dispatch;
- crash during call: outcome UNKNOWN; reconcile or retry with stable identity;
- call succeeds, worker dies before settle: new worker may retry; sink must deduplicate/fence;
- old worker wakes after takeover: all durable settlement writes with old token are rejected;
- ambiguous claim response: query authoritative row/lease state before acting.

## Critical distinctions
- CLAIM_LEASE != EXTERNAL_FENCE
- LEASE_EXPIRY != REMOTE_CANCELLATION
- STALE_SETTLEMENT_REJECTED != STALE_EFFECT_PREVENTED
- WORKER_ID != WORKER_INCARNATION
- ACK_LOST != DISPATCH_FAILED
- CLAIM_TAKEN_OVER != OLD_CALL_DID_NOT_EXECUTE
- RENEWED_LEASE != FENCED_IN_FLIGHT_CALL
- DEDUPE != GLOBAL_ATOMICITY

## Nexo implication
The effect plane needs two separate protections: (1) durable outbox claim fencing so stale workers cannot corrupt relay state, and (2) provider-side EffectID/fence enforcement where duplicate or stale external effects must be prevented. The architecture must not collapse these into one generic 'lease' primitive.
