## Explicit retry distinction
RETRY_ADMISSIBLE = current authorization + current recovery ownership + effect-class retry rule + required target/provider conditions.

RETRY_SAFE_EQUIVALENT = RETRY_ADMISSIBLE + stable logical identity + provider-enforced deduplication/equivalence (or independently proven equivalent semantics).

The second property is strictly stronger. RFC 9110 cautions against automatically retrying non-idempotent requests unless their semantics are known to be idempotent or the client can determine the original was not applied. AWS Durable Execution similarly distinguishes at-least-once replay from at-most-once-per-retry and notes that neither alone establishes exactly-once across a whole workflow. citeturn0search1turn0search0

## Evidence binding rule
A response, acknowledgement, or reconciliation result must be bound to the exact logical effect identity and the declared property being claimed. HTTP conditional requests demonstrate the narrower pattern: a state-changing request can be conditioned on a current validator and the condition is evaluated before applying the method; this prevents a stale target update but does not itself establish Nexo authority freshness or external cross-resource atomicity. citeturn0search1

## Crash/recovery rule
A crash does not justify promoting an uncertain state. Recovery reconstructs durable facts, marks unresolved external outcomes UNKNOWN/RECONCILIATION_REQUIRED, and re-establishes current authority/fence before any new effectful attempt. AWS documentation likewise notes that after an interrupted side-effecting step, the external system may need to be checked before deciding what to do next. citeturn0search2
