# Nexo AB104.407 — Authenticated Lineage and Replay / Stale-Lineage Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.406 → AB104.407
Implementation: NOT PERFORMED

## Research question

Which lineage fields must be authenticated and bound to the protected operation, which intermediaries enter the TCB, and how should Nexo reject replayed, reordered, duplicated, or stale lineage across queues, callbacks, retries, authority epochs, and resource incarnations?

## Evidence reviewed

W3C Trace Context defines trace propagation for correlation and distributed tracing. It permits intermediaries to update parent identifiers and explicitly treats trace context as tracing information; it does not define application authorization semantics. Therefore a trace ID must not be treated as an authority token or proof of effect equivalence. citeturn0search0turn0search4

RFC 9334 RATS separates Evidence, Verifier-produced Attestation Results, and Relying Party authorization. It also states that freshness only narrows the age of evidence/results and that state can change immediately afterward, leaving a race that must be handled architecturally. citeturn0search3

## Core finding

Lineage needs two separate properties:

1. **Correlation integrity** — events can be associated with the same causal chain.
2. **Authorization binding** — the protected transition is authorized for this exact operation/effect/participant/authority generation.

A mechanism can provide the first without providing the second.

Therefore:

`VALID_LINEAGE_CORRELATION != VALID_AUTHORITY_BINDING`

## Candidate authenticated lineage envelope

For a protected boundary, candidate fields are:

- OPERATION_ID
- EFFECT_ID, where applicable
- ATTEMPT_ID
- PARENT_LINEAGE_ID
- LINEAGE_SEQUENCE / predecessor reference
- PARTICIPANT_ID
- RESOURCE_INCARNATION
- AUTHORITY_EPOCH
- FENCE_GENERATION
- EFFECT_CLASS_EFFECTIVE
- FOOTPRINT_CLOSURE_ROOT
- CAPABILITY_GENERATION
- POLICY / CONTRACT VERSION
- EXPIRY / FRESHNESS BASIS where applicable
- ISSUER / AUTHORITY_DOMAIN
- DESTINATION / PARTICIPANT DOMAIN
- LINEAGE_SCHEMA_VERSION
- NONCE or replay-prevention state where the protocol requires it

The exact set remains claim-specific. A field is not required merely because it exists in this list.

## Binding rule

For high-consequence effects, a downstream participant should not trust caller-supplied lineage merely because it is syntactically valid.

Candidate chain:

`AUTHORITY_DECISION`
→ authenticated lineage envelope
→ participant/path validation
→ replay/staleness checks
→ local protected linearization
→ effect attempt.

If an intermediary rewrites lineage, the rewrite must have a defined semantic rule. Otherwise the intermediary becomes an implicit trust boundary/TCB component.

## Trace Context limitation

W3C Trace Context allows a service to update the parent-id while continuing the same trace. This is useful for causal correlation but demonstrates why trace context cannot itself serve as immutable authorization lineage. citeturn0search0turn0search4

Candidate rule:

`TRACEPARENT != AUTHORIZATION_LINEAGE`

A trace can reference an authorization lineage record, but the authorization binding must be separately authenticated and validated.

## Replay attacks

Potential replay classes:

- same message delivered twice;
- delayed old message delivered after authority rollover;
- duplicate queue delivery;
- old callback replayed after effect completion;
- old retry replayed after compensation;
- old child execution resumed after resource replacement;
- captured lineage replayed to a different participant;
- valid lineage replayed after its footprint closure was invalidated.

Candidate response:

`REPLAY_OR_STALE_LINEAGE => REJECTED`

or, where execution state cannot determine whether it is safe:

`UNKNOWN/HOLD/RECONCILIATION_REQUIRED`

No replay protection should depend solely on wall-clock freshness when a monotonic generation/epoch can express the required state.

## Reordering attacks

A valid message can still be semantically invalid if delivered out of order.

Candidate predecessor binding:

`LINEAGE_SEQUENCE` or equivalent monotonic causal state

must be checked against authoritative participant state when ordering is a protected property.

A valid signature on event N does not prove event N is currently admissible if event N+1 already linearized or the resource incarnation changed.

## Cross-domain lineage

When crossing provider/authority domains:

`DOMAIN_A_LINEAGE` → authenticated handoff → `DOMAIN_B_LINEAGE`

Domain B should not blindly inherit all of Domain A's authority. It should validate:

- issuer/domain;
- intended destination;
- effect/operation identity;
- permitted inheritance rule;
- authority epoch/fence;
- participant/resource incarnation;
- footprint closure binding;
- capability generation;
- freshness/invalidation state.

If no trusted mechanism establishes the handoff semantics, the boundary is not proven safe.

## Intermediary TCB rule

An intermediary enters the TCB for a property when Nexo relies on it to enforce or preserve that property's security/authority semantics.

Examples:

- pure trace forwarder: generally observability dependency, not authority TCB;
- lineage-signing gateway: TCB for the claims it signs;
- authorization-aware queue broker: TCB for properties it enforces;
- opaque provider callback router: cannot be treated as transparent if downstream safety depends on its routing semantics;
- verifier: TCB for the claims it appraises, but its result remains input to Nexo policy per RATS. citeturn0search3

This prevents “trusted intermediary” from becoming an undefined blanket category.

## Freshness and epoch

RFC 9334 notes that freshness still permits a race because state can change after evidence or an attestation result is generated. citeturn0search3

Therefore:

`FRESH_LINEAGE != CURRENT_AUTHORITY`

A lineage record should be invalidated by protected generation changes where those generations are part of the claim:

- authority epoch rollover;
- fence generation rollover;
- resource incarnation change;
- capability generation change;
- footprint closure invalidation;
- policy/contract version invalidation.

## Candidate replay state

For a participant that must prevent duplicate execution, candidate durable state includes:

- last accepted lineage generation/sequence;
- accepted EffectID / operation state;
- resource incarnation;
- authority/fence generation;
- replay window or nonce-consumption state where applicable;
- final outcome state.

The exact mechanism depends on the provider protocol. Nexo must not assume that signatures alone provide replay prevention.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| duplicate delivery | valid signature => execute again | durable dedup/replay rule |
| delayed old lineage | signature valid => current | epoch/incarnation validation |
| callback replay | same callback ID => safe | bind to current effect state |
| reordered events | signed => correct order | predecessor/order validation |
| cross-domain reuse | valid in A => valid in B | explicit handoff policy |
| trace ID reuse | same trace => same authority | separate authority lineage |
| intermediary rewrite | rewritten parent => preserved authority | authenticated semantic rewrite |
| stale capability | old capability evidence => current | generation validation |
| resource replacement | same resource ID => same target | incarnation binding |
| closure invalidation | old closure root => current | revalidation |
| compensation replay | old effect => retry safely | state-machine check |
| recovery replay | old recovery lineage => new recovery authority | recovery ownership/epoch validation |

## Candidate invariants

- `VALID_LINEAGE_CORRELATION != VALID_AUTHORITY_BINDING`
- `TRACEPARENT != AUTHORIZATION_LINEAGE`
- `LINEAGE_SIGNATURE_VALID != CURRENT_AUTHORIZATION`
- `REPLAYED_LINEAGE_CANNOT_CREATE_NEW_AUTHORITY`
- `STALE_EPOCH_LINEAGE_CANNOT_PASS_FINAL_GATE`
- `RESOURCE_INCARCATION_CHANGE_INVALIDATES_BOUND_LINEAGE`
- `FOOTPRINT_CLOSURE_INVALIDATION_INVALIDATES_BOUND_LINEAGE`
- `INTERMEDIARY_ENFORCEMENT_PROPERTY => INTERMEDIARY_IN_TCB`
- `CROSS_DOMAIN_LINEAGE_REQUIRES_EXPLICIT_HANDOFF_BINDING`
- `VALID_SIGNATURE != VALID_ORDER`
- `FRESH_LINEAGE != CURRENT_AUTHORITY`
- `AUTHENTICATED_LINEAGE != AUTOMATIC_AUTHORITY`

## Residuals / not proven

- Exact cryptographic envelope/protocol selection.
- Key lifecycle, rotation, compromise and recovery semantics.
- Formal replay-window semantics under partition.
- Complete causal ordering model across heterogeneous providers.
- Formal minimal TCB for each lineage-preservation architecture.
- Provider-specific support for authenticated lineage propagation.
- Implementation correctness and fault-injection evidence.
