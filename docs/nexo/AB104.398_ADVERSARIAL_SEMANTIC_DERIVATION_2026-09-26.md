# Nexo AB104.398 — Adversarial Semantic Dependency Derivation

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective
Attack the semantic REQUIRED_SET derivation itself: contradictory policy/effect/schema rules, recursive cycles, branch-dependent dependencies, rule updates during derivation, and deterministic recomputation.

## 1. Contradictory semantic authorities

Example:
- Policy P8 requires D1,D2.
- Effect contract E4 requires D1,D2,D3.
- Schema S8 defines D2 differently.
- Adapter declares D1,D2,D4.

A deterministic algorithm can still deterministically produce the wrong answer if precedence is undefined.

Therefore deterministic recomputation is necessary for reproducibility, not sufficient for semantic correctness.

Candidate requirement:
SEMANTIC_PRECEDENCE_RULE must itself be versioned, protected and claim-scoped.

## 2. Attack — precedence update during derivation

Timeline:
1. Derivation starts under precedence rule R7.
2. R8 becomes current.
3. Derivation finishes using R7.
4. Result is submitted as current.

Rule:
- result must bind to exact precedence/semantic rule version;
- if currentness requires R8, R7 result becomes historical;
- no silent mixed-rule derivation.

## 3. Attack — contradictory requirements

If one authoritative rule says D3 REQUIRED and another says D3 FORBIDDEN:
- do not resolve by “latest timestamp” unless policy explicitly defines that semantics;
- return CONFLICT/UNKNOWN;
- require explicit governance resolution.

A contradiction is a semantic safety condition, not merely a parser error.

## 4. Attack — recursive cycle

D1 requires D2; D2 requires D3; D3 requires D1.

A fixed-point algorithm must detect the cycle.

Cycle != proof of completeness.
Cycle resolution is valid only if the semantic contract explicitly defines recursive equivalence/termination semantics.

Otherwise:
UNKNOWN/QUARANTINED.

## 5. Attack — branch-dependent dependency

Example:
if provider_mode=A -> D3
if provider_mode=B -> D4

The derivation must bind the branch predicate to protected/current facts.

Unsafe:
- branch selected from stale cache;
- branch changes after derivation;
- result remains valid for both branches without proving equivalence.

Candidate:
BRANCH_CONTEXT_VERSION + BRANCH_FACTS + BRANCH_POLICY_VERSION become closure dependencies.

## 6. Attack — hidden runtime branch

A runtime component discovers D5 only after a protected operation starts.

If D5 was semantically foreseeable, omission indicates incomplete derivation.

If D5 is genuinely unknowable before runtime:
- protected operation must transition to a new evaluation boundary before relying on D5;
- the original closure cannot silently absorb D5.

## 7. Attack — nondeterministic derivation

Two derivations with identical semantic inputs produce different REQUIRED_SET values.

Possible causes:
- unordered traversal;
- current time;
- mutable external registry;
- nondeterministic plugin;
- network-dependent metadata;
- locale/environment dependence.

Candidate rule:
semantic derivation inputs must be explicit and version-bound; nondeterministic sources must either be fixed as inputs or excluded from safety-critical derivation.

DETERMINISTIC_REPLAYABILITY is a candidate validation property.

## 8. Attack — deterministic but wrong implementation

A buggy implementation consistently omits D3.

Recomputing it reproduces the same wrong result.

Therefore:
REPRODUCIBILITY != CORRECTNESS.

Candidate independent validation:
- reference semantics/specification;
- adversarial test corpus;
- differential implementation/verifier where practical;
- mutation/property testing;
- explicit semantic invariants.

No single implementation should be treated as self-proving.

## 9. Attack — schema migration

S8 changes meaning of field X.

Old derivation interprets X as requirement D2.
New derivation interprets X as capability C2.

A shared serialization format does not imply semantic compatibility.

Migration must bind:
FROM_SCHEMA + TO_SCHEMA + MAPPING_RULE + SEMANTIC_COMPATIBILITY_CLAIM.

If compatibility is not proven for the relevant claim:
UNKNOWN.

## 10. Attack — policy/effect contract disagreement

If policy permits an effect but effect contract imposes stricter safety dependencies:
the stricter contract cannot be silently discarded.

Candidate rule:
effective required set must satisfy all applicable mandatory constraints after explicit precedence resolution.

But “stricter” itself must be semantically defined, not inferred from set size alone.

## 11. Attack — dependency subtraction

Policy update removes D4.

A cached D4 requirement remains in historical result.

Current derivation may legitimately no longer require D4, but old evidence must not be rewritten.

This creates two distinct records:
- historical REQUIRED_SET(P7)
- current REQUIRED_SET(P8)

Never mutate history to resemble current semantics.

## 12. Attack — semantic rollback

P9 -> P8 rollback.

Rollback is not automatically equivalent to continuity.

Candidate requirement:
new policy generation + explicit rollback event + compatibility/invalidation evaluation.

A previous valid result under P8 cannot automatically become current merely because P8 returns.

## 13. Attack — cross-contract recursion

Claim C1 requires effect contract E1.
E1 requires claim C2.
C2 requires E2.
E2 eventually requires C1.

Need explicit graph-cycle semantics.

If recursion represents legitimate fixed-point semantics, the contract must define the least/greatest fixed point or equivalent rule.

Without such semantics, return UNKNOWN rather than inventing a closure.

## 14. Attack — semantic resource exhaustion

Adversary supplies a contract causing exponential dependency expansion.

Safety rule:
- bounded computation;
- deterministic resource accounting;
- explicit LIMIT_REACHED state;
- no silent truncation;
- no promotion to COMPLETE.

This protects liveness without weakening completeness.

## 15. Candidate derivation contract

DERIVE(CLAIM, POLICY, SCHEMA, EFFECT_CONTRACT, SEMANTIC_RULESET, BRANCH_CONTEXT)

must return:
- REQUIRED_SET;
- REQUIRED_SET_ROOT;
- semantic-rule version;
- policy/schema/effect versions;
- dependency graph;
- branch context;
- cycle/conflict status;
- completeness status;
- resource consumption;
- limitations;
- invalidation dependencies.

CURRENT_COMPLETE is admissible only when:
- all semantic inputs are version-bound;
- precedence is explicit;
- recursion terminates under defined semantics;
- all applicable branches are resolved;
- no unresolved conflict exists;
- computation completed without truncation;
- required semantic rules are valid/current;
- independent validation requirements are satisfied.

## 16. Key result

AB104.398 rejects a tempting but unsafe assumption:

DETERMINISTIC_DERIVATION == SEMANTIC_COMPLETENESS.

Correct distinction:
DETERMINISTIC_DERIVATION -> reproducibility.
SEMANTIC_COMPLETENESS -> reproducibility + correct semantic specification + complete rule coverage + valid current inputs + successful validation.

## 17. Candidate invariants

- DETERMINISM != CORRECTNESS
- REPRODUCIBILITY != COMPLETENESS
- SEMANTIC_PRECEDENCE_MUST_BE_EXPLICIT
- CONFLICT != RESOLUTION
- CYCLE != COMPLETENESS
- UNRESOLVED_RECURSION => UNKNOWN
- BRANCH_CONTEXT_IS_A_DEPENDENCY
- STALE_BRANCH_FACTS_CANNOT_AUTHORIZE_CURRENT_CLOSURE
- DYNAMIC_DISCOVERY_REQUIRES_NEW_BOUNDARY
- SCHEMA_COMPATIBILITY_MUST_BE_EXPLICIT
- POLICY_ROLLBACK_IS_A_NEW_GENERATION
- HISTORICAL_SETS_ARE_IMMUTABLE
- RESOURCE_LIMIT != COMPLETE
- SINGLE_IMPLEMENTATION != SELF_PROOF

## Status

AB104.398 establishes that the semantic derivation layer itself requires a specification, precedence model, versioning, recursion semantics, branch binding, bounded execution and independent validation. A deterministic derivator can still be consistently wrong.

Not proven: correctness of any concrete derivation algorithm, completeness of the semantic specification, Byzantine resilience, or formal/implementation correctness.

## Exact next action

AB104.399 — study independent/differential validation of semantic derivation: reference model vs production derivator, property-based/adversarial testing, proof obligations, disagreement handling, and whether the verifier itself can remain outside the authoritative TCB.
