## Research question

What can TPM/NV counters, measured boot, attestation, secure boot, and hardware-backed rollback resistance actually establish for Nexo?

## Evidence

The current TCG TPM 2.0 Library specification is Version 185 (March 2026). The TPM architecture specifies NV counters that cannot move backward; it also addresses deletion/recreation of counters through protected tracking of the highest prior value. citeturn0search5turn0search50

NIST SP 800-193 describes authenticated updates, rollback protection, detection, and secure recovery as separate platform-resiliency mechanisms. It notes that rollback to an older firmware version may require explicit physical authorization in some designs. citeturn0search48turn0search1

NIST IR 8320 describes measured boot/PCRs and remote attestation, and notes that a monotonically incremented counter can prevent rollback of firmware/configuration to an older version. It also shows that measurements can be evaluated remotely against expected values. citeturn0search49

Microsoft documents Secure Boot/Trusted Boot as enforcing trusted boot components and separately requires firmware rollback protection; this demonstrates that signature verification and anti-rollback are distinct controls. citeturn0search6turn0search7

Android KeyMint exposes a rollback-resistance authorization property for keys, while Android's storage documentation shows rollback resistance being used to protect key material. citeturn0search9turn0search8

## Core finding

Hardware can provide a stronger local root for anti-rollback and measured-state claims, but:

HARDWARE_MONOTONICITY != CURRENT_AUTHORITY

and:

ATTESTED_BOOT_STATE != CORRECT_APPLICATION_STATE.

Hardware protects a primitive and its defined semantics. Nexo still has to define what that primitive means for authority, recovery, resource fencing, and external effects.

## Capability H1 — TPM NV monotonic counter

Candidate guarantee:
- counter does not decrease under the TPM's specified semantics;
- deletion/recreation rollback is addressed by TPM mechanisms.

Useful for:
- local anti-rollback generation;
- boot/configuration version floors;
- recovery generation binding.

Limitations:
- counter value alone does not identify the correct distributed authority;
- does not prove policy correctness;
- does not prove external state;
- device replacement requires a new identity/incarnation model;
- availability/failure of TPM becomes a dependency.

Candidate Nexo use:
RESOURCE_LOCAL_FENCE_FLOOR or RECOVERY_GENERATION_FLOOR.

## Capability H2 — Secure/verified boot

Secure Boot establishes that boot components satisfy signature/trust policy.

Useful for:
- preventing unauthorized boot software;
- establishing a trusted execution starting point.

It does not prove:
- application correctness;
- current distributed authority;
- policy correctness;
- external provider state.

Therefore:

SECURE_BOOT != APPLICATION_CORRECTNESS.

## Capability H3 — measured boot

Measured boot records measurements of the boot path; remote attestation can expose those measurements to a verifier.

Useful for:
- evidence about what software/configuration booted;
- binding a claim to a measured platform state.

Limitations:
- measurement is evidence, not authorization;
- verifier policy determines what measurements mean;
- a valid measurement can become stale after state changes;
- it does not prove runtime behavior after measurement.

Therefore:

MEASURED_STATE != RUNTIME_BEHAVIOR.

## Capability H4 — hardware-backed key rollback resistance

Rollback-resistant keys can make older software/configuration unable to use protected key material under defined platform semantics.

Useful for:
- preventing a rollback from recovering previously invalidated key state;
- strengthening identity continuity.

Limitations:
- key state is not equivalent to Nexo authority state;
- key compromise/revocation still requires explicit semantics;
- hardware-backed key protection does not prove external effect state.

## Capability H5 — hardware + attestation

Candidate chain:

BOOT
→ MEASURE
→ TPM/TEE PROTECTED STATE
→ ATTESTATION EVIDENCE
→ VERIFIER APPRAISAL
→ Z1 POLICY
→ AUTHORITY DECISION.

This follows the AB104.390/401 separation:

EVIDENCE != AUTHORITY.

## Anti-rollback property decomposition

Hardware can help establish:

A. local monotonicity;
B. protected version floor;
C. measured boot identity;
D. key/state binding;
E. resistance to selected local rollback attacks.

It cannot, by itself, establish:

F. globally current authority;
G. distributed uniqueness;
H. policy correctness;
I. participant closure;
J. external-effect confirmation;
K. cross-provider atomicity;
L. absence of common-mode compromise.

## Device replacement

Suppose device D1 has hardware counter C9 and is replaced by D2 with counter C0.

C0 is not automatically invalid, because D2 may be a legitimate new incarnation.

Therefore hardware counter values require:

DEVICE_ID
+ HARDWARE_INCARNATION
+ AUTHORITY_DOMAIN
+ RECOVERY_GENERATION

to distinguish replacement from rollback.

Candidate:

NEW_DEVICE != ROLLED_BACK_DEVICE.

Replacement requires explicit identity/continuity binding.

## Hardware reset/clear

A security primitive that can be reset or cleared must specify:
- who can authorize reset;
- what historical state survives;
- whether reset creates a new incarnation;
- whether prior authority is invalidated;
- how recovery evidence is generated.

Never treat:

HARDWARE_RESET => SAME_AUTHORITY

without proof.

## Hardware unavailable

If Nexo's claim depends on a hardware anti-rollback primitive and that primitive is unavailable:

HARDWARE_UNAVAILABLE => CLAIM_DEPENDENCY_UNKNOWN.

For high-consequence claims, this should normally produce HOLD/REVALIDATE/QUARANTINE rather than silently falling back to ordinary storage.

## Measured boot rollback scenario

T0 trusted image I8 measured.
T1 system rolls back to I7.
T2 measurement reports I7.

A verifier can reject I7 if policy requires I8 or higher.

But this depends on:
- trusted measurement chain;
- correct expected-value policy;
- current policy version;
- verifier integrity;
- anti-rollback semantics.

Therefore:

MEASUREMENT_VALIDITY != POLICY_CURRENTNESS.

## TPM counter versus distributed generation

A TPM counter is a local monotonic primitive.

A distributed authority generation is a protocol state.

Candidate composition:

DISTRIBUTED_GENERATION
bound to
HARDWARE_ATTESTED_INCARNATION
and
LOCAL_MONOTONIC_FLOOR.

This can make rollback harder without pretending the TPM is the distributed authority.

## Hardware-backed fence candidate

For a resource device:

1. authority issues generation G;
2. device validates authority binding;
3. device stores/advances local HWM;
4. mutation requires matching generation + incarnation;
5. device emits evidence;
6. Z1/reconciliation evaluates evidence separately.

This remains a candidate protocol, not implementation.

## TCB impact

Hardware can reduce some software rollback dependencies while adding:
- hardware vendor/firmware;
- secure boot chain;
- device identity;
- attestation verifier;
- firmware update process;
- recovery/reset authority;
- hardware availability;
- manufacturing/provisioning trust.

Therefore:

HARDWARE_ROOT_CAN_SHRINK_ONE_DEPENDENCY_AND_ADD_OTHERS.

TCB must be claim-specific.
