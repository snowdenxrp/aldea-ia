# AB104.501 — authority certificate contracts: assumptions, guarantees, input-enabledness, rejection and quarantine

## Evidence

## Nexo contract model
For each protected authority claim C, define:
`Contract_C = (Inputs, Outputs, Assumptions, Guarantees, Rejections, QuarantineConditions)`.

The contract must make the environment boundary explicit. Assumptions may include authenticated identity, current authority epoch, valid membership configuration, required freshness/fence state, and availability of required evidence. Guarantees describe what authorization outcome is permitted when assumptions hold.

## Input-enabledness
A certificate verifier must not treat every syntactically valid input as an admissible authority request. For security-sensitive inputs, unsupported/ambiguous/invalid inputs must have explicit outcomes: reject or quarantine.

Therefore:
`PARSEABLE_INPUT != AUTHORIZED_INPUT`
`UNSUPPORTED_CRITICAL_INPUT => REJECT_OR_QUARANTINE`
`MISSING_REQUIRED_ASSUMPTION => NO_AUTHORITY`

Input-enabledness must be claim-specific. Making a verifier broadly input-enabled can accidentally turn malformed or semantically unknown certificates into accepted authority.

## Rejection is observable security behavior
Rejection/quarantine should be included in the abstract observable alphabet for authority refinement. Otherwise an implementation could appear trace-compatible while changing an old rejection into an acceptance.

Candidate observable event:
`AUTHZ_EVENT = {claim, profile, epoch, decision_digest, outcome, reason_class}`
where outcome includes `ALLOW`, `DENY`, `REJECT`, `QUARANTINE`, and `UNKNOWN`.

This lets refinement check that a new profile does not replace a forbidden old outcome with `ALLOW`.

## Assumption changes
A new profile may strengthen an assumption, but this can reduce the set of environments in which the guarantee applies. That is not automatically equivalent to the old contract. Conversely, weakening an assumption while preserving the old guarantee can enlarge the authority surface and therefore requires explicit proof.

Candidate migration classification:
- same assumptions + same guarantees → `EQUIVALENT`;
- stronger assumptions + no new authority → `RESTRICTED/NOT_AUTOMATICALLY_EQUIVALENT`;
- weaker assumptions → `POTENTIAL_AUTHORITY_EXPANSION`;
- stronger guarantees with no weaker safety boundary → `STRICTER`;
- changed rejection/quarantine semantics → `SEMANTIC_CHANGE`;
- incomparable assumptions/guarantees → `INCOMPARABLE`.

## Contract-aware refinement gate
For protected claim C, promotion should require:
1. explicit input/output alphabet;
2. explicit assumptions;
3. explicit guarantees;
4. explicit rejection/quarantine behavior;
5. refinement relation checked over security-relevant traces;
6. no new ALLOW trace outside the authorized refinement relation;
7. migration epoch/profile binding;
8. adversarial counterexample search for assumption weakening and rejection-to-allow changes.

## Key result
For Nexo, rejection/quarantine must be first-class semantic outcomes, not implementation details. Otherwise certificate migration can preserve successful traces while silently weakening failure behavior.
