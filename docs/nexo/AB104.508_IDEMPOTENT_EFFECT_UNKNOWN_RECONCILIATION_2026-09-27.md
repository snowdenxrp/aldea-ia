# AB104.508 — idempotent effects, UNKNOWN outcomes, and reconciliation

## Evidence
RFC 9110 defines idempotency in terms of the intended server effect and explains why it permits safe retry after a communication failure where the client cannot know whether the first request succeeded. It also warns that non-idempotent requests should not be automatically retried unless the client has a mechanism to determine whether the original was applied. citeturn0search0turn0search2 The current Idempotency-Key Internet-Draft specifies a client-generated key used to recognize retries, requires uniqueness across different payloads, and distinguishes completed duplicate requests from concurrent requests. citeturn0search3turn0search10 A 2026 draft for agent-friendly HTTP APIs makes the same systems point more explicit for autonomous agents: side-effecting writes should support idempotency keys, and stored state must distinguish a settled result from a temporary failure. citeturn0search6

## Nexo finding
For an external side effect, transport success/failure is not equivalent to effect success/failure.

Candidate state machine:
`ABSENT → INTENT_DURABLE → DISPATCHED → UNKNOWN | APPLIED | REJECTED`

`UNKNOWN` is a first-class epistemic state, not an error synonym and not permission to retry blindly.

## Operation identity
Every protected effect should carry an immutable operation identity:
`OperationID + PayloadDigest + TargetIdentity + DecisionDigest + AuthorityEpoch + FenceToken`.

The target/effect executor must bind the idempotency record to the operation identity. Reusing an OperationID with a different payload or authority decision must be rejected.

## Retry rule
If an operation is known idempotent and the same operation identity is presented again, the executor may return the durable prior result rather than execute the effect again. RFC 9110's retry guidance provides the underlying semantic rationale. citeturn0search2

If the effect is non-idempotent and the prior outcome is UNKNOWN, Nexo must reconcile the target state before deciding whether another effect is safe. Blind retry is prohibited.

`UNKNOWN + NON_IDEMPOTENT => RECONCILE_BEFORE_RETRY`

## Durable result
A durable operation record should distinguish at least:
- `INTENT`
- `IN_FLIGHT`
- `APPLIED`
- `REJECTED`
- `UNKNOWN`
- `RECONCILED_APPLIED`
- `RECONCILED_NOT_APPLIED`
- `RECONCILIATION_UNAVAILABLE`

A temporary transport failure must not be stored as a final negative result if the external effect may already have occurred.

## Reconciliation
Reconciliation must query an authoritative target-side state or an independently verifiable effect receipt. A client timeout alone cannot establish non-application.

Candidate reconciliation contract:
`Reconcile(OperationID) -> {APPLIED, NOT_APPLIED, UNKNOWN}`

Only `NOT_APPLIED` permits a fresh execution attempt, and even then the authorization/fence state must be revalidated immediately before dispatch.

## Revocation race
If revocation occurs after the external effect was committed but before Nexo receives confirmation, the result may be `UNKNOWN` and must not be converted to `REJECTED`. Revocation can prevent future retries/effects, but it cannot retroactively erase an already committed external effect unless the target provides an explicit compensating operation.

`REVOCATION_AFTER_COMMIT != EFFECT_UNDO`
`COMPENSATION != RETROACTIVE_FENCING`

## Crash matrix
- crash before durable intent → no operation is authorized from volatile memory;
- crash after intent before dispatch → reconcile/verify no target effect, then continue only if current authorization is valid;
- crash after dispatch before response → `UNKNOWN`, then reconcile;
- crash after target commit before durable result → target reconciliation must recover the result;
- duplicate retry with same identity → return existing durable result when available;
- same OperationID with different payload/digest → reject;
- revocation before dispatch → deny/recompute;
- revocation after confirmed commit → record historical applied result; future retry denied; compensation requires separate authorization.

## Core invariants
- `TIMEOUT != NOT_APPLIED`
- `UNKNOWN != REJECTED`
- `UNKNOWN != SUCCESS`
- `NON_IDEMPOTENT_UNKNOWN => NO_BLIND_RETRY`
- `SAME_OPERATION_ID + DIFFERENT_PAYLOAD => REJECT`
- `NOT_APPLIED + CURRENT_AUTHORIZATION => MAY_RETRY`
- `REVOCATION_AFTER_COMMIT != RETROACTIVE_UNDO`
- `RECONCILIATION_UNAVAILABLE => UNKNOWN`
- `RETRY != NEW_AUTHORITY`
- `DURABLE_RESULT_MUST_BIND_OPERATION_ID_AND_PAYLOAD_DIGEST`

## Status
Research complete. This establishes a candidate external-effect contract. No implementation or formal verification performed. The remaining design gap is the exact reconciliation protocol and its trust boundary: what evidence is sufficient to conclude APPLIED versus NOT_APPLIED when the target itself is distributed or only eventually consistent.

Next exact step: AB104.509 — investigate reconciliation against eventually consistent and distributed targets, including read-after-write guarantees, receipts, monotonic operation ledgers, duplicate suppression across failover, and the point at which Nexo must remain UNKNOWN rather than infer a result.
