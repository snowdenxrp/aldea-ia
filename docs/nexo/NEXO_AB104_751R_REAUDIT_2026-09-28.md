# NEXO AB104.751R — InFlightRequests ordering and mismatch lifecycle re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct source findings

`InFlightRequests.add()` inserts each request with `addFirst()`. `completeNext(node)` removes with `pollLast()`, explicitly defining completion as oldest-first (FIFO). `lastSent(node)` observes the newest request via `peekFirst()`.

`NetworkClient.handleCompletedReceives()` asks `completeNext(source)` without consulting the response correlation ID. Correlation validation occurs only afterward in `parseResponse(...)`.

Therefore, when multiple requests are in flight to one node, source semantics show that the next receive is associated with the oldest queued request before its correlation ID is validated. A mismatching response does not get matched by correlation ID at this layer; it consumes the next FIFO in-flight entry first. This remains source-derived until executed.

## Test evidence

`NetworkClientTest.testDisconnectWithMultipleInFlights()` creates two requests to the same node, verifies distinct correlation IDs and two in-flight requests, then disconnects and verifies returned disconnected responses preserve request order and drain the in-flight count to zero. This is evidence for disconnect completion ordering, not for response-correlation validation.

Repository inspection did not find a test that injects a response with an independently chosen correlation ID while two requests are simultaneously in flight and then asserts the resulting mismatch/queue state.
