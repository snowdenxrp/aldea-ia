# Nexo AB104.571 — TOCTOU closure at final recovery activation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Evidence
etcd transactions can atomically guard writes with comparisons over key value/revision state; its STM implementation builds comparisons over the read set before committing. This is a concrete implementation pattern for rejecting a write when protected state changed after it was read. citeturn0search1turn0search14 HotStuff similarly makes voting conditional on the current lock and a valid higher-view justification; a certificate is not sufficient without the current safety predicate. citeturn0search0

## Finding
Final recovery validation has a TOCTOU window if the system performs:
READ dependency snapshot -> VALIDATE -> later COMMIT authority.
A dependency, witness epoch, continuity anchor or revocation state can change between validation and commit.

Therefore final recovery activation must be a conditional protected transition whose preconditions include the exact versions/incarnations used during validation.

## Candidate contract
RecoveryCertificate binds:
DependencySnapshotDigest, DependencyVersions, WitnessSetEpoch, AuthorityEpoch, ContinuityAnchorDigest, RecoveryGeneration, FenceRevision, StateDigest.

Final commit condition:
ACCEPT iff every protected dependency still equals the captured version/incarnation and the recovery fence is still current.
Otherwise reject and restart validation.

Conceptually:
SNAPSHOT -> VALIDATE -> FENCE/REVISION CAPTURE -> CONDITIONAL COMMIT

The authoritative store must evaluate the condition and state change atomically. A client-side comparison followed by a separate write does not close the race.

## Fence interaction
A recovery fence should prevent an older prepared recovery attempt from committing after a newer recovery epoch or revocation has superseded it. Thus the conditional commit should include both:
- dependency/version equality;
- current recovery/authority fence equality.

A stale attempt can remain valid historical evidence but cannot become current authority.

## Crash semantics
If the conditional commit succeeds, the new authority boundary is committed as one protected transition. If it fails, no new authority is granted. If the result of the commit itself is UNKNOWN, recovery must reconcile the authoritative state before retrying; it must not assume failure or success.

## Important distinction
A database CAS closes the internal state TOCTOU only when the protected decision and state transition are within the same authoritative linearization domain. It does not prove external effects, remote provider state, or physical-world outcomes.

Therefore:
CAS != GLOBAL_ATOMICITY
CAS != EXTERNAL_EFFECT_CONFIRMATION
VERSION_MATCH != WORLD_TRUTH
FENCE_MATCH != PROVIDER_ENFORCEMENT

## Nexo consequence
The final recovery gate should be modeled as a protected conditional transition over a coherent VersionSet/DependencySnapshot plus RecoveryFence. This directly connects AB104.534–AB104.541, AB104.533 and AB104.570. If any protected input changed, the prepared recovery decision expires rather than being silently reused.
