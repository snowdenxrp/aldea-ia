# Nexo AB104.456 — Concrete DKG/VSS/Proactive Protocol and Implementation Evidence

## Research question

What do concrete threshold implementations demonstrate, what remains outside their cryptographic guarantees, and what evidence can safely enter Nexo's TCB?

## Primary protocol evidence

RFC 9591 defines FROST signing but explicitly leaves key generation/configuration outside the signing protocol. It identifies two broad setup approaches: trusted dealer and DKG. Its security assumptions include secure generation/distribution of shares and corruption of fewer than the threshold number of participants. citeturn0search0turn0search8

The RFC also states that the Coordinator and signer set are chosen externally to FROST. Thus participant selection and governance remain outside the cryptographic signing protocol. citeturn0search0

FROST does not provide robustness against a participant refusing to participate; a malicious participant can cause denial of service. Misbehaving participants that produce invalid shares can be identified, but the policy for removing them is outside the protocol. citeturn0search8

## Real implementation evidence

The Zcash Foundation's frost repository implements FROST in Rust and includes:
- trusted-dealer key generation;
- DKG;
- repairable threshold scheme;
- share refresh;
- participant removal;
- multiple ciphersuites.

The repository reports that an NCC audit covered v0.6.0 of frost-core and several ciphersuites, including both trusted-dealer and DKG key generation; it states that identified issues were addressed and reviewed by NCC. The audit did not cover every component in the repository. citeturn1search0turn1search2

This is useful implementation evidence, but not evidence that the implementation is appropriate as Nexo's recovery authority. It validates only bounded claims about the inspected implementation/version and audit scope.

## Finding I — setup is outside signing

A correctly implemented threshold signing layer can still receive:
- unauthorized participants;
- stale participant configuration;
- wrong policy generation;
- compromised governance;
- incorrect recovery target.

Therefore:

SIGNATURE_LAYER_CORRECTNESS != RECOVERY_AUTHORITY_CORRECTNESS.

## Finding II — audited implementation is bounded evidence

An audit of a specific version and components does not establish:
- all future versions are secure;
- deployment configuration is secure;
- dependencies are uncompromised;
- participant governance is correct;
- recovery policy is correct;
- external effects are correct.

Candidate:

AUDIT_SCOPE = CLAIM_SCOPE.

No silent expansion.

## Finding III — DKG is a protocol, not governance

A DKG can remove a trusted dealer from the secret-generation trust boundary, but the participant set and eligibility still need an external basis.

Candidate:

DKG_SUCCESS => GROUP_KEY_GENERATION_EVIDENCE
not:
DKG_SUCCESS => NEXO_RECOVERY_AUTHORITY.

## Finding IV — VSS verifies consistency, not legitimacy

FROST's trusted-dealer appendix uses VSS commitments so participants can verify that their shares correspond to the same polynomial. This is valuable cryptographic consistency evidence. It does not establish that the dealer was authorized to establish Nexo's root. citeturn0search8

Candidate:

VSS_CONSISTENCY => SHARE_RELATION_VALID
VSS_CONSISTENCY != GOVERNANCE_LEGITIMACY.

## Finding V — refresh has a bounded claim

The Zcash Foundation implementation explicitly supports share refresh and participant removal. citeturn1search0

Refresh can establish a new share epoch under the protocol's assumptions.

It does not prove:
- old shares were never copied;
- old participants forgot secrets;
- historical signatures were valid;
- governance remained uncompromised.

Therefore:

REFRESH_EPOCH_VALID != HISTORICAL_COMPROMISE_ERASED.

## Finding VI — robustness is separate

FROST explicitly does not provide robustness against refusal/DoS. citeturn0search8

Nexo therefore must not equate:

THRESHOLD_AVAILABLE
with
THRESHOLD_ROBUST.

If recovery cannot obtain the required independent threshold, safety should hold rather than silently lower the threshold.

## Finding VII — participant selection is a protected transition

Because FROST assumes the coordinator and participants are chosen externally, Nexo must model:

ENROLL_PARTICIPANT
REMOVE_PARTICIPANT
ROTATE_PARTICIPANT
CHANGE_THRESHOLD

as protected governance transitions.

They require their own:
- authority basis;
- generation;
- dependency closure;
- evidence;
- anti-replay;
- activation semantics.

## Finding VIII — code review target

For any candidate implementation, Nexo's research audit should inspect at minimum:

1. key-generation transcript handling;
2. participant identity binding;
3. participant-set commitment;
4. threshold parameter binding;
5. version/ciphersuite binding;
6. message validation;
7. nonce lifecycle;
8. share zeroization/lifetime;
9. replay resistance;
10. state persistence/crash recovery;
11. invalid participant handling;
12. refresh/rotation semantics;
13. dependency versions;
14. test/property/fuzz coverage;
15. audit scope and unresolved findings.

## Finding IX — evidence classes

Implementation evidence should be classified:

E0 — source exists.
E1 — protocol behavior documented.
E2 — tests exercise property.
E3 — independent review/audit covers property.
E4 — deployment configuration independently verified.
E5 — runtime evidence demonstrates the property in the actual deployment.

No E0–E3 artifact should be silently promoted to E4/E5.

## Finding X — implementation evidence enters the TCB claim-specifically

For example:

FROST implementation correctly rejects malformed scalar input

could be an implementation-level claim if tested/reviewed.

It does not establish:

Nexo recovery authorization is valid.

The latter requires the entire relevant trust/authority/dependency/evidence chain.

## Real-code observation

The Zcash Foundation repository also provides a separate tools repository for DKG, trusted-dealer, coordinator and participant demonstrations, but explicitly marks those demos as not for production use. This is a useful warning that “reference/demo code exists” and “production deployment is justified” are different claims. citeturn1search1
