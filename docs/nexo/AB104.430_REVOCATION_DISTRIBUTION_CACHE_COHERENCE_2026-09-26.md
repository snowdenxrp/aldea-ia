# Nexo AB104.430 — Revocation Distribution, Cache Coherence and Authoritative Propagation

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.429 → AB104.430
Implementation: NOT PERFORMED

## Research question

How should Nexo compare push, pull, cached decisions, versioned snapshots, watch streams, quorum reads, and resource-side fencing when current revocation/authority state must propagate without silently authorizing stale state?

## Evidence

NIST IR 8587 (published September 15, 2026) states that token/assertion revocation status must propagate to associated connected systems and notes the difficulty of cutting off distributed stateless access tokens; it points to token-status and global-revocation mechanisms as possible approaches. citeturn0search0turn0search36

AWS documents that IAM control-plane changes can be read-after-write consistent while authorization in the data plane is eventually consistent, with propagation delays that can last seconds or longer. citeturn0search5

AWS also documents authorization-result caching and explicitly warns that caching can delay policy enforcement; a recent AWS architecture example quantifies that a nonzero cache TTL can allow a revoked policy to continue permitting access until the cached decision expires. citeturn0search7turn0search9

## Core finding

No distribution mechanism automatically proves current authorization.

Each mechanism trades latency, availability, bandwidth, complexity, and currentness.

Therefore:

PROPAGATION_SUCCESS != CURRENT_AUTHORITY

and:

CACHE_INTEGRITY != CACHE_CURRENTNESS.

## Distribution patterns

### D1 — push invalidation

Authority publishes revocation/generation changes to consumers.

Advantages:
- low normal detection latency;
- can reduce polling load.

Required semantics:
- authenticated source;
- ordered generations;
- anti-replay;
- gap detection;
- durable consumer state;
- recovery after disconnect.

Critical failure:

MISSED_PUSH != NO_REVOCATION.

A consumer must detect sequence gaps or otherwise re-establish authoritative state.

### D2 — pull current state

Consumer periodically or per-request reads authority state.

Advantages:
- simpler completeness story than best-effort push;
- explicit revalidation.

Risks:
- stale replica;
- partition;
- unavailable authority;
- race between read and protected effect.

Therefore:

CURRENT_READ != CURRENT_EFFECT unless the read is bound to the protected admission/effect boundary.

### D3 — cached authorization result

Fast but intrinsically introduces a staleness interval unless invalidation is guaranteed.

Candidate cache record:

DECISION_ID
CLAIM_ID
POLICY_GENERATION
AUTHORITY_GENERATION
RESOURCE_INCARNATION
DECISION_GENERATION
ISSUED_AT
MAX_STALENESS
INVALIDATION_GENERATION
STATUS.

Cache use must validate the relevant generations/currentness conditions.

### D4 — versioned snapshot

Authority publishes a snapshot with:

STATE_ROOT
GENERATION
PREDECESSOR
POLICY_VERSION
TRUST_GENERATION
ISSUED_AT
VALIDITY/FRESHNESS POLICY.

Snapshot integrity can be strongly validated.

But:

VALID_SNAPSHOT != CURRENT_SNAPSHOT.

A snapshot requires a currentness rule.

### D5 — watch/stream

Long-lived stream sends ordered state changes.

Required:
- sequence/generation;
- authenticated channel;
- replay/resume position;
- gap detection;
- snapshot fallback;
- stream incarnation;
- invalidation.

If the stream detects a gap:

CONTINUITY_UNKNOWN
→ SNAPSHOT_REVALIDATION_REQUIRED.

### D6 — quorum reads

Multiple replicas can provide stronger evidence under some failure models.

But:

REPLICA_COUNT != CURRENTNESS
and
QUORUM_COUNT != INDEPENDENCE.

If replicas share a common control plane or storage root, quorum may not provide the independence assumed by the claim.

### D7 — resource-side fencing

Resource checks the request's authority/fence generation against its own protected state.

This is the strongest candidate for preventing stale actors from producing protected mutations when the resource boundary is authoritative.

But it does not prove upstream authorization was current.

## Cache coherence

For Nexo, cache coherence should be treated as a security property when cached decisions influence protected effects.

Candidate cache states:

CURRENT
→ STALE
→ INVALIDATION_PENDING
→ REVALIDATION_REQUIRED
→ CURRENT

Also:

CURRENT
→ CONFLICTED
→ QUARANTINED

No transition:

CURRENT → CURRENT

after an unexamined generation change.

## Generation-aware cache

A cache entry should be bound to the state it evaluated.

Candidate:

CACHE_ENTRY_GENERATION == REQUIRED_AUTHORITY_GENERATION

and, where applicable:

CACHE_ENTRY_RESOURCE_INCARNATION == CURRENT_RESOURCE_INCARNATION.

A TTL alone cannot replace these bindings for immediate revocation.

## Push + pull hybrid

Strong candidate architecture:

1. push for low-latency invalidation;
2. sequence/generation tracking for gap detection;
3. pull/snapshot revalidation after gap;
4. cache invalidation;
5. resource-side fence for high-consequence effects.

This does not assume push is complete.

## Snapshot + watch hybrid

A robust stream can use:

SNAPSHOT(G)
→ WATCH FROM G
→ RECEIVE G+1...Gn.

If stream continuity breaks:

STOP_USING_INCREMENTAL_STATE
→ FETCH_NEW_SNAPSHOT
→ VERIFY_PREDECESSOR/GENERATION
→ RESUME.

This prevents silent divergence.

## Read-before-write race

Suppose:

T0 read authority G7
T1 authority advances to G8
T2 external effect is attempted using G7.

A normal read does not close this TOCTOU.

The protected effect needs:

- provider/resource fence;
- conditional state;
- or another protected linearization/equivalent mechanism.

This directly carries AB104.369–AB104.385 forward.

## Cache TTL semantics

TTL answers:

“How long may this cache entry be used under policy?”

It does not answer:

“Has authority changed?”

Therefore:

TTL_VALID != AUTHORITY_CURRENT.

A TTL can be a bounded-risk policy only when the claim explicitly permits that staleness window.

## Revocation push failure

If revocation notification fails:

NOTIFICATION_FAILED != REVOCATION_FAILED.

The authority must retain authoritative state independently of notification delivery.

Consumers should detect missed updates and revalidate.

## Versioned snapshots and rollback

A restored snapshot with generation G7 must not become current if authoritative continuity has advanced to G8.

Therefore snapshot acceptance requires continuity validation, not only cryptographic integrity.

This carries AB104.410–AB104.413 forward.

## Watch-stream replay

A replayed old update must not move state backward.

Candidate acceptance:

incoming_generation > current_generation

or, if equal:

incoming_state_root == current_state_root.

Otherwise:

CONFLICT / QUARANTINE.

## Gap detection

If expected sequence is 42 and received 44:

state 43 is unknown.

Do not infer:

43 = NO_REVOCATION.

Instead:

GAP_DETECTED
→ CURRENTNESS_UNKNOWN
→ SNAPSHOT_REVALIDATION.

## Quorum limitations

A quorum read can fail in two directions:

- stale replicas form a seemingly valid quorum;
- compromised/common-mode replicas agree on a false state.

Therefore quorum evidence must include dependency/failure-domain analysis from AB104.417–AB104.420.

## Provider-specific evidence

AWS demonstrates real-world cases where authorization data and authorization enforcement have different consistency behavior, and cached authorization decisions can continue to apply until TTL expiry. citeturn0search5turn0search9

This is evidence for the general problem, not proof that every provider behaves identically.

## Candidate high-consequence rule

If a protected effect depends on immediate revocation:

- do not rely solely on TTL;
- do not rely solely on best-effort push;
- do not treat a signed old snapshot as current;
- do not assume replica quorum equals current authority;
- prefer current authoritative validation or resource-side fencing;
- if currentness cannot be established, HOLD/REVALIDATE/QUARANTINE according to effect class.
