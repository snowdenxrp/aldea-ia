# AB104.504 — dynamic dependency closure and coherent snapshots

## Evidence
Incremental SCC algorithms maintain SCC structure as graph edges change, showing that recomputation need not always start from the full graph; however, dynamic maintenance itself is a distinct algorithmic problem with explicit update semantics. citeturn0search2turn0search4 etcd provides a stronger systems pattern for coherent state: revisions define versions of state, transactions are atomic, and watch events are ordered/atomic by revision; watch itself is not linearizable, so consumers must validate revisions. citeturn0search0 etcd's MVCC model preserves historical versions, allowing snapshots/time-travel views instead of mixing current and prior values. citeturn0search5

## Nexo finding
The dependency graph must be treated as a versioned artifact, not as a live mutable object during an authority decision.

Candidate snapshot:
`DependencySnapshot = {StateRevision, GraphDigest, VertexSetDigest, EdgeSetDigest, HyperedgeSetDigest, MembershipEpoch, TrustBasisEpoch, CheckpointRevision, FenceRevision}`.

All dependency inputs for one authority decision must be read from a coherent snapshot. A watcher may discover changes incrementally, but discovery is not authorization evidence until the snapshot is revalidated at the decision boundary.

## Incremental maintenance
Dynamic SCC maintenance is a valid optimization candidate when updates are monotonic or otherwise modeled, but its cached result must be tagged with the graph revision/digest that produced it. citeturn0search2turn0search4

Candidate rule:
`CachedClosure(GraphRevision = R) -> usable only if CurrentGraphRevision == R`.

If the graph changed, either recompute affected closure or conservatively invalidate the cached authority result. No stale SCC/common-mode/cut result may authorize a protected transition.

## Snapshot consistency
A dangerous sequence is:
`read membership(R) -> read trust basis(R+1) -> read checkpoint(R) -> compute closure`.

The resulting graph may never have existed as one coherent state.

Use one of two safe strategies:
1. atomic/coherent snapshot from an authoritative store;
2. capture versions for every dependency and validate all versions at the final authority gate.

etcd's revisioned MVCC and atomic transaction/watch semantics provide concrete evidence for the value of revision-bound state and coherent event boundaries. citeturn0search0turn0search5

## Watch limitation
A watch stream is useful for detecting that recalculation is needed, but cannot itself be treated as a linearizable authorization read. etcd explicitly requires consumers to reason about revisions because watches are not linearizable. citeturn0search0

Therefore:
`WATCH_EVENT != AUTHORITY_SNAPSHOT`
`CHANGE_DETECTED != CHANGE_VALIDATED`
`CACHED_CLOSURE != CURRENT_CLOSURE`

## Change classes
- membership/trust-basis change → invalidate all dependent authority closures;
- checkpoint change → invalidate checkpoint-dependent evidence and any derived cuts;
- fence change → invalidate authorization eligibility immediately;
- policy/profile change → invalidate semantic refinement results;
- evidence revocation → invalidate claims transitively dependent on that evidence.

The invalidation relation must be explicit and provenance-linked rather than inferred from timestamps.

## Candidate authority algorithm
`capture coherent snapshot → compute/obtain closure → bind closure digest → evaluate contracts → revalidate all dependency revisions → authorize or quarantine`.

If revalidation fails:
`STALE_OR_MIXED_SNAPSHOT => NO_AUTHORITY / RECOMPUTE`.

## Invariants
- `LIVE_GRAPH != AUTHORITY_SNAPSHOT`
- `WATCH_EVENT != LINEARIZABLE_AUTHORITY_READ`
- `CACHED_CLOSURE != CURRENT_CLOSURE`
- `MIXED_REVISIONS => NO_AUTHORITY`
- `GRAPH_DIGEST + REVISION MUST BE BOUND`
- `DEPENDENCY_CHANGE => TRANSITIVE_INVALIDATION`
- `FINAL_REVALIDATION_REQUIRED`
- `STALE_CLOSURE => RECOMPUTE_OR_QUARANTINE`
- `HISTORICAL_SNAPSHOT != CURRENT_AUTHORITY`

## Status
Research complete. Dynamic SCC maintenance is a viable optimization layer, but correctness requires revision-bound caches and final coherent-snapshot validation. No implementation or formal verification performed.
