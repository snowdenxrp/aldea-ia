# Nexo AB104.523 — Idempotency retention and negative reconciliation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
An idempotency record can close an UNKNOWN interval only while its provider-defined scope and retention semantics still cover the entire ambiguity window. Expiration of that record reopens uncertainty; it does not prove that the operation never occurred.

## Evidence
- AWS EC2 documents client-token idempotency, parameter binding, and scope; retries with the same token and parameters do not perform a further action after successful completion. The scope can be regional or zonal depending on the API.
- AWS ECS documents a concrete 24-hour client-token TTL for RunTask and different information returned for older failures, demonstrating that idempotency/retry evidence has a bounded retention scope.
- etcd preserves historical revisions but compaction removes revisions before the compact revision; therefore historical absence cannot be inferred across a compacted interval.

## Candidate rule
For an operation with ambiguity interval [t0,t1], a provider idempotency registry is sufficient for negative reconciliation only if:
1. the idempotency key is bound to the exact logical operation/request digest;
2. its scope covers the exact provider/region/target domain;
3. the registry's retention/lookup guarantee covers [t0,t1] or another authoritative mechanism covers the missing portion;
4. expiry is itself observable and unambiguous;
5. target incarnation is bound where delete/recreate is possible;
6. provider semantics define what absence of the record means.

If any condition is missing, UNKNOWN remains UNKNOWN.

## Critical distinctions
- IDEMPOTENCY_EXPIRY != PROOF_OF_NOT_APPLIED
- RECORD_ABSENCE_AFTER_EXPIRY != HISTORICAL_NONOCCURRENCE
- SAME_TOKEN != SAME_OPERATION unless request parameters and scope are bound
- TOKEN_SCOPE != GLOBAL_SCOPE
- PROVIDER_RETENTION != NEXO_RETENTION
- CURRENT_RESOURCE_ABSENCE != OPERATION_HISTORY_ABSENCE
- COMPACTION/PRUNING != NEGATIVE_EVIDENCE
- RETRY_SUCCESS != HISTORICAL_PROOF_OF_SINGLE_EXTERNAL_EFFECT unless provider semantics establish that property

## Safe reconciliation state
UNKNOWN -> IDENTIFY_OPERATION -> CHECK_PROVIDER_SCOPE -> CHECK_RETENTION_COVERAGE -> CHECK_TARGET_INCARNATION -> QUERY_AUTHORITATIVE_OPERATION_RECORD ->
  PRESENT_MATCH -> APPLIED
  PRESENT_REJECTION/NOT-APPLIED RECORD -> NOT_APPLIED
  ABSENT_WITH_COMPLETE_COVERAGE -> NOT_APPLIED
  EXPIRED/INCOMPLETE_COVERAGE -> UNKNOWN_OR_QUARANTINE

## Nexo implication
The provider capability vector must include explicit idempotency retention/expiry semantics. A capability claim such as 'supports idempotency' is incomplete without scope, retention, parameter binding, duplicate detection, and behavior after expiry.
