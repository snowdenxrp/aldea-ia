## Research question
Can a durable ATTEMPT_RECORD plus a final authority check close the gap between local authorization and the real external release? If not, what mechanism bounds it?

## Fresh research
The key distributed-systems finding is that a lease/lock at the coordinator does not by itself stop a delayed or paused old holder from issuing a later request. Fencing moves stale-owner rejection to the protected resource: the resource receives a monotonically ordered token and rejects operations carrying an older token. This is explicitly described by Martin Kleppmann's analysis and related distributed-systems literature. citeturn0search0turn0search36

A lease remains useful for liveness/takeover, but expiry alone is not a proof that an already-running client cannot continue. AWS's DynamoDB lock documentation describes lease expiry/heartbeat coordination, but that primitive alone does not establish the external stale-request exclusion property Nexo needs. citeturn0search12

## TOCTOU attack
Candidate sequence:

1. Final gate validates authority epoch E1.
2. ATTEMPT_RECORD is durably committed under E1.
3. Authority rolls over to E2.
4. Old process releases the external request carrying E1.
5. Provider accepts it because it does not validate E1.

The local records can all be internally consistent while the external effect violates NO_EFFECT_FROM_STALE_AUTHORITY.

Therefore:
**durable attempt ordering + local authority validation is insufficient to close the external TOCTOU window.**

## Mechanism comparison

### A. Lease/TTL only
- Bounds ownership duration/liveness.
- Does not prevent a paused or partitioned client from sending after expiry.
- Cannot by itself establish stale-request rejection.
- Nexo property: insufficient for strict stale-authority exclusion.

### B. Local CAS/version check only
- Can atomically validate local state and record the attempt.
- Does not control an already-issued network request or a provider that ignores the version.
- Nexo property: insufficient for external stale-request exclusion.

### C. Fencing token enforced by provider/resource
- Authority issuance produces a monotonically ordered fence/epoch.
- Every protected request carries the fence.
- The receiving resource atomically rejects a fence older than its accepted high-water mark.
- This moves the critical stale-owner check to the boundary where the external mutation is accepted.
- Nexo property: candidate mechanism for closing the stale-authority TOCTOU, subject to provider actually enforcing it and preserving its fence state across restart/failover. citeturn0search0turn0search36

### D. Conditional target/version token
- Protects against stale target state/lost updates.
- Does not necessarily encode current Nexo authority.
- Useful alongside fencing, not a substitute for authority fencing.

### E. Idempotency key
- Protects retry identity when the provider actually deduplicates the same key.
- Does not by itself reject stale authority.
- Does not prove non-execution after a lost response.

### F. Trusted intermediary/owned gateway
- If the actual provider cannot consume fencing, a Nexo-controlled intermediary can be the resource boundary that validates fence + identity before releasing downstream.
- This only shifts the boundary; the downstream call remains subject to ambiguity unless it has its own idempotency/reconciliation semantics.
- Therefore intermediary fencing is not equivalent to provider-level atomic stale-effect rejection.

## Stronger candidate protocol
For a protected external mutation:

AUTHORITY_EPOCH_E1
→ FINAL_GATE(E1, targetVersion)
→ DURABLE_ATTEMPT(E1, EffectID)
→ RELEASE_REQUEST(EffectID, E1)
→ PROVIDER_FENCE_CHECK(E1)
→ PROVIDER_MUTATION

On authority rollover:

E1 → E2

Provider/resource must reject E1 if E2 has already established a higher accepted fence for that resource. A local recovery component cannot retroactively cancel a packet already released.

## Important limitation
Fencing does not mean the system can recall an already accepted effect. It means a stale request that reaches the fenced resource can be rejected if a newer fence has already been established there.

If the provider cannot enforce the fence, the system cannot claim NO_EFFECT_FROM_STALE_AUTHORITY solely from local leases, timestamps, CAS, or durable records.

## New findings
1. The external TOCTOU is not closed by local atomicity alone.
2. The minimum candidate mechanism for stale-authority exclusion is resource-side fence enforcement or an equivalent protected-resource conditional.
3. Lease/TTL is a liveness mechanism; fencing is a safety mechanism.
4. Fencing must be bound to the exact resource/effect scope; a global epoch without recipient enforcement is only metadata.
5. The protected resource must retain enough fence state across restart/failover to reject stale requests after recovery.
6. A provider-side fence still does not prove external confirmation; it only strengthens admission/rejection safety.
7. If no provider fence exists, Nexo must downgrade the claim, require a trusted intermediary, or classify the property as UNKNOWN/HOLD.
