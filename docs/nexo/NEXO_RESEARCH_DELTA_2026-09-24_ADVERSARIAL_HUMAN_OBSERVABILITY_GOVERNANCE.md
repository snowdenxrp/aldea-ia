# NEXO RESEARCH DELTA — ADVERSARIAL, HUMAN, OBSERVABILITY, GOVERNANCE AND LONG-RUN FAILURE
Date: 2026-09-24
Status: RESEARCHED / ARCHITECTURE BLOCKED

## Purpose
This pass tests whether the future clean architecture remains complete when the environment is adversarial, telemetry is misleading, humans make mistakes, specifications are incomplete, and failures accumulate over long operation.

## External basis
NIST AI 100-2 E2025 provides a lifecycle-oriented taxonomy of adversarial ML attacks, attacker goals/capabilities and mitigations. NIST SP 800-160 treats trustworthy systems as multidisciplinary systems containing machine, physical and human components. NIST SP 800-160 Vol. 2 Rev. 1 frames resilience as anticipating, withstanding, recovering from and adapting to adverse conditions. NIST AI RMF emphasizes lifecycle risk management and multiple actors rather than a model-only view.

These sources inform research categories; they do not prove any future Nexo property.

## 1. Threat model completeness
Threat modeling must cover more than external attackers:
- malicious external actor;
- compromised dependency/provider;
- malicious or compromised operator;
- accidental operator;
- compromised privileged account;
- compromised recovery/update path;
- malicious data source;
- poisoned training/fine-tuning/evaluation data;
- adversarial input;
- prompt/instruction injection;
- compromised model/provider;
- insider collusion;
- supply-chain compromise;
- stale/replayed evidence;
- clock/time manipulation;
- network partition;
- storage corruption;
- observability compromise;
- common-mode failure;
- unknown/novel failure.

Threat identity must be separate from failure identity. A failure can be accidental, adversarial, environmental, or unknown.

## 2. Trust-boundary matrix
Every component/service/data source should be classified by:
- authority it possesses;
- capabilities it can exercise;
- data it can observe;
- effects it can cause;
- evidence it can produce;
- trust roots it depends upon;
- failure domains it shares;
- recovery/update powers;
- ability to influence policy or verification.

Critical anti-confusion rule:
CAN_OBSERVE != CAN_AUTHORIZE != CAN_EXECUTE != CAN_VERIFY.

A verifier that can alter the protected state it verifies creates a dependency/correlation that must be explicitly modeled.

## 3. Adversarial evidence
Evidence must be treated as an attack surface.

Possible attacks:
- forged evidence;
- replay;
- stale-but-authentic evidence;
- context substitution;
- target substitution;
- operation/effect mismatch;
- provenance laundering;
- compromised observer;
- correlated observers;
- evidence truncation;
- selective logging;
- clock manipulation;
- deletion of negative evidence;
- generated evidence mistaken for independent observation.

Required binding:
EVIDENCE -> EXACT CLAIM -> EXACT OPERATION/EFFECT -> TARGET -> OBSERVER -> TIME/FRESHNESS -> PROVENANCE -> DEPENDENCY CLOSURE -> POLICY/INVARIANT VERSION -> TRUST ROOT -> AUTHORITY CONTEXT.

## 4. Observability is not automatically truth
Telemetry can be:
- missing;
- delayed;
- duplicated;
- reordered;
- replayed;
- stale;
- corrupted;
- selectively filtered;
- generated by a compromised component;
- internally consistent but externally false.

Therefore:
LOGGED != OBSERVED
OBSERVED != VERIFIED
VERIFIED != TRUE IN ALL CONTEXTS.

The architecture needs an explicit epistemic path from raw observation to verified claim, with provenance and freshness.

## 5. Specification gaming / proxy failure
A capable planner can satisfy a measurable proxy while violating the actual mission.

Failure pattern:
MISSION -> SPECIFICATION -> METRIC/REWARD -> OPTIMIZATION -> LOCAL SUCCESS -> HARMFUL WORLD EFFECT.

Therefore the architecture needs independent gates around external effects, not merely optimization constraints.

Critical distinction:
GOOD SCORE != AUTHORIZED ACTION
TASK COMPLETE != MISSION COMPLETE
MODEL CONFIDENCE != WORLD CONFIRMATION.

## 6. Human failure modes
Human authority is powerful but fallible.

Model:
AUTHENTIC HUMAN INPUT != CORRECT HUMAN DECISION.

Potential failures:
- accidental approval;
- ambiguous wording;
- wrong target;
- wrong scope;
- stale instruction;
- conflicting instructions;
- social engineering;
- coercion;
- fatigue;
- automation bias;
- confirmation bias;
- misunderstanding of system state;
- approval of a preview that differs from executed effect.

Mitigations are not necessarily “more confirmation.” The architectural requirement is exact binding, scope, authority, freshness, visibility of consequential parameters, and independent verification where required.

## 7. Conflicting authority
Possible concurrent authorities:
- mission owner;
- safety authority;
- security authority;
- emergency authority;
- operator;
- update authority;
- recovery authority;
- delegated agent.

The architecture needs explicit precedence and conflict semantics.

No component should resolve an authority conflict by inventing precedence from arrival order, confidence, model preference, or local optimization.

## 8. Policy/configuration drift
Safety can change without code changing.

Examples:
- policy version changes;
- trust-root changes;
- configuration changes;
- dependency changes;
- model/provider changes;
- schema changes;
- environment changes;
- operational limits change.

Therefore assurance must bind to a versioned effective context.

Context change can invalidate prior:
- authorization;
- evidence;
- release eligibility;
- proof status;
- test applicability;
- safety claims.

## 9. Long-running operation
A system that is safe at t0 may not remain safe after:
- clock rollover;
- lease expiry;
- key expiration;
- certificate rotation;
- dependency update;
- policy update;
- model drift;
- data drift;
- accumulated state;
- resource exhaustion;
- storage growth;
- log truncation;
- backup aging;
- evidence expiration;
- operator handoff;
- forgotten delegated task.

Need periodic/triggered revalidation, not only startup validation.

Long-running invariants should identify:
- what must remain invariant;
- what may evolve;
- what invalidates the invariant;
- how invalidation is detected;
- what restricted state follows;
- how revalidation restores assurance.

## 10. Recovery can itself be adversarial
Recovery paths are high-value authority.

Threats:
- forged recovery token;
- stale checkpoint;
- malicious rollback;
- recovery into vulnerable version;
- poisoned backup;
- compromised recovery verifier;
- recovery owner collusion;
- replayed recovery state;
- recovery-induced external effect duplication.

Therefore recovery must inherit the same effect identity, authority, dependency, evidence and common-mode rules as normal operation, rather than being treated as trusted by definition.

## 11. Governance and change control
Architecture must distinguish:
- changing a normal parameter;
- changing policy;
- changing safety invariant;
- changing trust root;
- changing authority model;
- changing formal model;
- changing evidence semantics;
- changing recovery semantics.

A change that alters the meaning of a safety property cannot be treated as an ordinary configuration update.

Need:
change identity, proposer, authority, rationale, impact analysis, affected claims, dependency closure, verification plan, migration/rollback plan, effective version and durable record.

## 12. Failure accumulation and hidden debt
A long-lived system accumulates:
- obsolete evidence;
- orphaned capabilities;
- stale delegates;
- unused credentials;
- old schemas;
- legacy endpoints;
- dead workers;
- unreconciled effects;
- unverified migrations;
- forgotten recovery artifacts.

“Nothing currently failing” does not imply lifecycle cleanliness.

Periodic integrity/reconciliation audits are therefore architectural functions, not optional maintenance.

## 13. Unknown-state persistence
Unknown must be a durable epistemic state where ambiguity cannot safely disappear.

Examples:
- external operation outcome unknown;
- observer unavailable;
- dependency status unknown;
- authority status unknown;
- migration status unknown;
- recovery status unknown.

Restart must restore UNKNOWN, not convert it to ABSENT/FAILED/SUCCESS.

This reinforces the existing Nexo rule:
TIMEOUT/CRASH/PARTITION != NO EFFECT.

## 14. Cross-domain attack chains
Threats must be composed, not analyzed only individually.

Example chain:
compromised dependency -> altered telemetry -> false verification -> stale authority -> external effect -> recovery -> malicious rollback.

A property that survives each single failure independently may still fail under composition.

Threat analysis therefore needs attack-chain scenarios across:
identity + authority + dependency + evidence + execution + recovery + update.

## 15. New invariants
A-01: Trust classification is explicit for every component participating in a critical claim.
A-02: Observation authority, authorization authority, execution authority and verification authority remain distinct unless an explicit reviewed exception exists.
A-03: Critical evidence is bound to exact claim/effect/target/context and freshness.
A-04: Authentic telemetry is not automatically truthful telemetry.
A-05: Policy/configuration/model/dependency changes can invalidate prior assurance.
A-06: Proxy/metric success cannot authorize an external effect by itself.
A-07: Human approval cannot exceed the authenticated scope and current authority context.
A-08: Authority conflicts have explicit precedence/hold semantics.
A-09: Long-running systems periodically or trigger-wise revalidate assumptions that can age.
A-10: Recovery paths are subject to security, authority, dependency and evidence controls.
A-11: Unknown external-effect state survives restart until reconciled.
A-12: Cross-domain failure chains are evaluated, not just isolated component failures.
A-13: Governance changes that alter safety meaning require stronger change control than ordinary configuration.
A-14: Lifecycle cleanup detects orphaned authority, stale evidence, unreconciled effects and obsolete recovery/update paths.

## 16. Research status
This pass strengthens the previously identified holes around adversarial behavior, observability, humans, specification completeness, long-running operation and governance.

Still explicitly OPEN:

Architecture remains BLOCKED. The correct next activity is to consolidate these research deltas into a single canonical completeness/distillation ledger before designing the clean architecture.
