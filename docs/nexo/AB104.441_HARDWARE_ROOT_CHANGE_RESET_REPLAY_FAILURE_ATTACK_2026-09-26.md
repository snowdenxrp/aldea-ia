# Nexo AB104.441 — Hardware Root Change, Reset, Replay and Failure Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.440 → AB104.441
Implementation: NOT PERFORMED

## Research question

Can Nexo preserve continuity when its hardware root changes, resets, becomes unavailable, or produces replayable attestation evidence?

## Current external evidence

TCG currently lists TPM 2.0 Library Specification Version 185 (March 2026). The TPM specification family provides hardware-rooted authorization, protected storage, and NV mechanisms, but Nexo must bind those primitives to its own authority/incarnation semantics. citeturn0search8turn0search16

NIST SP 800-193 treats protection, detection, and secure recovery as separate firmware-resiliency functions and explicitly discusses rollback, authenticated updates, manual recovery, and automatic recovery. citeturn0search0turn0search48

NIST's replay-resistance guidance distinguishes authenticated messages from freshness/replay resistance; a previously valid authentication artifact can be replayed unless freshness/challenge/timeliness is part of the protocol. citeturn0search15

Android KeyMint explicitly exposes rollback-resistance as a separate key authorization property, while Android attestation also binds device information to hardware-backed secrets. This demonstrates that key authenticity, device identity, and rollback resistance are separate semantics. citeturn0search6turn0search10

## Core finding

A hardware root is not a permanent identity of the Nexo authority.

The safe abstraction is:

HARDWARE_ROOT
→ HARDWARE_INCARNATION
→ ATTESTATION_EVIDENCE
→ APPRAISAL
→ NEXO_AUTHORITY_BINDING.

Therefore:

HARDWARE_ID != AUTHORITY_ID
HARDWARE_INCARNATION != AUTHORITY_GENERATION
ATTESTATION_VALID != ATTESTATION_CURRENT.

## Attack H1 — device replacement

D1 has:
- hardware identity H1;
- authority incarnation A7;
- generation G42.

D1 is replaced by D2:
- hardware identity H2;
- local counter C0.

D2 must not inherit A7 merely because an operator says it is the replacement.

Candidate transition:

D1/A7/G42
→ REPLACEMENT_AUTHORIZED
→ D2/H2 VERIFIED
→ NEW_HARDWARE_INCARNATION
→ CONTINUITY_RECONCILIATION
→ NEW_RECOVERY_GENERATION
→ EXPLICIT_RELEASE.

A replacement is a continuity event, not an ordinary restart.

## Attack H2 — TPM reset/clear

A reset or clear can destroy local protected state.

Nexo must distinguish:

RESET_WITH_CONTINUITY_PROOF
vs
RESET_WITHOUT_CONTINUITY_PROOF.

If continuity cannot be independently reconstructed:

RESET_LOSES_REQUIRED_STATE
=> CURRENT_AUTHORITY = UNKNOWN.

Do not silently reuse the previous authority generation.

## Attack H3 — firmware downgrade

NIST SP 800-193 explicitly treats rollback as a separate concern from authenticating the update. citeturn0search48

Therefore:

SIGNED_OLD_FIRMWARE != SAFE_CURRENT_FIRMWARE.

If rollback protection is part of a Nexo claim, downgrade below the protected version floor invalidates the claim until revalidation/recovery.

## Attack H4 — replayed attestation

An attacker captures a previously valid attestation:
A(G41, image=I8, device=H1).

Later Nexo requires G42.

Replay of A(G41) must fail freshness/current-generation requirements.

Candidate protected fields:
- challenge/nonce;
- authority generation;
- hardware incarnation;
- measurement digest;
- policy/trust generation;
- issuance/freshness metadata;
- verifier generation.

NIST's replay-resistance guidance supports treating freshness as an explicit property rather than assuming an authenticated old message is fresh. citeturn0search15

## Attack H5 — compromised firmware

Valid hardware attestation can establish that measured software matches the expected measurement.

It does not prove that the software is semantically correct.

Therefore:

EXPECTED_MEASUREMENT_MATCH != APPLICATION_CORRECTNESS.

If firmware compromise is suspected:
- freeze affected authority;
- invalidate affected attestation generation;
- determine dependency closure;
- identify keys/credentials exposed by the compromised environment;
- reconstruct affected effects;
- establish a new trusted image/generation;
- re-attest;
- revalidate authority.

## Attack H6 — verifier rollback

Even perfect hardware evidence becomes dangerous if the verifier runs an older policy/verification implementation.

Candidate:
VERIFIER_GENERATION < REQUIRED_VERIFIER_GENERATION
=> ATTESTATION_APPRAISAL_NOT_CURRENT.

This extends AB104.390–AB104.400:
evidence validity depends on verifier generation and policy, not just evidence signature.

## Attack H7 — hardware failure

If hardware cannot prove a required property:

HARDWARE_UNAVAILABLE
=> DEPENDENCY_UNKNOWN.

Safe fallback depends on the claim.

For high-consequence anti-rollback claims:
no hardware + no independent continuity proof
=> HOLD / QUARANTINE.

A weaker fallback must be explicitly modeled as a different assurance state, never silently treated as equivalent.

## Attack H8 — cloned hardware state

A disk image containing Nexo state is copied to D2.

If D2's hardware identity differs, the old authority state cannot automatically be reused.

Candidate binding:

STATE_ROOT
+ AUTHORITY_INCARNATION
+ HARDWARE_INCARNATION
+ RECOVERY_GENERATION.

This blocks the false equivalence:

CLONED_STATE == SAME_AUTHORITY.

## Attack H9 — hardware counter wrap/reuse

A finite counter eventually has a boundary.

If a generation can repeat under the same identity/incarnation:

OLD_GENERATION == NEW_GENERATION

may become possible.

Therefore counter width alone is insufficient. Nexo needs explicit:
- no-reuse horizon;
- epoch/incarnation;
- rollover procedure;
- recovery semantics.

## Attack H10 — physical recovery bypass

NIST SP 800-193 notes that secure local rollback/update mechanisms can rely on unambiguous physical authorization, but also warns that physical/rogue-administrator paths remain security considerations. citeturn0search48

For Nexo, physical recovery should create an explicit recovery event rather than silently restoring ordinary authority.

Candidate:
PHYSICAL_RECOVERY
=> RECOVERY_GENERATION++
=> OLD_AUTHORITY_REQUIRES_REVALIDATION.

## Attack H11 — attestation key replacement

Attestation key rotation does not necessarily mean platform replacement.

Conversely, keeping the same attestation key does not prove that application state is unchanged.

Therefore:
KEY_GENERATION != PLATFORM_INCARNATION.

Key lifecycle must be represented separately.

## Attack H12 — verifier trust-root rollback

Verifier trusts key generation K9, then is restored to K8.

A previously revoked trust root may become accepted again.

Candidate:
TRUST_ROOT_GENERATION_ROLLBACK
=> VERIFIER_QUARANTINED
until continuity is independently established.

## Attack H13 — hardware root unavailable during recovery

Recovery cannot grant itself authority merely because hardware is unavailable.

Candidate:
RECOVERY_WITHOUT_REQUIRED_ROOT
=> QUARANTINED / LIMITED_RECOVERY_ONLY.

The recovery subsystem may gather evidence and prepare reconstruction, but release requires an explicit trusted basis.

## Attack H14 — hardware replacement with stale cloud state

D2 attests correctly, but the remote authority store is stale.

Hardware freshness does not repair remote-state staleness.

Therefore:

HARDWARE_FRESHNESS != DISTRIBUTED_STATE_CURRENTNESS.

Both must be evaluated.

## Critical distinction

The hardware root should establish a bounded primitive:

LOCAL_NONROLLBACKABLE_STATE

not:

GLOBAL_CURRENT_AUTHORITY.

This keeps hardware below Z1 rather than turning hardware state into an implicit universal authority source.
