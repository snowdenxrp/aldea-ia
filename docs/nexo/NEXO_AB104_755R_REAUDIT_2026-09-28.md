# NEXO AB104.755R — SocketServer/production receive lifecycle re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct findings

Production `Selector.poll()` explicitly documents and implements the client-side lifecycle: completed sends/receives/connections/disconnections are cleared at the beginning of each poll and repopulated during that poll. It also documents that at most one completed receive is added per channel per poll, preserving per-channel request ordering.

This confirms that a NetworkClient-side parse exception does not cause the completed receive to be replayed by the same selector state indefinitely; the completed-receive container is reset on the next selector poll. This remains source-derived because the mismatch scenario itself was not executed.

The inspected `SocketServer.Processor` owns a selector per processor thread and maintains response/inflight structures, but the exact explicit `clearCompletedReceives()` processing site was not established from the inspected excerpt. Therefore we do not promote the earlier generic SocketServer-clearing claim beyond what the current source evidence establishes.
