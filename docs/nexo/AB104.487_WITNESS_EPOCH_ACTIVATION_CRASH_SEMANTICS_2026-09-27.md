# AB104.487 — witness-epoch activation atomicity and crash semantics

## Evidence
RFC 9162 defines consistency proofs as evidence that a later Merkle tree extends an earlier tree; this establishes history continuity, not atomic governance activation. citeturn0search0 RATS separates evidence appraisal from the relying party's application-specific authorization decision, so validated evidence must still pass the Nexo authorization transition. citeturn0search1

ZooKeeper provides a concrete distributed-systems pattern: proposals receive a total-order transaction ID containing an epoch and counter, and a proposal is committed only after quorum acknowledgement with persistent recording. citeturn0search2 etcd similarly supports atomic compare-and-swap transactions over revisions. citeturn0search3turn0search4 These are implementation evidence for useful primitives, not proof that Nexo should adopt either system.

## Candidate activation protocol

A witness epoch transition should have a durable linearization point:

`OLD_ACTIVE → TRANSITION_PREPARED → OLD_FENCED + NEW_VALIDATED → ACTIVATION_COMMITTED → NEW_ACTIVE`

The activation record should bind at minimum:
`NewEpochID + ParentEpochDigest + PreviousAcceptedCheckpoint + NewWitnessSet + Threshold + TrustBasis + PolicyVersion + ActivationRevision`.

Before `ACTIVATION_COMMITTED`, the new epoch may be validated but must not authorize protected recovery. After commitment, readers must reject the old epoch for new authorization even if an old replica is still serving stale state.

## Crash matrix

- Crash before PREPARED durable: no transition may be inferred.
- PREPARED durable, before OLD_FENCED: recovery resumes validation; no new authorization.
- OLD_FENCED durable, NEW_VALIDATED absent: remain fenced/quarantined; do not reactivate old authority automatically.
- NEW_VALIDATED durable, ACTIVATION_COMMITTED absent: validated candidate remains non-authoritative.
- ACTIVATION_COMMITTED durable, process crashes before acknowledgement: recover NEW_ACTIVE from durable state; do not roll back to OLD_ACTIVE merely because the acknowledgement was lost.
- Conflicting durable activation records: quarantine; never choose by wall-clock time alone.

## Key invariant

`VALIDATED != ACTIVE`
`FENCED != DELETED`
`ACTIVATION_COMMITTED != EXTERNAL_EFFECT_CONFIRMATION`
`CRASH_AFTER_COMMIT != ROLLBACK_TO_OLD_EPOCH`
`STALE_REPLICA != CURRENT_AUTHORITY`

The final activation must be linearizable/consensus-protected within the authoritative store if concurrent recovery decisions are possible. The exact storage/consensus mechanism remains open.

## Important boundary

The transparency checkpoint continuity proof answers whether the new history extends the accepted history. It does not by itself prove that the new witness set is independent, that its governance transition is authorized, or that an external effect occurred. Those properties require separate evidence contracts.
