# NEXO AB104.747R — OFLE protocol-version boundary re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct findings

### MessageTest
`testOffsetForLeaderEpochVersions()` is specifically OFLE, but it tests the REQUEST message. It checks round-trip behavior across versions 0..2 and version-3+ transitions involving current_leader_epoch and replica_id.

It is not a dedicated OFLE response-version test.

### RequestResponseTest.testSerialization()
The generic test loops over every ApiKeys value and every supported version, calling getRequest/checkRequest/checkErrorResponse/checkResponse.

Important OFLE-specific detail:
- getRequest(OFFSET_FOR_LEADER_EPOCH, version) calls createLeaderEpochRequestForReplica(1) and does NOT pass the loop version into that factory.
- createLeaderEpochRequestForReplica uses OffsetsForLeaderEpochRequest.Builder.forFollower(...), whose builder is explicitly constrained to version 4.
- getResponse(OFFSET_FOR_LEADER_EPOCH, version) calls createLeaderEpochResponse(), which constructs response data without taking the loop version.

Therefore the generic all-API loop must NOT be interpreted as a dedicated OFLE request/response version matrix merely because it iterates version values. The OFLE fixture itself is not version-parameterized in the same way as APIs whose factories receive the version.

### Protocol evidence
Kafka protocol documentation distinguishes OFLE response versions structurally: v0 has error/partition/end_offset; v1 adds leader_epoch; v2 adds throttle_time_ms, with later protocol evolution. This confirms response-version boundaries are semantically meaningful, so a generic fixture not parameterized by version is insufficient as dedicated version-boundary evidence.
