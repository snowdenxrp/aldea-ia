# Nexo AB104.438 — Continuity Anchor Adversarial Attack

## Research question

Can a continuity anchor safely detect rollback, equivocation, stale state, compromise, loss, or split-brain without silently becoming an unbounded hidden authority?

## External evidence

RFC 9162 shows that append-only Merkle consistency proofs can establish that a newer log is a superset of an older log, but also explicitly warns that a misbehaving log can present inconsistent views to different clients; cross-observer auditing is therefore relevant. citeturn0search0

RFC 9334 separates Evidence, Verifier appraisal, and Relying Party authorization. It also states that freshness is policy-dependent and that state can change immediately after evidence generation. citeturn0search2

in-toto demonstrates a signed, linked evidence chain for ordered supply-chain steps, but its own security audit documents a layout-replay limitation: valid older metadata can be replayed unless an additional freshness/anti-replay mechanism is used. citeturn0search3turn0search4

## Core finding

A continuity anchor can prove a relationship between states without necessarily proving that the anchor itself is the current authority.

Therefore:

ANCHOR_INTEGRITY != ANCHOR_CURRENTNESS
ANCHOR_CONSISTENCY != AUTHORITY
SIGNED_ANCHOR != CURRENT_AUTHORITY.

## Attack A1 — stale anchor

Primary state = G8.
Anchor = G7.

A valid signature on G7 does not make G7 current.

Required response:
STALE_ANCHOR => HOLD / RECONCILE / QUARANTINE.

## Attack A2 — primary rollback

Primary restores G7 while anchor retains G8.

Required:
RESTORED_G7 < ANCHOR_G8 => RESTORE_NOT_CURRENT.

The system must reconcile missing G8+ decisions/effects before release.

## Attack A3 — anchor rollback

Primary is G8 but anchor itself is restored to G7.

If the primary trusts the restored anchor blindly, rollback succeeds.

Therefore the anchor needs its own continuity protection or an independent witness/authority.

## Attack A4 — equivocation

Anchor presents root R8a to observer A and R8b to observer B for the same protected generation.

Two valid signatures do not resolve the conflict.

RFC 9162's CT model demonstrates the analogous problem: a log can present inconsistent views, and consistency/auditing mechanisms are needed to detect this. citeturn0search0

Candidate:
SAME_GENERATION + DIFFERENT_ROOT => EQUIVOCATION_CANDIDATE.

Response:
freeze affected authority, preserve both proofs, compare predecessor chains, determine affected claims/effects, then recover under explicit governance/policy.

## Attack A5 — lost anchor

Anchor becomes unavailable.

Unavailability must not automatically become “current.”

For high-consequence effects:
ANCHOR_UNAVAILABLE => CURRENTNESS_UNKNOWN
unless another independently valid continuity mechanism satisfies the claim.

## Attack A6 — compromised anchor key

Signature remains cryptographically valid after key compromise if old signatures are checked only for authenticity.

Therefore:
SIGNATURE_VALIDITY != CURRENT_TRUST.

Key/trust generation and compromise interval must enter dependency closure.

Affected historical evidence may remain useful for reconstruction but should not automatically remain admissible for new authority decisions.

## Attack A7 — forked anchors

Two anchors evolve independently from the same predecessor.

A1: G8/R8a
A2: G8/R8b

Generation equality is insufficient.

Candidate uniqueness property:
ONE_CURRENT_CONTINUITY_ROOT_PER_AUTHORITY_DOMAIN.

If uniqueness cannot be established:
DISPUTED / QUARANTINED.

## Attack A8 — witness outage

Independent witness unavailable.

Do not silently lower quorum requirements.

Witness-set and threshold changes are protected state and require a new admission boundary.

This carries AB104.415–AB104.417 forward.

## Attack A9 — replayed old anchor

A valid historical anchor is replayed after newer authority exists.

RFC 9334's freshness model supports treating freshness as a separate appraisal property rather than assuming signature validity implies currentness. citeturn0search2

Candidate:
HISTORICAL_ANCHOR != CURRENT_ANCHOR.

## Attack A10 — anchor says current, primary disagrees

Primary state root = R9.
Anchor says R8.

Neither should silently overwrite the other.

Result:
STATE_DISPUTE
→ freeze security-critical transitions
→ collect independent evidence
→ reconstruct divergence
→ reconcile external effects
→ establish explicit recovery generation.

## Attack A11 — primary says current, anchor disagrees

Same treatment.

The anchor is evidence for continuity, not an automatic replacement authority.

## Attack A12 — malicious freshness manipulation

A timestamp says anchor is fresh, but its generation is old.

Therefore:
FRESH_TIMESTAMP != CURRENT_STATE.

Generation/predecessor continuity must be checked in addition to time.

## Attack A13 — anchor compromise during recovery

Recovery begins using anchor G8.
During recovery, anchor trust generation changes to G9.

The old recovery evaluation cannot silently commit under G9.

Candidate:
TRUST_GENERATION_CHANGE => STALE_RECOVERY_EVALUATION.

This follows the protected-generation race model from AB104.414.

## Attack A14 — anchor truncation

Historical anchor records are compacted or deleted.

This is acceptable only if the retained commitment preserves the continuity property required by the claim.

Therefore:
COMPACTION_REQUIRES_CONTINUITY_PRESERVATION.

## Attack A15 — anchor dependency recursion

Anchor depends on the same storage, key, deployment, policy, or recovery path it is supposed to independently validate.

Then its apparent independence collapses.

Candidate:
ANCHOR_DEPENDENCY_OVERLAP => INDEPENDENCE_REDUCED / CLAIM_REVALIDATION.
