# NEXO — AB104.370 — Authority-change timeline adversarial analysis

Date: 2026-09-26
Status: RESEARCH / DESIGN EVIDENCE ONLY
Implementation: NOT PERFORMED. No V21. No formal proof. No runtime/deployment claim.

## Objective

Continue exactly from AB104.369. Enumerate adversarial authority changes across:

PREPARE -> FINAL_GATE -> LINEARIZE -> EXTERNAL_ATTEMPT

and classify the resulting state as REJECTED, HOLD/REVALIDATE, or UNKNOWN.

## Evidence used

RFC 7232 establishes a useful state-precondition analogy: a state-changing conditional request is evaluated by the origin server before the requested method is applied, and a false If-Match condition prevents application of the method, except for the narrow already-succeeded duplicate case. This supports the ordering principle for target-state preconditions, but does not prove Nexo authority semantics.

Chubby (Burrows, OSDI 2006) documents an engineering pattern directly relevant to stale/delayed requests: a lock acquisition count/sequencer can be carried to the protected server, which rejects a request if the sequence is no longer valid. The paper explicitly describes the delayed-packet problem and the need for the recipient resource to test the sequencer. This supports resource-side fencing as an evidence-backed design pattern, not as a proof of Nexo correctness.

## Core adversarial timeline

### T0 — PREPARE

Operation records:
- AuthorityEpoch/fence E
- required authority scope/state S
- target VersionSet V
- operation/effect identity O
- dependency/incarnation set D

At PREPARE, authority validity is only an observation. It is not yet permission to mutate.

If authority is already revoked/unknown/narrower than required:
=> REJECTED or HOLD/REVALIDATE.
No protected mutation.

### T1 — authority revocation before FINAL_GATE

Prepared E becomes stale before the operation reaches the protected final gate.

=> REJECTED.

The prepared artifact does not retain authority merely because it was valid at PREPARE.

### T2 — scope narrowing before FINAL_GATE

AuthorityEpoch may be unchanged while the required scope S is no longer sufficient.

=> REJECTED if the authoritative scope state is known and insufficient.
=> HOLD/REVALIDATE if current scope cannot be established.

Therefore AuthorityEpoch alone is NOT yet proven sufficient. Scope/policy state must participate in the final authorization predicate where scope can change independently.

### T3 — authority epoch rollover before FINAL_GATE

Expected E != current E.

=> REJECTED.

Retry is a new authorization evaluation. It must not inherit the stale authorization merely because O is the same operation identity.

### T4 — recovery ownership changes before FINAL_GATE

The operation was prepared under owner A, but recovery ownership/fence now belongs to B.

=> REJECTED or HOLD/REVALIDATE, depending on whether the new authoritative ownership is known.

The old owner cannot regain authority by replaying its prepared artifact.

### T5 — authority changes during FINAL_GATE

The final gate must evaluate authority generation/scope and target VersionSet as one protected predicate at the authoritative ordering point.

If the authority change linearizes first:
=> REJECTED.

If the operation's protected transition linearizes first:
=> the local mutation is authorized under E at that linearization point. Later revocation does not retroactively erase the local mutation.

This removes the PREPARE/FINAL_GATE TOCTOU for the protected local mutation only if both predicates and the mutation truly share the same authoritative linearization semantics.

### T6 — target changes during FINAL_GATE

If target VersionSet changes before the operation's linearization point:
=> REJECTED.

If target state becomes UNKNOWN:
=> HOLD/REVALIDATE or UNKNOWN according to whether the protected store can establish whether the transition committed.

Authority validity does not compensate for unknown target state.

### T7 — LINEARIZE succeeds; authority is revoked immediately afterward

The local protected transition already linearized under E.

=> Local transition remains committed under its defined semantics.
=> Do NOT retroactively classify it as never authorized.
=> Any subsequent external effect requires a separate authorization/fence decision.

This is a critical boundary: revocation after local linearization is not equivalent to cancellation of an already committed local state transition.

### T8 — authority revokes after LINEARIZE but before EXTERNAL_ATTEMPT

The local state is committed, but the external effect has not yet been attempted.

Without an external fence/authorization check enforced at the effect resource:

=> external actuation MUST NOT be treated as automatically authorized by the old local commit.
=> HOLD/REVALIDATE before attempting the effect.

If the provider/resource can enforce E or an equivalent fence at the actual effect boundary:
=> the stale attempt can be rejected by the protected resource.

If the provider cannot enforce freshness and the design still sends the effect:
=> the desired stale-effect safety property is NOT established.

### T9 — stale external request is already in flight when authority is revoked

Client-side revocation cannot by itself prove that an already-sent request did not arrive or execute.

Possible states:
- provider/resource rejects stale fence => REJECTED;
- provider confirms cancellation before execution, with reliable semantics => REJECTED/CANCELLED under the provider contract;
- outcome cannot be established => UNKNOWN;
- provider confirms an effect occurred => EXTERNAL_CONFIRMED, followed by reconciliation if authority had already changed.

No assumption of instantaneous remote cancellation is allowed.

Chubby's sequencer pattern specifically addresses delayed/reordered requests by requiring the receiving resource to reject a stale sequencer. This is the relevant defense boundary.

### T10 — crash after LINEARIZE, before EXTERNAL_ATTEMPT

Local durable state says the protected transition committed, but there is no evidence yet that the external effect was attempted.

=> On recovery, do not infer external success.
=> EXTERNAL_ATTEMPTED remains unproven.
=> Reconcile from durable intent/effect identity and external observation.

If external effect identity cannot distinguish a prior attempt:
=> outcome may remain UNKNOWN.

### T11 — crash during/after EXTERNAL_ATTEMPT with no response

The request may have reached the provider even though the client has no acknowledgement.

=> UNKNOWN, not REJECTED and not CONFIRMED.

Recovery must reconcile using stable effect identity, provider state, independent observation, or other evidence defined by the effect contract.

Retrying creates a new ATTEMPT, not automatically a new external effect. Idempotency/effect identity must be enforced by the relevant resource if duplicate suppression is required.

### T12 — retry after stale authority

A retry using the old E:

=> REJECTED.

A retry that obtains a new authority generation and re-evaluates all required target/dependency versions:

=> potentially admissible, subject to the complete final predicate.

The retry must not inherit a stale PREPARE authorization.

## Adversarial matrix

| Interleaving | Local protected transition | External effect | Classification |
|---|---|---|---|
| revoke before FINAL_GATE | not allowed | none | REJECTED |
| scope narrows before FINAL_GATE | not allowed if known | none | REJECTED |
| scope currentness unknown | not allowed | none | HOLD/REVALIDATE |
| epoch rollover before FINAL_GATE | not allowed | none | REJECTED |
| recovery owner changes before FINAL_GATE | not allowed by old owner | none | REJECTED/HOLD |
| authority revokes first at frontier | not committed | none | REJECTED |
| operation linearizes first, revocation second | committed | not yet authorized externally | local COMMITTED |
| revocation after local commit, before effect | committed | not automatically permitted | HOLD/REVALIDATE |
| stale in-flight request rejected by resource fence | committed | no effect | REJECTED |
| in-flight request outcome unknowable | committed | unknown | UNKNOWN |
| external effect confirmed after revocation | committed | effect exists | CONFIRMED + RECONCILIATION |
| crash after local commit, before attempt | committed | attempt unproven | HOLD/RECONCILE |
| crash during/after external attempt, no response | committed | unknown | UNKNOWN |
| retry with stale epoch | no new commit | no new effect | REJECTED |
| retry with new epoch + fresh versions | conditional | conditional | REVALIDATE/possibly admissible |

## Remaining TOCTOU windows

### Closed by the AB104.369 candidate frontier

The specific window:

read authority -> later target-only CAS

is eliminated only when authority freshness, target CAS, and the protected mutation share one authoritative linearization point or equivalent fencing semantics.

### Still open after local LINEARIZE

A new semantic boundary exists:

LOCAL_LINEARIZATION -> EXTERNAL_ATTEMPT

Local atomicity does not make this boundary atomic with the external world.

Therefore the remaining safety question is not simply another CAS problem. It is an external-effect protocol question requiring one or more of:
- provider-side fencing;
- stable effect identity/idempotency;
- provider conditional authorization;
- durable effect intent;
- reconciliation;
- explicit UNKNOWN state;
- compensation/reversal as a new protected effect.

### New finding

AuthorityEpoch is necessary evidence for freshness but has not been shown sufficient by itself.

At minimum, the final protected authorization predicate may require:

AUTHORITY_EPOCH
+ REQUIRED_SCOPE/POLICY_VERSION
+ TARGET_VERSIONSET
+ DEPENDENCY/INCARNATION SET
+ OPERATION/EFFECT IDENTITY
+ RECOVERY OWNERSHIP/FENCE where applicable.

Whether all of these can share one protected linearization domain remains OPEN.

## Candidate invariants strengthened

1. NO_EFFECT_FROM_STALE_AUTHORITY
A protected mutation cannot linearize unless the required authority generation and scope are valid at its authoritative linearization point.

2. NO_ACCEPTED_EXTERNAL_EFFECT_FROM_STALE_FENCE
An external resource must reject an effect carrying a stale fence/epoch if the design claims stale-effect exclusion.

3. NO_INFERENCE_FROM_MISSING_ACK
Missing provider acknowledgement does not establish non-execution.

4. RETRY_IS_NOT_EFFECT_IDENTITY
A retry is a new attempt. It may map to the same logical effect only through an explicit stable effect identity/idempotency contract.

5. REVOCATION_IS_NOT_RETROACTIVE
Revocation after a linearized local transition does not erase that transition; later external effects must be separately authorized.

## Open questions after AB104.370

1. Can AuthorityEpoch + ScopeVersion + PolicyBaseline be represented as one immutable authorization generation, or must they remain separate dimensions?
2. What exact semantics are required when authority changes across multiple protected stores with no common linearization domain?
3. Which external effect classes require provider-side fencing versus reconciliation-only semantics?
4. How is a delayed request treated when the provider supports idempotency but not fencing?
5. What evidence is sufficient to move UNKNOWN -> CONFIRMED or UNKNOWN -> REJECTED?
6. How does recovery ownership interact with an already prepared effect and an in-flight effect?
7. Can the complete protected predicate be modeled without creating an impractically large transaction/TCB?
