# Nexo AB104.544 — Transactional outbox relay failure modes

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A transactional outbox reliably preserves committed intent, but the relay boundary is normally at-least-once. A relay crash after external publication and before durable relay acknowledgement causes replay. Therefore duplicate suppression must be bound to a stable event/operation identity at the receiving boundary. Ordering also has a defined scope; parallel relays can preserve per-key order only when partitioning and routing are designed for it.

## Evidence
Microsoft's 2026 Cosmos DB outbox sample explicitly uses a change feed with at-least-once delivery and idempotent consumers that deduplicate by event ID. The transactional outbox pattern literature documents the relay crash window after publish-before-recording-success and requires idempotent consumers. Debezium's outbox router uses an event key specifically to preserve ordering in Kafka partitions. citeturn0search0turn0search1turn0search5

## Relay failure matrix
1. Crash before reading outbox row: row remains durable and eligible.
2. Crash after claiming row, before publish: claim must expire/recover; row remains deliverable.
3. Publish succeeds, ACK lost: outcome UNKNOWN; retry may duplicate.
4. Publish succeeds, relay records success: normal completion.
5. Relay records success before publish: unsafe unless the broker and durable relay state share a transaction; otherwise creates loss.
6. Consumer receives duplicate: consumer must recognize the same EventID/OperationID and make the effect idempotent.

## Candidate relay state
OUTBOX_DURABLE -> RELAY_CLAIMED -> DISPATCH_ATTEMPTED -> ACKNOWLEDGED -> RELAY_COMPLETED

Exceptions:
RELAY_CLAIM_UNKNOWN, DISPATCH_UNKNOWN, REPLAY_REQUIRED, QUARANTINED.

The relay must never turn DISPATCH_UNKNOWN into NOT_SENT solely because no ACK was observed.

## Stable identity
The outbox record should carry a stable identity sufficient to bind the downstream operation:
OperationID, EffectID/EventID, RequestDigest, TargetIdentity, TargetIncarnation, AuthorityEpoch, FenceRevision, ProviderScope, ordering key, and schema/profile version where required.

A retry of the same logical operation reuses the same identity. A genuinely new operation gets a new identity.

## Ordering
Ordering should be stated as a property with scope, not as a global assumption:
- per aggregate/resource key may be preserved by deterministic partitioning;
- unrelated keys need not have a total order;
- multiple relay workers can reorder rows unless the partitioning/coordination protocol prevents it;
- a late retry must not silently overtake a newer operation when the target requires sequencing.

## Idempotency retention
Deduplication is only as strong as the retention period and lookup semantics of the idempotency record. If the record expires while a delayed duplicate can still arrive, the old event can be accepted again. Therefore retention must cover the complete duplicate-delivery interval or a stronger historical reconciliation mechanism must exist.

## Reconciliation
For lost ACKs, reconciliation should query the authoritative downstream record using the stable identity and target incarnation. If the provider cannot distinguish the operation after its retention boundary, result remains UNKNOWN rather than NOT_APPLIED.

## Critical distinctions
- OUTBOX_DURABLE != DISPATCHED
- DISPATCH_ATTEMPTED != ACKNOWLEDGED
- ACK_LOST != DISPATCH_FAILED
- AT_LEAST_ONCE != EXACTLY_ONCE
- EVENT_ID_DEDUPE != CROSS_DOMAIN_ATOMICITY
- IDEMPOTENCY_RECORD_PRESENT != HISTORICAL_NONOCCURRENCE
- PER_KEY_ORDER != GLOBAL_ORDER
- RELAY_SUCCESS != EXTERNAL_EFFECT_CONFIRMED
- ACKNOWLEDGED != WORLD_TRUTH

## Nexo implication
The outbox/relay belongs in the effect execution plane, while the protected authority layer must retain the exact durable intent and stable effect identity. The relay is allowed to retry, but retries cannot create new logical effects. Lost acknowledgements remain UNKNOWN until provider reconciliation closes them.
