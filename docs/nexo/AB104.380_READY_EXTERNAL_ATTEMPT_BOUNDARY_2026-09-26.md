## Research question
What minimum durable ordering is required so that a crash cannot leave an externally executable request without a reconstructable record of the attempt?

## External evidence
RFC 9110 establishes a useful narrower analogue: conditional preconditions such as If-Match are evaluated before the state-changing method is performed, and a failed precondition prevents the method from being performed. RFC 9110 also warns against automatic retry of non-idempotent requests unless idempotent semantics are known or the client can establish the original was not applied. citeturn0search0turn0search2
AWS Durable Execution documents the same fundamental ambiguity: an interrupted side-effecting step can be replayed, and safe replay requires idempotent semantics or an external idempotency key that the provider actually enforces. Neither at-most-once-per-retry nor at-least-once replay establishes exactly-once execution across a workflow. citeturn0search1

## Boundary attack
The dangerous sequence is:
READY durable → process prepares request → process sends request → crash → attempt record was not durably established → recovery sees READY → recovery cannot distinguish 'never sent' from 'sent and outcome unknown'.
Therefore, a local READY marker is insufficient to prove non-execution after a crash if an external send can occur without a durable attempt boundary.

## Minimum candidate ordering
For crash-sensitive effects, the minimum safe candidate structure is:
1. Durable INTENT_DURABLE with exact OperationID + EffectID.
2. Establish a durable ATTEMPT record/boundary containing the same exact identity and the authority/fence/target conditions under which the attempt is authorized.
3. Only after that boundary is durably committed may the external request be released.
4. If the process crashes after the durable attempt boundary but before response, recovery classifies outcome as UNKNOWN unless provider/reconciliation evidence resolves it.
5. Recovery must never infer 'not executed' merely because no response or completion record exists.

This creates a deliberate asymmetry: durable attempt before send prevents an unrecorded attempt; durable attempt does NOT prove that the provider executed the request.

## Important limitation
A durable ATTEMPTED record written before the network send does not create exactly-once external execution. It creates a durable record that the system authorized/released an attempt. The provider may reject, receive, execute, execute and lose the response, or become unreachable.
Writing the attempt record only after receiving a response recreates the crash window and cannot safely establish absence of an external attempt.

## Candidate protocol
INTENT_DURABLE → FINAL_GATE → ATTEMPT_RECORD_DURABLE → RELEASE_EXTERNAL_REQUEST → EXTERNAL_ATTEMPTED → ACK/UNKNOWN

The final gate must validate current authority/fence and target conditions. The attempt record must bind EffectID, OperationID, AuthorityEpoch/fence, required scope/policy baseline, target VersionSet/incarnation, provider/resource identity, effect class, retry identity, attempt sequence, recovery ownership/fence, and trusted ordering metadata where applicable.

## Adversarial cases
### Crash before ATTEMPT_RECORD_DURABLE
No external release is permitted by the candidate protocol. Recovery may re-admit the durable intent.
### Crash after ATTEMPT_RECORD_DURABLE, before release
Recovery sees a durable attempt reservation but no proof of provider execution. It must not silently create a new EffectID. Reconciliation or same-identity retry is determined by the provider/effect contract.
### Crash during release
The outcome is UNKNOWN unless independent provider evidence resolves it.
### Crash after provider execution, before local response
UNKNOWN. Same EffectID retry is potentially safe only if provider-enforced idempotency/equivalence exists.
### Authority revocation after ATTEMPT_RECORD_DURABLE but before release
Local record does not itself preserve external authorization. The provider must enforce the relevant fence/epoch at admission, or the system must classify stale-request exclusion as UNKNOWN/HOLD.
### Provider does not support fencing
The durable attempt record cannot prove that a stale in-flight request will be rejected. NO_EFFECT_FROM_STALE_AUTHORITY cannot be claimed solely from local ordering.

## New findings
1. Durable attempt-before-send is the minimum candidate ordering for preventing an unrecorded external attempt.
2. It is not an exactly-once protocol; it moves crash ambiguity to an explicit durable UNKNOWN boundary.
3. The attempt record is authorization/effect-intent evidence, not proof of provider execution.
4. Local durable ordering cannot enforce revocation against an already released request unless the external resource consumes a valid fence/condition.
5. Stable EffectID + provider idempotency complements, but does not replace, durable attempt ordering.
6. The exact guarantee is provider/effect-class dependent; irreversible effects require stricter gates.
