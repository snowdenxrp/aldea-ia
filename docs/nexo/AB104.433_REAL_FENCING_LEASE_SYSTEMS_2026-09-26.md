## Research question

Which guarantees from real distributed coordination systems are actually transferable to Nexo's authority/fencing boundary?

## Evidence reviewed

### ZooKeeper
ZooKeeper documents linearizable writes, potentially stale reads, monotonically ordered zxids, quorum-based coordination, and ephemeral nodes tied to sessions. Its current documentation also emphasizes durable transaction logging and quorum operation. citeturn0search3turn0search7

Important boundary: an ephemeral node expresses session liveness/ownership state. It is not by itself proof that an arbitrary external resource will reject delayed requests from an old owner.

ZooKeeper's own documentation states that reads are not linearizable and may be stale, while writes are linearizable. Therefore a Nexo design cannot assume that an ordinary ZooKeeper read is a current authorization proof. citeturn0search3

### etcd
etcd provides atomic transactions with comparisons over values, versions, and revisions. Revisions form a logical ordering of changes. etcd explicitly documents that leases alone do not guarantee mutual exclusion; version/revision validation is part of the locking mechanism. citeturn0search4turn0search10turn0search12

This is directly relevant to Nexo:

LEASE_OWNERSHIP != STALE_ACTOR_EXCLUSION

The resource mutation must be conditionally bound to the current revision/lease identity where that property matters.

### Kubernetes Lease
Kubernetes uses Lease objects for leader election. Leadership is acquired through optimistic concurrency on the API object, and lease expiry allows another candidate to take over. Kubernetes documents the lease as a distributed lock/coordination mechanism. citeturn0search0turn0search5

Again, leader election does not automatically fence arbitrary external resources. A resource that can receive delayed commands needs its own stale-command protection if stale execution is unsafe.

### Chubby
Google's Chubby work describes a distributed lock service designed around reliability and availability for loosely coupled systems. It is useful evidence that distributed locks are coordination primitives, not universal external-effect guarantees. citeturn0search8

## Comparative result

| Mechanism | Strongest relevant property | Main limitation for Nexo |
|---|---|---|
| ZooKeeper ephemeral session | session/ownership lifecycle | external resource still needs stale-request protection |
| ZooKeeper zxid/version | ordered durable coordination state | ordinary reads may be stale |
| etcd revision/CAS transaction | atomic conditional state transition | only resources participating in etcd condition are protected |
| etcd lease | liveness/ownership | lease alone is not mutual exclusion/fencing |
| Kubernetes Lease | leader election | does not automatically fence arbitrary external effects |
| Chubby-style lock | reliable distributed coordination | external effect still needs a boundary/contract |

## Transferable Nexo primitives

### P1 — durable logical generation

Use a monotonic logical state/revision to identify authority transitions.

### P2 — conditional mutation

Bind protected mutation to the generation/revision observed by the authority/resource.

### P3 — explicit incarnation

A restart or replacement must be distinguishable from the previous authority/resource incarnation.

### P4 — session/lease only as liveness

Use leases to determine ownership/liveness where appropriate, but do not treat lease possession as sufficient stale-request safety.

### P5 — resource-side enforcement

The resource that can cause the protected effect should enforce the fence whenever the resource supports it.

### P6 — durable recovery

Authority/fence state must survive crash or recover with a strictly distinguishable incarnation/generation.

### P7 — gap/revalidation path

Watch-based replicas need gap detection and authoritative snapshot/revalidation.

## Important non-transferable assumption

Nexo must NOT assume that because a coordination system offers a distributed lock, every external side effect is automatically fenced.

The coordination system can establish:

CURRENT_OWNER = X

while the external resource still needs to enforce:

REQUEST_GENERATION == RESOURCE_CURRENT_GENERATION.

## Candidate Nexo pattern

AUTHORITY SERVICE
→ assigns generation/incarnation
→ publishes/commits authority state
→ issues resource-bound fence

RESOURCE
→ stores current fence durably
→ validates fence at mutation
→ rejects stale generation/incarnation

CLIENT
→ may use lease/watch/cache for efficiency
→ cannot convert stale local state into current authority

RECOVERY
→ preserves or advances generation
→ validates continuity
→ quarantines if continuity is uncertain

## Why etcd is particularly instructive

etcd's documentation explicitly says its lease mechanism itself does not guarantee mutual exclusion; conditional validation of revision/lease identity is what protects the operation. citeturn0search12

This independently reinforces the Nexo separation:

LIVENESS/OWNERSHIP
vs
STALE-ACTOR SAFETY.

## Why ZooKeeper is particularly instructive

ZooKeeper's current documentation distinguishes linearizable writes from potentially stale reads. This is a concrete warning against using a coordination store's generic read path as an unquestioned currentness oracle. citeturn0search3

## Why Kubernetes is particularly instructive

Kubernetes leader election uses leases and optimistic concurrency to select one active leader. This is appropriate for control-plane leadership but should not be generalized into an external-effect fencing guarantee without an enforcement point at the resource. citeturn0search0turn0search5

## Candidate Nexo invariant set

- LEASE_OWNERSHIP != STALE_ACTOR_EXCLUSION
- LEADER_ELECTION != EXTERNAL_EFFECT_FENCING
- COORDINATION_STATE != RESOURCE_EFFECT_STATE
- DURABLE_GENERATION > PROCESS_LOCAL_GENERATION
- CONDITIONAL_MUTATION > READ_THEN_UNCONDITIONAL_WRITE for stale-target safety
- ORDINARY_COORDINATION_READ != CURRENT_AUTHORIZATION_PROOF
- RESOURCE_FENCE_MUST_BE_ENFORCED_AT_EFFECT_BOUNDARY_WHEN_STALE_EXECUTION_IS_UNSAFE
- RESTART_MUST_NOT_REUSE_AN_UNDISTINGUISHABLE_AUTHORITY_INCARNATION
- WATCH_STATE_REQUIRES_GAP_DETECTION_AND_REVALIDATION
- LEASE_EXPIRY_DOES_NOT_ERASE_DELAYED_REQUESTS
- COORDINATION_SERVICE_SUCCESS != EXTERNAL_EFFECT_SUCCESS
- EXTERNAL_EFFECT_REQUIRES_SEPARATE_RECONCILIATION

## Architecture implication

The research does NOT justify choosing ZooKeeper, etcd, Kubernetes Lease, or any other provider yet.

What it does justify is a provider-independent abstraction boundary:

1. Authority Generation
2. Authority/Resource Incarnation
3. Lease/Ownership Evidence, if needed
4. Conditional/Fenced Mutation
5. Durable Replay Identity
6. Recovery Continuity
7. External Effect Reconciliation

Technology selection remains a later stage.
