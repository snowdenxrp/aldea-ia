# Nexo AB104.418 — Minimum-Cut and Correlated-Failure Analysis for Witness Quorums

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.417 → AB104.418
Implementation: NOT PERFORMED

## Research question

How can Nexo identify the smallest set of shared failure domains whose compromise or failure could invalidate a required witness quorum, without reducing assurance to a misleading scalar score?

## Evidence

NIST SP 800-160 Vol. 2 Rev. 1 explicitly identifies attack-tree, attack-graph, fault-tree, FMECA, and STPA-style analysis as ways to represent attack scenarios and system fragility. This supports using cut-set-style analysis as an engineering analysis technique rather than treating a witness count as sufficient assurance. citeturn0search37

NIST SP 800-160 emphasizes that security is an emergent system property and that analysis must account for components and services on which the system depends. citeturn0search1turn0search5

RFC 9334 separates Verifier appraisal from Relying Party authorization and explicitly models trust anchors and appraisal-policy dependencies. This supports including trust and policy dependencies in the failure-domain graph rather than treating the witness signature alone as the security boundary. citeturn0search0turn0search36

## Core finding

A quorum can fail even when many witnesses remain operational.

What matters is whether a sufficiently small set of shared dependencies can simultaneously invalidate the evidence required by the protected claim.

Therefore:

WITNESS_COUNT != MINIMUM_CUT

and:

MINIMUM_CUT != SECURITY_SCORE

A cut is a structural explanation of dependency concentration, not a universal measure of trustworthiness.

## Candidate model

Let:

Q = required witness set

D = claim-relevant failure-domain nodes

Each witness W_i maps to a dependency closure C_i.

A failure set F ⊆ D is a quorum-invalidating cut if compromising/failing F removes or invalidates enough independent witness contributions that the protected quorum condition can no longer be satisfied.

Candidate:

CUT(F, claim, Q) =
all witness contributions whose required assurance depends on at least one d ∈ F

A set F is security-critical when:

Q - INVALIDATED_BY(F)

cannot satisfy the protected quorum policy.

## Why minimum cut matters

Consider five witnesses:

W1,W2 depend on domain A
W3,W4 depend on domain B
W5 depends on domain C

If compromise of A invalidates W1,W2, compromise of B invalidates W3,W4, and the policy requires 3 independent contributions, no single A/B/C domain may be sufficient.

But if all five depend on policy domain P, then:

{P}

may invalidate the whole quorum for claims dependent on that policy.

The important output is not “security = X.”

The output is:

CRITICAL_SHARED_DOMAIN = P

## Hypergraph representation

Ordinary edges can be insufficient because one dependency may affect many witnesses simultaneously.

Candidate model:

- witness nodes;
- failure-domain nodes;
- dependency hyperedges;
- claim/property nodes;
- quorum-policy node;
- trust-generation nodes;
- recovery-domain nodes.

A hyperedge can represent:

ONE_DEPENDENCY → MANY_WITNESSES

This directly captures common-mode failure.

## Claim-specific cut sets

The cut must be evaluated per protected property.

For storage integrity:

Provider/control-plane may be critical.

For policy integrity:

Policy source may be critical.

For freshness:

Time source or freshness authority may be critical.

For verifier correctness:

Verifier implementation may be critical.

Therefore:

MIN_CUT(claim A) != MIN_CUT(claim B)

This prevents one global failure-domain graph from being incorrectly reused for every Nexo property.

## Single-point-of-failure classification

Candidate categories:

C0 — no identified critical single-domain cut within modeled closure.

C1 — one domain can invalidate the required quorum.

C2 — at least two-domain combination is required.

C3+ — larger combinations required under the current model.

These are **structural classes**, not security ratings.

A C1 result does not automatically mean a system is unsafe; it identifies a concentration that must be evaluated against the protected property and policy.

## Unknown closure

If dependency closure is incomplete:

MINIMUM_CUT = UNKNOWN

not:

MINIMUM_CUT = NONE

This is important because an undiscovered common dependency can create a hidden single-point failure.

Candidate:

UNKNOWN_DEPENDENCY_CLOSURE
=> NO_CLAIM_OF_CUT_COMPLETENESS

## Byzantine interpretation

For Byzantine witnesses, a cut can represent either:

- compromise of witnesses directly;
- compromise of a shared dependency causing correlated Byzantine behavior;
- compromise of the verifier/policy path that turns honest evidence into a false Attestation Result.

Therefore:

EFFECTIVE_BYZANTINE_PARTICIPANTS

must be evaluated after dependency projection.

Logical witness count cannot be directly substituted into a Byzantine fault assumption.

## Cut sets versus trust roots

A trust root can be a critical cut even if all witnesses have distinct keys.

Example:

W1 key K1 → Root R
W2 key K2 → Root R
W3 key K3 → Root R

Three signatures exist, but compromise of R may invalidate the trust relationship for all three.

Thus:

KEY_DIVERSITY != TRUST_ROOT_DIVERSITY

## Cut sets versus policy

Likewise:

W1,W2,W3 use independent hardware and keys,
but all depend on Policy P.

If P controls whether their evidence is accepted:

P may be a claim-critical cut.

Therefore:

INFRASTRUCTURE_DIVERSITY != POLICY_INDEPENDENCE

## Cut sets versus recovery

A live quorum may appear independent while all recovery paths depend on one backup/control system.

Candidate separate graph:

G_live
G_recovery

The protected recovery property must analyze:

MIN_CUT(recovery, claim)

independently.

## Cut-set generation

Candidate analysis:

1. establish protected claim/property;
2. derive required witness contributions;
3. obtain claim-specific dependency closure;
4. project dependencies into failure domains;
5. identify shared-domain hyperedges;
6. enumerate minimal candidate cuts;
7. test each cut against quorum policy;
8. identify critical cuts;
9. record unknown dependencies and limitations;
10. bind result to graph/policy/generation versions.

The result is evidence for Z1, not authority.

## Dynamic cut invalidation

A previously calculated cut set can become stale.

Changes include:

- witness enrollment/removal;
- provider migration;
- verifier update;
- policy change;
- trust-root rotation;
- recovery architecture change;
- dependency discovery;
- failure-domain reassignment.

Candidate:

FAILURE_DOMAIN_GRAPH_VERSION_CHANGE
=> CUT_ANALYSIS_STALE

and:

STALE_CUT_ANALYSIS
=> REVALIDATE

## Cut analysis race

If the graph changes while the analysis is running:

GRAPH_G = analyzed
GRAPH_G+1 = current

The result must not be silently used as current.

Candidate final gate:

ANALYSIS_GRAPH_VERSION == CURRENT_GRAPH_VERSION
AND
POLICY_VERSION == CURRENT_POLICY_VERSION
AND
TRUST_GENERATION == CURRENT_TRUST_GENERATION
AND
QUORUM_POLICY_GENERATION == CURRENT_GENERATION

Otherwise REVALIDATE/HOLD.

## Independence versus cut size

A larger minimum cut can indicate more structural separation under the model, but Nexo should not convert this into:

“higher number = safer.”

Reasons:

- domains can have different consequence;
- a low-cardinality cut may be intentionally protected;
- model incompleteness changes results;
- Byzantine behavior is claim-specific;
- liveness and safety have different requirements.

Therefore retain the cut itself and its assumptions.

## Residuals

- Efficient exact minimum-cut computation for dynamic hypergraphs remains open.
- The dependency graph may itself be incomplete or compromised.
- Cut analysis does not solve semantic correctness of dependencies.
- Cut analysis does not establish Byzantine correctness without an explicit fault model.
- Cut analysis does not prove external-effect atomicity.
- Numeric quorum thresholds remain policy/model dependent.
- Formal proof, implementation, fault injection, and deployment verification remain unperformed.

## Exact next research
