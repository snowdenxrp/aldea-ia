# Nexo AB104.444 — Single-Vendor Total Compromise Boundary

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY

## Research question

If one vendor failure domain controls the hardware root, firmware, attestation root, update signing, verifier, cloud control plane, and support path, what can Nexo still safely establish?

## External evidence

RFC 9334 explicitly separates manufacturer endorsements/trust anchors, Verifier appraisal, and Relying Party decisions. A relying party may require evidence about the Verifier itself before accepting Attestation Results. This supports treating the vendor as a bounded trust dependency rather than as Nexo authority. citeturn0search2turn0search4

SLSA states that provenance trust depends on the build platform being trusted and that Build L3 does not cover compromise of the build platform itself. It therefore illustrates a general boundary: stronger evidence can reduce some attacks while leaving compromise of the underlying trust root unresolved. citeturn0search0turn0search10

NIST key-management guidance requires explicit compromise recognition, notification, replacement, revocation and recovery procedures rather than treating compromised key material as permanently trustworthy. citeturn0search49turn0search48

RFC 9162 demonstrates that append-only transparency evidence can expose inconsistent log views through consistency auditing, but an observer/auditor is itself part of the detection architecture. citeturn0search5

## Core finding

If one vendor controls every supposedly independent layer, the layers are not independent evidence.

Therefore:

VENDOR_TOTAL_COMPROMISE
=> ALL_VENDOR_DEPENDENT_CLAIMS_REVIEW_REQUIRED.

And:

MULTIPLE_VENDOR_SIGNALS != MULTIPLE_INDEPENDENT_FAILURE_DOMAINS.

## Scenario VTC-1 — complete vendor root compromise

Assume one vendor can compromise:
- hardware firmware;
- TPM/TEE/Secure Element firmware;
- attestation roots;
- update signing;
- verifier software;
- cloud-HSM control plane;
- support credentials;
- vendor policy service.

Then all claims depending on those components share a failure domain.

The correct result is not “everything is false.”

It is claim-specific dependency invalidation.

Candidate state:
CURRENT → VENDOR_COMPROMISE_SUSPECTED → AFFECTED_CLAIMS_UNKNOWN/INVALIDATED.

Unaffected claims may remain valid if their dependency closure is genuinely outside the compromised domain.

## Scenario VTC-2 — vendor forges perfect evidence

A fully compromised vendor can potentially create:
- valid signatures;
- internally consistent measurements;
- apparently fresh attestations;
- valid HSM signatures;
- valid provenance.

Cryptographic validity therefore does not rescue a claim whose trust root is itself compromised.

Candidate:
VALID_SIGNATURE + COMPROMISED_ROOT => EVIDENCE_NOT_SUFFICIENT_FOR_CURRENT_AUTHORITY.

## Scenario VTC-3 — independent external anchor survives

Suppose Nexo has an independently operated continuity witness that records:
G41/R41.

Vendor-controlled hardware reports:
G43/R43.

If the witness is genuinely independent and its continuity is current, Nexo can detect a divergence.

It does not automatically know which side is correct.

Result:
CONFLICT_DETECTED
→ freeze affected admission
→ preserve both histories
→ reconstruct predecessor/decision/effect lineage
→ determine whether a valid external recovery authority exists.

## Scenario VTC-4 — external anchor also depends on vendor

If the “independent” witness uses:
- same vendor hardware;
- same vendor cloud;
- same vendor keys;
- same vendor verifier;
- same vendor update channel;

then independence collapses.

Therefore:

EXTERNAL_LOCATION != INDEPENDENT_FAILURE_DOMAIN.

## Scenario VTC-5 — vendor compromise after last trusted checkpoint

Suppose last independently validated state is G41.

Vendor compromise begins after G41.

If all subsequent evidence depends on the vendor, Nexo may retain G41 as historical trusted continuity while treating G42+ as UNKNOWN/UNTRUSTED until independently reconstructed.

This is a useful boundary:

LAST_INDEPENDENTLY_VALIDATED_STATE != CURRENT_STATE.

But it provides a safe reconstruction starting point, not proof of what happened afterward.

## Scenario VTC-6 — vendor compromise before checkpoint

If the vendor was already compromised before the last checkpoint and no independent evidence covers that interval, the checkpoint cannot be assumed clean merely because it was vendor-signed.

Result:
CHECKPOINT_TRUST_DEPENDENCY_UNKNOWN.

This prevents “trusted checkpoint” from becoming an unexamined assumption.

## Scenario VTC-7 — vendor supplies emergency clean image

A vendor provides a new firmware image after compromise.

Its signature can establish provenance under the new key/trust generation.

It does not independently establish that the image is semantically safe.

Candidate recovery:
NEW_IMAGE
→ independent validation
→ new trust generation
→ hardware/attestation revalidation
→ dependency closure
→ recovery generation
→ explicit release.

## Scenario VTC-8 — vendor rotates keys

Key rotation is not automatically compromise recovery.

Need distinguish:
NORMAL_KEY_ROTATION
COMPROMISE_ROTATION
TRUST_ROOT_REPLACEMENT.

The semantics and invalidation scope differ.

## Scenario VTC-9 — vendor cloud control plane compromised

Cloud HSM keys may remain cryptographically protected while:
- authorization metadata;
- cluster membership;
- backup/restore;
- identity mappings;
- audit streams;
- lifecycle state

are manipulated.

Therefore key custody does not establish correctness of surrounding control state.

## Scenario VTC-10 — support channel compromised

A vendor support credential can create apparently legitimate recovery actions.

Those actions require explicit Nexo authority binding.

SUPPORT_ACTION != NEXO_AUTHORITY_ACTION.

## Scenario VTC-11 — no independent root remains

If every evidence source needed for a claim is inside the compromised vendor failure domain, Nexo cannot manufacture independence.

Correct state:
CLAIM_CURRENTNESS = UNKNOWN.

For high-consequence authority/effects:
HOLD / QUARANTINE.

Recovery requires establishment of a new independent trust basis.

## Scenario VTC-12 — vendor compromise but external effect history survives

External providers may retain independent records of effects.

These records can help reconstruct:
- attempted operations;
- acknowledged operations;
- resource state;
- effect identities.

But they do not automatically prove Nexo's authority at the time.

Thus:
EXTERNAL_EFFECT_HISTORY != AUTHORITY_HISTORY.

## Minimum surviving guarantees

After total compromise of one vendor domain, Nexo may still preserve claims whose complete dependency closure remains outside that domain.

Examples:
- an independently witnessed historical anchor;
- an external resource-side fence controlled outside the vendor;
- independent provider effect records;
- independent recovery governance;
- independent key/witness infrastructure.

But each must be evaluated for actual failure-domain independence.

## Independence test

For a claim C, define:

DEPENDENCY_CLOSURE(C) = all components whose compromise could falsify C.

A purported independent anchor A is independent for C only if:
A ∉ DEPENDENCY_CLOSURE(C)

and the path from A to the admission decision does not re-enter the compromised domain in a way that can falsify the claim.

This extends AB104.392–AB104.420.

## Recovery after total vendor compromise

Candidate:

VENDOR_TOTAL_COMPROMISE
→ FREEZE_AFFECTED_AUTHORITY
→ INVALIDATE_VENDOR_DEPENDENCIES
→ PRESERVE_LAST_INDEPENDENT_EVIDENCE
→ COLLECT_EXTERNAL_EFFECT_HISTORY
→ BUILD_COMPROMISE_INTERVAL
→ CLASSIFY_CLAIMS_BY_DEPENDENCY_CLOSURE
→ ESTABLISH_NEW_TRUST_ROOTS
→ ESTABLISH_NEW_HARDWARE/KEY INCARNATIONS WHERE REQUIRED
→ REATTEST
→ REVALIDATE
→ NEW_RECOVERY_GENERATION
→ EXPLICIT_RELEASE.

No recovery step may treat the compromised vendor as its own independent verifier.

## What an external anchor can and cannot rescue

It can potentially:
- detect rollback;
- detect fork/equivocation;
- preserve historical continuity;
- constrain the earliest known trusted state.

It cannot by itself:
- prove the vendor hardware behaved correctly;
- reconstruct hidden internal events;
- prove absence of unauthorized external effects;
- restore current authority automatically.

## Important TCB conclusion

A hardware root is not enough.

A second hardware root from the same vendor is not enough.

A second cloud service from the same vendor is not enough.

A second verifier using the same vendor trust root is not enough.

Independence must be established through the dependency graph and failure-domain model.
