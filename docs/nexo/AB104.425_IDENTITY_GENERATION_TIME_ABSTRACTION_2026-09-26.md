# Nexo AB104.425 — Safe Abstraction of Identity, Generations, and Time

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.424 → AB104.425
Implementation: NOT PERFORMED

## Research question

Which identity, generation, and temporal state can be abstracted without destroying properties involving stale authority, revocation, recovery, replay, lineage, and currentness?

## Evidence

NIST research on abstraction shows that reductions must preserve the relevant soundness relation; its model-checking reduction work explicitly modifies state-machine and temporal constraints to avoid unsound results. citeturn0search0turn0search24

NASA notes that temporal properties are state-dependent and that finite approximations for timing must be conservative for the properties being analyzed. citeturn0search14turn0search25

NIST also treats model differences as material to analyzer findings rather than assuming different models are interchangeable. citeturn0search11

## Core finding

Identity and generation fields are not merely metadata when they determine whether an observation, authority, replay, recovery action, or external effect is still applicable.

Therefore:

IDENTITY_ABSTRACTION != METADATA_ABSTRACTION

and:

GENERATION_COLLAPSE can destroy temporal safety even when ordinary functional behavior appears unchanged.

## Identity classes that should remain distinct

Candidate protected distinctions:

- IDENTITY_DOMAIN
- SUBJECT_ID
- OPERATION_ID
- EFFECT_ID
- ATTEMPT_ID
- PARENT_LINEAGE_ID
- PARTICIPANT_ID
- RESOURCE_ID
- RESOURCE_INCARNATION
- EXECUTION_ID
- RECOVERY_ATTEMPT_ID
- WITNESS_ID
- WITNESS_INCARNATION

These identities have different semantics and must not be collapsed merely because they are all identifiers.

## Safe identity abstraction candidate

An identity can be abstracted when the property is invariant under the transformation.

Example:

Renaming unrelated subject IDs while preserving all equality/inequality relationships may be safe.

Candidate condition:

IDENTITY_RENAME_PRESERVES_RELATIONS
AND
PROPERTY_IS_RENAME_INVARIANT
=> SAFE_RENAMING_ABSTRACTION

This is a property-specific result.

## Unsafe identity abstraction

If two resources have different incarnations:

R, INC_1
R, INC_2

and the model collapses them into:

R

then stale lineage or stale authorization may appear current.

Candidate:

RESOURCE_INCARNATION_COLLAPSE
=> POSSIBLE_FALSE_SAFETY.

## Generation semantics

Nexo currently has multiple generation concepts:

- authority epoch;
- fence generation;
- policy generation;
- trust generation;
- dependency generation;
- graph generation;
- replay-state generation;
- continuity generation;
- recovery generation;
- invalidation generation.

These should not be treated as one generic version number unless equivalence is explicitly proven.

Candidate:

GENERATION_TYPE_COLLAPSE => PROOF_OBLIGATION.

## Generation equality versus ordering

A model may preserve:

g1 < g2

while losing exact generation identity.

That can be sufficient for some monotonic properties.

But some claims require exact binding:

EVIDENCE_GENERATION == CURRENT_GENERATION.

Therefore:

ORDER_PRESERVATION != IDENTITY_PRESERVATION.

## Safe temporal abstraction classes

### T0 — irrelevant time

If time never affects the protected property, it may be abstracted away.

This must be justified by a property analysis.

### T1 — discrete ordering

For properties requiring only before/after relationships, exact timestamps may be abstracted into an ordered event relation.

### T2 — generation-based time

If authority freshness is represented by monotonic generations, wall-clock values may be abstracted while preserving generation transitions.

This does not prove that the generation mechanism itself is safe.

### T3 — quantitative deadlines

If safety depends on actual elapsed time, arbitrary time abstraction is unsafe.

The abstraction must preserve the relevant timing constraints.

## Wall-clock abstraction

Replacing timestamps with logical ordering can be valid only when the property does not depend on elapsed duration.

Candidate:

CLOCK_ABSTRACTION_SAFE
iff
PROPERTY_DEPENDENCY_ON_TIME == ORDER_ONLY.

Otherwise:

CLOCK_ABSTRACTION => PROOF_GAP.

## Freshness versus ordering

A newer generation does not automatically mean an observation is fresh in every semantic sense.

Conversely, a recent timestamp does not prove current state.

Therefore:

TIMESTAMP_FRESHNESS != STATE_CURRENTNESS
GENERATION_NEWNESS != SEMANTIC_FRESHNESS.

## Revocation abstraction

A model that collapses:

CURRENT
→ REVOKED

into one state cannot verify revocation races.

At minimum, the model needs the ordering:

VALID
→ REVOCATION_ISSUED
→ REVOCATION_EFFECTIVE_FOR_ADMISSION

where the exact transition semantics are claim-specific.

## Authority epoch abstraction

For stale-authority properties, preserve:

AUTHORITY_EPOCH
and
transition relation.

If all epochs are collapsed into CURRENT, the model cannot expose:

old request + new authority epoch.

Candidate:

EPOCH_COLLAPSE => CANNOT_PROVE_NO_EFFECT_FROM_STALE_AUTHORITY.

## Replay abstraction

Replay safety often depends on:

EFFECT_ID
+ CONSUMPTION_STATE
+ CURRENT_GENERATION.

Collapsing all attempts into one state can hide:

ATTEMPT_1
→ consumed
→ ATTEMPT_2 replay.

Candidate:

ATTEMPT_IDENTITY_COLLAPSE => POSSIBLE_REPLAY_FALSE_NEGATIVE.

## Lineage abstraction

A parent and child execution may share a trace correlation ID while having different authorization semantics.

Therefore:

TRACE_CORRELATION != AUTHORIZATION_LINEAGE.

The abstraction must preserve parent/child authorization binding when that property is claimed.

## Recovery abstraction

Recovery generation must remain distinct from normal authority generation when recovery can:

- restore state;
- reconcile effects;
- establish new ownership;
- change authority;
- invalidate old lineage.

Candidate:

RECOVERY_GENERATION_COLLAPSE => POSSIBLE_RESTORE_REPLAY_OR_STALE_AUTHORITY_FALSE_NEGATIVE.

## Continuity anchor abstraction

Continuity generations may be abstracted to ordering if the property only asks whether state is newer than a checkpoint.

But if the claim requires exact state-root binding:

CONTINUITY_GENERATION + STATE_ROOT

must remain linked.

## Dynamic graph abstraction

A graph version can sometimes represent many internal mutations if the property only cares whether the dependency graph changed.

But if a particular edge determines a critical cut, that edge must remain visible.

Candidate:

GRAPH_VERSION_ONLY != DEPENDENCY_EDGE_PRESERVATION.

## Identity-generation coupling

Some properties require both:

RESOURCE_ID
+
RESOURCE_INCARNATION
+
AUTHORITY_EPOCH
+
FENCE_GENERATION.

Collapsing any one may allow a stale request to appear valid.

Candidate protected tuple:

AUTHORIZATION_BINDING =
(DOMAIN, RESOURCE_ID, RESOURCE_INCARNATION, AUTHORITY_EPOCH, FENCE_GENERATION).

Exact fields remain claim-specific.

## Temporal quotienting

Candidate abstraction operation:

Many concrete states
→ one abstract state

is permitted only if all merged states are equivalent with respect to the property.

For a safety property P:

if abstract state A represents concrete states C1...Cn, then abstraction must not merge states whose distinction can change whether P holds or whether a protected transition is enabled.

Candidate:

PROPERTY_RELEVANCE_PARTITION.

## Stuttering abstraction

If an internal sequence of transitions has no observable effect on the property, those transitions may potentially be collapsed.

But a transition that changes:

- authority;
- revocation;
- resource incarnation;
- fence;
- recovery;
- external-effect status

cannot be assumed stuttering.

Candidate:

PROTECTED_STATE_CHANGE != STUTTERING_STEP.

## Time compression

Compressing many heartbeat/telemetry events into one step may be safe if they cannot affect the property.

However, compressing:

revocation
+
admission
+
external attempt

into one step destroys the race being studied.

Therefore:

SECURITY_RELEVANT_ORDER_MUST_BE_PRESERVED.

## Candidate abstraction equivalence relation

Two concrete states may be merged only when:

- all protected identities relevant to the property have equivalent relationships;
- relevant generations have equivalent ordering/binding;
- relevant temporal transitions remain distinguishable;
- protected transition enablement is equivalent;
- UNKNOWN semantics remain equivalent;
- recovery semantics remain equivalent;
- external-effect boundary remains equivalent.

This is a candidate semantic criterion, not yet a formal proof.

## Counterexample-guided temporal refinement

If an abstract model reports SAFE but the abstraction relation is insufficient, safety cannot be promoted.

If it reports a counterexample:

ABSTRACT_TRACE
→ CONCRETIZE
→ REAL/SPURIOUS.

If spurious:

REFINE identity/generation/time partition.

If real:

COUNTEREXAMPLE_FOUND.

## Resource exhaustion

An attacker may create many generations or rapid state changes.

If abstraction times out:

TIME_ABSTRACTION_INCONCLUSIVE != SAFE.

No automatic collapse to “latest state only” is allowed without proof that intermediate states are irrelevant.

## Z1 boundary

Temporal/identity abstraction results remain evidence.

They do not grant authority.

Therefore:

TEMPORAL_ABSTRACTION_RESULT != Z1_AUTHORITY.

## Residuals

- Formal equivalence relation for identity/generation/time remains open.
- Exact temporal property language remains open.
- Quantitative deadline abstractions require separate timing semantics.
- Distributed-clock assumptions remain open.
- Interaction with external-effect timing remains open.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
