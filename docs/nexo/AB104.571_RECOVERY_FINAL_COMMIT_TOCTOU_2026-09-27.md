# Nexo AB104.571 — Final recovery TOCTOU and conditional activation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Evidence
etcd transactions atomically evaluate comparisons and then apply writes, including comparisons over key version and modification revision. Its STM implementation guards the read set by comparing the observed ModRevision at commit, preventing a write based on a stale read set. citeturn0search0turn0search4 Fencing implementations similarly place generation checks in the transaction guard so a post-fence mutation fails rather than committing with stale authority. citeturn0search5

## Finding
A final dependency revalidation followed by a separate authority commit creates a TOCTOU window:

VALIDATE(Snapshot S)
→ dependency changes
→ COMMIT(Recovery R based on S)

The recovery can be safe at validation time but invalid at commit time.

The protected solution is not merely to validate again immediately before commit. The commit itself must be conditionally bound to the exact validated dependency snapshot and authority epoch.

## Candidate final gate
AUTHORITY_COMMIT succeeds only if all protected predicates still match atomically:
- DependencySnapshotDigest == validated digest;
- AuthorityEpoch == expected epoch;
- WitnessSetEpoch == expected epoch;
- ContinuityAnchorDigest == expected anchor;
- RecoveryGeneration == expected generation;
- FenceRevision == expected fence;
- required root statuses/revocation generations unchanged;
- dependency versions/incarnations unchanged.

If any comparison fails, the transaction fails and the prepared recovery certificate is stale.

## Why this closes the race
A concurrent revocation or dependency update changes one of the guarded versions before the authority commit. The conditional commit then rejects the stale recovery rather than allowing a previously valid snapshot to authorize after the change. This is the same semantic pattern as etcd's atomic Compare-and-Then transaction and STM read-set validation. citeturn0search0turn0search4

## Fence role
The recovery fence must be part of the guarded commit, not merely generated before it. A generated token without provider/enforcement-side comparison does not close the stale-writer race.

FENCE_PREPARED != FENCE_ACTIVE
TOKEN_GENERATED != TOKEN_ENFORCED
VALIDATION_PASSED != COMMIT_AUTHORIZED

## Failure semantics
- Guard passes: recovery authority may commit at the protected linearization point.
- Guard fails: prepared recovery becomes STALE and must be recomputed.
- Store/authority state UNKNOWN: do not assume the guard passed; remain blocked/quarantined.
- Crash after successful protected commit: recovery reconstructs the committed authority boundary from durable state.
- Crash before commit: prepared certificate has no authority merely because it exists.

## Scope boundary
The conditional commit closes the TOCTOU race inside the authoritative store. It does not automatically make external providers atomic with the recovery decision. External effects still require the existing EffectID/fence/reconciliation machinery.

## Nexo consequence
The final recovery transition should be modeled as a single protected conditional state transition whose compare-set includes the complete claim-relevant dependency/version/incarnation snapshot. This gives a precise linearization point for recovery authority without falsely claiming cross-domain atomicity.
