# AB105.068R — KAFKA G0 A1 AUTHORIZATION-SCOPE RESOLUTION — 2026-10-01

## Verified
Kafka revision: 99b940733a9f6bc409457dba7108f08421d81e42

## Findings
1. KafkaApis' Produce path invokes AuthHelper.filterByAuthorized with operation WRITE and resource type TOPIC over the Produce topic/partition data.
2. AuthHelper constructs one Action per distinct topic name and calls the configured Authorizer with those actions.
3. StandardAuthorizer evaluates Action.operation() and Action.resourcePattern(); therefore the runtime wrapper can distinguish the intended WRITE/TOPIC authorization from unrelated authorizer calls.
4. The wrapper must NOT block every ALLOWED result. That compile-probe behavior is unsuitable for runtime because it could intercept metadata, DESCRIBE, cluster, or other authorization traffic and destroy the witness.
5. A1 should therefore gate only an authorization invocation whose actions match the isolated target topic and WRITE/TOPIC semantics, while recording the delegated ALLOW result before waiting.
6. The existing G0 witness rule remains strict: A1 is a real target Produce authorization call that has delegated to StandardAuthorizer and is held BEFORE the authorization result returns to Kafka.

## D1 implication
D1 must use a fresh Produce request with the same non-superuser principal and target topic, reach broker 0 after D0, and independently observe DENIED before A1 is released. D1 cannot be inferred from metadata absence or from the completion of DeleteAcls.
