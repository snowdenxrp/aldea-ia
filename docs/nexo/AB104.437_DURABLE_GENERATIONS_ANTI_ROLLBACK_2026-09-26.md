# Nexo AB104.437 — Durable Monotonic Generations, WAL, Consensus Revisions and Anti-Rollback

## Research question

What mechanisms can preserve monotonic authority/fence state across crash, restart and rollback, and what assumptions must Nexo refuse to hide inside the storage layer?

## External evidence

etcd assigns an increasing revision to modifying operations and documents durability and linearizable KV operations; serializable local reads can be stale, while linearizable reads use consensus. citeturn0search1turn0search7

Raft defines committed log entries as replicated to a majority and durable; committed entries are then applied to state machines. citeturn0search26

ZooKeeper exposes a zxid composed of epoch + counter and commits proposals after quorum acknowledgement. Its transaction log is written to non-volatile storage before an update takes effect; recovery replays transaction logs against snapshots. citeturn0search4turn0search0

ZooKeeper also explicitly treats snapshots as potentially fuzzy and relies on transaction-log replay for recovery, demonstrating that snapshot integrity alone is not the complete current state. citeturn0search0turn0search27

## Core finding

A monotonic value is safe only relative to a protected continuity mechanism.

Therefore:

MONOTONIC_COUNTER != ANTI_ROLLBACK_PROOF

and:

DURABLE_LOCAL_STATE != CURRENT_AUTHORITY.

## Mechanism classes

### G1 — local persistent counter

A counter persisted to local storage may survive ordinary process restart.

It does not automatically survive:
- storage rollback;
- snapshot restore;
- cloned disks;
- failover to an older replica;
- operator restoration.

Therefore it is insufficient as a universal authority epoch.

### G2 — WAL / transaction log

A write-ahead or transaction log can preserve ordered mutations across crash when its durability and replay semantics are correctly defined.

But:
- the log itself has storage/trust dependencies;
- truncation/compaction must preserve required continuity;
- restoring an older log can roll state backward;
- external continuity may be required to detect rollback.

So:

WAL_DURABILITY != GLOBAL_ANTI_ROLLBACK.

### G3 — consensus-backed revision

A consensus log can provide a durable ordered history under its specified failure model.

Raft's committed-prefix model is strong evidence for this class. citeturn0search26

etcd's revision is a concrete example of a logical ordering associated with durable KV mutations. citeturn0search1

Still, the Nexo property is not merely “revision increases”; it requires that a restored or replaced authority cannot silently reuse an older accepted revision as current.

### G4 — external continuity anchor

A separate continuity authority can detect rollback of the primary state.

Candidate:

PRIMARY_GENERATION < ANCHOR_GENERATION
=> RESTORE_NOT_CURRENT.

This expands the dependency/TCB and therefore requires the same independence analysis already established in AB104.412–AB104.420.

### G5 — resource-side fence high-water mark

The resource itself stores the highest accepted fence generation.

Candidate:

incoming_fence < local_HWM
=> REJECT.

This directly addresses stale actors at the resource boundary.

But if the resource HWM itself rolls back, the safety property can fail.

Therefore HWM durability/continuity is part of the fence claim.

## Anti-rollback distinction

Four separate properties must not be conflated:

1. INTEGRITY — state was not modified undetectably.
2. DURABILITY — committed state survives specified failures.
3. CONTINUITY — state is linked to the correct predecessor/history.
4. CURRENTNESS — state is the current authoritative state.

A signed snapshot can establish integrity without establishing currentness.

A durable WAL can establish crash recovery without proving the storage has not been rolled back to an older valid WAL.

## Snapshot restore

Candidate safe restore:

RESTORE_SNAPSHOT
→ VERIFY_INTEGRITY
→ VERIFY_PREDECESSOR/CONTINUITY
→ COMPARE_EXTERNAL_OR_CONSENSUS_GENERATION
→ RECONCILE_POST_SNAPSHOT_DECISIONS
→ CREATE_RECOVERY_GENERATION
→ REVALIDATE_DEPENDENCIES
→ RELEASE.

Unsafe:

RESTORE
→ START_NORMAL.

## Compaction

Compaction must preserve whatever evidence is needed to distinguish:
- current generation;
- predecessor;
- committed boundary;
- invalidated generations;
- replay state;
- recovery epoch.

Deleting old events is acceptable only if the retained state preserves the safety-relevant continuity relation.

Therefore:

HISTORY_COMPACTION != HISTORY_ERASURE

when continuity proofs depend on retained summaries/anchors.

## Counter wrap / generation reuse

A finite counter eventually wraps.

If old G1 and future G1 become indistinguishable, stale requests can become admissible.

Candidate requirements:
- sufficiently large generation domain;
- explicit epoch/incarnation;
- no reuse within the protected validity horizon;
- rollover protocol before exhaustion.

No numeric size is selected here.

## Clone / fork attack

Two nodes can be cloned from the same valid state S7.

Both may then issue G8 independently.

Therefore:

SAME_SNAPSHOT != SAME_AUTHORITY.

A continuity mechanism must establish uniqueness/current authority, not merely identical starting state.

## Failover to stale replica

Replica B has state G7 while authority A has G8.

Failover to B must not make G7 current without reconciliation.

Candidate:

FAILOVER_CANDIDATE_GENERATION < CURRENT_CONTINUITY_ANCHOR
=> QUARANTINED.

## Consensus caveat

Consensus can provide a strong ordered history inside its configured domain, but it does not automatically prove:
- correct application semantics;
- correct policy;
- correct external provider state;
- absence of common-mode compromise;
- correctness after an operator restores arbitrary historical data.

Consensus is therefore a mechanism, not a universal correctness theorem.
