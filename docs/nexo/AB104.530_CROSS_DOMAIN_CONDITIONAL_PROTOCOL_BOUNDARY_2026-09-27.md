# Nexo AB104.530 — Cross-domain conditional protocol boundary

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Provider-side conditional operations can provide a reusable adapter contract, but they do not by themselves create a global commit protocol with Nexo. AWS transactional-outbox guidance explicitly treats the database commit and downstream notification as separate concerns and recommends idempotent consumers; AWS also describes saga orchestration when transactions span service boundaries. Google Spanner documentation similarly warns that external APIs cannot be atomically coupled to a database transaction.

## Evidence
- AWS transactional outbox: database state and emitted event are committed separately; outbox closes the local dual-write gap, while downstream delivery can still duplicate and therefore needs idempotency.
- AWS saga guidance: when work spans independent data stores without a common transaction coordinator, saga-style coordination/compensation is used instead of assuming one ACID transaction.
- Google Spanner: external APIs/non-transactional operations should not be executed directly inside a retried transaction because the transaction may replay; an external call cannot simply inherit the database transaction's atomicity.
- AWS durable execution: at-least-once and at-most-once retry semantics do not automatically imply exactly-once end-to-end behavior.

## Candidate reusable adapter contract
Nexo -> Provider:
Prepare/Admit request binds:
OperationID, EffectID, RequestDigest, TargetIdentity, TargetIncarnation, NexoAuthorityEpoch, FenceRevision, ProviderScope, Expiry.

Provider must return one of:
REJECTED_BEFORE_COMMIT
ACCEPTED_DURABLE
APPLIED_WITH_RECEIPT
CANCELLED_BEFORE_COMMIT
UNKNOWN

Provider-side conditional mutation must atomically validate all predicates that it claims to enforce.

Nexo then reconciles provider state; it does not infer a global commit from local provider acceptance.

## Strong boundary
If the provider supports a durable operation record plus atomic conditional state transition and authoritative lookup, Nexo can reduce the UNKNOWN surface and make retries/reconciliation safer.
If the provider lacks these capabilities, Nexo must preserve the two-domain boundary and may have to retain UNKNOWN.

No generic protocol discovered here can turn independent provider atomicity into global atomicity without an explicit trusted bridge.

## Critical distinctions
- PROVIDER_CAS != GLOBAL_COMMIT
- OUTBOX_ATOMICITY != EXTERNAL_EFFECT_ATOMICITY
- SAGA_COORDINATION != ATOMIC_TRANSACTION
- PROVIDER_ACCEPTED != NEXO_COMMITTED
- NEXO_COMMITTED != EXTERNAL_APPLIED
- IDEMPOTENT_RETRY != EXACTLY_ONCE_GLOBAL_EFFECT
- COMPENSATION != ROLLBACK_OF_HISTORY
- TRANSACTIONAL_OUTBOX != CROSS_DOMAIN_LINEARIZATION

## Nexo implication
The architecture should define a provider-neutral Effect Adapter boundary rather than pretend every provider offers the same transaction semantics. The adapter declares capabilities and maps provider-specific conditional/operation/reconciliation semantics into Nexo's canonical states. Capability absence is a first-class input to admission and may force UNKNOWN/quarantine.
