# AB105.038R — nested stacks, child-resource mapping, and AWS Config relationships audit

Date: 2026-09-30
Chain: AB105.037R → AB105.038R

## Research question

Can CloudFormation StackResource/StackResourceSummary plus AWS Config relationships or supplementary configuration provide a reliable mapping for nested stacks and child resources without becoming a universal causal claim?

## Primary evidence

CloudFormation StackResource/StackResourceSummary exposes StackId, LogicalResourceId, ResourceType, PhysicalResourceId, status and timestamps. DescribeStackResources can locate resources by stack identity or by PhysicalResourceId; for deleted stacks, CloudFormation retains resource information for up to 90 days. PhysicalResourceId is the name or unique identifier corresponding to a physical instance ID, and its semantics depend on the resource.

CloudFormation StackSummary exposes StackId, ParentId and RootId for nested stacks. AWS documents nested stacks as a hierarchy; each nested stack has an immediate parent and ultimately a root stack.

AWS Config ConfigurationItem exposes accountId, ARN, Region, resource identity, capture time, relationships and supplementaryConfiguration. AWS Config explicitly supports CloudFormation stacks as a recorded resource type and documents relationships as resource associations. AWS Config also states that direct/indirect relationships can cause additional ConfigurationItems.

## Findings

### 1. Nested-stack identity is materially stronger than a name-only relationship

For nested stacks, CloudFormation provides explicit StackId, ParentId and RootId. This gives a provider-native hierarchy that can bind a nested stack to its parent/root without inferring ancestry from stack names.

Therefore:
nested StackId + ParentId/RootId + resource-type semantics -> BOUNDED_NESTED_STACK_IDENTITY

Parent/root identifiers do not prove every child resource transition occurred because of the parent operation.

### 2. StackResource provides a concrete child-resource mapping layer

A StackResource record binds:
- StackId
- LogicalResourceId
- ResourceType
- PhysicalResourceId
- resource status/timestamp

This is a stronger bridge than matching a CloudFormation event to Config by timestamp alone. It can map a CloudFormation logical resource to the provider's physical identifier, after which the physical identifier can be compared against Config's resourceId/ARN only when the relevant resource-type identity contract supports that comparison.

The bridge remains resource-type-specific. CloudFormation does not establish a universal theorem that every PhysicalResourceId is identical to Config resourceId.

### 3. AWS Config relationships are association evidence, not operation causality

Config relationships describe how resources are related. Config can also generate CIs because of direct or indirect relationships. This makes relationships useful for topology and evidence dependency graphs.

However:
relationship(A,B) != operation(A caused B)

A relationship may explain why a CI exists or why a resource is associated with another resource, but it does not by itself identify the CloudFormation operation, request, operation ID, or causal chain.

### 4. SupplementaryConfiguration is an additional-data channel, not a universal identity oracle

AWS Config documents supplementaryConfiguration as additional contents for certain resource types. Its presence can strengthen resource-specific reconstruction when the provider defines the contained semantics.

Its absence cannot be treated as proof that no relationship or child-resource state existed.

### 5. One-sided evidence remains one-sided

- CloudFormation StackResource + no Config CI: bounded CloudFormation resource mapping; Config observation remains UNKNOWN.
- Config CI + relationship + no StackResource: bounded Config topology/state evidence; CloudFormation participation remains UNKNOWN.
- Both ledgers + exact resource identity + compatible resource type + temporal/state compatibility: BOUNDED_CROSS_LEDGER_BINDING.
- Relationship only or timestamp only: CORRELATION_ONLY.
- Identity/coverage gap: UNKNOWN.

## Anti-collapse rules

- StackName != StackId.
- LogicalResourceId != global resource identity.
- ParentId/RootId != causal operation chain.
- PhysicalResourceId != universal Config resourceId.
- Config relationship != CloudFormation operation causality.
- SupplementaryConfiguration != universal identity/history.
- CI generated by relationship != proof of the triggering operation.
- Deleted-stack 90-day CloudFormation visibility != complete historical retention.
- Timestamp compatibility != causal proof.
- One provider ledger cannot silently close another ledger's missing coverage.
- Current topology != complete historical lifecycle.

## New distilled rule

provider_native_stack_hierarchy + provider_native_child_mapping + exact resource-type identity bridge + compatible temporal/state semantics + coverage/provenance -> BOUNDED_CROSS_LEDGER_BINDING

relationship-only or time-only -> CORRELATION_ONLY

missing identity/coverage -> UNKNOWN
