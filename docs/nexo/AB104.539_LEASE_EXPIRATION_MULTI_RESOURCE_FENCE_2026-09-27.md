# Nexo AB104.539 — Lease expiration during multi-resource fence acquisition

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A multi-resource fence set backed by leases is valid only while every required lease remains valid under the same admission boundary. Staggered TTLs create a partial-validity state: one resource can expire while another remains leased. Renewal success for one member does not prove the complete set remains valid.

## Evidence
etcd leases expire when the cluster does not receive keepAlive within the TTL, and attached keys are deleted on expiry. etcd also states that a client can be uncertain about an operation after timeout or network disruption. Kubernetes Lease uses renewTime and leaseDurationSeconds to determine expiration, with resourceVersion providing the object-version boundary. ZooKeeper ephemeral lock nodes disappear when the associated session ends. These mechanisms show that lease validity is a state observed at an authoritative service, not a local timer assumption. citeturn0search2turn0search12turn0search0turn0search36

## Candidate invariant
For required lease set L:
VALID_FENCE_SET iff every required member is currently valid, belongs to the same admission epoch, matches the expected target incarnation, and has not crossed its expiry/revocation boundary.

If any member becomes UNKNOWN or expired:
VALID_FENCE_SET = false
and external admission is blocked until the complete set is revalidated.

## Staggered TTL race
Example:
A expires at t=10, B expires at t=20.
At t=11, B is still valid but the set {A,B} is not.
Therefore extending B cannot repair the set. A must be reacquired/revalidated, and the operation may need a new FenceSetDigest.

## Renewal race
Renewal must not be treated as a side-channel update that preserves an already-issued authorization indefinitely. Candidate rule:
- renewal is a protected transition;
- it validates current authority, target incarnation, and existing fence lineage;
- it produces a new validity interval or fence revision;
- final external admission revalidates the complete set after renewal.

A renewal response lost in transit is UNKNOWN; retry/recovery must reconcile rather than assume renewal failed or succeeded.

## Lease expiry versus fence semantics
Lease expiration can invalidate the right to continue acting, but it is not automatically evidence that a previously dispatched external effect did not occur. Existing effects retain their independent external-effect state and may require reconciliation.

## Crash boundary
If the process crashes while acquiring A, then B, then renewing A:
- recover the durable acquired subset;
- query authoritative lease state;
- discard expired members;
- do not infer validity from local timers;
- rebuild the complete set before admission.

## Candidate validity structure
FenceMemberValidity = {Scope, AuthorityEpoch, TargetIdentity, TargetIncarnation, FenceRevision, LeaseID, LeaseExpiryBoundary, ObservedAt, ObservationRevision, Status}

FenceSetValidity = {ResourceSetDigest, MemberValidityDigests, AuthorityEpoch, ValidationRevision, ValidUntil/LeaseBound, Status}

## Critical distinctions
- ONE_MEMBER_RENEWED != FENCE_SET_VALID
- LOCAL_TIMER != AUTHORITATIVE_LEASE_STATE
- LEASE_VALID != EXTERNAL_EFFECT_NOT_APPLIED
- RENEWAL_ACK != GLOBAL_REVALIDATION
- LEASE_EXPIRY != RETROACTIVE_CANCELLATION
- LOST_RENEWAL_RESPONSE != RENEWAL_FAILURE
- PARTIAL_LEASE_SET != COMPLETE_FENCE_SET
- LONGER_TTL != STRONGER_AUTHORITY

## Nexo implication
If leases are used as part of fencing, the complete FenceSet must have an explicit validity boundary. Final admission should revalidate every member together, and any expired/unknown member forces HOLD/RE-ADMIT. Lease duration is a liveness parameter, not proof of external effect state.
