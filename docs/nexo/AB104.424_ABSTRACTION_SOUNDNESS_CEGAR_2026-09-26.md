# Nexo AB104.424 — Abstraction Soundness and Counterexample-Guided Refinement

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.423 → AB104.424
Implementation: NOT PERFORMED

## Research question

How can Nexo reduce a large distributed quorum/failure-domain model while preserving the ability to detect real violations and avoiding false safety conclusions caused by an unsound abstraction?

## Evidence

NIST's work on abstraction for model checking explicitly distinguishes sound reductions from reductions that can generate unsound results, and defines a soundness condition for when abstract counterexamples correspond to the original specification. citeturn0search0turn0search24

NASA material describes conservative abstraction: an abstract model may contain additional behaviors, and a safety result on such a conservative abstraction can imply the corresponding concrete safety property; counterexamples may nevertheless be spurious and require refinement. citeturn0search25turn0search26

NASA's CEGAR description separates abstraction, verification, counterexample validation, and refinement, and notes that the loop may continue until a real counterexample is found or the property is verified. citeturn0search27

NIST's current sound-analysis criteria also emphasize that analyzer findings depend on models and assumptions, and that model differences must be explicitly reported rather than silently treated as equivalent. citeturn0search4turn0search13

## Core finding

For safety claims, abstraction cannot silently remove behaviors that matter to the protected property.

Candidate requirement:

ABSTRACT_MODEL must be conservative with respect to the property being proved, or the analysis must explicitly downgrade its conclusion.

Therefore:

ABSTRACTION_VALIDITY != MODEL_SIZE_REDUCTION

and:

ABSTRACT_PROOF != CONCRETE_PROOF

unless the required abstraction relation has been established.

## Two abstraction directions

### A — conservative over-approximation

Abstract model includes every concrete behavior plus possibly extra behaviors.

For safety properties, proving the property on the over-approximation can provide a sound path to the concrete safety property, subject to a valid abstraction relation.

But a counterexample in the abstract model may be spurious.

### B — under-approximation

Abstract model contains only a subset of concrete behaviors.

Finding a real counterexample can be useful.

But proving safety on an under-approximation cannot establish safety of the full concrete system.

Candidate:

UNDER_APPROX_SAFETY_RESULT != GLOBAL_SAFETY_PROOF.

## Property-direction rule

Nexo must record the relation between abstraction and property.

Candidate:

ABSTRACTION_RELATION:
- OVER_APPROXIMATION
- UNDER_APPROXIMATION
- MIXED
- UNKNOWN

For high-consequence claims:

UNKNOWN abstraction relation => no full safety conclusion.

## CEGAR candidate loop

ABSTRACT
→ VERIFY
→ if SAFE: CHECK_ABSTRACTION_SOUNDNESS
→ if COUNTEREXAMPLE:
   → CONCRETIZE
   → if REAL: COUNTEREXAMPLE_FOUND
   → if SPURIOUS: REFINE
→ repeat

A refinement must preserve the original property and remove the identified spurious behavior.

## Spurious counterexample sources

A false abstract counterexample may arise from:

- merged states;
- omitted dependency generations;
- collapsed witness identities;
- collapsed failure domains;
- abstracted time;
- abstracted ordering;
- abstracted resource incarnation;
- abstracted recovery state;
- abstracted UNKNOWN;
- omitted external participant;
- nondeterministic abstraction of deterministic behavior.

Each must be traceable.

## Dangerous abstraction for Nexo

A particularly dangerous simplification is:

WITNESS_A
WITNESS_B
WITNESS_C

→

WITNESS_COUNT = 3

This destroys dependency topology.

Likewise:

DOMAIN_A
DOMAIN_B

→

DOMAIN_COUNT = 2

does not preserve independence if both depend on the same provider.

Therefore:

COUNT_ABSTRACTION != FAILURE_DOMAIN_ABSTRACTION.

## Identity abstraction attack

Collapsing:

RESOURCE_INCARNATION_1
RESOURCE_INCARNATION_2

into one resource can hide replacement semantics.

Candidate:

RESOURCE_INCARNATION_COLLAPSE => POSSIBLE_FALSE_SAFETY.

## Epoch abstraction attack

Collapsing:

AUTHORITY_EPOCH_10
AUTHORITY_EPOCH_11

can hide stale-authority races.

Candidate:

EPOCH_COLLAPSE => TEMPORAL_PROPERTY_UNSOUND.

## UNKNOWN abstraction attack

Mapping:

UNKNOWN → SAFE

is prohibited for security-critical properties.

Mapping:

UNKNOWN → FALSE

may also change semantics depending on the property.

The abstraction must preserve the specified UNKNOWN semantics.

## Recovery abstraction attack

Collapsing NORMAL and RECOVERY states can hide:

- stale restored state;
- continuity-anchor rollback;
- recovery authority escalation;
- missing post-snapshot decisions.

Therefore:

NORMAL ≠ RECOVERY

must remain explicit where recovery is inside the claim boundary.

## External-world abstraction

A model that ends at:

WITNESS_QUORUM

cannot prove:

EXTERNAL_RESOURCE_STATE

unless the model explicitly includes the binding mechanism and its assumptions.

Therefore:

INTERNAL_QUORUM_MODEL != EXTERNAL_EFFECT_MODEL.

## Refinement predicates

When a counterexample is spurious, candidate refinement predicates include:

- witness identity;
- dependency identity;
- failure-domain membership;
- resource incarnation;
- authority epoch;
- fence generation;
- policy generation;
- trust generation;
- graph version;
- recovery generation;
- participant lineage;
- external effect state.

Refinement should target the cause of spuriousness, not arbitrarily increase model detail.

## Refinement minimality

Over-refinement can cause state explosion.

Candidate goal:

MINIMAL_REFINEMENT_SUFFICIENT_TO_SEPARATE_REAL_AND_SPURIOUS_BEHAVIOR.

But minimality itself is not required to be globally optimal; safety takes precedence over performance.

## Abstraction-induced false proof

The highest-risk failure is not a spurious counterexample.

It is an abstraction that removes a real violating behavior and then reports SAFE.

Therefore:

FALSE_NEGATIVE_ABSTRACTION > SPURIOUS_COUNTEREXAMPLE

for safety assurance.

Candidate policy:

If soundness cannot be established, the result cannot be promoted to a full safety claim.

## Abstraction-induced false positive

A conservative over-approximation can generate a spurious counterexample.

This is acceptable if it leads to refinement rather than unsafe rejection of the model's safety claim.

Candidate status:

SPURIOUS_COUNTEREXAMPLE_PENDING_REFINEMENT.

## Three-valued outcome

For a bounded abstract analysis:

SAFE_WITH_SOUND_ABSTRACTION
COUNTEREXAMPLE
INCONCLUSIVE

No fourth implicit state called “probably safe.”

## CEGAR nontermination

CEGAR may fail to terminate because refinements continue without reaching a conclusive abstraction.

Therefore:

REFINEMENT_RESOURCE_EXHAUSTION != SAFE.

Candidate result:

INCONCLUSIVE / HOLD.

## Abstraction poisoning

An attacker could influence the abstraction generator so that a security-critical dependency is collapsed away.

Candidate defenses:

- protected abstraction contract;
- versioned abstraction algorithm;
- preserved-field assertions;
- mutation testing;
- independent reference abstraction;
- final currentness check.

## Differential abstraction

Use distinct abstractions where practical:

ABSTRACTION_A
ABSTRACTION_B

Compare whether both preserve the required property semantics.

Disagreement:

ABSTRACTION_DISPUTED.

This does not automatically establish which abstraction is sound.

## Counterexample certificate

A counterexample should contain:

- abstract trace;
- abstraction version;
- property;
- graph root;
- generations;
- omitted/collapsed fields;
- concretization result;
- real/spurious classification;
- refinement predicate;
- evidence IDs.

Historical counterexamples remain immutable.

## Z1 boundary

A model-checking result is evidence.

Even a result marked CURRENT_VALIDATED does not become authority by itself.

Therefore:

ABSTRACTION_RESULT != Z1_AUTHORITY.

## Residuals

- Formal abstraction relation for Nexo's eventual distributed model remains open.
- Exact property-preserving abstraction predicates remain claim-specific.
- CEGAR termination is not guaranteed.
- Dynamic graph/recovery abstractions need additional research.
- External-world semantics remain outside purely internal model checking unless explicitly modeled.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
