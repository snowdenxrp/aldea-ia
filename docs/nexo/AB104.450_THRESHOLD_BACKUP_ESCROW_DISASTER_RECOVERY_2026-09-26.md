# Nexo AB104.450 — Backup/Escrow Recovery and Disaster Restoration of Threshold Shares

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.449 → AB104.450
Implementation: NOT PERFORMED

## Research question

How can Nexo use backups or escrowed threshold-share material for disaster recovery without resurrecting revoked authority, compromised identities, stale generations, or a compromised trust domain?

## External evidence

NIST SP 800-57 distinguishes key recovery from compromise recovery. Backup exists to recover unavailable keying material, but when compromise is suspected the recovered key should be replaced rather than simply returned to normal use. NIST also warns that every additional copy increases exposure. citeturn0search36turn0search38

NISTIR 8214 identifies recovery/replacement/rejuvenation as a separate concern in threshold systems and notes that stateful participants require consistent recovery sub-protocols. It also recognizes reactive and proactive recovery as distinct modes. citeturn0search37

NIST's 2026 threshold call explicitly treats recovery mechanisms against mobile/adaptive compromise as an augmentation to threshold schemes, not an automatic consequence of having a threshold signature scheme. citeturn0search39

RFC 9162 provides a useful independent-observation pattern: history can be audited for consistency, but transparency evidence does not itself become authority. citeturn0search12

## Core finding

BACKUP_RECOVERY is not AUTHORITY_RESTORATION.

A backup proves that historical keying material was preserved. It does not prove that the corresponding authority is still valid.

Therefore:

BACKUP_MATERIAL != CURRENT_AUTHORITY.

## Attack B1 — restore revoked share

A revoked member's backup is restored after disaster.

Cryptographically valid share material remains available.

It must not regain authority.

Candidate:
RESTORED_SHARE requires current member incarnation + current generation + explicit reactivation.

## Attack B2 — restore old generation

Backup contains G41.
Current authority was G42.

Restoring G41 must not decrease protected authority generation.

Candidate:
RESTORE(G41) can become historical recovery input, but cannot silently become CURRENT_GENERATION.

## Attack B3 — restore compromised share

A share was compromised before disaster.
The backup predates detection and contains the same compromised material.

Recovery from it recreates the compromise.

NIST's compromise-recovery guidance supports replacement after suspected compromise rather than ordinary reuse. citeturn0search36

Result:
COMPROMISED_BACKUP => NON_AUTHORITATIVE.

## Attack B4 — escrow is a hidden root

An escrow service can reconstruct enough shares to restore signing.

If escrow can independently activate authority, it is effectively an authority root.

Therefore escrow must have an explicitly modeled scope and dependency closure.

Candidate:
ESCROW_RECONSTRUCTION_CAPABILITY != AUTHORITY_UNLESS_EXPLICITLY_AUTHORIZED.

## Attack B5 — escrow compromise

All backups are stored under one escrow provider.

Compromise of that provider can defeat the intended threshold independence.

Therefore backup placement requires failure-domain analysis.

BACKUP_DIVERSITY != TRUST_DIVERSITY unless dependencies are independent.

## Attack B6 — backup copies share one encryption key

Backups appear geographically distributed but all use one compromised key-management root.

The apparent redundancy is common-mode.

Candidate:
BACKUP_FAILURE_DOMAIN = dependency closure, not storage location.

## Attack B7 — restore without policy context

Old share is restored but old policy is not restored.

The system cannot infer which governance semantics apply.

Recovery must bind restored material to current policy generation.

## Attack B8 — restore without identity incarnation

Device/member ID is restored from backup and reused.

Old credentials can be confused with a new device.

Candidate:
RESTORE_REQUIRES_IDENTITY_INCARNATION_BINDING.

## Attack B9 — disaster recovery creates a new root accidentally

A fresh key is generated and treated as replacement for the old root.

Cryptographic freshness does not establish authority.

Candidate:
NEW_KEY != NEW_AUTHORITY.

The new root needs an explicit recovery/governance admission.

## Attack B10 — backup rollback of governance state

A complete system snapshot restores:
- old member set;
- old threshold;
- old policy;
- old recovery generation.

The snapshot is internally consistent but externally stale.

This is a classic continuity attack.

Candidate:
SNAPSHOT_CONSISTENCY != CURRENTNESS.

## Attack B11 — partial backup recovery

Only some threshold shares are recovered.

Do not infer that the threshold state is restored.

Need explicit recovered-member set and current-generation validation.

## Attack B12 — backup from mixed generations

Recovered shares come from different generations.

A threshold may accidentally be assembled from incompatible epochs.

Candidate:
MIXED_SHARE_GENERATIONS => REJECT/QUARANTINE.

## Attack B13 — recovery during active compromise

Disaster recovery begins while attacker still controls some original nodes.

Recovered nodes can be re-compromised or receive malicious state.

Recovery must first establish the compromise boundary and isolate affected domains.

## Attack B14 — backup becomes authoritative before reconciliation

Recovered state is activated before external effects are reconciled.

This can cause duplicate or contradictory external actions.

Therefore:
RECOVERED_AUTHORITY != EFFECT_RECONCILIATION_COMPLETE.

## Attack B15 — emergency restore becomes permanent

A disaster-recovery state is left active indefinitely.

Temporary recovery credentials or relaxed constraints can become normal authority.

Candidate:
DISASTER_RECOVERY_MODE requires bounded lifetime and explicit transition back to normal authority.

DISCOVER_BACKUP
→ AUTHENTICATE_BACKUP
→ VERIFY_INTEGRITY
→ IDENTIFY_GENERATION
→ CHECK_COMPROMISE_INTERVAL
→ CHECK_MEMBER_INCARNATIONS
→ CHECK_POLICY_GENERATION

The backup itself never performs the final release.

## Historical vs current state

A backup can establish:

“this material existed and was captured under generation G.”

It cannot automatically establish:

“G is still the current authority.”

Therefore:

BACKUP_EVIDENCE = HISTORICAL_EVIDENCE unless independently revalidated.

## Backup compromise interval

Every backup should be evaluated against the known/unknown compromise interval.

If a root/member was potentially compromised before backup creation:
- backup material is suspect;
- it must not be used as ordinary authority;
- it may still provide historical evidence if its integrity/provenance is preserved.

This preserves epistemic value without granting authority.

## Escrow design constraint

Escrow may preserve availability but must not silently become:
- governance root;
- recovery root;
- policy root;
- currentness oracle.

If escrow can execute all of these functions, its dependency closure belongs inside the corresponding TCB.

## Recovery generation

Restoration must advance into a NEW_RECOVERY_GENERATION.

Candidate:

OLD_GENERATION
→ HISTORICAL_ONLY
NEW_RECOVERY_GENERATION
→ CANDIDATE
→ REVALIDATED
→ CURRENT.

A physical restoration does not reset the logical generation.

## Key rotation after recovery

If compromise cannot be ruled out:

RECOVER_BACKUP
→ DO_NOT_USE_AS_NORMAL_AUTHORITY
→ ESTABLISH_NEW_MEMBER/KEY INCARNATIONS
→ REKEY/RESHARE
→ FENCE_OLD_GENERATION.

This aligns with NIST's distinction between recovering inaccessible material and replacing material after suspected compromise. citeturn0search36

## Backup independence

For claim C:

BACKUP_INDEPENDENCE(C,B)
requires that compromising one backup domain does not by itself satisfy the authority predicate for C and that the backup's recovery dependencies do not collapse the intended threshold independence.

Thus:
GEOGRAPHIC_SEPARATION != INDEPENDENCE.

## Disaster recovery safety boundary

If current authority cannot be reconstructed:

UNKNOWN_CURRENT_AUTHORITY
→ HOLD/QUARANTINE.

Do not choose the newest backup merely because it has the largest generation number.

Generation is useful only when its continuity anchor is itself trusted.
