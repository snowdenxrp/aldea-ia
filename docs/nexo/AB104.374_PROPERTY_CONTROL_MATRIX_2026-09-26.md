## Fresh evidence
RFC 9110 defines conditional requests as preconditions evaluated before the target action; If-Match failure prevents application of the method, with a documented exception when the state-changing request can be determined to have already succeeded. It also states that non-idempotent requests should not be automatically retried unless semantics are known to be idempotent or the original application can be detected. citeturn0search1
AWS Durable Execution documents that at-least-once replay is appropriate for idempotent operations, while non-idempotent external side effects require stronger attempt/retry handling; stable idempotency keys allow providers that support them to deduplicate retries. citeturn0search0

## Property implications
1. NO_EFFECT_FROM_STALE_AUTHORITY cannot be claimed merely because the caller checked authority locally. The provider or a trusted equivalent frontier must enforce the required freshness through the actual effect boundary.
2. NO_LOST_UPDATE requires target conditional/version validation at the resource that owns the mutation. RFC 9110's If-Match is a concrete example of this pattern. citeturn0search1
3. RETRY_DEDUPLICATION requires stable logical identity plus provider semantics that bind repeated requests to that identity; idempotency alone does not prove authorization freshness. citeturn0search0
4. NO_BLIND_RETRY_AFTER_UNKNOWN requires either exact independent reconciliation or a provider contract that makes repetition safe. Otherwise outcome remains UNKNOWN.
5. EXACTLY_ONCE_EXTERNAL_EFFECT is not established by local durable intent, client retry policy, or an idempotency key alone.
6. CROSS_PROVIDER_ATOMICITY is not established by combining individually idempotent providers. Partial commit remains possible unless a separate coordination protocol supplies the required property.
7. IRREVERSIBLE_EFFECT_SAFETY has the strictest admission frontier: if an essential authorization, fencing, identity, or evidence requirement cannot be enforced, admission becomes HOLD/REJECTED under that claimed property.

## Minimal contract by class
E0: identity + authenticated observation + freshness/claim binding.
E1: authority + target condition + effect identity + durable intent + reconciliation; fence when required.
E2: authority + stable idempotency + target condition when relevant + durable intent + reconciliation.
E3: authority + exact identity + target condition + fence + durable intent + reconciliation; compensation is separate effect.
E4: all E3 controls plus explicit irreversible-effect gate, strong external confirmation, and quarantine on UNKNOWN.
E5: E4-like controls per participant plus coordination, partial-commit state, participant reconciliation, and explicit compensation semantics.
