# Nexo AB104.403 — REQUIRED_CONTEXT_SCHEMA Semantic Authority Attack
Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Chain: AB104.402 -> AB104.403

## Question

Can REQUIRED_CONTEXT_SCHEMA itself become a hidden, unbounded TCB or be weakened by policy inheritance, effect-class transitions, dynamic dependencies, migrations, conflicting authorities, recursion, or rollback?

## Evidence reviewed

RFC 9334 separates Verifier appraisal from Relying Party authorization and notes that freshness only narrows recency; state and appraisal policy may change after appraisal. NIST SP 800-162 describes authorization as evaluation of subject/object/operation/environment attributes against policy. XACML explicitly treats required missing attributes as Indeterminate rather than permitting a definitive decision.

These sources support the architectural direction but do not prove Nexo's model.

## Primary attack

If REQUIRED_CONTEXT_SCHEMA is produced by a single mutable derivation engine and Z1 trusts its output as complete, the derivator becomes a hidden authority:

CLAIM -> DERIVATOR -> "complete context" -> Z1 GRANT

A compromised, buggy, stale, or downgraded derivator can remove a dependency while still producing a internally consistent root.

Therefore schema integrity is not semantic authority.

## Result: two independent obligations

1. SEMANTIC_REQUIREMENT:
   What context is actually required to establish the protected property?
2. INSTANCE_CLOSURE:
   Does the concrete evaluation contain and validate every required dependency?

Candidate chain:

PROTECTED PROPERTY CONTRACT
+ EFFECT CLASS
+ PROTECTED POLICY/SCHEMA
+ SEMANTIC RULE VERSION
-> REQUIRED_CONTEXT_REQUIREMENT
-> REQUIRED_SET_ROOT
-> INSTANCE CLOSURE
-> Z1 FINAL GATE

The derivator may compute this, but its algorithm/version/trust basis is itself part of the assurance boundary.

## Attack matrix

### 1. Policy inheritance
Child policy silently drops a parent dependency.

Result: child cannot weaken inherited safety requirements unless a new semantic validation boundary explicitly establishes the weaker property.

### 2. Effect-class transition
An operation changes from E1 to E4/E5 but retains the old context schema.

Result: re-derive requirements from the new effect class; old admission cannot be reused.

### 3. Dynamic dependency
A runtime branch introduces a resource, provider, capability, or authority dependency after closure.

Result: previous admission does not cover it. New evaluation/admission boundary required.

### 4. Migration/schema coexistence
Old and new schema versions coexist and an older version has fewer dependencies.

Result: version rollback/coexistence must not reduce the protected required set for the same claim/property. Ambiguous schema selection => HOLD/UNKNOWN.

### 5. Conflicting authorities
Policy A says resource incarnation matters; Policy B says it does not.

Result: no arbitrary precedence inside the derivator. Conflict => DISPUTED/UNKNOWN until an authoritative precedence rule resolves it.

### 6. Recursive derivation
A dependency rule requires another schema, which requires the first.

Result: cycle must be explicit and bounded. Unresolved cycle => INCOMPLETE/UNKNOWN, never silently treated as closure.

### 7. Rollback
A valid old REQUIRED_SET_ROOT is replayed after policy/schema/security changes.

Result: historical validity is not current validity. Current policy/schema generation must bind the root.

### 8. Effect-class under-declaration
A contract declares E2 while the actual external operation has E4 semantics.

Result: effect class must be independently derived/validated from the protected operation semantics; caller declaration alone is insufficient.

### 9. Optionality downgrade
A required field becomes OPTIONAL/ANY/null-compatible.

Result: semantic weakening requires explicit new validation; syntax/version compatibility cannot authorize it.

### 10. Resource/path substitution
The same claim is executed through a different adapter or provider path with different enforcement capabilities.

Result: path identity/capability profile becomes required when enforcement semantics depend on it.

## Key boundary

The derivation engine must not be allowed to answer all three questions alone:

A. What property is being claimed?
B. What dependencies are necessary to establish it?
C. Whether those dependencies are currently satisfied.

At minimum, A/B must be anchored in protected claim/effect/policy semantics, while C is evaluated against current authoritative state.

Otherwise the system risks circularity:
"the context is complete because the component that defines completeness said so."

## Candidate schema contract

REQUIRED_CONTEXT_SCHEMA should carry, at minimum:

- schema_id / version
- claim/property class
- effect class
- policy/schema versions
- semantic rule version/digest
- required dependency classes
- applicability conditions
- REQUIRED_SET_ROOT
- derivation provenance
- invalidation dependencies
- conflict/cycle status
- resource/path constraints where applicable
- limitations
- validation status

A root over this object gives integrity, not correctness or completeness.

## Dynamic dependency rule

A dependency discovered after final authorization cannot be silently appended to an already-authorized closure.

Candidate invariant:

NEW_REQUIRED_DEPENDENCY => NEW_ADMISSION_BOUNDARY

This prevents hidden runtime branches from expanding the effective TCB after authorization.

## Monotonic safety rule

For the same protected property, a schema update may add requirements, but cannot remove an existing required dependency without explicit semantic revalidation.

Candidate:

SCHEMA_UPDATE_REMOVAL_OF_REQUIRED_DEPENDENCY => NEW_PROPERTY_VALIDATION

This is stronger than ordinary version compatibility.

## Effect-class binding

Required context must be derived using the effective effect class, not merely the declared one.

Candidate:

EFFECT_CLASS_EFFECTIVE = independent semantic classification of the protected operation

If declared_effect_class != effective_effect_class:
REJECT / HOLD / REVALIDATE.

## Conflict and uncertainty

Borrowing the important fail-closed shape seen in XACML, missing required information should not silently become permission. XACML treats missing required attributes as Indeterminate; Nexo should apply its own stronger claim-specific UNKNOWN/HOLD/REVALIDATE semantics.

UNKNOWN is particularly important for:
- unresolved policy precedence,
- incomplete dependency derivation,
- recursive closure,
- schema ambiguity,
- dynamic dependency discovery,
- stale derivation engine trust.

## New invariants

- REQUIRED_CONTEXT_SCHEMA_IS_NOT_AUTHORITY
- DERIVATOR_CANNOT_SELF_DEFINE_COMPLETENESS
- SEMANTIC_REQUIREMENT != INSTANCE_CLOSURE
- EFFECT_CLASS_MUST_BE_BOUND_TO_PROTECTED_OPERATION
- SCHEMA_ROLLBACK_CANNOT_WEAKEN_REQUIRED_CONTEXT
- REQUIRED_DEPENDENCY_REMOVAL_REQUIRES_REVALIDATION
- NEW_REQUIRED_DEPENDENCY_REQUIRES_NEW_ADMISSION_BOUNDARY
- CONFLICTING_REQUIREMENTS_CANNOT_SELF_RESOLVE
- RECURSIVE_REQUIREMENT_CYCLES_CANNOT_COUNT_AS_CLOSURE
- HISTORICAL_ROOT != CURRENT_AUTHORITY
- DERIVATION_INTEGRITY != SEMANTIC_CORRECTNESS

## Remaining UNKNOWN

- Exact mechanism for independently deriving effective effect class.
- Exact protected authority for semantic rule precedence.
- How to bound dynamic dependency discovery without universal state capture.
- How to formally prove completeness of the requirement derivation.
- Whether a small trusted kernel can validate required-context schemas without reproducing the full semantic model.
- No implementation, formal proof, or runtime verification performed.

## Exact next action

AB104.404 — attack the boundary between EFFECT_CLASS, protected property semantics, and REQUIRED_CONTEXT_SCHEMA: attempt to make a low-consequence class inherit high-consequence behavior, hide irreversible effects behind reversible declarations, exploit provider-specific semantics, and create cross-resource operations whose effective class cannot be determined statically.

DO NOT implement Nexo architecture from this result.
