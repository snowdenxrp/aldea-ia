# Nexo AB104.448 — Threshold Membership Rotation, Proactive Resharing and Generation/Fencing Semantics

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.447 → AB104.448

## Research question

Can Nexo rotate threshold shares or membership without accidentally preserving compromised authority, admitting stale members, or breaking continuity?

## External evidence

NIST's threshold-cryptography work explicitly treats setup and maintenance, system models, security tradeoffs, and implementation validation as part of threshold-scheme security rather than assuming the primitive alone is sufficient. citeturn0search3turn0search7

NIST also identifies proactive recovery/rejuvenation as important in long-lived threshold systems: compromised components may need replacement or refreshing, and stateful nodes require a consistent recovery sub-protocol. It warns that recovery can have different synchrony and failure assumptions from the normal protocol. citeturn0search36

Research on dynamic proactive secret sharing demonstrates that membership and threshold can change over time, but those changes are themselves protocol operations rather than merely changing a list. citeturn0search4

Research on proactive refresh for accountable threshold signatures shows that shares can be refreshed while retaining the same public key/threshold in some constructions, but security/accountability properties depend on the construction. citeturn0search0

NIST's 2026 threshold call requires technical specifications, reference implementations, and experimental evaluation, reinforcing that a theoretical threshold property must not be promoted directly to an implementation claim. citeturn0search1turn0search6

## Core distinction

Three different operations must not be conflated:

1. SHARE_REFRESH — same logical membership/authority, new secret shares.
2. MEMBER_ROTATION — logical signer set changes.
3. AUTHORITY_ROTATION — the protected authority generation itself changes.

They have different continuity semantics.

Therefore:

SHARE_REFRESH != MEMBER_ROTATION != AUTHORITY_ROTATION.

## Attack R1 — compromised member survives refresh

A signer is compromised before refresh.
A normal proactive resharing distributes fresh shares but the compromised participant remains a valid member.

If the adversary retains enough current participation/control, refresh did not solve the membership problem.

Result:
SHARE_REFRESH != COMPROMISE_ERADICATION.

## Attack R2 — removed member receives new share

A revoked member participates in the refresh protocol and obtains a new share.

Membership eligibility must be frozen before share distribution.

Candidate:
MEMBER_SET_VERSION captured at refresh start and revalidated at commit.

## Attack R3 — stale share after rotation

Old member holds a valid old share.
New governance state is active.

Old share must not authorize the new generation.

Candidate signing context:
AUTHORITY_GENERATION + MEMBER_SET_VERSION + MEMBER_INCARNATION.

## Attack R4 — public key continuity hides authority change

Proactive refresh may preserve the same public key while changing the internal shares. This can be cryptographically desirable, but it can also obscure that membership or recovery state changed.

Therefore public-key equality cannot be used as proof that governance state is unchanged.

Invariant:
SAME_PUBLIC_KEY != SAME_GOVERNANCE_STATE.

## Attack R5 — refresh under stale policy

Refresh begins under policy P7.
Policy changes to P8.
Nodes complete refresh using P7.

The resulting share set must not become current merely because the cryptographic protocol completed.

Candidate:
POLICY_GENERATION captured at prepare and checked at commit.

## Attack R6 — partial resharing

Some members receive new shares.
Others retain old shares.
System crashes.

Do not infer completion from local success.

Need explicit refresh transaction state:
PREPARED → DISTRIBUTION_STARTED → DISTRIBUTION_COMPLETE → ACTIVATED
with a durable generation boundary.

## Attack R7 — old and new shares accepted simultaneously

During transition, both old and new shares can produce valid signatures.

This creates an overlap window in which stale authority may remain effective.

Candidate:
OLD_SHARE_ACCEPTANCE_CUTOFF = protected activation boundary.

After activation:
old generation => reject.

## Attack R8 — rollback after successful rotation

System restores old share metadata or old member set.

Cryptographic signatures from old shares remain valid unless generation/fencing is checked.

Therefore:
ROLLBACK_RESISTANCE_REQUIRES_DURABLE_GENERATION_STATE.

## Attack R9 — member replacement with reused identity

Member M1 is removed.
A new device is assigned the same MemberID.

Without incarnation, old credentials/records can be confused with the new member.

Candidate:
MEMBER_ID + MEMBER_INCARNATION.

## Attack R10 — replacement inherits compromised dependencies

A new signer is provisioned from the same compromised image, identity provider, administrator, or cloud control plane.

New key material does not guarantee a new trust domain.

Candidate:
REPLACEMENT_INDEPENDENCE_REQUIRES_DEPENDENCY_CLOSURE_RECHECK.

## Attack R11 — proactive refresh crosses a compromise window

Refresh protocol assumes fewer than t compromised participants during the refresh interval.
An adaptive attacker compromises additional participants during the protocol.

Security depends on the protocol's explicit adversary model and timing assumptions.

Therefore:
REFRESH_SAFETY_REQUIRES_EXPLICIT_COMPROMISE_MODEL.

## Attack R12 — recovery protocol is weaker than normal protocol

Normal signing tolerates a Byzantine model, but recovery assumes synchrony or a trusted dealer.

This can create the weakest-link recovery path.

Invariant:
RECOVERY_PROTOCOL_SECURITY >= REQUIRED_RECOVERY_PROPERTY.

## Attack R13 — dealer becomes hidden root

A central dealer generates/distributes replacement shares.

This can silently reintroduce single-party authority.

If a dealer exists, its trust and compromise impact must be explicitly included in the dependency closure.

## Attack R14 — refresh accidentally changes logical authority

A share refresh intended only to rejuvenate nodes changes signer membership or threshold.

This is not a refresh; it is a governance transition.

Therefore operation type must be explicit.

## Candidate generation model

AUTHORITY_GENERATION G
MEMBER_SET_VERSION M
MEMBER_INCARNATION I
SHARE_GENERATION S
POLICY_GENERATION P
RECOVERY_GENERATION R.

A signing authorization context is bound to the complete relevant tuple:

(G, M, I, S, P, R, CLAIM_SCOPE, EFFECT_SCOPE).

Not every operation necessarily needs every component, but protected dependencies must be explicit.

## Candidate rotation protocol

ROTATION_PREPARE:
- capture current G/M/P/R;
- define target member set;
- define target threshold;
- define target share generation;
- calculate dependency closure;
- establish transition ID.

ROTATION_VALIDATE:
- verify current authority;
- verify member identities/incarnations;
- verify failure-domain constraints;
- verify target policy;
- verify no forbidden compromise;
- verify recovery mode.

ROTATION_DISTRIBUTE:
- perform protocol-specific share generation/refresh;
- produce participant evidence;
- prevent revoked members from becoming current.

ROTATION_COMMIT:
- protected linearization point;
- atomically advance relevant generation/version;
- activate target member set;
- fence old member/share generation.

ROTATION_RECONCILE:
- verify participant state;
- verify old generation is rejected;
- record failures/partial state.

## Important distinction: refresh vs rotation

### Share refresh

Possible semantics:
G unchanged
M unchanged
P unchanged
R unchanged
S increments.

This can preserve logical authority while rejuvenating secret shares.

### Member rotation

Possible semantics:
G may remain logically continuous
M increments
I changes for affected members
S increments.

Requires membership governance.

### Authority rotation

Possible semantics:
G increments
M/S/P may also change
old G fenced.

This is a recovery/security-boundary transition.

## Candidate fencing rule

For protected signing:

ACCEPT(signature, context)
only if:
- context.G == CURRENT_G;
- context.M == CURRENT_M;
- signer incarnation current;
- share generation accepted;
- policy generation current;
- recovery generation current;
- signer status ACTIVE;
- no quarantine/conflict.

A valid cryptographic signature from an old generation is evidence of cryptographic possession, not current authority.

## Recovery after suspected compromise

If one member is compromised:

1. freeze affected authority if claim requires;
2. revoke/suspend member;
3. establish new member set;
4. invalidate old admission contexts;
5. execute approved rotation/resharing protocol;
6. advance protected generation;
7. verify old shares cannot authorize;
8. revalidate dependencies;
9. explicitly release.

If compromise scope is uncertain, treat the affected trust domain as UNKNOWN and expand quarantine rather than assuming only the named member was compromised.

## Availability boundary

If rotation cannot safely complete:
- preserve current safe state if still trusted;
- otherwise quarantine;
- never force completion by accepting stale or unauthorized shares;
- do not lower threshold automatically.

This separates:
SAFETY
from
LIVENESS.
