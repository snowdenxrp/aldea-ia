# Nexo AB104.443 — Hardware Vendor / Provider Trust Boundary Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.442 → AB104.443
Implementation: NOT PERFORMED

## Research question

What happens when the vendor, firmware supply chain, attestation root, HSM provider, or update path is compromised, and how can Nexo contain that compromise without making the vendor an implicit Z1 authority?

## Evidence

NIST SP 800-193 treats platform firmware resilience as protection, detection, and recovery and emphasizes authenticated updates, protected recovery, and platform-specific recovery controls. citeturn0search0turn0search48

NIST SP 800-155 describes firmware integrity measurement and the need for trustworthy update/measurement infrastructure. citeturn0search3

NIST SP 800-218 (SSDF) treats secure software development practices as a supply-chain risk control, but does not make a software vendor an authority over a deployed system's runtime state. citeturn0search4

RFC 9334 separates manufacturer/platform claims, attestation evidence, verifier appraisal, trust anchors, and relying-party authorization. This is directly relevant to preventing “vendor attestation == Nexo authority.” citeturn0search1

SLSA's provenance model similarly distinguishes evidence about build provenance from the downstream policy decision that consumes that evidence. citeturn0search5

## Core finding

Vendor trust is one dependency in the claim's trust graph, not a universal authority.

Therefore:

VENDOR_ATTESTATION != CURRENT_NEXO_AUTHORITY

and:

HARDWARE_AUTHENTICITY != FIRMWARE_SEMANTIC_CORRECTNESS.

## Attack V1 — malicious firmware update

Firmware image is correctly signed by the vendor but contains malicious behavior.

A signature proves authorized signing under the vendor key, not that the firmware satisfies Nexo's semantic property.

Required separation:
SIGNATURE_VALID
→ AUTHENTICATED_SOURCE
→ SOFTWARE_APPRAISAL
→ NEXO_POLICY_DECISION.

No automatic authority promotion.

## Attack V2 — compromised vendor signing key

A vendor signing key is compromised.

Previously valid firmware may remain cryptographically authentic while becoming unacceptable for new deployments.

Candidate:
VENDOR_KEY_COMPROMISE
→ TRUST_GENERATION_INVALIDATION
→ AFFECTED_FIRMWARE_IDENTIFICATION
→ PLATFORM_FREEZE/RESTRICTION
→ REATTESTATION
→ REVALIDATION.

Historical evidence may remain useful for reconstruction but not automatically for new authority admission.

## Attack V3 — malicious firmware rollback

A vendor-signed older image is installed.

Signature remains valid.

Anti-rollback must independently enforce a version/generation floor.

Therefore:
SIGNED_OLD_IMAGE != CURRENT_ALLOWED_IMAGE.

## Attack V4 — compromised attestation root

An attestation root key is compromised.

All downstream attestations depending on it may become suspect.

The trust-root generation becomes a protected dependency.

Candidate:
ATTESTATION_ROOT_COMPROMISE
→ VERIFIER_TRUST_INVALIDATION
→ AFFECTED_EVIDENCE_CLOSURE
→ QUARANTINE
→ NEW_TRUST_ROOT
→ REATTESTATION
→ CLAIM_REVALIDATION.

## Attack V5 — vendor claims “secure”

Vendor documentation says a feature is secure or monotonic.

Documentation is evidence about a claimed capability, not verification of Nexo's required property.

This extends AB104.388:

DOCUMENTED_FEATURE != OBSERVED_BEHAVIOR != VERIFIED_PROPERTY.

## Attack V6 — update infrastructure compromise

The vendor's distribution channel is compromised.

An attacker can alter or replace packages before deployment.

Candidate controls:
- authenticated content;
- independent digest verification;
- provenance;
- trusted release metadata;
- local policy floor;
- staged rollout;
- independent validation;
- rollback/recovery path.

But provenance still remains evidence, not Z1 authority.

## Attack V7 — HSM/cloud provider control-plane compromise

A cloud HSM service may protect key material while its surrounding identity/control plane is compromised.

Therefore:
HSM_KEY_PROTECTION != PROVIDER_CONTROL_PLANE_CORRECTNESS.

If the provider can silently alter:
- authorization;
- cluster membership;
- key lifecycle;
- backup/restore;
- attestation;
- firmware state;

then those become dependencies in the claim.

## Attack V8 — provider-issued “current” status

Provider API says:
CURRENT = true.

Nexo must not treat that field as authoritative merely because it comes from the provider.

Provider status is an evidence input requiring appraisal against Nexo's protected state and dependency policy.

## Attack V9 — vendor rollback of attestation policy

Vendor verifier/firmware policy is rolled back.

Old software may begin satisfying old policy.

Therefore:
VERIFIER_POLICY_GENERATION < REQUIRED_POLICY_GENERATION
=> APPRAISAL_STALE.

## Attack V10 — vendor recovery procedure restores vulnerable state

A vendor recovery process can legitimately restore firmware but accidentally reintroduce revoked software.

Recovery must be treated as a new state transition with explicit generation and anti-rollback checks.

## Attack V11 — vendor outage

Vendor attestation/update service becomes unavailable.

For claims that require live vendor evidence:
VENDOR_EVIDENCE_UNAVAILABLE => DEPENDENCY_UNKNOWN.

Nexo may continue only if an already-valid independent continuity basis explicitly covers the property.

No silent fail-open.

## Attack V12 — vendor dependency common mode

TPM, firmware, attestation service and verifier all originate from the same vendor.

They can produce multiple apparently independent signals while sharing one failure domain.

Therefore:
MULTIPLE_VENDOR_COMPONENTS != INDEPENDENT_EVIDENCE.

## Attack V13 — hardware replacement through vendor RMA

RMA device arrives with a new hardware identity.

The vendor says it is “the same device.”

Nexo requires an explicit replacement/incarnation record.

Candidate:
RMA_REPLACEMENT != SAME_HARDWARE_INCARNATION.

## Attack V14 — vendor emergency override

Vendor requests an emergency authorization to restore functionality.

Vendor emergency status does not automatically grant Nexo authority.

Emergency transition must be represented in Nexo's own authority/policy model.

## Attack V15 — malicious support/recovery credentials

Vendor support account can access recovery mechanisms.

Those credentials must be modeled as a separate authority domain with explicit scope, auditing, expiry/revocation, and protected transition semantics.

Support access is not universal authority.

## Independence requirement

For high-consequence claims, Nexo should not count several signals as independent merely because they have different APIs.

Independence analysis must include:
- vendor;
- firmware;
- attestation root;
- verifier;
- policy source;
- storage;
- deployment;
- update path;
- cloud provider;
- operator;
- recovery infrastructure.

## Important boundary

The vendor can provide:
- hardware identity evidence;
- firmware provenance;
- attestation evidence;
- documented capabilities;
- security advisories.

Nexo Z1 decides:
- whether those claims are sufficient;
- whether they are current;
- whether dependencies are acceptable;
- whether authority may be granted;
- whether effects may proceed.

Therefore:

VENDOR_EVIDENCE → APPRAISAL → Z1 POLICY → AUTHORITY.

Not:

VENDOR_EVIDENCE → AUTHORITY.

## New invariants

- VENDOR_ATTESTATION != CURRENT_NEXO_AUTHORITY
- HARDWARE_AUTHENTICITY != FIRMWARE_SEMANTIC_CORRECTNESS
- SIGNATURE_VALID != SAFE_CURRENT_FIRMWARE
- VENDOR_KEY_COMPROMISE_INVALIDATES_DEPENDENT_CURRENTNESS
- ATTESTATION_ROOT_COMPROMISE_INVALIDATES_DEPENDENT_APPRAISALS
- DOCUMENTED_FEATURE != VERIFIED_PROPERTY
- HSM_KEY_PROTECTION != PROVIDER_CONTROL_PLANE_CORRECTNESS
- PROVIDER_STATUS != NEXO_AUTHORITY
- VERIFIER_POLICY_ROLLBACK => APPRAISAL_STALE
- VENDOR_EVIDENCE_UNAVAILABLE != AUTOMATIC_FAIL_OPEN
- MULTIPLE_VENDOR_COMPONENTS != INDEPENDENT_EVIDENCE
- RMA_REPLACEMENT != SAME_HARDWARE_INCARNATION
- VENDOR_EMERGENCY != NEXO_AUTHORITY
- SUPPORT_CREDENTIAL != UNIVERSAL_AUTHORITY
- VENDOR_COMPROMISE_REQUIRES_DEPENDENCY_CLOSURE
- VENDOR_EVIDENCE_REMAINS_EVIDENCE
- HARDWARE_ROOT_REQUIRES_EXTERNAL_POLICY_SEMANTICS

## Residuals

- Need analyze vendor compromise when no independent alternative trust root exists.
- Need distinguish firmware compromise from hardware silicon compromise.
- Need research certificate/attestation root rotation and emergency revocation.
- Need model supply-chain evidence freshness and revocation.
- Need formalize how much assurance remains when one major vendor domain is fully compromised.
- Fault injection, formal verification, and implementation remain unperformed.
