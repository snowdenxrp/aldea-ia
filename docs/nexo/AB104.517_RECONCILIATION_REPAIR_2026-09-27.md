## Evidence
AWS EC2 documents that mutating API calls can time out or encounter server issues while asynchronous workflows may already have progressed; idempotency prevents successful retries from performing duplicate actions when the same client token and parameters are reused. citeturn0search2 Cloud Storage documents socket timeouts/TCP disconnects as retryable conditions whose safety depends on idempotency, and defines conditionally idempotent operations using generation/ETag preconditions. citeturn0search3 Cloud Storage generation preconditions reject a mutation with `412 Precondition Failed` when the targeted generation does not match, and its retry guidance uses these preconditions to avoid races caused by delayed duplicate requests. citeturn0search0

## Canonical finding
Provider-side preconditions can establish a provider-local rejection at the mutation boundary, but a lost response remains ambiguous. Nexo therefore separates:
- `PRECONDITION_REJECTED`: provider explicitly evaluated and rejected the predicate;
- `APPLIED_CONFIRMED`: exact operation/effect and target incarnation are confirmed at provider scope;
- `NOT_APPLIED_CONFIRMED`: provider-authoritative evidence establishes non-application;
- `UNKNOWN`: timeout, disconnect, crash, ambiguous server error, or insufficient reconciliation evidence.

`UNKNOWN != PRECONDITION_REJECTED`
`UNKNOWN != NOT_APPLIED`
`UNKNOWN != SUCCESS`

## Retry contract
A retry after UNKNOWN may remain the same logical operation only when the provider's idempotency scope and request binding permit it:
`OperationID + EffectID + RequestDigest + TargetIdentity + TargetIncarnation + ProviderIdempotencyScope`.

AWS requires the same client token and parameters for safe reuse of an idempotent request. citeturn0search2 Cloud Storage distinguishes always-idempotent, conditionally idempotent, and non-idempotent operations; retry safety therefore depends on the actual operation contract. citeturn0search3

`SAME_OPERATION_RETRY => SAME_CANONICAL_REQUEST_DIGEST`
`TIMEOUT => NO_AUTOMATIC_RETRY_PERMISSION`
`UNKNOWN + NON_IDEMPOTENT_PROVIDER => NO_BLIND_RETRY`

## Reconciliation
For UNKNOWN:
`PRESERVE_EFFECT_ID → AUTHORITATIVE_PROVIDER_LOOKUP → APPLIED | NOT_APPLIED | UNKNOWN`.

A new EffectID must not be created merely because the executor crashed or the response was lost. If the provider cannot resolve the original operation within the evidence required by the effect class, UNKNOWN persists or the operation is quarantined.

## Race example retained
Cloud Storage explicitly describes a delayed original delete arriving after a later delete and recreation, and shows generation-match preconditions preventing the stale request from affecting the new generation. citeturn0search0 This is concrete evidence for Nexo's `TargetIncarnation + ProviderPrecondition` rule.
