# Nexo AB104.395 — Coherent Dependency Snapshot and Linearization Boundary

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective
Determine whether the closure engine can evaluate a dependency graph and its protected dependency state from one coherent snapshot, while keeping the authoritative TCB minimal.

Freshness research in RFC 9334 explicitly recognizes that evidence can become stale immediately after generation and discusses epoch transitions, race conditions, windows and retry behavior. This supports treating freshness/version checks as protected state rather than as a timestamp-only property. citeturn0search0turn0search1

## 1. Core race
Candidate timeline:
1. Closure engine reads graph version G10.
2. Dependency D is observed at epoch E7.
3. D changes to E8.
4. Graph is still G10.
5. Engine records VALIDATED_CURRENT using E7.

This result is unsafe if the claim requires current D. A graph snapshot without a protected dependency-state snapshot is insufficient.

Reverse attack:
1. Graph changes from G10 to G11.
2. Engine has already traversed G10.
3. New dependency D2 exists only in G11.
4. Engine commits a G10 result as if it were current G11.

Therefore both graph identity and dependency-state identity must participate in the evaluation boundary.

## 2. Candidate snapshot object
Define a candidate immutable evaluation context:

EVALUATION_SNAPSHOT = {
  graph_version,
  graph_root_digest,
  claim_policy_version,
  dependency_state_versions[],
  resource_incarnations[],
  authority_epoch,
  evidence_set_id,
  freshness_basis
}

Not every field must be globally authoritative. The protected set should contain only values required for the specific claim.

## 3. Candidate linearization rule
A current-use evaluation is admissible only if:

SNAPSHOT_CAPTURED
AND GRAPH_INTEGRITY_VALID
AND CLOSURE_COMPLETE
AND REQUIRED_DEPENDENCY_VERSIONS_MATCH
AND RESOURCE_INCARNATIONS_MATCH
AND POLICY_VERSION_MATCHES
AND AUTHORITY_REQUIREMENTS_HOLD
AND NO_INVALIDATION_OCCURRED

at one protected commit/equivalent validation boundary.

If any protected generation changes before the evaluation is durably accepted, the candidate result is discarded and re-evaluated from a fresh snapshot.

This is analogous to optimistic validation, but no implementation mechanism is selected yet.

## 4. Attack — graph mutation during evaluation
Graph G10 is captured, then G11 is committed before evaluation result acceptance.
Result: G10 evaluation cannot be accepted as a G11 current claim. Either G10 remains a historical evaluation or the engine retries against G11.

## 5. Attack — dependency mutation during evaluation
D changes E7→E8 after capture but before result acceptance.
If D is currentness-required, the E7 result fails final validation. It must not be promoted to CURRENT.

## 6. Attack — policy migration
Policy P7 is replaced by P8 while evaluation is running.
P7 evidence remains historical. A P8-required current claim must be re-evaluated under P8 unless an explicit protected compatibility rule exists.

## 7. Attack — resource replacement
Resource R incarnation I1 becomes I2 during evaluation.
Any claim bound to I1 must not silently bind to I2. The I1 evaluation is historical or invalid for current use; I2 requires its own evidence/dependency binding.

## 8. Attack — authority rollover
Authority epoch A4 becomes A5 while closure evaluation is in progress.
If current authority is a required dependency, the A4 snapshot cannot authorize current use after A5 unless the claim explicitly permits a bounded epoch transition. Such compatibility must itself be protected policy state.

## 9. Migration and version coexistence
During schema or graph migration, both old and new representations may coexist.
Candidate rule:
- historical G_old evaluations remain readable;
- current evaluation must identify the canonical graph generation;
- compatibility mappings are explicit protected artifacts;
- a migration mapping cannot silently manufacture missing dependencies;
- if old and new graphs disagree on required closure, current status becomes UNKNOWN until resolved;
- migration completion does not retroactively rewrite historical evidence.

## 10. Revocation race
Candidate timeline:
1. Evidence result V is current under policy P8.
2. Revocation R is issued.
3. Closure engine has a cached V.
4. Current operation requests V before cache refresh.

Safety-critical use must consult the authoritative revocation/invalidation state or an explicitly bounded freshness mechanism. A stale cache cannot be treated as proof that V remains current.

RFC 9334's epoch discussion similarly notes that epoch transitions create race conditions and that solutions may require retries or explicit epoch windows. citeturn0search0

## 11. Minimal TCB direction
Do not put the entire evidence graph inside the authoritative core merely to obtain coherence.
Candidate minimal protected frontier:
- graph root/version/digest;
- claim-policy version;
- required dependency versions/epochs/incarnations;
- relevant authority epoch;
- invalidation/revocation generation;
- evaluation commit record.

Large evidence bodies, historical provenance, ordinary graph traversal, indexing and analytics may remain outside the authoritative core if their integrity is cryptographically/procedurally bound to the protected frontier.

This preserves the architectural rule: only authority-critical state belongs in the protected core unless further evidence proves otherwise.

## 12. Candidate two-phase evaluation
Phase A — Build:
Resolve graph snapshot and dependency closure outside the protected commit path; produce a candidate snapshot digest.

Phase B — Validate/commit:
At the protected boundary, re-check graph root/version, required dependency versions, policy version, resource incarnations, authority epoch and invalidation generation. If all match, persist the evaluation result. Otherwise reject and retry.

Important limitation: this protects the consistency of the local evaluation record. It does not itself prove that an external resource has remained unchanged after the boundary.

## 13. Attack — snapshot starvation
An adversary or high-churn environment can continually change dependencies so every evaluation fails.
Safety response: never weaken validation merely to obtain liveness. Enter HOLD/DEGRADED/UNKNOWN according to policy, with bounded retry/backoff and resource-exhaustion protection.

## 14. Attack — dependency-set expansion at the boundary
A dependency that was not in the candidate closure becomes required because another dependency changes.
Required behavior: the protected boundary must validate the dependency-set root itself. If the required closure root changed, the old evaluation cannot commit.

## 15. Candidate invariants
- GRAPH_AND_DEPENDENCY_STATE_MUST_BE_COHERENT
- NO_CROSS_GENERATION_CLOSURE
- CURRENT_CLAIM_REQUIRES_FINAL_VERSION_VALIDATION
- RESOURCE_INCARNATION_MUST_MATCH
- POLICY_VERSION_MUST_MATCH
- AUTHORITY_EPOCH_MUST_MATCH_WHEN_REQUIRED
- REVOCATION_GENERATION_MUST_BE_CURRENT_WHEN_REQUIRED
- CACHE_FRESHNESS != AUTHORITATIVE_CURRENTNESS
- MIGRATION_MAPPING_CANNOT_MANUFACTURE_DEPENDENCIES
- HISTORICAL_EVIDENCE_IS_NOT_REWRITTEN
- SAFETY_VALIDATION_MUST_NOT_BE_WEAKENED_FOR_LIVENESS
- SNAPSHOT_STARVATION != PERMISSION_TO_BYPASS_VALIDATION

## Status
AB104.395 establishes a candidate coherent-snapshot/validation boundary and identifies the minimum protected frontier needed to avoid mixing graph and dependency generations.

Not proven: formal atomicity, completeness of the dependency-set root, migration correctness, revocation propagation correctness, or implementation correctness.

## Exact next action
AB104.396 — attack the dependency-set root itself: determine whether closure completeness can be represented by a stable root/digest, how graph mutations are serialized, and whether an omitted dependency can evade final validation.
