# Nexo AB104.540 — Safe lease/fence handoff between old and new holders

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A new holder must not become externally effective merely because it has acquired a new lease. The handoff must establish an ordered succession in which the old holder is no longer permitted to create new protected effects before the new holder is admitted. A lease/leadership change alone is insufficient unless the downstream resource enforces the corresponding fencing token.

## Evidence
ZooKeeper leader election uses ephemeral sequential nodes: the smallest sequence is leader, and deletion of the ephemeral node causes succession. ZooKeeper explicitly warns that a create can succeed while the response is lost, requiring recovery by checking server state. etcd's election implementation binds leadership to a lease and uses the leader key's creation revision in transactions to test ownership. A current fencing implementation example based on etcd revisions has the downstream resource reject lower fencing tokens; this illustrates the required provider-side enforcement boundary. citeturn0search0turn0search6turn0search5

## Candidate handoff protocol
OLD_ACTIVE(F_old)
-> SUCCESSION_PREPARED
-> OLD_FENCE_SUPERSEDED
-> NEW_FENCE_COMMITTED
-> NEW_FENCE_PROVIDER_VALIDATED
-> NEW_HOLDER_ACTIVE

The exact linearization point is the authoritative commit that supersedes the old holder and commits the new fence. If the provider has its own fencing state, that state must reject F_old before F_new is considered externally effective.

## Overlap window
There can be an unavoidable observation window in which the old holder has not yet learned that it lost authority. Safety therefore cannot depend on the old holder voluntarily stopping. The downstream protected resource must reject stale F_old after F_new is accepted.

If the provider does not enforce fencing, the system can only claim coordination/lease ownership, not prevention of concurrent external effects.

## Handoff crash cases
- Crash before succession commit: old state remains authoritative; new holder must not assume authority.
- Crash after succession commit but before new holder learns it: new fence is authoritative; old fence is stale; new holder reconciles and activates.
- Crash after provider accepts new fence but before response: new holder must reconcile provider state; it cannot assume rejection.
- Crash after old holder dispatches an effect but before learning of succession: that effect retains its independent external-effect state and may be UNKNOWN.

## Renewal interaction
Renewing the old lease during a pending handoff must not silently restore old authority after the new succession commit. Ownership must be checked against the current leader/fence revision, not merely lease possession.

## Safe overlap rule
The desired property is not "old process has stopped"; it is:
`NO_EXTERNAL_EFFECT_ACCEPTED_WITH_FENCE_OLDER_THAN_CURRENT_FENCE`
for every provider that claims fencing protection.

## Critical distinctions
- NEW_LEASE != NEW_EXTERNAL_AUTHORITY
- LEASE_EXPIRY != RETROACTIVE_STOP
- SUCCESSION_COMMIT != PROVIDER_FENCE_ENFORCEMENT
- OLD_HOLDER_UNAWARE != OLD_HOLDER_AUTHORIZED
- NEW_FENCE_COMMITTED != NEW_EFFECT_CONFIRMED
- PROVIDER_ACCEPTED_NEW_FENCE != OLD_EFFECT_NOT_APPLIED
- RENEWAL_SUCCESS != RESTORED_OLD_AUTHORITY
- COORDINATION_HANDOFF != EFFECT_ATOMICITY

## Nexo implication
The handoff contract should bind `OldFence`, `NewFence`, `AuthorityEpoch`, `TargetIncarnation`, succession linearization revision, provider enforcement evidence, and crash/reconciliation state. Provider enforcement is the actual stale-writer safety boundary; local lease state is not.
