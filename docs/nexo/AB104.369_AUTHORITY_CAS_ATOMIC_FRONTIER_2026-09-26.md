# NEXO — AB104.369 — Atomic Authority + CAS Frontier

Date: 2026-09-26
Status: RESEARCH / DESIGN EVIDENCE ONLY
Implementation: NOT PERFORMED. No V21. No runtime claim.

## Objective

Continue AB104.368 by determining the required semantics when authority validation and target-state CAS meet at the same protected transition, including authority change during the frontier.

## Baseline carried forward

AB104.368 established that Authority (A) and Target state (T) are independent validity dimensions:
- A=VALID, T=UNKNOWN => UNKNOWN/STOP.
- A=UNKNOWN, T=VALID => UNKNOWN/STOP.
A locally valid target does not compensate for unknown authority, and valid authority does not compensate for unknown target state.

RFC 7232 provides an analogous state-precondition principle: an If-Match condition is evaluated before a state-changing method and a false condition prevents the method from being applied. It is evidence for the precondition/CAS pattern, not proof of Nexo's broader authority semantics.

## AB104.369 finding

A safe protected transition must not perform:

1. read authority;
2. read target version;
3. later CAS only the target;
4. separately assume the earlier authority remains valid.

That creates a TOCTOU frontier between authority validation and the actual mutation.

The candidate protected commit predicate is instead conceptually:

COMMIT iff
  authority_epoch == expected_authority_epoch
  AND authority_state/scope == required valid state
  AND target_version == expected_target_version
  AND all other protected preconditions hold

and the evaluation of those predicates plus the protected mutation must share one authoritative linearization point (or an equivalent mechanism that provides the same semantics).

## Authority-change interleavings

### Case 1 — authority changes before the protected linearization point

Result: REJECT / HOLD / REVALIDATE.

The stale operation must not mutate the protected target merely because its earlier authority observation was valid.

### Case 2 — authority changes between an authority read and a target CAS

A target-only CAS is insufficient. If the authority epoch is not part of the atomic guard, the stale operation can still commit.

Therefore authority freshness must participate in the same protected conditional write/transaction, or an equivalent fencing mechanism must make the stale operation rejectable at the protected resource.

### Case 3 — authority changes during the atomic frontier

There must be a single defined ordering point.

If authority change linearizes first, the operation fails its authority predicate.
If the protected operation linearizes first, the operation was authorized under the authority generation that existed at that linearization point; a later revocation cannot retroactively make the already-linearized local mutation un-happen.

This does NOT automatically authorize a later external effect. External effect authorization requires its own contract/fence/reconciliation semantics.

### Case 4 — authority changes after local commit but before external effect

Local CAS success is not equivalent to external authorization.

The operation must carry the authority generation/fence into the external-effect contract where the external resource can enforce it. If the external resource cannot enforce the generation, the design cannot claim that local CAS alone prevents stale external actuation. The outcome must remain subject to the external-effect and reconciliation contract.

### Case 5 — authority changes after external attempt

The external outcome may already exist. Revocation cannot be treated as retroactive cancellation. The result must be represented using the external effect state and reconciliation semantics; any compensation/reversal is a new protected effect.

## Stronger invariant derived

For an authority-sensitive mutation:

NO_EFFECT_FROM_STALE_AUTHORITY

A mutation is admissible only if the authority generation/scope required by the operation is still valid at the mutation's authoritative linearization point, not merely at preparation/read time.

For external effects, the stronger property is:

NO_ACCEPTED_EXTERNAL_EFFECT_FROM_STALE_FENCE

but this requires the protected external resource/provider to actually enforce the supplied fence/epoch, or another mechanism with equivalent semantics. A client-side check alone is insufficient.

## Important distinction

Atomicity of:
(A validation + T CAS)

does not automatically imply atomicity of:
(A validation + T CAS + external world effect).

Therefore:

CONTROL_ATOMICITY != EFFECT_ATOMICITY

The previous Nexo rule remains unchanged.

## Candidate contract

The protected transition should capture at minimum:

- expected AuthorityEpoch / fence
- required authority state/scope
- expected target VersionSet
- read set
- write set
- dependency versions/incarnations
- exact operation/effect identity
- linearization point
- invalidation/revocation semantics
- crash semantics
- retry/idempotency semantics
- external authorization/fencing requirements
- evidence required to distinguish REJECTED from UNKNOWN

## Failure modes that remain OPEN

1. Whether authority generation alone is sufficient, or whether scope/policy baseline versions must also enter the atomic predicate.
2. Whether all authority-sensitive writes can share one protected store/linearization domain.
3. How to express authority changes that affect multiple resources with no common atomic domain.
4. How provider APIs that cannot consume fencing tokens are handled.
5. Whether a prepared operation can survive authority revocation, and under exactly which final-gate rules.
6. Formal proof of the invariant has NOT been performed.

## Evidence boundary

AB104.369 establishes a design requirement/candidate invariant, not a correctness proof.

No implementation, SANY/TLC verification, runtime verification, fault-injection result, or deployment verification is claimed.
