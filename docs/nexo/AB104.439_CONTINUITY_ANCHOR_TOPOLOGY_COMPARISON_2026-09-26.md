## Research question

Compare a single anchor, replicated/consensus-backed anchor, transparency-log witnesses, and hardware-backed monotonic state for rollback resistance, equivocation detection, availability, independence, and TCB impact.

## Evidence

RFC 9162 shows that append-only Merkle structures can provide inclusion and consistency proofs, but a malicious log can still present inconsistent views to different clients; monitoring/auditing is therefore needed. citeturn0search0turn0search2

RFC 9334 separates trust anchors, verifier appraisal, freshness, and relying-party authorization. It explicitly notes that freshness can race with state changes and that trust-anchor stores themselves require protection. citeturn0search1

etcd documents that linearizable reads reflect current cluster consensus, while serializable member-local reads may be stale; its watch API is ordered by revision but the client must reason about revision continuity. citeturn0search3turn0search6

NIST's CMVP material demonstrates that TPMs are hardware security modules used for authenticity/integrity-related functions, but a hardware root by itself does not define Nexo's distributed authority or continuity semantics. citeturn0search7turn0search8

## Topology T1 — single continuity anchor

Candidate model:
PRIMARY → ANCHOR

Strengths:
- simple semantics;
- small protocol surface;
- easy predecessor binding.

Weaknesses:
- single availability dependency;
- compromise can corrupt currentness evidence;
- anchor rollback requires a second mechanism;
- no independent equivocation detection if only one observer exists.

Safety implication:
A single anchor can be authoritative evidence only within an explicitly bounded trust model.

## Topology T2 — replicated/consensus-backed anchor

Candidate model:
PRIMARY → CONSENSUS-BACKED ANCHOR SET

Strengths:
- durable ordered state;
- failover;
- stronger continuity under its configured consensus assumptions;
- linearizable access can bind decisions to a current consensus state.

Weaknesses:
- consensus members can share common-mode dependencies;
- quorum count is not independence;
- consensus correctness does not prove application semantics or external-world truth;
- restoring arbitrary historical cluster state can still create a recovery problem.

Therefore:
CONSENSUS_QUORUM != UNIVERSAL_TRUTH.

## Topology T3 — transparency log + independent witnesses

Candidate model:
PRIMARY → APPEND-ONLY LOG → WITNESSES/MONITORS

Strengths:
- historical consistency proofs;
- equivocation can become externally detectable;
- multiple observers can compare views;
- useful for audit/reconstruction.

Weaknesses:
- detection may be asynchronous;
- the log does not itself prevent the underlying bad action;
- witnesses can share dependencies;
- monitor outage can reduce detection coverage;
- log evidence remains evidence, not Z1 authority.

RFC 9162 directly supports this separation: CT logs help detect misbehavior; what the relying party does after detection is outside the log's mechanism. citeturn0search0

## Topology T4 — hardware-backed monotonic state

Candidate model:
AUTHORITY/RESOURCE → HARDWARE-BACKED MONOTONIC PRIMITIVE

Potential strengths:
- rollback resistance can be rooted below ordinary software state;
- useful for key/state protection and boot/recovery continuity;
- can reduce dependence on ordinary filesystem/database rollback.

Limitations:
- exact primitive semantics vary;
- hardware availability/failure becomes a dependency;
- hardware monotonicity does not automatically provide distributed uniqueness;
- it does not prove policy correctness, participant closure, or external effect confirmation.

Therefore:
HARDWARE_MONOTONICITY != DISTRIBUTED_AUTHORITY.

## Key distinction: prevention vs detection

A transparency log may detect equivocation after the fact.

A resource-side fence can prevent a stale actor from mutating the protected resource.

A consensus-backed authority can serialize authority transitions.

A hardware primitive can resist local rollback.

These mechanisms solve different properties and should not be treated as interchangeable.

## TCB analysis

Adding an anchor can shrink one claim's uncertainty while expanding dependencies.

For every anchor design Nexo must record:
- storage dependency;
- key/trust dependency;
- software/verifier dependency;
- deployment dependency;
- time dependency if used;
- network dependency;
- recovery dependency;
- operator/governance dependency;
- witness dependency;
- hardware dependency where applicable.

This continues the failure-domain algebra from AB104.417–AB104.420.

## Anti-rollback rule

A mechanism that merely stores a number is insufficient.

The protected claim is:

NO_OLDER_VALID_STATE_CAN_SILENTLY_BECOME_CURRENT.

This requires identity/continuity semantics, not just monotonic arithmetic.

## Independence rule

Independent keys do not necessarily create independent evidence.

Likewise:
- different processes can share one storage system;
- different regions can share one control plane;
- different witnesses can share one verifier;
- different hardware modules can share one compromised policy source.

Therefore:

KEY_DIVERSITY != FAILURE_DOMAIN_DIVERSITY.

## Candidate architecture boundary

The research supports a layered abstraction, not a specific product:

1. Z1 defines authority/currentness policy.
2. An authoritative state mechanism maintains generation/order.
3. Resource-side fencing prevents stale protected mutation.
4. Durable replay/effect state handles crash/retry identity.
5. Independent observation detects continuity/equivocation failures where required.
6. Optional hardware anti-rollback reduces local rollback dependency.
7. Reconciliation remains responsible for external ambiguity.
