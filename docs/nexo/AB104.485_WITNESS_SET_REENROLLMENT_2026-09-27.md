# AB104.485 — safe witness-set re-enrollment after trust-domain compromise

RFC 9162 shows that transparency clients can audit signed tree heads for append-only consistency and detect conflicting views, but it does not define a complete recovery/governance protocol for replacing a compromised log trust domain. Failed audit can provide signed evidence of misbehavior; what to do with that evidence is local policy. citeturn0search0turn0search1

## Recovery model

A safe witness-set transition should be treated as a protected trust transition, not as ordinary membership editing:

OLD_SET -> COMPROMISE_DETECTED -> QUARANTINED_SET -> INDEPENDENT_REVIEW -> NEW_SET_ADMITTED -> CHECKPOINT_CONTINUITY_VERIFIED -> NEW_SET_ACTIVE

Old witnesses must not be able to authorize their own restoration after compromise. New witnesses must be admitted using a trust basis that does not depend solely on the compromised set.

## Checkpoint continuity

The new set should retain the last uncontested checkpoint and require a consistency proof before automatically accepting a later tree. Conflicting checkpoints remain evidence of equivocation and require quarantine/reconciliation rather than silent selection of one side. RFC 9162 defines the consistency proof needed to establish that one tree extends another. citeturn0search22

## Key rotation is not membership recovery

KEY_ROTATION != WITNESS_REENROLLMENT
WITNESS_REENROLLMENT != CHECKPOINT_RECOVERY
CHECKPOINT_RECOVERY != EXTERNAL_EFFECT_CONFIRMATION

Rotating keys without changing the compromised trust basis does not restore independence. Replacing members without preserving checkpoint continuity can create a rollback window. Restoring transparency history does not establish the truth of the logged external-effect claim.

## Quorum transition

A new quorum must be evaluated for failure-domain independence. Merely increasing the number of witnesses does not create independent trust if they share the same operator, infrastructure, upstream identity provider, storage, or signing authority.

New invariants:
- COMPROMISED_SET != AUTHORITY_TO_SELF_REENROLL
- KEY_ROTATION != TRUST_DOMAIN_RECOVERY
- NEW_WITNESS_COUNT != INDEPENDENCE
- NEW_QUORUM != AUTOMATIC_AUTHORITY
- CHECKPOINT_CONTINUITY_REQUIRED_ACROSS_TRUST_TRANSITION
- CONFLICTING_CHECKPOINTS => QUARANTINE
- OLD_WITNESS_AFTER_REVOKE => NO_AUTHORITY
- TRUST_REENROLLMENT != EXTERNAL_EFFECT_CONFIRMATION
- RECOVERY_MUST_HAVE_INDEPENDENT_TRUST_BASIS

Evidence status: safe re-enrollment is a governance and trust-transition problem layered above transparency cryptography. RFC 9162 supplies concrete consistency/inclusion mechanisms but leaves recovery action to local policy. No implementation or formal verification performed.
