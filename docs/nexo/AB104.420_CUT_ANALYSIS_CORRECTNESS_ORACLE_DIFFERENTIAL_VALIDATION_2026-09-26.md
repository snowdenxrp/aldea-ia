# Nexo AB104.420 — Cut-Analysis Correctness, Oracle Problem and Differential Recompute

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.419 → AB104.420
Implementation: NOT PERFORMED

## Research question

How can Nexo obtain evidence that its computed critical cuts are complete and correct, without making the cut-analysis engine a hidden single point of trust?

## Evidence

NIST describes the oracle problem as the difficulty of determining the correct expected result for complex software; it notes that model-based testing, assertions, standards, prior implementations, and alternative techniques can reduce but not universally eliminate the problem. citeturn0search37 NIST also describes model checking as a way to generate/evaluate tests from formal state-machine specifications. citeturn0search2

NIST's security-testing work shows that model-based specifications can generate test vectors and drivers, while metamorphic testing can detect security defects without requiring a conventional oracle for every individual input/output pair. citeturn0search0turn0search11

NASA's IV&V material distinguishes verification from validation and emphasizes independent technical, managerial, and financial independence for IV&V. NASA also reports that model-based testing can expose contradictions and incompleteness in requirements as well as implementation errors. citeturn0search38turn0search36

## Core finding

A cut-analysis engine can produce a deterministic answer and still be wrong.

Therefore:

DETERMINISTIC_CUT_RESULT != CORRECT_CUT_RESULT

and:

REPRODUCIBLE_ANALYSIS != SEMANTIC_CORRECTNESS

The key problem is not only whether the algorithm runs correctly, but whether it computes the cuts required by the protected property.

## Four assurance questions

Cut analysis has at least four distinct questions:

### A — Semantic specification

Did Nexo define the correct failure-domain/quorum property?

### B — Algorithm correctness

Does the algorithm compute the required cut set from the specified graph?

### C — Implementation conformance

Does the implementation actually match the validated algorithm?

### D — Current deployment/evidence

Is the analysis result based on the current graph, policy, trust generations, and witness set?

Agreement on B does not prove A.
Agreement on C does not prove B.
A valid result for D-1 does not prove D-current.

## Oracle problem

For a given graph G, the engine outputs:

CUT_RESULT = f(G, policy, claim)

But who proves that f(G) is complete?

A second implementation can help, but:

TWO_IMPLEMENTATIONS_SAME_SPEC != CORRECT_SPEC

Two implementations can share the same semantic defect.

Therefore differential recomputation is evidence, not absolute proof.

## Candidate independent differential analysis

Use at least two materially distinct analysis paths where claim consequence justifies it:

ANALYZER_A(G)
ANALYZER_B(G)

Compare:

- minimum cuts;
- all critical cuts;
- affected witness sets;
- failure-domain projections;
- quorum-invalidating conditions;
- unknown/incomplete dependency handling.

Agreement increases evidence.

Disagreement:

ANALYSIS_DISPUTED

not:

SELECT_A_BY_DEFAULT

## Independent implementation requirements

Independence should include more than different process IDs.

Candidate independence dimensions:

- algorithm formulation;
- implementation language;
- codebase;
- test corpus;
- graph parser;
- dependency-closure engine;
- policy source;
- operator;
- build/deployment pipeline;
- runtime environment;
- trust roots.

This carries forward the failure-domain algebra from AB104.417–AB104.419.

## Reference model

Candidate reference model should be deliberately simple and auditable.

For small bounded graphs:

- enumerate witness subsets;
- enumerate relevant failure-domain subsets;
- determine which subsets invalidate the quorum;
- derive exact minimal cuts.

This is not necessarily scalable enough for production, but it can act as a bounded oracle for testing optimized algorithms.

Candidate:

REFERENCE_EXACT_MODEL

vs

OPTIMIZED_ANALYZER

Mismatch => ANALYSIS_DISPUTED.

## Bounded exhaustive validation

For small graphs, exhaustive enumeration can test:

- zero shared dependencies;
- one shared dependency;
- nested dependencies;
- overlapping domains;
- witness additions/removals;
- quorum threshold changes;
- unknown dependencies;
- domain merges/splits;
- Byzantine witness assumptions.

This provides strong local evidence without claiming universal correctness.

## Property-based validation

Generate graph families and assert structural properties such as:

1. Adding a dependency cannot create a falsely stronger independence claim.
2. Removing a witness cannot silently increase effective independence.
3. Merging failure domains cannot improve the claimed independence without a new analysis.
4. Adding an unrelated domain should not alter unrelated claim results.
5. A cut must actually invalidate the required quorum under the modeled policy.
6. Every reported critical cut must be reproducible from the same graph/policy generations.

These are properties of the analysis, not individual expected outputs.

## Metamorphic testing

NIST identifies metamorphic testing as a way to alleviate the oracle problem for security testing. citeturn0search11

Candidate transformations:

### M1 — rename-only

Rename domain IDs without changing topology.

Expected:
CUT_SEMANTICS unchanged.

### M2 — permutation

Reorder witnesses/domains.

Expected:
CUT_SET semantics unchanged.

### M3 — unrelated addition

Add a disconnected domain irrelevant to the claim.

Expected:
existing claim cuts unchanged.

### M4 — dependency merge

Merge two domains.

Expected:
independence cannot silently increase.

### M5 — witness removal

Remove a contributing witness.

Expected:
effective quorum strength cannot silently improve.

### M6 — policy threshold increase

Increase required quorum.

Expected:
the set of invalidating cuts cannot become smaller merely because the requirement became stricter.

These are candidate properties; exact monotonicity must be proved for each policy formulation before being treated as universal.

## Mutation testing

Intentionally mutate the graph or algorithm:

- delete a dependency;
- delete a witness;
- merge domains;
- split domains;
- alter threshold;
- omit a policy dependency;
- change trust generation;
- flip a quorum predicate;
- remove a cut;
- inject a false edge.

The validation stack should detect the mutation where the mutated property matters.

A test suite that cannot detect critical graph mutations is weak evidence of analysis correctness.

## Differential graph representations

Avoid relying on one parser/graph representation.

Candidate:

SOURCE_GRAPH
→ REPRESENTATION_A
→ ANALYZER_A

and independently:

SOURCE_GRAPH
→ REPRESENTATION_B
→ ANALYZER_B

If both representations share the same parser/normalizer, their independence is reduced.

## Minimal-cut witness certificate

A reported cut should carry a certificate explaining why it is a cut.

Candidate certificate:

- claim;
- policy generation;
- graph root;
- cut domain set;
- affected witnesses;
- quorum before cut;
- quorum after cut;
- dependency paths;
- proof that each cut member is necessary for that particular minimality claim;
- analysis algorithm version;
- reference-model result where available.

The certificate is evidence and must be independently checkable.

## Minimality versus validity

Two separate claims:

VALID_CUT:
Removing the cut invalidates the required quorum.

MINIMAL_CUT:
No strict subset of the cut also invalidates the required quorum.

An algorithm can correctly identify a valid cut but incorrectly claim it is minimal.

Therefore:

VALIDITY != MINIMALITY

Both need independent checks.

## Completeness versus minimality

Another distinction:

CUT_VALIDITY
CUT_MINIMALITY
CUT_SET_COMPLETENESS

Finding one valid cut does not prove that all critical minimal cuts were found.

Therefore:

FOUND_CUT != COMPLETE_CUT_SET

This is a major oracle boundary.

## Approximation

For large dynamic graphs, exact enumeration may be expensive.

An approximation may be useful operationally, but it must never silently become an exact safety claim.

Candidate statuses:

EXACT
BOUNDED_EXACT
APPROXIMATE
INCOMPLETE
UNKNOWN

For high-consequence claims:

APPROXIMATE/INCOMPLETE cannot satisfy a policy requiring complete cut coverage unless the policy explicitly and safely permits it.

## Resource exhaustion attack

An attacker can construct a graph whose exact cut enumeration is computationally expensive.

If the analyzer times out and returns “no critical cut found,” the system has converted computation failure into false safety.

Candidate:

ANALYSIS_TIMEOUT != NO_CRITICAL_CUT

Required result:

UNKNOWN / HOLD / DEGRADED according to claim policy.

## Adversarial graph mutation

During analysis:

G0 is loaded.
Attacker/change produces G1.
Analyzer finishes using G0.

If G1 is current:

RESULT(G0) != CURRENT_RESULT

Therefore graph version/root must be bound to the result and checked at the final admission boundary.

## Independent checker

Candidate architecture:

PRIMARY_ANALYZER
→ CUT_CERTIFICATE
→ INDEPENDENT_CHECKER

The checker verifies the certificate without reusing every internal assumption of the analyzer.

For minimality/completeness, bounded reference recomputation may supplement certificate checking.

## No circular validation

Unsafe:

Analyzer A validates Analyzer B

Analyzer B validates Analyzer A.

Candidate:

## Residuals

- Formal specification of the exact protected cut property remains open.
- Complete independent oracle for arbitrary dynamic graphs remains impossible to assume.
- Exact minimum-cut computation at scale remains a performance/design question.
- Independence of differential analyzers requires its own dependency analysis.
- Semantic correctness of the failure-domain graph remains an upstream problem.
- Formal proof, implementation, fault injection, and deployment verification remain unperformed.
