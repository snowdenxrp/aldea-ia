## Research question
Can a parent GLOBAL_AUTHORITY_EPOCH (GAE) plus child RESOURCE_FENCE (RF) safely reject stale work when authority rolls over between resource admissions?

## Evidence
Fencing safety requires the protected resource to validate a monotonic token at the mutation boundary; lease expiry or coordinator-side observation is not enough. The resource must retain ordering state needed to reject stale requests. citeturn0search0turn0search1

A hierarchical composition does not automatically create a safety guarantee. If a child resource accepts a locally fresh RF while the parent GAE is stale, the child may accept work that the authority layer no longer permits.

## Attack model
Let G1 be the current parent authority epoch, G2 the newer epoch, R1 a protected resource, F1 a child fence issued under G1, and F2 a child fence issued under G2.

### Attack A — Parent rollover before child admission
1. Operation carries G1 + F1.
2. Parent rolls to G2.
3. Operation reaches R1.
4. R1 sees F1 as locally valid.
5. If R1 checks only F1 and not the parent generation/equivalent binding, it may accept stale-authority work.

Candidate result: REJECT if G1 is not current; otherwise strict stale-authority exclusion is not established.

### Attack B — Parent rollover between R1 and R2
1. Operation is admitted for R1 and R2 under G1.
2. R1 accepts under G1/F1.
3. Parent rolls to G2.
4. R2 has not yet accepted.
5. R2 must reject G1 work unless its contract explicitly permits the old generation through a protected transaction boundary.

R1 is not retroactively undone. Global outcome becomes PARTIAL_COMMIT / RECONCILIATION_REQUIRED.

### Attack C — Child RF freshly translated from stale GAE
1. Provider receives stale G1.
2. Provider locally allocates a new RF=200.
3. Provider treats RF=200 as proof of current authority.
4. External mutation is accepted.

This is unsafe: a fresh local RF cannot manufacture freshness that the parent authority did not possess.

### Attack D — GAE current but RF stale
1. G2 is current.
2. Delayed request carries G1/F1.
3. Resource sees F1 below its high-water mark.
4. Request must reject.

### Attack E — GAE rollover concurrent with child fence issuance
If GAE rollover and RF issuance are not ordered through a common authoritative transition, a provider may issue an RF based on G1 after G2 has already become authoritative.

Candidate rule: RF issuance must be bound to a protected snapshot/epoch of GAE, or the resulting RF must carry an authority generation that the resource validates.

### Attack F — Parent rollover after resource-side acceptance
1. R1 accepts G1/F1 at its resource linearization point.
2. Parent changes to G2.
3. Previously accepted R1 effect is not retroactively invalidated.
4. Any later effect under the operation must be re-admitted under G2 unless the operation contract explicitly defines a bounded protected transaction epoch.

Revocation is not retroactive.

## Candidate safety rule
For a resource mutation, acceptance requires:
- GAE bound to the request is current for the required authority domain;
- RF is valid for the exact RESOURCE_ID + RESOURCE_INCARNATION;
- RF is not below the resource high-water mark;
- target preconditions hold;
- effect contract holds.

This only works if the resource can actually validate the GAE binding or a trusted equivalent. Carrying GAE as metadata is insufficient.

## Stronger composition candidates

### Model 1 — Resource validates both GAE and RF
Every protected request carries:
AUTHORITY_DOMAIN + GAE + RESOURCE_ID + RESOURCE_INCARNATION + RF + EFFECT_ID

The resource atomically validates the authority generation and RF with the mutation.

This is the cleanest local acceptance rule, but requires every protected resource to understand Nexo authority semantics.

### Model 2 — Trusted authority gateway translates GAE to RF
The gateway is itself an authoritative protected boundary. It validates current GAE and maintains a durable RF mapping per resource incarnation. The downstream resource validates RF.

This can hide Nexo-specific authority semantics from heterogeneous providers, but the gateway becomes part of the TCB and must preserve the mapping and fence state across restart/failover. It also does not make downstream effects atomic across multiple providers.

## False proof attacks
The following are invalid:
- RF is newer, therefore GAE is current.
- The operation passed FINAL_GATE once, therefore every later resource attempt remains authorized.
- A fresh provider-local token proves Nexo authority freshness.
- R1 succeeded, therefore R2 is authorized to proceed under the same old generation.
- New EffectID means new authorization.
- Timeout means the stale request did not execute.
- Parent epoch rollover cancels an already accepted external effect.
