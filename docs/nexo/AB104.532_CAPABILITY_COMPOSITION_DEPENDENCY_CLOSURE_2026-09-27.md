# Nexo AB104.532 — Compositional capability dependencies

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Provider capabilities do not compose automatically. A higher-level effect claim is valid only when every prerequisite capability in its dependency closure is satisfied for the same target, scope, epoch, and transition. One UNKNOWN or incompatible prerequisite can invalidate the composed claim.

## Evidence
The Nexo research on dependency graphs/common-mode failures establishes that local certificate validity does not imply composed authority validity. etcd transactions provide atomicity only inside their own consistency domain; Kubernetes version/identity controls are resource-scoped. Cloud Storage generation preconditions protect a specific object generation, not arbitrary external effects. These examples reinforce scope-specific composition.

## Candidate dependency model
CapabilityClaim C has:
- CapabilityID
- Scope
- TargetIdentity
- TargetIncarnation
- ProviderIdentity
- ProviderRevision/Generation
- AuthorityEpoch
- PolicyProfile
- EvidenceDigest
- DependencySet

A composed capability C_comp is supported only if every dependency D in closure(C_comp) is SUPPORTED and semantically compatible.

## Example
E4_RECONCILIABLE_EFFECT may depend on:
D1 operation identity
D2 idempotency scope
D3 target incarnation
D4 conditional mutation
D5 durable operation history
D6 authoritative status lookup
D7 retention coverage
D8 receipt binding
D9 fence enforcement, when the claim requires stale-writer prevention

If D5 is UNKNOWN because history can expire, E4 cannot silently remain fully supported; it must downgrade the claim or enter UNKNOWN.

## Compatibility dimensions
Capabilities must agree on:
- provider identity
- target identity/incarnation
- operation scope
- authority epoch
- fence/generation
- protocol/profile
- validity interval
- evidence freshness
- trust basis

A capability proven for target I1 must not silently satisfy a claim for I2.

## Composition rule
COMPOSED_SUPPORTED(C) iff:
all required dependencies are SUPPORTED
AND scopes intersect safely
AND epochs/generations are compatible
AND no dependency is revoked/expired
AND evidence freshness is sufficient
AND no common-mode dependency invalidates the independence assumption.

Otherwise:
- missing optional capability -> claim-specific restriction;
- missing required capability -> UNSUPPORTED;
- uncertain required capability -> UNKNOWN/QUARANTINE.

## Critical distinctions
- LOCAL_CAPABILITY != COMPOSED_CAPABILITY
- DOCUMENTED_DEPENDENCY != VERIFIED_DEPENDENCY
- PARTIAL_CLOSURE != COMPLETE_CLOSURE
- CAPABILITY_COUNT != INDEPENDENCE
- TARGET_I1_CAPABILITY != TARGET_I2_CAPABILITY
- FRESH_COMPONENT != FRESH_COMPOSITION
- VALID_COMPONENT != VALID_GLOBAL_CLAIM
- OPTIONAL_MISSING != REQUIRED_UNKNOWN
- PROVIDER_ATOMICITY != COMPOSED_CROSS_DOMAIN_ATOMICITY

## Nexo implication
The Effect Adapter should expose not only a capability vector but also a dependency closure and evidence digest. Final admission evaluates the composed claim, not each capability independently. This connects provider capability research directly to the existing Nexo dependency-closure/common-mode model.
