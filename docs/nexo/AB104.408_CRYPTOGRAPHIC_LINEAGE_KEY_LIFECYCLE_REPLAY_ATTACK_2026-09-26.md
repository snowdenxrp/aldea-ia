# Nexo AB104.408 — Cryptographic Lineage Binding, Key Lifecycle and Replay Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.407 → AB104.408
Implementation: NOT PERFORMED

## Research question

Can authenticated lineage remain trustworthy across retries, queues, callbacks and authority-domain handoffs when signatures, MACs, nonces, key rotation, compromise and revocation are introduced?

## Evidence reviewed

RFC 9421 defines HTTP Message Signatures and requires verifiers to check appropriate key material, algorithm, signature coverage and application-specific requirements. It explicitly identifies replay risk and describes nonce/time mechanisms, while warning that valid signatures can still be replayed if the covered message is insufficiently differentiated. It also notes that compromise of a signing key permits an attacker to create valid signatures and discusses key rotation as a mitigation. citeturn0search1turn0search6turn0search37

RFC 8705 defines certificate-bound OAuth access tokens so the protected resource can verify that the party presenting the token possesses the corresponding private key, reducing replay of stolen bearer credentials. This is sender/key binding, not proof that the underlying authorization remains current. citeturn0search0turn0search3

RFC 9449 DPoP binds a proof to an HTTP method/URI and uses short validity periods plus optional server nonces and `jti` replay tracking. It illustrates that cryptographic authenticity and replay prevention are separate protocol obligations. citeturn0search2turn0search35

## Core finding

`SIGNATURE_VALID != LINEAGE_CURRENT`

and:

`KEY_POSSESSION != CURRENT_AUTHORITY`

A cryptographic signature proves a statement was authorized/signed under a key according to the verifier's cryptographic checks. It does not by itself prove that the statement remains valid after authority rollover, resource replacement, footprint invalidation, policy change, or key compromise.

## Candidate lineage-binding layers

1. **Message integrity** — the covered lineage fields cannot be modified without detection.
2. **Signer authentication** — the verifier knows which authority/domain/key signed.
3. **Audience/path binding** — the proof is intended for this participant/path.
4. **Operation/effect binding** — lineage is tied to the exact logical operation/effect.
5. **Freshness/replay binding** — duplicate/stale use is rejected.
6. **State-generation binding** — authority/fence/resource/capability generations are checked.
7. **Semantic authorization** — Z1 still independently decides whether the protected transition is authorized.

No lower layer should be treated as automatically proving the higher layer.

## Candidate signed coverage

For a protected lineage message, candidate signed fields include:

- OPERATION_ID
- EFFECT_ID
- ATTEMPT_ID
- PARENT_LINEAGE_ID
- LINEAGE_SEQUENCE / predecessor
- PARTICIPANT_ID
- RESOURCE_ID + RESOURCE_INCARNATION
- DESTINATION / AUDIENCE
- AUTHORITY_DOMAIN
- AUTHORITY_EPOCH
- FENCE_GENERATION
- EFFECT_CLASS_EFFECTIVE
- FOOTPRINT_CLOSURE_ROOT
- CAPABILITY_GENERATION
- POLICY / CONTRACT VERSION
- ISSUER / KEY ID
- NONCE or unique message identifier
- issued-at / expiry where time is part of the protocol

The exact set remains claim-specific. RFC 9421's warning about unsigned message components directly supports the principle that security-relevant fields cannot remain mutable outside the authenticated coverage. citeturn0search1

## Replay

Candidate replay defenses can combine:

`SIGNED_BINDING + UNIQUE_ID/NONCE + DURABLE_REPLAY_STATE + STATE_GENERATION_CHECK`

A timestamp alone is insufficient for strong protected effects because clock uncertainty and delayed delivery can create ambiguity.

A nonce alone is also insufficient if its consumption state is not durably enforced.

A signature alone is insufficient because a valid signature can be replayed. RFC 9421 explicitly documents this attack. citeturn0search1turn0search6

For high-consequence effects, the participant should have an authoritative replay decision at its protected boundary:

`ACCEPTED_NONCE/EFFECT/ATTEMPT` → durable state before treating the protected transition as admitted.

Exact atomicity with the external effect remains a separate unresolved problem.

## Key rotation

Key rotation creates at least three generations:

- signing-key generation;
- lineage/evidence generation;
- authority/policy generation.

A new signing key does not automatically revoke all old lineage. Conversely, cryptographic retirement of an old key does not prove that all effects signed under it never executed.

Candidate state:

`KEY_STATUS = ACTIVE | RETIRING | RETIRED | REVOKED | COMPROMISED | UNKNOWN`

A lineage accepted under an old key may remain historically valid for audit while becoming unusable for new protected authorization.

Therefore:

`HISTORICAL_SIGNATURE_VALIDITY != CURRENT_ADMISSION_VALIDITY`

## Key compromise

RFC 9421 states that if a signing key is compromised, an attacker can generate valid signatures; key rotation can limit the useful lifetime of a stolen key. citeturn0search37

Nexo therefore needs a compromise response that is stronger than simply changing the current key:

1. identify affected key generation;
2. identify lineage/evidence depending on that generation;
3. invalidate current-use claims according to policy;
4. preserve historical records as historical;
5. prevent compromised lineage from creating new authority;
6. reconcile effects that may already have crossed the external boundary.

This is another instance where evidence invalidation and effect reconciliation are distinct.

## Cross-domain handoff

Candidate handoff:

`DOMAIN_A`
→ signed lineage assertion
→ authenticated channel / proof-of-possession
→ DOMAIN_B validation
→ local admission context
→ Z1/domain-B gate.

Domain B should not inherit Domain A's authority wholesale.

The handoff must bind at least, where required:

- issuer;
- intended recipient/audience;
- operation/effect identity;
- permitted inheritance rule;
- resource incarnation;
- relevant authority/fence generation;
- footprint closure;
- capability generation;
- expiry/replay state.

Certificate-bound credentials and proof-of-possession mechanisms demonstrate useful binding patterns, but they do not establish Nexo's full semantic authorization model. citeturn0search0turn0search2

## Intermediaries

An intermediary need not be permanent TCB merely because it transports lineage.

Candidate classification:

- **Transparent transport:** cannot modify protected lineage; not trusted for authority semantics.
- **Lineage-transforming intermediary:** if it changes protected fields, it becomes part of the TCB for those transformations.
- **Authorization-delegating intermediary:** TCB for the delegated property.
- **Cryptographic re-signer:** TCB for the semantic correctness of what it re-signs.
- **Opaque router:** if protected correctness depends on its routing decision, it is part of the relevant TCB.

This keeps the TCB claim-specific.

## Downgrade / algorithm attacks

The cryptographic envelope must bind the accepted algorithm/key context. RFC 9421 warns about key-specification mixup and algorithm requirements. citeturn0search1

Candidate rule:

`UNAPPROVED_ALGORITHM_OR_KEY_CONTEXT => REJECT`

Cryptographic agility must not become a path for weakening the semantic lineage contract.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| stolen signature | valid signature => valid execution | replay + current-state checks |
| unsigned critical field | signature valid => whole message trusted | reject/invalidate incomplete coverage |
| nonce reuse | same nonce => harmless duplicate | durable uniqueness enforcement |
| old key | old signature => current authority | key-generation + authority-generation validation |
| compromised key | cryptographically valid => trustworthy | compromise invalidation |
| key rollover | new key => old effects erased | preserve historical validity; invalidate current use per policy |
| audience substitution | valid signature => any recipient | explicit audience/path binding |
| cross-domain reuse | signed in A => authorized in B | local handoff validation |
| algorithm downgrade | weaker valid algorithm => accepted | protected algorithm policy |
| re-signer | new signature => semantic continuity | bind transformation semantics |
| stale closure | valid lineage => current footprint | closure-generation validation |
| resource replacement | same ID => same target | incarnation binding |
| replay after compensation | old proof => repeat effect | state-machine/reconciliation check |
| verifier compromise | signature/appraisal => current truth | verifier trust generation + Z1 policy |

- `SIGNATURE_VALID != LINEAGE_CURRENT`
- `KEY_POSSESSION != CURRENT_AUTHORITY`

- `RE_SIGNING_REQUIRES_SEMANTIC_BINDING`
- `RESOURCE_INCARNATION_CHANGE_INVALIDATES_BOUND_LINEAGE_WHERE_REQUIRED`
- `CRYPTOGRAPHIC_AUTHENTICITY != SEMANTIC_AUTHORIZATION`

## Residuals / not proven

- Exact cryptographic protocol for Nexo lineage.
- Key storage/HSM architecture.
- Rotation and compromise propagation latency.
- Durable replay-state scalability under partition.
- Formal proof of cross-domain handoff semantics.
- Formal mapping between key generations and evidence/authority generations.
- Privacy implications of persistent lineage identifiers.
- Implementation and fault-injection correctness.
