# Nexo AB104.442 — TPM vs TEE/Secure Element vs HSM vs Cloud-Backed Hardware Roots

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.441 → AB104.442
Implementation: NOT PERFORMED

## Research question

Which hardware-root class can provide which Nexo property, and where does each class move the TCB rather than eliminate it?

## Evidence

NIST IR 8320 describes TPMs, TEEs, secure enclaves and HSMs as different components in a layered hardware-enabled security model rather than interchangeable primitives. citeturn0search15

The current TCG TPM 2.0 Library specification is Version 185 (March 2026). citeturn0search4

Android KeyMint explicitly distinguishes hardware-enforced rollback resistance and can expose hardware-backed attestation; Android also distinguishes Trusted Environment and StrongBox security levels. citeturn0search6turn0search12

Android documentation states that key attestation is intended to let a remote party determine whether a key is hardware-backed and what constraints apply, and its attestation protocol uses a challenge to resist replay. citeturn0search1turn0search14

AWS CloudHSM provides dedicated HSMs for key generation/storage and cryptographic operations, with clustered synchronization/durability options. citeturn0search0turn0search3turn0search47

## Core finding

There is no universal “hardware root” abstraction that provides all Nexo properties.

The useful abstraction is:

PRIMITIVE CAPABILITY
→ EVIDENCE
→ CLAIM-SPECIFIC APPRAISAL
→ Z1 AUTHORITY DECISION.

## T1 — TPM

Primary role:
- platform identity;
- measured boot support;
- protected keys;
- NV/monotonic state;
- local anti-rollback primitives.

Best fit:
LOCAL_CONTINUITY_FLOOR
BOOT/CONFIGURATION_MEASUREMENT
HARDWARE_BOUND_IDENTITY.

Not established automatically:
- global authority;
- external effect state;
- distributed consensus;
- policy correctness.

TCG's TPM architecture is therefore a candidate foundation, not a complete Nexo authority substrate. citeturn0search4

## T2 — TEE

Primary role:
- isolated execution;
- hardware-backed key operations;
- protected application logic/state.

Strong point:
A TEE can place a security-critical operation closer to the hardware trust boundary.

Limit:
The TEE implementation, secure monitor, firmware, provisioning and attestation chain become dependencies.

Candidate:
TEE can host a local enforcement primitive, but:
TEE_CORRECTNESS != DISTRIBUTED_CORRECTNESS.

## T3 — Secure Element / StrongBox-like isolated hardware

Primary role:
- highly isolated key/state protection;
- tamper-resistant operations;
- hardware-backed identity.

Android's StrongBox model illustrates a discrete, tamper-resistant implementation distinct from a normal TEE. citeturn0search7

Useful for:
- signing continuity statements;
- protecting non-exportable identity keys;
- storing selected rollback-resistant metadata.

Limit:
small state/capability surface and device-specific lifecycle semantics.

## T4 — HSM

Primary role:
- protected cryptographic keys;
- signing;
- cryptographic policy boundary.

AWS CloudHSM demonstrates dedicated HSMs with customer-managed users/keys and clustered synchronization/durability. citeturn0search0turn0search47

Useful for Nexo:
- continuity-anchor signing keys;
- witness signing;
- recovery authorization keys;
- high-value root keys.

Limit:
HSM can prove/control possession and use of keys, but it does not automatically know whether the signed state is semantically correct or current.

Therefore:
HSM_SIGNATURE != STATE_CORRECTNESS.

## T5 — Cloud-backed hardware root

Cloud HSM can increase availability and operational durability by clustering hardware, but cloud control-plane, provisioning, backup, region, identity, network and provider dependencies become part of the claim's dependency graph. AWS documents synchronization/durability behavior and cluster management explicitly. citeturn0search3turn0search47

Useful:
- remotely available root signing;
- durable key custody;
- multi-node cryptographic service.

Not automatic:
- independent truth from the cloud provider;
- external-world confirmation;
- anti-rollback of Nexo's entire distributed state.

Therefore:
CLOUD_HSM_DURABILITY != GLOBAL_CONTINUITY.

## Critical distinction: local versus distributed continuity

Hardware can establish:

“This device possesses protected state X under hardware identity H.”

Nexo needs a stronger question:

“Is X the current continuity state for authority domain D, under current generation G, policy P, trust T, and recovery generation R?”

The second question requires distributed/state-machine semantics outside the hardware primitive.

## Candidate layered Nexo use

### Device layer
TPM/TEE/Secure Element:
- hardware identity;
- local protected state;
- anti-rollback floor;
- measured boot;
- attestation.

### Authority layer
Consensus/durable store:
- authoritative generation;
- state root;
- protected transitions;
- recovery generation.

### Resource layer
Fence:
- stale actor exclusion;
- resource incarnation;
- fence HWM.

### Observation layer
Independent witnesses/transparency log:
- continuity observation;
- equivocation detection;
- historical reconstruction.

### Key custody layer
HSM/secure element:
- root signing;
- witness keys;
- recovery keys;
- non-exportable authority material.

No single hardware component replaces these layers.

## Replacement rule

A hardware root replacement must bind:

OLD_HARDWARE_INCARNATION
→ REPLACEMENT_AUTHORIZATION
→ NEW_HARDWARE_ID
→ NEW_HARDWARE_INCARNATION
→ CONTINUITY_EVIDENCE
→ RECOVERY_GENERATION
→ REVALIDATION
→ RELEASE.

The new hardware must not simply inherit the old identity.

## Compromise rule

If hardware compromise affects a protected claim:

CURRENT
→ SUSPECTED_HARDWARE_COMPROMISE
→ AUTHORITY_FREEZE
→ KEY/TRUST_GENERATION_INVALIDATION
→ DEPENDENCY_IMPACT
→ EXTERNAL_EFFECT_RECONCILIATION
→ NEW_ROOT/INCARNATION
→ REATTESTATION
→ REVALIDATION
→ RELEASE.

## Important finding about HSMs

An HSM is especially useful for protecting the ability to sign continuity evidence, but signing authority itself must remain subordinate to Z1 policy.

Therefore:

HSM_CAN_PROTECT_SIGNING_KEY
but
HSM_MUST_NOT_DEFINE_GLOBAL_AUTHORITY_BY_KEY_POSSESSION.

This prevents a hardware key from silently becoming “whoever possesses it is Nexo.”

## Important finding about TEEs

A TEE may enforce local rules that ordinary software cannot bypass, but Nexo cannot assume that a TEE implementation has the same failure model as a consensus state machine.

Therefore:
TEE_ENFORCEMENT != DISTRIBUTED_LINEARIZATION.

## Important finding about secure elements

Small secure hardware is valuable precisely because its exposed semantics can be narrow.

For Nexo, this favors using it for:
- identity keys;
- protected generation floors;
- recovery authorization material;

rather than placing the entire Nexo semantic model inside the device.
