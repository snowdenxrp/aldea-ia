# AB104.514 — revocation/freshness race closure

## Evidence
RFC 9334 states that freshness only narrows the recentness of evidence; the attester state or appraisal policy can change immediately after evidence is generated, so a race always remains unless the protected protocol adds stronger ordering/validation. citehttps://www.rfc-editor.org/rfc/rfc9334.html RFC 9334 also notes that epoch IDs can be delayed/replayed and that an epoch window is only a freshness mechanism, not proof that the underlying state remains unchanged. citehttps://www.rfc-editor.org/rfc/rfc9334.html NIST SP 800-102 describes verifier-supplied nonces as evidence that a signature was generated after the nonce was received, while noting that the signed message itself may have been assembled earlier; therefore nonce freshness does not automatically establish freshness of every claim. citehttps://www.nist.gov/publications/recommendation-digital-signature-timeliness

## Race timeline
The protected path must distinguish:
`ISSUED → EVIDENCE_GENERATED → EVIDENCE_APPRAISED → ADMITTED → DISPATCHED → EXTERNAL_EFFECT`
from concurrent invalidation:
`REVOCATION_REQUESTED → REVOCATION_COMMITTED → REVOCATION_VISIBLE`.

The dangerous interval is any overlap where evidence was valid at appraisal but a revocation/epoch/fence/target transition committed before the final protected-effect gate.

## Candidate closure rule
At final authorization, revalidate the current protected state against the admission snapshot:

`CurrentAuthorityEpoch == AdmissionAuthorityEpoch`
`CurrentRevocationGeneration == AdmissionRevocationGeneration`
`CurrentFenceRevision == AdmissionFenceRevision`
`CurrentTargetIncarnation == AdmissionTargetIncarnation`
`CurrentPolicyProfile == AdmissionPolicyProfile`
`CapabilityEvidenceStillEligible == TRUE`

If any required value advanced or became UNKNOWN:
`FINAL_GATE => REJECT_OR_RECOMPUTE_OR_QUARANTINE`.

This is stronger than merely checking the original evidence expiry time.

## Linearization requirement
A capability admission and its invalidation must share an authoritative ordering domain, or Nexo must have an explicit cross-domain fencing protocol. Otherwise it cannot prove which happened first when they race.

Candidate protected transaction:
`READ_CURRENT_STATE + VALIDATE_EVIDENCE + VALIDATE_REVOCATION + VALIDATE_FENCE + COMMIT_ADMISSION`
with a single authoritative revision/linearization point.

If the external provider cannot participate in that ordering, the final gate can only establish Nexo-side authorization; it cannot retroactively guarantee that an external effect was not already applied.

## In-flight effects
If revocation commits after external dispatch, Nexo must not reinterpret the historical authorization as invalid retroactively. Instead:
- record the revocation generation;
- preserve the original admission/effect identity;
- reconcile the external effect;
- determine whether compensation/reversal is supported;
- prevent subsequent retries under the revoked authority.

`REVOCATION_AFTER_EFFECT != EFFECT_NEVER_HAPPENED`
`REVOCATION_AFTER_DISPATCH != AUTOMATIC_ROLLBACK`
`HISTORICAL_AUTHORIZATION != CURRENT_AUTHORITY`

## Unknown ordering
If the system cannot establish whether revocation committed before or after the final gate/effect boundary, the result is `UNKNOWN_ORDER`, not an assumed safe ordering.

`UNKNOWN_ORDER => NO_BLIND_RETRY`
`UNKNOWN_ORDER + PROTECTED_EFFECT => RECONCILIATION_REQUIRED`

## Epoch-window limitation
An accepted previous epoch can prevent false negatives during propagation, but it must not override a current revocation/fence/target-incarnation change. Therefore epoch-window acceptance is subordinate to explicit invalidation generations.

`EPOCH_WINDOW_ACCEPTED != NONREVOKED`
`FRESH_EVIDENCE != CURRENT_AUTHORITY`
`CURRENT_EPOCH != CURRENT_TARGET`

## Race matrix
| Race | Required result |
|---|---|
| Evidence before revocation, final gate after revocation | Reject/recompute |
| Evidence after revocation but stale cached policy | Reject/recompute |
| Revocation after admission, before dispatch | Block dispatch |
| Revocation after dispatch, effect unknown | Reconcile; no blind retry |
| Revocation after confirmed effect | Preserve history; compensation only if explicitly supported |
| Target replaced after evidence | Reject stale incarnation |
| Fence advanced after admission | Reject stale fence |
| Ordering unavailable | UNKNOWN_ORDER / quarantine according to effect class |

## Invariants
- `EVIDENCE_FRESHNESS != REVOCATION_FINALITY`
- `ADMISSION_SNAPSHOT != CURRENT_STATE`
- `REVOCATION_AFTER_DISPATCH != NO_EFFECT`
- `REVOCATION_AFTER_EFFECT != RETROACTIVE_ERASURE`
- `UNKNOWN_ORDER != SAFE_ORDER`
- `EPOCH_WINDOW != REVOCATION_OVERRIDE`
- `TARGET_REPLACEMENT => STALE_EVIDENCE`
- `FENCE_ADVANCE => STALE_ADMISSION`
- `FINAL_GATE_REQUIRES_CURRENT_REVOCATION_GENERATION`
- `FINAL_GATE_REQUIRES_CURRENT_TARGET_INCARNATION`
- `NO_BLIND_RETRY_AFTER_UNKNOWN_ORDER`

## Status
Research complete. The race is closed on the Nexo side only when the final protected gate revalidates the current authority, revocation generation, fence, target incarnation, policy profile, and evidence eligibility against an authoritative ordering point. External-world ordering remains a separate boundary requiring provider reconciliation.

No implementation or formal verification performed.

Next exact step: AB104.515 — research cross-domain ordering when Nexo authority and provider state have separate revisions: hybrid logical clocks, provider revision binding, transaction/fence tokens, and the exact point where Nexo must downgrade from strong ordering to UNKNOWN.
