# Nexo AB104.405 — Effect Footprint / Participant Closure Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.404 → AB104.405
Implementation: NOT PERFORMED

## Research question

Can Nexo safely classify and authorize an external effect when the operation's protected footprint is not fully visible from its declared API/resource list?

## External evidence

- AWS transactional outbox documents the dual-write boundary between a durable state change and downstream event notification, including duplicate delivery and ordering concerns. A successful local transaction therefore does not itself establish downstream completion. [AWS Prescriptive Guidance]
- AWS Step Functions exposes Request/Response, Run-a-Job, and Wait-for-Callback patterns, demonstrating that one logical workflow can cross synchronous, asynchronous, and callback boundaries.
- Step Functions supports retries, parallel/distributed child executions, and redrive behavior; retry/redrive can change execution paths and child work.
- CloudEvents standardizes event description, but an event envelope does not by itself prove the complete downstream effect topology.

## Core finding

`DECLARED_FOOTPRINT != EFFECTIVE_FOOTPRINT`

A caller's participant list, API surface, or immediate resource set cannot be treated as the complete protected effect footprint.

Hidden or deferred participants may include downstream databases or queues; event buses and consumers; callbacks/webhooks; asynchronous workers; provider-managed automations; fan-out/parallel child executions; retries/redrives; triggers that invoke another provider; implicit secondary resources; and resource-incarnation-specific dependencies.

For high-consequence protected properties, an undiscovered participant is not equivalent to “no participant”.

## Required distinctions

1. `DECLARED_FOOTPRINT` — what the request/contract declares.
2. `DISCOVERED_FOOTPRINT` — participants derived from authoritative contract/path/capability information.
3. `OBSERVED_FOOTPRINT` — participants actually observed during execution.
4. `PROTECTED_FOOTPRINT` — participants whose behavior is inside the safety property being claimed.
5. `FOOTPRINT_CLOSURE_STATUS` — whether the protected footprint is complete for the claim.

`OBSERVED_FOOTPRINT` cannot prove `COMPLETE_FOOTPRINT`; absence of an observed event is not proof that no downstream participant exists.

## Candidate closure model

`PROPERTY + EFFECT_CLASS + OPERATION_CONTRACT + PATH_CAPABILITIES + PARTICIPANT_RULES + RESOURCE_INCARNATIONS`

→ `REQUIRED_FOOTPRINT_RULE`
→ `DECLARED_FOOTPRINT`
→ `DISCOVERED_FOOTPRINT`
→ `PARTICIPANT_CLOSURE`
→ `EFFECT_FOOTPRINT_STATUS`
→ Z1 final gate.

The closure must be claim-scoped. Nexo must not attempt universal closure of every possible downstream behavior.

## Asynchronous boundary

`ENQUEUE != DOWNSTREAM_EFFECT`

Admission to a queue, event bus, workflow, or callback mechanism authorizes at most the protected transition explicitly covered by that boundary. A downstream worker may require its own authority/effect admission unless the parent contract proves a safe inherited authorization and effect identity.

A provider acknowledgement that a message/job was accepted is not equivalent to external confirmation of all downstream work.

## Retry / redrive boundary

`RETRY != NEW_EFFECT_IDENTITY`, but also:
`RETRY != PROOF_OF_SAME_DOWNSTREAM_TOPOLOGY`

A stable EffectID can bind retries of the same logical operation only when provider/path semantics actually enforce that equivalence. Retry policy may alter execution paths, child executions, timing, or participant exposure. Therefore footprint closure must include relevant retry/redrive semantics.

## Cross-provider / trigger expansion

If resource R1 can trigger R2 in another authority/failure domain, then R2 may be a protected participant even if R2 is absent from the caller's request.

For E4/E5-class properties, unresolved cross-domain participant discovery should produce `UNKNOWN/HOLD/REVALIDATE`, not a weaker effect classification.

A gateway or adapter cannot silently hide downstream participants from the protected closure; if it is the claimed enforcement boundary, it must be included in the claim's TCB/dependency closure.

## Resource incarnation

A resource replacement can change its downstream topology, callbacks, policies, or provider capabilities.

Therefore: `RESOURCE_INCARNATION_CHANGE -> FOOTPRINT_CLOSURE_INVALIDATION` where the footprint depends on that incarnation.

The closure must bind relevant participants to exact resource incarnation and path/capability generations.

## Bounded closure

Universal dynamic closure is not a realistic admission requirement. Candidate policy should instead define a protected closure boundary and a bounded set of acceptable participant classes.

If closure exceeds the declared policy boundary, discovers an unbound protected participant, or encounters unresolved dynamic expansion: `FOOTPRINT_CLOSURE_STATUS = UNKNOWN` and the protected transition cannot silently proceed as if closure were complete.

## Candidate data

`EFFECT_FOOTPRINT_CONTEXT`: EFFECT_ID; OPERATION_ID; CLAIM_ID / PROPERTY_CLASS; EFFECT_CLASS_EFFECTIVE; ROOT_RESOURCE + RESOURCE_INCARNATION; DECLARED_FOOTPRINT_ROOT; DISCOVERED_FOOTPRINT_ROOT; PROTECTED_FOOTPRINT_RULE_VERSION; PARTICIPANT_SET_ROOT; PATH / ADAPTER IDENTITIES; CAPABILITY GENERATIONS; DYNAMIC_EXPANSION_STATUS; RETRY / REDRIVE SEMANTICS; CROSS_DOMAIN_PARTICIPANT_STATUS; CLOSURE_STATUS; INVALIDATION_GENERATION; LIMITATIONS.

These fields remain candidates; the claim contract determines which are necessary.

## Adversarial matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| hidden downstream DB | not declared => irrelevant | derive/close or UNKNOWN |
| queue worker | enqueue == completed effect | separate boundary |
| webhook/callback | provider ACK == callback completion | ACK only proves accepted boundary |
| fan-out | parent operation has one participant | expand protected closure |
| retry/redrive | same request means same topology | validate retry semantics |
| cross-provider trigger | downstream provider outside request | include participant or reject/hold |
| provider automation | documented API hides managed side effect | capability/evidence validation |
| resource replacement | same resource ID | bind incarnation |
| dynamic callback | runtime discovers new participant | new admission boundary or UNKNOWN |
| partial participant failure | one participant succeeds | PARTIAL_COMMIT / reconciliation |
| missing telemetry | no event observed | cannot infer absence |
| gateway | gateway hides downstream path | include gateway/path and downstream enforcement evidence |

## Candidate invariants

- `DECLARED_FOOTPRINT != PROTECTED_FOOTPRINT`
- `OBSERVED_FOOTPRINT != COMPLETE_FOOTPRINT`
- `UNDISCOVERED_PROTECTED_PARTICIPANT => CLOSURE_INCOMPLETE`
- `CLOSURE_INCOMPLETE => NO_HIGHER_AUTHORITY_GRANT`
- `ENQUEUE != DOWNSTREAM_EFFECT`
- `PROVIDER_ACK != DOWNSTREAM_CONFIRMATION`
- `RETRY != PROOF_OF_SAME_TOPOLOGY`
- `RESOURCE_INCARNATION_CHANGE => CLOSURE_REVALIDATION`
- `DYNAMIC_PROTECTED_EXPANSION => NEW_ADMISSION_BOUNDARY`
- `GATEWAY_CANNOT_HIDE_PROTECTED_PARTICIPANTS`
- `PARTICIPANT_SUCCESS != CROSS_RESOURCE_ATOMICITY`
- `ABSENCE_OF_OBSERVATION != EVIDENCE_OF_ABSENCE`

## Residuals / not proven

- Formal completeness of footprint derivation.
- Complete semantic rules for identifying all protected participants.
- Runtime implementation correctness.
- Provider-specific guarantees across all failover/retry paths.
- Formal proof that a bounded closure is sufficient for every effect property.
- Independent observation of every downstream effect.
- Cross-provider atomicity.
