# Nexo AB104.534 — Atomic snapshot versus fence-token final revalidation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Atomic snapshot and fence-token approaches solve different parts of the final-admission problem.

- An atomic snapshot gives Nexo a coherent view of its own authority-critical dependencies.
- A fence token converts that snapshot into a stale-writer defense only if the destination/provider actually enforces the token or an equivalent generation/precondition.
- If the provider cannot participate, Nexo can prove its own admission state but cannot prove that the external effect observes the same snapshot.

## Evidence
etcd transactions atomically evaluate multiple comparisons and apply a single success/failure branch, with one revision for the transaction. This supports coherent local conditional admission. Cloud Storage generation/metageneration preconditions make a remote mutation conditional on the exact resource state and reject mismatches with 412. Cloud Storage also documents that replacing an object creates a new generation, so name reuse does not preserve the old generation identity.

## Candidate pattern A — atomic local snapshot
1. Read/commit authority-critical VersionSet/DependencySnapshot atomically.
2. Validate authority, revocation, policy, capability, target identity and fence state.
3. Produce DecisionDigest and EffectID.
4. Dispatch externally.
5. Reconcile because the provider did not participate in the snapshot.

Strength: coherent Nexo-side decision.
Limit: no external stale-writer proof without provider enforcement.

## Candidate pattern B — fence token
1. Establish authoritative fence/generation F.
2. Bind EffectID + target incarnation + F.
3. Provider atomically checks/enforces F or an equivalent version.
4. Reject stale requests.
5. Reconcile resulting provider state.

Strength: protects against delayed/stale external actors when the provider enforces the token.
Limit: provider must understand/enforce the token; Nexo-local tokens alone are advisory outside Nexo.

## Candidate hybrid
SNAPSHOT -> DECISION -> FENCE_ISSUED -> PROVIDER_CONDITIONAL_ADMISSION -> RECEIPT -> RECONCILIATION

This is stronger than either alone for external effects, but it is still not global atomicity.

## Non-participating provider
If the provider cannot accept any bound fence/version/incarnation:
- Nexo may safely decide whether to admit based on its own current state;
- it cannot claim the provider will reject an old request after the decision;
- delayed/stale requests remain an external uncertainty;
- strong stale-writer protection requires compensation, isolation, provider-side controls, or UNKNOWN/quarantine.

## Critical distinctions
- ATOMIC_SNAPSHOT != EXTERNAL_ATOMICITY
- FENCE_TOKEN != FENCE_ENFORCEMENT
- LOCAL_SNAPSHOT != GLOBAL_SNAPSHOT
- DECISION_COMMITTED != EFFECT_APPLIED
- PROVIDER_PRECONDITION != NEXO_AUTHORITY_CHECK
- TARGET_GENERATION != GLOBAL_AUTHORITY_EPOCH
- NON_PARTICIPATING_PROVIDER => NO_CROSS_DOMAIN_LINEARIZATION
- CURRENT_LOCAL_STATE != PROOF_OF_REMOTE_STATE

## Nexo implication
The final gate should produce both a coherent authoritative snapshot and, for protected external effects, an externally enforceable fence/precondition whenever the claim requires stale-writer protection. Providers unable to participate must be represented explicitly as weaker capability domains rather than hidden behind a universal adapter.
