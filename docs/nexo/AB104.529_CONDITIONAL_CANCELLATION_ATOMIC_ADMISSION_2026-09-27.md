# Nexo AB104.529 — Conditional cancellation and atomic effect admission

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Provider-side conditional mutation can close a stale-writer race when the provider atomically checks a resource generation/version and performs the mutation. This is stronger than a separate read followed by an unconditional cancellation. However, it only establishes the provider-local conditional boundary; it does not automatically create cross-domain atomicity with Nexo authority.

## Evidence
Google Cloud Storage supports generation/metageneration preconditions. A mutation proceeds only when the supplied generation matches, otherwise it fails with 412. Its documentation explicitly describes delayed deletes and name reuse: binding the delete to the intended generation prevents a delayed request from deleting a replacement object.
Kubernetes uses resourceVersion for optimistic concurrency: a mutation can be conditioned on the observed version rather than blindly applying to a newer state.
etcd transactions provide compare-and-swap style atomic compare/write behavior inside the etcd consistency domain.

## Candidate provider pattern
CHECK(TargetIncarnation == I)
AND CHECK(TargetRevision == R)
AND CHECK(Fence == F, if provider-enforced)
THEN ATOMICALLY transition provider state / accept cancellation
ELSE REJECT

This closes TOCTOU inside the provider when all checked predicates participate in the same atomic provider operation.

## Cancellation limitation
A conditional cancellation is only a true cancellation of the original effect if the provider's state machine defines the cancellation transition as mutually exclusive with effect commit. If the provider can already have committed the effect outside that state, cancellation success cannot prove NON_EFFECT.

## Cross-domain limitation
Nexo can atomically decide REVOKE/FENCE in its own domain, while the provider atomically checks its own target version, but:
NEXO_ATOMICITY != PROVIDER_ATOMICITY != CROSS_DOMAIN_ATOMICITY.

Without an explicit bridge, the result remains two ordered domains rather than one global linearization point.

## Candidate capability classes
C0: unconditional cancellation/request.
C1: cancellation with target version precondition.
C2: atomic provider state transition with operation identity + target incarnation.
C3: C2 plus provider-enforced Nexo fence/generation.
C4: C3 plus durable operation identity and authoritative reconciliation.

These are capability classes, not quality scores.

## Critical distinctions
- READ_THEN_CANCEL != ATOMIC_CONDITIONAL_CANCEL
- PROVIDER_CAS != NEXO_AUTHORITY_CAS
- PROVIDER_ATOMICITY != CROSS_DOMAIN_ATOMICITY
- TARGET_VERSION != TARGET_INCARNATION
- TARGET_INCARNATION != NEXO_AUTHORITY_EPOCH
- PRECONDITION_REJECTED != PROOF_NO_PRIOR_EFFECT
- CONDITIONAL_CANCEL_SUCCESS != NON_EFFECT_CONFIRMED unless provider semantics establish mutual exclusion with effect commit
- FENCE_CHECKED != FENCE_ENFORCED

## Nexo implication
The provider capability vector should record whether cancellation is conditional, which identity/version predicates participate atomically, whether cancellation and effect commit are mutually exclusive in the provider state machine, whether a Nexo fence is actually enforced, and how the resulting state can be reconciled.
