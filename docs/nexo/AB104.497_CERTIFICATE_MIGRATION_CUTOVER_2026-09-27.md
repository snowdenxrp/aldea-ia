# AB104.497 — certificate migration cutover, mixed versions, crash and rollback

## Evidence
Raft joint consensus keeps a transitional configuration until it is committed; the old and new configurations cannot make unilateral decisions during the joint phase. citeturn0search0 etcd's current upgrade process permits mixed versions while using the lowest common protocol version, and only considers the cluster upgraded after all members are upgraded. Its documented downgrade is an explicit staged operation rather than an implicit fallback. citeturn0search1turn0search8 An etcd issue also demonstrates that upgrade/membership state can become inconsistent across snapshots during rolling upgrades, reinforcing that migration state must itself be durable and reconciled. citeturn0search7

## Nexo migration model
For certificate semantics, use an explicit migration epoch rather than simultaneous ambiguous acceptance:

`V_old_ONLY → V_MIXED_RESTRICTED → V_new_ACTIVE → V_old_RETIRED`

`V_MIXED_RESTRICTED` is not permission for both profiles to authorize the same claim. It is a compatibility state in which each certificate remains bound to its own schema/domain/semantic profile, while the authoritative policy defines exactly which profile may authorize which transition.

## Dual-read / dual-write
Dual-read may be used for historical compatibility, but reads must preserve the original certificate's schema/domain/epoch and must not normalize it into current authority.

Dual-write is safe only if both representations are generated from one canonical decision and are durably bound by the same transition identity. Two independently generated authority decisions are not equivalent to one decision.

Candidate rule:
`ONE_AUTHORITY_DECISION -> ONE_DECISION_DIGEST -> {OLD_ENCODING, NEW_ENCODING}`

If the encodings differ semantically, the system must not dual-write them as equivalent.

## Cutover
The cutover record should bind:
`MigrationEpoch + OldSchema + NewSchema + SemanticProfile + Domain + MembershipEpoch + MembershipDigest + TrustBasisEpoch + ActivationRevision`.

Before `CUTOVER_COMMITTED`, the new profile cannot become sole authority. After commit, old-profile authorization is rejected for protected transitions unless an explicit compatibility policy remains active.

## Crash matrix
- crash before migration record durable → remain old profile;
- migration prepared but not committed → recover as prepared/non-authoritative;
- new profile validated but cutover absent → no new-profile authority;
- cutover committed → recover new profile; do not infer rollback from missing acknowledgement;
- old verifier sees new critical semantics → reject/quarantine;
- conflicting cutover records → quarantine;
- rollback request → requires explicit authorized migration transition, not binary replacement.

## Mixed-version safety
The etcd model shows a useful principle: during mixed versions, the active protocol must be the common compatible subset, and stronger features are enabled only after the cluster reaches the required version state. citeturn0search1 Nexo should apply the same principle to semantic authority: the common subset must be explicitly declared and must not silently weaken a protected claim.

## Invariants
- `DUAL_READ != DUAL_AUTHORITY`
- `DUAL_WRITE != TWO_AUTHORITY_DECISIONS`
- `MIXED_VERSION != MIXED_SEMANTIC_AUTHORITY`
- `NEW_SCHEMA_VALIDATED != NEW_SCHEMA_ACTIVE`
- `CUTOVER_COMMITTED => CURRENT_PROFILE_IS_EXPLICIT`
- `MISSING_CUTOVER_ACK != ROLLBACK`
- `LEGACY_VERIFIER_UNKNOWN_CRITICAL_FIELD => REJECT`
- `ROLLBACK_REQUIRES_EXPLICIT_AUTHORIZATION`
- `HISTORICAL_CERTIFICATE_SCHEMA_MUST_BE_PRESERVED`
- `CONFLICTING_CUTOVER_RECORDS => QUARANTINE`
