# Nexo AB104.419 — Dynamic Hypergraph Cut Analysis and In-Flight Dependency Change

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.418 → AB104.419
Implementation: NOT PERFORMED

## Research question

How can Nexo update critical failure-domain cut analysis when witnesses, dependencies, trust generations, or failure domains change, without allowing an in-flight authority decision to rely on stale analysis?

## Evidence

NIST SP 800-160 Vol. 2 Rev. 1 treats attack scenarios and sources of fragility as system-level analysis problems and identifies attack graphs, attack trees, fault trees, FMECA, and STPA as analysis representations. This supports treating cut analysis as a model whose assumptions must remain tied to the current system configuration. citeturn0search37turn0search5

RFC 9334 explicitly separates Verifier appraisal from Relying Party authorization and states that freshness only narrows the acceptable recentness; state and appraisal policy can change immediately after evidence generation. This is directly analogous to a cut analysis becoming stale after its dependency graph changes. citeturn0search0

## Core finding

A cut analysis is not durable truth.

It is a claim-scoped analysis over a particular:

GRAPH_VERSION
+ POLICY_VERSION
+ TRUST_GENERATION
+ WITNESS_SET
+ DOMAIN_ASSIGNMENT

Therefore:

CUT_ANALYSIS_CURRENTNESS != CUT_ANALYSIS_EXISTENCE

and:

GRAPH_CHANGE => POSSIBLE_CUT_CHANGE

## Dynamic change classes

### D1 — witness membership change

Add/remove/suspend/revoke witness.

Effect:
- witness set root changes;
- quorum composition changes;
- cut sets may change.

Candidate:
WITNESS_SET_CHANGE => CUT_ANALYSIS_STALE

### D2 — dependency change

A witness gains or loses a relevant dependency.

Effect:
- hyperedge changes;
- shared failure domain may appear/disappear.

Candidate:
DEPENDENCY_CLOSURE_CHANGE => CUT_ANALYSIS_STALE

### D3 — trust-root change

Witness keys remain distinct but trust-root generation changes.

Effect:
- previous independence assumptions may no longer hold.

Candidate:
TRUST_GENERATION_CHANGE => CUT_ANALYSIS_STALE

### D4 — verifier/policy change

A common verifier or policy dependency changes.

Effect:
- multiple witness contributions can change simultaneously.

Candidate:
VERIFIER_OR_POLICY_GENERATION_CHANGE => CUT_ANALYSIS_STALE

### D5 — failure-domain reassignment

Provider migration, deployment migration, recovery-path change, operator-domain change.

Effect:
- domain overlap graph changes.

Candidate:
FAILURE_DOMAIN_GRAPH_CHANGE => CUT_ANALYSIS_STALE

## Incremental analysis candidate

Full recomputation is not required for every unrelated change, but safety cannot depend on an unproven incremental algorithm.

Candidate process:

1. identify changed node/domain;
2. traverse reverse dependency index;
3. mark affected claims;
4. invalidate affected cut analyses;
5. recompute impacted subgraphs;
6. validate unchanged assumptions;
7. publish new analysis generation;
8. bind Z1 admission to the new generation.

The reverse index is an optimization, not the authority.

If its completeness is uncertain:

REVERSE_INDEX_INCOMPLETE => FULL_RECOMPUTE / HOLD

## Monotonic invalidation

Safety-critical invalidation should be monotonic:

CURRENT_ANALYSIS
→ STALE
→ REVALIDATION_REQUIRED

It must not silently transition back to CURRENT merely because no new failure was observed.

A new current result requires a new analysis boundary.

## In-flight authority race

Timeline:

T0: cut analysis generated for GRAPH_G.
T1: Z1 begins evaluating operation.
T2: dependency changes to GRAPH_G+1.
T3: old cut analysis reaches final gate.

Unsafe behavior:

GRAPH_G analysis accepted under GRAPH_G+1 state.

Candidate protected predicate:

ALLOW only if:

CUT_GRAPH_VERSION == CURRENT_GRAPH_VERSION
AND
POLICY_VERSION == CURRENT_POLICY_VERSION
AND
TRUST_GENERATION == CURRENT_TRUST_GENERATION
AND
WITNESS_SET_ROOT == CURRENT_WITNESS_SET_ROOT
AND
QUORUM_POLICY_GENERATION == CURRENT_QUORUM_POLICY_GENERATION
AND
all required dependency generations remain unchanged

at one protected final gate/equivalent fencing boundary.

Otherwise:

STALE => REVALIDATE / HOLD.

## Why timestamps are insufficient

A cut result can be only seconds old and still be invalid if a critical dependency changed immediately after analysis.

Therefore:

RECENT_CUT_ANALYSIS != CURRENT_CUT_ANALYSIS

This follows the same freshness limitation described by RFC 9334 for attestation results. citeturn0search0

## Change impact cone

Candidate optimization:

For changed dependency d, compute:

IMPACT_CONE(d) =
all witness contributions
→ claims
→ failure domains
→ quorum policies
→ cut analyses
that transitively depend on d.

Only analyses inside the impact cone become candidates for invalidation.

But completeness of the impact cone is itself a security property.

## Hidden dependency discovery

If a previously unknown dependency is discovered:

D_new ∉ prior closure

then previous cut completeness is no longer established.

Candidate:

NEW_SECURITY_RELEVANT_DEPENDENCY
=> CUT_COMPLETENESS_UNKNOWN
=> REVALIDATION

Do not attempt to patch the old analysis by simply appending the dependency without recomputing affected cuts.

## Cut deletion versus cut addition

Dependency changes can:

- create a new smaller cut;
- remove a former cut;
- change affected witness membership;
- change the quorum threshold required after failure.

All are security-relevant.

Therefore an incremental update must prove both:

NO_NEW_CRITICAL_CUT_MISSED

and:

NO_OLD_ASSUMPTION_REUSED_AFTER_INVALIDATION.

## Trust-generation transition

Candidate transition:

G_old
→ ROTATION_PENDING
→ G_new_ACTIVE

During transition, policy must explicitly define which witness evidence can be used.

The cut analysis must bind to the effective trust generation.

Historical analysis under G_old remains historical; it does not automatically become current under G_new.

## Failure-domain merge

Two domains that were previously distinct can merge:

D1 != D2
→ shared provider/policy/recovery dependency
→ D1 ∪ D2

This can reduce effective independence without changing witness count.

Candidate:

DOMAIN_MERGE => REVALIDATION

## Failure-domain split

A domain can also split after architecture separation:

D1
→ D1a + D1b

This may improve independence, but the new property must be established rather than assumed.

Candidate:

DOMAIN_SPLIT => NEW_ANALYSIS_REQUIRED

## Quorum membership race

If a witness is revoked while cut analysis is being evaluated:

W_SET_G
→ revoke W
→ W_SET_G+1

The old cut analysis cannot be used to prove safety of the new quorum.

Candidate:

WITNESS_SET_GENERATION_MISMATCH => REVALIDATE

## Partitioned graph views

Two components may hold:

GRAPH_A
GRAPH_B

If they disagree about a security-critical dependency:

GRAPH_CONFLICT => UNKNOWN / QUARANTINED

Do not select the larger graph, newer timestamp, or majority view without a protected rule establishing current authority.

## Recovery after graph divergence

Candidate:

GRAPH_DIVERGENCE
→ FREEZE_HIGH_CONSEQUENCE_ADMISSION
→ COLLECT_GRAPH_VIEWS
→ VERIFY_PROVENANCE
→ COMPARE_GENERATIONS
→ RECONSTRUCT_DEPENDENCY_HISTORY
→ RECOMPUTE_AFFECTED_CUTS
→ ESTABLISH_NEW_GRAPH_GENERATION
→ REVALIDATE_QUORUM
→ RELEASE

This connects AB104.410–AB104.415 with the dependency graph.

## Candidate cut-analysis generations

Introduce:

CUT_ANALYSIS_GENERATION

bound to:

- GRAPH_VERSION
- DEPENDENCY_ROOT
- FAILURE_DOMAIN_GRAPH_ROOT
- WITNESS_SET_ROOT
- TRUST_GENERATION
- POLICY_VERSION
- QUORUM_POLICY_VERSION
- ANALYSIS_ALGORITHM_VERSION

A new analysis is a new evidence object, not a mutation of the old one.

## Candidate state machine

CURRENT
→ CHANGE_DETECTED
→ INVALIDATION_PENDING
→ STALE
→ RECOMPUTATION
→ VALIDATED
→ CURRENT

Exceptions:

DISPUTED
UNKNOWN
QUARANTINED

The historical CURRENT result remains preserved with its original generations.

## Candidate Z1 final gate

Z1 may accept cut analysis only if:

1. claim/property matches;
2. effect class matches;
3. analysis generation is current;
4. graph root is current;
5. witness set root is current;
6. trust/policy generations are current;
7. required dependency closure is complete;
8. no unresolved graph conflict exists;
9. final protected generations remain unchanged.

Otherwise no current high-consequence grant.

- RECENT_CUT_ANALYSIS != CURRENT_CUT_ANALYSIS
- NEW_SECURITY_RELEVANT_DEPENDENCY => CUT_COMPLETENESS_UNKNOWN
- DOMAIN_MERGE => REVALIDATION
- DOMAIN_SPLIT => NEW_ANALYSIS_REQUIRED

## Residuals

- Formal dynamic hypergraph algorithm remains open.
- Completeness of dependency-change detection remains open.
- Reverse-index integrity and recovery remain open.
- Efficient exact cut enumeration for large graphs remains open.
- Graph authority and distributed graph synchronization remain open.
- Cut analysis still does not prove semantic correctness of dependencies.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
