# Nexo AB104.543 — 2PC versus outbox/durable execution at the provider boundary

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
2PC can provide atomic commit across participants that genuinely implement the protocol and retain durable prepared state. An ordinary external API cannot be upgraded into a 2PC participant merely by wrapping it. Outbox/durable-execution patterns instead make the local intent durable and replayable, then cross the external boundary with idempotency and reconciliation. They do not provide global atomicity, but they avoid pretending that an unrelated provider is transactionally coupled.

## Evidence
Oracle describes 2PC as prepare then commit, with participants durably recording prepare state and remaining in-doubt until the coordinator's decision. PostgreSQL PREPARE TRANSACTION similarly stores prepared state durably for later commit/rollback. Microsoft’s 2026 transactional-outbox example describes atomically writing business state plus an event inside one transactional partition, followed by independent downstream relay; it explicitly identifies the dual-write crash gap. citeturn0search1turn0search9turn0search13

## 2PC model
PREPARE all participants
-> durable prepared state
-> COMMIT decision
-> COMMIT all participants

If a participant is prepared but the coordinator decision is unavailable, it may remain in-doubt and hold resources until recovery/decision resolution. This gives atomic commit within the protocol domain but introduces coordinator/recovery and blocking costs.

## Outbox/durable-execution model
LOCAL_ATOMIC_COMMIT:
  authoritative state + durable intent/outbox
then:
  dispatcher -> provider -> external effect
then:
  receipt/reconciliation

The local commit is atomic, but external execution is not. Therefore the state machine must retain EXTERNAL_ATTEMPTED / CONFIRMED / UNKNOWN rather than manufacture a global commit point.

## When 2PC is actually applicable
2PC is a candidate only when every required participant:
- implements the protocol;
- can durably prepare;
- can honor the coordinator's final decision after crash/restart;
- exposes compatible isolation/locking semantics;
- belongs to the declared transaction scope.

A REST API, cloud service, device, or arbitrary external system that lacks these properties is not a 2PC participant.

## Nexo candidate decision boundary
For heterogeneous effects, prefer:
AUTHORITY_COMMIT -> DURABLE_INTENT -> PROVIDER_ADMISSION -> EXTERNAL_ATTEMPT -> RECONCILIATION

For a genuinely 2PC-capable closed participant set, a separate transaction protocol may prove atomic commit within that set, but external side effects outside it remain separate.

## Critical distinctions
- PREPARED != COMMITTED
- 2PC_CAPABLE != GENERIC_EXTERNAL_API
- LOCAL_ATOMICITY != CROSS_DOMAIN_ATOMICITY
- OUTBOX != 2PC
- DURABLE_INTENT != EFFECT_APPLIED
- IDEMPOTENT_RETRY != ATOMIC_COMMIT
- COORDINATOR_RECOVERY != EXTERNAL_WORLD_RECOVERY
- RECONCILIATION != ROLLBACK

## Nexo implication
Do not choose 2PC merely because an operation spans multiple systems. First classify whether all participants actually support a common commit protocol. Otherwise the architecture should use durable intent/outbox or durable execution plus stable effect identity, provider fencing where available, and explicit reconciliation. This preserves UNKNOWN rather than hiding the external boundary.
