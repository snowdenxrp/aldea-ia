# Nexo AB104.531 — Minimum provider capability vector by effect class

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
The minimum provider capability required to reduce UNKNOWN depends on the effect class and the claim Nexo wants to make. A provider capability is not a quality score; it is a semantic prerequisite for a particular transition.

## Evidence
Cloud Storage request preconditions atomically compare generation/metageneration and reject a mutation when the target does not match, closing a provider-local stale-write race. Kubernetes resourceVersion provides ordered change tracking and conditional consistency semantics within a resource type. These demonstrate that version/identity preconditions are concrete provider capabilities, not generic guarantees.

## Candidate capability matrix

E0 — informational/no protected external effect:
- Fresh observation may be sufficient for the claim being made.
- Historical non-occurrence generally still requires history if the claim is historical.

E1 — reversible/local effect with authoritative current state:
- Current authoritative state + target identity/version may close some UNKNOWN states.
- Strong historical non-effect still requires coverage of the ambiguity interval.

E2 — idempotent external mutation:
- Stable operation identity/idempotency key.
- Request-parameter binding.
- Explicit idempotency scope.
- Provider retention/expiry semantics.
- Authoritative lookup/reconciliation.
- Target incarnation/version binding where reuse is possible.

E3 — conditional mutation/cancellation:
- E2 plus atomic target precondition (generation/version/incarnation).
- Provider state machine must define whether cancellation and effect commit are mutually exclusive.
- Rejection on stale precondition must be observable.
- Conditional success does not prove historical non-effect unless provider semantics provide that equivalence.

E4 — externally significant asynchronous effect:
- E3 plus durable operation record.
- Authoritative operation state.
- Stable receipts/revisions.
- Asynchronous completion semantics.
- Late callback binding to operation + incarnation.
- Reconciliation after timeout/failover.
- Defined retention horizon covering the ambiguity interval.

E5 — high-consequence/non-compensable effect:
- E4 plus provider-enforced Nexo fence/generation where feasible.
- Independent/authoritative observation path.
- Strong reconciliation capability.
- Explicit cancellation/compensation semantics.
- Recovery/quarantine path when cross-domain order is UNKNOWN.
- No automatic promotion from provider ACK to world-truth.

These are design classes, not rankings.

## Core rule
CAPABILITY_REQUIRED = CLAIM_REQUIRED.

A provider can satisfy one effect class and not another. Nexo must select the protected transition contract from the actual claim/effect class rather than assuming a universal provider interface.

## Candidate transition
ProviderCapabilityAssessment -> {SUPPORTED, UNSUPPORTED, UNKNOWN}
SUPPORTED means the documented/runtime evidence satisfies the exact semantic prerequisite for the requested effect class and scope.
UNSUPPORTED means the prerequisite is absent.
UNKNOWN means evidence is insufficient or stale.

UNKNOWN capability must not silently promote to SUPPORTED.

## Critical distinctions
- CAPABILITY != GUARANTEE_OF_CURRENT_STATE
- DOCUMENTED_CAPABILITY != VERIFIED_RUNTIME_BEHAVIOR
- PROVIDER_VERSION != PROVIDER_CAPABILITY_PROOF
- IDEMPOTENCY_SUPPORT != HISTORICAL_RECONCILIATION
- VERSION_PRECONDITION != CROSS_DOMAIN_FENCE
- CANCEL_SUPPORT != NON_EFFECT_PROOF
- RECEIPT_SUPPORT != WORLD_TRUTH
- EFFECT_CLASS != PROVIDER_CLASS

## Nexo implication
The Effect Adapter should expose a claim-specific capability vector, not a single provider score. Admission can require a minimum semantic set for the selected effect class; if that set is missing or UNKNOWN, the transition must degrade to RESTRICT/RECONCILE/QUARANTINE rather than silently weakening the claim.
