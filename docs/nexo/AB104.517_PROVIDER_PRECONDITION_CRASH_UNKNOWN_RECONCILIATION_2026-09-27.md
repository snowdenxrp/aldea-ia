# AB104.517 — provider precondition crash semantics and reconciliation

## Evidence
AWS EC2 documents that mutating requests can time out or encounter server errors even though the operation may already have completed, creating uncertainty about whether the request succeeded. Its idempotency model uses a client token and rejects reuse with different parameters. citeturn0search0 Google Cloud Storage similarly documents socket timeouts/TCP disconnects as retryable conditions but makes retry safety depend on idempotency; generation/ETag preconditions can make otherwise non-idempotent mutations conditionally idempotent. citeturn0search1turn0search2

## Core finding
A provider-side precondition can close the **stale-writer race at the provider mutation boundary**, but it does not by itself close the **client-to-provider knowledge gap after a crash or timeout**.

Therefore Nexo needs two separate properties:
1. `PRECONDITION_SAFETY`: stale requests are rejected by the provider.
2. `OUTCOME_RECONCILIABILITY`: an ambiguous request can later be mapped to APPLIED / NOT_APPLIED / UNKNOWN without creating a second logical effect.

`PRECONDITION_SAFETY != OUTCOME_CERTAINTY`.

## Crash/timeout matrix
| Event | What Nexo knows | Safe immediate classification |
|---|---|---|
| Provider returns explicit precondition failure | Predicate was false at provider mutation boundary | `PRECONDITION_REJECTED` |
| Provider returns bound durable success receipt | Provider accepted/applied operation under declared scope | `APPLIED` at provider scope |
| Connection lost before response | Request may have reached provider | `UNKNOWN` |
| Client crashes after dispatch, before durable receipt | External outcome may exist | `UNKNOWN` |
| Retry with same idempotency identity + same request digest | Provider may return original result/no second effect if contract guarantees it | `RECONCILE_OR_APPLIED` |
| Retry with same identity + different parameters | Provider must reject as parameter mismatch when such idempotency contract exists | `CONFLICT` |
| Fresh read proves exact target state required by operation | State observation can classify only if freshness/incarnation semantics are authoritative | `APPLIED` or `NOT_APPLIED` as scoped |

## Idempotency boundary
AWS explicitly scopes idempotency and rejects parameter mismatches for a reused client token. citeturn0search0 Nexo should therefore bind:
`IdempotencyKey/EffectID + RequestDigest + TargetIdentity + TargetIncarnation + ProviderScope`.

A retry is the same logical operation only when this binding remains identical. Changing target, incarnation, request parameters, or provider scope creates a different semantic request and must not silently inherit the old idempotency identity.

## Conditional precondition + idempotency
Cloud Storage shows that a mutation can become conditionally idempotent when an appropriate generation/ETag precondition is supplied. citeturn0search1 This is useful but the two properties solve different races:
- precondition → stale target state;
- idempotency → duplicate execution after retry.

Strong Nexo effect admission therefore needs both where the effect class requires both.

## Reconciliation state machine
`INTENT_DURABLE`
→ `EXTERNAL_ATTEMPTED`
→ either `PROVIDER_REJECTED` / `PROVIDER_ACKNOWLEDGED` / `UNKNOWN`

For `UNKNOWN`:
`RECONCILIATION_REQUIRED`
→ authoritative provider lookup / provider operation-history lookup
→ `APPLIED | NOT_APPLIED | UNKNOWN`

If the provider cannot expose sufficient history or authoritative current state, the terminal state remains `UNKNOWN` rather than being inferred from timeout, absence of an ACK, or a stale read.

## Preconditions do not prove non-effect after timeout
A request may have passed its precondition and then be applied before the connection fails. Conversely, it may have failed the precondition before the client receives the failure. Therefore a timeout cannot be translated into either success or rejection.

`TIMEOUT != PRECONDITION_REJECTED`
`TIMEOUT != NOT_APPLIED`
`TIMEOUT != APPLIED`

## Reconciliation evidence hierarchy
Candidate evidence strength:
1. provider-authoritative operation record bound to exact EffectID/request digest;
2. provider-authoritative current state with target incarnation + required postcondition;
3. provider receipt bound to exact operation and target;
4. ordinary current read;
5. cached/stale read or client-local observation.

Only the first levels that actually satisfy the effect-specific contract may resolve UNKNOWN. Evidence strength is claim-specific; no generic hierarchy automatically proves world truth.

## Critical invariant after revocation
If revocation occurs while an external operation is UNKNOWN, revocation does not prove that the operation was never applied. Nexo must preserve the original EffectID and reconcile it before considering retry/compensation.

`REVOCATION_DURING_UNKNOWN != NOT_APPLIED`
`UNKNOWN + NON_IDEMPOTENT_PROVIDER => NO_BLIND_RETRY`
`SAME_EFFECT_RETRY => SAME_CANONICAL_REQUEST_BINDING`

## Final contract
For a strong protected effect:
`CURRENT_NEXO_AUTHORITY`
AND `CURRENT_TARGET_INCARNATION`
AND `PROVIDER_PRECONDITION_ENFORCED`
AND `STABLE_EFFECT_IDENTITY`
AND `IDEMPOTENCY_SCOPE_KNOWN`
AND `RECONCILIATION_CAPABILITY_KNOWN`

Otherwise the effect class must downgrade its guarantee and explicitly expose `UNKNOWN` where outcome cannot be established.

## Invariants
- `PRECONDITION_SAFETY != OUTCOME_CERTAINTY`
- `TIMEOUT != PRECONDITION_REJECTED`
- `TIMEOUT != NOT_APPLIED`
- `TIMEOUT != APPLIED`
- `IDEMPOTENCY != PRECONDITION`
- `SAME_IDEMPOTENCY_KEY + DIFFERENT_REQUEST_DIGEST => CONFLICT`
- `UNKNOWN != SAFE_TO_RETRY_BLINDLY`
- `REVOCATION_DURING_UNKNOWN != NOT_APPLIED`
- `PROVIDER_RECEIPT_SCOPE_MUST_BE_EXPLICIT`
- `STALE_READ != AUTHORITATIVE_RECONCILIATION`
- `NO_RECONCILIATION_CAPABILITY => UNKNOWN_OR_QUARANTINE`

## Status
Research complete. Provider preconditions solve stale-state admission at the provider mutation boundary; idempotency solves duplicate retry execution; reconciliation solves the knowledge gap after ambiguous outcomes. They must remain separate contracts and be composed explicitly.

No implementation or formal verification performed.
