# Nexo AB104.421 — Differential Analyzer Independence and Common-Mode Failure

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY

## Research question

When two cut analyzers agree, what evidence supports treating that agreement as independent assurance rather than common-mode confirmation of the same defect?

## Evidence

NIST SP 800-160 emphasizes that system security is an emergent property of interacting components, dependencies, and system elements; independence therefore has to be analyzed across the actual dependency structure, not inferred from process or product identity alone. citeturn0search37turn0search5

NASA IV&V distinguishes independent verification and validation from ordinary verification/testing and describes independence across technical, managerial, and financial dimensions. This supports treating analyzer independence as a multi-dimensional property rather than “different executable = independent.” citeturn0search38turn0search36

RFC 9334 separates appraisal from relying-party authorization and models trust anchors, appraisal policy, and verifier behavior as relevant trust inputs. Two analyzers sharing such inputs may therefore share a common failure mode even if their implementations differ. citeturn0search0

## Core finding

Two different analyzers can fail identically because they share:

- the same flawed protected specification;
- the same graph source;
- the same parser/normalizer;
- the same policy;
- the same dependency-closure engine;
- the same test corpus;
- the same compiler/toolchain;
- the same runtime;
- the same deployment pipeline;
- the same trust roots;
- the same operator;
- the same recovery system.

Therefore:

DIFFERENT_IMPLEMENTATIONS != INDEPENDENT_ANALYSIS

and:

ANALYZER_AGREEMENT != CORRECTNESS_PROOF

## Independence is claim-specific

A1 and A2 may be independent with respect to implementation but correlated with respect to:

- policy;
- graph source;
- specification;
- trust root.

Thus:

ANALYZER_INDEPENDENCE = f(CLAIM, PROPERTY, FAILURE_MODEL, DEPENDENCY_CLOSURE)

not a permanent binary property.

## Common specification failure

If both analyzers implement the same wrong specification:

SPEC_WRONG
→ A1 wrong
→ A2 wrong

Agreement provides no independent semantic assurance.

Candidate requirement:

SPECIFICATION_ASSURANCE

must remain a separate evidence layer.

## Common graph-source failure

If both analyzers consume the same compromised graph:

GRAPH_WRONG
→ A1 agrees
→ A2 agrees

Differential implementation cannot detect the shared source defect.

Candidate:

GRAPH_SOURCE_INDEPENDENCE

for high-consequence claims where source compromise matters.

## Common parser failure

A1 and A2 may have distinct cut algorithms but share one parser.

A malformed graph can therefore enter both analyzers identically.

Candidate:

PARSER_INDEPENDENCE

or independent representation validation.

## Common normalization failure

Two analyzers may use separate parsers but one shared normalization library.

A semantic edge could be added/removed before analysis.

Therefore:

PARSER_DIVERSITY != SEMANTIC_PIPELINE_DIVERSITY

## Common policy failure

Both analyzers use policy P.

If P incorrectly says a dependency is irrelevant, both analyzers may correctly follow the same wrong rule.

Therefore:

POLICY_AGREEMENT != POLICY_CORRECTNESS

## Common test corpus

If both analyzers are validated against the same incomplete tests, they may miss the same mutation.

Candidate:

TEST_CORPUS_DIVERSITY

as an evidence dimension.

But different test corpora do not guarantee semantic independence if both derive from the same flawed specification.

## Common compiler/toolchain

Distinct implementations built by one compromised compiler/toolchain may share an implementation defect.

This does not mean compiler diversity is always required; it means the dependency must be included in the claim-specific failure analysis when relevant.

## Common runtime/deployment

Separate containers on one host or one orchestration control plane can share failure domains.

Therefore:

PROCESS_SEPARATION != FAILURE_DOMAIN_SEPARATION

## Common recovery

Two analyzers may be independent while running independently, but both restore from the same compromised snapshot.

Recovery independence must be analyzed separately.

## Common operator/governance

For high-consequence assurance, two technically separate analyzers may share one privileged operator capable of changing:

- specification;
- policy;
- graph;
- trust roots;
- deployment;
- test corpus.

That can become a common-mode domain.

## Independent specification problem

If both analyzers share the same specification, adding implementation diversity may not address the largest common-mode risk.

Candidate assurance stack:

SPECIFICATION
→ independent semantic review/model
→ reference model
→ analyzer A
→ analyzer B
→ differential comparison
→ independent appraisal
→ currentness validation

No single layer substitutes for another.

## Reference model independence

A reference model is useful only if it is simpler and materially different from the optimized analyzers.

Unsafe:

A1 and A2 optimized code
+
A3 copied implementation

This creates apparent multiplicity without meaningful independence.

## Shared libraries

Common cryptographic/parser/graph libraries may be acceptable for low-risk properties, but for high-consequence analyzer assurance their failure domain should be explicitly modeled.

No universal requirement for full software diversity is selected.

## Differential disagreement

If A1 and A2 disagree:

Do not automatically choose either.

Classify:

- parser disagreement;
- graph disagreement;
- policy disagreement;
- algorithm disagreement;
- currentness mismatch;
- dependency-closure disagreement;
- implementation defect;
- specification ambiguity;
- unknown.

Security-critical unresolved disagreement:

DISPUTED / UNKNOWN / HOLD

## Differential agreement

If A1 and A2 agree:

The result can be promoted only according to an explicit assurance policy that considers their shared dependencies.

Agreement may increase evidence strength, but:

AGREEMENT != PROOF

## Mutation independence

A useful differential test should include mutations targeted at each analyzer's distinct assumptions.

If both analyzers survive the same critical mutation:

COMMON_MODE_ORACLE_GAP

This can reveal that apparent implementation diversity is not meaningful.

## Deployment substitution attack

A validated analyzer may be replaced with another build carrying:

same version;
same interface;
different binary.

Therefore current deployment identity/digest must be bound to the validation evidence.

Candidate:

VALIDATED_ARTIFACT_DIGEST != CURRENT_DEPLOYED_ARTIFACT_DIGEST
=> NO_CURRENT_VALIDATION

## Policy substitution attack

Likewise:

VALIDATED_POLICY_VERSION != CURRENT_POLICY_VERSION
=> STALE_ANALYSIS

Policy must be bound to the evidence record.

## Residuals

- Exact quantitative/qualitative independence policy remains open.
- Semantic specification assurance remains a major upstream problem.
- Graph-source independence and dependency completeness remain open.
- Toolchain/deployment compromise detection remains open.
- Formal proof that analyzer diversity provides the intended assurance remains open.
- Implementation, fault injection, and deployment verification remain unperformed.
