# AB104.507 — protected-effect finality and fencing

## Research
etcd documents that its distributed lock only protects resources inside etcd's own keyspace; external resources require their own revision/fencing validation. It explicitly identifies fencing tokens as the mechanism preventing a paused/disconnected old holder from acting concurrently with a new holder. citeturn0search0turn0search9 The etcd Raft API distinguishes quorum-based safe linearizable reads from lease-based reads and notes that lease-based linearizability depends on bounded clock drift. citeturn0search11 NFS specifications provide concrete crash/partition fencing semantics: expired state must not silently remain usable, and revoked clients' operations must fail after fencing. citeturn0search2turn0search10 RFC 5663 further requires fencing against partitions and delays when resources move between clients. citeturn0search4turn0search12

## Nexo finding
A certificate can be current and still fail to protect an external effect unless the effect target participates in the same authority/fencing boundary.

Therefore separate:
`AUTHORIZATION_FINALITY` = the authority decision is committed under the accepted epoch/revision;
`EFFECT_FINALITY` = the target system has accepted that decision under a non-stale fence and cannot accept a superseded actor;
`OBSERVATION` = evidence that the effect occurred.

These are not interchangeable.

## Candidate protected-effect contract
`EffectPermit = {OperationID, DecisionDigest, AuthorityEpoch, RevocationGeneration, FenceToken, TargetIdentity, TargetRevision, Expiry/ValidityWindow}`

Before the irreversible/protected effect:
1. validate current authority/revocation generation;
2. validate current fence/generation at the target;
3. bind `OperationID` to the decision;
4. perform the target operation under that fence;
5. record durable outcome or explicit UNKNOWN;
6. reconcile after timeout/crash rather than blindly retrying.

## Why a lease alone is insufficient
A lease can detect or bound holder validity, but if the external resource does not validate a fencing token/revision, an old paused actor may continue operating after another actor receives a new lease. etcd explicitly warns about this boundary. citeturn0search0turn0search9

Candidate rule:
`LEASE_VALIDITY != EXTERNAL_EFFECT_AUTHORITY`
`FENCE_VALIDATION_AT_TARGET => PROTECTED_STALE_ACTOR_REJECTION`

Where the target cannot validate a fence, Nexo must not claim strong protected-effect safety from the authority layer alone.

## Consensus/linearization options
Three broad mechanisms were compared:
- quorum/consensus commit: strongest for establishing one ordered authority state, but does not automatically fence an external target;
- lease-based authority: useful for availability/optimization but depends on timing assumptions and still needs target fencing for external effects;
- explicit target fencing/version check: necessary when an old actor may physically or logically continue after authority changes.

A compensating action after an unsafe effect is not equivalent to preventing the unsafe effect:
`COMPENSATION != FENCING`.

## Partition and crash matrix
- partition before authorization commit → no protected effect;
- authorization committed, target unreachable → effect state `UNKNOWN`, never infer success;
- old actor resumes after fence increment → target rejects stale fence;
- crash after target commit but before local acknowledgement → reconcile by `OperationID`;
- retry with same `OperationID` → idempotent/reconcile path, not new authority;
- new authority while old target session remains alive → target fence must reject old generation;
- target has no fence/version validation → strong safety claim unavailable;
- conflicting target acknowledgements → `UNKNOWN/QUARANTINE` until reconciled.

## Invariants
- `AUTHORIZATION_FINALITY != EFFECT_FINALITY`
- `EFFECT_FINALITY != OBSERVED_SUCCESS`
- `LEASE_VALIDITY != EXTERNAL_EFFECT_AUTHORITY`
- `OLD_FENCE < CURRENT_FENCE => OLD_ACTOR_MUST_FAIL`
- `UNKNOWN_EFFECT != SUCCESS`
- `TIMEOUT != FAILURE_PROOF`
- `RETRY != NEW_AUTHORITY`
- `COMPENSATION != FENCING`
- `NO_TARGET_FENCE => NO_STRONG_EXTERNAL_EFFECT_SAFETY_CLAIM`
- `OPERATION_ID_MUST_SURVIVE_RETRY_AND_RECOVERY`

## Status
Research complete. No implementation or formal verification performed. The main architectural conclusion is that Nexo's authority model must terminate at a target-side fencing/linearization contract whenever it claims protection of an external effect. Where target fencing is impossible, the model must explicitly weaken its guarantee instead of pretending the authority certificate protects the resource.

Next exact step: AB104.508 — investigate idempotent effect protocols and UNKNOWN outcomes after crash/timeout, including operation identifiers, durable intent/outcome records, reconciliation, duplicate suppression, and how revocation interacts with an already-committed external operation.
