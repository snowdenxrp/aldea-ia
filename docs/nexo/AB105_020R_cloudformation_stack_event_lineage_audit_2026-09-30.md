# AB105.020R — CloudFormation stack-event lineage across acquisition boundaries
Date: 2026-09-30
Status: RESEARCH/AUDIT ONLY — no implementation, no semantic freeze.

## Research question

Does the provider's own CloudFormation stack-event stream supply enough lineage to bridge a resource-import/acquisition event to earlier lifecycle evidence?

## Primary evidence

AWS CloudFormation's StackEvent schema provides EventId, StackId, LogicalResourceId, PhysicalResourceId, ResourceType, Timestamp, ResourceProperties, ResourceStatus, ResourceStatusReason, ClientRequestToken, and OperationId where present.

AWS states that all events generated by a given stack operation share the same ClientRequestToken, while OperationId identifies the operation that generated the stack event when present. CloudFormation resource-status events delivered through EventBridge also include stack-id, logical-resource-id, physical-resource-id, status, status reason, resource type, and client-request-token.

CloudTrail independently records CloudFormation API activity and gives each event a unique eventID; records may also include requestID, resources, recipientAccountId, serviceEventDetails, and sharedEventID.

## Findings

### F1 — Stack events are materially stronger than a bare import timestamp

A StackEvent can bind an observation to a specific stack instance, logical resource, physical resource identifier, operation token, operation ID, status, and timestamp. This creates a substantially stronger provider-side correlation structure than an isolated timestamp.

Therefore the provider event stream can support bounded lifecycle reconstruction when the relevant events are retained and cover the target interval.

### F2 — EventId is event identity, not resource incarnation

EventId uniquely identifies the stack event. PhysicalResourceId identifies the physical instance associated with the resource event.

EventId != PhysicalResourceId
PhysicalResourceId != proof of complete historical continuity

A physical identifier can be strong target-binding evidence, but the examined provider schema does not state that every PhysicalResourceId is a globally immutable incarnation identifier across all resource types and lifecycle transitions. That claim must remain scoped to the semantics documented for the particular resource type.

### F3 — StackId gives stack-instance lineage, not complete resource lineage

CloudFormation defines StackId as the unique ID of the stack instance. This can distinguish stack incarnations that share a stack name.

However:
StackId != resource incarnation

Resources can be moved or refactored between stacks. AWS documents resource import as a mechanism that can move resources between stacks while retaining the resource. Stack lineage and resource lineage are therefore related but not identical.

### F4 — ClientRequestToken and OperationId provide explicit operation grouping

All StackEvents generated by a given stack operation share the same ClientRequestToken, and OperationId identifies the operation when present.

This provides a provider-supported relation:
stack_event -> stack_operation

It is stronger than inferring operation membership from timestamps, but operation grouping does not prove that the target had the same historical incarnation before the operation.

### F5 — PhysicalResourceId is useful but not sufficient as a universal historical bridge

A CloudFormation event can expose the physical resource identifier. Repeated events referencing the same identifier can therefore provide useful evidence about repeated observations of that target.

This does not by itself prove that the identifier existed continuously between observations, that no deletion/recreation/replacement occurred, that management was uninterrupted, or that all intermediate configuration states are known.

Those claims require provider/resource-specific semantics or independent evidence.

### F6 — ResourceProperties can bind expectation/configuration to a specific event

CloudFormation StackEvent may contain ResourceProperties. This is materially stronger than comparing an old event with today's template for a historical claim.

However, event-scoped ResourceProperties must not be silently promoted into a continuous historical configuration record for intervals where no observation exists.

### F7 — Forwarding through EventBridge does not create independent historical evidence

CloudFormation events delivered through EventBridge represent provider event semantics. Forwarding or re-indexing an event does not create new historical knowledge.

EventBridge_delivery(event) == another representation of provider evidence
not:
EventBridge_delivery(event) == independent historical observation

### F8 — Retention and coverage remain decisive

CloudTrail Event history is limited to 90 days and management events in a single Region/account context. AWS recommends trails or event data stores for ongoing records. Event data stores have configurable retention windows.

Therefore an absent historical event remains UNKNOWN unless the source contract establishes that the relevant event class, resource scope, account/region, and time interval were covered and retained.

Likewise, currently retrievable CloudFormation stack events cannot automatically be treated as a complete immutable lifecycle journal for every historical interval.

## Concrete acquisition-boundary chain

For an imported resource, the strongest provider-side reconstruction currently supported by the examined schemas is approximately:

1. CloudTrail/API evidence identifies the management/import operation.
2. CloudFormation StackEvent binds the operation to StackId, LogicalResourceId, PhysicalResourceId, operation token/OperationId where available, status, and timestamp.
3. Earlier StackEvents can be linked to the same physical identifier only where provider/resource semantics justify that continuity.
4. ResourceProperties/expectation identity can support claims about the configuration represented by each specific event.
5. Coverage and retention must establish that the searched event population is sufficient for the historical claim.
6. Any interval or lifecycle property not bridged by those contracts remains UNKNOWN.

This is a bounded evidence chain, not a general historical reconstruction engine.

## Anti-collapse rules

Do not collapse:
StackEvent.EventId -> resource incarnation
StackId -> resource incarnation
ClientRequestToken -> historical continuity
OperationId -> resource continuity
PhysicalResourceId -> complete lifecycle
Timestamp order -> causal order
ResourceProperties at event T -> configuration at every prior T
EventBridge copy -> independent evidence
Current retrievable events -> complete historical journal

## AB105.019R refinement

AB105.019R established that a provider event log can be a possible evidence bridge only when identity, lineage, semantics, scope, retention, expectation version, and causal/correlation relations are sufficient.

AB105.020R adds a concrete provider-specific result: CloudFormation StackEvents expose several required fields and explicit operation-grouping relations, making bounded reconstruction more plausible than from CloudTrail alone. However, the provider documentation examined does not establish a universal resource-incarnation contract for PhysicalResourceId across every resource type and lifecycle transition.

Therefore the acquisition boundary is still NOT globally closed.

## Exact next research direction

Investigate resource-type-specific identity semantics and replacement behavior for imported resources. Determine whether provider resource schemas/APIs expose a stable physical identity or incarnation boundary that can distinguish same-resource observation across management transitions, replacement, deletion/recreation, logical-ID reuse, and cross-stack movement.

Do not generalize PhysicalResourceId into an incarnation guarantee until the provider's resource-specific contract supports it.
