# AB104.519 — positive evidence: UNKNOWN → APPLIED

## Evidence
AWS EC2 idempotency binds retries to a client token and parameters; a retry with the same token and parameters can return the original successful result without performing another action. This demonstrates that positive outcome evidence is strongest when tied to stable operation identity rather than inferred solely from a later target state. citeturn0search1 AWS also distinguishes successful completion from transient/server errors and documents retry behavior by response class. citeturn0search1 etcd provides a contrasting model: completed operations are durable and linearizable reads return the current value, while serializable reads can be stale; historical revisions can later be compacted. citeturn0search8turn0search0

## Core finding
`UNKNOWN → APPLIED` requires positive evidence that is bound to the exact logical effect and sufficient for the claim being made.

Candidate proof:
`AppliedEvidence = {ProviderIdentity, OperationID/EffectID, RequestDigest, TargetIdentity, TargetIncarnation, ProviderRevision, ProviderReceipt, PostconditionEvidence, EvidenceScope, ObservedAt, Retention/Validity}`

The proof must establish:
1. the operation identity matches the original UNKNOWN operation;
2. the request digest matches the original canonical request;
3. the target identity/incarnation matches;
4. the provider evidence comes from an authoritative scope;
5. the provider revision/receipt is durable enough for the claimed property;
6. the observed postcondition is compatible with the exact effect;
7. no evidence invalidation or identity transition makes the observation ambiguous.

## Receipt vs target state
A target postcondition alone can be insufficient: another operation could produce the same state, or a later operation could change it after the original effect. An exact provider operation record/receipt bound to `EffectID + RequestDigest` is therefore preferred when available.

`TARGET_POSTCONDITION != OPERATION_RECEIPT`
`CURRENT_STATE_MATCH != PROOF_OF_HISTORICAL_OPERATION`

Conversely, a receipt whose scope is only "request accepted" may prove less than "effect durably applied to target". Provider receipt semantics must be explicit.

## Provider revision
A provider revision can establish where the observation sits in that provider's ordering domain. etcd revisions are monotonically increasing and linearizable reads provide current-state semantics when using the linearizable API path. citeturn0search7turn0search8 But a revision does not automatically prove Nexo-side authority or global-world state.

`PROVIDER_REVISION != NEXO_REVISION`
`PROVIDER_REVISION != WORLD_TRUTH`

## Retention and replay
Positive evidence must survive long enough for Nexo's required audit/recovery horizon or be replaced by an independently verifiable durable artifact. etcd shows that historical revisions can be compacted and become inaccessible. citeturn0search0 Therefore a provider receipt/reference that points only to ephemeral history cannot support indefinite reconstruction after retention expiry.

Candidate durable binding:
`ReceiptDigest + ProviderRevision + TargetIncarnation + RequestDigest + EffectID + EvidenceRetentionClass`.

If the underlying provider record is later pruned, the remaining digest is not automatically sufficient to reconstruct the claim unless Nexo has independently preserved the authoritative receipt bytes or another trusted proof.

`RECEIPT_REFERENCE != PRESERVED_RECEIPT`
`PRUNED_HISTORY != HISTORICAL_PROOF`

## Idempotency and positive recovery
When the provider's idempotency contract returns the original result for the same operation identity, a retry can resolve UNKNOWN to APPLIED without creating a new effect. AWS explicitly documents this behavior for identical client-token requests. citeturn0search1

But the identity scope matters: AWS documents regional/zonal differences, so the same token can represent distinct operations in different scopes. citeturn0search1

Therefore:
`IDEMPOTENCY_KEY + SCOPE + PARAMETERS = OPERATION_BINDING`.

## Positive reconciliation state machine
`UNKNOWN`
→ `RECONCILIATION_QUERY`
→ `OPERATION_IDENTITY_MATCHED`
→ `TARGET_INCARNATION_MATCHED`
→ `AUTHORITATIVE_POSITIVE_EVIDENCE`
→ `APPLIED`

If any required stage fails:
`UNKNOWN_OR_QUARANTINE`.

A weaker observation may instead resolve only a weaker claim, such as `PROVIDER_ACCEPTED`, without promoting to `EXTERNAL_EFFECT_CONFIRMED`.

## Effect-class boundary
For an E0/E1-like informational operation, a provider acknowledgement may be sufficient. For stronger effect classes, Nexo should require provider-specific evidence that the actual state transition occurred. The evidence contract therefore belongs to the effect class, not merely the transport API.

`ACK_SCOPE != EFFECT_SCOPE`
`PROVIDER_ACCEPTED != EXTERNAL_EFFECT_CONFIRMED`

## Revocation interaction
If capability revocation occurs after the provider has durably applied the original effect, the later revocation does not erase the historical applied event. Nexo records:
`EffectAppliedAt(EvidenceRevision)` and separately:
`AuthorityRevokedAt(RevocationGeneration)`.

The resulting history can truthfully state that an effect was authorized under an earlier generation and later revoked; it must not rewrite the earlier outcome.

## Status
Research complete. Positive reconciliation is the mirror of negative reconciliation: it requires exact operation binding, target-incarnation binding, authoritative provider evidence, sufficient durability/retention, and an effect-class-specific proof level. A matching current state or generic acknowledgement cannot automatically prove the historical external effect.

No implementation or formal verification performed.
