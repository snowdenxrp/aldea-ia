## Research question
How much independence is required before Nexo can rely on capability evidence, and when should promotion require dual control or quorum?

## Fresh external evidence
RFC 9334 separates Attester, Verifier, and Relying Party roles and states that the Relying Party applies its own policy to Attestation Results. It also warns that freshness only narrows the race window; system state can change immediately after an attestation result is produced. citeturn0search0

NIST's zero-trust architecture similarly separates policy decision from policy enforcement and treats enforcement at/near the protected resource as a distinct function. citeturn0search24turn0search1

These sources support role separation, but they do not prescribe Nexo's exact quorum thresholds.

## Independence classes
I0 — self/producer path: provider claim, provider logs, provider telemetry.
I1 — separate observation path but same provider/failure domain.
I2 — independent test execution/observer path.
I3 — independent trust domain/verifier.
I4 — independent provider/resource implementation or independently controlled enforcement boundary.

Independence is multidimensional. Two systems with different process IDs but the same provider, adapter, telemetry and control plane are not fully independent.

## Candidate promotion thresholds

| Effect class | Capability evidence threshold | Promotion control |
|---|---|---|
| E0 Read/observation | I1 for ordinary freshness; I2 where ambiguity affects decisions | Single verifier may promote low-consequence claims |
| E1 Reversible mutation | I2 for AF/DFS/R; I3 for highest-consequence recovery claims | Dual-control for AF/DFS promotion |
| E2 Idempotent mutation | I2 for ID/AB/R; I3 for AF/DFS when stale-authority exclusion is claimed | Dual-control for authority/fence claims |
| E3 Non-idempotent reversible | I3 for AF/DFS/R/RV | Dual-control; quorum may be required for cross-domain evidence |
| E4 Irreversible | I3 minimum; I4 preferred for AF/DFS/XF and exact confirmation | Dual-control mandatory; no promotion on verifier unavailability |
| E5 Multi-resource | I3 per participant + independent composition evidence; I4 for strongest global atomicity claims | Multi-party approval / quorum; no weakest-participant bypass |

These are candidate policy thresholds, not proven universal numbers.

## Why thresholds rise with effect severity
For E0, an incorrect capability claim may mainly produce stale/incomplete information.
For E4, a false claim can authorize an irreversible external effect.
For E5, a false claim at one participant can invalidate the global property.

Therefore evidence independence should scale with consequence and with the number of failure domains whose behavior is part of the claim.

## Dual-control model
For high-consequence promotion:
1. Verifier A independently appraises the evidence.
2. Verifier B independently appraises the same claim under the same authorized policy but with an independent execution/evidence path.
3. Promotion record is created only when both results satisfy policy.
4. Authority plane accepts the promotion result; neither verifier alone gains operational authority.

Dual control is meaningful only if A and B are actually independent for the property being claimed.

## Quorum model
For multi-resource or multi-domain claims, candidate quorum record:
PROMOTION_CLAIM {
  claim_id
  participants[]
  evidence_roots[]
  verifier_results[]
  independence_classes[]
  policy_version
  quorum_rule
  contradictions[]
  authority_decision
}

A quorum must be claim-specific. A 2-of-3 rule is not automatically safe if two members share the same provider/control-plane failure domain.

Candidate rule:
quorum_count != independence_guarantee

Weighted/domain-aware quorum is stronger:
required_independent_domains >= K
AND required_participant_coverage = ALL_RELEVANT_PARTICIPANTS
AND no unresolved contradiction affecting the claim.

## Provider/gateway collusion attack
If provider and gateway collude or share a compromised control plane, provider telemetry + gateway logs + gateway verifier are common-mode evidence.

For a stale-authority claim, this cannot establish independence merely by increasing evidence count.

Candidate response:
- classify shared dependencies;
- require an independent resource-side observer/enforcer;
- or downgrade the claim to gateway-boundary-only;
- or HOLD/QUARANTINE.

## Verifier unavailable
RATS describes verifier unavailability as a distinct failure case. citeturn0search0

Candidate Nexo rule:
- Existing VALIDATED result may remain usable only until its declared validity/freshness boundary and only if no invalidation event occurred.
- New safety-critical promotion cannot occur without required verifier evidence.
- Do not substitute provider self-attestation for unavailable verification.
- If current capability is UNKNOWN and the effect requires it, HOLD/RESTRICT rather than infer safety.

## Verifier compromise
A verifier compromise invalidates results that depend on it according to the trust model. A second verifier is useful only if its trust root, evidence path, policy source, and runtime boundary are sufficiently independent.

## Policy-owner compromise
The appraisal policy itself is a trust input. If the policy owner or policy distribution path is compromised, promotion results based on the affected policy cannot be treated as authoritative until policy integrity is restored.

## Freshness race
A fresh attestation does not freeze provider state. Therefore:
VALID_AT_T0 != GUARANTEED_VALID_AT_T1

For effects requiring current authority/fence, the protected operation must revalidate at the final gate or rely on a resource-side enforcement mechanism that makes stale work fail.
