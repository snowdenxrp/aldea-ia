# AB105.019R — Provider event logs as a possible acquisition-boundary bridge
Date: 2026-09-30
Status: RESEARCH/AUDIT ONLY — no implementation, no semantic freeze.

## Question

Can provider-side event logs/audit trails bridge the evidence gap across a resource acquisition/management boundary, and what minimum lineage must exist before a later reconstruction of pre-acquisition history is justified?

## Primary evidence reviewed

### AWS CloudTrail

AWS documents that CloudTrail Event history provides a searchable/downloadable immutable record of the past 90 days of management events, scoped by AWS Region. For longer-lived records AWS points to trails or event data stores. Event history is separate from trails/event data stores.

CloudTrail event records expose, among other fields:
- eventTime
- eventVersion
- userIdentity
- eventSource
- eventName
- awsRegion
- requestID (optional)
- eventID (required)
- resources (optional)
- recipientAccountId (optional)
- serviceEventDetails (optional)
- sharedEventID (optional)

CloudTrail defines eventID as a GUID that uniquely identifies an event. requestID is generated by the called service. eventTime is the time the request was completed, using the service API endpoint's host clock. Therefore eventTime is an event timestamp, not by itself a causal-order proof.

CloudTrail coverage is also bounded by the configured source/selector and by the event type/service. Event history itself is management-event-only and limited to 90 days. CloudTrail Lake/event-data-store retention is configurable, and retention is evaluated using eventTime.

### AWS CloudFormation resource import

CloudFormation resource import requires a template plus resource identifiers. Import validation checks that the resource exists, that the supplied template properties satisfy the resource type schema/required properties, and that the resource is not already managed by another stack. AWS explicitly states that import does NOT check that template configuration matches the resource's actual configuration.

AWS recommends drift detection after import for that comparison.

This means a CloudTrail record proving an import API action can establish that an import-management event occurred, but it does not by itself establish the resource's complete pre-import lifecycle or pre-import configuration history.

## Findings

### F1 — An event log can be historical evidence, but only for what the event actually observes

A provider audit record can establish a provider-side event at a particular time and scope. It does not automatically establish every prior state of the target.

Therefore:

provider_event(t1) -> historical_fact(t1)

is valid only within the semantics of the provider event.

But:

provider_event(t2) -> arbitrary_state(t1)

is not valid merely because the later event names the same resource.

### F2 — eventID is event identity, not target/incarnation identity

CloudTrail's eventID uniquely identifies the audit event. The event record separately carries resource information when available.

Therefore:

eventID != resource_identity
eventID != resource_incarnation
eventID != historical_lineage

A reconstruction that uses only eventID/requestID cannot safely distinguish a reused logical identifier, reattached resource, or different incarnation unless the provider supplies an explicit binding.

### F3 — requestID and eventID provide correlation, not universal causality

requestID identifies the service request and eventID identifies the CloudTrail event. sharedEventID can link copies of the same AWS action delivered to different accounts.

These identifiers are useful correlation anchors, but a timestamp ordering such as:

eventA.eventTime < eventB.eventTime

does not itself prove:

eventA caused eventB

A causal edge requires provider semantics, explicit correlation, or another independently supported relation.

### F4 — target identity must be stronger than a reused logical name

A resource ARN/name/identifier can identify the target of an event, but the acquisition-boundary problem specifically concerns whether the same physical/logical target is the same historical incarnation.

Minimum safe treatment therefore separates:

target_identity
+
incarnation/lineage

If the provider does not expose an incarnation/lineage binding, historical reconstruction across identity reuse remains UNKNOWN unless another authoritative source supplies that bridge.

### F5 — expectation version is conditional, not interchangeable with event identity

For claims about configuration conformance, the evidence must bind the observed target to the exact expectation/template/version being evaluated.

AB105.009R already established:

observation under expectation E2 != proof of conformance under earlier expectation E1.

Therefore an expectation_version/template identity is required whenever the reconstructed claim is about historical conformance, drift, or policy compliance. It is not a substitute for target identity or event identity.

### F6 — retention and coverage are part of historical admissibility

CloudTrail Event history's 90-day window and the configurable retention of event data stores demonstrate that an event source can be authoritative while still having an incomplete historical window.

Absence of a matching event therefore cannot be interpreted as proof that the event never happened unless the evidence source's coverage, retention, selector scope, and relevant service/event coverage are themselves established.

Thus:

no_event_found != event_did_not_occur

unless the source contract proves complete coverage for the claim's population and interval.

### F7 — acquisition event does not retroactively become a lifecycle checkpoint

A CloudFormation import event can establish the management-acquisition action. It cannot, without additional provider lineage evidence, prove:
- the resource's complete pre-import history,
- its pre-import configuration at an arbitrary earlier time,
- that no earlier drift occurred,
- that an earlier expectation was satisfied,
- or that the current managed incarnation is historically continuous with every prior use of the logical identifier.

This directly preserves the AB105.018R boundary.

## Minimum lineage required for historical reconstruction

A historical reconstruction crossing the acquisition boundary should not be admitted from a provider event log unless the evidence set can establish, at minimum:

1. **event_identity**
   - provider event ID or equivalent immutable event identity.

2. **event_semantics**
   - provider/source, event type/name, and enough schema/version information to interpret the event.

3. **target_identity**
   - unambiguous resource identity, including identifier type/value and ARN or provider-equivalent identity where applicable.

4. **incarnation_or_lineage**
   - explicit provider lineage/incarnation identity, or an authoritative cross-record binding that establishes continuity of the same resource incarnation.
   - If unavailable: UNKNOWN for claims requiring continuity across the boundary.

5. **event_time**
   - provider-defined event time with its semantic meaning preserved.
   - Retrieval/ingestion time must not be substituted for event time.

6. **scope**
   - account/tenant, region/location, resource scope, and any selector/population boundary necessary to know what the record covers.

7. **authority**
   - identity/source that generated the event and the authority semantics under which the record is considered authoritative.

8. **retention_and_coverage**
   - retention interval, source configuration/selector scope, and evidence that the relevant service/event class was covered for the claimed period.

9. **expectation_version**
   - required when the claim concerns historical conformance, drift, policy, or configuration expectation.
   - Must identify the exact expectation/template/version, not merely the current one.

10. **causal_or_correlation_relation**
   - explicit provider correlation/causal relation where reconstruction depends on linking multiple events.
   - Timestamp order alone is insufficient.

11. **integrity/provenance**
   - provenance showing where the event record came from and whether the record was retained in a manner sufficient for the intended evidentiary claim.

## Reconstruction admission rule

A later provider event may bridge the acquisition boundary only for a specific historical claim when the provider evidence supplies the required identity/lineage relation and the source contract establishes coverage and retention for the claimed interval.

Otherwise:

later_event -> current/provider-observed fact

and:

pre_acquisition_historical_claim -> UNKNOWN / unsupported

must remain separate.

In particular:

IMPORT_EVENT != PRE_IMPORT_STATE_PROOF
EVENT_ID != RESOURCE_LINEAGE
REQUEST_ID != CAUSAL_PROOF
TIMESTAMP_ORDER != CAUSAL_ORDER
RESOURCE_NAME/ARN != INCARNATION_PROOF
EVENT_PRESENT != COMPLETE_HISTORY
NO_EVENT_FOUND != EVENT_NEVER_OCCURRED
CURRENT_EXPECTATION != HISTORICAL_EXPECTATION
CURRENT_AUTHORITY != PAST_AUTHORITY

## Coverage consequence

The event-log route is a possible evidence bridge, not an automatic bridge.

For Nexo's evidence graph, the acquisition boundary can be closed for a particular claim only when:
- the target is bound to the correct incarnation/lineage,
- the event semantics establish what was actually observed,
- the expectation version is bound when relevant,
- the temporal and scope semantics are explicit,
- the source had sufficient retention and coverage,
- and the causal/correlation relation used for reconstruction is provider-supported rather than inferred from timestamps.

If any of those are missing, the unsupported portion remains UNKNOWN rather than being reconstructed by inference.

## Exact next research direction

Investigate concrete provider event chains where an acquisition/import action can be linked to earlier resource lifecycle events, with special attention to:
- whether provider APIs expose stable incarnation identifiers,
- whether import/acquisition events contain explicit target-resource lineage,
- whether CloudTrail/CloudFormation records can be joined without inferring causality from timestamps,
- and what coverage guarantees exist for the underlying service events.

Do not convert this into architecture or implementation until the evidence gap is actually closed.
