# AB104.510 — provider reconciliation capability vector

## Evidence
etcd distinguishes linearizable reads from serializable reads that may be stale, and assigns monotonically increasing revisions to modifications; watch events are ordered and resumable but are not themselves linearizable. citeturn0search0turn0search1 Kubernetes similarly exposes explicit resource-version semantics including `Most Recent`, `Not Older Than`, and `Exact`, with explicit handling for unavailable/compacted revisions. citeturn0search2turn0search3 AWS EC2 documents eventual consistency and recommends confirming resource state before subsequent mutation; its idempotency contract binds retries to the same client token and parameters. citeturn0search5turn0search6

## Nexo capability vector
A provider must not be classified simply as "consistent" or "eventually consistent". Reconciliation needs a capability vector:

`R = {FreshRead, Revision, MonotonicReceipt, AuthoritativeStatus, ReadAfterWrite, IncarnationIdentity, TombstoneVisibility, IdempotencyScope, DuplicateDetection, UnknownSemantics, HistoricalLookup, FenceEnforcement}`

Each dimension has an evidence level and scope. A capability at one scope must not be promoted to another.

## Capability meanings
- **FreshRead:** can return state at or beyond a specified revision/freshness boundary.
- **Revision:** returned state carries a comparable monotonic version.
- **MonotonicReceipt:** provider receipt can prove an operation reached a particular provider revision/state.
- **AuthoritativeStatus:** a documented source is authoritative for the target state.
- **ReadAfterWrite:** a successful mutation can be subsequently observed under a defined consistency guarantee.
- **IncarnationIdentity:** resource identity distinguishes replacement/recreation from the prior object.
- **TombstoneVisibility:** deletion/absence can be observed with sufficient identity and revision semantics.
- **IdempotencyScope:** exact scope in which an operation key prevents duplicate application.
- **DuplicateDetection:** provider can identify an already-applied logical operation.
- **UnknownSemantics:** provider explicitly documents what timeout/lost response means; absence of such documentation does not imply NOT_APPLIED.
- **HistoricalLookup:** prior operation/resource state can be queried within a defined retention window.
- **FenceEnforcement:** provider/resource rejects stale actor generations rather than merely recording them.

## Capability classes
Candidate classes:
- `R0`: no trustworthy reconciliation capability beyond best-effort observation;
- `R1`: freshness/revision evidence but weak effect identity or idempotency;
- `R2`: stable operation identity + authoritative status/reconciliation;
- `R3`: R2 + target incarnation + monotonic receipts + enforceable fence;
- `R4`: R3 + durable historical lookup sufficient to resolve late/crash outcomes.

These are design classes, not quality scores. A provider can be strong in one dimension and weak in another.

## Critical distinction
Kubernetes demonstrates why "resourceVersion" has multiple semantics: an exact revision, a lower-bound freshness constraint, and a most-recent read are different guarantees. citeturn0search2turn0search3 Therefore Nexo must store the exact capability semantics used for each reconciliation decision, not just the provider's name/version.

## Decision rule
For each effect class `E` define required capability predicate `Required(E)`. Then:
`ProviderCap(R) ⊨ Required(E) => reconciliation path eligible`.

Otherwise:
`INSUFFICIENT_CAPABILITY => UNKNOWN_OR_QUARANTINE`, unless the operation is provably impossible without the missing capability.

A capability claim must include scope, version, evidence source, observation time, and trust basis. A provider's documentation is evidence about the contract; runtime attestation/monitoring is separate evidence about actual deployment behavior.

## Idempotency scope
AWS shows that idempotency may be scoped by Region or Availability Zone; therefore `IdempotencyKey` without scope is insufficient. citeturn0search5 Nexo should bind:
`{OperationID, Provider, IdempotencyScope, RequestDigest, TargetIdentity, TargetIncarnation}`.

Retry across a different scope must not be assumed equivalent to retry within the original scope.

## Invariants
- `PROVIDER_CLASS != PROOF_OF_CURRENT_STATE`
- `FRESH_READ != EFFECT_CONFIRMATION`
- `REVISION != INCARNATION`
- `RECEIPT != WORLD_TRUTH`
- `IDEMPOTENCY_KEY_WITHOUT_SCOPE != COMPLETE_OPERATION_IDENTITY`
- `ABSENCE_ON_STALE_READ != NOT_APPLIED`
- `MISSING_PROVIDER_CAPABILITY => UNKNOWN_OR_QUARANTINE`
- `CAPABILITY_SCOPE_MUST_BE_EXPLICIT`
- `DOCUMENTED_CAPABILITY != VERIFIED_DEPLOYMENT_BEHAVIOR`
- `PROVIDER_FAILOVER != SAME_RECONCILIATION_SCOPE`

## Status
Research complete. The capability vector is now the candidate abstraction between provider-specific semantics and Nexo's generic reconciliation protocol. No implementation or formal verification performed.

Next exact step: AB104.511 — research how to verify provider capability claims at runtime and detect capability drift: contract probes, attestation, canary operations, version/config changes, and safe demotion when a previously trusted capability becomes UNKNOWN.
