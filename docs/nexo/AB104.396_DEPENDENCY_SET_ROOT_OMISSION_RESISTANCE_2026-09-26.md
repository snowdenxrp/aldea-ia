# Nexo AB104.396 — Dependency-Set Root and Omission Resistance

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective
Attack whether a stable dependency-set root/digest can make closure completeness machine-checkable, prevent omitted dependencies from escaping final validation, and remain coherent under graph mutation and migration.

RFC 9162 documents Merkle inclusion and consistency proofs: a root commits to tree contents, while an inclusion proof demonstrates membership and consistency proofs demonstrate append-only continuity. This is useful evidence for commitment structure, but it does not by itself prove that Nexo's dependency graph is semantically complete. citeturn0search1turn0search2

RFC 9334 likewise treats freshness as policy-bound and explicitly notes races when state or appraisal policy changes around epoch transitions. Therefore a dependency root cannot replace final current-state validation. citeturn0search0

## 1. Candidate dependency-set root

Define:

DEPENDENCY_ROOT = H(canonicalized required dependency declarations + edge semantics + scope + resource/incarnation bindings + graph generation)

Candidate closure result binds:
- graph_version
- graph_root
- dependency_root
- policy_version
- dependency_state_versions
- resource_incarnations
- authority/invalidation generations where relevant

The root is a commitment to a declared graph/set, not proof that the declaration itself is complete.

## 2. Omission attack

Attack:
1. Actual semantics require D1, D2, D3.
2. Candidate graph contains only D1 and D2.
3. Root commits to the incomplete graph.
4. Closure verifies perfectly against that root.
5. Result is marked CURRENT.

Conclusion: a valid root cannot detect a dependency omitted before root construction.

Therefore completeness has two separate properties:

A. INTEGRITY_OF_DECLARED_GRAPH
B. COMPLETENESS_OF_REQUIRED_DEPENDENCIES

A Merkle/root commitment can strongly support A. It cannot establish B without an independent rule that derives the required dependency set from authoritative semantics.

## 3. Candidate completeness authority

Required dependency set should be derived from a claim-specific dependency specification:
DEPENDENCY_SCHEMA / CLAIM_CONTRACT / EFFECT_CONTRACT / POLICY.

Candidate rule:

REQUIRED_SET = DeriveRequiredDependencies(
  claim,
  property,
  effect_class,
  resource_scope,
  policy_version,
  architecture_schema_version
)

Then:

DEPENDENCY_ROOT = Commit(Canonical(REQUIRED_SET + graph edges))

A result is not CURRENT merely because its root verifies. The derivation rule itself must be current, authenticated, version-bound, and included in the claim closure.

## 4. Attack — dependency added after evaluation starts

If D4 becomes required because policy/schema changes:
- old dependency_root remains historically valid for its original generation;
- it cannot satisfy the newer policy;
- current evaluation must derive the new REQUIRED_SET and produce a new root.

No silent expansion or retroactive rewriting.

## 5. Attack — graph root changes but dependency root does not

If graph generation G10 -> G11 changes relevant edges while dependency_root remains unchanged:
- either the root is incorrectly defined, or
- the binding between graph and root is missing.

Candidate invariant:
GRAPH_VERSION_AND_GRAPH_ROOT_AND_DEPENDENCY_ROOT_MUST_BE_BOUND_AS_ONE_EVALUATION_CONTEXT.

## 6. Attack — dependency root changes without graph version change

This can occur if dependency state is represented separately from graph topology.

That is legitimate only if the root explicitly commits to the dependency declarations and their state-generation bindings. Otherwise the system can validate topology while using stale dependency state.

Therefore:
GRAPH_TOPOLOGY_VERSION != DEPENDENCY_STATE_VERSION.

Both must be captured where currentness requires both.

## 7. Attack — mutable dependency aliases

A dependency name such as provider-A/current-key/current-adapter can resolve to a different object after evaluation.

Candidate protection:
- bind immutable identifiers;
- bind resource incarnation;
- bind adapter/provider generation;
- bind relevant configuration digest;
- reject alias-only identity for safety-critical closure.

NAME != IDENTITY.
IDENTITY != CURRENT_STATE.

## 8. Attack — migration and dual graph versions

During migration:
G_old and G_new coexist.

A root for G_old must not be interpreted as a root for G_new.

Candidate migration object:
MIGRATION_ID + FROM_GRAPH_VERSION + TO_GRAPH_VERSION + COMPATIBILITY_RULE_VERSION + MAPPING_DIGEST + AUTHORITY + STATUS.

A compatibility mapping may establish explicit equivalence only for properties it actually covers. It cannot manufacture omitted dependencies.

If G_old and G_new disagree on required dependencies, current status is UNKNOWN/QUARANTINED until the conflict is resolved.

## 9. Attack — malicious graph with internally consistent omission

This is the strongest omission attack.

A compromised producer can generate a perfectly signed, internally consistent graph that intentionally excludes a required dependency.

Therefore:
SIGNED_GRAPH != COMPLETE_GRAPH.

Protection must come from an independently controlled dependency derivation source, policy, schema, or verifier logic whose own dependency closure is included in the claim.

This follows the RATS separation of evidence production, verification/appraisal, and relying-party policy rather than allowing producer self-attestation to establish its own completeness. citeturn0search0

## 10. Attack — root collision or canonicalization ambiguity

If two semantically different dependency sets can serialize to the same canonical representation, the commitment is unsafe.

Candidate canonicalization requirements:
- deterministic ordering;
- explicit edge direction/type;
- explicit null/absence representation;
- domain-separated hashes;
- versioned canonicalization algorithm;
- exact encoding of scope/incarnation/generation;
- reject ambiguous encodings.

Formal cryptographic collision resistance is not proven here.

## 11. Attack — graph mutation after root creation

If G11 is created after root R10:
- R10 remains bound to G10;
- a G10 result cannot become G11 CURRENT merely because R10 still verifies;
- final validation must compare current graph generation/root.

Consistency proofs can establish relationships between append-only roots, but append-only consistency is not equivalent to semantic equivalence or current validity. citeturn0search1

## 12. Candidate two-level commitment

Potential minimal structure:

LEVEL 1 — SEMANTIC REQUIRED-SET ROOT
Commits to the claim-specific dependencies required by policy/schema.

LEVEL 2 — INSTANCE CLOSURE ROOT
Commits to the actual resolved dependency graph, identities, incarnations and relevant versions.

Current evaluation requires:
REQUIRED_SET_ROOT matches current claim contract/policy
AND
INSTANCE_CLOSURE_ROOT matches resolved graph
AND
all required dependency state versions match protected state.

This prevents a graph from proving its own completeness without an external semantic requirement.

## 13. Protected TCB boundary

Do not move the entire graph into Z1.

Candidate protected fields:
- claim/effect contract version;
- required-set root;
- graph root/version;
- closure root/version;
- dependency-state versions/epochs;
- policy version;
- resource incarnations;
- invalidation generation;
- evaluation record.

The graph contents and traversal can remain outside the authoritative core if their exact roots and semantic contracts are protected and independently validated.

## 14. Attack — stale dependency-set derivation

Policy P8 says D1,D2,D3 are required.
Cached derivation from P7 says only D1,D2.

If P8 is current, the P7-derived set cannot authorize P8.

Candidate invariant:
DEPENDENCY_DERIVATION_VERSION_MUST_MATCH_POLICY_AND_SCHEMA_VERSION.

## 15. Attack — dynamic dependency discovered during execution

A dependency D4 becomes relevant only after a runtime branch is selected.

This exposes a distinction:

STATIC_CLOSURE != DYNAMIC_RUNTIME_CLOSURE.

Candidate rule:
- if D4 was predictable from the claim/effect contract, it should already be in REQUIRED_SET;
- if D4 is genuinely runtime-discovered, entering its protected use requires a new closure/evaluation boundary;
- no protected effect may rely on an undeclared dependency silently.

This avoids pretending that a single upfront root can cover dynamically discovered dependencies it did not commit to.

## 16. Candidate invariants

- DEPENDENCY_ROOT_COMMITS_TO_DECLARED_SET_NOT_COMPLETENESS
- COMPLETENESS_REQUIRES_INDEPENDENT_REQUIRED_SET_DERIVATION
- SIGNED_GRAPH != COMPLETE_GRAPH
- GRAPH_VERSION_AND_ROOT_MUST_BE_BOUND
- REQUIRED_SET_ROOT_MUST_BE_POLICY_AND_SCHEMA_BOUND
- INSTANCE_CLOSURE_ROOT_MUST_BIND_TO_IDENTITIES_AND_INCARNATIONS
- DEPENDENCY_STATE_VERSION != GRAPH_VERSION
- ALIAS != IMMUTABLE_IDENTITY
- MIGRATION_MAPPING_CANNOT_MANUFACTURE_DEPENDENCIES
- OLD_GRAPH_ROOT != NEW_GRAPH_ROOT
- STATIC_CLOSURE != DYNAMIC_RUNTIME_CLOSURE
- UNDECLARED_PROTECTED_DEPENDENCY_CANNOT_BE_SILENTLY_ACCEPTED
- APPEND_ONLY_CONSISTENCY != SEMANTIC_COMPLETENESS
- ROOT_VALIDITY != CURRENT_USABILITY

## Status

AB104.396 closes an important conceptual ambiguity:

A root/digest can provide integrity and binding for a declared dependency graph, but **cannot prove that the declared dependency graph is complete**.

Nexo therefore needs two separate claims:
1. the declared dependency set is complete according to an independently governed semantic derivation rule;
2. the concrete closure matches that required set and current protected state.

Neither claim is formally proven yet.

## Exact next action

AB104.397 — attack the semantic required-set derivation itself: who/what is authoritative for completeness, how recursive/dynamic dependencies are represented, how policy/schema migration changes the set, and whether the derivation engine can become a hidden TCB expansion.
