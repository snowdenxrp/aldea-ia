# Nexo AB104.404 — EFFECT_CLASS / PROPERTY / REQUIRED_CONTEXT_SCHEMA Attack
Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Chain: AB104.403 -> AB104.404

## Question

Can a protected operation be incorrectly classified as a low-consequence effect, allowing a weaker REQUIRED_CONTEXT_SCHEMA and therefore a weaker Z1 admission gate?

## Evidence reviewed

NIST SP 800-162 defines ABAC authorization in terms of subject, object, requested operation and, where applicable, environment attributes evaluated against policy. NIST SP 800-205 emphasizes that an authoritative body must address the properties of attributes used in access-control systems. RFC 9334 separates appraisal from Relying Party authorization and warns that freshness does not eliminate state-change races. XACML specifies that missing required attributes can produce Indeterminate rather than a definitive authorization decision.

These sources support the need to bind authorization to the actual requested operation and authoritative attributes. They do not establish Nexo's effect-class taxonomy.

## Primary attack

Assume a dangerous external operation has actual semantics E4/E5 but is declared E1/E2.

If EFFECT_CLASS is trusted only from the request, the operation receives a weaker context and gate:

actual effect E4
-> declared E1
-> E1 context requirements
-> E1 admission
-> protected effect

This is a class-confusion attack.

## Core result

EFFECT_CLASS cannot be treated as an ordinary caller-provided attribute.

The effective class must be derived or independently constrained from the protected operation semantics and resource/provider path.

Candidate separation:

DECLARED_EFFECT_CLASS
!=
EFFECTIVE_EFFECT_CLASS

Z1 may accept the declaration only if it is consistent with independently protected semantic classification.

If the effective class cannot be established:
HOLD / REVALIDATE / UNKNOWN.

## Attack matrix

### 1. Irreversible operation disguised as reversible

Example: operation appears to have a compensation endpoint, but provider semantics do not guarantee that compensation reverses the original external effect.

Result: classify based on actual external semantics, not presence of a compensating API.

COMPENSATION_AVAILABLE != REVERSIBLE.

### 2. Idempotent API disguised as harmless

A provider may deduplicate repeated requests, but the operation may still be consequential or irreversible.

Result: idempotency affects retry semantics; it does not determine effect consequence.

IDEMPOTENT != LOW_CONSEQUENCE.

### 3. Provider-specific semantic downgrade

Adapter A treats an operation as conditional; provider B's equivalent endpoint has weaker guarantees.

Result: effective class and capability profile are path/resource/provider-specific where semantics differ.

### 4. Cross-resource hidden composition

An operation writes R1 and triggers a downstream effect on R2.

If classified from only the visible R1 operation, the actual footprint is understated.

Result: effective class must include discovered participant/effect footprint. Cross-resource behavior cannot be hidden behind a local operation label.

### 5. Asynchronous side effect

A request returns successfully while a provider queues the actual external effect.

Result: synchronous API response does not establish effect atomicity or reversibility. The effect class must consider queued/asynchronous execution semantics.

### 6. Trigger/webhook/cascade

A seemingly local mutation causes provider-side automation, webhook, event trigger, or downstream action.

Result: if that cascade is within the claimed protected property, it becomes part of the effect model. If it cannot be bounded, the property cannot be admitted as if it were local.

### 7. Capability-dependent class

The same logical operation may be E2 with one provider capability vector and E3/E4 with another.

Result: EFFECTIVE_CLASS may depend on validated provider capability profile. Capability profile changes invalidate the classification/admission.

### 8. Multi-provider operation

A composed operation has participant classes E1 + E4.

The composite cannot inherit the weakest participant.

Candidate rule:

EFFECTIVE_COMPOSITE_CLASS >= maximum required consequence class of all protected participants, plus coordination requirements.

This is a candidate safety rule, not a mathematical proof.

### 9. Runtime branch changes class

A planning/model branch selects a provider or operation whose semantics differ from the original classification.

Result: branch-dependent class change requires reclassification and new admission.

### 10. Class migration / rollback

A newer schema says E4; an older schema says E2.

Historical E2 authorization cannot be reused merely because its root is valid.

Current semantic rule version and effective class must bind the admission.

### 11. False reversibility through compensation

Compensation itself can fail, race, have different authorization requirements, or leave observable side effects.

Result: compensation is a separate effect and cannot erase the original event from history.

### 12. Hidden resource incarnation

Same resource identifier is recreated with different semantics.

Result: EFFECTIVE_CLASS and capability profile must bind to resource incarnation when semantics depend on it.

## Required context implications

The effective class determines minimum context requirements, but does not replace property-specific dependencies.

Candidate:

REQUIRED_CONTEXT =
  PropertyRequiredContext
  UNION
  EffectClassRequiredContext
  UNION
  PathCapabilityContext
  UNION
  ParticipantClosureContext

For E4/E5 candidates, context may additionally require:
- exact resource/incarnation;
- stronger authority/fence binding;
- stable EffectID;
- durable intent;
- provider capability validation;
- participant closure;
- reconciliation requirements;
- compensation contract where applicable;
- UNKNOWN handling;
- independent observation where the property requires confirmation.

The list remains candidate and claim-specific.

## Critical distinction

EFFECT_CLASS is not a risk score.

It is a semantic classification of the external effect and its recovery/atomicity properties.

Do not compress E0-E5 into a numerical "danger score"; doing so would obscure which guarantees are actually required.

## Static vs dynamic classification

Static classification is preferable only when the semantics are fully determined by protected immutable inputs.

Dynamic classification is required when class depends on:
- provider capability,
- resource incarnation,
- operation parameters,
- participant set,
- adapter path,
- asynchronous/cascade behavior,
- current policy.

Dynamic classification must complete before the final Z1 gate.

If classification remains UNKNOWN at the gate, it cannot silently fall back to a weaker class.

Candidate invariant:

UNKNOWN_EFFECT_CLASS_CANNOT_DEFAULT_TO_WEAKER_CLASS.

## Class monotonicity

A safe refinement may move an operation to a stricter class when new information reveals greater consequence.

A downgrade requires explicit semantic evidence that the weaker classification is valid under the current path and resource semantics.

Candidate:

CLASS_DOWNGRADE_REQUIRES_INDEPENDENT_SEMANTIC_JUSTIFICATION.

This is stronger than accepting a caller-supplied class version.

## Hidden footprint

A major residual risk is that EFFECTIVE_CLASS depends on complete effect-footprint discovery.

Therefore:

UNDISCOVERED_PROTECTED_PARTICIPANT => INCOMPLETE_CLASSIFICATION

and

INCOMPLETE_CLASSIFICATION => NO_HIGHER_AUTHORITY_GRANT

unless the property explicitly excludes that participant and the exclusion is itself authoritative.

## New invariants

- DECLARED_EFFECT_CLASS != EFFECTIVE_EFFECT_CLASS
- EFFECT_CLASS_CANNOT_BE_CALLER_AUTHORITY
- UNKNOWN_EFFECT_CLASS_CANNOT_DEFAULT_TO_WEAKER_CLASS
- COMPENSATION_AVAILABLE != REVERSIBLE
- IDEMPOTENT != LOW_CONSEQUENCE
- COMPOSITE_CLASS_CANNOT_IGNORE_STRONGER_PARTICIPANT
- HIDDEN_PROTECTED_PARTICIPANT_INVALIDATES_CLASSIFICATION
- CLASS_DOWNGRADE_REQUIRES_SEMANTIC_JUSTIFICATION
- CAPABILITY_CHANGE_CAN_INVALIDATE_EFFECT_CLASS
- RESOURCE_INCARCATION_CAN_INVALIDATE_EFFECT_CLASS
- CLASSIFICATION_INTEGRITY != CLASSIFICATION_CORRECTNESS

## Remaining UNKNOWN

- Exact mechanism to derive effective class without reproducing provider-specific semantics in Z1.
- How much provider behavior must be inside the semantic model versus attested as capability evidence.
- How to detect hidden cascades/triggers with sufficient assurance.
- Formal rule for composite-class aggregation across heterogeneous effects.
- Whether effect class can be safely monotonic across all operation refinements.
- No implementation or formal proof performed.
