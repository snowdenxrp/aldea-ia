# Nexo AB104.400 — Adversarial Attack on the Semantic Validation Stack

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective

Attack the complete AB104.399 validation stack for common-mode failures, specification defects, test blind spots, verifier compromise, stale appraisal, and evidence-chain TCB expansion.

Fresh evidence:
NIST defines IV&V as objective review, analysis and testing intended both to verify that requirements are correctly defined and to validate that the implementation satisfies them. NIST also emphasizes that assurance is claim-specific and evidence-based. citeturn0search1turn0search3
NIST IR 8397 recommends multiple verification techniques including threat modeling, automated testing, structural/black-box testing, historical tests and fuzzing rather than relying on one technique. citeturn0search2turn0search9
NASA describes technical independence as important because development-side testing can miss subtle requirements, design and coding errors; NASA also treats IV&V as a lifecycle risk-mitigation activity. citeturn0search24turn0search15

## 1. Stack under attack

Candidate chain:

SEMANTIC_SPECIFICATION
→ REFERENCE_MODEL
→ PROPERTY_SUITE
→ ADVERSARIAL/MUTATION_TESTS
→ PRODUCTION_DERIVATOR
→ DIFFERENTIAL_COMPARISON
→ VERIFIER/APPRAISER
→ PROTECTED_APPRAISAL_RESULT
→ Z1 AUTHORITY DECISION

The chain is only as strong as the claim-specific dependencies capable of falsifying the result.

## 2. Attack — specification bug

Suppose the semantic specification omits D7.

Reference model, production derivator and tests all agree on {D1..D6}.

Result:
AGREEMENT = TRUE
SPECIFICATION_CORRECTNESS = UNKNOWN

Therefore no amount of internal differential agreement alone establishes semantic truth.

Required countermeasure:
- independent requirements review;
- domain-level semantic invariants;
- negative requirements (“must-not-omit” conditions);
- adversarial specification review;
- traceability from operational property to semantic rule.

## 3. Attack — common parser/compiler

Reference and production implementations use the same parser or generated semantic library.

One parser defect removes D5 in both.

Differential test passes.

Countermeasure:
dependency-graph independence analysis; shared critical artifacts collapse the independence claim.

## 4. Attack — shared test corpus

Reference and production are tested against the same examples.

An omitted class never appears.

Passing tests provide little evidence for that class.

Countermeasure:
independently generated cases, mutation campaigns, fuzzing, historical failures, and requirement-derived tests.

NIST IR 8397 explicitly recommends combining multiple verification techniques rather than a single test mode. citeturn0search2

## 5. Attack — verifier compromise

Verifier V marks a disputed result VALIDATED_CURRENT.

Candidate response:
- verifier result becomes invalid if verifier integrity/trust state is compromised;
- dependent current claims become UNKNOWN/DEGRADED/QUARANTINED;
- historical appraisal remains retained;
- revalidation requires a valid verifier path.

VERIFIED_OUTPUT != AUTHORITY.

## 6. Attack — stale appraisal

At T0:
APPRAISAL_VALID.

At T1:
policy, dependency, adapter, resource incarnation or verifier state changes.

A cached appraisal is reused.

Rule:
CURRENT_USABLE requires current invalidation/freshness/dependency checks. A previously valid appraisal may remain historical without remaining operationally usable.

## 7. Attack — evidence replay

An old valid appraisal is replayed against:
- new resource incarnation;
- new adapter;
- new policy;
- new dependency root;
- new authority epoch.

Result must fail exact binding rather than merely pass signature verification.

SIGNATURE_VALID != CONTEXT_CURRENT.

## 8. Attack — test oracle compromise

The expected-result generator is compromised.

Tests now validate the implementation against malicious expected outputs.

Countermeasure:
expected-result generation must itself have independent trust/dependency closure, and critical properties should include implementation-independent assertions.

## 9. Attack — mutation campaign theater

Mutation testing reports 100% mutation kill rate because:
- mutation set excludes semantic mutations;
- generator and oracle share the same bug;
- equivalent mutants are misclassified;
- critical dependency classes are never mutated.

Therefore mutation coverage is evidence about the chosen mutation model, not proof of correctness.

Candidate mutation taxonomy:
M-SPEC, M-PRECEDENCE, M-DEPENDENCY-OMISSION, M-BRANCH, M-CYCLE, M-MIGRATION, M-INCARNATION, M-INVALIDATION, M-RESOURCE-LIMIT, M-VERIFIER-BYPASS.

## 10. Attack — independence collapse

Three “independent” validators share:
- same policy source;
- same deployment artifact;
- same cryptographic key;
- same time source;
- same provider;
- same graph store.

Counting them as 3-of-3 is invalid for the affected claim.

Independence must be derived from failure-domain closure, not validator count.

## 11. Attack — disagreement suppression

R != P.

A policy says “prefer production result.”

This converts disagreement into apparent certainty.

Candidate rule:
unresolved disagreement remains DISPUTED/UNKNOWN regardless of which result is operationally convenient.

Adjudication requires an explicit independent semantic resolution.

## 12. Attack — verifier unavailable

Verifier outage occurs while a high-consequence appraisal is required.

Unsafe:
provider self-attestation substitutes automatically.

Candidate:
- existing appraisal remains usable only within its declared validity and no invalidation;
- new promotion requiring unavailable verification becomes HOLD/UNKNOWN;
- no downgrade of evidence requirements merely for availability.

## 13. Attack — common-mode policy compromise

Policy source changes maliciously and simultaneously drives:
- reference model;
- production derivator;
- verifier;
- expected-result generator.

All agree under the compromised policy.

Therefore policy integrity is itself part of the claim closure.

## 14. Attack — deployment substitution

Validated derivator version D7 is approved.

Runtime actually executes D8 due to:
- fallback;
- stale container;
- adapter substitution;
- dynamic plugin;
- configuration override.

Candidate runtime binding:
IMPLEMENTATION_ID + VERSION + ARTIFACT_DIGEST + CONFIG_DIGEST + ADAPTER_PATH.

Declared capability/result cannot exceed the actually executed path.

## 15. Attack — rollback

Runtime returns from D8 to D7.

A previous D7 appraisal may be technically applicable only if:
- exact artifact/config/path match;
- policy and dependency state remain compatible;
- no revocation/invalidation;
- resource incarnation remains in scope.

Rollback is a new state transition, not automatic restoration of authorization.

## 16. Attack — evidence chain circularity

Reference model validates verifier.
Verifier validates reference model.
Both validate each other.

This creates no independent root of trust.

Candidate rule:
at least one trust anchor must terminate the evidence dependency graph in a separately governed source, specification, formal artifact, trusted measurement, or independent appraisal path appropriate to the claim.

## 17. Attack — TCB expansion by verification machinery

Naively placing:
- parser;
- reference model;
- fuzzing engine;
- test database;
- mutation engine;
- verifier;
- graph database;
- evidence store

inside Z1 creates a huge protected core.

That increases complexity and correlated failure surface.

Candidate minimal Z1 semantic frontier:
- approved semantic-specification identity/version/digest;
- approved verifier/appraisal policy/version;
- exact REQUIRED_SET_ROOT / closure root;
- validity/invalidation generation;
- claim scope;
- protected appraisal status;
- verifier trust identity/version;
- dependency closure root for the appraisal itself.

Heavy computation stays outside Z1 where possible.

## 18. Candidate evidence state machine

UNVALIDATED
→ TESTED
→ DIFFERENTIALLY_CONSISTENT
→ INDEPENDENTLY_APPRAISED
→ CURRENT_VALIDATED

Exceptions:
DISPUTED
UNKNOWN
DEGRADED
QUARANTINED
INVALIDATED
HISTORICAL_ONLY

No exception state may silently become CURRENT without satisfying the current promotion contract.

## 19. Candidate promotion predicate

CURRENT_VALIDATED iff:

semantic specification is approved/current
AND reference/derivation result is bound to exact inputs
AND required-set root verifies
AND independent validation requirements are satisfied
AND no unresolved disagreement exists
AND critical failure-domain dependencies are current
AND verifier/appraisal path is trusted/current
AND deployment artifact/path matches the validated implementation
AND no invalidation/revocation applies
AND scope/resource/incarnation match
AND freshness requirements hold.

This is a candidate policy predicate, not a proof.

## 20. Strong negative result

AB104.400 confirms that the validation stack cannot be reduced to “run more tests.”

There are at least four independent assurance questions:

A. Did we specify the right semantics?
B. Did the derivator implement them?
C. Did the deployed system execute the validated derivator/path?
D. Is the evidence still valid for this exact current claim/resource?

Each needs different evidence.

## 21. Candidate invariants

- AGREEMENT != SEMANTIC_CORRECTNESS
- TEST_COVERAGE != SEMANTIC_COMPLETENESS
- MUTATION_SCORE != PROOF
- SIGNATURE_VALID != CONTEXT_CURRENT
- VERIFIED_OUTPUT != AUTHORITY
- COMMON_MODE_DEPENDENCIES_COLLAPSE_INDEPENDENCE
- DISAGREEMENT_MUST_NOT_BE_SILENTLY_SUPPRESSED
- VERIFIER_UNAVAILABLE != SELF_ATTESTATION
- DEPLOYED_ARTIFACT_MUST_MATCH_VALIDATED_ARTIFACT
- ROLLBACK != AUTOMATIC_AUTHORIZATION
- CIRCULAR_VALIDATION != INDEPENDENT_ASSURANCE
- HISTORICAL_VALIDITY != CURRENT_USABILITY
- HIGH_CONSEQUENCE_VALIDATION_MUST_NOT_WEAKEN_FOR_LIVENESS
- TCB_MUST_REMAIN_CLAIM_SPECIFIC

## Status

AB104.400 substantially closes the conceptual attack on the validation stack itself.

It does NOT prove:
- semantic specification correctness;
- derivator correctness;
- verifier correctness;
- deployment correctness;
- evidence freshness correctness;
- independence completeness;
- formal correctness.

It establishes a candidate architecture where those claims are separated, traceable and independently invalidatable.
