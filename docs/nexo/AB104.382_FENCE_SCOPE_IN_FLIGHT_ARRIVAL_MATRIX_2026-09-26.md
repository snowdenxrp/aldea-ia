## Research question
What fence scope and resource-side ordering are minimally required to distinguish requests arriving before, concurrently with, and after a newer fence is established?

## Fresh research
Kleppmann's fencing model requires the protected resource to receive a monotonically increasing token and reject a request carrying a token lower than the resource's remembered high-water mark. This is specifically what prevents a delayed old client from acting after a newer owner has taken over. citeturn0search0

etcd provides a related concrete pattern inside its own key-value domain: revisions provide ordering, transactions atomically evaluate comparisons, and version/revision conditions can reject unintended concurrent updates. Its documentation also explicitly notes that protecting external resources requires those resources to provide version validation and consistent replica behavior; a lock in the coordinator alone does not protect an unrelated external resource. citeturn0search2turn0search5

ZooKeeper documents linearizable writes and version-checked updates, while also warning that client observations can lag because of network delay. Therefore the matrix below uses resource-side linearization, not client clocks or notification arrival, as the ordering authority. citeturn0search3turn0search12

## Fence scope matrix

| Scope candidate | What it protects | Main risk if too broad/narrow | Candidate status |
|---|---|---|---|
| Per global authority domain | All protected effects under one authority generation | Over-serialization; unrelated resources invalidate each other | Candidate, not selected |
| Per provider | All effects accepted by one provider | May be too coarse for independent resources; provider may host multiple authority domains | Candidate |
| Per resource | Exact protected resource incarnation | Strong locality; requires durable fence state per resource | Strong candidate |
| Per resource incarnation | Prevents reuse of a fence across replacement/recreated resource | Requires explicit incarnation identity and durable lifecycle | Strong candidate |
| Per operation | Isolates one logical operation | Too weak if multiple operations contend for the same resource | Usually insufficient alone |
| Per effect class | Groups semantics such as E1–E5 | Does not identify the concrete protected resource | Insufficient alone |
| Authority domain + resource | Binds authority to exact resource under the relevant authority scope | More metadata/coordination, but avoids unrelated cross-resource invalidation | Strong candidate |

### Preliminary result
A fence should not be treated as merely a global epoch attached to a request. The protected acceptance boundary needs a fence identity whose scope is explicit enough to identify the resource (and, where replacement matters, its resource incarnation) plus the authority domain that issued it.

This is a research conclusion, not a formal proof.

## In-flight arrival matrix

Define:
- F1 = older fence
- F2 = newer fence
- H = resource's durable accepted fence/high-water mark
- L = resource-side linearization point for the protected mutation
- "arrival" means reaching the resource's acceptance/validation boundary, not client send time.

| Case | Resource state at linearization | Request | Candidate result | Why |
|---|---|---|---|---|
| A | H=F1, before F2 established | F1 | ACCEPT, if all other guards pass | F1 is current at the resource; later F2 is not retroactive |
| B | H=F2, F2 established before F1 is evaluated | F1 | REJECT_STALE_FENCE | Resource sees F1 below high-water mark |
| C | H=F1, F2 request establishes newer fence first | F2 | ACCEPT and advance H→F2 | Newer fence becomes authoritative at resource |
| D | H=F2, delayed F1 arrives afterward | F1 | REJECT_STALE_FENCE | Network delay cannot revive older authority |
| E | F1 and F2 requests arrive concurrently | Depends on resource linearization order | First successfully linearized fence determines ordering; later stale fence rejects | Client clocks cannot decide concurrent ordering |
| F | F1 accepted before F2 establishment, then F2 established | F1 effect already accepted | NOT RETROACTIVELY REJECTED | Revocation/fence rollover does not erase an already accepted effect |
| G | F2 established but provider only stores volatile H; restart loses H | delayed F1 | UNKNOWN / safety claim unavailable | Resource can no longer prove F1 is stale after losing the high-water mark |
| H | F2 established; failover preserves H atomically | delayed F1 | REJECT_STALE_FENCE | Safety state survived failover |
| I | F2 established; failover resets H to F0 | delayed F1 | HOLD/UNKNOWN; strict stale exclusion unproven | Reset permits possible stale acceptance |
| J | F1 retry after F2 | F1 + same EffectID | REJECT_STALE_FENCE | Idempotency identity does not override current fence |
| K | F2 retry with same EffectID | F2 | Candidate retry, subject to provider idempotency/effect contract | Current fence and stable identity are both required |
| L | F1 request queued inside intermediary, F2 established before release | F1 | Reject at provider/intermediary if fence is checked at acceptance | Queue delay must not bypass fence validation |
| M | F1 request already accepted by provider, response delayed until after F2 | F1 | Preserve accepted outcome; do not reinterpret as stale | Confirmation timing is distinct from acceptance timing |
| N | Client receives timeout; provider may have accepted F1 | F1 | UNKNOWN until exact evidence/reconciliation | Missing response is not proof of rejection/non-execution |

## Critical ordering rule
"Before/during/after" must be defined at the protected resource's authoritative acceptance/linearization boundary. Client timestamps, packet-send time, local lease expiry, notification time, or when the client learns F2 are not sufficient ordering facts.

Therefore:

**F2 established before F1's resource-side linearization → F1 must reject.**

**F1 resource-side linearization before F2 establishment → F1 is not retroactively invalidated.**

**Concurrent arrival → resource-side linearization order decides; if that order cannot be reconstructed, the claimed property may be UNKNOWN.**

## Scope and resource-incarnation requirement
A resource replacement must not silently inherit an old resource's identity while resetting its fence state. Candidate protected identity:

RESOURCE_ID + RESOURCE_INCARNATION + AUTHORITY_DOMAIN + FENCE_GENERATION

A replacement that is semantically a new resource should receive a new incarnation and require fresh admission. Reusing an old incarnation while losing its fence high-water mark creates a stale-request acceptance hazard.

## Delayed, queued, and retried work
Every protected request that can remain in flight, queued, cached, or retried must carry the fence context required by its contract. A background worker cannot rely on having once passed a local FINAL_GATE. The acceptance boundary must revalidate the fence or use an equivalent provider-enforced conditional.

A new EffectID with an old fence is still stale. A fresh EffectID with a fresh fence is a new logical effect and requires its own admission.

## What the matrix does NOT prove
- Fencing does not provide external confirmation.
- Fencing does not cancel or reverse an already accepted effect.
- A provider that cannot persist/validate the high-water mark cannot support the strict stale-fence property after state loss.
- A trusted intermediary can enforce a fence at its own boundary, but downstream semantics remain separately unresolved.
- Per-resource fencing does not establish cross-resource atomicity.
- Formal proof and implementation verification remain unperformed.

## Candidate invariants
- FENCE_SCOPE_MUST_BIND_TO_PROTECTED_RESOURCE
- RESOURCE_INCARNATION_MUST_BE_EXPLICIT_WHEN_REPLACEMENT_CAN_OCCUR
- STALE_FENCE_REJECTED_AT_RESOURCE
- CONCURRENT_FENCE_ORDER_IS_RESOURCE_LINEARIZATION_ORDER
- REVOCATION_IS_NOT_RETROACTIVE
- FENCE_HIGH_WATER_MARK_MUST_SURVIVE_RESOURCE_RECOVERY
- QUEUED_OR_DELAYED_REQUESTS_MUST_NOT_BYPASS_FENCE_VALIDATION
- NEW_EFFECT_ID_DOES_NOT_REFRESH_STALE_AUTHORITY
- MISSING_RESPONSE_DOES_NOT_PROVE_NON_EXECUTION
- FENCE_REJECTION_OR_ACCEPTANCE != EXTERNAL_CONFIRMATION
