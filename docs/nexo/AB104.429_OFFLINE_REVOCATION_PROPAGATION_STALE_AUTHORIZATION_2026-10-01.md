# Nexo AB104.429 — Offline Revocation, Propagation Delay, and Stale Authorization

Date: 2026-10-01
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.428 → AB104.429
Implementation: NOT PERFORMED

## Research question

How can Nexo prevent stale authorization when a verifier or protected resource cannot synchronously observe current revocation/generation state?

## Evidence

RFC 7009 distinguishes immediate logical invalidation from distributed propagation delay: after revocation, some servers can temporarily remain unaware of the invalidation. This establishes that revocation currentness is a separate distributed-state problem. 

Recent IETF work on finality-bound revocation likewise distinguishes cached authorization state from authoritative current state and treats maximum accepted staleness as a security parameter for protected operations. It also identifies lost, duplicated, delayed, and reordered revocation events as conditions requiring explicit handling.

## Core finding

OFFLINE_VERIFICATION + IMMEDIATE_REVOCATION_REQUIREMENT cannot be satisfied merely by proving that a credential is authentic, unexpired, or recently checked.

The verifier must have a trustworthy way to establish the relevant current revocation/generation state, or the claim must be weakened to an explicitly bounded-staleness policy.

Therefore:

CREDENTIAL_VALIDITY != CURRENT_AUTHORIZATION

CACHE_FRESHNESS != CURRENT_AUTHORITY

REVOCATION_RECEIVED != REVOCATION_EFFECTIVE_FOR_THIS_RESOURCE

and:

NO_CURRENT_REVOCATION_STATE => UNKNOWN_FOR_PREVENTION_CLAIM

## Three authorization modes

### A — Synchronous current-state validation

At the protected admission/finality boundary, the verifier obtains current authoritative revocation/generation state.

Candidate:

ADMIT iff
AUTHENTIC
AND SCOPE_VALID
AND GENERATION_CURRENT
AND NOT_REVOKED
AND REQUIRED_DEPENDENCIES_CURRENT.

This provides the strongest currentness semantics, subject to the authority and protected-boundary assumptions.

### B — Bounded-staleness validation

The verifier may use cached state only if the protected claim explicitly permits a maximum staleness bound.

Candidate record:

CACHE_STATUS:
- SOURCE
- STATE_GENERATION
- OBSERVED_AT
- MAX_ACCEPTED_STALENESS
- POLICY_VERSION
- TRUST_GENERATION
- INVALIDATION_GENERATION
- LAST_GAP_DETECTED
- STATUS

The resulting claim is not equivalent to zero-staleness prevention.

BOUNDED_STALENESS_ALLOWED != IMMEDIATE_REVOCATION_PREVENTION.

### C — Offline artifact carrying sufficient current-state evidence

An offline verifier may evaluate an artifact that contains a generation/checkpoint/freshness mechanism capable of establishing currentness without contacting the authority.

This is only safe if the artifact's currentness anchor itself has a protected trust/continuity model and cannot silently roll back.

SIGNED_REVOCATION_STATE != CURRENT_REVOCATION_STATE

unless the artifact is bound to an authoritative freshness/currentness mechanism.

## Propagation state machine

A revocation should not collapse into one boolean.

Candidate:

REVOCATION_REQUESTED
→ REVOCATION_AUTHORIZED
→ REVOCATION_COMMITTED
→ REVOCATION_PROPAGATING
→ REVOCATION_OBSERVED_AT_RESOURCE
→ REVOCATION_EFFECTIVE_FOR_ADMISSION

Possible uncertainty states:

REVOCATION_UNKNOWN
REVOCATION_CONFLICT
REVOCATION_GAP_DETECTED
REVOCATION_SOURCE_STALE.

The exact transition required for a protected consequence is claim/effect-class specific.

## Generation and gap detection

For push or replicated revocation, a monotonic generation/sequence can expose missing events.

Example:

resource has generation 41
received update says generation 43

Generation 42 is missing.

The verifier must not silently infer that generation 43 is complete if the protocol requires contiguous protected state.

Candidate:

GENERATION_GAP => UNKNOWN / REVALIDATE / HOLD

unless the protocol has an independently verified checkpoint proving that the gap is safe to skip.

Likewise:

GENERATION_ROLLBACK => INVALID / QUARANTINE / REVALIDATE.

## Cache semantics

A cache entry can be:

- CURRENT
- BOUNDED_STALE
- STALE
- UNKNOWN
- INVALIDATED
- CONFLICTING.

A cache hit must not itself establish authority.

AUTH_CACHE_HIT != CURRENT_AUTHORITY.

A cache invalidation signal is also not equivalent to resource-side enforcement unless the protected resource has actually incorporated the new state.

## Lost and reordered revocation events

Push systems must tolerate:

- lost revocation event;
- duplicated event;
- delayed event;
- reordered event;
- replayed old event;
- conflicting event;
- source rollback;
- subscription gap;
- observer restart from stale checkpoint.

Candidate controls:

- monotonic generation;
- authenticated checkpoint;
- gap detection;
- replay-safe subscription;
- protected durable cursor;
- re-synchronization from an authoritative source;
- final-gate generation check.

A missing event must not make older state appear current.

MISSED_REVOCATION_EVENT != NO_REVOCATION.

## Partition behavior

During a partition, a resource may know only an older authority generation.

If the protected consequence requires immediate revocation prevention, accepting that stale state is not equivalent to current authorization.

Candidate:

CURRENT_STATE_UNAVAILABLE
→ HOLD / FAIL_CLOSED / REVALIDATE

unless the policy explicitly permits bounded stale operation.

Availability fallback must not silently change the security property.

## Finality boundary

The strongest boundary is not merely:

CHECK_REVOCATION
→ SEND_EFFECT

because state may change between those steps.

For a high-consequence operation, candidate semantics require the revocation/generation condition to be bound to the protected commit/effect boundary or an equivalent resource-side fencing mechanism.

Candidate:

FINAL_GATE:
1. establish current authority/revocation generation;
2. bind decision to operation/effect/resource scope;
3. verify no protected generation changed before commit;
4. perform effect under the same protected generation/fence semantics;
5. record the committed generation.

If the resource cannot enforce this relation, the model must not claim consequence-wide revocation prevention.

## Alternate paths

A primary path can be revocation-safe while another path bypasses it.

Candidate alternate paths requiring equivalent protection:

- direct API;
- queue worker;
- retry worker;
- recovery;
- admin override;
- cached execution;
- background scheduler;
- provider callback;
- device-side action;
- failover region;
- offline replay.

Therefore:

PRIMARY_PATH_SAFE != CONSEQUENCE_WIDE_SAFE.

Every path capable of producing the protected effect must satisfy the relevant currentness contract or be excluded explicitly from the claim boundary.

## Recovery

Crash recovery must not resurrect a pre-revocation authorization state.

Candidate:

RESTORED_SNAPSHOT_GENERATION < CURRENT_REVOCATION_GENERATION
=> RESTORED_AUTHORIZATION_NOT_CURRENT.

A crash after authorization but before effect must revalidate before retry.

A crash after external effect commit must not blindly replay the effect merely because the old authorization was once valid.

This preserves the existing Nexo distinction:

CRASH != EXECUTION_RESULT.

## Offline impossibility boundary

If the verifier has:

- no current revocation state;
- no trusted generation/checkpoint;
- no bounded-staleness policy;
- no resource-side fence;
- and the claim requires immediate revocation prevention,

then the strongest honest result is:

CURRENT_AUTHORIZATION = UNKNOWN

not VALID.

This is a semantic limit, not an implementation defect.

## Claim-specific consequence classes

Not every Nexo operation requires zero-staleness.

Candidate classes:

C0 informational/non-consequential
C1 reversible low-consequence
C2 bounded external effect
C3 consequential external effect
C4 irreversible/high-impact effect.

The acceptable revocation-staleness bound should be defined by claim/effect class, not globally assumed.

No universal threshold is frozen here.

## Candidate invariants

- CREDENTIAL_VALIDITY != CURRENT_AUTHORIZATION
- CACHE_FRESHNESS != CURRENT_AUTHORITY
- REVOCATION_RECEIVED != REVOCATION_EFFECTIVE_FOR_RESOURCE
- NO_CURRENT_REVOCATION_STATE => UNKNOWN_FOR_IMMEDIATE_REVOCATION_PREVENTION
- BOUNDED_STALENESS_ALLOWED != IMMEDIATE_REVOCATION_PREVENTION
- SIGNED_REVOCATION_STATE != CURRENT_REVOCATION_STATE without a protected freshness/currentness anchor
- GENERATION_GAP => UNKNOWN / REVALIDATE / HOLD unless an authoritative checkpoint closes the gap
- GENERATION_ROLLBACK => INVALID / QUARANTINE / REVALIDATE
- AUTH_CACHE_HIT != CURRENT_AUTHORITY
- MISSED_REVOCATION_EVENT != NO_REVOCATION
- PARTITIONED_STALE_STATE != CURRENT_AUTHORITY
- PRIMARY_PATH_SAFE != CONSEQUENCE_WIDE_SAFE
- RESTORED_OLD_REVOCATION_STATE != CURRENT_AUTHORIZATION
- REVOCATION_CURRENTNESS != SIGNATURE_VALIDITY
- FINAL_GATE_CURRENTNESS must bind to the relevant protected effect boundary when prevention is claimed

## Residuals

- Exact zero-staleness versus bounded-staleness policy by Nexo effect class remains open.
- Exact generation/checkpoint protocol remains open.
- Resource-side fencing semantics remain resource-specific.
- Offline trust-anchor and checkpoint rotation remain open.
- Revocation conflict/equivocation resolution remains open.
- Alternate-path closure needs explicit system-boundary mapping.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
