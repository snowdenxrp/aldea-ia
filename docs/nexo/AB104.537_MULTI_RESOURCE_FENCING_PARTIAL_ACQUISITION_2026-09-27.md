# Nexo AB104.537 — Multi-resource fencing and partial acquisition

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
When one logical effect touches multiple resources, a single global-looking fence is unsafe unless every affected resource is covered by the same authoritative transition or every resource independently enforces a compatible fence. Partial fence acquisition must never be presented as full authorization.

## Evidence
etcd transactions can atomically compare multiple keys and apply multiple modifications under one revision, providing a concrete local primitive for coherent multi-key admission. ZooKeeper's lock recipes provide ordered distributed locks, and Apache Curator's Multi Shared Lock explicitly acquires multiple locks as one recipe and releases already-acquired locks when acquisition fails. These mechanisms demonstrate that multi-resource coordination needs an explicit acquisition protocol and failure handling rather than independent lock calls. citeturn0search2turn0search0turn0search1

## Candidate models

### M1 — Single common fence scope
All affected resources are covered by one authoritative scope and one activation transition.
Strength: simplest semantic model when all resources share one authority domain.
Requirement: every protected resource must enforce the resulting fence or participate in the authoritative transaction.

### M2 — Per-resource fences + aggregate admission
Each resource gets its own fence (scope_i, epoch_i, revision_i, incarnation_i).
The operation also records an aggregate FenceSetDigest.
Admission succeeds only when the complete required set is acquired and validated.

### M3 — Hierarchical fence
Parent fence covers a known closed resource hierarchy; child resources inherit protection only if the hierarchy contract explicitly binds them.
Dynamic child discovery after activation cannot silently expand the protected set.

## Partial acquisition
If resources A and B are required and only A is fenced:
FENCE(A) + NO_FENCE(B) != AUTHORIZED(A+B)

On partial failure:
- do not release A and continue as if B were protected;
- either atomically abort before any external effect, or enter a defined compensation/reconciliation path;
- preserve which fences were actually activated;
- recovery must not assume missing fences were active.

## Scope closure
The protected footprint must be determined before admission:
RequiredResourceSet -> Closed -> BoundToDecisionDigest
If execution discovers a new required resource, this is footprint expansion and requires re-admission/re-fencing rather than silently borrowing the old authorization.

## Release semantics
Release is itself a protected state transition:
- old fence remains recognized as historical;
- new acquisitions receive a strictly later valid fence/epoch;
- delayed operations carrying the released fence must be rejected by participating resources;
- release acknowledgment is not proof that an already-dispatched effect did not occur.

## Cross-domain limitation
If A is governed by Nexo and B by an unrelated provider with no shared fence/transaction primitive, Nexo cannot claim a single atomic fence across A+B. The aggregate operation must retain a two-domain UNKNOWN boundary or use an explicit coordinator/protocol with defined compensation semantics.

## Critical distinctions
- SINGLE_FENCE_SCOPE != AUTOMATIC_GLOBAL_FENCE
- FENCE_SET_COMPLETE != EFFECT_APPLIED
- PARTIAL_FENCE != FULL_AUTHORITY
- LOCK_ACQUIRED != PROVIDER_FENCE_ENFORCED
- RESOURCE_SET_DISCOVERED_LATE != AUTHORIZED_FOOTPRINT
- RELEASE_ACK != NON_EFFECT_PROOF
- PER_RESOURCE_ORDER != GLOBAL_ORDER
- COORDINATION != ATOMICITY
- MULTI_LOCK_ACQUISITION != EXTERNAL_EFFECT_ATOMICITY

## Nexo implication
The protected transition contract should carry a closed AffectedResourceSet and either one common fence scope or a complete FenceSet bound to the decision. Partial acquisition is an explicit failure state, not a degraded success. This directly connects footprint closure, fencing, and cross-resource effect semantics.
