## Research question

When several witnesses appear independent, how can Nexo determine whether their trust dependencies actually collapse into one effective failure domain?

## Evidence

RFC 9334 separates Evidence, Verifier appraisal, Attestation Results, and Relying Party authorization. It also treats trustworthiness as a decision-relevant quality and freshness as an explicit architectural concern. This supports modeling witness assurance as dependency-bound rather than as a permanent identity property. citeturn0search0

RFC 9162 provides a concrete example where multiple observers can compare signed tree views to detect inconsistent behavior, while also warning that a misbehaving log can present different views. The example supports treating observer multiplicity and observer independence as separate properties. citeturn0search1turn0search25

## Core finding

A quorum is not fundamentally a count of witnesses.

It is a composition of witnesses plus their relevant shared dependencies.

Therefore:

WITNESS_COUNT != INDEPENDENT_FAILURE_DOMAINS

and:

QUORUM_STRENGTH = f(CLAIM, WITNESS_SET, DEPENDENCY_CLOSURE, FAILURE_MODEL)

No universal numeric quorum threshold is selected here.

## Dependency graph

Candidate graph:

WITNESS
→ identity/key
→ trust root
→ verifier
→ verifier software
→ policy
→ reference values
→ adapter/path
→ provider
→ storage
→ network/control plane
→ deployment
→ operator/governance
→ recovery/backup
→ time source

Each edge represents a dependency that may matter for a particular claim.

A witness can be operationally separate while remaining security-dependent on another witness's infrastructure.

## Failure-domain algebra

Represent each protected dependency as a domain label:

D = {d1, d2, ... dn}

Each witness has a claim-specific dependency closure:

C(W, claim) = {failure domains required to support the witness's claim}

For a witness set Q:

C(Q, claim) = union C(W_i, claim)

But safety cannot be inferred from union size alone.

The important question is how many independent failure domains can produce the required evidence.

Candidate:

EFFECTIVE_FAILURE_DOMAINS(Q, claim)

= maximal set of domains whose compromise/failure does not simultaneously invalidate all required quorum contributions.

This is intentionally a semantic definition, not a numeric score.

## Collapse examples

### Shared trust root

W1 → Root A
W2 → Root A
W3 → Root B

Three witnesses do not imply three trust domains.

For a claim depending on trust-root integrity:

W1 + W2 may form one failure domain.

### Shared verifier

W1 and W2 run different witness processes but both rely on the same verifier implementation/configuration.

A verifier compromise may corrupt both appraisals.

Therefore:

DIFFERENT_ATTESTERS + SAME_VERIFIER = POSSIBLE_COMMON_MODE

### Shared policy

W1 and W2 use different infrastructure but identical mutable policy source P.

If P is compromised:

both can honestly produce the same wrong result.

Therefore:

DIFFERENT_EXECUTION_PATH + SAME_POLICY_ROOT = COMMON_MODE

### Shared deployment

W1 and W2 run independently but are released by one deployment pipeline.

A malicious image or compromised release process can affect both.

### Shared recovery

Two witnesses use separate live systems but restore from the same compromised backup.

Their apparent independence can disappear during recovery.

### Shared operator

Different technical systems may share the same privileged operator/governance domain.

For some claims, operator compromise is a common failure domain.

### Shared time

Two witnesses may have separate infrastructure but depend on one compromised time source for freshness.

For freshness-sensitive claims, that can become a common dependency.

## Domain projection is claim-specific

The same witness set can have different effective independence for different claims.

Example:

Claim A: storage state integrity.
Claim B: policy integrity.
Claim C: freshness.
Claim D: deployment provenance.

A dependency common to B may be irrelevant to A, while a shared time source may be critical to C.

Therefore:

INDEPENDENCE_CLAIM_A != INDEPENDENCE_CLAIM_B

## No scalar independence score

A single “independence = 0.8” number would hide which dependency causes correlation.

Candidate representation should preserve:

- dependency IDs;
- domain IDs;
- dependency type;
- version/generation;
- claim relevance;
- compromise impact;
- observer evidence;
- common-mode relationships;
- confidence/status.

This preserves the evidence graph instead of compressing it into an opaque score.

## Quorum composition matrix

| Composition | Nominal count | Effective interpretation |
|---|---:|---|
| 3 witnesses, 1 trust root | 3 | one trust-root failure domain for affected claims |
| 3 witnesses, 1 verifier | 3 | common verifier dependency |
| 3 witnesses, 3 verifiers, 1 policy | 3 | common policy dependency |
| 3 witnesses, independent roots/verifiers/policies | 3 | potentially independent, subject to closure |
| 5 witnesses, 2 providers | 5 | at most provider diversity relevant to claim |
| 5 witnesses, one recovery backend | 5 | recovery common-mode |
| 5 witnesses, unknown dependencies | 5 | independence UNKNOWN |

The table is descriptive, not a ranking.

## Byzantine threshold implication

Classical Byzantine thresholds depend on assumptions about independent faulty participants.

If multiple logical witnesses collapse into one failure domain, treating them as separate Byzantine participants can invalidate the assumed fault bound.

Therefore:

LOGICAL_PARTICIPANTS != EFFECTIVE_FAILURE_PARTICIPANTS

The architecture must not import a Byzantine threshold without explicitly validating its failure-model assumptions.

## Common-mode compromise

If one dependency can cause k witnesses to produce the same malicious result:

COMMON_MODE_DOMAIN d
→ affects {W1...Wk}

Then those k contributions cannot be treated as independent evidence for claims dependent on d.

Candidate rule:

COMMON_MODE_COMPROMISE_CAPABILITY
=> collapse affected contributions for independence analysis.

This does not mean all evidence is automatically false; it means the affected evidence loses the independence property attributed to it.

## Unknown dependency

If the dependency graph is incomplete:

DEPENDENCY_CLOSURE = UNKNOWN

then independence cannot be safely claimed.

Candidate:

UNKNOWN_REQUIRED_DEPENDENCY
=> NO_HIGHER_INDEPENDENCE_CLAIM

For high-consequence quorum decisions:

UNKNOWN_INDEPENDENCE => HOLD / REVALIDATE / QUARANTINE

depending on the property.

## Failure-domain overlap graph

Candidate representation:

Node = failure domain.
Witness = set of domain nodes.
Edge = shared dependency/correlation.

A quorum analysis can then ask:

1. Which witnesses share each domain?
2. Which domains are critical to the claim?
3. Which combinations can simultaneously invalidate enough witnesses?
4. Which domains are independently observed?
5. Which domain generations are current?

This is more precise than simply counting witnesses.

## Domain generation

Failure-domain membership itself can change.

Example:

W1 previously used Provider A.
W1 migrates to Provider B.

Or:

W1's verifier changes implementation.

Therefore:

FAILURE_DOMAIN_SET_VERSION

should be protected state.

Candidate:

DOMAIN_SET_CHANGE => REVALIDATION

## Correlation discovery after admission

A witness can be admitted with incomplete knowledge.

Later evidence may reveal a shared dependency.

Candidate:

CURRENT
→ CORRELATION_SUSPECTED
→ DEPENDENCY_ANALYSIS
→ INDEPENDENCE_RECALCULATED
→ CURRENT / DEGRADED / SUSPENDED / QUARANTINED

Historical decisions are not silently rewritten.

## Failure-domain policy cannot be self-defined

Witnesses may report their own dependencies, but their declaration is evidence, not authority.

Candidate flow:

WITNESS_DECLARATION
→ EXTERNAL/INDEPENDENT APPRAISAL
→ DEPENDENCY CLOSURE
→ CLAIM-SPECIFIC FAILURE-DOMAIN PROJECTION
→ Z1 POLICY
→ QUORUM ELIGIBILITY

This carries forward AB104.396–AB104.403.

## Recovery-domain collapse

A particularly dangerous case:

Live systems are independent,
but recovery systems share one backup/control plane.

During normal operation, quorum appears independent.

During recovery, all witnesses may become correlated.

Therefore:

NORMAL_FAILURE_DOMAIN_SET != RECOVERY_FAILURE_DOMAIN_SET

Recovery must have its own dependency closure.

## Candidate composition rule

ALLOW only if:

1. witness identities/incarnations are current;
2. claim-specific dependency closures are complete;
3. relevant failure-domain generations are current;
4. required independence constraints are satisfied;
5. no critical common-mode domain exceeds policy;
6. no unresolved Byzantine/equivocation evidence invalidates the required composition;
7. quorum policy is current;
8. final protected generations remain unchanged.

Otherwise:

REVALIDATE / HOLD / QUARANTINE / RECONCILIATION_REQUIRED.

## Residuals

- Formal algebra for correlated failure combinations remains open.
- Exact Byzantine threshold selection remains policy/model dependent.
- Dependency graph completeness remains an open assurance problem.
- Dynamic correlation detection remains incomplete.
- Common-mode compromise can be difficult to observe.
- Formal proof, implementation, fault injection, and deployment verification remain unperformed.
