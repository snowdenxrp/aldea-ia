# NEXO AB104.756R — SocketServer completed-receive exception/cleanup re-audit

Date: 2026-09-28
Source baseline: Apache Kafka abf522e1ca5d7f4375baddc4da004da9fcb6e9ca

## Direct source findings

`Processor.run()` calls `processCompletedReceives()` after selector poll. The method iterates `selector.completedReceives` and wraps each receive's processing in a per-receive `try/catch`.

On a processing exception, `processChannelException()` closes the affected channel (when still open/closing) and logs/processes the exception without rethrowing ordinary throwables. After the receive iteration finishes, `selector.clearCompletedReceives()` is called unconditionally in normal method flow. Therefore the SocketServer path is intentionally different from the client-side NetworkClient mismatch path: request-processing failures are isolated to the affected channel and completed receives are explicitly cleared after iteration.

If request construction has not completed (`header == null || req == null`), `receive.close()` returns the receive buffer to the memory pool before the channel exception path. Once a `Request` has been constructed, that early buffer-close condition is not taken here; the Request owns/handles the payload lifecycle through the subsequent request path.

`Processor.run()` also has an outer Throwable catch so a ControlThrowable is rethrown while ordinary unexpected throwables are processed without killing the processor thread. `processCompletedReceives()` itself handles ordinary per-receive exceptions, so one bad receive is not intended to abort the entire receive loop.

## Evidence boundary

Direct source evidence establishes cleanup and channel-isolation semantics. Repository search did not find a dedicated test named around `processCompletedReceives` + `clearCompletedReceives` + exception. No Kafka tests were executed by this audit.

This SocketServer evidence must NOT be conflated with NetworkClient's client-side correlation mismatch path: NetworkClient removes an in-flight request before parsing and lets the mismatch escape `poll()`, while SocketServer catches request-processing exceptions per receive and closes the affected channel.
