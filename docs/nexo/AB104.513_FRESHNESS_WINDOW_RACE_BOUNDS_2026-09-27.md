# AB104.513 — freshness-window sizing and race bounds

## Evidence
RFC 9334 states that epoch freshness necessarily has a race at epoch transitions. It recommends an epoch window whose depth is proportional to maximum network propagation delay and inversely proportional to epoch duration. It also notes that epoch identifiers can be delayed, dropped, reordered, or replayed, so the epoch-distribution mechanism becomes security-relevant. citehttps://www.rfc-editor.org/rfc/rfc9334.html

NIST's digital-signature timeliness guidance shows that nonce-based freshness establishes when the signature was generated, but not automatically when the signed message's underlying content was created; trusted timestamps add a separate time-assurance mechanism. citehttps://www.nist.gov/publications/recommendation-digital-signature-timeliness

## Nexo bound model
A freshness window must be an explicit security parameter, not an arbitrary "recent enough" value.

Candidate parameters:
- `D_net_max`: maximum accepted propagation delay for the relevant trust domain;
- `D_proc_max`: maximum accepted processing/queueing delay;
- `S_clock_max`: maximum trusted clock skew, if timestamps are used;
- `D_revocation_max`: maximum delay for relevant revocation/generation information;
- `E_duration`: epoch duration;
- `W_epoch`: accepted previous-epoch depth.

For an epoch-based mechanism, a conservative candidate condition is:
`W_epoch * E_duration >= D_net_max + D_proc_max + safety_margin`.

This is a design bound, not a proven universal formula: the actual bound must cover every path by which freshness state and evidence can be delayed, including verifier/RP processing and trust-domain propagation.

## Security versus availability
A larger freshness window reduces false rejection during propagation races but increases the maximum interval during which stale evidence may remain admissible. Therefore:
`L_stale_max ≈ W_epoch * E_duration + D_delivery_bound`.

The window must be chosen against the protected property's maximum tolerable stale-authority interval. If the property cannot tolerate the resulting bound, the system must use a stronger freshness mechanism rather than enlarging the window.

## Authority transitions
Epoch freshness is not sufficient during a security-critical authority transition. A revocation, trust-root compromise, target replacement, or fence change can require immediate invalidation independent of the ordinary epoch window.

Candidate final gate:
`FreshnessWindowAcceptable`
AND `AuthorityEpochCurrent`
AND `RevocationGenerationCurrent`
AND `TargetIncarnationCurrent`
AND `FenceCurrent`
AND `CapabilityScopeMatch`.

A previous epoch may be acceptable for freshness only when no newer revocation/fence/identity transition invalidates it.

## Race classes
1. **Epoch propagation race:** sender has new epoch; receiver still has old epoch.
2. **Evidence delivery race:** evidence was fresh when generated but arrives after a transition.
3. **Revocation race:** capability is revoked after evidence generation but before protected effect.
4. **Target replacement race:** capability evidence is fresh but target incarnation changed.
5. **Clock race:** timestamp appears valid under skew/rollback while authority generation has advanced.
6. **Policy race:** appraisal policy changes while cached evidence remains within its old validity interval.

These races require separate predicates; one freshness window must not mask them.

## Canary/probe implication
Runtime probes should record their own evidence epoch and propagation bounds. A successful probe at epoch `E` cannot establish capability for an effect admitted under epoch `E+1` unless the capability contract explicitly permits that carry-forward.

`PROBE_SUCCESS(E) != CURRENT_CAPABILITY(E+1)`

## Unknown bounds
If `D_net_max`, `D_proc_max`, or equivalent propagation bounds cannot be justified, the freshness window cannot be claimed safe merely because it is finite. Nexo should treat the relevant freshness property as `UNKNOWN` and require stronger evidence or quarantine the protected effect.

## Invariants
- `ARBITRARY_WINDOW != SECURITY_BOUND`
- `LARGER_WINDOW != STRONGER_FRESHNESS`
- `FRESHNESS_WINDOW != REVOCATION_FINALITY`
- `CURRENT_EPOCH != CURRENT_AUTHORITY` unless authority binding is explicit
- `FRESH_EVIDENCE != CURRENT_TARGET`
- `FRESH_EVIDENCE != NONREVOKED_CAPABILITY`
- `CLOCK_VALIDITY != EPOCH_VALIDITY`
- `UNKNOWN_PROPAGATION_BOUND => UNKNOWN_FRESHNESS_ASSURANCE`
- `SECURITY_TRANSITION_CAN_OVERRIDE_ORDINARY_FRESHNESS_WINDOW`
- `PROBE_SUCCESS(E) != AUTOMATIC_AUTHORITY(E+1)`

## Status
Research complete. Freshness windows are bounded race-management mechanisms, not proofs of current authority. Their safety requires explicit propagation assumptions and separate checks for revocation, target incarnation, fence, policy, and authority epoch. No implementation or formal verification performed.

Next exact step: AB104.514 — research revocation/freshness race closure: ordering capability issuance, revocation, evidence generation, admission, and external effect so that no stale capability can cross the final protected-effect gate during an in-flight transition.
