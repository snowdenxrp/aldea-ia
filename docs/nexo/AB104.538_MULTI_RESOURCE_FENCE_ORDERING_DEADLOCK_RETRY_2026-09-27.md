# Nexo AB104.538 — Multi-resource fence ordering, deadlock, retry, and dynamic-footprint hazards

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
Canonical resource ordering can prevent circular acquisition deadlocks only when the protected resource set is known and stable for the acquisition attempt. It does not by itself solve crashes, ambiguous ownership, stale observations, or resources discovered after acquisition.

## Evidence
ZooKeeper's lock recipe establishes an explicit total order among contenders using sequence numbers and has recovery handling for a successful create whose response is lost. etcd supports atomic multi-key conditional transactions, so a common authoritative domain can avoid independent lock acquisition altogether. ## Candidate protocol
1. Compute the closed RequiredResourceSet.
2. Canonicalize each resource identity and sort deterministically.
3. Bind the ordered set to a ResourceSetDigest.
4. Acquire/fence in that order, or use one atomic authoritative transaction when all resources share the same authority store.
5. On any failure, stop acquisition and record the exact acquired subset.
6. Revalidate the complete set before external admission.
7. If a new resource is discovered, invalidate the admission and restart with a new closed set.

## Why ordering is not enough
Ordering prevents A->B and B->A circular waits, but:
- a crash after acquiring A leaves an uncertain partial state;
- a lost response can make acquisition outcome UNKNOWN;
- a resource can change incarnation while later resources are acquired;
- a retry can use a stale prepared fence;
- a dynamically discovered dependency can expand the footprint;
- cross-domain resources may not share the same ordering authority.

Therefore canonical ordering is a deadlock-control mechanism, not a global atomicity mechanism.

## Retry semantics
A retry must reuse the same OperationID when it is the same logical attempt. It must not silently create a second effect or treat a newly acquired fence as proof that an earlier attempt never reached a provider.

If acquisition result is UNKNOWN, reconciliation is required before declaring the old attempt absent.

## Crash states
Candidate:
PREPARE_SET
-> ACQUIRE_i
-> PARTIAL_SET
-> COMPLETE_SET
-> FINAL_REVALIDATION
-> EXTERNAL_ADMISSION

Crash after PARTIAL_SET => recover exact subset, not an assumed all-or-none state.
Crash after COMPLETE_SET but before final admission => fences may be active, but effect is not admitted.
Crash after external admission => effect outcome follows the independent external-effect state machine.

## Dynamic footprint
DISCOVERED_AFTER_FENCING is a safety boundary.
The newly discovered resource is not implicitly covered by the old FenceSet. The operation must either:
- prove it was already included in the closed set, or
- invalidate/re-admit with the expanded set.

## Release
Release in reverse canonical order can reduce contention and simplify cleanup, but release is not proof that an already-dispatched external effect was cancelled or not applied.

## Critical distinctions
- CANONICAL_ORDER != GLOBAL_ATOMICITY
- ORDERED_ACQUISITION != DEADLOCK_FREE_UNDER_ALL_FAILURES
- PARTIAL_SET != COMPLETE_SET
- ACQUISITION_ACK != EFFECT_NONOCCURRENCE
- RETRY != NEW_LOGICAL_OPERATION
- NEW_FENCE != PROOF_OLD_ATTEMPT_DID_NOT_EXECUTE
- DYNAMIC_DISCOVERY != AUTHORIZED_EXPANSION
- LOCAL_LOCK_ORDER != CROSS_DOMAIN_ORDER
- RELEASE != REVERSAL

## Nexo implication
The protected transition contract should include a canonical ResourceOrder, AffectedResourceSet, ResourceSetDigest, acquired-subset state, and crash/recovery semantics. Where one authoritative store can atomically validate and update all resources, that is preferable to distributed lock choreography; otherwise the system needs explicit partial-acquisition and reconciliation states.
