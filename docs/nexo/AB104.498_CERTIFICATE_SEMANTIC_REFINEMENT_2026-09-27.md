# AB104.498 — semantic equivalence/refinement between certificate profiles

## Evidence
TLS 1.3 separates version negotiation from the legacy field and includes explicit downgrade protection; a selected version must be one actually supported/advertised, and unacceptable versions abort the handshake. citeturn0search1 COSE requires critical protected parameters to be understood, with an unknown critical parameter being a processing failure. citeturn0search0 Kubernetes explicitly documents that API versions can have incompatible semantics and therefore migration instructions may be required; its conversion layer distinguishes representation conversion from the stored version. citeturn0search8turn0search9 Kubernetes storage migration also requires actively rewriting objects before an old storage version can safely be removed. citeturn0search2turn0search4 etcd's mixed-version behavior uses the lowest common protocol version and only declares full upgrade after all members reach the target version. citeturn0search6

## Nexo semantic refinement
A new certificate profile must not be considered equivalent merely because it can parse old bytes or reproduce the same fields. Compatibility must be claim-specific.

For each protected claim C define:
`Interpret_old(C, cert) -> decision_conditions_old`
`Interpret_new(C, cert) -> decision_conditions_new`

Then classify the migration as:
- `EQUIVALENT`: same admissible decisions for C;
- `STRICTER`: new profile removes unsafe cases without adding authority;
- `INCOMPARABLE`: semantics changed and require an explicit migration boundary;
- `WEAKER`: new profile admits a case forbidden by old policy — prohibited for silent activation.

## Critical semantic change
If a field changes meaning, preserving its name or encoding is insufficient. The field needs a new semantic identifier/profile and authenticated binding. An implementation that cannot understand a critical semantic field must reject/quarantine rather than reinterpret it. This follows the same safety direction as COSE critical parameters and TLS downgrade handling. citeturn0search0turn0search1

## Claim-by-claim migration gate
Candidate gate:
`NEW_PROFILE_ACTIVE(C)` only if:
1. old and new interpretation are explicitly mapped;
2. required fields are authenticated and domain-separated;
3. no new authorization path appears outside the declared profile;
4. any stronger restriction is explicitly recorded;
5. historical certificates retain original bytes/digest/profile;
6. mixed-version operation has one explicit active semantic profile per protected transition.

A conversion function is not itself evidence of semantic equivalence. Kubernetes conversion demonstrates why representation conversion and storage/serving semantics must remain distinct. citeturn0search4turn0search9

## Rollback rule
Rollback of code/schema must not silently restore weaker authority semantics. If a new profile has become authoritative, returning to an older profile requires an explicit migration/recovery transition whose policy proves that the old profile is still permitted for the affected claims. Otherwise the older profile remains historical-only.

## Invariants
- `PARSE_COMPATIBILITY != SEMANTIC_EQUIVALENCE`
- `FIELD_PRESENCE != FIELD_MEANING_EQUIVALENCE`
- `REPRESENTATION_CONVERSION != AUTHORITY_EQUIVALENCE`
- `EQUIVALENT_OR_STRICTER_REQUIRED_FOR_SILENT_PROMOTION`
- `INCOMPARABLE => EXPLICIT_MIGRATION_BOUNDARY`
- `WEAKER_PROFILE => NO_SILENT_ACTIVATION`
- `UNKNOWN_CRITICAL_SEMANTICS => REJECT_OR_QUARANTINE`
- `HISTORICAL_CERTIFICATE != CURRENT_AUTHORITY`
- `ROLLBACK != AUTOMATIC_AUTHORITY_RESTORATION`
- `MIXED_VERSION => SINGLE_EXPLICIT_AUTHORITY_PROFILE_PER_CLAIM`
