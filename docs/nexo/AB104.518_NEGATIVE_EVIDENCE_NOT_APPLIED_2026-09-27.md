# AB104.518 — negative evidence and UNKNOWN → NOT_APPLIED

## Evidence
etcd maintains historical revisions and deletion tombstones, but compaction eventually removes older history; therefore absence from current state is not automatically proof that an historical operation never occurred. citeturn1search1turn1search4 Kubernetes resourceVersion/watch semantics provide ordered change history within the API server, while stale/older reads are explicitly possible under some read semantics; clients requiring stronger freshness must request appropriate resource-version semantics. citeturn1search0

## Core finding
`NOT_APPLIED` is a **negative claim** and requires evidence capable of excluding the relevant operation from the provider's authoritative history/state for the exact target incarnation and operation identity.

A current absence is insufficient when:
- the operation history may be pruned;
- deletion/recreation can reuse a name;
- reads may be stale;
- operation records have expired;
- the provider's idempotency window has ended;
- the provider does not expose durable operation history.

## Minimum negative-evidence contract
Candidate proof object:
`NegativeEffectEvidence = {ProviderIdentity, TargetIdentity, TargetIncarnation, OperationID/EffectID, RequestDigest, ObservationRevision, HistoryCoverage, Tombstone/DeletionEvidence, QueryConsistency, ObservedAt, EvidenceExpiry}`

A transition `UNKNOWN → NOT_APPLIED` requires that the provider's semantics establish all relevant conditions:
1. the queried target is the same incarnation;
2. the observation is fresh enough for the effect class;
3. the relevant operation history is covered for the entire ambiguity interval;
4. no matching operation record exists in that authoritative history;
5. the target state satisfies the required non-effect postcondition;
6. the evidence has not been invalidated by a newer revision/fence/transition.

## Tombstones
A deletion tombstone can establish that a particular provider-side object generation ended at a known revision. etcd explicitly models deletion as a tombstone ending a key generation. citeturn1search1 But a tombstone is not automatically proof that a particular external operation never occurred before deletion. It must be bound to the exact operation and claim being evaluated.

`TOMBSTONE != OPERATION_NON_OCCURRENCE`
`DELETED_NOW != NEVER_APPLIED`

## Historical coverage
etcd demonstrates the crucial limitation: historical revisions can be compacted and then become unavailable. citeturn1search3turn1search4 Therefore:
`HISTORY_GAP => NO_PROOF_OF_NON_OCCURRENCE`.

If the ambiguity interval starts at revision/time `R0`, the provider must retain or otherwise attest coverage from at least the relevant predecessor state through the observation point. A current snapshot alone cannot reconstruct missing history unless the provider supplies an equivalent authoritative proof.

## Read freshness
Kubernetes distinguishes current/most-recent reads from semantics that permit older data, and exposes resourceVersion matching to control freshness. citeturn1search0 Nexo therefore cannot treat an ordinary or cached `NOT_FOUND` as negative evidence for a protected effect.

`STALE_NOT_FOUND != NOT_APPLIED`
`CURRENT_ABSENCE != HISTORICAL_NON_OCCURRENCE`

## Operation history beats target-state inference
Where available, provider-authoritative operation history bound to `EffectID`/idempotency identity is stronger for answering whether that exact operation was applied than inferring from the final target state. A later operation may produce the same final state, or an applied operation may subsequently be compensated.

Candidate precedence for this specific claim:
`AUTHORITATIVE_OPERATION_NONEXISTENCE`
→ `AUTHORITATIVE_OPERATION_RECORD_SHOWS_NOT_APPLIED`
→ `AUTHORITATIVE_TARGET_HISTORY_EXCLUDES_EFFECT`
→ `CURRENT_TARGET_POSTCONDITION`
→ `ORDINARY_CURRENT_READ`
→ `CLIENT_LOCAL_ABSENCE`.

This is claim-specific, not a universal evidence ranking.

## Idempotency retention interaction
AWS documents idempotency scoped by client token and parameters, including regional/zonal scope for some operations. citeturn1search8 Therefore a provider may no longer recognize an old EffectID after its retention boundary. If that happens during an UNKNOWN interval, absence of the idempotency record does not prove non-application.

`IDEMPOTENCY_RECORD_ABSENT_AFTER_EXPIRY != NOT_APPLIED`
`PRUNED_OPERATION_HISTORY != NEVER_APPLIED`

## Safe transition rule
Candidate transition:
`UNKNOWN`
→ `RECONCILIATION_QUERY`
→ `COVERAGE_VALIDATED`
→ `INCARNATION_VALIDATED`
→ `NEGATIVE_EVIDENCE_VALIDATED`
→ `NOT_APPLIED`

Any missing condition returns to `UNKNOWN` or `QUARANTINED`, never directly to `NOT_APPLIED`.

## In-flight revocation
Revocation does not create negative evidence about an earlier external operation. If an operation is UNKNOWN and the capability is subsequently revoked, the original effect must still be reconciled.

`REVOCATION != NON_OCCURRENCE_PROOF`
`CAPABILITY_REVOKED != EFFECT_NOT_APPLIED`

## Invariants
- `UNKNOWN != NOT_APPLIED`
- `CURRENT_ABSENCE != HISTORICAL_NON_OCCURRENCE`
- `STALE_NOT_FOUND != NOT_APPLIED`
- `TOMBSTONE != OPERATION_NON_OCCURRENCE`
- `DELETED_NOW != NEVER_APPLIED`
- `HISTORY_GAP => NO_PROOF_OF_NON_OCCURRENCE`
- `PRUNED_OPERATION_HISTORY != NEVER_APPLIED`
- `IDEMPOTENCY_RECORD_ABSENT_AFTER_EXPIRY != NOT_APPLIED`
- `REVOCATION != NON_OCCURRENCE_PROOF`
- `NOT_APPLIED_REQUIRES_EXACT_TARGET_INCARNATION`
- `NOT_APPLIED_REQUIRES_COVERAGE_OF_AMBIGUITY_INTERVAL`
- `MISSING_COVERAGE => UNKNOWN_OR_QUARANTINE`

## Status
Research complete. The key closure is that `UNKNOWN → NOT_APPLIED` requires proof of historical coverage, exact target incarnation, sufficient freshness, and operation-specific negative evidence. Current absence, deletion, expired idempotency records, or missing historical data cannot be silently promoted to non-application.

No implementation or formal verification performed.
