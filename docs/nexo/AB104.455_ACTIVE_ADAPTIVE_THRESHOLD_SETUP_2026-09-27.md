# Nexo AB104.455 — Active-Adaptive Threshold Adversaries and Setup Trust

## Research question

What do trusted-dealer setup, verifiable secret sharing (VSS), distributed key generation (DKG), and proactive resharing actually protect against, especially when an adversary can adaptively compromise participants over time?

## Evidence

NIST's Multi-Party Threshold Cryptography program explicitly treats key generation, threshold signatures, VSS-related techniques, adaptive corruption, and proactive security as distinct research topics. NIST's 2026 threshold call continues this work and includes active-adaptive adversary security in scope. citeturn0search0turn0search1

The 2026 NIST workshop distinguishes DKG and VSS and includes research on adaptive corruptions and proactive security, reinforcing that setup, corruption model, and share-refresh properties are separate dimensions rather than one generic "threshold security" property. citeturn0search2

NIST has also documented robust threshold systems that tolerate Byzantine faults while using share recovery and proactive share renewal, demonstrating that proactive renewal is a distinct mechanism rather than an automatic property of threshold signing. citeturn0search3

## Core distinction

Nexo must distinguish:

TRUSTED_DEALER
VSS
DKG
PROACTIVE_RESHARING
ACTIVE_ADAPTIVE_SECURITY

They solve different problems.

## T0 — trusted dealer

A trusted dealer generates the secret and distributes shares.

What it can provide:
- initial secret sharing;
- threshold confidentiality if the dealer behaves correctly;
- a defined initial public key.

What it introduces:
- dealer trust during setup;
- dealer compromise as a root-of-trust problem;
- possible knowledge of the reconstructed secret unless the protocol explicitly prevents it.

Candidate:

TRUSTED_DEALER_COMPROMISE => SETUP_TRUST_COMPROMISED.

A secure signing protocol afterward cannot retroactively remove a malicious dealer's setup authority.

## T1 — VSS

VSS adds mechanisms allowing participants to detect or reject inconsistent/malicious share distribution.

What it can protect:
- against a dealer distributing incompatible shares;
- against certain participant/dealer equivocation;
- verifiability of the sharing relation.

What it does NOT automatically prove:
- dealer is authorized to establish Nexo's recovery root;
- participants are independent;
- policy is correct;
- recovery event is legitimate;
- external world state is correct.

Therefore:

VSS_CORRECTNESS != GOVERNANCE_AUTHORITY.

## T2 — DKG

DKG removes the need for one trusted dealer to know the complete secret by having participants jointly contribute to key generation.

Potential benefit:
- no single dealer needs to possess the resulting private key.

But DKG still requires assumptions about:
- participant authentication;
- participant eligibility;
- protocol security;
- corruption threshold;
- communication;
- implementation;
- group membership;
- final public-key agreement.

Therefore:

DKG_REMOVES_SINGLE_DEALER_TRUST != DKG_REMOVES_ALL_TRUST.

## T3 — malicious DKG participant

An active participant can send malformed, inconsistent, or adversarial protocol messages.

A robust DKG must define how invalid contributions are detected and how the protocol terminates.

Candidate:

MALFORMED_PARTICIPANT_MESSAGE => REJECT_OR_QUARANTINE_PARTICIPANT.

Never silently convert protocol failure into a lower recovery threshold.

## T4 — adaptive corruption

Static corruption assumes the adversary chooses corrupted participants under a defined model before execution.

Adaptive corruption allows the adversary to choose targets during protocol execution based on observed state/transcripts.

NIST explicitly identifies active-adaptive security as a current threshold-cryptography research concern. citeturn0search0turn0search2

Candidate:

STATIC_SECURITY != ADAPTIVE_SECURITY.

Nexo cannot claim the latter from evidence for the former.

## T5 — sequential compromise

Suppose threshold = 3/5.

At time G10, attacker compromises participant A.
At G20, A is rotated.
At G30, attacker compromises B.
At G40, attacker compromises C.

Even if never holding three shares simultaneously, the attacker may accumulate enough information across epochs depending on the scheme and share-refresh properties.

Therefore compromise must be analyzed over time:

COMPROMISE_HISTORY × SHARE_EPOCHS.

## T6 — proactive resharing

Proactive resharing changes shares while preserving the underlying secret/public key.

Its intended benefit is limiting the useful lifetime of a compromised share.

But proactive resharing does NOT automatically:
- revoke a compromised participant's administrative identity;
- establish new governance;
- prove previous shares were never copied;
- erase evidence of compromise;
- change the public trust root.

Therefore:

SHARE_REFRESH != ROOT_ROTATION.

## T7 — participant removal during proactive resharing

If a compromised participant is excluded from the new share set, the old share must no longer be accepted for the new epoch.

Candidate:

NEW_SHARE_EPOCH => OLD_SHARE_EPOCH_REJECTED_FOR_CURRENT_PROTOCOL.

However, this is a protocol property, not proof that the attacker forgot or destroyed an old share.

## T8 — compromise before refresh

If an attacker obtains enough shares before proactive refresh, refreshing later cannot retroactively invalidate signatures or decisions already made.

Therefore:

POST_COMPROMISE_REFRESH != HISTORICAL_ERASURE.

Affected historical claims require separate reassessment.

## T9 — adaptive corruption during DKG

If the adversary can compromise participants while DKG is running, the protocol's corruption threshold must explicitly cover that model.

If the security proof only covers static corruption, Nexo must classify adaptive protection as UNKNOWN.

Candidate:

UNPROVEN_ADAPTIVE_SECURITY => NO_ADAPTIVE_SECURITY_CLAIM.

## T10 — setup transcript replay

An old DKG/VSS transcript is replayed to recreate an old group configuration.

Candidate controls:
- setup event ID;
- group incarnation;
- participant-set hash;
- protocol version;
- transcript commitment;
- activation generation;
- anti-replay state.

Candidate:

OLD_SETUP_TRANSCRIPT != CURRENT_GROUP_CONFIGURATION.

## T11 — participant enrollment is part of the TCB

A perfect DKG with maliciously selected participants still creates a malicious recovery group.

Therefore participant enrollment requires:
- authenticated identity;
- authorization;
- governance basis;
- dependency closure;
- revocation;
- activation generation.

Candidate:

CRYPTOGRAPHIC_PARTICIPATION != AUTHORIZED_PARTICIPATION.

## T12 — implementation diversity

Different implementations may reduce correlated implementation failures, but diversity itself is not proof of independence.

Conversely, identical implementations can share a common vulnerability.

Therefore software diversity is evidence about a failure domain, not a universal independence guarantee.

## T13 — proactive resharing cannot solve governance compromise

If the same compromised authority controls participant enrollment, resharing may simply create fresh shares under the same compromised governance.

Candidate:

GOVERNANCE_COMPROMISE_SURVIVES_SHARE_REFRESH.

## T14 — share recovery is not trust recovery

A lost participant can sometimes have a share recovered or reissued.

That does not establish:
- current authority;
- legitimacy of the replacement participant;
- independence;
- absence of compromise.

Candidate:

SHARE_RECOVERY != TRUST_RECOVERY.

## T15 — VSS/DKG and external evidence

Cryptographic proof that a key was generated correctly does not prove that the machine running the protocol is uncompromised or that the resulting root is the correct Nexo recovery root.

Therefore the cryptographic ceremony remains one layer in the broader trust/evidence graph.

## Comparative matrix

| Mechanism | Main property | Main dependency | Does not establish |
|---|---|---|---|
| Trusted dealer | Secret distribution | Dealer trust | Independent setup |
| VSS | Verifiable sharing | Protocol + participant model | Governance legitimacy |
| DKG | No single dealer knows full secret | Participant/protocol assumptions | Participant independence |
| Proactive resharing | Limits share exposure across epochs | Secure refresh protocol | Historical erasure |
| Adaptive-secure protocol | Security under adaptive corruption model | Correct security model + implementation | Governance authority |

## Candidate Nexo setup stack

For high-consequence recovery:

GOVERNED_PARTICIPANT_ENROLLMENT
→ AUTHENTICATED_GROUP_CONFIGURATION
→ DKG_OR_OTHER_APPROVED_SETUP
→ VSS/ROBUSTNESS_CHECKS
→ PUBLIC_KEY_ACTIVATION
→ PROTECTED_GENERATION
→ PERIODIC_OR_TRIGGERED_PROACTIVE_RESHARING
→ PARTICIPANT_REVOCATION/ROTATION
→ INDEPENDENT_RECOVERY_EVIDENCE.

This is a candidate research model, not an implementation prescription.
