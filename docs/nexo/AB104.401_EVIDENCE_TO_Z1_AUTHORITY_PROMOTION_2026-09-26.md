# Nexo AB104.401 — Evidence-to-Z1 Authority Promotion Boundary

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective

Attack the final boundary where a validated appraisal/evidence result becomes input to Z1 authority. The key question is what Z1 must revalidate immediately before granting protected authority.

RFC 9334 explicitly separates the Verifier, which produces Attestation Results, from the Relying Party, which applies its own policy for application-specific authorization. It also states that freshness can still race with state/policy changes after an appraisal is produced. citeturn0search0turn0search1 NIST's Policy Enforcement Point definition similarly distinguishes enforcement from policy decision. citeturn0search2

## 1. Core boundary

Candidate flow:

EVIDENCE
→ VERIFICATION/APPRAISAL
→ ATTESTATION_RESULT
→ Z1 PRE-AUTHORIZATION CHECK
→ Z1 AUTHORITY DECISION
→ PROTECTED TRANSITION

The appraisal result is evidence/input. It does not itself grant Nexo authority.

## 2. Attack — revocation between appraisal and use

Timeline:
1. Verifier produces VALIDATED_CURRENT at T0.
2. Dependency/policy/verifier/resource is revoked at T1.
3. Z1 receives the cached result at T2.
4. Z1 grants authority.

Unsafe.

Candidate rule:
Z1 must validate current invalidation/revocation generation and all claim-critical bindings immediately before authority grant.

## 3. Attack — verifier compromise after appraisal

Timeline:
1. V1 produces valid appraisal.
2. V1 becomes compromised.
3. Cached appraisal is presented.
4. Z1 accepts solely because signature is valid.

Signature validity is not sufficient if current trust policy requires the verifier to remain trusted.

Candidate:
VERIFIER_TRUST_GENERATION must be bound to the appraisal and checked at Z1.

Historical appraisal remains retained but current usability can become UNKNOWN/QUARANTINED.

## 4. Attack — semantic specification rollback/change

P8 validates a dependency result.
P9 becomes current.
P9 changes required semantics.
Later P8 is restored.

The old P8 appraisal cannot automatically become current.

Rollback is a new protected semantic state transition requiring compatibility/currentness validation.

## 5. Attack — resource incarnation change

Appraisal binds resource R/I1.
Resource is replaced: R/I2.
Cached appraisal is reused.

Must reject unless the appraisal explicitly covers I2 and the exact binding is current.

RESOURCE_ID alone is insufficient when replacement can occur.

## 6. Attack — adapter path substitution

Validated path:
D7 → Adapter A7 → Provider P7.

Runtime path:
D7 → Adapter A8 → Provider P7.

Even if D7 remains unchanged, semantic enforcement may differ.

Z1 must bind the appraisal to actual adapter/path/configuration identity where that path affects the claim.

## 7. Attack — authority epoch rollover

Appraisal is valid under authority epoch A4.
Before authority grant, A5 becomes current.

If the appraisal claim requires A4 currentness, it is stale.

Candidate:
AUTHORITY_EPOCH must be checked at the protected authorization boundary whenever it is part of the claim.

## 8. Attack — stale cache race

A result is inside its nominal time-based freshness interval but a protected invalidation event occurred.

Therefore:
TIME_FRESH != STATE_FRESH.

For safety-critical claims, event/generation-based invalidation should take precedence over a permissive TTL when the protected property requires immediate revocation.

RFC 9334 explicitly notes that freshness thresholds narrow recency but do not eliminate races with state changes. citeturn0search0

## 9. Attack — Z1 revalidates too little

Suppose Z1 checks only:
signature + expiry.

It misses:
policy generation, dependency root, resource incarnation, verifier trust generation, adapter path, authority epoch.

A formally valid signature can therefore authorize a context different from the one appraised.

Candidate minimum is claim-specific, not universal.

## 10. Attack — Z1 revalidates everything

Opposite failure: Z1 imports the complete evidence graph and entire verifier stack.

This expands the authoritative core excessively.

Candidate principle:
Z1 revalidates only the protected frontier necessary for the claimed authority property.

Heavy evidence processing remains outside Z1; exact roots, versions, generations, scope and appraisal status cross the boundary.

## 11. Candidate AUTHORITY_ADMISSION_CONTEXT

For a claim C, candidate protected context:

AUTHORITY_ADMISSION_CONTEXT = {
  CLAIM_ID/VERSION,
  REQUIRED_SET_ROOT,
  INSTANCE_CLOSURE_ROOT,
  POLICY_VERSION/DIGEST,
  SEMANTIC_RULE_VERSION,
  VERIFIER_TRUST_GENERATION,
  APPRAISAL_POLICY_VERSION,
  RESOURCE_ID,
  RESOURCE_INCARNATION,
  ADAPTER/PATH_ID where relevant,
  DEPENDENCY_STATE_GENERATIONS,
  INVALIDATION_GENERATION,
  AUTHORITY_EPOCH,
  EFFECT_CLASS,
  SCOPE,
  FRESHNESS_BASIS,
  APPRAISAL_ID
}

Not every field is mandatory for every claim. The claim contract defines the minimum.

## 12. Candidate final gate

Z1 may promote appraisal input to authority only if:

APPRAISAL_AUTHENTIC
AND CLAIM_SCOPE_MATCH
AND REQUIRED_SET_ROOT_MATCH
AND CLOSURE_ROOT_MATCH
AND POLICY/SEMANTIC_VERSIONS_CURRENT
AND VERIFIER_TRUST_CURRENT
AND REQUIRED_DEPENDENCY_GENERATIONS_CURRENT
AND RESOURCE_INCARNATION_CURRENT
AND ADAPTER_PATH_CURRENT_WHERE_REQUIRED
AND INVALIDATION_GENERATION_CURRENT
AND AUTHORITY_EPOCH_CURRENT_WHERE_REQUIRED
AND FRESHNESS_REQUIREMENT_SATISFIED
AND NO_UNRESOLVED_CONTRADICTION
AND EFFECT_CLASS_POLICY_SATISFIED.

Then Z1 records the protected authority decision.

## 13. Atomicity requirement

The final checks cannot be performed as unrelated reads followed by a later authority grant if any checked value can change in the gap.

Candidate:
FINAL_AUTHORITY_GATE must use one protected linearization point or an equivalent fencing/versioned commit mechanism.

This repeats the earlier AB104.369–370 lesson:
CHECK_AUTHORITY ≠ AUTHORITY_COMMIT.

## 14. Attack — invalidation concurrent with final gate

If invalidation I2 and authority grant A2 race:

- invalidation linearizes first → grant rejected/held;
- grant linearizes first → the grant was valid under the protected state at that boundary; subsequent invalidation is not retroactive, but future protected effects require current authorization/fencing;
- ambiguous ordering → protected state must expose enough evidence to classify, otherwise UNKNOWN/HOLD.

## 15. Attack — evidence revoked after grant but before external effect

Local authority may remain historically valid, but external effect authorization can become stale.

Therefore:
Z1 authority grant != permanent external permission.

External effect boundary still requires current authority/fence as established in AB104.369–385.

## 16. Attack — verifier outage

If verifier is unavailable:
- no new high-consequence appraisal promotion unless existing appraisal remains valid under explicit policy and all current invalidation checks pass;
- outage must not be replaced with provider self-attestation;
- when required validity expires, status becomes UNKNOWN/HOLD.

## 17. Attack — revocation propagation delay

A revoked dependency may not instantly propagate to every cache.

Candidate safety rule:
Z1's authoritative invalidation state is the decision point for protected authority. Distributed caches are optimization only unless their bounded-staleness semantics are explicitly included in the safety claim.

## 18. Candidate separation of states

APPRAISAL_STATUS:
UNVALIDATED / VALIDATED / INVALIDATED / HISTORICAL / UNKNOWN

AUTHORITY_STATUS:
NOT_GRANTED / GRANTED / REVOKED / EXPIRED / QUARANTINED

Never infer:
VALIDATED → GRANTED

Promotion is a separate protected transition.

## 19. Key invariants

- VERIFIED != AUTHORIZED
- AUTHENTIC_APPRAISAL != CURRENT_AUTHORIZATION
- TIME_FRESH != STATE_FRESH
- SIGNATURE_VALID != CONTEXT_CURRENT
- VERIFIER_TRUST_MUST_BE_CURRENT
- RESOURCE_INCARNATION_MUST_MATCH
- REQUIRED_DEPENDENCY_GENERATIONS_MUST_MATCH
- FINAL_AUTHORITY_GATE_MUST_BE_ATOMIC_OR_FENCED
- INVALIDATION_BEFORE_GATE => NO_GRANT
- INVALIDATION_AFTER_GATE != RETROACTIVE_ERASURE
- AUTHORITY_GRANT != PERMANENT_EXTERNAL_PERMISSION
- CACHE_IS_NOT_AUTHORITATIVE_INVALIDATION_STATE
- Z1_REVALIDATION_MUST_BE_CLAIM_SPECIFIC
- HISTORICAL_APPRAISAL_MUST_NOT_BE_REWRITTEN

## Status

AB104.401 establishes a candidate final promotion boundary:

**Verifier/appraisal establishes evidence; Z1 independently decides whether that evidence is currently sufficient for protected authority.**

The minimum Z1 check is not “signature + TTL.” It is the claim-specific protected frontier required to ensure that the appraisal still refers to the same semantic contract, dependency closure, resource incarnation, trust state, invalidation generation and authority context.

Not proven: formal atomicity, complete claim-specific field selection, implementation correctness, distributed revocation latency bounds, or deployment correctness.

## Exact next action

AB104.402 — attack the AUTHORITY_ADMISSION_CONTEXT itself: whether its fields can be complete without becoming a universal state snapshot, how dependencies are selected claim-by-claim, and whether a malicious/buggy claim contract can omit a critical field.
