# Nexo AB104.542 — Provider atomicity boundary: high-water mark versus external mutation

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A provider can atomically update its own durable state and high-water mark when the protected effect is itself part of that provider's transactional domain. It cannot automatically make an unrelated external side effect atomic with that high-water mark. Therefore provider-side fencing closes stale-writer races only inside the provider's transaction boundary; outside it, the effect remains a separate external-effect state machine.

## Evidence
etcd transactions atomically evaluate comparisons and apply multiple key/value operations, with one store revision for the transaction. DynamoDB TransactWriteItems similarly provides all-or-nothing atomicity for writes within its transactional domain, while AWS explicitly notes that downstream stream/index propagation is not itself transactional/ordered in the same way. DynamoDB conditional writes also demonstrate the pattern of making a state transition conditional on the latest stored value. citeturn0search5turn0search1turn0search0

## Boundary model
Inside provider transaction:
CHECK(Fence >= HighWaterMark)
AND CHECK(TargetIncarnation == expected)
AND CHECK(ProviderState == expected)
THEN atomically:
  HighWaterMark := Fence
  ProviderOperationState := accepted/applied
  OperationRecord := durable

This can close the provider-local stale-writer race.

Outside provider transaction:
ProviderCommit -> network -> external system
is a separate boundary.
A successful provider transaction cannot prove the external world changed, and an external change cannot be rolled back merely because the provider transaction later fails.

## Candidate result classes
1. REJECTED_BEFORE_PROVIDER_COMMIT — no provider-side admission.
2. PROVIDER_COMMITTED — fence and provider operation state committed.
3. EXTERNAL_ATTEMPTED — provider dispatched externally.
4. EXTERNAL_CONFIRMED — independent evidence confirms external postcondition.
5. UNKNOWN — crash/lost response prevents determining whether the external boundary was crossed.

## Crash cases
- Crash before provider commit: retry same logical operation after reconciliation.
- Crash after provider commit before external dispatch: durable provider record permits deterministic recovery.
- Crash after external dispatch before response: external result is UNKNOWN until reconciled.
- Crash after external confirmation but before local acknowledgement: confirmation evidence must be recoverable/reconciled.

## Why idempotency is not atomicity
A stable OperationID and provider idempotency can prevent duplicate provider-side admission, but they do not turn an unrelated external system into the same transaction. AWS documents transaction idempotency windows and recommends stable idempotency tokens for retries; that is retry safety, not cross-system atomicity. citeturn0search1turn0search3

## Critical distinctions
- PROVIDER_ATOMICITY != CROSS_DOMAIN_ATOMICITY
- HIGH_WATER_MARK_COMMITTED != EXTERNAL_EFFECT_CONFIRMED
- PROVIDER_COMMIT != EXTERNAL_COMMIT
- IDEMPOTENCY != ATOMICITY
- DURABLE_INTENT != EFFECT_APPLIED
- PROVIDER_RECEIPT != WORLD_TRUTH
- TRANSACTIONAL_DOMAIN != EXTERNAL_WORLD
- LOCAL_ROLLBACK != REMOTE_ROLLBACK

## Nexo implication
E3-E5 capability evidence must include the provider's actual atomic boundary. A provider may receive strong fencing assurance while the external effect remains UNKNOWN after the dispatch boundary. The architecture should preserve that distinction rather than promoting provider commit into external confirmation.
