## Research question
How should Nexo adversarially validate provider capabilities, and how should evidence dependencies prevent common-mode evidence from being mistaken for independent confirmation?

## Fresh external evidence
Amazon S3 documents that conditional writes evaluate If-Match against the object ETag during the write and reject mismatches; it also documents concurrent conditional-write outcomes. ## Validation suite

### V0 — Identity and scope
Verify provider, resource, resource incarnation, adapter, API version, configuration, and capability-profile version.
Failure => capability remains UNVALIDATED.

### V1 — Positive target-condition test
Execute a valid conditional mutation.
Expected: accepted only when target predicate holds.
Evidence: exact request, target version, response, resulting state.

### V2 — Stale-target adversarial test
Change target version after admission and before mutation.
Expected: stale conditional request rejected.
Failure => TC not VALIDATED.

### V3 — Authority-fence adversarial test
Issue F1, establish F2, then deliver delayed F1.
Expected: resource rejects F1.
Failure => AF not VALIDATED.

### V4 — Concurrent fence-order test
Race F1/F2 at resource acceptance.
Expected: resource linearization determines one ordered result; stale generation cannot be accepted after a newer fence has taken effect.
Unknown ordering => claim narrowed.

### V5 — Restart fence persistence
Establish F2, restart resource, then deliver F1.
Expected: F1 rejected if DFS is claimed.
Acceptance => DFS claim invalid.

### V6 — Failover fence persistence
Establish F2 on active path, fail over, deliver F1.
Expected: F1 rejected if XF/DFS is claimed.
Failure => failover guarantee invalidated.

### V7 — Resource-incarnation replacement
Replace resource, ensure old-incarnation effect cannot target replacement resource under old identity/fence.
Expected: rejection/quarantine.
Failure => incarnation binding invalid.

### V8 — Stable EffectID duplicate test
Submit same EffectID twice under defined retry conditions.
Expected: one logical effect according to provider contract.
If two effects occur => ID/idempotency claim fails.

### V9 — New EffectID replay
Repeat the same business intent with a new EffectID.
Expected: treated as a new logical effect, not automatically deduplicated.
This tests the distinction RETRY != EFFECT_IDENTITY.

### V10 — Crash after durable intent
Crash after intent persistence and before external release.
Expected: reconstructable state; no unrecorded external execution should be inferred.

### V11 — Crash at attempt boundary
Crash around attempt-record/release ordering.
Expected: if an external attempt may have escaped, state becomes UNKNOWN/reconciliation-required rather than silently rejected.

### V12 — Ambiguous acknowledgement
Allow provider execution while dropping/delaying response.
Expected: UNKNOWN until exact evidence resolves outcome.

### V13 — ACK identity-binding
Return/observe an acknowledgement that cannot be bound to exact EffectID.
Expected: insufficient for EXTERNAL_CONFIRMED.

### V14 — Reconciliation exactness
Create ambiguous outcome and query provider.
Expected: reconciliation identifies exact effect/resource state.
If two possible effects are indistinguishable, exact-confirmation claim fails.

### V15 — Cancellation race
Issue cancellation concurrently with acceptance.
Expected: result follows documented provider race semantics; timeout/cancel response must not be interpreted as proof of non-execution.

### V16 — Reversal semantics
Execute reversible effect, then compensation.
Expected: compensation is a new protected effect with its own identity/evidence; original event remains historical.

### V17 — Gateway boundary test
Validate GAE/RF at gateway, then test delayed stale request against downstream.
Expected: downstream stale-effect property is claimable only if downstream itself or an equivalent controlled boundary enforces it.

### V18 — Mixed direct/gateway composition
Combine direct-fenced and gateway-mediated participants.
Expected: global claim is limited by the weakest relevant participant and coordination contract.

### V19 — Capability downgrade in flight
Validate P5, begin operation, then remove/disable required fence semantics before release.
Expected: release blocked or claim downgraded/HOLD.

### V20 — Adapter-path mismatch
Declare native fencing but route request through a fallback path that only supports target conditional.
Expected: safety-critical capability claim invalidated.

### V21 — Provider failover semantic drift
Fail over to a path with different conditional/fence behavior.
Expected: capability profile becomes UNKNOWN/DEGRADED until revalidated.

### V22 — Evidence-source compromise/common mode
Generate multiple observations through the same provider telemetry/control plane.
Expected: evidence dependency graph marks them non-independent.

## Evidence closure rule
For a safety claim C:
C is promotable only if:
1. every required capability has valid evidence;
2. evidence covers the actual protected boundary;
3. all required dependency nodes are within declared scope;
4. contradictory evidence is absent or explicitly resolved;
5. common-mode dependencies are visible;
6. required failover/recovery evidence exists;
7. claim-specific limitations are retained.

## Evidence invalidation
Any failed V2–V21 relevant to a promoted capability creates an invalidation event. The old evidence is retained historically; current capability becomes UNKNOWN/DEGRADED/QUARANTINED according to severity.

A successful later test does not erase the earlier failure; it creates new evidence that may explain, scope, or supersede the prior result.
