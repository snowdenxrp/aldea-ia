# Nexo AB104.397 — Semantic Required-Set Authority and TCB Boundary

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## Objective
Determine who or what may establish the completeness of the semantic REQUIRED_SET without turning the derivation engine into an unnecessarily large authoritative TCB.

Fresh evidence: RFC 9334 separates Evidence production, Verifier appraisal, and Relying Party application-specific policy/authorization. NIST SP 800-207 similarly separates policy decision from policy enforcement. These are useful architectural analogies: deriving or appraising a requirement set is not automatically the same as authorizing its operational use. citeturn0search0turn0search24

## 1. Core distinction

Three claims must remain separate:

1. SEMANTIC_COMPLETENESS — the required dependency set was derived from the applicable claim/effect semantics.
2. INSTANCE_CLOSURE_INTEGRITY — the concrete graph actually contains and binds the declared dependencies.
3. OPERATIONAL_AUTHORITY — the current protected system permits the resulting claim/effect.

A derivation engine may support (1) without possessing (3).

## 2. Candidate authority chain

CANDIDATE:
CLAIM_CONTRACT / EFFECT_CONTRACT
→ POLICY + SCHEMA
→ REQUIRED_SET_DERIVATION
→ REQUIRED_SET_ROOT
→ INSTANCE_CLOSURE
→ VERIFICATION
→ Z1 AUTHORITY DECISION

The derivation engine is therefore a semantic function whose output is evidence/input to the authoritative decision, not authority itself.

## 3. Hidden-TCB attack

If Z1 asks an opaque derivation service “what dependencies are required?” and trusts the answer without binding the derivation logic/version/policy, that service becomes a hidden TCB.

Attack:
- malicious or buggy derivator omits D4;
- produces valid root for D1,D2,D3;
- Z1 verifies the root;
- operation is authorized despite missing D4.

Conclusion: DERIVATION_LOGIC + POLICY + SCHEMA + REFERENCE_SEMANTICS are part of the completeness claim's trust closure.

## 4. Minimal TCB candidate

Do not put the whole derivation engine into Z1.

Candidate protected semantic anchors:
- CLAIM_CONTRACT_ID/version;
- EFFECT_CONTRACT_ID/version;
- POLICY_ID/version/digest;
- SCHEMA_ID/version/digest;
- DERIVATION_ALGORITHM_ID/version/digest;
- REQUIRED_SET_ROOT;
- DERIVATION_RESULT_STATUS;
- invalidation/revocation generation.

Large parsing, graph traversal, indexing and historical evidence can remain outside Z1 if their output is bound to these immutable semantic anchors and independently verified.

## 5. Two verification models

### Model A — Reproducible derivation
Z1 or a verifier can deterministically recompute REQUIRED_SET from immutable semantic inputs.

Advantage: fewer opaque trust assumptions.
Cost: semantic rules and canonicalization must be deterministic and sufficiently small/auditable.

### Model B — Attested derivation
An external derivator produces REQUIRED_SET plus a signed/attested result.

Advantage: complex derivation can remain outside Z1.
Cost: derivator, derivation version, policy, schema and evidence path become part of the trust closure; self-attestation cannot establish completeness by itself.

RFC 9334's Attester/Verifier/Relying Party separation supports treating an attested result as evidence for a relying party rather than as automatic authorization. citeturn0search0

## 6. Recursive dependencies

A dependency may itself have dependencies.

Candidate rule:
- recursively expand semantic requirements to a fixed point;
- each expansion step records its rule/version;
- cycle detection is mandatory;
- unresolved cycle or contradictory requirement => UNKNOWN/QUARANTINED;
- maximum depth/resource limits are safety constraints, not permission to silently truncate.

A bounded evaluator that truncates an unresolved dependency chain must not claim completeness.

## 7. Dynamic dependencies

Some dependencies are branch-dependent.

Candidate representation:
REQUIRED_SET = BASE_SET + CONDITIONAL_REQUIREMENTS(branch predicates)

For a protected operation, all predicates that can affect authorization must be resolved before the relevant protected boundary.

If a genuinely new dependency is discovered after the boundary, the operation must enter a new evaluation/authorization boundary rather than silently expanding its TCB at runtime.

## 8. Policy/schema migration

P7→P8 or S7→S8 can change REQUIRED_SET.

Rules:
- derivation result is bound to exact policy/schema versions;
- old result remains historical;
- compatibility is explicit and versioned;
- compatibility cannot invent equivalence for uncovered semantic properties;
- if old/new required sets differ materially, current use requires new derivation unless a protected compatibility rule explicitly covers the transition.

## 9. Conflicting authorities

Possible sources:
- policy says D1,D2;
- effect contract says D1,D2,D3;
- runtime adapter says D1,D2,D4.

Do not silently choose one.

Candidate precedence must be explicit in the claim contract/policy. If no deterministic conflict-resolution rule exists, status is UNKNOWN/QUARANTINED.

## 10. Completeness is claim-specific

There is no universal “complete dependency graph.”

The required set depends on:
claim property + effect class + resource scope + policy + schema + execution path.

Therefore:
COMPLETENESS(C1) does not imply COMPLETENESS(C2).

This prevents overclaiming from a generic graph-validation result.

## 11. Derivation compromise

If the derivation engine is compromised:
- previously issued results remain historical evidence;
- current safety-critical usability is invalidated if the compromised derivation is a required dependency;
- re-derive under trusted logic/policy;
- do not delete historical records;
- no automatic promotion based on cached prior output.

## 12. Denial-of-service / liveness attack

A dependency rule can recursively expand without bound.

Safety rule:
- enforce explicit resource/depth/complexity limits;
- distinguish RESOURCE_LIMIT_REACHED from COMPLETE;
- return UNKNOWN/DEGRADED rather than truncating and declaring completeness.

Liveness optimization must not weaken semantic completeness.

## 13. Candidate machine-checkable contract

DERIVATION_RESULT valid for current use iff:

contract/version current
AND policy/schema versions match
AND derivation algorithm version is approved
AND required-set root verifies
AND dependency expansion completed without unresolved cycles/conflicts
AND all conditional predicates relevant to the protected claim are resolved
AND no required derivation dependency is invalid/revoked
AND result scope/resource/incarnation matches
AND result freshness/invalidation requirements hold.

Then the result is still evidence/input to Z1; it is not itself authority.

## 14. Candidate invariants

- SEMANTIC_COMPLETENESS != INSTANCE_CLOSURE_INTEGRITY
- INSTANCE_CLOSURE_INTEGRITY != OPERATIONAL_AUTHORITY
- DERIVATION_ENGINE_CANNOT_SILENTLY_BECOME_HIDDEN_TCB
- DERIVATION_LOGIC_MUST_BE_VERSION_BOUND
- POLICY_AND_SCHEMA_MUST_BE_VERSION_BOUND
- SIGNED_DERIVATION_RESULT != AUTOMATIC_COMPLETENESS
- SELF_ATTESTATION != INDEPENDENT_COMPLETENESS_VALIDATION
- RECURSIVE_CLOSURE_MUST_REACH_FIXED_POINT_OR_RETURN_UNKNOWN
- RESOURCE_LIMIT != COMPLETENESS
- DYNAMIC_DEPENDENCY_REQUIRES_NEW_BOUNDARY
- MIGRATION_CANNOT_SILENTLY_CHANGE_SEMANTICS
- CONFLICTING_REQUIREMENTS_MUST_NOT_BE_COLLAPSED
- COMPLETENESS_IS_CLAIM_SPECIFIC
- DERIVATION_COMPROMISE_INVALIDATES_CURRENT_DEPENDENT_CLAIMS
- HISTORICAL_RESULTS_ARE_RETAINED

## Status

AB104.397 establishes a candidate separation between semantic derivation and authority. The derivation engine can remain outside Z1 if its semantic inputs, algorithm identity, result root, scope, version and invalidation state are protected and independently appraised.

Not proven: deterministic semantic derivation correctness, completeness of recursive/dynamic rules, Byzantine resistance, migration correctness, or formal/implementation correctness.

## Exact next action

AB104.398 — adversarially attack the semantic derivation contract itself: contradictory policy/effect/schema rules, recursive cycles, branch-dependent dependencies, rule updates during derivation, and whether deterministic recomputation is actually sufficient to establish semantic completeness.
