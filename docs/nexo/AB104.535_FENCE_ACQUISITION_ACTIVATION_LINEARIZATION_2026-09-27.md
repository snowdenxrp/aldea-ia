# Nexo AB104.535 — Fence acquisition race and activation linearization

Date: 2026-09-27
Status: RESEARCH COMPLETE — DESIGN INPUT ONLY

## Finding
A fence value must be allocated and activated through the same authoritative ordering domain that protects the state it fences. Merely reading state, generating a token locally, and later publishing it leaves a race in which a newer authority epoch or target generation can supersede the token before activation.

## Evidence
etcd transactions provide atomic compare-and-put semantics and a monotonic revision for a successful transaction. ZooKeeper's zxid/order and ephemeral/sequence mechanisms provide ordered state transitions and fencing patterns; the classic fencing-token model requires recipients to reject older tokens. Kubernetes resourceVersion similarly lets a writer condition a mutation on the version it observed.

## Candidate safe acquisition
1. Read authoritative VersionSet/AuthorityEpoch/TargetIncarnation.
2. In one protected transition, validate the expected versions and allocate next FenceRevision.
3. Persist the fence activation atomically with the protected state transition.
4. Only then expose the fence to an executor.
5. Provider must reject lower/older fence or generation values where stale-writer protection is required.

Candidate:
CAS(ExpectedVersionSet, AuthorityEpoch, TargetIncarnation)
AND allocate FenceRevision = current + 1
AND persist FenceRecord
=> ACTIVATED

If CAS fails: fence not activated; recompute.

## Monotonicity
Fence values must be monotonic within their authority scope. Reusing a lower fence after restart, failover, rollback, or snapshot restoration can resurrect stale writers.

Required checks include:
- FenceRevision > previously accepted fence for the same scope.
- AuthorityEpoch compatible with the fence.
- TargetIncarnation compatible with the fence.
- Recovery/restore cannot lower the fence without an explicit trust transition.

## Activation race
A fence can be prepared but not yet active. A prepared fence must not be treated as authorization. Crash semantics:
- no durable activation -> no active fence;
- activation committed -> recover active fence;
- conflicting durable activation -> quarantine/reconcile;
- stale prepared fence -> discard/recompute.

## Provider boundary
A Nexo fence protects external stale writers only if the provider enforces it. A locally monotonic token that the provider ignores is evidence metadata, not a fence.

## Critical distinctions
- FENCE_PREPARED != FENCE_ACTIVE
- TOKEN_GENERATED != TOKEN_ENFORCED
- MONOTONIC_LOCAL_COUNTER != GLOBAL_STALE_WRITER_PROTECTION
- NEW_FENCE != AUTOMATIC_AUTHORITY
- FENCE_ACTIVATION != EXTERNAL_EFFECT_COMMIT
- CRASH_BEFORE_ACTIVATION != ACTIVE_FENCE
- ROLLBACK != SAFE_FENCE_REUSE
- PROVIDER_ACK != FENCE_ENFORCEMENT

## Nexo implication
Fence acquisition belongs inside the protected authoritative transition, not in an ordinary executor or planner. The fence record needs durable scope, authority epoch, target incarnation, predecessor/current value, activation revision, and recovery semantics. Provider adapters must separately attest whether the fence is actually enforced.
