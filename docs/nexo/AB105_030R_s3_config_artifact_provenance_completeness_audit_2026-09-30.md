# AB105.030R — S3 versioning and Config delivery artifacts: provenance strengthened, completeness still claim-bound
Date: 2026-09-30
Status: RESEARCH/AUDIT ONLY — no implementation, no semantic freeze.

## Research question

Can S3 object versioning, object identity/metadata, and AWS Config delivery notifications establish provenance and completeness of exported Config history artifacts strongly enough to turn missing artifacts into negative historical evidence?

## Primary evidence

AWS Config automatically delivers configuration history files for recorded resource types to an S3 bucket. Configuration snapshots are point-in-time collections of recorded ConfigurationItems, while the configuration stream is an automatically updated list of recorded ConfigurationItems delivered through SNS. AWS Config exposes delivery status separately for history, snapshots, and stream notifications. citeturn0search0turn0search1

S3 Versioning keeps multiple versions of an object key. A delete inserts a delete marker rather than immediately removing prior versions, and overwrites create new object versions. Version IDs are generated by S3 and are immutable/opaque. citeturn0search4

AWS CloudTrail can log S3 object-level API operations such as PutObject, DeleteObject, and ListObjectVersions when data-event logging is configured; bucket-level management events are separately logged. citeturn0search3

AWS Config has its own retention policy for ConfigurationItems, separate from S3/SNS retention policies. citeturn0search2

## Findings

### F1 — S3 VersionId strengthens artifact identity, not historical completeness

For a versioned delivery bucket, a VersionId gives a provider-generated identity to a particular object version. This can distinguish an original delivered artifact from later overwrites.

Therefore:

object key + VersionId -> stronger artifact identity

But:

artifact identity != proof that all expected artifacts exist

A complete provenance chain still requires expected scope/time/resource-type coverage.

### F2 — Versioning protects against ordinary overwrite/delete ambiguity, subject to retention and deletion authority

S3 Versioning can preserve prior versions when objects are overwritten or deleted, with delete markers representing deletes. However, permanent deletion of a specific version is possible to an authorized principal, and versioning does not itself establish that every historically expected object was ever delivered. citeturn0search4

Thus:

versioned artifact retained -> positive provenance evidence

missing versioned artifact -> not automatically “never delivered”

### F3 — CloudTrail can independently evidence object-level mutations, but only when configured for them

S3 object-level operations are data events. AWS states that these are distinct from management events and require appropriate CloudTrail data-event configuration. citeturn0search3

This can create an independent provenance layer:

Config delivery
-> S3 object/version
-> CloudTrail object-level mutation evidence

But the independence is conditional. If CloudTrail data events were not enabled for the relevant bucket/prefix/period, absence of an object-level event cannot establish that no mutation occurred.

### F4 — Delivery notifications bind occurrence to delivery, not necessarily to full expected-set completeness

AWS Config's stream/notification path can demonstrate that a configuration item was emitted through that channel. DeliveryChannelStatus separately reports stream delivery status. citeturn0search0turn0search1

A notification is therefore positive evidence of a delivered/attempted change notification.

It does not, by itself, prove that every expected notification was delivered and retained across an interval.

### F5 — S3 storage and Config retention are separate evidence boundaries

AWS explicitly states that AWS Config and S3/SNS have separate data stores and retention policies. citeturn0search2

Therefore a surviving S3 artifact may outlive the corresponding Config-native history, while the reverse can also occur.

This is useful for evidence preservation but means the retention contract must identify the exact evidence layer being relied upon.

### F6 — Completeness requires an expected-set argument

To turn “no artifact found” into a bounded negative fact, the model needs more than object listing.

Minimum expected-set proof:

1. exact AWS Config resource type/Region/account scope;
2. recorder scope and recording interval;
3. documented delivery-file semantics;
4. delivery-channel status/coverage for the interval;
5. expected artifact naming/time partition semantics;
6. S3 object/version inventory covering the expected namespace;
7. S3 retention/deletion policy and authorization context;
8. CloudTrail object-level evidence where configured;
9. integrity/provenance of retrieved artifacts;
10. resource identity/incarnation binding.

Without an established expected set, “missing object” remains UNKNOWN.

### F7 — Object metadata/timestamps must not be promoted to causal or historical truth

An S3 object's storage metadata can establish facts about the stored artifact, but an object timestamp does not by itself prove the underlying AWS resource changed at that time, nor does it prove causal ordering against the originating Config event.

Therefore:

artifact_time -> artifact storage fact

artifact_time != resource lifecycle time

### F8 — The acquisition boundary remains open

Even a versioned, independently logged S3 history bucket only proves what was delivered and retained within its configured evidence boundary.

It cannot reconstruct resource history before Config recording/delivery began.

Therefore:

pre_Config/delivery interval -> retained independent evidence | UNKNOWN

covered recorded/delivered interval -> potentially bounded historical claim

## New distilled rule

Artifact provenance and historical completeness are separate dimensions.

provider-generated artifact identity + delivery evidence + expected-set coverage + retention/deletion evidence + optional independent object-event evidence + integrity
-> bounded artifact provenance/completeness claim

artifact missing + no expected-set/completeness proof
-> UNKNOWN

S3 VersionId, CloudTrail object events, and Config delivery notifications strengthen the evidence graph, but none independently becomes a universal completeness oracle.

## Anti-collapse rules

- S3 VersionId != resource incarnation ID;
- object key equality != same delivery event;
- object timestamp != resource event timestamp;
- versioned bucket != immutable forever;
- object present != complete artifact set;
- object absent != never delivered;
- CloudTrail object event absent != no object mutation unless coverage is proven;
- Config notification != complete retained notification history;
- S3 retention != Config retention;
- artifact provenance != resource lifecycle completeness.

## Exact next research direction

Investigate AWS Config configuration-history file semantics and ordering/partition behavior in enough detail to determine whether an expected artifact set can be formally enumerated for a bounded interval, including resource-type prefixes, delivery cadence, and whether missing files can ever be distinguished from “no change” without relying on undocumented assumptions.
