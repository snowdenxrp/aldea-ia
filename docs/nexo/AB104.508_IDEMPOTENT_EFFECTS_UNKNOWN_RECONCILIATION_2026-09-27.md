# AB104.508 — idempotent effects, UNKNOWN outcomes and reconciliation

## Evidence
AWS documents idempotency as a contract for safe retries using a unique client request identifier; repeated requests with the same identifier and parameters can return the prior result without repeating the action. It also requires parameter mismatch detection, and its Builders' Library notes that recording the idempotency token and mutating work must be atomic to avoid recording-without-effect or effect-without-record. citeturn0search0turn0search10 AWS further distinguishes the practical difficulty of guaranteeing exactly-once effects in distributed systems and recommends idempotency tokens for retries. citeturn0search5

## Nexo effect contract
The logical operation identity must be created before the first attempt and remain stable across retries, worker migration and crash recovery:

`OperationID = unique logical effect identity`

Bind it to:
`OperationID + CallerIdentity + OperationType + TargetIdentity + IntentDigest + DecisionDigest + AuthorityEpoch + FenceToken`

A retry with the same OperationID but different intent must be rejected as an idempotency-parameter mismatch, not treated as a new operation. This mirrors AWS's explicit mismatch handling. citeturn0search1turn0search10

## Durable effect ledger
Candidate states:
`PREPARED → DISPATCHED → COMMITTED → CONFIRMED`
with explicit terminal/exception states:
`REJECTED`, `QUARANTINED`, `UNKNOWN`, `COMPENSATION_REQUIRED`.

The ledger must durably preserve the operation identity, intent/decision digest, target, fence, attempt metadata, and last known outcome. A crash must not create a second logical operation merely because the previous response was lost.

## UNKNOWN is not failure and not success
After timeout/crash, the system may not know whether the external effect happened:
`TIMEOUT_AFTER_DISPATCH => UNKNOWN`

It must not infer:
`UNKNOWN => RETRY_AS_NEW`
`UNKNOWN => SUCCESS`
`UNKNOWN => NOT_EXECUTED`

Reconciliation must query authoritative target state or an equivalent durable effect record. If the target supports the same OperationID/idempotency key, retry may safely converge to the existing operation. If it does not, reconciliation must remain conservative and may require quarantine/manual recovery.

## Atomicity boundary
The local effect ledger and an external side effect generally cannot share one ordinary ACID transaction. Therefore Nexo must not claim a universal exactly-once distributed transaction. The safe contract is instead:
`durable intent + at-least-once dispatch + idempotent receiver OR authoritative reconciliation`.

If the receiver cannot provide idempotency and cannot expose authoritative reconciliation, the strongest safe state may remain `UNKNOWN` rather than pretending success.

## Revocation interaction
A retry after revocation is not automatically authorized because the original OperationID was authorized earlier. Before any new external attempt, revalidate current authority/fence/revocation state. However, if reconciliation proves that the original external effect already committed before revocation, the system must not claim that revocation retroactively undid that effect. It must enter the explicit post-commit/revocation handling path.

`OLD_DECISION != CURRENT_RETRY_AUTHORITY`
`REVOCATION != RETROACTIVE_UNDO`
`RECONCILIATION != NEW_AUTHORIZATION`

## Crash matrix
- crash before durable intent → no externally authorized operation exists;
- intent durable, dispatch absent → safe to dispatch/reconcile using same OperationID after current authorization check;
- dispatch attempted, response lost → `UNKNOWN`, reconcile before deciding next action;
- external commit known, local ACK lost → recover `COMMITTED/CONFIRMED` from target evidence;
- revocation before retry → no new dispatch without fresh authorization;
- revocation after external commit → preserve historical commit and enter explicit revocation/compensation policy;
- same OperationID + changed intent → reject mismatch;
- duplicate delivery with same valid OperationID → receiver/ledger must collapse it to one logical effect where supported.

## Invariants
- `OPERATION_ID_IS_STABLE_ACROSS_RETRIES`
- `SAME_OPERATION_ID + DIFFERENT_INTENT => REJECT`
- `UNKNOWN != SUCCESS`
- `UNKNOWN != NOT_EXECUTED`
- `UNKNOWN != NEW_OPERATION`
- `RECONCILIATION != NEW_AUTHORIZATION`
- `RETRY_REQUIRES_CURRENT_AUTHORITY`
- `EXTERNAL_COMMIT_BEFORE_REVOCATION != RETROACTIVE_UNDO`
- `NO_IDEMPOTENT_RECEIVER + NO_RECONCILIATION => CONSERVATIVE_UNKNOWN`
- `LOCAL_LEDGER != DISTRIBUTED_TRANSACTION`
- `EXACTLY_ONCE_MUST_BE_SCOPED_TO_A_DEFINED_EFFECT_CONTRACT`

## Status
Research complete. No implementation or formal verification performed. The remaining gap is defining the precise reconciliation contract for targets that expose partial state, delayed visibility, or no durable operation identity.
