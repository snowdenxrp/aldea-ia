# Nexo AB104.422 — Failure-Domain/Quorum Specification Common-Mode Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY

## Research question

How can Nexo obtain assurance that the protected failure-domain/quorum specification is itself correct, complete, unambiguous, and appropriate to the claimed property, rather than merely proving that implementations consistently follow the same specification?

## Evidence

NIST SP 800-160 distinguishes validated stakeholder requirements from system requirements and states that system requirements should be clear, concise, and verifiable; validation asks whether the system is effective for the stated mission, while verification checks implementation against requirements. citeturn0search35turn0search4

NASA's requirements-validation guidance explicitly checks clarity, absence of ambiguity, completeness, explicit assumptions, and whether important requirement areas were omitted. citeturn0search2

NASA IV&V distinguishes verification ("building the product right") from validation ("building the right product") and treats technical, managerial, and financial independence as separate dimensions of independence. citeturn0search0turn0search34

NASA's IV&V requirements further call for requirements/design relationships to be traceable, consistent, complete, accurate, and testable, and require validation of interfaces and security/safety behavior. citeturn0search1

## Core finding

A perfectly implemented quorum algorithm can still be unsafe if its specification is wrong.

Therefore:

SPECIFICATION_CORRECTNESS != IMPLEMENTATION_CORRECTNESS

and:

TWO_ANALYZERS_AGREEING_WITH_ONE_SPEC != SPECIFICATION_VALIDATION

## What must be specified

For a claim that a witness quorum protects property P, the specification must define at minimum:

- protected property;
- system boundary;
- failure model;
- adversary model;
- witness semantics;
- dependency semantics;
- failure-domain semantics;
- quorum rule;
- evidence freshness assumptions;
- trust-root assumptions;
- recovery assumptions;
- partition assumptions;
- Byzantine behavior assumptions;
- unknown-state semantics;
- external-effect implications;
- scope and exclusions.

An omitted assumption is not equivalent to a safe assumption.

## Specification attack classes

### S1 — ambiguous quorum semantics

Terms such as "independent", "fresh", "current", "trusted", "available", or "majority" can have multiple meanings.

Candidate:

AMBIGUOUS_SECURITY_TERM => SPECIFICATION_NOT_VERIFIABLE

### S2 — hidden failure assumption

Example:

The specification assumes two witnesses are independent but omits a shared policy provider.

Then:

DECLARED_INDEPENDENCE != ACTUAL_FAILURE_INDEPENDENCE

### S3 — incomplete failure model

The specification models crash failures but the claimed property depends on Byzantine equivocation.

Then the proof scope is insufficient.

Candidate:

UNMODELED_FAILURE_CLASS => CLAIM_SCOPE_INCOMPLETE

### S4 — wrong boundary

A quorum may prove that witnesses agree about a state while the claimed property requires proving the external resource actually has that state.

Then:

WITNESS_AGREEMENT != EXTERNAL_WORLD_TRUTH

### S5 — omitted recovery model

A specification can be correct during normal operation but unsafe after restore/failover.

Candidate:

NORMAL_MODE_SPECIFICATION != RECOVERY_SPECIFICATION

### S6 — omitted unknown semantics

If unavailable or contradictory evidence is silently treated as false/valid, the specification can create fail-open behavior.

Candidate:

UNKNOWN_MUST_HAVE_EXPLICIT_SEMANTICS

## Property-first specification

Candidate protected chain:

MISSION/STAKEHOLDER NEED
→ SECURITY/SAFETY PROPERTY
→ THREAT/FAILURE MODEL
→ CLAIM CONTRACT
→ QUORUM SPECIFICATION
→ ANALYSIS MODEL
→ IMPLEMENTATION

This prevents the quorum rule from becoming an unexplained architectural primitive.

## Counterexample-driven specification review

Before implementation, attempt to construct a system satisfying the specification while violating the intended property.

For each proposed rule:

SPECIFICATION
→ ADVERSARIAL MODEL
→ COUNTEREXAMPLE SEARCH
→ REPAIR OR CONFIRM SCOPE

A single valid counterexample can show that the specification is insufficient for the claimed property.

## Reference semantics

Create a deliberately simple executable/formal reference model for bounded cases.

The reference model should answer:

- when quorum is satisfied;
- which failures invalidate it;
- what UNKNOWN means;
- what partition means;
- what recovery means;
- which dependencies count as shared failure domains.

The reference model is evidence, not authority.

## Independent semantic review

Independent review should not merely re-read implementation code.

Reviewers should challenge:

- whether the property is the correct one;
- whether the boundary is correct;
- whether assumptions are complete;
- whether failure classes are complete;
- whether the quorum rule actually implies the intended property;
- whether recovery changes the proof;
- whether external effects exceed the modeled boundary.

NASA IV&V explicitly treats requirements quality and traceability as independent assurance concerns, not merely code correctness. citeturn0search1turn0search10

## Completeness cannot be proven by a checklist alone

A checklist can show that categories were considered.

It cannot prove that no relevant category was omitted.

Therefore:

CHECKLIST_COMPLETE != SEMANTICALLY_COMPLETE

Candidate additional evidence:

- threat-model challenge;
- independent domain review;
- counterexample search;
- model checking for bounded cases;
- differential reference models;
- mutation testing;
- assumption audit;
- adversarial scenario generation.

## Specification mutation testing

Mutate the specification itself:

- remove a dependency;
- weaken quorum threshold;
- change UNKNOWN to FALSE;
- allow stale witnesses;
- remove recovery constraints;
- remove external-resource binding;
- collapse two failure domains;
- remove predecessor continuity;
- permit fail-open under partition.

Then ask whether the validation stack detects the semantic weakening.

If not:

SPECIFICATION_ASSURANCE_GAP

## Specification differentialization

Two independent semantic models can be useful:

MODEL_A(property, failure model)
MODEL_B(property, failure model)

Compare:

- valid states;
- invalid states;
- minimal counterexamples;
- quorum boundaries;
- unknown states;
- recovery states.

Disagreement should trigger semantic review, not automatic selection.

## Common-mode specification attack

The strongest common-mode attack is not implementation sharing.

It is:

WRONG_SPEC
→ MODEL_A follows it
→ MODEL_B follows it
→ ANALYZERS AGREE
→ Z1 trusts false premise

Therefore specification assurance must be upstream of analyzer differential assurance.

## Mission validation versus requirement verification

NIST and NASA distinguish whether requirements were correctly implemented from whether the requirements themselves address the intended mission/need. citeturn0search35turn0search6

For Nexo:

VERIFIED_QUORUM_RULE != VALIDATED_SECURITY_PROPERTY

Both are required for a strong claim.
