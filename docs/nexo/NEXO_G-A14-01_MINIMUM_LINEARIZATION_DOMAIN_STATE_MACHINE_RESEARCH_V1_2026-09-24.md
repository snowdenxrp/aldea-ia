No SANY/TLC proof. Architecture-build gate remains closed.\n\n## 1. Question\nWhat is the smallest state that must live inside the authoritative linearization domain so Nexo can safely implement authority, fencing, STOP, operation/effect identity, currentness acceptance, VersionSet/context, recovery, and capability admission while leaving hardware anchors and external providers as non-atomic participants?\n\n## 2. It explicitly addresses crash-after-commit-before-response with stable client serial numbers and stored results, reinforcing that durable logical identity belongs to the authoritative state machine rather than the caller response. Raft also requires the replicated state machines to process the same ordered command sequence. Central result\nThe smallest defensible linearization domain is NOT all Nexo state.\n\nIt is the minimum protected state required to answer atomically and with current authoritative context:\n1. Who is allowed?\n2. Which exact effect is being authorized?\n3. Under which fence/epoch?\n4. Is STOP blocking it?\n5. Under which safety/version context?\n6. Is the protected state current enough to authorize?\n7. What unresolved effect identity must survive ambiguity?\n8. Which recovery/decommission lineage owns the state?\n\n## 4. Candidate minimum protected state\nIdentity/Lifecycle: identity_id, lifecycle_epoch, lifecycle_state, decommission closure/anti-resurrection state.\nAuthority: authority_epoch, authority_state, authority_scope/domain.\nEffect identity: operation_id, effect_key, target_fingerprint, parameter/payload fingerprint, effect class, effect lifecycle.\nFence/coordination: owner identity, fence/generation, relevant coordination epoch.\nSTOP: STOP epoch/state for the affected safety domain and blocking phase.\nSafety context: VersionSet, policy baseline identity, invariant baseline identity, footprint/dependency context epoch.\nCurrentness: accepted currentness lineage/witness reference, currentness validity state, recovery lineage.\nRecovery: recovery epoch, recovery owner/fence, quarantine/release state, unresolved reconciliation ownership.\nProtected history floor: durable transition revision plus critical unresolved-effect summary and compaction/recovery floor sufficient to prevent resurrection or false resolution.\n\n## 5. What does not need to be inside by default\nModel state, planner internals, ordinary memory, embeddings, UI state, telemetry aggregates, optimization metrics, non-authoritative caches, ordinary analytics, full evidence payloads, complete dependency graphs, provider response bodies, raw TPM/NV data, and external-world state.\n\nThe core may instead store protected references, digests, validity epochs and summaries.\n\n## 6. Object versus predicate\nThe core does not need to own every evidence object. It needs the authoritative result required for admission, such as EvidenceEligible(claim, context), or an equivalent context-bound validity record.\n\nLikewise, the core need not own the entire dependency graph if it safely consumes a protected, context-bound closure result whose invalidation rules are enforced. This keeps the linearization domain small while preserving safety semantics.\n\n## 7. Minimum atomic transition\nCandidate canonical transition: PROTECTED_ADMISSION.\n\nInputs: operation_id, effect_key, target/parameter fingerprints, requested capability/effect class, authority basis, presented context, currentness evidence reference, requested fence/owner, recovery state.\n\nAtomic decision: VALIDATE_ALL, then either REJECT/HOLD/QUARANTINE or COMMIT_ADMISSION.\n\nCOMMIT_ADMISSION must atomically establish at least effect identity binding, current authority epoch, current fence, STOP non-blocking relation, VersionSet/context binding, accepted currentness relation, lifecycle/recovery ownership, and durable admission identity.\n\n## 8. Capability issuance\nCapability issuance need not be physically inside the same transaction if the protocol provides a safe refinement.\n\nCandidate flow: PROTECTED_ADMISSION_COMMITTED → capability materialization → EFFECT_BOUNDARY_REVALIDATE.\n\nThe capability is a derived artifact containing enough context to be rejected when stale. If issuance is ambiguous, the protected admission identity survives and capability state is reconciled.\n\nTherefore the minimum linearization domain does not necessarily include the capability table itself.\n\n## 9. Hardware currentness anchor\nThe hardware anchor remains a participant rather than a magic extension of the state machine.\n\nThe protected core stores the authoritative relation between state lineage and accepted anchor lineage/value. The concrete protocol must prove this relation.\n\nIf the anchor is unavailable, reset, ahead without state, behind the state, or ambiguous, the affected currentness becomes UNKNOWN and protected release is blocked.\n\n## 10. External provider\nProvider state remains outside the linearization domain.\n\nThe core linearizes intent identity, authority, fence, admission and retry identity. It does not linearize the external world's actual effect.\n\nProvider reconciliation remains INTENT → ATTEMPT → UNKNOWN/OUTCOME → OBSERVATION → RECONCILIATION → VERIFIED_OUTCOME.\n\nLocal admission commit is never a substitute for world-truth evidence.\n\n## 11. Why operation/effect identity must be inside\nCounterexample: Operation A is admitted, an external attempt occurs, the caller crashes, the result is UNKNOWN, recovery creates Operation B, and B is treated as unrelated. This permits duplicate effect or erasure of unresolved state.\n\nTherefore operation/effect identity must be protected and durable.\n\n## 12. Why STOP must be inside\nIf STOP is outside the linearization domain, admission can read STOP=clear, STOP can be asserted elsewhere, and the admission can commit without a defined ordering. The relevant STOP epoch/blocking relation therefore participates in the protected ordering domain.\n\n## 13. Why fence must be inside\nIf fencing is external, actor A can hold fence 10 while actor B advances to 11 and A commits with stale local state. The authoritative fence/epoch comparison must therefore be inside the protected transition.\n\n## 14. Why VersionSet/context binding must be inside\nIf VersionSet is checked only before entering the store, V1 admission can race V2 activation and issue an old-context capability. The protected transition must bind the accepted context to admission identity.\n\n## 15. Why full evidence does not need to be inside\nEvidence can be large and externally generated. The core needs claim/effect identity, evidence validity state, context fingerprint/version, invalidation epoch or dependency summary, and a reference sufficient for retrieval/verification.\n\nThis is a candidate reduction, not yet proof that every evidence class can be externalized.\n\n## 16. Conflict-domain implication\nThe linearization domain cannot be chosen merely by storage convenience. It must contain every protected state participating in an invariant the transition claims to preserve.\n\nThe correct unit is a PROTECTED CONFLICT DOMAIN, not a database table or an effect key.\n\nIf two effects share protected capacity or an invariant, their relevant reservation/admission state must share one coordination domain or use a proven cross-domain protocol.\n\n## 17. Candidate semantic record\nProtectedAdmissionRecord candidate fields:\n- identity/lifecycle reference\n- operation_id\n- effect_key\n- target/parameter fingerprint\n- effect class\n- authority epoch/scope\n- fence/owner/generation\n- STOP epoch/relation\n- VersionSet/context fingerprint\n- footprint epoch/result\n- currentness relation reference\n- recovery epoch/owner\n- external effect lifecycle\n- critical evidence validity summary\n- protected transition revision\n- compaction/recovery floor\n\nThis is a semantic record, not yet a concrete schema.\n\n## 18. Adversarial tests\nT1 Old snapshot: all local replicas restored together. Expected: internal agreement is insufficient to infer currentness.\nT2 Stale capability: capability syntax is correct but authority/fence is old. Expected: effect boundary rejects.\nT3 STOP race: STOP and admission are concurrent. Expected: protected ordering determines their relation; if ordering cannot be established, admission remains unresolved/blocked.\nT4 Version race: V1 admission races V2 activation. Expected: protected context binding prevents silent cross-version admission.\nT5 UNKNOWN retry: external result is unknown. Expected: same operation/effect identity survives.\nT6 Compaction: pending UNKNOWN is old. Expected: age alone cannot delete it.\nT7 Recovery: recovery owner starts with old state. Expected: old fence/authority cannot complete admission.\nT8 Cross-shard effect: two effects touch shared protected capacity. Expected: independent local commits are prohibited unless disjointness is proven.\n\n## 19. Code-study result\nThe repository's current src/nexo/dependency_closure_evaluator.py reinforces this boundary. The evaluator is explicitly non-authoritative and cannot grant authority or execute effects. It computes deterministic fingerprints, dependency closure, bad dependency states and conservative assurance ceilings.\n\nThat is the correct placement for analysis machinery: it produces inputs to protected admission; it does not become admission authority.\n\nThe code also illustrates why too much should not be placed inside the core: recursive graph traversal and correlation analysis belong in analysis/validation layers unless a specific protected transition requires their mutation.\n\n## 20. Negative result\nA replicated state machine alone does not solve G-A14-01.\n\nIt solves authoritative ordering inside its domain, durable logical identity, atomic protected-state transitions and failover consistency under its assumed failure model.\n\nIt does not automatically solve hardware-anchor continuity, provider-world truth, compromised host/kernel, device effects, external cancellation, Byzantine participants or deployment closure.\n\n## 21. Candidate minimum boundary\nCurrent strongest candidate:\nLINEARIZATION DOMAIN = Identity/Lifecycle + Authority + Effect Identity + Fence + STOP relation + Safety Context + Accepted Currentness relation + Recovery ownership + Critical unresolved-effect/history floor.\n\nEverything else is externalized only if its protected validity relation is represented and invalidation is enforced.\n\n## 22. Mini-audit\nThe minimum-domain hypothesis is substantially strengthened.\n\nNo evidence supports putting the entire system inside the state machine.\nNo evidence supports shrinking the domain below authority + effect identity + fence + STOP relation + context + currentness relation + recovery/history without introducing a race or resurrection path.\n\nImportant qualification: this is a semantic minimum candidate, not a mathematically proven minimum.\n\nNo technology is selected.\n\n## 23.
