## Research question
Can a global authority epoch safely coexist with per-resource fencing for multi-resource effects, and what composition is required without creating false acceptance or unnecessary invalidation?

## Fresh research
Google's Chubby was designed as a coarse-grained coordination/locking service and uses sequencer state associated with lock acquisition; its design emphasizes reliable coordination rather than making a single coarse lock equivalent to every downstream resource's acceptance state. citeturn0search0turn0search1

Hierarchical Chubby research explores separating a master-level coordination layer from worker clusters that own subsets of locks. The important architectural lesson for Nexo is that hierarchical coordination can scale scope, but moving/resharding ownership requires explicit state transfer and preservation of lock semantics. A hierarchy therefore does not remove the need to define the authoritative boundary and state continuity for each protected resource. citeturn0search25

## Candidate model
Use two logically distinct layers:

1. GLOBAL_AUTHORITY_EPOCH (GAE): current authority generation for a protected authority domain.
2. RESOURCE_FENCE (RF): monotonically ordered within the exact protected resource/resource-incarnation scope and validated by that resource.

Candidate request envelope:
AUTHORITY_DOMAIN + GLOBAL_AUTHORITY_EPOCH + RESOURCE_ID + RESOURCE_INCARNATION + RESOURCE_FENCE + EFFECT_ID + OPERATION_ID

GAE answers which authority generation authorized the work. RF answers which ownership/fence generation is current for the concrete resource. Resource incarnation identifies the concrete lifecycle instance. EffectID identifies the logical external effect. OperationID identifies the protected operation.

## Why one global fence is insufficient
A single global fence could order all protected operations, but it can unnecessarily invalidate unrelated resources and may be impractical for heterogeneous providers. Conversely, only per-resource fences can miss a global authority event if a resource does not receive or apply the new authority generation.

Therefore the two layers serve different properties and must not be conflated.

## Multi-resource effect matrix
Assume an effect touches R1 and R2.

| Situation | GAE | R1 fence | R2 fence | Candidate outcome |
|---|---|---|---|---|
| All current | current | current | current | Candidate admission |
| GAE stale, both resource fences current | stale | current | current | REJECT/HOLD |
| GAE current, R1 stale | current | stale | current | REJECT/HOLD |
| GAE current, R2 stale | current | current | stale | REJECT/HOLD |
| GAE current, R1 accepts then R2 rejects | current | accepted | rejected | PARTIAL_COMMIT / reconciliation |
| GAE rolls over after R1 acceptance but before R2 | new | accepted under old | pending | R2 requires current GAE/fence; R1 is not retroactively invalidated |
| Both resources accept under same GAE but different RF values | same | RF1 | RF2 | Potentially valid only if each independently validates RF |
| One resource lacks durable fence state | current | durable | volatile/reset | Strict stale-effect claim unavailable for that resource |
| Resource replaced during operation | current | old incarnation | new incarnation | Old effect must not silently target new incarnation |

## Composition rule
Candidate admission is conjunctive:
ADMISSIBLE = GAE_current AND RF1_current AND RF2_current AND incarnation1_current AND incarnation2_current AND target_preconditions AND effect_contract

But this does not create atomic external commit.

If R1 accepts and R2 does not, the partial result must be represented explicitly. It cannot infer global success merely because the admission predicate was true before the first external attempt.

CONTROL_ATOMICITY != MULTI_RESOURCE_EFFECT_ATOMICITY
ALL_RESOURCES_ADMISSIBLE != ALL_RESOURCES_COMMITTED

## Hierarchical authority/fence model
Candidate hierarchy:
AUTHORITY_DOMAIN
→ GLOBAL_AUTHORITY_EPOCH
→ RESOURCE_GROUP / PROVIDER
→ RESOURCE_INCARNATION
→ RESOURCE_FENCE
→ EFFECT_ID

The hierarchy is metadata and scope unless each boundary actually enforces the relevant predicate.

A parent epoch rollover can require all child operations to re-admit. A child resource fence can reject stale work even when the parent authority generation has not changed.

Non-equivalence:
- Parent GAE does not replace child RF.
- Child RF does not replace parent authority validation.
- Provider-level ordering does not prove cross-provider atomicity.
- A new EffectID does not refresh stale authority.
- A fresh RF does not authorize an operation if GAE/scope is stale.

## Cross-resource acceptance ordering
For R1/R2, each resource independently decides acceptance when it has atomic fence validation. There is no implied single external linearization point across them.

"R1 accepted before R2" is a partial order unless a separate coordination protocol establishes stronger ordering. If either participant's outcome is unknown, the global effect remains at least PARTIAL_COMMIT/UNKNOWN until reconciliation resolves the required property.

## Fence issuance and transfer
A resource fence should be issued by an authority capable of preserving monotonicity for that fence scope. Rebalancing or moving resource ownership cannot reset the fence sequence without an explicit new resource incarnation or equivalent proof that old requests are impossible.

Ownership transfer is itself protected state:
- old owner fenced out;
- new owner receives a higher generation;
- resource-side acceptance preserves ordering;
- recovery/failover preserves the high-water mark.

The Chubby and hierarchical-Chubby literature supports treating ownership transfer and lock state as explicit coordination state rather than assuming a local cache or worker restart preserves safety. citeturn0search1turn0search25

## Candidate invariants
- GLOBAL_AUTHORITY_EPOCH != RESOURCE_FENCE
- RESOURCE_FENCE_MUST_BE_VALIDATED_AT_RESOURCE
- GLOBAL_AUTHORITY_MUST_BE_CURRENT_AT_ADMISSION
- RESOURCE_INCARNATION_MUST_MATCH_EFFECT_TARGET
- MULTI_RESOURCE_ADMISSION != MULTI_RESOURCE_COMMIT
- PARTIAL_COMMIT_MUST_BE_EXPLICIT
- UNKNOWN_PARTICIPANT_PREVENTS_UNQUALIFIED_GLOBAL_SUCCESS
- FENCE_HIGH_WATER_MARK_MUST_SURVIVE_OWNERSHIP_TRANSFER
- FENCE_HIGH_WATER_MARK_MUST_SURVIVE_RESOURCE_FAILOVER
- NEW_EFFECT_ID_DOES_NOT_REFRESH_STALE_AUTHORITY
