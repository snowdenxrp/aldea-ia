# AB105.061R — CloudFormation Hooks identity bridge audit

Date: 2026-09-30
Chain: AB105.060R -> AB105.061R

## Research question

Do CloudFormation Hook identifiers provide a deterministic bridge that strengthens operation/resource reconstruction?

## Primary evidence

AWS documents OperationEvent with OperationId, StackId, LogicalResourceId, PhysicalResourceId, HookType, HookInvocationPoint, HookStatus, and HookFailureMode. A Hook invocation error is represented as an event type within the operation event model. citeturn0search0turn0search1

AWS also documents HookInvocationId as a unique 36-character identifier in StackEvent data. Stack events retain ClientRequestToken, and AWS states that all events triggered by a given stack operation receive the same client request token. citeturn0search3

AWS provides a separate Hook-results surface. The Invocation Summary covers Hook invocations for the past 90 days, and individual results can be retrieved by HookResultId. The result includes target identity, action, invocation time, status, and annotations. citeturn0search5

For Guard Hooks, AWS documents ChangeSetId when a CloudFormation change set caused the invocation, and TargetLogicalId / ResourceLogicalID for the evaluated target. citeturn0search9

## Findings

### 1. HookInvocationId is a real invocation identity

HookInvocationId is explicitly documented as a unique identifier for the Hook invocation.

Therefore:

HookInvocationId equality = EXACT Hook invocation identity.

This is stronger than timestamp proximity.

### 2. HookInvocationId does not by itself identify the CloudFormation operation

The Hook event also carries OperationId in the OperationEvent model, while StackEvent carries HookInvocationId and ClientRequestToken. The evidence establishes separate identifiers, not universal equality between them.

Therefore:

HookInvocationId -> OperationId = BOUNDED only when both occur in the same event record.

HookInvocationId -> OperationId from independent records without a documented bridge = UNKNOWN.

### 3. ClientRequestToken provides an operation grouping bridge in StackEvents

AWS explicitly states that all StackEvents generated by a given stack operation share its ClientRequestToken. This permits bounded grouping of StackEvents belonging to that operation. citeturn0search3

This does not mean ClientRequestToken is a universal identity for a Hook invocation.

Therefore:

ClientRequestToken -> same stack-operation event group = BOUNDED/PROVIDER-DOCUMENTED.

ClientRequestToken -> HookInvocationId = UNKNOWN unless the same event record supplies both.

### 4. ChangeSetId can strengthen Hook provenance

AWS documents ChangeSetId in Guard Hook results when the invocation was caused by an executed change set. This is useful as a plan/execution bridge.

However, ChangeSetId does not by itself prove that a resource replacement or physical mutation completed.

Therefore:

ChangeSetId -> Hook invocation provenance = BOUNDED when present.

ChangeSetId -> physical resource transition = UNKNOWN without resource lifecycle evidence.

### 5. HookResultId is an observation identity, not a physical-resource identity

A HookResultId identifies the stored Hook result. It does not establish that the target resource was created, updated, deleted, replaced, or retained.

Therefore:

HookResultId -> Hook result = EXACT.

HookResultId -> resource incarnation = UNKNOWN unless independently bound through target and lifecycle evidence.

### 6. WARN and FAIL have different causal implications

AWS documents that FAIL stops provisioning and can roll back the stack, while WARN allows the operation to continue. citeturn0search8

Thus a Hook failure is not equivalent to physical non-creation in all cases.

A FAIL result is evidence of a blocking validation outcome, but final physical state still requires CloudFormation lifecycle evidence.

A WARN result explicitly cannot be interpreted as a mutation denial.

### 7. Hook history has its own retention boundary

The Hook Invocation Summary is documented as covering the past 90 days. This is a retention statement for that Hook-results surface, not a universal 90-day retention guarantee for CloudFormation OperationEvents or StackEvents. citeturn0search5

Therefore:

Hook-result-history-window = 90 days for the documented Invocation Summary surface.

Universal CloudFormation-event-retention = NOT ESTABLISHED.

### 8. Hooks add evidence; they do not replace the lifecycle ledger

The strongest reconstruction pattern is:

ChangeSetId
  -> Hook invocation
  -> OperationId / ClientRequestToken when co-recorded
  -> StackEvent resource lifecycle
  -> PhysicalResourceId

Each edge must be supported by an actual shared field or provider-documented semantic.

No edge may be inferred solely from time ordering.

## Distilled rule

Hook identifiers strengthen reconstruction only through explicit co-recorded fields or documented provider semantics.

HookInvocationId is an invocation identity, not a resource identity.

HookResultId is an evidence-record identity, not a resource-incarnation identity.

ChangeSetId strengthens provenance but does not prove execution completion or physical mutation.

Hook FAIL/WARN semantics affect the possible operation graph but do not replace resource lifecycle evidence.

## Anti-collapse rules

- HookInvocationId != OperationId.
- HookResultId != PhysicalResourceId.
- ChangeSetId != completed resource mutation.
- Hook failure != universal no-mutation proof.
- WARN != blocked operation.
- 90-day Hook invocation history != universal CloudFormation event retention.
- Timestamp proximity != identity.
- Hook evidence != replacement for StackEvents/OperationEvents.
