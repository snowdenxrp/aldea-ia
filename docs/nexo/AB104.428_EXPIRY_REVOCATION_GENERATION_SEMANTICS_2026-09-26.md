# Nexo AB104.428 — Expiry, Deadlines, Revocation and Generation Semantics

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity: AB104.427 → AB104.428
Implementation: NOT PERFORMED

## Research question

When can time-based expiration safely be replaced by generation-based invalidation, and where are the two semantics fundamentally non-equivalent?

## Evidence

RFC 7009 distinguishes token revocation from token lifetime and explicitly notes that revocation can become effective immediately while propagation delay may exist across servers. citeturn0search4

NIST SP 800-63B separately defines expiration and revocation/termination. It states that expiration makes an authenticator unusable after its expiry, while revocation removes the binding maintained by the CSP; it specifically calls out revocation as necessary for blocking offline use during the interval before expiration. citeturn0search7

AWS STS provides a concrete deployment example of time-bounded credentials: credentials become invalid after their expiration, while AWS also documents mechanisms for disabling/revoking session permissions before expiration. AWS notes that temporary credentials themselves have a specified lifetime and that permission changes can be used to achieve revocation effects. citeturn0search1turn0search3

## Core finding

Expiration and revocation answer different questions.

EXPIRATION:
“Has the credential/effect reached the end of its permitted temporal lifetime?”

REVOCATION:
“Has the authority binding been invalidated before its nominal lifetime?”

Therefore:

EXPIRATION != REVOCATION

and:

GENERATION_INVALIDATION != TEMPORAL_EXPIRY.

A generation mechanism can replace expiration only when the intended policy is actually state-based invalidation rather than elapsed-time validity.

## Semantic dimensions

### Expiration

Depends on:
- clock basis;
- issue time;
- expiry/deadline;
- clock uncertainty;
- evaluation point;
- allowed skew;
- provider time semantics.

### Revocation

Depends on:
- revocation event;
- current authority state;
- propagation/currentness semantics;
- generation or invalidation state;
- protected evaluation point.

### Generation invalidation

Depends on:
- current generation;
- credential/evidence binding;
- generation transition;
- authoritative state;
- final-gate validation.

No physical clock is inherently required.

## Where generation can replace expiry

Generation-based invalidation is a candidate replacement when the policy means:

“Once authority changes, artifacts from the previous authority must no longer be admitted.”

Example:

ARTIFACT bound to AUTHORITY_EPOCH=7.
Authority transitions to epoch 8.
Admission requires artifact_epoch == current_epoch.

The artifact becomes invalid because state changed, not because a number of seconds elapsed.

Candidate:

STATE_INVALIDATION_POLICY => GENERATION_CONTROL.

## Where generation cannot replace expiry

If the policy means:

“This credential may be used for at most 10 minutes regardless of whether authority state changes.”

A generation alone cannot establish elapsed duration.

Candidate:

ELAPSED_TIME_REQUIREMENT => TIME_SEMANTICS_REQUIRED.

Likewise:

“Do not admit after 17:00 UTC”

requires a time basis.

## Hybrid semantics

Many systems need both.

Example:

credential is valid while:

CURRENT_GENERATION == ISSUED_GENERATION
AND
CURRENT_TIME < EXPIRY.

This expresses state-based invalidation plus bounded temporal lifetime.

Candidate:

VALIDITY = STATE_VALIDITY ∧ TIME_VALIDITY.

Failure of either condition can reject admission.

## Revocation before expiry

VALID_AT_ISSUANCE does not imply VALID_AT_ADMISSION.

If authority is revoked before expiry, a final gate must use current authority state.

Therefore:

HISTORICALLY_VALID != CURRENTLY_AUTHORIZED.

## Expiry does not equal revocation

An expired credential may simply reach its normal end-of-life.

A revoked credential may become invalid while still temporally unexpired.

Therefore the state machine should preserve:

ACTIVE → EXPIRED

and independently:

ACTIVE → REVOKED.

Possible combined terminal status:

EXPIRED_AND_REVOKED.

Do not collapse these transitions.

## Propagation delay

RFC 7009 explicitly notes that revocation can have propagation delay across servers. citeturn0search4

Therefore:

REVOCATION_ISSUED != REVOCATION_OBSERVED_EVERYWHERE.

For Nexo, a security-critical distributed revocation claim needs an explicit currentness/fencing model.

Candidate:

REVOCATION_EFFECTIVE_FOR_ADMISSION

must be defined separately from:

REVOCATION_REQUESTED.

## Offline verification

Offline verification exposes a fundamental difference.

If a verifier has no access to current revocation state, generation-based revocation cannot be guaranteed current unless the artifact carries a mechanism that lets the verifier determine current state.

Time-based expiry can remain locally evaluable if trusted time is available.

However, time does not solve immediate revocation either.

Therefore:

OFFLINE + IMMEDIATE_REVOCATION_REQUIREMENT

creates a synchronization/currentness problem, not merely a timestamp problem.

## Credential lifetime versus authority lifetime

A credential can have:
- cryptographic validity;
- temporal validity;
- authorization scope;
- authority-generation binding.

These must remain distinct.

Signature validity does not prove CURRENT_AUTHORITY.
Expiration validity does not prove CURRENT_AUTHORITY.
Generation equality can establish current generation binding, but does not establish an elapsed-time requirement.

## Deadline versus revocation

Deadline:
“Operation must be admitted before T.”

Revocation:
“Operation must not be admitted after authority transition R.”

They can occur independently.

Timeline:

T0 issue
T1 revocation
T2 deadline
T3 request

At T3 both checks may fail, but for different reasons.

A model collapsing them into one INVALID state loses causal semantics needed for recovery and audit.

## Deadline and external effects

Even when admission deadline is enforced correctly:

DEADLINE_PASSED != EXTERNAL_NON_EXECUTION.

If an operation crossed the external attempt boundary before expiry, later local expiry does not erase that attempt.

The external-effect state machine from AB104.376 remains authoritative for outcome classification.

## Generation rollover

Generation values must not wrap into an indistinguishable old value.

Candidate requirement:

GENERATION_REUSE_WITHOUT_DISTINGUISHABLE_INCARNATION
=> POSSIBLE_REPLAY/STALENESS_FAILURE.

If storage restoration can roll generation state backward, continuity mechanisms from AB104.410–AB104.413 remain required.

## Monotonic generation versus time

A monotonic generation establishes protocol/state order.
It does not establish duration.

Thus:

g8 > g7

does not imply “10 minutes elapsed.”

Conversely:

10 minutes elapsed

does not imply authority generation changed.

## Expiry extension

Refreshing an artifact changes its validity semantics.

A new credential/lease should not silently inherit old authority without explicit binding.

Candidate:

RENEWAL => NEW_VALIDITY_BINDING

and, where authority semantics require:

RENEWAL => REVALIDATION.

## AWS example

AWS documents temporary credentials with explicit expiration, but also documents disabling/revoking permissions before expiration. This is concrete evidence that temporal lifetime and state-based revocation are complementary controls rather than interchangeable semantics. citeturn0search0turn0search3

## Candidate validity predicate

For a time-bound artifact:

ADMIT iff

AUTHENTIC
AND
SCOPE_VALID
AND
GENERATION_CURRENT
AND
NOT_REVOKED
AND
CURRENT_TIME_WITHIN_ALLOWED_WINDOW
AND
RESOURCE_INCARNATION_CURRENT
AND
ALL_REQUIRED_DEPENDENCIES_CURRENT.

Not every artifact needs every field; required context remains claim/effect-class specific.

## Candidate state model

ISSUED → ACTIVE

From ACTIVE:
→ EXPIRED
→ REVOKED
→ SUSPENDED
→ QUARANTINED

From EXPIRED:
→ RENEWED only through a new admission/issuance process.

From REVOKED:
→ no automatic resurrection.

Recovery requires a new authority/issuance decision where policy permits.

## Generation-based alternative

ISSUED_AT_GENERATION_G

Authority transition:

G → G+1.

Admission:

artifact_generation == current_generation.

This provides logical invalidation at the protected state boundary without requiring a synchronized wall clock.

But the protected generation store itself becomes authority-critical.

## Candidate choice rule

Use generation/state invalidation when the policy is about:
- authority change;
- revocation;
- configuration/policy generation;
- resource replacement;
- replay-state generation;
- recovery generation;
- dependency invalidation.

Use physical time when the policy is about:
- absolute deadlines;
- maximum elapsed duration;
- contractual time windows;
- certificate/credential expiration defined temporally;
- externally imposed temporal constraints.

Use both when the policy contains both classes of requirement.

## New invariants

- EXPIRATION != REVOCATION
- GENERATION_INVALIDATION != TEMPORAL_EXPIRY
- HISTORICALLY_VALID != CURRENTLY_AUTHORIZED
- REVOCATION_REQUESTED != REVOCATION_EFFECTIVE_FOR_ADMISSION
- REVOCATION_OBSERVED != REVOCATION_OBSERVED_EVERYWHERE
- ELAPSED_TIME_REQUIREMENT => TIME_SEMANTICS_REQUIRED
- GENERATION_ORDER != ELAPSED_DURATION
- ELAPSED_DURATION != AUTHORITY_CHANGE
- DEADLINE_PASSED != EXTERNAL_NON_EXECUTION
- GENERATION_REUSE_WITHOUT_DISTINGUISHABLE_INCARNATION => POSSIBLE_REPLAY/STALENESS_FAILURE
- RENEWAL => NEW_VALIDITY_BINDING
- EXPIRED != REVOKED
- SIGNATURE_VALIDITY != CURRENT_AUTHORITY
- TIME_VALIDITY != CURRENT_AUTHORITY
- GENERATION_EQUALITY != ELAPSED_TIME_PROOF
- REVOCATION_CURRENTNESS_REQUIRES_EXPLICIT_DISTRIBUTED_SEMANTICS

## Residuals

- Exact Nexo offline-revocation model remains open.
- Distributed revocation propagation/fencing semantics remain open.
- Credential/lease renewal semantics remain open.
- Generation rollover and continuity need formal treatment.
- Provider-specific expiry/revocation behavior remains resource-specific.
- Formal verification, implementation, fault injection, and deployment verification remain unperformed.
