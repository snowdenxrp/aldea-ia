# Nexo AB104.406 — Runtime Footprint Expansion and Effect Lineage Attack

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.405 → AB104.406
Implementation: NOT PERFORMED

## Research question

Can Nexo incorporate a protected participant discovered only after execution begins without silently expanding authority, and can operation/effect lineage remain trustworthy across queues, callbacks, retries, fan-out and provider boundaries?

## Evidence reviewed

AWS Step Functions documents Distributed Map as parent/child workflow execution with separate child histories, and documents retries/redrives that can reschedule failed branches or child workflows. A redrive can preserve the same execution ARN while representing a new recovery attempt; some Distributed Map recovery paths can create a new Map Run. This demonstrates that execution lineage has multiple layers and that retry/recovery cannot be represented by a single undifferentiated attempt field. citeturn0search0turn0search1turn0search3

W3C Trace Context standardizes propagation of request/trace context across services and provides a portable trace identifier, but explicitly describes tracing as correlation/observability. It does not by itself establish authorization, effect identity, or semantic equivalence of downstream operations. citeturn0search5

## Core finding

A runtime-discovered participant cannot simply be appended to an already-authorized protected operation.

Candidate rule:

`NEW_PROTECTED_PARTICIPANT_AFTER_FINAL_GATE
=> NO_SILENT_AUTHORITY_EXPANSION`

If the newly discovered participant is inside the protected property, Nexo needs one of:

1. pre-authorized bounded dynamic expansion whose rules and maximum footprint were already part of the protected admission;
2. a new admission boundary for the expanded effect; or
3. UNKNOWN/HOLD/REVALIDATE if neither is available.

Observed discovery after the fact is evidence about what happened; it is not retroactive authorization.

## Lineage must be layered

A single ID is insufficient for all semantics.

Candidate separation:

- `OPERATION_ID` — logical requested operation.
- `EFFECT_ID` — stable logical external effect identity where semantics support it.
- `ATTEMPT_ID` — one concrete execution/retry attempt.
- `PARENT_LINEAGE_ID` — causal parent.
- `PARTICIPANT_ID` — exact protected participant/resource incarnation.
- `EXECUTION_ID` — provider/workflow execution identity.
- `FENCE_GENERATION` — authorization/fencing generation.
- `RECOVERY_ATTEMPT_ID` — recovery/redrive lineage.

These identities must not be conflated.

## Why retries are adversarial

AWS shows that retry/redrive behavior can selectively rerun failed branches, while preserving successful work, and Distributed Map can have separate child executions and Map Run resources. Therefore:

`SAME_OPERATION_ID` does not imply `SAME_ATTEMPT`

and

`SAME_EXECUTION_ARN` does not imply `SAME_EXECUTION_ATTEMPT`.

Conversely, a new attempt does not automatically mean a new logical effect. Effect equivalence requires provider/path semantics that actually bind the attempts to the same protected effect.

## Async lineage boundary

For a queue/workflow boundary:

`PARENT_EFFECT -> ENQUEUED_MESSAGE -> CHILD_EXECUTION -> DOWNSTREAM_EFFECT`

The child must retain enough authenticated lineage to establish whether it is:

- continuation of the parent's authorized bounded effect;
- a new effect requiring independent admission; or
- an untrusted/ambiguous descendant requiring quarantine.

A trace identifier may help correlate these events, but correlation alone cannot prove authorization or effect equivalence. citeturn0search5

## Fan-out

Distributed execution can create many child workflows with independent histories. citeturn0search0

Candidate invariant:

`PARENT_AUTHORIZATION` cannot silently become unlimited child authority.

The parent contract must define a bounded participant rule, such as:

- allowed participant class;
- maximum expansion;
- resource/tenant boundary;
- exact capability profile;
- inheritance conditions;
- child identity binding;
- failure/reconciliation semantics.

If the child falls outside those constraints, the child requires a new admission boundary.

## Runtime discovery

Candidate states:

- `FOOTPRINT_PREDECLARED`
- `FOOTPRINT_BOUNDED_DYNAMIC`
- `FOOTPRINT_EXPANSION_PENDING`
- `FOOTPRINT_CLOSURE_CURRENT`
- `FOOTPRINT_EXPANSION_UNAUTHORIZED`
- `FOOTPRINT_UNKNOWN`
- `FOOTPRINT_QUARANTINED`

A runtime observer may transition the evidence state, but must not directly grant authority.

## Recovery / redrive

Recovery creates another adversarial boundary. AWS documents redrive behavior where unsuccessful portions can be rerun and, for Distributed Map, child executions may be redriven or new Map Runs started depending on failure conditions. citeturn0search1turn0search3

Therefore recovery must carry explicit lineage:

`ORIGINAL_OPERATION -> ORIGINAL_EFFECT -> RECOVERY_ATTEMPT -> CHILD_ATTEMPT`

and must revalidate:

- current authority epoch;
- recovery ownership;
- resource incarnation;
- effect-class requirements;
- footprint closure;
- provider capability;
- stable effect identity where required;
- prior participant outcomes.

## Candidate lineage record

`EFFECT_LINEAGE_CONTEXT`:

- OPERATION_ID
- EFFECT_ID
- ATTEMPT_ID
- PARENT_LINEAGE_ID
- RECOVERY_ATTEMPT_ID
- EXECUTION_ID
- PARTICIPANT_ID
- RESOURCE_INCARNATION
- AUTHORITY_EPOCH
- FENCE_GENERATION
- FOOTPRINT_CLOSURE_ROOT
- LINEAGE_SCHEMA_VERSION
- PROVIDER_ID / ADAPTER_ID
- CAPABILITY_GENERATION
- INHERITANCE_RULE_ID
- INVALIDATION_GENERATION

Only claim-required fields belong in the protected context.

## Main attacks

| Attack | Unsafe inference | Required response |
|---|---|---|
| late participant | discovered after admission => automatically authorized | new boundary or pre-bounded rule |
| trace propagation | same trace => same authorized effect | correlation is not authority |
| child workflow | parent authorized => child universally authorized | bounded inheritance |
| retry | same operation => same attempt | separate attempt identity |
| redrive | same execution ID => no new lineage | explicit recovery lineage |
| fan-out | parent scope => unlimited child scope | bounded participant rule |
| cross-provider hop | propagated ID => downstream trust | authenticate/bind each boundary |
| provider substitution | same logical operation => same semantics | capability/path revalidation |
| resource replacement | same logical resource => same participant | exact incarnation binding |
| hidden callback | callback observed => retroactively authorized | pre-bound or new admission |
| partial expansion | some children admitted => all children admitted | per-participant closure |
| lineage tampering | child-controlled parent ID | authenticated lineage, not caller assertion |

## Candidate invariants

- `RUNTIME_DISCOVERY_IS_NOT_RETROACTIVE_AUTHORIZATION`
- `NEW_PROTECTED_PARTICIPANT_REQUIRES_PREBOUND_RULE_OR_NEW_ADMISSION`
- `TRACE_CORRELATION_IS_NOT_AUTHORITY`
- `OPERATION_ID != ATTEMPT_ID`
- `EFFECT_ID != ATTEMPT_ID`
- `RECOVERY_ATTEMPT != ORIGINAL_ATTEMPT`
- `PARENT_AUTHORITY_CANNOT_EXPAND_UNBOUNDED`
- `CHILD_INHERITANCE_MUST_BE_AUTHENTICATED_AND_BOUND`
- `RESOURCE_INCARNATION_BINDS_PARTICIPANT_IDENTITY`
- `LINEAGE_INTEGRITY != LINEAGE_SEMANTIC_CORRECTNESS`
- `SAME_EXECUTION_ID != SAME_ATTEMPT`
- `OBSERVED_LINEAGE != AUTHORIZED_LINEAGE`

## Residuals / not proven

- Formal semantics for bounded dynamic footprint expansion.
- Exact inheritance model for parent-to-child authority.
- Formal equivalence relation for EffectID across retries/redrives.
- Cross-provider authenticated lineage without making every intermediary part of the TCB.
- Complete handling of malicious lineage propagation.
- Formal proof that runtime closure remains safe under concurrent expansion.
- Implementation/runtime correctness.
