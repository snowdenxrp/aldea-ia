# Nexo AB104.393 — Dependency Closure Algorithm and Dynamic Invalidation

Date: 2026-09-26
Status: RESEARCH / DESIGN CANDIDATE — NOT IMPLEMENTED

## 1. Research result
Derived a candidate machine-checkable dependency-closure procedure for safety-relevant evidence claims, plus dynamic invalidation when a required dependency changes or is compromised. This is not a formal proof or implementation.

RFC 9334 separates Attester, Verifier, and Relying Party roles and treats freshness as something that must be assessed against changing state; it explicitly notes races where state or appraisal policy changes after evidence generation. This supports explicit dependency and freshness binding rather than timeless trust in a prior result. https://www.rfc-editor.org/rfc/rfc9334.html

in-toto provides a useful provenance analogue: authorized steps and signed link metadata form a chain that can be automatically validated. It informs explicit provenance structure but does not prove Nexo safety properties. https://in-toto.io/docs/getting-started/

## 2. Candidate dependency graph
Node types: CLAIM, EVIDENCE, PRODUCER, VERIFIER, POLICY, TRUST_ROOT, ADAPTER, PROVIDER, RESOURCE, RESOURCE_INCARNATION, FAILOVER_DOMAIN, OBSERVER, RECONCILIATION_SOURCE, TIME_SOURCE, CONFIGURATION, KEY_MANAGEMENT, DEPLOYMENT_ARTIFACT, NETWORK_PATH, GATEWAY.

Edge types: DEPENDS_ON, DERIVED_FROM, VERIFIED_BY, APPRAISED_UNDER, BINDS_TO, PRODUCED_BY, OBSERVED_BY, INVALIDATED_BY.

Every safety-relevant claim must identify exact scope, version/generation, resource incarnation and policy context. Required dependencies must be transitively discoverable.

## 3. Candidate closure algorithm
Input: ClaimID, EvidenceSet, DependencyGraph, CurrentProtectedState, ClaimPolicy.

1. Authenticate and integrity-check the graph and referenced nodes.
2. Check claim scope, property, effect class and resource/incarnation binding.
3. Traverse from ClaimID over all claim-relevant dependency edges until closure reaches a fixed point.
4. Reject the closure as unresolved if a required node is missing, ambiguous, outside scope, or cannot be stably identified.
5. For each required dependency, compare evidence-bound version/generation/epoch/incarnation/configuration with current protected state where the claim requires currentness.
6. Evaluate explicit invalidation predicates: compromise, revocation, replacement, semantic drift, policy change, adapter change, failover-state change and expiry.
7. Emit a closure result containing dependency IDs, bound versions/epochs/incarnations, invalidation causes, freshness, independence/dependency domains, unresolved dependencies, contradictions and policy version.
8. Classify: VALIDATED_CURRENT, DEGRADED, UNKNOWN, QUARANTINED or HISTORICAL_ONLY.
9. Preserve the original evidence and prior evaluation; append a new evaluation record rather than rewriting history.

Candidate predicates:
Closure(C,t) = ReachableRequiredDependencies(C, Graph)
Current(C,t) = every required dependency is in scope, correctly identified, current under policy, valid and fresh enough.
Usable(C,t) = Current(C,t) AND policy satisfied AND no unresolved contradiction.

Currentness is claim-specific: some dependencies may require exact current state, others bounded freshness or historical binding.

## 4. Historical validity versus current usability
Distinguish CLAIM_VALID_AT(T0) from CLAIM_CURRENTLY_USABLE_AT(T1). Evidence correctly validated at T0 is not erased because a dependency changes at T1. Historical evidence and its evaluation remain retained; current usability is recomputed.

If a dependency compromise can affect an unresolved external outcome, the outcome may become UNKNOWN and require reconciliation. RFC 9334's freshness model likewise recognizes that state can change immediately after evidence generation.

## 5. Dynamic invalidation attacks
- Shared provider compromise: invalidate or downgrade every current claim whose required closure contains that provider.
- Policy-source change: a result bound to P1 cannot silently satisfy a claim requiring P2.
- Adapter change: capability evidence remains bound to the exact adapter/version/path.
- Resource replacement: old evidence cannot silently bind to a new resource incarnation.
- Failover fence-state change: durable-fence claims become UNKNOWN/QUARANTINED until revalidated.
- Gateway/downstream change: gateway evidence is invalid when a required downstream enforcement dependency changes.
- Time-source compromise: freshness claims lose their freshness basis unless independently established.
- Shared deployment artifact compromise: apparently independent observers may collapse into common-mode evidence.
- Omitted dependency: prior validation is not proof of completeness; revalidation is required.
- Dependency compromise during an external attempt: historical attempt remains, but confirmation may need downgrade to UNKNOWN pending reconciliation.

## 6. Propagation rule
Candidate rule: if required dependency d is invalidated at t, every currently usable claim whose required closure contains d is invalidated/downgraded unless policy proves d is outside that claim's relevant scope.

Propagation is transitive. A reverse index DependencyID -> ClaimIDs may accelerate lookup, but it is only an optimization; authoritative recomputation must use the protected graph and dependency state.

## 7. Anti-staleness binding
Candidate current-use record fields: CLAIM_ID, PROPERTY, SCOPE, RESOURCE_ID, RESOURCE_INCARNATION, EVIDENCE_SET_ID, DEPENDENCY_ROOT_ID, DEPENDENCY_GRAPH_VERSION, dependency epochs/generations, POLICY_VERSION, VERIFIER_ID, issued/freshness basis, expiry if applicable, invalidation references, independence/failure-domain classification and status.

Graph version is not dependency state version. An unchanged graph can represent changed provider/resource/policy state.

## 8. Failure rules
Never silently convert missing dependency into independence; stale dependency into current dependency; provider self-assertion into independent validation; evidence count into independence; timestamp freshness into unchanged state; successful verification into automatic authority; historical validity into current usability; verifier outage into successful revalidation; or missing telemetry into evidence of absence.

RFC 9334 explicitly separates Verifier appraisal from the Relying Party's application-specific decision and describes freshness as subject to state-change races. https://www.rfc-editor.org/rfc/rfc9334.html

## 9. Candidate invariants
- DEPENDENCY_CLOSURE_MUST_BE_TRANSITIVE
- DEPENDENCY_SCOPE_MUST_BE_EXPLICIT
- CLAIM_CURRENTNESS_REQUIRES_CURRENT_REQUIRED_DEPENDENCIES
- GRAPH_VERSION != DEPENDENCY_STATE_VERSION
- RESOURCE_INCARNATION_BINDS_EVIDENCE_SCOPE
- POLICY_VERSION_BINDS_APPRAISAL
- COMPROMISED_REQUIRED_DEPENDENCY_INVALIDATES_CURRENT_CLAIM
- HISTORICAL_EVIDENCE_IS_RETAINED
- HISTORICAL_VALIDITY != CURRENT_USABILITY
- INDEPENDENCE_IS_DERIVED_FROM_FAILURE_DOMAINS_NOT_COUNT
- COMMON_MODE_DEPENDENCY_COLLAPSES_INDEPENDENCE
- MISSING_DEPENDENCY != PROVEN_ABSENCE
- FRESHNESS_DOES_NOT_ELIMINATE_STATE_CHANGE_RACE
- VERIFIED != AUTOMATIC_AUTHORITY
- INVALIDATION_PROPAGATES_TRANSITIVELY
- NEW_EVIDENCE_FROM_COMPROMISED_DOMAIN_DOES_NOT_RESTORE_INDEPENDENCE

## 10. Closure status
This closes a candidate semantic mechanism for computing dependency closure and propagating current-state invalidation.

It does NOT prove graph completeness, algorithm correctness, Byzantine-resilient graph integrity, compromise-detection correctness, universal freshness semantics, formal safety, implementation correctness or deployment correctness.

Remaining research: exact edge semantics; cycles/conflicts; stale reverse indexes; atomic graph/state snapshots; E0-E5 coverage; compromise timing around evidence issuance/use; bounded dependency transitions; and revocation propagation without deleting history.
