# Nexo AB104.410 — Replay-State Rollback, Continuity Anchors and Fork Detection

Date: 2026-09-26
Status: RESEARCH / DESIGN ONLY
Continuity anchor: AB104.409 → AB104.410
Implementation: NOT PERFORMED

## Research question

Can Nexo prevent security-critical replay state from being silently reverted or forked after crash recovery, backup restore, replica divergence, disaster recovery, or authority-epoch rollover?

## Evidence reviewed

RFC 9162 provides a useful append-only-log model: Merkle consistency proofs can demonstrate that a later tree is consistent with an earlier tree, while comparison/auditing can detect inconsistent views and rollback-like behavior. This is evidence for a design pattern, not proof that a Merkle root alone solves Nexo continuity. citeturn0search3

DynamoDB documents that point-in-time recovery restores table data to a selected historical point and creates a new table; some operational/security settings must be configured separately after restore. This demonstrates why restored data cannot automatically be treated as the complete current control state. citeturn0search0turn0search1

NIST SP 800-57 discusses recovery of keying material and the need to preserve integrity/authentication capability across key recovery. This supports treating recovery of trust material as a distinct protected process rather than ordinary data restoration. citeturn0search48

in-toto provides a concrete provenance pattern in which signed layouts and signed link metadata form a verifiable chain of authorized steps. It is useful evidence for chained provenance, but it does not itself establish Nexo's replay-state authority semantics. citeturn0search10

## Core finding

A backup is a historical state, not automatically the current authoritative state.

RESTORED_STATE != CURRENT_AUTHORITY

Likewise:

VALID_SNAPSHOT != NON_ROLLBACK

A cryptographically valid snapshot can still be old.

## Primary rollback attack

Before failure:

REPLAY_GENERATION = 100
EFFECT(E) = CONSUMED

Backup captures generation 100.

Later:

REPLAY_GENERATION = 107
EFFECT(E) = CONSUMED
AUTHORITY_EPOCH = 12

System fails and restores backup 100.

If restored state is accepted as current:

EFFECT(E) = UNUSED

The system can re-admit E.

Therefore restoration must first establish whether the restored state is still on the current authoritative history.

## Candidate continuity anchor

A security-critical replay domain should have a protected monotonic continuity record containing, at minimum as claim-required:

- DOMAIN_ID
- CONTINUITY_GENERATION
- AUTHORITY_EPOCH
- REPLAY_STATE_GENERATION
- CURRENT_STATE_ROOT / authenticated digest
- PREVIOUS_ANCHOR_REFERENCE
- ANCHOR_SCHEMA_VERSION
- POLICY / CONTRACT VERSION
- RESOURCE/STATE INCARNATION where applicable
- KEY/TRUST GENERATION where applicable
- issuance/commit metadata
- invalidation generation

The anchor is not itself authority. It is evidence that the current state belongs to a particular continuity lineage.

## Anti-rollback rule

Candidate protected transition:

RESTORE_REQUEST
→ RESTORE_QUARANTINED
→ verify snapshot integrity
→ verify anchor lineage
→ compare protected generation against external/current anchor
→ reconcile missing post-snapshot decisions
→ establish new recovery generation
→ only then release protected authority.

If current continuity cannot be established:

UNKNOWN / HOLD / QUARANTINED

not automatic recovery.

## Why a local monotonic counter is insufficient

A counter stored only inside the restored dataset rolls back with the dataset.

Example:

counter=107 → backup → counter=108 → crash → restore backup → counter=107

The restored system cannot distinguish “legitimate current 107” from “rolled back 107” using that counter alone.

Therefore the anti-rollback anchor must have an independence property from the state being restored, or the restoration procedure must obtain authoritative evidence from outside the restored state.

## External anchor options

Candidate families:

1. Independent durable authority — stores latest generation/root; strongest direct anti-rollback boundary, but introduces dependency and availability cost.
2. Append-only transparency/log service — later state proves consistency with prior committed state; can detect rollback/fork if clients compare views; service becomes a trust/evidence dependency.
3. Quorum of independent anchors — can tolerate some anchor failures; independence must be failure-domain based.
4. Hardware-backed monotonic primitive — potentially strong local anti-rollback; hardware replacement/migration become dependencies.
5. External operator/governance checkpoint — can establish a recovery decision; not automatically machine-verifiable safety evidence.

No option is selected yet.

## Fork attack

Rollback is not the only danger.

A compromised or divergent replica may produce:

ANCHOR_A: generation 108 → root X
ANCHOR_B: generation 108 → root Y

Both can be internally consistent.

This is a fork, not simple rollback.

RFC 9162's transparency model shows why append-only consistency and cross-observer consistency are separate properties. citeturn0search3

Candidate rule:

CONFLICTING_CURRENT_ANCHORS => QUARANTINED

No majority number is assumed safe without a failure-domain/independence model.

## Snapshot integrity vs snapshot freshness

Separate:

- SNAPSHOT_INTEGRITY: bytes/data match authenticated snapshot.
- SNAPSHOT_PROVENANCE: origin and generation are known.
- SNAPSHOT_FRESHNESS: sufficiently current for the claim.
- SNAPSHOT_CONTINUITY: state extends accepted lineage.
- SNAPSHOT_AUTHORITY: Z1 decides whether restored state may authorize transitions.

Candidate invariant:

SNAPSHOT_INTEGRITY != SNAPSHOT_CONTINUITY != CURRENT_AUTHORITY

## Recovery generation

After a valid restore, simply reusing the old generation is dangerous.

Candidate:

RESTORE_GENERATION > PRE_RESTORE_GENERATION

RECOVERY_GENERATION must be bound to restored state, recovery owner, reconciliation result and new authority epoch where required.

This prevents a recovered instance from presenting itself as the pre-failure instance.

## Resource incarnation

Restoring a resource or state store can create a new incarnation even when its logical identifier is unchanged.

RESOURCE_ID_same + RESOURCE_INCARNATION_different => OLD_LINEAGE_STALE

## Missing post-snapshot events

Suppose backup includes E1–E100 and the live system reached E130.

Restoring E100 does not prove E101–E130 never happened.

MISSING_FROM_SNAPSHOT != NEVER_HAPPENED

Recovery must reconcile the post-snapshot interval or quarantine affected effects.

A missing local record cannot prove the external world lacks the effect.

## Authority epoch rollover

A safe recovery should normally establish a new protected authority epoch rather than simply revive the old one.

Candidate sequence:

OLD_EPOCH
→ RECOVERY_FENCE
→ reconcile
→ NEW_AUTHORITY_EPOCH
→ re-admit only after current context is rebuilt.

This blocks old lineage from becoming current merely because a snapshot was restored.

## Attack matrix

| Attack | Unsafe inference | Required response |
|---|---|---|
| old backup restore | valid snapshot => current | external/current anchor validation |
| local counter rollback | counter valid => current | independent continuity evidence |
| forked replica | internally valid => globally current | cross-anchor consistency check |
| missing post-snapshot events | absent locally => never happened | reconciliation/UNKNOWN |
| restored resource | same ID => same resource | new incarnation |
| old authority epoch | snapshot contains authority => authority still valid | recovery fence + new epoch |
| stale key state | key metadata restored => current trust | key-generation validation |
| old policy | signed policy => current policy | current policy anchor |
| log rollback | valid old root => current root | consistency/current-anchor check |
| backup metadata omission | data restored => security state restored | explicit recovery checklist |
| split-brain recovery | two valid states => choose one silently | QUARANTINED / governance |
| external effect omission | no local record => no external effect | external reconciliation |
